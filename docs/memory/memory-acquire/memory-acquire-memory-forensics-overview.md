# 内存取证总览

<a id="section-1"></a>

## 一、概述

如果你接手的是一台**还在运行**的机器，或者一台刚刚被人手动关机的机器，那么有一个问题磁盘永远回答不了：**这台机器在被关掉的那一刻，到底在做什么？**

磁盘上的一切都是过去式。文件时间戳、注册表 hive、事件日志、缓存文件，全是已经落盘的状态快照。

内存是现在进行式。它装着正在跑的进程、当前的网络连接、已解密但从未写回磁盘的会话密钥、正在编辑但从未保存的文档。这部分数据在磁盘上不是"被删除了"，而是**从未被写入过**。

所以会出现这种局面：磁盘分析做了好几天，最后才发现委托方真正想问的那个问题，答案在设备断电那刻就已经灭失了。而且不可补。

内存取证卡在整个流程的最前端，属于**采集**环节，而且是唯一一个"顺序错了就全盘皆输"的环节。它的上游依赖很少：目标机还开着、有权限、有外接存储，三条就行。下游则支撑起后面所有分析工作——进程与注入检测、网络连接归属、凭据与密钥提取，全都只能从内存镜像起步。

按流程位置排：现场在线判断 → 内存采集 → 同期状态快照 → 磁盘镜像 → 离线分析。内存排在磁盘前面不是习惯问题，是证据属性决定的。

这块能碰到的工件分四种载体：

| 载体 | 典型工件 | 关键字段 |
|---|---|---|
| 物理内存镜像 | `DigiForensics-mem.raw`、`lime`/`avml` 输出、`.vmem` 快照、`hiberfil.sys` | 物理地址空间、页表、符号表 |
| 运行态结构 | `EPROCESS`、`_RTL_USER_PROCESS_PARAMETERS`、内核池 tag | 进程链、命令行、模块基址 |
| 活动会话状态 | `tasklist` / `netstat -ano` / `route print` / `arp -a` 的现场输出 | PID、协议、本地与远端地址 |
| 分析配置 | Volatility Profile 的 PDB GUID 与 build 号、ISF 符号文件 | `NtBuildLab`、符号版本号 |

最后一类最容易被忽略：**没有匹配的符号，内存镜像里的一切都读不出来**。所以 Profile 机制不是工具细节，是内存分析的准入条件。

据此能回答的是这些：某时刻有哪些进程在运行、进程之间是什么父子关系、有哪些已建立或已关闭的 TCP 连接、哪些内存区域是私有可执行页（注入特征）、会话密钥与解密后内容是否驻留在内存、攻击者程序是否只存在于内存中而磁盘无痕。

回答不了的是这些：用户在采集区间内具体看到或输入了什么、精确到秒的行为先后顺序、设备在采集区间之前已经发生过的行为、以及任何在采集时被换出到 `pagefile.sys` 而未随镜像采集的内容。内存镜像代表的是一个**区间**而不是一个时刻，这一点决定了所有结论的表述方式。

往下读之前，先确认你已经具备：磁盘镜像与只读挂载的基本能力（否则拿到的 `.raw` 无法进入分析环境，见[镜像制作](../../imaging/imaging-acquire/imaging-acquire-disk-imaging-and-evidence-preservation.md)）、哈希与保管链的常规意识（见[证据保管链](../../fundamentals/fundamentals-chain/fundamentals-chain-chain-of-custody-and-authorization.md)）、以及最低限度的体系结构知识——理解进程、虚拟地址空间、内核与用户态的分界。

磁盘侧还一无所获时，先看[取证工件地图](../../computer/computer-registry-log/computer-registry-log-windows-artifact-map.md)建立对照。

## 二、核心原理

<a id="section-3"></a>

### 2.1 易失性等级（Order of Volatility）

这是内存取证最核心的操作原则。证据的易失性从高到低有严格顺序，采集必须按此顺序进行——不是"按方便程度"，而是"按丢失速度"。

| 顺序 | 证据类型 | 丢失机制 | 典型采集手段 |
|---|---|---|---|
| **1** | **CPU 寄存器 / 指令指针 / 栈顶** | 纳秒~微秒 | 硬件调试器（JTAG/FPGA）、崩溃转储寄存器段 |
| **2** | **运行时表（内核池、活动结构）** | 秒级 | 内核内存镜像、NetScan 类扫描 |
| **3** | **网络连接、DNS 缓存、路由表、ARP 缓存** | 秒~分钟 | 内核池扫描、NDIS 状态 |
| **4** | **运行中的进程与线程上下文** | 秒~分钟 | 进程/线程枚举与转储 |
| **5** | **用户态数据：会话、句柄表、剪贴板、编辑缓冲区** | 分钟~小时 | 进程转储、`dumpfiles` |
| **6** | **文件系统缓存（页缓存、文件数据）** | 分钟~小时 | `filescan` + `dumpfiles`、pagefile |
| **7** | **磁盘上的持久化数据** | 永久 | 常规磁盘取证 |

> **为什么"寄存器排第一"**：如果攻击者正在执行，CPU 寄存器里的指令指针指向他此刻正在跑的代码——这是最直接的活动证据。但软件采集拿不到寄存器（只有崩溃转储或硬件方法才行），因此软件采集实际上从第 2 层开始，第 1 层是理论上的最优起点。这一点在报告里要写明，不能声称"已采集寄存器"。

**顺序的实际含义**：应结合易失性安排采集顺序。复制数 TB 的磁盘可能需要数小时，期间内存内容可能变化或消失。

先关机再采内存**同样错**。关机瞬间内存归零。

正确顺序：**保持开机 → 采集内存 → 然后才是磁盘**。

<a id="section-4"></a>

### 2.2 内存为什么"一采就变"

内存不是只读介质。采集过程本身就在改写它：

```
采集开始 ──┬─ 加载驱动/内核模块（本身要占内存）
            ├─ 分配目标缓冲区（挤占被采集的数据）
            ├─ 把内存页 pin 住（防止被换出）
            └─ 目标系统继续运行（网络包、内核日志仍在变化）
```

这导致一个根本性事实：**内存镜像的物理地址不再等于采集瞬间的物理地址。** 你在镜像里看到的"偏移 `0x1a3e5000` 的字节"，是采集期间某一刻被复制过去的，它之前的内容已经被覆盖。

对取证的直接影响分三块。

不能做的，是对内存镜像做严格的"逐字节解释"。要求毫秒级时序精度的场景（函数入口追踪之类）直接排除。

可以放心做的是枚举类操作——进程、网络、句柄，加上字符串搜索、注入特征检测。这些只需要"某个时刻存在过"，不要求"精确在那一刻"。

还有一条容易写反：**报告中不应把内存的时序精度说成比磁盘更高**。恰恰相反，内存证据的时序精度受采集耗时影响，**远低于**磁盘上的 FILETIME 精度。

<a id="section-5"></a>

### 2.3 采集的时机窗口

内存证据的"窗口"由三件事共同决定：**采集耗时**（32 GB 内存、软件采集、USB 3.0 写入通常 5–15 分钟；1 TB 服务器用 PCIe FPGA 可缩短到 1–2 分钟）、**采集期间的系统活动**（采集越慢，"镜像代表哪一刻"越模糊）、**数据自然衰减**（部分内容会被换出、被覆盖）。

这三项里，采集耗时最容易被低估。它同时决定两件事：镜像有多长，以及"镜像代表哪一刻"这个问题有多模糊。

> **必须在报告中记录的三个时间点**：`采集开始时间`（到秒）、`采集结束时间`（到秒）、`时区与 UTC 偏移`。只有开始时间是不够的——"内存镜像代表的时间"是一个区间 [开始, 结束]，不是时刻。

<a id="section-6"></a>

### 2.4 手机与小内存设备：现实约束

| 约束 | 桌面 Windows | 手机 |
|---|---|---|
| 物理内存大小 | 8–128 GB | 4–12 GB |
| 采集权限 | 管理员即可 | **必须 root**（iOS 需越狱） |
| 加密存储 | BitLocker（可尝试） | 文件级加密 + SELinux 双层 |
| 采集通道 | USB 3.0 / PCIe | USB 2.0/3.0 慢，或直接推送到云 |
| 电池 | 不考虑 | **边充边采，否则中途关机全丢** |
| 热管理 | 一般无问题 | 长时间采集易过热降频甚至强制重启 |

**最要命的一条是"必须先解锁"**：现代手机在重启后需要用户输入口令才能解密 data 分区。已锁定状态下 `/data` 里的内容在内存中是不可读的密文。

所以对已关机的手机做内存取证基本无意义——内存里没有你想要的明文。

## 三、操作步骤

<a id="section-9"></a>

### 3.1 第 1 步：现场评估——先判断"还有没有内存可采"

在动手之前必须先回答一个问题：这台机器现在是开着的吗？内存里还有东西吗？

```powershell
# Windows：确认系统在线（不要执行任何会关闭服务的命令）
Get-Date
query session

# 确认内存总量，这决定后续存储规划
systeminfo | Select-String 'Total Physical Memory','Available Physical Memory'
```

```bash
# Linux：确认在线 + 内存总量
uptime
free -h

# Android（已连接 adb）
adb shell getprop ro.product.model
adb shell cat /proc/meminfo | head -3
adb shell "su -c 'getenforce'"     # SELinux 状态，决定能否采
```

> ⚠️ **这一步的顺序绝不能颠倒**。很多处置流程写成"先断开网络防止数据外传"——**但如果执行方式是物理断电，内存就没了**。正确做法是：先评估能否就地采集内存，不具备条件才考虑断电，并在报告中写明"因设备条件限制未采集内存，该部分证据已灭失"。

<a id="section-10"></a>

### 3.2 第 2 步：准备存储与工具

```bash
# 内存镜像大小 ≈ 物理内存大小（或略大，取决于采集工具与地址空间）
# 必须按"镜像大小"规划，且分析阶段还要额外空间

# 检查目标机可用的外部存储
df -h /media/usb

# 记录采集工具自身的哈希（关键，报告要用）
sha256sum /media/usb/avml ./winpmem.exe ./lime.ko
md5sum    /media/usb/avml                      # 部分旧工具只提供 MD5
```

**必须提前准备的三件事**：

| 准备项 | 理由 |
|---|---|
| **工具版本与哈希** | 同名工具不同版本行为可能不同，报告需可复现 |
| **充足的外部存储** | 镜像等于物理内存大小；32 GB 内存的机器要准备 ≥ 32 GB 空间 |
| **确认目标机未被污染** | 采集前不要在目标机上安装其他取证工具，会往内存里写入新东西 |

<a id="section-11"></a>

### 3.3 第 3 步：按易失性顺序采集

具体命令见[第 02 篇](memory-acquire-memory-acquisition-methods.md)。此处只给出**顺序骨架**：

```
[第一层] 崩溃转储中的寄存器段（若有）或硬件方式
[第二层] 内存镜像 ← 软件采样的起点
          Windows: winpmem / DumpIt
          Linux:   AVML（优先）或 LiME
          macOS:   osxpmem（需 kext 签名/SIP 放行）
          Android: 需 root
[第三层] 当前状态快照，与内存镜像同时进行
          进程列表、netstat -ano、路由表、ARP 表、已打开文件
[第四层] 关机 / 拆卸后按标准流程做磁盘镜像
```

> **"同时进行"是难点**：内存镜像采集要花几分钟，期间系统状态一直在变。务实在内存采集开始的那一刻，把进程列表和 netstat 输出也记下来——这两样是"采集开始时刻"的快照，比镜像本身更接近真实起点。

<a id="section-12"></a>

### 3.4 第 4 步：立即固定与验证

```bash
# 采集后立刻算哈希（不要做任何其他操作）
sha256sum DigiForensics-mem.raw | tee acquisition-hash.txt

# 记录镜像大小，应与物理内存大小接近
wc -c < DigiForensics-mem.raw
ls -lh DigiForensics-mem.raw

# 记录采集工具哈希
sha256sum /media/usb/avml | tee tool-hash.txt
```

**验证清单**：

| 验证对象 | 方法 | 通过标准 |
|---|---|---|
| 镜像完整性 | 哈希已记录且后续复算一致 | 两次 SHA-256 相同 |
| 镜像大小 | `wc -c < 镜像` | 接近物理内存大小（偏差 < 5%） |
| 镜像可解析 | `windows.info` / `linux.pslist` | 能输出结构化结果 |
| 时间可信 | 采集开始/结束时间已记录 | 含时区 |

<a id="section-13"></a>

### 3.5 第 5 步：分析产出必须可复现

```bash
# 每条分析命令都要留痕（这是报告的"可复现性"要求）
mkdir -p /evidence/analysis/{commands,output}
cd /evidence/analysis

# 用 -l 参数把 Volatility 自己的日志也留下来
python3 vol.py -f /evidence/DigiForensics-mem.raw -l vol.log -q windows.info
```

## 四、常见陷阱

内存取证最贵的错误不是"没采到"，而是**采到了却把它当成了它不是的东西**。

把一个跨越 12 分钟的混合体当成某一时刻的快照。把"没找到"当成"没发生"。把工具自己写进内存的痕迹当成攻击者留下的痕迹。

这三种错每一种都无法在事后弥补。下面按采集决策、时间归属、现场执行、结论表述四组展开。

<a id="section-15"></a>

### 4.1 采集时机与现场决策

<a id="section-16"></a>

#### 陷阱 1：先断电或先拔网线，再考虑能不能采内存 ★

**现象**：处置流程第一步写"切断网络连接防止数据外传"，执行人直接拔了网线或按了电源键，之后才想起内存还没采。

**原因**：拔网线本身不损失内存，但很多执行人把"断电"和"断网"当成同一个动作——而**物理断电的那一刻，全部易失性证据归零**。

3.1 的评估步骤把"确认系统在线"放在第一条，原因就在这里：它决定了后续所有动作的可行性。一旦机器已经关了，2.1 那张易失性等级表里的第 1 到第 6 层就同时不可采。

而这部分证据在磁盘上**根本没有对应物**，不是"之后再想办法"的问题。

**影响**：不可补。这类损失在报告里只能写成一句"因处置顺序不当，易失性证据灭失"。

而委托方往往正是冲着"这台机器关机前在做什么"来的。结论链条在最关键的一环直接断开，后面对磁盘的完整分析无法回答这个问题。

**核查**：现场第一判断永远是"能否就地采集内存"，而不是"如何快速断电止损"。

若确实不具备采集条件（无外接存储、无采集工具、无权限），再断电，并在报告的证据灭失说明里明确列出"未采集的易失性层"。

需要防止数据外传时，优先用防火墙规则或交换机端口隔离，**保持主机运行**。

<a id="section-17"></a>

#### 陷阱 2：先做磁盘镜像，再想办法采内存

**现象**：按"先把整盘拷走"的直觉流程执行，1 TB NVMe 的全盘镜像跑了 4 小时，之后才尝试内存采集。

**原因**：这不是经验问题，是顺序定义问题。2.1 已经写明易失性等级是**按丢失速度排序**的，磁盘位于第 7 层、永久保留。

把第 7 层放在第 2 层前面，等于用永久保存的东西去换即将消失的东西。

4 小时足够让加密会话密钥被换出、fileless payload 被下一段内存覆盖、TCP 连接的池结构被复用。

**影响**：采到内存并不意味着"还能采到刚才的内存"。

采集时刻已经过去 4 小时，内存镜像反映的是 4 小时后的系统状态，与委托方关心的时刻之间存在一个无法弥补的偏移。

而报告里不会出现任何提示——数据看起来一样完整。

**核查**：顺序固定为 保持开机 → 采集内存 → 采集与之同时刻的状态快照 → 之后才是磁盘镜像。

若现场有多个设备且资源有限，也按"易失性高的先采"排序，而不是按"好采的先采"排序。

<a id="section-18"></a>

#### 陷阱 3：把"先关机保留现场"当成保守做法

**现象**：为了"保护现场不被破坏"，选择关机后把设备带回实验室再分析。

**原因**：关机对磁盘确实是最保守的动作，但内存是易失性介质。

**关机不是保护，是销毁。**

实验室里的内存取证能力再强，也无法作用于一块已经断电的内存条。传统取证直觉（保持现场原状、最小扰动）在易失性证据上与实际操作要求正好相反。

**影响**：设备带回去，硬盘分析做得再细，也答不出"当时有没有未落盘的解密内容"这类问题。

委托方往往在此时才发现真正想要的答案已经不可能获得，而现场也无法补采。

**核查**：把"最小扰动"这个词在内存场景下重新定义为"**在采完之前最小化对系统的改变**"。

2.2 列出的采集本身造成的改写——加载驱动、分配缓冲、pin 页、目标系统继续运行——消不掉，只能靠缩短采集耗时和如实记录采集区间来约束。

关机回避不了这个事实。

<a id="section-19"></a>

#### 陷阱 4：在目标机上安装取证工具

**现象**：把采集程序复制到目标机 `C:\Tools\` 下再运行，或用包管理器现场安装依赖。

**原因**：安装动作会真实写入内存：可执行文件的映像被加载、依赖库被映射、解压过程在用户态堆上留下内容。2.5 和 3.2 都把"工具全部放在外接介质"列为准备项，但执行时往往因为"外接盘路径太长/权限受限"而临时拷贝。更隐蔽的是安装日志本身会成为后续分析里的可疑痕迹。

**影响**：污染是**双向**的。

它既可能让 05 篇的注入检测找到你自己加载的模块，也可能让攻击者留下的同类型痕迹被淹没在你制造的噪声里，无法区分。

后一种情况更严重——报告里出现了真实证据，但因为无法自证来源而被质疑。

**核查**：工具、脚本、依赖全部预置在外接介质并**从外接路径直接执行**，目标机不落任何文件。

执行后用 `windows.dlllist` 或模块列表对比采集起止两次的差异，把工具自身引入的模块变化在报告里显式声明。

<a id="section-20"></a>

### 4.2 时间归属与镜像属性

<a id="section-21"></a>

#### 陷阱 5：把内存镜像当成"关机时刻"或"某一瞬间"的证据

**现象**：报告里写"镜像显示 10:29:52 时系统处于该状态"，并以此推断攻击者在该时刻执行了某操作。

**原因**：2.2 已经指出采集过程本身在持续改写内存，采集工具是**按块复制**的，不同物理地址被复制到镜像里的时刻不同，整个镜像是一个时间区间内的混合体。案例第 3 步记录的 12 分 37 秒不是流程冗余，而是这个镜像的固有属性。`windows.info` 输出的 SystemTime 只是"某一页里读到的系统时间"，它落在采集区间内是**预期结果**，不是"镜像就是这一时刻"的证明。

**影响**：这是本板块最高频的错误时间推理。一旦用单一时刻做因果论证（"因此攻击发生在 10:29:52"），整条时间线就建立在一个镜像并不具备的精度上。

反向的误判同样存在：用镜像里"没有"某事件否定该事件，也是把区间当成了点。

**核查**：报告的表述单元是区间。写"本次镜像代表 [10:23:41, 10:36:18] 区间内的系统状态，采集耗时 12 分 37 秒"。

需要精确到秒的因果关系，改用采集开始时刻同步抓取的 `tasklist`、`netstat` 等状态快照，或回到磁盘上的时间戳证据上论证。

<a id="section-22"></a>

#### 陷阱 6：用内存证据做"谁先谁后"的因果推断

**现象**：在内存镜像里发现 A 进程创建时间比 B 早 3 秒，据此认定 A 是 B 的父进程触发者，或认定某注入发生在某网络请求之前。

**原因**：磁盘上的 FILETIME 是内核维护的 100 纳秒级时间戳，写入后不可变；内存中的时间字段同样由内核更新，但它**可能被后续写入覆盖，也可能来自被换出又换入的页**。更重要的是，2.2 明确"不能对内存镜像做严格的逐字节解释"。把内存的时间字段当成与磁盘 FILETIME 同等的精度来源，是把两种证据的可靠性混为一谈。

**影响**：因果顺序一旦被写进结论，后续的时间线重建、行为归因全部建立在这个薄弱基础上。

攻击者只需让某个无关进程在镜像里呈现一个更早的创建时间，就能让整段归因被反转。而分析员很难自查出来。

**核查**：内存中的时间字段只用于**粗排序**和**相关性提示**，正式的时间线必须回到磁盘侧的 FILETIME、Prefetch、事件日志等稳定工件上。

确需从内存建立顺序时，用结构本身的关系（PEB 中的父子链、句柄指向的创建顺序）而不是时间戳差值。

<a id="section-23"></a>

#### 陷阱 7：只记录采集开始时间

**现象**：保管链里只有一行"2026-03-14 10:23 采集内存"，没有结束时间。

**原因**：2.3 的引文块已经写明，内存证据的窗口由采集耗时、期间系统活动、数据自然衰减三件事共同决定，而 3.4 的验证清单把"采集开始/结束时间已记录"列为通过标准。只记开始时间，看起来记录了时间，实际上把 12 分钟的空白留在了保管链里。

**影响**：交叉验证时无法自证。当对方问"你说镜像里 10:29 有连接，那连接是在采集之前还是之后建立的"，唯一的回答是"不知道"。

起止时间是区间结论的必要条件。缺了它，前面所有基于区间的表述都失去支撑。

**核查**：起止时间都记，精确到秒，格式带时区偏移（如 `2026-03-14T10:23:41+08:00`），并且与 `windows.info` 的 SystemTime 交叉验证。

三者在同一条时间线上才对得上。

<a id="section-24"></a>

#### 陷阱 8：用镜像大小偏差判断"镜像完整"

**现象**：镜像 33889966080 字节、物理内存 31.7 GB，认为"大小吻合，镜像完整"，然后在报告里写"已获得目标机全部物理内存"。

**原因**：大小接近物理内存只是**必要条件**，不是充分条件。

采集工具可能因地址范围限制或工具自身选项只采了部分区域。采集过程也可能静默中断（设备掉线、目标机异常、存储写满）而没有报错——此时文件仍然是那个大小，只是尾部或某些区间是零填充。

案例里的 5% 偏差标准只用于排除"明显采少了"这一类问题。

**影响**：把"大小对得上"当成"内容完整"，会让后续所有分析建立在一个未经验证的前提上。

更麻烦的是这类缺页往往**不表现为解析错误**——Volatility 仍能输出进程列表，只是少了一些结构，分析员没有任何提示。

**核查**：完整性验证要靠多条独立证据：`windows.info` 能正确解析并给出符号信息、核心结构（EPROCESS 链表、模块链表）能完整遍历、镜像内无异常大段全零区域、采集日志无错误行。

把这些写成验证清单逐项记录，而不是只记一个大小数字。

<a id="section-25"></a>

### 4.3 现场执行与设备约束

<a id="section-26"></a>

#### 陷阱 9：把采集工具运行后残留的自身痕迹当成可疑证据

**现象**：`windows.inject` 或模块列表里出现采集驱动、`cmdline` 里出现采集工具路径，分析员将其列为"可疑注入"或"可疑命令行"。

**原因**：采集工具本身是一个加载到内核或用户态的普通组件，它会出现在模块枚举、进程列表、命令行里，**这是采集动作的直接产物，不是被检系统的行为**。2.2 列出的"加载驱动/内核模块"就是这件事。同一类问题还包括采集过程中被 UAC 弹窗、EDR 拦截后产生的额外进程。

**影响**：这类假阳性的杀伤力在于它最"像真的"——命令行里带路径、模块里有未签名驱动，形态与真实的恶意行为高度相似。

报告里若把它和真实发现混列，真实发现的可信度会被一起拉低。

**核查**：采集前先记录工具的文件路径、哈希、进程名、驱动名，**在分析阶段把它们列入已知白名单并在报告中显式声明**。

任何以工具路径、工具哈希为特征的命中，一律先排除再判断。

反过来，采集结束后立即检查是否被安全软件响应并记录。这也是现场状态的一部分。

<a id="section-27"></a>

#### 陷阱 10：手机边采边掉电，或采到一半过热重启

**现象**：4 GB 内存的手机通过 USB 采集，写到 3 GB 时电量耗尽关机，进程已终止但文件未收尾。

**原因**：2.4 的约束表把"电池"和"热管理"单独列出，因为它们是手机端与桌面端最实质的差别。

USB 通道带宽远低于内存容量所需，边充边采是硬要求而不是建议。同时长时间高负载采集会让 SoC 温度上升，触发降频甚至保护性重启。

**这两件事都不会给出明显的错误提示**——掉电后的文件大小可能看起来正常。

**影响**：得到一个大小正常但尾部缺失的镜像，而且**没有第二台设备可以重采**。

手机通常只有一次机会。现场记录里若没写"设备已重启/已掉电"，后续没人会怀疑这个镜像。

**核查**：采集期间接充电器并持续监控电量与温度。

采集进程在设备上留一份日志，采集完成后立即验证镜像尾部与整体大小。

把"设备全程未重启、未断电"作为一条明确的现场事实写进报告。无法保证时必须写明"采集期间设备重启，该镜像不完整"。

<a id="section-28"></a>

#### 陷阱 11：对已锁定或已重启的设备做内存取证并期待明文

**现象**：手机重启后处于锁屏状态，对 `/data` 做了内存采集，然后在镜像里搜索聊天记录或文件内容，一无所获。

**原因**：现代 Android 与 iOS 使用文件级加密，密钥由硬件安全模块（SE/TEE）派生，**系统解锁前 data 分区在内存里是密文**。

内存中确实存在这些数据，但呈现形式是不可读的密文块。用明文关键字搜索不会有任何命中。

这一点在 2.4 的最后一段已经点明。

**影响**：容易滑向两个坏结论之一——"设备上没有聊天记录"（错误，磁盘上有，只是没解开），或者为了解密而绕过锁屏（超出授权范围）。

前者是错误定性，后者是取证违规。

**核查**：先判断设备状态再决定内存取证是否有意义。

已关机、已重启、已锁定的设备，内存取证的价值主要在易失性网络与运行态信息。明文内容应转向磁盘侧的解锁后镜像。

**任何情况下都不要为取证目的绕过锁屏**。

<a id="section-29"></a>

### 4.4 结论表述与阴性发现

<a id="section-30"></a>

#### 陷阱 12：把"内存里没找到"写成"没发生"

**现象**：在镜像里没有搜到某个关键词、某段 shellcode、某个外部 IP，报告写"未发现入侵痕迹"或"该主机未与该 IP 通信"。

**原因**：内存内容会被换出、被覆盖、被释放后复用。2.5 与表格最后几行都指向同一件事：某段数据"不在内存里"和"从未在内存里存在过"是两个完全不同的命题，而内存镜像无法区分它们。

未命中可能是因为数据在采集前已换出到 pagefile（而 pagefile 没有随镜像一起采集）、因为被新的分配覆盖、或者因为采集期间该页正好在被改写。

**影响**：这是一个方向性错误，会把"能力不足"包装成"结论干净"。

委托方据此排除嫌疑或停止调查，而真实证据可能就在同一台机器的 `pagefile.sys` 或被覆盖前的其他镜像里。

**核查**：阴性发现必须写成限定范围的陈述：「在 [10:23:41, 10:36:18] 区间的物理内存镜像内、以关键字 X 和模式 Y 进行的全文搜索中，未发现命中」。

未覆盖的范围要一并列出来——未采集的 `pagefile.sys` / `swapfile.sys`、未包含的设备空闲页、采集期间已被覆盖的数据。

**不限定范围的"未发现"不能写进报告。**

<a id="section-31"></a>

#### 陷阱 13：用内存里的渲染缓存推断"用户看到了什么"

**现象**：在镜像里找到浏览器或文档编辑器的渲染缓存、GDI 对象、窗口标题，报告写"用户当时正在查看该页面"。

**原因**：这些是**历史痕迹**。窗口标题可能属于已经关闭或最小化的窗口，渲染缓存可能来自几天前的一次会话，内容也可能只是模板或预取。

2.2 的"可以放心做的"清单里明确枚举能力：内存适合"某个时刻存在过"的枚举，**不适合重建用户感知**。

而"用户看到了什么"是一个感知层命题，需要输入设备证据支撑。

**影响**：这类推断在案件里常被直接当作主观状态的证据，用来支持"知情""故意"等定性。

一旦对方调取显示器录像或登录会话记录与之矛盾，整份报告的可信度都会受影响。

**核查**：内存里的界面痕迹只能表述为"该进程曾创建过标题为 X 的窗口""该进程存在与 Y 内容相关的渲染数据"。

要确认用户实际看到的内容，必须配合截屏/录屏、窗口活动记录、键盘输入痕迹等其他证据。

<a id="section-32"></a>

#### 陷阱 14：只按桌面工作站的经验评估小内存设备

**现象**：对一台 4 GB 内存的手机做内存取证时，仍按"拿到 4 GB 就能覆盖系统全部热点数据"的预期安排分析范围。

**原因**：2.4 的对照表里，桌面是 8–128 GB、手机是 4–12 GB，这不是数量级差异，是**容量预算差异**。

手机系统进程占掉大部分，文件缓存很小，**被换出的比例远高于工作站**；同时它对采集通道、权限（必须 root）、加密状态的要求又高得多。

同样的分析工具、同样的关键字，在两类产品上的命中率可以差一个量级。

**影响**：预期错位会直接导致阴性结论被过度解读。

命中率低本该是"该设备不适用此方法"，却容易被写成"未发现"，进而被当作排除性证据。

**核查**：动手前先做容量与状态评估（3.1 的 `cat /proc/meminfo`、`getenforce`），并在报告里写明**该设备的内存容量、采集方式、未覆盖范围**。

对内存较小的设备，磁盘侧的工件（应用私有目录、日志、数据库）应作为主战场，内存分析定位为补充。

## 五、案例示例

<a id="section-34"></a>

### 5.1 活动会话判定与 winpmem 在线采集闭环

**场景**

查获一台 Windows 11 工作站（32 GB RAM，1 TB NVMe），处于开机运行状态，屏幕显示用户在浏览器查看某个网站。委托方要回答两个问题：该机当时是否运行了未登记的远程控制软件，以及是否与某外部 IP 发生过数据外传。

这类委托里，**内存镜像的证据属性是否成立**是全案的地基。镜像不可信，后面所有分析都是废纸。

屏幕亮着不代表人还活跃——屏保、未锁屏、远程会话断开都可能留下亮屏。所以第一步不是插采集盘，而是判定会话状态。

**处置过程**

先确认会话是否活动，决定能不能在线采：

```powershell
PS> query session
会话 ID 用户名           ID 状态                    类型
------- ----------------- -- ------------------------ ------
1        foren\zhangsan    1 Disc                     连接到控制台
```

状态为 `Disc`（已连接控制台）且非 `Disc2`/`Down`，内存可采。决策：**不关机，就地采集。**

再核容量余量，避免采集盘被写满导致转储截断：

```powershell
PS> systeminfo | Select-String 'Total Physical Memory','Available Physical Memory'
Total Physical Memory:  31.7 GB
Available Physical Memory:  18.2 GB
```

准备 64 GB 外接 SSD（1.8 倍余量），并对采集工具本身取哈希：

```powershell
PS> Get-FileHash -Algorithm SHA256 E:\kit\winpmem.exe
Algorithm  Hash                                                             Path
---------  ----                                                             ----
SHA256     A3F1...(完整值抄录至 evidence/custody.txt)                        E:\kit\winpmem.exe
```

采集的同时必须记录起止时刻与当时的系统快照。快照的意义是**冻结"采集从哪一刻开始"的系统状态**，事后无法回溯：

```powershell
# 起始时刻，精确到秒并带时区
PS> Get-Date -Format "yyyy-MM-ddTHH:mm:ssK"
2026-03-14T10:23:41+08:00

PS> tasklist /fo csv > E:\evidence\proclist-at-start.csv
PS> netstat -ano      > E:\evidence\
etstat-at-start.txt
PS> route print      > E:\evidence\route-at-start.txt
PS> arp -a           > E:\evidence\arp-at-start.txt

PS> E:\kit\winpmem.exe -o E:\evidence\DigiForensics-mem.raw
[INFO] Setting acquisition mode 2
[INFO] Dumping Range 0x0000000000000000 - 0x000000007FFFFFFF
...
# 结束时刻
PS> Get-Date -Format "yyyy-MM-ddTHH:mm:ssK"
2026-03-14T10:36:18+08:00
```

**采集耗时 12 分 37 秒。**

这个数字要写进报告正文，不是附录。

立即哈希与体积核验：

```powershell
PS> Get-FileHash -Algorithm SHA256 E:\evidence\DigiForensics-mem.raw
PS> (Get-Item E:\evidence\DigiForensics-mem.raw).Length
33889966080          # ≈ 31.55 GiB
```

最后用镜像自身的系统时间确认可用性：

```bash
$ python3 vol.py -f /evidence/DigiForensics-mem.raw -q windows.info
Kernel Base   0xffff802000000000
SystemTime    2026-03-14 10:29:52
NtBuildLab    22631.3155.amd64fre.ni_release.241203-1105
```

**结论**

`SystemTime = 10:29:52` 落在 `[10:23:41, 10:36:18]` 区间内，说明镜像内部的时钟与采集窗口自洽。

镜像可采、可信、时间归属正确。

| 结论 | 支撑证据 | 强度 |
|---|---|---|
| 采集合法、镜像完整 | 起止时间戳、工具哈希、镜像哈希、体积与物理内存吻合 | 强 |
| 镜像代表 10:23:41–10:36:18 区间 | 起止记录 + `windows.info` 的 SystemTime 落区间内 | 强 |
| 采集期间目标机处于活动会话 | `query session` + 起始 `tasklist` | 强 |
| 全部结论只对该 12 分 37 秒区间成立 | 采集耗时 | 作为局限明示 |

**不能证明的**：镜像不能代表采集开始前的任何状态。

屏幕显示的网站页面在 `10:23` 之前就可能已被关闭。内存里能查到浏览痕迹，只说明采集窗口内数据尚在，不能直接回推到"事发时刻用户正在看"。

**误判对照**

最容易出的错，是把 `SystemTime` 落在采集区间内当成"镜像完整"的**充分**条件，然后据此认为镜像内容全部可信。

判据要分两层。

体积吻合是必要条件。本次 `33889966080` 字节 ≈ 31.55 GiB，与 `Total Physical Memory: 31.7 GB` 差 0.5%，属正常换算差（GiB/GB 口径 + 保留区），可以接受。

若体积明显偏小（比如只有 28 GB），即使 `SystemTime` 正常，也说明转储被中途截断，后半段物理页缺失。

这时候 `windows.pstree` 之类跨区域解析的插件会静默少列进程——"没列出的进程"绝不能读成"没运行的进程"。

第二层是转储模式本身。日志里的 `Setting acquisition mode 2` 是 SSD 模式（跳过不可读页与缓存一致性不保证的区域）。

如果目标机是机械盘、模式为 0（全量）而实际仍有大量坏道，winpmem 会跳过这些区域并在日志里出现 skip 记录。日志必须随镜像一并留存。

按错误判据走的代价是：报告里写"镜像完整、内容可信"，而对方律师在复核时发现某进程恰好落在被跳过的物理区，你的"未发现该进程"就被推翻。

正确做法是把工具日志与镜像绑定交付，并显式写出"本结论适用区间为 10:23:41–10:36:18，超出区间未作断言"。

<a id="section-35"></a>

### 5.2 采集工具自身痕迹的误报排除

**场景**

同一台工作站的委托推进到第二步：委托方提供了一份人员名单，要求确认该机上是否运行过名单之外的远程控制软件。初步 `windows.pslist` 结果里出现了 4 个不在业务软件清单内的进程，其中 `mstsc.exe`、`wpr.exe` 两个名字引起怀疑。

这是内存取证里最高频的误报来源——**取证工具自己会在内存里留下完整痕迹**，而且痕迹形态与被调查对象高度相似。

**处置过程**

第一步是把采集期间在目标机上执行过的动作列全，这是排除的基线：

```bash
# 取采集工具的进程名与 PID，注意采集工具自身也是进程
$ python3 vol.py -f /evidence/DigiForensics-mem.raw -q windows.pslist \
    --output csv | head -1
PID   PPID  ImageFileName  Offset(V)  Threads  Handles  SessionId  WOW64  CreateTime  ExitTime  File output

# 提取采集中可能产生进程的工具名
$ python3 vol.py -f /evidence/DigiForensics-mem.raw -q windows.pslist --pid 6312
Process: winpmem.exe
CreateTime: 2026-03-14 10:23:39+08:00
ExitTime:   2026-03-14 10:36:31+08:00
```

关键点：把这些进程的 `CreateTime` 与采集起始时刻 `10:23:41` 做比对。凡是**创建时间落在采集窗口内**的进程，都属于"由本次取证动作派生"，不能作为被调查行为的证据。

第二步对每个可疑进程核对命令行与父进程：

```bash
$ python3 vol.py -f /evidence/DigiForensics-mem.raw -q windows.cmdline --pid 4420
Process: mstsc.exe
Args:    mstsc /v:digi-internal-01
$ python3 vol.py -f /evidence/DigiForensics-mem.raw -q windows.pstree --pid 4420
PID    Name           PPID  Threads  CreateTime
4420   mstsc.exe      1804  9        2026-03-14 09:12:03
1804   explorer.exe    1440  64       2026-03-14 08:02:11
```

`mstsc.exe` 的 `CreateTime = 09:12:03` 远早于采集窗口，父进程是 `explorer.exe`（由用户会话 `explorer` 直接拉起），命令行目标是内网主机名。

这是**用户在桌面双击打开的正常远程桌面连接**，不是远控软件。

第三步核对远程控制类痕迹的真正指标：外联地址、出向连接方向、以及是否有对应的服务与自启动项。

真正的远控软件会同时具备这四者。单独一个进程名说明不了任何问题。

**结论**

4 个"可疑"进程全部排除，理由分两类：

| 进程 | 排除依据 | 结论 |
|---|---|---|
| `winpmem.exe` | CreateTime 10:23:39 落在采集窗口内，取证动作派生 | 非证据 |
| `wpr.exe` | 同上，采集期间为验证转储完整性启动 | 非证据 |
| `mstsc.exe` | 09:12 启动、父进程 explorer、内网主机名 | 正常业务 |
| `svchost.exe`(异常变体) | 见 5.1，路径与基线一致 | 系统进程 |

**能证明的**：在采集窗口内，未发现与人员名单外的远程控制软件相符的四要素组合（外联地址 + 出向连接 + 服务 + 自启动项）。

**不能证明的**：不能证明"该机从未安装过远控软件"。

已卸载的软件不会出现在内存里。已退出但未卸载的进程也可能因对象池残留而被 `filescan` 命中，却无实际网络活动。

**误判对照**

这里最典型的错误判据是只看进程名，不看 `CreateTime` 与 `PPID`。

`wpr.exe`（Windows Performance Recorder）在名字上完全不像取证工具，但它出现在内存里时，最常见的情况是取证方或运维方自己启动的 Windows 性能记录器。

判据是三个字段的组合：

1. `CreateTime` 是否落在 `[10:23:41, 10:36:18]` 内或紧邻之前数秒内
2. `PPID` 是否为采集工具自身或 PowerShell / cmd
3. 目标地址是内网主机名还是公网 IP

按只看进程名的判据走，代价是报告里出现"发现未登记进程 wpr.exe"的指控性表述，而对方只需提供一份运维工单即可完全推翻，且会连带质疑整份报告的严谨性。

反向的误判同样存在：把 `CreateTime` 落在采集窗口内的进程一律排除。

如果某可疑程序在采集开始前的 30 秒自行重启（自愈机制），它的 `CreateTime` 会落在窗口内，但**它的父进程和已建立的 socket 都在窗口之前**。

所以正确的排除判据不是单一时间戳，而是"时间戳 + 父进程 + 网络连接"三者同时指向取证动作，才算排除。

<a id="section-36"></a>

### 5.3 反例：渲染缓存不等于用户看到了什么

**场景**

委托方补充了一条线索：声称在事发时段，某用户在远程桌面会话中打开了带有敏感文件名的文档。内存里确实检索到了该文件名，但检索位置不在任何文档应用的缓存目录，而在浏览器与图形子系统的渲染缓存里。

这是**内存取证里最容易写出过度结论的一类场景**：检索命中只能证明"这些字节在某时刻存在于物理内存"，不能证明"用户看到了"。

**处置过程**

第一步，定位命中位置与所在进程：

```bash
$ python3 vol.py -f /evidence/DigiForensics-mem.raw -q windows.vadinfo --pid 2204
PIDProcessName: 2204  chrome.exe
...
```

第二步，检索命中的原始上下文，判断字节的性质：

```bash
$ python3 vol.py -f /evidence/DigiForensics-mem.raw -q windows.vadyarascan \
    --pid 2204 --pattern "季度财务" --dump
Offset    VAD      Protection  Content
0x1a3f4000  0x...   RW-         ...季度财务报表_final_v3.xlsx...
```

命中上下文前后是完整的文件名，且所在 VAD 的保护属性为 `RW-`（可读写堆），不是 `RX-`（可执行），也不是页缓存。

第三步，交叉验证是否有打开动作的对应痕迹。真正"打开并显示"会留下文件句柄与内存映射记录：

```bash
# 该进程是否持有 .xlsx 相关句柄
$ python3 vol.py -f /evidence/DigiForensics-mem.raw -q windows.handles \
    --pid 2204 | grep -i -E '\.xlsx|excel'
# 无输出
```

第四步，统计该字节的副本分布，判断是否只是被索引过：

```bash
$ python3 vol.py -f /evidence/DigiForensics-mem.raw -q windows.vadyarascan \
    --pid 2204 --pattern "季度财务" | wc -l
3
```

**结论**

3 处副本全部位于 `chrome.exe` 的堆内存，且该进程**未持有任何 .xlsx 句柄**。

**能证明的**：该字符串在采集时刻存在于 `chrome.exe` 进程内存中，可能来自网页内容、下载文件名、或表单历史。

**不能证明的**：不能证明用户在界面上"看到"了文档内容。不能证明文档在屏幕上渲染过。不能证明用户知晓该文件存在。

渲染缓存与堆残留只说明数据曾经流经该进程。

**误判对照**

这个案例里最容易得出的错误结论是："内存检索命中文件名 + 命中次数 3 次 + 命中位置在图形相关区域 → 用户打开并观看了该文档"。

正确判据有三条，缺一不可：

1. **进程归属** —— 命中必须在**文档或阅读类进程**（`excel.exe`、`wps.exe`、`AcroRd32.exe`）内，在浏览器进程内只能说明"浏览器经手过这个字符串"
2. **句柄证据** —— 打开行为会在 `windows.handles` 留下 `.xlsx` 的 File 句柄，且常伴随 `windows.malfind` 的私有可执行区命中
3. **副本分布** —— 真正渲染过的内容会在多个进程的 VAD 中出现副本（含 GDI/DirectWrite 侧）；只在单一堆区出现 3 次，符合"解析过但未显示"

本次三条判据**全部不满足**：进程归属错（浏览器非文档程序）、句柄证据缺失、副本不跨进程。

按错误判据走，报告会把"浏览器缓存里有个文件名"写成"用户打开了财务文件并已阅知"。这是把检索命中当成行为证明，**属于结论强度超出证据强度的典型越界**。

阴性发现的范围限定：本次仅在 `DigiForensics-mem.raw` 采集窗口（10:23:41–10:36:18）内、对 `chrome.exe`(PID 2204) 的 VAD 空间做了字符串检索，未发现文档程序的对应句柄。

**未覆盖范围**包括：已终止进程的 VAD、其他用户会话的进程、以及页面数据被浏览器加密存储后未以明文驻留的部分。

## 七、命令速查

```bash
# ===== 1. 环境准备（Ubuntu 分析机）=====
sudo apt install -y python3-venv python3-pip
python3 -m venv ~/vol3env && source ~/vol3env/bin/activate
pip install volatility3
python3 vol.py --version

# ===== 2. 采集前：目标机状态记录 =====
# Windows: Get-Date / tasklist /fo csv / netstat /ano / route print / arp -a
# Linux:    uptime ; free -h ; ps auxf ; ss -tulnp ; ip route
# 全部重定向到证据目录，见 3.1

# ===== 3. 采集（详见第 02 篇）=====
# Linux:   ./avml /media/usb/DigiForensics-mem.raw
# Windows: winpmem.exe -o E:\evidence\DigiForensics-mem.raw

# ===== 4. 采集后：立即哈希与验证 =====
sha256sum DigiForensics-mem.raw | tee acquisition-hash.txt
wc -c < DigiForensics-mem.raw
sha256sum /media/usb/avml      | tee tool-hash.txt

# ===== 5. 确认镜像可解析 =====
python3 vol.py -f DigiForensics-mem.raw -q windows.info
python3 vol.py -f DigiForensics-mem.raw -q linux.pslist
```

```powershell
# ===== Windows 侧采集完整序列 =====
# 1) 起始时间
Get-Date -Format "yyyy-MM-ddTHH:mm:ssK" | Tee-Object E:\evidence\acq-start.txt

# 2) 起始状态快照
tasklist /fo csv > E:\evidence\proclist-at-start.csv
netstat /ano     > E:\evidence\
etstat-at-start.txt
route print     > E:\evidence\route-at-start.txt

# 3) 采集内存（务必输出到外接盘）
E:\kit\winpmem.exe -o E:\evidence\DigiForensics-mem.raw

# 4) 结束时间
Get-Date -Format "yyyy-MM-ddTHH:mm:ssK" | Tee-Object E:\evidence\acq-end.txt

# 5) 立即哈希并记入保管链
$h = (Get-FileHash -Algorithm SHA256 E:\evidence\DigiForensics-mem.raw).Hash
"{0} SHA256={1} size={2} tool=winpmem" -f (Get-Date -Format o), $h, `
```
