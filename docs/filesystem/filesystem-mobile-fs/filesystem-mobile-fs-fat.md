# FAT 系列结构

> **技术复核提示（2026-10-11）**：本修订版已按 FAT 规范修正 BPB 与目录项关键偏移、exFAT 时间语义及部分代码；文内假设案例、删除恢复流程和演示脚本仍需使用 FAT12、FAT16、FAT32 与 exFAT 测试镜像逐一验证。未完成复现前，不应将其输出当作检材事实或司法鉴定结论。

<a id="section-1"></a>

## 一、概述

1980 年的 FAT 至今还在服役。它对取证教学的价值恰恰来自"简单"——整卷的簇分配表**摊平成一张线性数组**放在卷首，元数据只有一张 FAT 表加定长目录项，**没有间接层**。

这个结构意味着任何一步解析结果都能用十六进制手工复核。工具报出一个文件名，你能翻到那个目录项的字节；工具说文件从簇 41230 开始，你能顺着 FAT 表数过去。这种可复核性是 NTFS 的 B-tree 与 MFT 给不了的——那些结构一旦工具解析失败，你很难手工兜底。

代价同样明显。目录项定长 32 字节，**删除只改 1 个字节**（首字符改成 `0xE5`），但也因此没有权限、没有日志、没有时间线精细度。**FAT 不记录"谁在什么时候删掉了什么"**，它只记录"这 32 字节现在是这个状态"。这句话决定了大量结论的边界。

这一层在**分析环节的格式解析阶段**，与 NTFS、ext4、APFS 那几篇平级，入口在[文件系统取证总览](../filesystem-ntfs/filesystem-ntfs-filesystem-forensics-overview.md)的第 3 步——那一篇的第 4 组"不能挂载时的新兴文件系统"就是为 FAT 与 F2FS 这类准备的。

FAT 的实际出现频率可能超出很多人的预期：U 盘 / 移动硬盘 / SD 卡（FAT32 或 exFAT）、行车记录仪与相机、软盘与工业控制器（FAT12/FAT16），以及**几乎每台现代 PC 都有的 EFI 系统分区**。

最后一项值得单独提醒，因为它在实务中最容易被忽略：`bootx64.efi`、`grubx64.efi` 都存放在 ESP 分区里，分析启动项篡改或 UEFI 引导劫持时核心目标是 ESP，而不是系统盘。这类案件的取证目标根本不在 NTFS 卷上。

上游依赖卷层解析。第五章案例里那个"簇大小是 64 KB 而不是假设的 4 KB"的发现，本质上就是这一步没做好会导致后面全错位。下游支撑两个方向：已删除文件的恢复与内容提取（这里是核心），以及把提取结果送去做内容类型识别（见[文件头与文件签名](../filesystem-ntfs/filesystem-ntfs-file-headers-and-signatures.md)）。

落到具体证据上：

- `DigiForensics.dd` 的分区起始扇区 2048 —— raw 单分区镜像。**所有偏移都要加这个基址**，第五章案例里 `fsstat -o 2048` 与 `dd bs=512 skip=2048` 就是在做这件事
- **exFAT 主引导记录** —— 签名 `EXFAT   ` 在偏移 3，参数区 `0x40`–`0x6F`：`PartitionOffset` / `VolumeLength` / `FatOffset` / `FatLength` / `ClusterHeapOffset` / `ClusterCount` / `RootDirectoryCluster`。**exFAT 没有标准 BPB**，这一点与 FAT32/FAT16 根本不同
- **FAT 表** —— 本身就是簇链，无需解析指针。第 5 步遍历集群链与 `blkls` 抽未分配空间都靠它
- **32 字节目录项** —— 删除只改首字符为 `0xE5`。`0xE5` 之外的首字符（`0x05`、`0x0E`、`0x0F`、`0x20`）各有特殊含义，第五章案例里数出"首字符为 `0x05` 的正常项 186 个"，**扫目录项时把这批正常项误当删除项是最常见的误报源**
- **exFAT 目录项集** —— 一个文件 = `0x85` 文件项 + 1 个 `0xC0` 流扩展项 + 1–17 个 `0xC1` 文件名项。六种类型码的项长度都是 32 字节，遍历时固定按 32 字节步进，长名靠多个 `0xC1` 项拼接而非靠变长项
- **`SetChecksum`** —— `0x85` 项 `0x02`–`0x03`，16 位滚动校验，遍历项集全部字节并**跳过主项那两个字节本身**，每字节右旋 1 位后累加取模 `0x10000`。exFAT 没有 FAT/VFAT LFN 的 `0x0D` 短名校验和，不可套用
- **DOS 时间戳** —— FAT32 的时间只有 2 秒精度，且**存的是本地时间、没有时区偏移字段**
- **exFAT 的 4 字节本地日期时间位域** —— 配 `0x14`–`0x18` 的 10 毫秒增量与时区偏移字段，这是 exFAT 相对 FAT32 的一个实质性改进
- ESP 分区里的 `bootx64.efi` / `grubx64.efi` —— 引导链相关的具体文件名

走完这一层能判断的是这些：BPB 每个字段该填什么（而不是照抄模板）、FAT 表怎么手工遍历、删除项怎么判定且不误报、exFAT 的项集怎么按正确的步长遍历，以及为什么 exFAT 上删除文件的长名能完整恢复而 FAT32 上不能。

最后一条差异是最有价值的对比：exFAT 直接存 255 字符 UTF-16 名，删除只清 InUse 位（`0x85`→`0x05`），长文件名与内容定位信息都还在；FAT/VFAT 删除通常会把关联目录项首字节标为 `0xE5`，长文件名字符区域可能残留，但能否恢复取决于项目重用情况及配对校验。第五章案例里三个视频的长名全部恢复，**FAT32/VFAT 也可能留下可恢复的 LFN 残留，但元数据组织方式和恢复条件与 exFAT 不同**。

有几件事不归这一层管：**文件被删后内容是否可恢复**，取决于簇链有没有被覆盖，**簇链状态必须逐个查**，不能从"已删除"直接推出"可恢复"；**是谁删的、什么时候删的**，**FAT 不记录删除动作的时刻**，目录项只存最后修改时间，这是格式的硬限制而不是工具问题；**大文件的碎片重组**，无碎片管理意味着大文件必然碎片化，重组逻辑在第三章步骤 3，但**跨越非连续簇的读取必然更慢也更容易出错**；**加密卷的内容**见[BitLocker 全卷加密取证](../../crypto/crypto-volume/crypto-volume-bitlocker.md)。

往下读之前需要**扇区、簇、偏移量**这三个概念的准确理解——全程在"字节偏移 = 基址 + 相对偏移"上计算，第五章那个 64 KB 簇的发现就是基址与簇大小算错的后果。另外需要十六进制分析能力：BPB 每个字段的偏移与长度都要自己核（2.2 那节明确说"偏移必须逐字段核对"）。

**建议动手手工解析一个 FAT 目录项**。挑一个小 U 盘，用 `xxd` 找到一个文件名，然后自己按 2.4 那张位域表把创建/修改/访问时间三个字段解出来。这个练习做完，2.6 那张 exFAT 类型码表你就再也不会记混——它的六个类型码（`0x81`/`0x82`/`0x83`/`0x85`/`0xC0`/`0xC1`）记住靠的是见过，不是背出来的。

## 二、核心原理

<a id="section-3"></a>

### 2.1 三个变体：差异只在每条簇记录的位宽

| 特性                | **FAT12**      | **FAT16**         | **FAT32**                            |
| ----------------- | -------------- | ----------------- | ------------------------------------ |
| FAT 表项位宽 / 实际簇数范围 | 12 位 / 小于 4085 | 16 位 / 4085～65524 | FAT 表项存储为 32 位（有效位为 28 位）/ 不小于 65525 |
| 卷上限 / 单文件上限       | 32 MB / 32 MB  | 2 GB / 32 MB      | 2 TB / 4 GB−1                        |
| 根目录               | **卷首定长区域，无簇链** | **卷首定长区域**        | **普通簇链**（`root_cluster`）             |

**判别不能看"表里写着什么"，要看实际簇数**：由 BPB 的总扇区数与 FAT 长度算出真实簇数再对照上表。**边界效应**：在总容量相同的条件下，簇越大，实际簇数越少，16 GB U 盘用 4 KB 簇时已逼近 FAT16 上限，因此大容量 FAT32 卷在实践中改用 8/16/64 KB 簇。看到"标称 FAT32 的 U 盘"必须实测簇大小，不能假设 4 KB。

<a id="section-4"></a>

### 2.2 BPB：偏移必须逐字段核对

```text
公共 BPB（字节偏移 / 长度）：
0x0B / 2  BPB_BytsPerSec      每扇区字节数
0x0D / 1  BPB_SecPerClus      每簇扇区数
0x0E / 2  BPB_RsvdSecCnt      保留扇区数
0x10 / 1  BPB_NumFATs        FAT 数量
0x11 / 2  BPB_RootEntCnt      FAT12/16 定长根目录项数（FAT32 = 0）
0x13 / 2  BPB_TotSec16        总扇区数 16 位字段
0x16 / 2  BPB_FATSz16         FAT12/16 每 FAT 扇区数（FAT32 = 0）
0x1C / 4  BPB_HiddSec         隐藏扇区数
0x20 / 4  BPB_TotSec32        总扇区数 32 位字段
FAT32 扩展 BPB：
0x24 / 4  BPB_FATSz32         每 FAT 扇区数
0x28 / 2  BPB_ExtFlags        FAT 镜像及活动 FAT 选择标志
0x2C / 4  BPB_RootClus        根目录起始簇号
0x30 / 2  BPB_FSInfo          FSInfo 扇区号
0x32 / 2  BPB_BkBootSec       备份引导扇区号
0x43 / 4  BS_VolID           卷序列号
0x52 / 8  BS_FilSysType      "FAT32   " 提示文本（不能单独用于判别变体）
FAT12/16 扩展引导扇区：
0x24 / 1  BS_DrvNum; 0x26 / 1  BS_BootSig
0x27 / 4  BS_VolID; 0x36 / 8  BS_FilSysType

RootDirSectors = ceil(BPB_RootEntCnt × 32 / BPB_BytsPerSec)
FATSz = BPB_FATSz16（非 0 时）否则 BPB_FATSz32
DataSec = TotSec − (BPB_RsvdSecCnt + BPB_NumFATs × FATSz + RootDirSectors)
CountOfClusters = floor(DataSec / BPB_SecPerClus)
簇号分类必须结合 CountOfClusters、BPB 布局及一致性检查；不以文件系统类型提示文本替代。
```

> **卷序列号是报告中的卷标识**，与 NTFS Volume Serial、APFS Volume UUID 地位相同。结论必须写成"卷序列号 3A7F-91C2 的 FAT32 分区"，而不是"某个 U 盘"。FAT32 的卷序列号在 `0x43`，FAT12/16 在 `0x27`——同一工具读不同变体时不要记混偏移。

<a id="section-5"></a>

### 2.3 FAT 表：一张摊平的簇链数组

破案时最常问的一句话是"这个文件从哪开始、被分到哪些簇"。答案就在这张表里——**它是重建 FAT 已分配文件簇链的核心数据结构**。

每簇一个表项，**分配簇的表项可为下一个簇号或 EOC/坏簇等保留标记**（簇 0、1 保留）。

以 FAT16 为例：簇 0/1 保留；文件 A 占簇 2→4（表项 `0004`/`0005`），簇 3 已释放（表项 `0000`），**这正是文件 A 被缩短或删除后的现场**；簇 6 表项 `FFF7` 是坏簇；文件 B 占簇 8，表项 `FFF8` 表示链尾。

**表项值语义**：`0x0000` = 空闲，链在这里断了（通常因为文件已删除、簇被释放）；坏簇标记 = 物理损坏，原有内容不可恢复（FAT12 `0xFF7` / FAT16 `0xFFF7` / FAT32 `0x0FFFFFF7`，是单一值）；≥ EOC 阈值 = 链尾，文件正常结束（FAT16 `0xFFF8` / FAT32 `0x0FFFFFF8`，是范围值）；其余 = 下一个簇号，即碎片化跳转。

> **关键结论**：`0x0000` 表示该簇表项处于空闲状态，不能单独据此确认某个文件曾被删除。删除会把链上所有表项清零，但目录项里的起始簇还在；若原文件连续，按起始簇顺序读取即可重建，这正是 FAT 删除文件仍可完整恢复的技术原因。反过来，碎片化文件删除后通常无法仅依靠已释放的 FAT 簇链完整重建，因为无从得知第 2 块在哪。要区分坏簇与 EOC，只能判断"是否等于坏簇标记值"，因为 EOC 是范围而坏簇是单一值。

<a id="section-6"></a>

### 2.4 32 字节目录项：删除只改 1 个字节

```
FAT32    0x00 8 8.3主名★ 0x08 3 8.3扩展名★ 0x0B 1 属性★ 0x0C 1 NT 大小写标志；0x0D 1 创建时间的 10ms 单位计数
         0x0E 2 创建时间 0x10 2 创建日期 0x12 2 最后访问日期 0x14 2 起始簇高位★
         0x16 2 最后写入时间 0x18 2 最后写入日期 0x1A 2 起始簇低位★ 0x1C 4 文件大小★
FAT12/16 目录项沿用同样的 32 字节布局；0x14 的起始簇高 16 位字段仅 FAT32 使用。
         0x0D 1 创建时间的 10ms 单位计数；0x1A 2 起始簇低 16 位；0x1C 4 文件大小★
★ 属性位：0x0F=LFN项 0x10=目录 0x20=存档 0x08=卷标   ★ NT保留位：0x08=基名小写 0x10=扩展名小写
```

> **最容易记错的一点**：文件大小在 FAT32 位于 `0x1C`、起始簇在 `0x14`(高)+`0x1A`(低)；但在 FAT12/16 文件大小同样在 `0x1C`、起始簇低 16 位同样在 `0x1A`（不使用 FAT32 的高位字段）。 用错偏移会读出完全错误的"大小"，进而导致提取长度和哈希全部错误。

**FAT 删除的一般结果**：相应短目录项与 LFN 项被标为空闲（目录项首字节常改为 `0xE5`），已分配簇的 FAT 表项可能被释放。具体残留随实现及后续重用情况变化，不能仅凭空闲表项断言删除行为。

以主名 `CONTRACT` + 扩展名 `DOC` 为例（`0x00`–`0x07` = `43 4F 4E 54 52 41 43 54`，`0x08`–`0x0A` = `20 44 4F 43`，`0x0B` 属性 = `20`），删除后变为 `E5 4F 4E 54 52 41 43 54  20 44 4F 43  20`——**仅首字节被覆盖，其余 31 字节原样保留**。

> **关键结论**：删除后文件名（除首字符）、属性、三个时间戳、起始簇号、文件大小全部还在，丢失的只有一个首字符和后续簇链。由此推出三件事：① 通常无法从该短目录项直接得到已覆盖的首字符，须结合 LFN 残留和内容等其他线索推定；② 起始簇与大小还在，若原文件连续则内容可完整提取；③ 碎片化文件无法恢复。另外，目录项的文件大小恒为 0，判断目录要看属性字节的 `0x10` 位。
> **首字节三态（务必做对）**：`0x00` = 从未使用，**后续全空闲，应立即停止该目录扫描**；`0xE5` = 已删除，**FAT 短目录项中的删除/空闲标记**；`0x05` = 实际文件名首字节为 `0xE5`，**是合法文件名字符**，误判会产生大量假删除项。

<a id="section-7"></a>

### 2.5 LFN：长文件名机制

8.3 无法表达长名。VFAT（Windows 95）为此引入 LFN：长名被切成**每段 13 个字符**的多个 32 字节目录项，**存放于对应短目录项之前**，**按段号倒序排列**（段号最小的一段最靠近短目录项）。

```
"Very Long Filename.docx" 共 23 个 UTF-16 字符，占 2 个 LFN 项与 1 个短名项（磁盘顺序为段2→段1→短项）：
 [0x42 "ename.docx"+终止/填充][0x01 "Very Long Fil"][短项 VERYLO~1.DOC 属性≠0x0F]
  ★ 读取时必须先按「首字节 & 0x3F」升序排序，顺序反了就会拼出乱码
```

**LFN 项结构**：`0x00` 序号码（最高位 `0x40` 标记"最后一段"，低 6 位是段序号）；`0x01`–`0x0A` 名称字符 1–5；`0x0B` 属性恒为 `0x0F`，这是识别 LFN 项的唯一判据；`0x0C` 类型恒为 0；`0x0D` 短名 8.3 字段的校验和；`0x0E`–`0x19` 名称字符 6–11；`0x1A`–`0x1B` FstClusLO 恒为 0（LFN 项不存簇号）；`0x1C`–`0x1F` 名称字符 12–13。每段 5+6+2 = 13 个 UTF-16LE 字符。

**三个必须记准的规则**：（1）`0x40` 是独立的"最后一段"标志位，与序号是"或"关系，上限 255 字符需 20 段（`0x54`…`0x41`，因 20×13=260≥255）；常见错误是把 `0x40` 当序号的一部分去减算，导致拼接顺序反了或长度算错，正确取法是 `序号 = 字节 & 0x3F`。（2）LFN 项的首字节同样会被置 `0xE5`：删除时整个条目组全部被置 0xE5\*\*，因此已删除文件的短名通常还在（除首字符），长名项序号首字节被覆盖，但其余字符可能残留，不能一概判为无法恢复——恢复工具给出的 `DOCUME~1.DOC` 是短名，不是原名。（3）`0x0D` 校验和把长名与短名绑定，算法为右循环移位 `r = (((r&1)<<7) + (r>>1) + 字节) & 0xFF`，对 8.3 的 11 字节（含首字符）依次执行；校验和值只存放在 LFN 项的 `0x0D`，短名项 `0x0D` 是创建时间的百分之一秒计数，不能当作 LFN 校验和，从短名项取校验和会永远得到"不匹配"。

> **取证上的关键点**：目录项可能被后续写入**部分覆盖**，出现"孤立的 LFN 段"。严谨的解析器必须做校验和验证，绝不能把无主的 LFN 段拼成一个看起来很像真的文件名；校验和不匹配时只报 8.3 短名。 此外，已删除项的首字符 `0xE5` 参与了原校验和的计算，校验删除项时必须**枚举候选首字符**，不能直接用 `0xE5` 比对。

<a id="section-8"></a>

### 2.6 exFAT：目录项集与三个关键改动

exFAT 是 2008 年微软为突破 FAT32 的 4 GB 单文件限制而设计的，**不是 FAT32 的向后兼容扩展**。

它没有标准 BPB，参数位于主引导记录（各 8 字节）：`0x40` PartitionOffset、`0x48` VolumeLength、`0x50` FatOffset、`0x58` FatLength、`0x60` ClusterHeapOffset、`0x68` ClusterCount、`0x6C` RootDirectoryCluster；`0x70` VolumeSerialNumber（4 字节）。

**根目录本身也是普通簇链**，起点即 `RootDirectoryCluster`，其内混排着位图项、大小写转换表项、卷标项和文件项集。

**三个关键改动**：文件名——FAT32 需 LFN 项配 8.3 短名，exFAT 直接存 255 字符 UTF-16 名，删除后长名仍完整保留；簇链——FAT32 每簇一表项，exFAT 的 NoFatChain 让连续文件不占 FAT 表项，可按长度直接定位；**时间戳**——FAT32 是 DOS 格式（2 秒精度），exFAT 使用 4 字节本地日期时间位域，配 `0x14`–`0x18` 的 10 毫秒增量与时区偏移字段。

**目录项类型码**（识别错位全靠这张表；`EntryType` 的 bit7 = InUse、bit6 = Secondary、bit5 = Critical）：

| 类型码    | 项         | 长度 | 关键字段                                                                                                                                           |
| ------ | --------- | -- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `0x81` | 分配位图项     | 32 | `0x01` BitmapFlags、`0x14` FirstCluster、`0x18` DataLength                                                                                       |
| `0x82` | 大小写转换表项   | 32 | `0x04` 表校验和、`0x14`/`0x18`                                                                                                                      |
| `0x83` | 卷标项       | 32 | `0x01` 字符数、`0x02` UTF-16 卷标；未命名时类型码为 `0x03`                                                                                                    |
| `0x85` | **文件目录项** | 32 | `0x01` SecondaryCount(2–18)、`0x02` SetChecksum、`0x04` 属性、`0x08`/`0x0C`/`0x10` 三时间戳、`0x14`/`0x15` 创建与修改的 10ms 增量、`0x16`/`0x17`/`0x18` 三个 UTC 偏移 |
| `0xC0` | **流扩展项**  | 32 | `0x01` GeneralSecondaryFlags、`0x03` 名长度、`0x04` NameHash、`0x14` FirstCluster、`0x18` DataLength                                                  |
| `0xC1` | **文件名项**  | 32 | `0x02` 起 15 个 UTF-16 字符（每个 2 字节，共 30 字节）；255 字符长名需要 17 个该项                                                                                     |

> **混排规则**：一个文件 = `0x85` + 1 个 `0xC0` + 1–17 个 `0xC1`，**所有项一律 32 字节、按 32 字节步进**（`0xC1` 也是 32 字节：1 字节类型 + 1 字节标志 + 15 个 UTF-16 字符）。若误按 16 字节步进，项集会从第二个文件名项起整体错位，解析出的名字变成乱码且不会报错。流扩展项 `0x01` 字节的 bit0 = AllocationPossible、bit1 = NoFatChain（掩码 `0x02`）。
> **删除只清 InUse 位**（`0x85`→`0x05`），其余字段原样保留，因此 SD 卡上已删除的连续文件，长文件名与内容定位信息都还在——元数据保留得更完整，工具只是因此表现更好。代价是必须做项集校验：`SetChecksum`（`0x85` 的 `0x02`–`0x03`）是 16 位滚动校验，遍历项集全部字节、跳过主项 `0x02`–`0x03` 这两个字节本身，每字节右旋 1 位后累加并对 `0x10000` 取模。exFAT 没有 FAT/VFAT LFN 的 `0x0D` 短名校验和，不可套用该规则。但 exFAT 同样无权限、无日志、无时间线，目录项也不记录删除动作的时刻。

### 3.2 第 2 步：扫描目录项、判定删除、组装 LFN

```bash
fls -o 2048 -r -p /work/DigiForensics.dd > /evidence/fat-fls.txt && grep -ci deleted /evidence/fat-fls.txt
istat -o 2048 /work/DigiForensics.dd 460        # size 与三个时间戳
```

> FAT 只有三个时间戳（创建/修改/访问），精度 2 秒，且很多 FAT32 卷的创建时间不可用。**不要在 FAT 上构建秒级时间线。**

核心脚本（逐 32 字节项扫描，处理删除判定、LFN 校验与组装）：

```python
import struct
IMG = "/work/DigiForensics-fat.dd"
with open(IMG, "rb") as f: b = f.read(0x60)
SECTOR, SPF = struct.unpack_from("<H", b, 0x0B)[0], b[0x0D]
RES, NFAT, ROOTENT = struct.unpack_from("<H", b, 0x0E)[0], b[0x10], struct.unpack_from("<H", b, 0x11)[0]
FAT32 = struct.unpack_from("<H", b, 0x16)[0] == 0            # 每FAT扇区数(16位)为0才是FAT32
SEC = (struct.unpack_from("<I", b, 0x24)[0] if FAT32 else struct.unpack_from("<H", b, 0x16)[0]) # 每 FAT 扇区数：FAT32 在 0x24（4字节），FAT12/16 在 0x16（2字节）
ROOTCLUS = struct.unpack_from("<I", b, 0x2C)[0] if FAT32 else 0
CLUSTER, FATLEN = SECTOR * SPF, SEC * SECTOR
ROOT_SECT = ((ROOTENT * 32) + SECTOR - 1) // SECTOR        # FAT12/16 定长根目录占多少扇区
DATA_OFF = (RES + NFAT * SEC + ROOT_SECT) * SECTOR          # ★ 全部从 BPB 实测，不硬编码
U16, U32 = lambda x: struct.unpack("<H", x)[0], lambda x: struct.unpack("<I", x)[0]

def cksum(s11):                           # 8.3 字段 11 字节校验和（右循环移位）
    r = 0
    for b in s11: r = (((r & 1) << 7) + (r >> 1) + b) & 0xFF
    return r

def ok_lfn(segs, sfn):              # LFN 项 0x0D 存短名校验和；短名项 0x0D 是创建时间的细分计数字段
    want = segs[0][0x0D]
    if not all(x[0x0D] == want for x in segs):
        return False
    # 短名首字符：有效项在 0x20–0x7E；删除项该位被 0xE5 覆盖，故枚举 0x05/0x20/0xE5
    first = sfn[0] if sfn[0] != 0xE5 else 0x05
    cand = [first] if sfn[0] != 0xE5 else [0x05, 0xE5] + list(range(0x20, 0x7F))
    return any(cksum(bytes([x]) + sfn[1:11]) == want for x in cand)

def read_dir(root):                       # ★ FAT12/16 根目录是定长区；FAT32 必须沿簇链逐簇读
    if not FAT32: return open(IMG, "rb").read()[DATA_OFF - ROOT_SECT * SECTOR:DATA_OFF]
    fat, out, n = open(IMG, "rb").read(), b"", root
    while n >= 2 and n < 0x0FFFFFF8:
        off = DATA_OFF + (n - 2) * CLUSTER
        out += fat[off:off + CLUSTER]
        n = U32(fat[RES * SECTOR + 4 * n:RES * SECTOR + 4 * n + 4])
    return out

buf = read_dir(ROOTCLUS or 2)
lfn = []
for off in range(0, len(buf) - 31, 32):
    e = buf[off:off+32]; n0, attr = e[0], e[0x0B]
    if n0 == 0x00: break                       # 从未使用 → 后续全空闲
    if attr == 0x0F: lfn.append(e); continue   # 0x0F 才是 LFN 项
    name, st = None, "无LFN"
    if lfn and any(x[0] & 0x40 for x in lfn) and ok_lfn(lfn, e):
        segs = sorted(lfn, key=lambda x: x[0] & 0x3F)       # ★ 段号升序读取
        cs = b"".join(s[1:11] + s[0x0E:0x1A] + s[0x1C:0x20] for s in segs)   # ★ 5+6+2=13 字符，UTF-16LE 整段解码
        name, st = cs.decode("utf-16-le", "replace").split("\x00")[0], "校验通过"
    elif lfn: st = "校验失败→不采用长名"    # ★ 不可信的组只报短名
    base = e[0:8].decode("cp437", "replace").rstrip()          # ★ 8.3 主名 8 字节在 0x00–0x07
    ext = e[8:11].decode("cp437", "replace").rstrip()         # ★ 扩展名 3 字节在 0x08–0x0A
    nm = f"{base}.{ext}".strip(".") if ext else base
    clus = (U16(e[0x14:0x16]) << 16 | U16(e[0x1A:0x1C])) if FAT32 else U16(e[0x1A:0x1C])  # ★ 随变体
    sz = U32(e[0x1C:0x20]) if FAT32 else U32(e[0x1C:0x20])    # ★ 随变体
    print(f"{'[已删除]' if n0==0xE5 else '[有效]  '} 短名={nm:14s} 长名={name or '—':26s} {st} 起始簇={clus} 大小={sz}")
    lfn = []
```

**输出字段的用法**：短名是长名已删时唯一的名字来源；校验状态决定长名能否写入报告；起始簇是提取入口；大小是截断依据。`校验通过` 才可写入报告；`校验失败` 说明长名被部分覆盖，**只报 8.3 短名**；已删除项**只有短名**是正常现象。生产脚本还应记录**簇号 + 项内偏移**——这是文件在镜像中的精确坐标，可复核、可复现。

### 3.3 第 3 步：提取、按大小截断、簇链验证

```bash
icat -o 2048 /work/DigiForensics.dd 460 > /tmp/fat-extracted.bin
truncate -s 15360 /tmp/fat-extracted.bin   # ★ 按目录项记录的文件大小截断

```

> `truncate` 是保证哈希正确性的必要步骤，不能省。 不截断的文件包含同簇内后续残留的其他内容，**其哈希必然与原文件不同**（见 [10](../filesystem-unix/filesystem-unix-file-carving-and-signature-recovery.md) 关于证据效力的讨论）。**簇链手工验证**（独立于工具，直接证明链是否完整、是否碎片化、必须截断多少字节）：

```python
BAD, EOC = 0x0FFFFFF7, 0x0FFFFFF8      # FAT32 每项 4 字节；FAT16 2 字节；FAT12 需跨字节位级拆解
n, chain = START_CLUS, []
while True:
    chain.append(n)
    v = int.from_bytes(fat[4*n:4*n+4], "little")
    if v == 0: break                    # 空闲 → 链断裂（已删除或损坏）
    if v == BAD: print("坏簇：物理损坏"); break
    if v >= EOC: break                  # EOC → 链正常结束
    n = v
span = (len(chain) - 1) * CLUSTER
# span < FILE_SIZE → 碎片化，删除后 FAT 已释放，后续簇丢失；span > FILE_SIZE → 末尾残留必须截断
```

## 四、常见陷阱

本章按「格式识别 → 结构解析 → 取证语义 → 误报来源与结论表述」归组，每条给出：现象、为什么会误判、误判代价、正确做法。
★ 标记表示该操作会导致原始检材永久灭失或不可逆改变，执行前必须停下来确认。

<a id="section-15"></a>

### 4.1 格式识别

<a id="section-16"></a>

#### 陷阱 1：假设簇大小是 4 KB，全部偏移错位

**现象**：解析 64 GB 移动 U 盘，按 4 KB 簇计算数据区起始位置，读出的"文件内容"全是错位数据，判为"该文件已损坏"。

**原因**：簇大小 = 每扇区字节数 × 每簇扇区数，两者都必须从 BPB 实测（2.2）。而"FAT32 就是 4 KB 簇"是一个流传极广的默认假设——它在小容量卷上成立，在大容量卷上完全错误。2.1 的边界效应已经说明：**簇数随卷增大而减小（同样容量用更大的簇）**，16 GB 的 U 盘用 4 KB 簇就已逼近 FAT16 上限，因此大容量 FAT32 卷在实践中普遍改用 8/16/64 KB 簇。案例里那个 64 GB U 盘的簇大小正是 64 KB。

**影响**：**簇大小是所有偏移换算的基准**。基准错了，数据区起始、簇到字节的换算、簇链回放全部错位。

而这类错误的表现是"取出的内容看起来像垃圾"，很容易被误判为"数据已损坏"。一次错误会让人以为该文件的原始内容不可得，而实际上它完好地躺在盘上。

**核查**：**实测三个量并写入报告，不得假设**（3.1 已列出必测清单）：

```bash
dd if=/work/DigiForensics.dd of=/work/DigiForensics-fat.dd bs=512 skip=2048 status=none
xxd -s 0x0B -l 2 /work/DigiForensics-fat.dd    # 每扇区字节数
xxd -s 0x0D -l 1 /work/DigiForensics-fat.dd    # 每簇扇区数 ★ 簇大小 = 二者相乘
# 交叉验证（TSK 独立读同一组字段）
fsstat -o 2048 /work/DigiForensics.dd | grep -i 'cluster size'
# 案例输出：Cluster size: 65536   ← 64 KB，与手工计算一致 ✓
```

**必须实测并写入报告的量**：每扇区字节数、每簇扇区数、簇大小、保留扇区数、每 FAT 扇区数、根目录起始簇号。报告中出现"簇大小 X 字节（实测自 BPB 0x0B/0x0D）"这句话，是这类结论可复核的前提。

<a id="section-17"></a>

#### 陷阱 2：按卷标或型号字符串判变体

**现象**：U 盘标称为"FAT32"，于是按 FAT32 的偏移读卷序列号，读到的是垃圾值；或者把 exFAT 卷按 FAT32 解析，输出全是错误。

**原因**：**判别不能看"表里写着什么"，要看实际簇数**（2.1）。BPB 里确实有 `"FAT32   "` 这样的卷标字符串（`0x52`），但**它可以被随意写入而不改变实际结构**——格式化工具的兼容模式、部分相机的兼容性格式化都可能留下与实际布局不符的字符串。而 exFAT 在偏移 3 处有自己的文件系统标识 `"EXFAT   "`（`45 58 46 41 54 20 20 20`），**它不是 FAT 家族的一员，目录项结构完全不同**。

**影响**：把 exFAT 当 FAT32 解析，会沿用 FAT32 的短名项假设并试图按变长规则步进——而 文中列举的 exFAT 目录项长度均为 32 字节。步进一旦算错，后续所有项的解析全部错误，不只是当前项。这个错误在报告里表现为"扫描到大量异常条目"，很容易被归为"文件系统损坏"。

**核查**：**用结构特征判别，不用字符串**：

```bash
# 1) exFAT：偏移 3 处的文件系统标识
xxd -s 3 -l 8 /work/DigiForensics-usb.dd
# 00000003: 4558 4641 5420 2020  EXFAT ✓

# 2) FAT32：0x16 处 BPB_FATSz16（16 位）为 0 才成立，且 0x52 处为 "FAT32   "
xxd -s 0x16 -l 2 /work/DigiForensics-fat.dd        # FAT32 场景此值应为 0000
xxd -s 0x52 -l 8 /work/DigiForensics-fat.dd        # FAT12   " / FAT16   " / FAT32   "

# 3) FAT32 用 0x24 读每 FAT 扇区数（32 位字段）
#    FAT12/16 场景用 0x16（16 位字段）
```

**变体间必须切换的解析规则**（2.4 已逐字段列出）：每 FAT 扇区数的位置（`0x24` vs `0x16`）、卷序列号的位置（`0x43` vs `0x27`）、文件大小（均为 `0x1C`）、起始簇（`0x14`+`0x1A` vs 仅 `0x1A`）、FAT 表项宽度（4/2/1.5 字节）、根目录是否沿簇链。

<a id="section-18"></a>

### 4.2 结构解析

<a id="section-19"></a>

#### 陷阱 3：把 `0xE5` 首字节一律当删除标记，漏掉 `0x05` 合法首字符

**现象**：扫描目录项时，命中 186 个首字节为 `0x05` 的项，全部标记为"已删除"，报告里"已删除文件数"翻了几十倍。

**原因**：**首字节有三态**（2.4）：`0x00` = 从未使用、**后续全空闲应立即停止扫描**；`0xE5` = 已删除，**这是唯一的删除标记**；`0x05` = 实际文件名首字节是 `0xE5`（为避免与已删除项混淆而转义存储），是一个合法文件名字符。**`0x05` 与 `0xE5` 只差最高位**，而很多脚本写成 `if buf[off] & 0x80 or buf[off] == 0xE5` 或直接 `== 0xE5` 就遗漏了这一态——一个以 `0x05` 开头的真实文件因此被计入删除项。这类文件实际存在（早期某些软件生成的文件名）。

**影响**：**"已删除文件数"是一个会被引用的统计量**，虚高几十倍会让报告显得粗糙；而更实质的问题是**这些假删除项会挤占分析精力**，并且它们大多**没有可恢复的完整簇链**（因为从未被删除过），投入产出极低。

**核查**：**三态都要处理，并保持扫描终止条件正确**：

```python
first = entry[0]
if first == 0x00:
    break                 # 从未使用 → 后续全空闲，立即停止该目录扫描
elif first == 0xE5:
    state = "已删除"       # 唯一的删除标记
else:
    state = "正常"         # 含 0x05：首字符就是 EOT 的合法文件
```

**报告里要分开统计**："扫描目录项 N 个，其中**删除项 4 个**（首字节 `0xE5`），**首字符为 `0x05` 的正常项 186 个**（非删除项）"——案例第 2 步正是这个写法。

<a id="section-20"></a>

#### 陷阱 4：错误地给 FAT12/16 文件拼接起始簇高 16 位

**现象**：在 FAT12/16 卷上误将 `0x14` 与 `0x1A` 拼为 32 位簇号，读到越界值；文件大小仍应统一从 `0x1C` 读取。

**原因**：**两个变体的目录项布局不同**（2.4 的对照）：FAT12/16/32 的文件大小均在 `0x1C`，起始簇低 16 位均在 `0x1A`；FAT32 另外使用 `0x14` 保存起始簇高 16 位，FAT12/16 不应据此组装簇号。用错偏移会读出**完全错误的"大小"**——而这个错误的破坏力在于它是**静默的**：读出的仍是一个 4 字节整数，不会在解析时报错。

**影响**：**文件大小错误会连锁影响三件事**：提取时的 `dd count` 算错（提取不足或超读）、**哈希因此完全不同**、以及后续任何按大小筛选的逻辑全部失效。证据效力问题在 [文件雕刻与签名恢复](../filesystem-unix/filesystem-unix-file-carving-and-signature-recovery.md) 中有专门讨论——一个长度错误的提取物，其哈希与原始文件无关，它不再是同一个文件。

**核查**：**将“是否存在高位字段”明确为分支，大小字段统一从 `0x1C` 读取**：

```python
if FAT32:
    size    = U32(entry[0x1C:0x20])
    clus    = (U16(entry[0x14:0x16]) << 16) | U16(entry[0x1A:0x1C])
else:
    size    = U32(entry[0x1C:0x20])
    clus    = U16(entry[0x1A:0x1C])
```

**提取后必须核对长度**：实际提取字节数与目录项声明的 `i_size`/size 是否一致。不一致就是有问题的信号，必须查清是碎片化、簇链断裂还是偏移读错。

<a id="section-21"></a>

#### 陷阱 5：给 exFAT 的 `0xC1` 文件名项按 16 字节步进

**现象**：在 exFAT 卷上扫描目录项，后面大量项的名字全是乱码或空字符串。

**原因**：**exFAT 的目录项不是变长的**。`0xC1` 文件名项承载 UTF-16 长文件名，但它同样是 32 字节：`0x00` 项类型 1 字节 + `0x01` 标志 1 字节 + `0x02` 起 15 个 UTF-16 字符共 30 字节。表中列举的六种常见类型码（`0x81`/`0x82`/`0x83`/`0x85`/`0xC0`/`0xC1`）的项长度全部是 32 字节，长文件名靠多个 `0xC1` 项横向拼接实现，与项长无关。若沿用「变长项、`0xC1` 是 16 字节」的印象去步进，每遇到一个 `0xC1` 项之后的定位就偏了 16 字节，此后的所有解析都是错位的——而错位产生的东西看起来"像是"有效的结构，只是名字不对。

**影响**：这类错误的隐蔽性很强：**你仍然能扫出"文件"**，只是名字错误、大小错乱。报告里如果写了文件名，**复核者会按错误的名字去找，找不到就会质疑整份报告**。

**核查**：**exFAT 所有目录项都是 32 字节，固定步进**：

```python
# 伪代码：步进规则均为 32 字节。0xC1 文件名项也是 32 字节（1+1+15×2）
off = 0
while off < len(buf):
    et = buf[off]
    off += 32
    # 删除判定：0x85 文件项的 EntryType，InUse 位（bit7）是否被清零
    # 校验：0x85 的 SetChecksum（0x02~0x03），不是 FAT 的 0x0D 短名校验和
# NoFatChain 在 0xC0 流扩展项 0x01 字节第 2 位（掩码 0x02）
```


**exFAT 的一个重要优势要在报告里点明**：长文件名直接存 255 字符 UTF-16，删除只清 InUse 位，文件名分毫未损（案例第 3 步）。**FAT32/VFAT 也可能留下可恢复的 LFN 残留，但元数据组织方式和恢复条件与 exFAT 不同**——FAT/VFAT 删除通常只会标记关联项为空闲，长名字符字节可能残留，需要按段号、位置和校验约束尝试恢复。两个变体的删除可恢复性差别巨大，报告里必须写明处理的是哪个变体。

<a id="section-22"></a>

#### 陷阱 6：LFN 校验和不校验，组装出错误的长名

**现象**：把 LFN 段按倒序拼起来，得到的长文件名读着通顺但与实际不符，报告里作为"原文件名"引用。

**原因**：**LFN 段必须通过校验和验证才能确认配对正确**（3.2 的脚本 `ok_lfn`）。校验和覆盖 8.3 短名字段的 11 个字节，存在 LFN 项的 `0x0D` 字节、而短目录项的 `0x0D` 是创建时间细分计数字段（不要求为零）——这个不对称是识别"这一组 LFN 段属于哪个短名项"的关键。不校验就直接拼接，会把不同文件的 LFN 段混在一起，产生一个"看起来完全合理但从未存在过"的文件名。

**影响**：**一个错误但通顺的文件名在报告里极具欺骗性**。委托方可能据此认为找到了特定文件，而实际上这个文件名的组合从未存在过。更麻烦的是它无法自检——复核者在文件系统里找不到这个名字，只能认为报告有误。

**核查**：**组装前必须过校验和，且注意删除项的首字符枚举**：

```python
# 校验和存在 LFN 项的 0x0D；短名项 0x0D 是创建时间细分计数字段
# 短名首字符：有效项在 0x20–0x7E；删除项该位已被 0xE5 覆盖 → 需枚举
first = sfn[0] if sfn[0] != 0xE5 else 0x05
cand = [first] if sfn[0] != 0xE5 else [0x05, 0xE5] + list(range(0x20, 0x7F))
# 任一候选通过校验和即认为配对成功
```

**同组内还要检查段号连续**（段序号在每个 LFN 项的 `0x00` 字节：最高位 `0x40` 标记"最后一段"，低 6 位是序号）：段号必须倒序连续覆盖 1..N，缺号或重复都要丢弃这一组。注意 `0x26`/`0x2E` 那个字节是**短名校验和**（低 8 位）加 FstClusLO 高字节，不是段号——从那里读段号会得到完全无关的值。

校验不通过的 LFN 组，宁可只用短名（形如 `LONGNA~1.MP4`）也不要拼一个未经验证的长名。

### 4.3 取证语义

<a id="section-24"></a>

#### 陷阱 7：★ 把 `0x0000` 表项当"文件损坏"，判为不可恢复

**现象**：沿簇链回放时遇到表项值为 `0x0000`，分析员判为"数据已损坏，该文件不可恢复"，写入报告。

**原因**：`0x0000` 表示簇已空闲、链在这里断了，通常是因为文件被删除、簇被释放（2.3）。**"簇被释放"与"物理损坏"是两件完全不同的事**——坏簇有专门的标记值（FAT12 `0xFF7` / FAT16 `0xFFF7` / FAT32 `0x0FFFFFF7`，**是单一值**），而 EOC（`0xFFF8` / `0x0FFFFFF8`）**是范围值**。**唯一可靠的区分方式是判断表项值是否等于坏簇标记**。而"`0x0000` 意味着不可恢复"这个推论，恰好跳过了 FAT 删除文件可恢复的技术原因：**目录项里的起始簇号与文件大小都还在**（2.4），**按起始簇顺序读取即可重建**。

**影响**：**这是本篇最贵的一个错误**——它把"最常见的可恢复情形"判成了不可恢复。而 FAT 删除文件仍可完整恢复恰恰是 FAT 结构最值得利用的特性，**放弃它等于放弃了这一整块证据**。

**核查**：**三态判读，且把恢复程度量化**：

```python
BAD, EOC = 0x0FFFFFF7, 0x0FFFFFF8      # FAT32 每项 4 字节；FAT16 2 字节；FAT12 需位级拆解
n, chain = START_CLUS, []
while True:
    chain.append(n)
    v = int.from_bytes(fat[4*n:4*n+4], "little")
    if v == 0:   break    # 空闲 → 链断裂：文件已删除/簇被释放，内容仍在链上部分区块
    if v == BAD: print("坏簇：物理损坏，此处内容不可恢复"); break
    if v >= EOC: break    # EOC → 链正常结束，文件完整
    n = v
```

**恢复程度的三个档位**（这是必须写进报告的量化判断）：

| 情形                      | 判据                       | 结论                                                 |
| ----------------------- | ------------------------ | -------------------------------------------------- |
| **连续 + 链完整**            | 链长 × 簇大小 ≥ 文件大小，末端 EOC   | **可完整恢复**                                          |
| **连续 + 链被 `0x0000` 截断** | 起始簇到断点连续，链长 × 簇大小 < 文件大小 | **可恢复前缀部分**，缺失部分不可得（例：812345600 字节文件中前 41230 个簇可读） |
| **碎片化**                 | 起始簇到断点不连续                | **仅首簇可读，其余丢失**                                     |

**报告写法**："该文件在 FAT 表中的簇链于第 N 簇处断裂（表项 `0x0000`），前 N−1 个簇物理连续，可恢复 `<N−1>` × 65536 = `<字节数>` 字节，占声明大小 `<百分比>`，其余内容因簇被释放而不可得。"

<a id="section-25"></a>

#### 陷阱 8：只凭扩展名认定已删除文件的身份

**现象**：扫出 4 个已删除项，三个是 `.mp4`，大小量级与监控视频吻合，报告直接写"三段监控视频已被删除"。

**原因**：**扩展名与大小都只是"相似性"，不是"同一性"**。同一台机器上可能存在多个其他 `.mp4`（个人录像、下载的视频、缓存片段），大小落在同一量级并不稀奇。而且 `0xE5` 只覆盖了首字符，文件名其余部分虽然还在，但"文件名"本身是被创建者命名的，它与文件内容是什么之间没有必然联系。案例第 2 步给出的是正确的判据组合：**大小吻合 + 簇号紧邻活跃文件**，**两项以上特征确认身份**。

**影响**：**指认了错误的文件**。

在需要确认"这份视频就是涉案的那份"的场景下，身份错误会让整个认定失效——而这类结论通常出现在报告的结论段落，是最被依赖的位置。

**核查**：**用两项以上独立特征确认，且优先用内容侧证据**：

```bash
# 特征 1：文件大小与预期量级吻合
# 特征 2：簇号邻近活跃文件（说明是连续使用中删除而非早期清理）
# 特征 3：文件名中的时间模式与内容内部时码吻合（最强，见下）
# 特征 4：容器/格式结构完整，可解析出流参数
ffprobe -v error -show_format -show_streams /tmp/carved.mp4
# 特征 5：内容内嵌时间与文件名中的时间模式一致
exiftool /tmp/carved.mp4 | grep -i 'create date'
# Create Date : 2024-04-11 07:42:03   ← 与长文件名 "0742-0817" 完全吻合 ✓
```

**第 5 条是决定性的**：**内部媒体时码与文件名中的时段自洽**——它独立于目录项，不受删除操作影响，**两个独立来源相互印证时，身份认定才站得住**。案例的三项独立特征（容器结构完整 + 流参数与监控设备规格吻合 + 内部时码自洽）共同构成了这个结论。

<a id="section-26"></a>

#### 陷阱 9：不截断就计算哈希，提取物哈希与原文件不符

**现象**：按簇链把内容读出来直接算哈希，得到的值与委托方提供的原始文件哈希不一致，报告里出现了两个互相矛盾的哈希。

**原因**：**文件在簇上占的空间通常是簇大小的整数倍**——一个 1843 字节的 `README.TXT` 占用一个 64 KB 簇，不截断的话提取物是 65536 字节，后面 63693 字节是同簇内后续残留的其他文件内容。**这个提取物在字节层面确实不是原文件**，它的哈希必然不同（见 [文件雕刻与签名恢复](../filesystem-unix/filesystem-unix-file-carving-and-signature-recovery.md) 关于证据效力的讨论）。

**影响**：**证据效力问题**。

报告里如果出现两个不一致的哈希，一个是委托方给的、一个是你算的，**而你无法解释差异来自哪里**——这会让人怀疑整个提取流程。

更实质的是，**未经截断的提取物无法用于与原始哈希比对**，也就无法证明"我提取的就是那个文件"。

**核查**：`truncate` 是保证哈希正确性的必要步骤，不能省（2.5）：

```bash
truncate -s 812345600 /tmp/carved.mp4    # ★ 按流扩展项 DataLength（或目录项 size）截断
# 然后才计算哈希
sha256sum /tmp/carved.mp4
# 核对提取字节数与声明大小是否一致
ls -l /tmp/carved.mp4
```

**手工验证簇链**（独立于工具，直接证明链是否完整、是否碎片化、必须截断多少字节）：

```python
span = (len(chain) - 1) * CLUSTER
# span < FILE_SIZE → 碎片化，删除后 FAT 已释放，后续簇丢失
# span > FILE_SIZE → 末尾残留必须截断
```

**报告里把截断依据写明**："按目录项声明大小 812345600 字节截断（末尾 63693 字节为同簇内后续残留）。"——**这句话是让哈希可复核的前提。**

<a id="section-27"></a>

#### 陷阱 10：在 FAT 上构建秒级时间线

**现象**：把 FAT 目录项的三个时间戳按秒级精度排序，得出"该文件在 14:30:07 创建、14:30:09 修改，两分钟内完成"的结论。

**原因**：FAT 只有三个时间戳（创建/修改/访问），精度为 2 秒（3.2 的明确提示）。DOS 日期/时间格式的秒字段是 2 秒为单位，**且不存时区**。更关键的是**很多 FAT32 卷的创建时间不可用**——部分格式化工具与部分设备不写这个字段，读出来是 0 或无效值。"三个时间戳"这个数量本身就比 NTFS 少，`$SI` 那种四值结构在 FAT 上根本不存在。

**影响**：**2 秒精度会产生虚假的时间关联**。两个事件在秒级时间线上相隔 1 秒、在 2 秒精度下却可能显示为"同一时刻"——**这个精度问题会直接导致因果推断错误**（"先做 A 后做 B"其实可能同时）。而在一个显示到秒的表格里，"14:30:07"和"14:30:09"看起来是两个明确的时间点，读者不会意识到它的分辨率只有 2 秒。

**核查**：**在 FAT 上不做秒级时间线，只做顺序与区间**：

- 结论粒度用"同日/同一 2 秒槽内/同日不同时段"；
- **明确写出精度限制**："FAT 时间戳精度为 2 秒且不含时区，本案时间线在此精度下构建"；
- 创建时间不可用时如实写"该卷未提供可用的创建时间"，不要用修改时间代替——**替换字段等于编造**；
- 需要更细时间线时**必须引入外部时钟**（视频内部时码、日志文件、应用层记录），并说明它记录的是哪个动作。

**案例的做法值得沿用**：把**文件内部时码**（`Create Date: 2024-04-11 07:42:03`）与**文件名中的时间模式**（`0742-0817`）相互印证——**这两者都来自 FAT 之外，精度为秒级**，正好补上了 FAT 时间的精度缺陷。

### 4.4 误报来源与结论表述

<a id="section-29"></a>

#### 陷阱 11：把 exFAT 的 `0xC1` 项当标准目录项，报告里出现空文件名

**现象**：在 exFAT 卷上按统一 32 字节结构解析，前几个项正常，之后出现大量"空文件名"条目，分析员判为"目录项大面积损坏"。

**原因**：`0xC1` 是 exFAT 的文件名项，承载 UTF-16 长文件名，字段语义与 `0x85` 文件项完全不同（2.5、3.4）。`0x85` 里的 `0x04` 是文件属性，`0xC1` 的 `0x04` 却已经是第一个字符的位置——用同一套偏移解析两类项，名字字段读到的就是属性位和保留位，表现为空或乱码。而错位解析出的东西**"看起来仍像"合法结构**，因为步进本身没错，错的是字段归属。

**影响**：一是**真实文件名大量丢失**——而 exFAT 的文件名是**删除不抹除的**（只清 InUse 位），这是它相对 FAT32 的最大优势，不该被解析错误浪费掉；二是"大面积损坏"这个结论会让委托方认为该卷不可用。

**核查**：所有项统一按 32 字节步进，但对每一类项的字段语义分别处理：

```bash
xxd -s 3   -l 8  /work/DigiForensics-usb.dd    # EXFAT 标识
xxd -s 0x40 -l 56 /work/DigiForensics-usb.dd   # 0x40~0x6F 主引导记录参数
xxd -s 0x6C -l 8  /work/DigiForensics-usb.dd   # 根目录簇号(4) + 卷序列号(4)
# 项类型：0x85 文件项 → 0xC0 流扩展项 → N × 0xC1 文件名项（每项 32 字节）
# 0x85 提供属性与三个时间戳，0xC0 提供 FirstCluster/DataLength，
# 0xC1 的 0x02~0x1F 是 15 个 UTF-16 字符，需按项序拼接
# 删除判定：0x85 的 EntryType 的 InUse 位(bit7) 是否被清零
```

**报告里要写明项集校验结果**——案例第 3 步对每个已删除项用 `SetChecksum` 校验通过，**这个校验是长名正确性的证明**。**没有校验的长名恢复是不可复核的。**

<a id="section-30"></a>

#### 陷阱 12：报告里用"某个 U 盘"这类模糊表述指代卷

**现象**：报告写"在查获的 U 盘中发现三个已删除的 MP4 文件"，全文没有出现卷序列号。

**原因**：**卷序列号是报告中的卷标识**，与 NTFS Volume Serial、APFS Volume UUID 地位相同（2.2 的强调）。**"U 盘"是一个物理描述，不是取证标识**——它无法区分同一设备上的多个卷、同一批次的多台设备，也无法让复核者精确定位到某个分区。FAT32 的卷序列号在 `0x43`，FAT12/16 在 `0x27`，**同一工具读不同变体时极易记混偏移**。

**影响**：**报告失去可复核性**。在一批设备同时扣押、需要把每个发现对应到具体设备时，**没有卷序列号的结论无法归属**。

而在后续环节（多台设备交叉比对、委托方核对实物）时，标识缺失会让整批发现都变成待确认状态。

**核查**：**结论一律写成「卷序列号 + 变体」**，BPB 与 exFAT 的序列号位置都要实测：

```bash
# FAT32：卷序列号在 0x43
xxd -s 0x43 -l 4 /work/DigiForensics-fat.dd
# FAT12/16：卷序列号在 0x27
xxd -s 0x27 -l 4 /work/DigiForensics-fat16.dd
# exFAT：卷序列号在 0x64
xxd -s 0x64 -l 4 /work/DigiForensics-usb.dd
```

**报告写法**："卷序列号 `3A7F-91C2` 的 exFAT 分区（单分区，起始扇区 2048，簇大小 65536 字节）中发现 4 个已删除项……"——四个参数（序列号、变体、起始扇区、簇大小）齐全，结论才可复核。

## 五、案例示例

<a id="section-32"></a>

### 5.1 exFAT U 盘上三段监控视频的删除与恢复

**场景**

查获一个 64 GB 移动 U 盘（exFAT），导出监控视频。委托要求确认 2024-04-11 的监控视频是否被删除并恢复。

镜像 `DigiForensics.dd`，raw，单一分区起始扇区 2048。

委托方的问题是"昨天的监控还在不在"。

选择这一路径的依据是 **exFAT 删除文件时长名分毫不动**——这与 FAT32 完全不同，也是本案能把三个长文件名完整恢复的根本原因。

**处置过程**

**第 1 步 · 变体识别与参数实测**：

```bash
xxd -s 3 -l 8 /work/DigiForensics.dd          # 00000003: 4558 4641 5420 2020  EXFAT ✓
dd if=/work/DigiForensics.dd of=/work/DigiForensics-usb.dd bs=512 skip=2048 status=none
fsstat -o 2048 /work/DigiForensics.dd | grep -iE 'cluster size|serial'
# Cluster size: 65536        ← 64 KB 簇！不是假设的 4 KB     Volume Serial: 3A7F-91C2
```

关键发现：**簇大小是 64 KB，不是假设的 4 KB**——若按 4 KB 计算，全部偏移都会错位。卷序列号 `3A7F-91C2` 记录为后续结论的卷标识。

**第 2 步 · 目录扫描与删除项发现**：

```text
项11: 2024-04-11_仓库内通道_1330-1650.mp4  起始簇=41230 大小=812345600
项19: 2024-04-11_西侧停车场_0900-1200.mp4  起始簇=41880 大小=1048576000
项23: 2024-04-11_东门入口_0742-0817.mp4    起始簇=42501 大小=943718400
项27: README.TXT                          起始簇=42620 大小=1843
已删除项: 4   首字符为 0x05 的正常项: 186
```

4 个已删除项，三个 MP4 的大小量级与监控视频吻合，且起始簇紧邻活跃文件 `README.TXT` 的簇号（42620），说明是连续使用中删除而非早期清理。**必须用两项以上特征确认身份**（大小吻合 + 簇号邻近活跃文件），**不能仅凭扩展名认定**。

**第 3 步 · 长名恢复与项集校验**（exFAT 的长名直接存在 `0xC1` 项里，删除不抹除；校验用 `SetChecksum`）：

```text
[已删除] 2024-04-11_仓库内通道_1330-1650.mp4  SetChecksum 校验通过
[已删除] 2024-04-11_西侧停车场_0900-1200.mp4  SetChecksum 校验通过
[已删除] 2024-04-11_东门入口_0742-0817.mp4    SetChecksum 校验通过
[已删除] README.TXT                        SetChecksum 校验通过
```

三个视频的长文件名全部恢复。校验用的是 `0x85` 项的 **SetChecksum**（16 位滚动校验，遍历项集全部字节并跳过主项 `0x02`–`0x03`），不是 FAT/VFAT 的 `0x0D` 短名校验和——exFAT 不存 8.3 短名，不存在该字段。**FAT32/VFAT 也可能留下可恢复的 LFN 残留，但元数据组织方式和恢复条件与 exFAT 不同**：删除通常会标记关联项为空闲，而非将所有长名字符字节清零。

**第 4 步 · 提取与完整性验证**：

```bash
# 数据扇区 = ClusterHeapOffset(17920) + (首簇-2) × 128 扇区/簇；12396 簇 = ceil(812345600/65536)
dd if=/work/DigiForensics-usb.dd bs=512 skip=5295104 count=1586688 of=/tmp/carved.mp4 status=none
truncate -s 812345600 /tmp/carved.mp4      # ★ 按流扩展项 DataLength 截断
ffprobe -v error -show_format -show_streams /tmp/carved.mp4 2>&1 | head -12
# Duration: 00:35:12.84        Stream #0:0 Video: h264, yuv420p, 1920x1080
exiftool /tmp/carved.mp4 | grep -i 'create date'
# Create Date : 2024-04-11 07:42:03   ← 内部时码 07:42 与长文件名 "0742-0817" 完全吻合 ✓
```

**第 5 步 · 三段视频互不重叠的簇段确认**（这一步容易被跳过，但它决定了能不能说"三段都完整"）：

```text
项11  首簇 41230  12396 簇   → 41230 … 53625
项19  首簇 41880  16000 簇   → 41880 … 57879
项23  首簇 42501  14400 簇   → 42501 … 56900
```

按声明大小算，项11 的整个簇区间（41230–53625）都落在项19 的区间（41880–57879）之内，项23 同样与两者大面积重叠。这说明删除之后簇区尚未被回收，三段视频的数据区**彼此踩踏**。因此"三段都完整"这句话需要逐段单独验证，不能因为文件名都在就一起下结论。

实际验证结果只有项11 通过了 `ffprobe` 解析与时码校验；项19 与项23 的容器虽然可解析，但内部 `moov` 的时长与声明大小推算不符，尾部 3–7 MB 落在被覆盖的簇区。**提取出可解析的前段，不等于恢复了完整文件**——这个区别必须在报告里写出来。

**结论**

能证明：①三段监控视频（仓库内通道、西侧停车场、东门入口，2024-04-11）已被删除，长文件名完整恢复且与内部媒体时码相互印证；②项11（仓库内通道）内容完整可恢复——容器可解析，长度 812345600 字节与流扩展项 `DataLength` 一致（已按声明长度截断）；③三个独立特征共同确认这一段是完整的监控视频而非碎片：容器结构完整、流参数 `1920x1080 h264` 与监控设备规格吻合、内部媒体时码与长文件名时段自洽。

项19 与项23 为部分恢复：容器头与 `moov` 可解析，可确认视频存在及其规格，但尾部数据区被后续文件覆盖，无法证明完整。

**不能证明**：①删除时间只能界定区间——exFAT 目录项**不记录删除动作的时刻**，只能界定在最后一次目录项写入之后至扣押日之间，**不得写成某个精确时刻**；②三个 MP4 **是内容完整的数据提取件，但并非"原件"**，应表述为"从卷序列号 3A7F-91C2 的 exFAT 分区中按目录项记录提取"。


未覆盖范围三条：①未对被覆盖区段做未分配空间扫描，被踩踏区域是否还有可拼接的原始片段未验证；②未分析 `README.TXT`（1843 字节，簇 42620）与三项的时间戳关系，删除操作与该文件写入是否同一时段未确认；③未核查是否存在卷影/历史副本，U 盘上通常没有，但委托方可能在其他设备上有同一批文件的副本。

第③条写进报告的价值在于：它把"未恢复的 7 MB"从机构能力问题转成了调证方向。若另一台设备上有完整副本，这份部分恢复件的价值就从"证据"变成"佐证"。

**误判对照**

最像的误判是把 `exiftool` 读出的 `Create Date : 2024-04-11 07:42:03` 当成删除时间。判据要区分两类时间：`Create Date` 是媒体容器记录的拍摄/创建时码，它是视频内容本身的属性，写在 MP4 的 `moov` box 里；而删除是文件系统层面把目录项的 InUse 位清零的动作，exFAT 目录项里没有任何字段记录它发生的时刻。注意 07:42 这个值与长文件名里的 "0742-0817" 完全吻合——正因为它描述的是**视频拍的是哪一段时间**，与文件何时从卷上消失毫无关系。正确判据是内容时码回答"这段视频是什么时候拍的"，目录项状态变化回答"它什么时候不被列出了"，两者分属不同层，不可互相代入。

三条判据：

①**这个时间存在哪一层结构里**。`Create Date` 写在 `moov` box 内，属文件内容；删除时刻若要被记录，得在目录项或日志里，而 exFAT 目录项只有三个时间域（创建/修改/访问），没有"删除时间"这个字段。看字段归属就能排除，不需要更多数据。

②**时间值与长文件名是否自洽**。07:42 与文件名里的 "0742-0817" 首尾相接，而这三段视频的拍摄时段在名称里已经写明。若 `Create Date` 落在 4 月 11 日凌晨 3 点（删除动作常在此时段），它与名称就对不上；本案完全吻合，说明它描述的是拍摄而非删除。

③**目录项的三个时间域能给出什么**。修改时间与访问时间落在扣押当日，创建时间在 4 月 11 日——三者都无法指向删除时刻，因为删除不改这三个值。**能在时间上成立的只有区间**：删除发生在最后一次目录项写入之后。

第③条是这节的落点。它把"不知道删除时间"从一个缺陷变成了一条可复用的区间结论，委托方拿它去比对值班表时，精度是"4 月 11 日之后"，而不是某个具体钟点。

按错误判据走的代价：委托方拿 04-11 07:42 07:42 去比对值班表，而真正的删除可能发生在数天后；若该时段责任人正在岗，删除行为的归属判断就完全建立在错误的时间点上了。

本案还有一个连带后果：初稿把三段视频统一写成"已完整恢复"，而实际只有一段完整。这句话后来被拆成"一段完整、两段部分恢复"两行，报告页数多了半页，但委托方据此追加调证了另一台设备——那个动作在初稿那版结论下不会被触发。把部分恢复写成完整恢复，代价不只是措辞不严谨，而是让一个本可执行的调查方向提前关闭。

### 5.2 64 KB 簇大小：这个参数错了后面全错

**场景**

同一 U 盘在另一批分析中，参数表默认簇大小为 4 KB，第一次提取产出的 MP4 只有前 4 KB 有效，`ffprobe` 报错。

将此情形单列的原因是 exFAT/FAT 的簇大小是从文件系统参数区读出来的，不能假设——而假设错一次的代价是全部偏移成倍偏离。

**处置过程**

1. 任何计算开始之前先实测：

```bash
fsstat -o 2048 /work/DigiForensics.dd | grep -iE 'cluster size|serial'
# Cluster size: 65536        ← 64 KB，与假设的 4 KB 差 16 倍
```

1. 用实测值重算数据区起点：

```text
首簇 41230，文件大小 812345600 字节
簇数 = ceil(812345600 / 65536) = 12396
每簇扇区数 = 65536 / 512 = 128
数据起始扇区 = ClusterHeapOffset + (41230 - 2) × 128
             = 17920 + 41228 × 128 = 5295104   ← 与第 4 步 dd 的 skip 值一致
```

1. 反向自检：若按 4 KB 假设，扇区数为 1586688（少 16 倍），提取长度会远小于声明大小。

**结论**

能证明：簇大小 65536 字节由文件系统参数区实测得出，非假设；数据区扇区算式经 dd 实际提取长度与文件声明大小双向验证通过。这项记录在案，供复核方独立重算。

**不能证明**：不能仅凭首簇与大小推出文件完整——还需流扩展项的 `DataLength` 与容器解析结果配合（这正是第 4 步另外两项验证的作用）。

**误判对照**

最像的误判是直接套用默认值 4 KB 或 4096。判据要落在偏移算式上：扇区偏移 = ClusterHeapOffset + (簇号 − 2) × 每簇扇区数，其中"每簇扇区数"由簇大小除以 512 得到；把 65536 当 4096，算出的扇区数是正确值的 1/16，提取出来的文件只有开头一小段有效——**而这不会报错**，`dd` 正常完成，只是文件是残的。正确判据是簇大小必须从参数区实测，任何偏移算式都要用实测值代入。按错误判据走的代价：如果后续只核对"提取长度与声明大小一致"这一项，它会当场暴露；但如果改用"按声明长度截断"来补救，就会把后面填充的零字节也当成文件内容，得到一个大小正确但内容大面积损坏的"完整"文件——**这比提取失败更危险，因为它通过了唯一的那道检查**。

### 5.3 反例：把 0xE5 首字节当作文件被删除

**场景**

某次 exFAT 分析中，目录项扫描出首字节为 `0xE5` 的项 186 个，分析员将其中的 4 个 `.mp4` 认定为被删除的目标文件。

实际核对后发现，这 4 个项全部通过了 `SetChecksum` 校验，而另外 182 个 `0xE5` 项是各类临时文件。

这条列为反例，是因为 `0xE5` 在 exFAT 里的含义与 FAT 系列并不相同——它只是"该项不再指向有效目录项"的通用标记，不携带删除语义。

**处置过程**

对照点在于 exFAT 项类型与 `SetChecksum` 的分工：

```text
0x05 在用项（Allocation Possible）   ← 活跃文件
0x05 已删除项                        ← InUse 位已清零，但内容完整
0x85 分配位图项                     ← SetChecksum 校验用
0xC1 长文件名项                      ← exFAT 特有，删除时不清零
0xE5 未分配项                        ← 该项从未被使用，或已被回收，
                                       内容是陈旧数据，SetChecksum 必然失败
```

```text
本案 4 个目标项：type=0x05 已删除 → SetChecksum 校验通过 ✓
    内容真实有效，可作为已删除文件处理
另 182 个 0xE5 项：SetChecksum 校验失败 → 陈旧数据，无效
```

**结论**

阴性发现：186 个 `0xE5` 首字节项中，**仅 0 个构成有效的已删除文件证据**——它们全部未通过 `SetChecksum`，属于已被回收的未分配项。**未覆盖范围**是这 182 项对应的原始文件名——若曾存在过，其信息已随项回收不可恢复。

**误判对照**

最像的误判是"首字节 `0xE5` = 文件名首字符被删除标记 = 该文件被删除"。判据要落在 exFAT 的项结构上：exFAT 的目录项有 8 种类型（`0x81`/`0x82` 分配位图、`0x83`/`0x84` 上卷簇堆位图、`0x85` 校验和、`0xC0`/`0xC1` 文本区与长名、`0x05` 在用/已删除目录项、`0xE5` 未分配），`0xE5` 表示该项当前不被任何文件使用——它可能是从未被用过，也可能是文件被删后该项被回收，两者在字节上无法区分。区分判据是 **`SetChecksum` 校验**：`0x05` 已删除项的校验值仍然有效（因为内容没被抹），`0xE5` 项的校验值必然对不上。按错误判据走的代价是把 182 项陈旧数据当作文件证据写进报告，而一旦对方按文件名索引复核，会发现这些文件从未存在于该卷——更实际的风险是把别人的无关临时文件误列为"被删除的业务文件"。

### 5.4 工具翻车：`NoFatChain` 置位却按 FAT 表逐跳找簇

**场景**

一块 8 GB 的 exFAT U 盘，`fsstat` 报出完整的卷参数（卷标、序列号、每簇扇区数、FAT 数量俱全），簇大小 64 KB 与预期一致。分析员据此定位已删除文件，提取结果是开头几 KB 正常、后面全是乱码。

试了几个文件都是这个形态——**部分正确**，比全错更难往下查。

**处置过程**

对照点在于 `0xC0` 流扩展项里的 NoFatChain 标志：

```bash
# 定位到该目录项集的首项（0x85 项），读出项类型与 SetChecksum
fls -o 2048 -r -p /case/DigiForensics.dd | grep -i '连续文件.dat'
# r/r 500-128-1:  ... 连续文件.dat
dd if=/case/DigiForensics.dd bs=512 skip=$((CLUSTER_HEAP_SECTOR + (0x1F4-2)*128)) count=4 status=none | xxd
# 00000000: 8560 218a 0300 0000  ....   ← 0x85 项，SetChecksum=0x8A21，SecondaryCount=3
# 00000020: c002 0008 e412 0000 a012 00   ← 0xC0 流扩展项：
#                    GeneralSecondaryFlags=0x02  → bit1 NoFatChain 置位（掩码 0x02）
#                    FirstCluster=0x000008E4
#                    DataLength=0x0012A000
```

逐项集解析后，`SetChecksum`（16 位滚动校验，遍历项集全部字节并跳过主项 `0x02`–`0x03`）是判定项集有效性的第一道关；`0xC0` 里的 `GeneralSecondaryFlags` 决定第二条分支走哪条路。

`NoFatChain` 置位的含义是**这个文件连续存放、不在 FAT 表里登记表项**——不是"文件没有簇"。按 FAT 表逐跳查下一个簇号，查到的那些表项属于别的文件，读出来自然对不上。

正确路径是不查表，直接按连续区间定位（2.6 已给出这两个字段的位置）：

```text
NoFatChain = 0：  首簇 → 查 FAT 表项得下一簇 → … → EOC
NoFatChain = 1：  首簇 → 连续读 DataLength 字节 → 结束
```

```bash
# 连续文件：按 FirstCluster + DataLength 定位
dd if=/case/DigiForensics.dd bs=65536 skip=$((0x8E4)) \
   count=$((0x12A000/65536)) of=/tmp/DigiForensics_extracted.bin
```

顺带把卷参数核一遍。exFAT 没有 BPB，全部参数在主引导记录 `0x40`–`0x70`：

```bash
dd if=/case/DigiForensics.dd bs=512 count=1 status=none | hexdump -C -s 0x40
# 0x40 PartitionOffset   0x48 VolumeLength   0x50 FatOffset
# 0x60 ClusterHeapOffset 0x68 ClusterCount  0x6C RootDirectoryCluster
# 0x70 VolumeSerialNumber → 3A7F-91C2
```

核对方式是把主引导记录 `0x70` 处 4 字节与 `fsstat` 报的卷序列号对一遍。对不上，说明层级搞错了——分区起点与卷起点可以差一整层，`FirstCluster` 算出的绝对位置会整体平移。

**结论**

阳性发现：`DigiForensics.dd` 中 exFAT 卷（序列号 3A7F-91C2）参数已按主引导记录逐字段核对一致，簇大小 64 KB 确认。4 个已删除连续文件按 `FirstCluster` + `DataLength` 提取成功，`0xC1` 项长文件名完整保留。

阴性发现：1 个碎片化文件未能恢复。其 `NoFatChain` 未置位，簇链需逐跳查 FAT 表，而删除已把链上表项清零（`0x0000`），链在第一跳就断——按 2.3 的结论，碎片化文件删除后通常无法仅依靠已释放的 FAT 簇链完整重建，这是格式的固有限制，不是工具能力问题。

**误判对照**

最像的误判是把 `NoFatChain` 读成"这个文件没有簇"。

判据要落在**位定义与可观察后果**上：`0xC0` 项 `0x01` 字节的 bit1（掩码 `0x02`）置位，含义是"连续存放，FAT 表里没有它的表项"。此时按表项逐跳查簇，得到的簇号来自别的文件的表项。之所以表现为"开头对、后面错"，是因为**首簇本来就是对的**——错的只是第二跳之后。

第二种误判是把 `fsstat` 的输出直接当卷级参数用。判据在于 exFAT 参数全在主引导记录 `0x40`–`0x70`，而 `fsstat` 面向分区，把分区偏移与卷偏移合并显示。

按错误判据走的代价是把一批完好的数据判成"文件已损坏"。方向一错，修复动作就完全对不上——真损坏要重新采集、换设备、换介质，而换什么都解决不了一个纯粹的定位算法问题。判错方向的代价通常比判错结果本身更贵。

<a id="section-36"></a>

### 5.5 反直觉结论：Trash 里那个 0 字节文件不是删除残留

**场景**

同一块 U 盘上，`.Trashes-1000` 目录里有一个 0 字节的 `DigiForensics-report.pdf`。目录项在、长文件名完整、`DataLength` 为 0。委托方要求确认"这份 PDF 是否曾存在并被删除"。

按 exFAT 保留长名的特性，初看像是删了个有内容的文件、只是内容没提出来。细查之后方向反了。

**处置过程**

`DataLength` 为 0 有三种成因，靠 `0xC0` 项的 `FirstCluster` 区分：

```bash
# 定位 .Trashes-1000 下该目录项集的 0x85 主项与其 0xC0 流扩展项
fls -o 2048 -r -p /case/DigiForensics.dd | grep -i 'DigiForensics-report.pdf'
# r/r 0x1F4: ... .Trashes-1000/DigiForensics-report.pdf
dd if=/case/DigiForensics.dd bs=512 skip=$((CLUSTER_HEAP_SECTOR + (0x1F4-2)*128)) count=4 status=none | xxd
# 00000000: 8560 a82a 0100 2000  ....   ← 0x85 项，Attr=0x20（Directory）
# 00000020: c002 0008 e412 0000 0000 00  ← 0xC0：GeneralSecondaryFlags=0x02
#                                                FirstCluster=0x000008E4  非零
#                                                DataLength=0x00000000   归零
```

判别点是 `FirstCluster` 非零而 `DataLength` 为零。这个组合表示文件系统认为"该文件曾占用从簇 `0x8E4` 起的簇群"，只是记录的长度为 0。

再落到 `0x01` 字节的 bit0（`AllocationPossible`，掩码 `0x01`）：NoFatChain 置位而 AllocationPossible 也置位，意味着这是**该文件最后一次写入时长度就是 0**——创建即空，或最后一次写入被截断到 0 字节后再未更新元数据。

反过来看，若是非空文件被删除，`DataLength` 会保留删除前的大小（exFAT 删除只清 InUse 位，其余字段原样保留），**不会变成 0**。

```text
DataLength=0 + FirstCluster≠0 + AllocationPossible=1  → 空文件/写入截断为 0
DataLength=0 + FirstCluster=0                         → 从未分配簇的占位项
DataLength>0 + EntryType=0x05                          → 真正的删除残留，可提取
```

补一步：`.Trashes-1000` 是 macOS 回收站，移入操作只把目录项搬进这个目录，不擦数据——这解释了名字为何这么完整。但要注意 Trash **不记录"移入时间"**这个字段，能用的仍只有那三个写入时间戳。

**结论**

阳性发现：`.Trashes-1000` 中 `DigiForensics-report.pdf` 的 `DataLength=0`、`FirstCluster=0x8E4` 非零、NoFatChain 置位——判定为**创建或最后一次写入时长度即为 0 的空文件**，不是"非空文件被删除后内容丢失"。

阴性发现：卷内未检出该 PDF 的任何数据区残留，`0x8E4` 起始的簇群为全零填充，**无该文件曾包含 PDF 内容的证据**。

未覆盖范围：`0x8E4` 所在簇群若曾被其他文件使用后清零，则那部分内容不可归因于本文件。

**误判对照**

最像的误判是"目录项在、名字完整、内容 0 字节 = 文件被删、内容丢失"。

判据要落在**删除动作改了哪个字段**上：exFAT 删除只清 `0x85` 项的 InUse 位（`0x85`→`0x05`），`DataLength`、`FirstCluster`、三个时间戳全部原样保留。所以被删除的非空文件，其 `DataLength` 仍是删除前的非零值——`DataLength` 归零这件事本身不可能由删除造成，它只发生在写入阶段。这条判据方向性很强，能把"从未有内容"和"有内容但没提取出来"完全分开。

第二种误判是见到 Trash 目录就推断"经由 Finder 删除"。判据在于 Trash 只搬运目录项，既不擦数据也不记录搬运时刻；要证明"经 Trash 删除"，只能靠 Trash 目录自身 mtime 与文件项时间戳的先后关系间接推。

按错误判据走的代价是把一份从未有内容的文件写进"已删除文件清单"，并据此推出"操作者在事后清理了报告"。这条叙事一旦成立，委托方的调查方向会整个偏掉——而实际答案可能只是脚本第一次运行就失败、生成了一个空文件。

## 六、扩展阅读方向

FAT 是本库里"结构最简单、结论限制最多"的文件系统。下面几组按你实际会遇到的场景分组——**其中有几条本库暂缺专篇，那才是真正的缺口**。

### 前置基础：先确认手里这个卷是什么

- [文件系统取证总览](../filesystem-ntfs/filesystem-ntfs-filesystem-forensics-overview.md) —— **本篇最重要的一条链接**。第 3 步"逐卷判定文件系统类型"是本篇的前置条件：BPB 每个字段都要自己核，**照抄别人镜像的参数必然错位**。第五章那个 64 KB 簇的发现就是这一步的价值
- [只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md) —— `losetup` 与 offset 的正确用法。本篇全程在"分区起始扇区 + 相对偏移"上计算，`-o` 参数给错则后面全错
- [时间戳换算](../../fundamentals/fundamentals-concepts/fundamentals-concepts-timestamps-and-timezones.md) —— DOS 时间的位域打包是那篇 2.5 的内容。本篇反复强调"不要在 FAT 上构建秒级时间线"，原因就在那篇：2 秒精度且无时区字段

<a id="section-39"></a>

### 同层深入：其他文件系统怎么解决同样的问题

- [NTFS 数据流与隐藏数据](../filesystem-ntfs/filesystem-ntfs-ntfs-alternate-data-streams.md) —— NTFS 侧的对照读物。**簇链 vs 运行列表（`$DATA` runs）**、有无权限与日志，两者的取舍差别一目了然
- [ext4 结构与 inode](../filesystem-unix/filesystem-unix-ext4-inode.md) —— journal 机制正是 FAT 缺的那样东西：FAT 没有日志，所以没有"从现状追到过程"的能力
- [F2FS 结构](filesystem-mobile-fs-f2fs.md) —— 同主题目录的移动端文件系统。它有日志与检查点，**因此能力上限高于 FAT，但结构复杂度也高得多**
- [NTFS 结构与 MFT 解析](../filesystem-ntfs/filesystem-ntfs-ntfs-master-file-table.md) —— 如果你要理解 FAT 为什么"适合当练习对象"，最好的办法是读完 NTFS 之后再回来。没有间接层与有 B-tree 的差别，读完才真正有体会

## 七、命令速查

```bash
sudo apt install sleuthkit file xxd python3

# ===== 定位与变体识别（BPB 全字段见 2.2）=====
mmls /work/DigiForensics.dd
dd if=/work/DigiForensics.dd of=/work/DigiForensics-fat.dd bs=512 skip=2048 status=none
xxd -s 0x0B -l 2  /work/DigiForensics-fat.dd   # 每扇区字节数
xxd -s 0x0D -l 1  /work/DigiForensics-fat.dd   # 每簇扇区数 ★簇大小=二者相乘
xxd -s 0x0E -l 2  /work/DigiForensics-fat.dd   # 保留扇区数（= FAT 起始）
xxd -s 0x24 -l 4  /work/DigiForensics-fat.dd   # 每FAT扇区数（FAT32；FAT12/16 在 0x16）
xxd -s 0x2C -l 4  /work/DigiForensics-fat.dd   # 根目录起始簇号（FAT32）
xxd -s 0x43 -l 4  /work/DigiForensics-fat.dd   # 卷序列号（FAT32；FAT12/16 在 0x27）
xxd -s 0x52 -l 8  /work/DigiForensics-fat.dd   # "FAT32   " 文本（FAT12/16 在 0x36）
xxd -s 3   -l 8  /work/DigiForensics-usb.dd   # EXFAT 签名
xxd -s 0x40 -l 56 /work/DigiForensics-usb.dd   # exFAT 主引导记录参数
fsstat -o 2048 /work/DigiForensics.dd

# ===== 目录树、删除项、LFN（脚本见正文 3.2）=====
fls -o 2048 -r -p /work/DigiForensics.dd > /evidence/fat-fls.txt
istat -o 2048 /work/DigiForensics.dd 460        # size + 三个时间戳（2 秒精度）
# 属性 0x10=目录（大小字段恒为 0，不能用 size==0 判断目录）
# FAT32 起始簇=0x14(高)|0x1A(低)；FAT12/16 只读0x1A低16位；文件大小均为0x1C
# LFN：属性==0x0F；序号=首字节&0x3F（0x40 位是最后一段标志）；字符位置 0x01(5) 0x0E(6) 0x1C(2)，共 13 字符/段，UTF-16LE
# ★ 校验和取自 LFN 项 0x0D（短名项 0x0D 是创建时间细分计数字段，不可取）
# ★ 已删除项短名首字符被 0xE5 覆盖，校验时须枚举候选首字符后比对

# ===== 提取与截断（关键）=====
icat -o 2048 /work/DigiForensics.dd 460 > /tmp/extracted.bin
truncate -s 15360 /tmp/extracted.bin            # ★ 按记录大小截断，否则哈希必错
stat -c '%s' /tmp/extracted.bin && sha256sum /tmp/extracted.bin
unzip -l /tmp/extracted.docx | head           # OOXML 内部条目是否完整
ffprobe -v error -show_format /tmp/carved.mp4 # MP4 容器与流是否可解析

# ===== 簇链验证（脚本见正文 3.3）=====
# FAT32 每项 4 字节，FAT16 2 字节，FAT12 需位级拆解；簇值 0=空闲(链断) / 0x0FFFFFF7=坏簇 / ≥0x0FFFFFF8=EOC
# 报告需写明：链是否完整、是否碎片化、必须截断的字节数

# ===== fatcat（只读用法；写选项严禁用于原始镜像）=====
fatcat /work/DigiForensics-fat.dd -i                # 卷信息
fatcat /work/DigiForensics-fat.dd -l / -d           # 列出目录，含已删除项
fatcat /work/DigiForensics-fat.dd -r /path/file.txt # 读取文件到 stdout
fatcat /work/DigiForensics-fat.dd -2                # 比对两份 FAT 表差异（只读）
fatcat /work/DigiForensics-fat.dd -@ 41230          # 查某簇的地址与 FAT 项
# ★ 写操作一律禁用：-m 合并 FAT / -w 写簇项 / -p 回补 FAT / -f 修目录 / -z -S 覆写未分配区

# ===== exFAT 专项（类型码与混排规则见 2.6）=====
# 0x85 文件项 → 0xC0 流扩展项 → N×0xC1 文件名项（每项 32 字节，固定步进）；校验用 0x85 的 SetChecksum
# NoFatChain 在 0xC0 项 0x01 字节 bit1（掩码 0x02）；删除项看 InUse 位(bit7)是否被清零
```
