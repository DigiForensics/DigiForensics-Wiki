# Steady State 与 $LogFile 还原

> 原文链接：[DigiForensics Wiki · 在线阅读](https://www.digiforensics.cn/wiki/filesystem-ntfs-steady-state-logfile)

<a id="section-1"></a>

## 一、概述

NTFS 的 MFT 解析回答的是**现状**：某个条目现在有哪些属性、哪些流、什么时间戳。"这个条目原本是什么，是谁在什么时候改掉的"是另一个问题。现状写在 `$MFT` 的当前字节里，**日志型文件系统还会另写一份"改动过程"**——NTFS 的这份记录就是 `$LogFile`（MFT 记录 2）与 `$UsnJrnl`。

不读日志的代价很具体：一个被删又重建的同名文件，`$MFT` 里只留下"未使用"标记和新条目的时间戳。你无法区分"这文件刚被创建"和"这文件被删掉之后又用同样的名字创建了一个"——后者意味着原文件被覆盖，两者的法律与取证意义完全不同。

这一层工作在分析环节的元数据纵深阶段，紧跟在 [NTFS 结构与 MFT 解析](filesystem-ntfs-ntfs-master-file-table.md) 之后、结论汇总之前。三个数据源的分工必须先分清：

| 数据源 | 记录什么 | 覆盖窗口 | 价值 |
|---|---|---|---|
| `$MFT` 当前内容 | 现在的元数据 | 无窗口概念 | 基准，但不能回答历史 |
| `$LogFile` | 元数据改动的 REDOP/UNDO 序列，带 LSN | 环形缓冲，容量决定 | 崩溃恢复依据 + 历史元数据 |
| `$UsnJrnl` | 文件操作流水（原因码 + 文件引用号 + 文件名） | 环形缓冲，通常几天 | 重命名/移动的时间与顺序 |

**三者不是替代关系**。第五章案例里 `季度汇报.docx` 这个已不存在的名字，靠 `$UsnJrnl` 与 `$LogFile` 两个独立源互相印证才敢写入结论——只有一个源支撑时，结论强度要降级。

上游是 `$MFT` 解析结果（读日志要靠 MFT 记录的 LSN 字段定位）；下游是时间线合并与主体归属。元数据日志能证明"文件被改名"，但证明不了"是谁改的"，那一跳要跳到 Windows 执行痕迹。

落到具体证据上：

- **`$LogFile`（MFT 记录 2）** —— 元数据日志本体。**`$DATA` 是原位的、`:$J` 是非原位的**，`icat` 提取时要选对地址
- LSN（LogFile Sequence Number） —— 每条日志记录与每个 MFT 条目携带的序列号。比对"日志里的 LSN"与"MFT 条目的 LSN"是判断某条目是否被日志覆盖过的关键动作
- **REDOP / UNDO 记录** —— 重做与撤销对。**一个逻辑操作通常对应多条记录**，不能按"一条 = 一次操作"计数
- **卷 dirty 位** —— 关机是否干净。非 Steady State 意味着日志里有未提交事务，2.x 的还原结论不能直接用
- `$UsnJrnl` 与 `$UsnJrnl%3A$J` —— 变更日志本体与它的非原位流。**环形缓冲结构，满了覆盖旧记录**
- **USN 原因码** —— 如 `0x80000023`（文件被关闭）、`0x00000102`（文件名变更）。**原因码是判断操作语义的第一手依据**
- **MFT 条目的四项时间戳** —— `$STANDARD_INFORMATION` 的 Created / Modified / Changed / Accessed。"改元数据只动 Changed、不动 Modified"是重命名的典型特征
- MFT 条目的 `Last Access Update Sequence Number` —— 系统当前 LSN 位置。与日志最大 LSN 比较可直接判断条目是否已被新事务覆盖
- `DigiForensics.dd` 中记录 2 的 `$DATA` 提取结果 —— 日志二进制本体。**体积明显小于配置上限，说明近期记录还在**
- `DigiForensics.dd` 中记录 132 的提取结果 —— `$UsnJrnl` 提取结果。`strings` 能捞出文件名，但时间是变长结构，位置需按版本验证

走完这一层能回答的是这些：这个卷是否处于 Steady State、某个 MFT 条目是否仍在日志覆盖范围内、某个已消失的旧文件名在什么时间窗口内出现过、**以及某项元数据变化能否被两个独立日志源互相印证**。

**回答不了的几件事必须提前说清**：

- **文件内容** —— `$LogFile` 记录的是元数据（文件名、大小、簇链描述），**不记录数据流内容**。想恢复内容走 slack 与未分配空间路线
- **"谁"改的** —— 日志里没有用户身份，只有文件引用号与原因码。**主体归属要靠 UsnJrnl 之外的执行痕迹**（登录会话、进程创建）
- **精确到秒的操作时刻** —— USN 记录是变长结构，时间字段偏移需按版本验证。**未做结构化解析时只能给时间窗口，不能给时刻**
- **超出缓冲窗口的旧操作** —— 两个日志都是环形缓冲。**窗口外的事实不是"没发生"，是"查不到"**
- **数据流层面的藏匿** —— 命名流与隐写属于 [NTFS 数据流与隐藏数据](filesystem-ntfs-ntfs-alternate-data-streams.md) 的范围，日志管不到

往下读之前必须已读 [NTFS 结构与 MFT 解析](filesystem-ntfs-ntfs-master-file-table.md)——要理解 LSN 在 MFT 记录头里的位置、`$STANDARD_INFORMATION` 的字段布局、记录号与文件引用号的换算，这三样是这里所有操作的输入，日志结构解析绕不开它们。

另外需要一点**二进制结构阅读的耐心**。这里刻意包含一条"无法结构化解析时怎么办"的路径（2.6），因为真实委托里工具版本经常不匹配。**知道退化路径是什么，比记住某个工具的语法更有用。**

LSN 体系与 REDOP/UNDO 的结构推导在[核心原理](#section-2)，提取与判读步骤在[操作步骤](#section-9)。这一层的产出直接决定你能写多强的结论，所以[常见陷阱](#section-15)那一章不是可选的——4.1 组的每一条都会让"已删除"或"已重命名"这类判断从成立变成不成立。原因码的完整表、记录结构与多记录合并成一次操作的技术，见[UsnJrnl 与文件操作时间线](../../computer/computer-execution/computer-execution-usn-journal-timeline.md)。完整还原流程见[案例示例](#section-31)，提取命令见[命令速查](#section-41)。

## 二、核心原理

<a id="section-3"></a>

### 2.1 Steady State：文件系统什么时候"静止"

**定义**：一个日志型文件系统处于 **Steady State** 时，意味着：

- 日志中**已完成**的记录所描述的元数据改动，**已经全部落到磁盘上的真实元数据结构中**；
- 因此，**磁盘上的元数据是当前有效的、最新的一致状态**；
- 日志中可能仍有**未完成**的记录（预写入但未提交），但这些不影响"已提交改动已落盘"这个性质。

```
时间轴 →
 ┌──────────────┬──────────────┬──────────────┬──────────────┐
 │  日志记录写入  │  元数据落盘   │  日志记录标记  │  日志空间复用  │
 │ (REDOP/UNDO)  │  (真实 MFT)  │  为已完成     │  (环形覆盖)   │
 └──────────────┴──────────────┴──────────────┴──────────────┘
        │                  │                 │
     崩溃可能点①         崩溃可能点②        崩溃可能点③
     日志有、盘无        盘改了一半         日志被覆盖丢失
```

**Steady State 的取证意义**：在 Steady State 镜像上看到的元数据 = 有效状态，**不需要回放日志**就能得到正确目录树（正常关机检材的常见情形）；非 Steady State 检材（异常断电）必须先评估日志，因为可能存在"日志里有、盘上没有"或"盘改了一半"的中间态。判断顺序永远是先状态、后内容。

**如何判断是否处于 Steady State**：

```bash
icat -o 2048 /work/DigiForensics.dd 2-0-0 > /evidence/LogFile.bin   # 头部字段解释需结合版本验证
ls -l /evidence/LogFile.bin
file /evidence/LogFile.bin
```

| 观察 | 推断 |
|---|---|
| 系统**正常关机**（有干净关机事件/标记） | 大概率 Steady State |
| 文件系统标记为 **dirty / needs recovery** | **非 Steady State**，必须评估日志 |
| `$LogFile` 体积远小于配置上限 | 环形缓冲未填满，近期日志尚在 |
| `$LogFile` 体积接近上限且很老 | 近期日志可能已被覆盖 |

> **关键提醒**：`$LogFile` 是**固定大小的环形缓冲区**（典型 4–64 MB，取决于卷大小与版本）。空间写满后**最早的记录被覆盖**。所以"日志里没有"永远**不等于**"没发生过"，只说明"那条记录已被覆盖"。

<a id="section-4"></a>

### 2.2 `$LogFile` 记录什么、不记录什么

| 类别 | 是否记录 | 说明 |
|---|---|---|
| 文件创建/删除/重命名 | ✅ | 对应 MFT 条目的标志位与 `$FILE_NAME` 改动 |
| 大小/时间戳变化 | ✅ | 多数涉及 MFT 记录的元数据更新 |
| **文件内容（`$DATA` 数据块）** | ❌ | **日志不记录数据内容** |
| 目录项的完整重建 | 部分 | 复杂目录操作可能触发整块元数据重写 |
| 簇分配/释放 | 部分 | 取决于操作是否触发 `$Bitmap` 更新入日志 |

**结论**：`$LogFile` 能回答"**元数据怎么变的**"，**不能**回答"**文件里是什么**"。把两者混淆会导致报告出现无法支撑的结论。

<a id="section-5"></a>

### 2.3 通用日志机制：REDOP / UNDO / 事务

几乎所有日志型文件系统（NTFS、ext3/4、XFS、JFS）都采用同一套抽象：

| 记录类型 | 全称 | 作用 |
|---|---|---|
| **REDOP** | **Redo** Operation（重做） | 记录"**要做什么**"：把某处元数据设为某值。回放它 = 重做这个操作 |
| **UNDO** | **Undo** Information（撤销） | 记录"**改之前是什么**"：把某处元数据原值保存下来。用于回滚未完成事务 |
| **Checkpoint** | 检查点 | 标记"到此为止的日志都已成为稳定状态"，并记录当时的 LSN |

LSN（Log Sequence Number，日志序列号） 贯穿整个机制：每条日志记录都带 LSN；MFT 记录头也存了 `$LogFile` 的 LSN（该 MFT 条目最后一次由日志更新时的 LSN）。比较两者即可判断"这个 MFT 条目的当前状态，是否反映了日志里的最新状态"：

```
MFT记录.LSN >= 日志中该操作的LSN  → 磁盘状态已包含该日志描述的改动
MFT记录.LSN <  日志中该操作的LSN  → 磁盘可能仍是改之前的旧状态
```

> **实操说明**：MFT 记录头偏移 `0x08`、长度 8 字节存放该 LSN（结构见 [02 篇](filesystem-ntfs-ntfs-master-file-table.md) 2.2），跨版本稳定。但 LSN 字段在 `$LogFile` 记录内部的字节位置随版本变化，需用实际解析工具确认，不要凭本文硬编码偏移。

<a id="section-6"></a>

### 2.4 LogMiner 类思路：不逐条解析，先做差分

直接逐字节解析 `$LogFile` 难度高、版本差异大。LogMiner 类工具的核心思路是"黑盒差分"，绕开结构解析——让两个 `$LogFile` 前缀分别驱动一次挂载，比较两次挂载后**元数据的差异**：

```
原始 $LogFile（长）
  ├── 取前 N 字节 → 补丁A → 挂载 → 导出目录树 → 快照A
  ├── 取前 M 字节 → 补丁B → 挂载 → 导出目录树 → 快照B   (M > N)
  └── 差分：快照A ⊕ 快照B = 区间 (N, M] 的日志导致的元数据变化
```

| 优势 | 局限 |
|---|---|
| **完全不需要理解内部结构** | 需要能**写盘**（在副本上，且驱动需支持日志补丁） |
| 版本差异不敏感 | 差分只说"变了什么"，**不说何时变、谁变的** |
| 可精确定位"哪段日志有效应" | 差分结果仍需人工归因 |

**这类方法属于"辅助生成假设"的技术**，产出的时间与主体信息需另找证据（`$UsnJrnl`、事件日志、Prefetch）佐证。代价是黑盒方法要求写盘能力。

<a id="section-7"></a>

### 2.5 元数据变化追踪：从"现状"到"过程"

即使不深入解析 `$LogFile`，**元数据变化追踪**本身也是高价值维度：

| 数据源 | 回答的问题 | 局限 |
|---|---|---|
| **`$MFT` 四个时间戳** | 文件何时创建/修改/访问/元数据变更 | 无历史，只有当前值 |
| **`$FILE_NAME` 时间戳** | 改名发生的时间 | 改名后原名不再可读 |
| **`$UsnJrnl`（USN 日志）** | 何时做了文件级操作（带操作类型与原因） | 环形缓冲，有上限；不含内容 |
| `$LogFile` | 元数据**如何**被一步步修改 | 环形覆盖；不含内容；需工具解析 |
| **事件日志** | 谁登录、执行了什么程序 | 依赖审计策略是否开启 |
| **Prefetch / Amcache** | 什么程序访问过该文件 | 需卷未加密、程序曾运行 |

`$UsnJrnl` 在多数实战中比 `$LogFile` 更实用：它结构简单、字段清晰（文件名、父目录引用、**原因码**、时间戳），且能直接回答"**这个文件什么时候被创建/修改/删除/重命名**"。

两者结合是元数据时间线的标准打法。

**常见原因码（Reason Codes）**（用于判断操作性质）：

| 原因 | 含义 |
|---|---|
| `0x00000001` | 数据被覆盖/写入 |
| `0x00000002` | 数据被截断/扩展 |
| `0x00001000` | 旧文件名（**rename 的旧名**） |
| `0x00002000` | 新文件名（**rename 的新名**） |
| `0x00002001` | 创建 |
| `0x00002002` | 删除 |
| `0x80000000` | Close（文件关闭） |

> 成对出现的 `0x1000` + `0x2000`（旧名 + 新名）就是**一次重命名的完整指纹**——这是 NTFS 环境下认定"文件被改名过"最可靠的证据。

<a id="section-8"></a>

### 2.6 无法解析日志时，能做什么

**必须诚实面对的现实**：`$LogFile` 的完整解析是 NTFS 取证的深水区。

本篇不给字节偏移，但给三条**不依赖深度解析**的可用路径：

| 路径 | 方法 | 能得到什么 |
|---|---|---|
| **A. 状态判定** | 判断是否 Steady State（关机状态 / dirty 标志） | 确定"要不要关心日志" |
| **B. 内容直读** | 用支持 NTFS 日志的驱动读取日志（见 3.2） | 日志记录的**文本/字符串**部分（文件名常以 UTF-16 出现） |
| **C. 交叉补全** | 用 `$UsnJrnl` 补时间线，用事件日志补主体 | 元数据变化的时间与主体，**不依赖 `$LogFile` 深度解析** |

路径 B 的现实价值常被低估：日志中记录的文件名/路径以 UTF-16LE 字符串形式落盘，直接关键字搜索往往能捞出"已经不在目录树里的文件名"：

```bash
# 从 $LogFile 中提取 UTF-16 字符串（文件名常以此形式存在）
strings -e l -n 6 /evidence/LogFile.bin | sort -u > /evidence/logfile-names.txt
head -50 /evidence/logfile-names.txt

# 与当前 $MFT 树做差集 → 日志中出现但目录树里没有的名字
comm -23 /evidence/logfile-names.txt <(cut -d' ' -f7- /evidence/fls-all.txt | sort -u) | head -30
```

> **定性要求**：在日志里搜到一个名字，**只说明"这个名字曾在元数据日志中出现过"**。它可能是重命名的旧名、可能是已正常删除的文件、也可能是误报（随机字节恰好解码成可读字符）。**必须与其他证据交叉验证后才能作为结论。**

## 三、操作步骤

<a id="section-10"></a>

### 3.1 第 1 步：判断是否 Steady State

```bash
# ① 提取 $LogFile（MFT 记录 2）
icat -o 2048 /work/DigiForensics.dd 2-0-0 > /evidence/LogFile.bin
ls -l /evidence/LogFile.bin

# ② 查卷的脏标志（不同 fsstat 版本字段名略有差异）
fsstat -o 2048 /work/DigiForensics.dd | grep -iE 'dirty|state|journal|logfile'

# ③ 交叉验证：查系统是否正常关机（Windows 事件日志，逻辑而非元数据）
#    典型依据：Event ID 6006（正常关机）/ 6008（异常关机）
#    若仅有 6008 → 疑似非 Steady State，日志分析优先级提高
```

**判定表**：

| 关机事件 | 文件系统标志 | 结论 |
|---|---|---|
| 6006 正常关机 | clean | **Steady State**，元数据可信 |
| 6008 异常关机 | dirty | **非 Steady State**，需评估日志 |
| 无事件日志（已清空） | 不确定 | 以 `fsstat` 与日志状态为准，并**在报告中声明不确定性** |

<a id="section-11"></a>

### 3.2 第 2 步：尝试用工具读取日志内容

```bash
# ① 确认可用的日志感知工具（ntfs-3g 家族）
dpkg -l | grep -i ntfs-3g

# ② 前提：先按安全规范挂载工作副本（严禁主副本）
sudo mount -t ntfs-3g -o ro,noatime /work/part2.dd /mnt/ev
ls -l '/mnt/ev/$LogFile'
ntfsinfo /mnt/ev                               # 输出含日志状态
sudo umount /mnt/ev

# ③ 无论工具是否支持，都做"字符串直读"（永不失败）
strings -e l -n 6 /evidence/LogFile.bin | sort -u > /evidence/logfile-names.txt
```

> **重要**：任何需要挂载的操作都**只能在工作副本上做**（`ro,noatime` + `blockdev --setro`），详见[只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md)。**主副本严禁挂载。**

<a id="section-12"></a>

### 3.3 第 3 步：提取 MFT 条目的 LSN 并比对

```bash
# ① MFT 记录头 0x08 处的 8 字节 LSN（小端）
dd if=/work/DigiForensics.dd bs=1024 skip=$((526336/512 + 11443)) count=1 of=/tmp/mft.bin status=none
xxd -s 8 -l 8 /tmp/mft.bin          # 如：a4 12 00 00 00 00 00 00

# ② 粗看日志中的 LSN 序列（日志内 LSN 位置随版本变化，需工具确认）
xxd -l 4096 /evidence/LogFile.bin | head -40

# ③ 更实用的间接验证：时间戳交叉（路径 C）
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -E 'Created|Modified|Changed'
```

<a id="section-13"></a>

### 3.4 第 4 步：用 `$UsnJrnl` 补齐时间线

```bash
fls -o 2048 -r -p /work/DigiForensics.dd | grep -i usnjrnl        # 名称含 $UsnJrnl%3A$J
icat -o 2048 /work/DigiForensics.dd 24-128-0 > /evidence/USN.bin  # inode 取自上一行 fls 输出；通常几十 MB
strings -e l -n 4 /evidence/USN.bin | sort | uniq -c | sort -rn | head -40
strings -e l -n 4 /evidence/USN.bin | grep -nE '旧名|新名关键词'   # 紧邻成对 = 重命名指纹
```

**`$UsnJrnl` 的三个必查点**：文件名出现频次（哪些文件被反复改动）、成对出现的两个名字（**是否发生过重命名，最强证据**）、已删除文件的名字（当前树中没有但曾被操作过）。

<a id="section-14"></a>

### 3.5 第 5 步：时间戳追踪（不依赖日志的实用路径）

```bash
# 批量导出元数据（前 200 个条目，量大时分批）
for ino in $(fls -o 2048 -r /work/DigiForensics.dd | grep -oE '[0-9]+-[0-9]+-[0-9]+' | sort -u | head -200); do
  echo "=== $ino ==="
  istat -o 2048 /work/DigiForensics.dd "$ino" 2>/dev/null | grep -E 'Created|Modified|Accessed|Changed|Type'
done > /evidence/timeline-raw.txt
```

判定规则（承自 [02 篇](filesystem-ntfs-ntfs-master-file-table.md) 3.3）：

| 组合 | 推断 |
|---|---|
| `Changed` ≫ `Modified`，其余正常 | **元数据被改**（重命名 / 权限 / ADS / 移动） |
| `Modified` 变、`Changed` 不变 | 内容被修改，元数据未动 |
| `Changed` 早于 `Created` | **时间戳被篡改**（工具改时间、或时钟回拨） |
| 所有时间戳同为 0 / 1970 | 被人为清零或结构损坏 |

**最后一行值得单列**：`Changed < Created` 在正常文件系统上不应出现——它要么是时钟被回拨过，要么是时间戳被人为改过。**这类异常比"某个时间看起来可疑"更有说服力。**

## 四、常见陷阱

本章按「能力边界 → 覆盖范围与取证代价 → 结论表述」归组，每条给出：现象、为什么会误判、误判代价、正确做法。
★ 标记表示该操作会导致原始检材永久灭失或不可逆改变，执行前必须停下来确认。

<a id="section-16"></a>

### 4.1 能力边界：日志记录范围与判读限制

<a id="section-17"></a>

#### 陷阱 1：把 `$LogFile` 当成能恢复文件内容的日志

**现象**：委托方问"能不能从日志里把被删掉的合同恢复出来"，分析员在 `$LogFile` 里搜到该文件的文件名，写报告称"已从元数据日志中恢复该文件"。

**原因**：`$LogFile`（MFT 记录 2）记录的是元数据的改动过程，不记录 `$DATA` 的数据块（2.2 的记录/不记录表）。文件名、大小、时间戳、簇链描述会进日志，**文件正文一个字节都不进**。

而"在日志里看到了文件名"这个现象非常容易触发一个直觉跳跃——既然名字、大小、时间都有，看起来就差内容了，于是把"找到了元数据"当成"找到了文件"。

**影响**：**报告里出现一个无法兑现的"已恢复"**，而委托方拿到报告后不会自己去翻日志，他只会问"内容呢"。

更实际的后果是：分析员据此认为不需要再在空闲区与未分配空间里做数据恢复，而那才是内容真正可能残留的地方——**一条元数据证据挤掉了一条内容证据。**

**核查**：**把两件事拆成两步分别落地**：

```bash
# 1) 元数据侧：日志里能给出的东西
strings -e l -n 6 /evidence/LogFile.bin | sort -u > /evidence/logfile-names.txt
# 得到：曾用过的文件名、涉及过的 MFT 条目号

# 2) 内容侧：只能在空闲区/未分配空间里找，日志给不出任何线索指向内容位置
blkls -o 2048 /work/part2.dd > /evidence/unalloc.bin
# 或直接在空闲区做签名/关键字恢复
# 注：blkls 的块号范围是【位置参数】（写在镜像名之后），不是 -s 选项；
#     -s 是"只输出 slack"的布尔开关，带上它会改变输出内容而非限定范围。
```

**报告写法**："`$LogFile` 中出现文件名 `季度汇报.docx`，据此认定该文件曾存在于元数据中。本日志不含文件内容，内容是否可恢复未在本次范围内确认（未对空闲区与未分配空间做数据恢复）。"

<a id="section-18"></a>

#### 陷阱 2：Steady State 概念用反，非 Steady State 镜像按现状出结论

**现象**：镜像的 `fsstat` 报 dirty，事件日志里只有 6008 异常关机，分析员仍照常导出目录树并写"当前目录下不存在 X 文件"。

**原因**：Steady State 的定义（2.1）是"已完成的日志改动已全部落到盘上"，成立时盘上元数据 = 有效状态，不需要回放日志。

而非 Steady State 恰恰相反：可能存在"日志里有、盘上还没落"或"盘改了一半"的中间态。此时你导出的目录树既不是旧状态也不是新状态，而是一个**在时间轴上从未真实存在过的中间快照**。

而"目录树里没有"这个观察在两种状态下的含义完全不同。

**影响**：**在一个本身不自洽的快照上做否定性结论**。案例里如果镜像是非 Steady State，"当前树中没有旧名"这条证据的证明力会大打折扣——它可能只是那次崩溃把元数据改坏了。**而这条证据当时正被用作四项印证之一**，一旦被质疑，整个结论链条都要重做。

**核查**：**先判状态，再决定结论能写到多强**：

```bash
fsstat -o 2048 /work/DigiForensics.dd | grep -iE 'dirty|state|journal|logfile'
# 事件日志侧交叉验证
#   Event ID 6006 → 正常关机；6008 → 异常关机
```

| 状态 | 目录树证据的效力 | 报告必须写的话 |
|---|---|---|
| Steady State | 强，可作为否定性结论依据 | "文件系统处于 Steady State，目录树反映有效状态" |
| 非 Steady State | 弱，**不能单独支撑"不存在"** | "检材为非 Steady State（异常关机，卷标记 dirty），目录树可能为中间态，**本节否定性结论仅为初步观察**" |
| 事件日志已丢失、状态无法交叉验证 | 中 | "缺少关机事件交叉验证，Steady State 判定基于 `<指标1>`、`<指标2>` 两项间接证据" |

<a id="section-19"></a>

#### 陷阱 3：硬编码 `$LogFile` 内部字段偏移

**现象**：按网上某篇文章给出的偏移，用 `xxd -s <偏移>` 读 `$LogFile` 里某个字段，得到的值"看起来像时间"，于是拿它当时间证据。

**原因**：`$LogFile` 内部记录的字节布局随 Windows 版本变化（3.2、七章的说明都明确写了这一点）。

而"读出来了一串数字/一段看似合理的值"几乎总能得到——错误偏移读到的是别处的字节，它不会报错，只会给你一个看起来能解释的东西。这类"解析出了结果但方法是错的"比直接解析失败危险得多，因为它能通过一次粗略的合理性检查。

**影响**：**编造出来的技术细节比没有细节更糟**。一旦这类时间值写进报告，对方换一个版本的解析工具复核就会发现它对不上，而由此支撑的整个时间线都要重估。

**核查**：**只信工具对该镜像的实际输出，不信任何来源的偏移表**。本篇只给一个确定位置——MFT 记录头 `0x08` 处的 8 字节 LSN（2.3、3.3），它属于 MFT 记录结构而非日志内部结构，跨版本稳定：

```bash
# 可用：MFT 记录头 LSN
xxd -s 8 -l 8 /tmp/mft.bin

# 不可用：$LogFile 内部任何字段的手工偏移读取
# 必须用解析工具对这台机器的 Windows 版本输出
```

**做不到结构化解析时，走 2.6 的路径 B/C**——UTF-16 字符串直读 + `$UsnJrnl` 交叉补全，结论强度低于结构化解析，但**结论是站得住的**。

宁可弱，不可伪。

<a id="section-20"></a>

#### 陷阱 4：把 LogMiner 式差分结果直接当"某人在某时改了文件"

**现象**：用 2.4 的差分法在两个日志前缀下分别挂载，得出"这条元数据在这个区间被改了"，报告写"操作人于 `<推断时间>` 修改了该文件"。

**原因**：差分法的输出是**一个差集**：区间 (N, M] 的日志导致了哪些元数据变化。它**天然不含时间，也不含主体**（2.4 局限表的原文就是"不说何时变、谁变的"）。

而**挂载动作本身由分析员发起、由系统执行**，差出来的每一个差异都是文件系统响应日志回放的机械结果——它没有"人"这个维度。

**影响**：**把一个"技术过程描述"写成了"人的行为描述"**。这种结论在质证时极难维持：它要求分析员证明"这个差异对应的是一次有意的操作"，而差分法完全无法支撑这一点。

**更实际的问题是它消耗了写盘权限**——这类方法必须能写盘，代价等级本身就要求先做非破坏性路径。

**核查**：把差分结果定位为"假设生成器"，时间与主体另找证据：

```bash
# 时间侧：$UsnJrnl 的时间戳、$MFT 四时间戳、事件日志
istat -o 2048 /work/DigiForensics.dd <MFT条目号> | grep -E 'Created|Modified|Changed'
# 主体侧：登录会话、进程创建记录、审计策略开启时的对象访问事件
```

**报告写法**："差分实验表明区间 (N, M] 的日志包含对条目 `<条目号>` 的元数据改动。**该结果不提供操作时间与操作主体**，时间与主体部分见第 3.4、3.5 节的独立证据。"

<a id="section-21"></a>

### 4.2 覆盖范围与取证代价

<a id="section-22"></a>

#### 陷阱 5：★ 为了读日志内容而挂载主副本

**现象**：为了用日志感知的驱动读 `$LogFile` 的内容，在主证据副本上执行了 `mount`。

**原因**：**"只读挂载"看起来是无害的**，尤其 `$LogFile` 本身不是常规文件、很多工具对它只能干读。

但**挂载一个日志型文件系统，驱动完全可能触发日志回放**——2.1 的时间轴里"崩溃可能点② 盘改了一半"描述的那种中间态，正是回放要处理的对象。

驱动是否回放、何时回放，取决于挂载选项与驱动实现，分析员无法从命令表面预知。 而 `$LogFile` 与 MFT 之间的关系是双向的：回放会改 MFT。

**影响**：主副本被改写，而封条已拆、镜像已做、工作量已投入——证据的原始性无法再主张。 这不是"可能有点影响"，而是"在争议程序里需要单独证明的事实"被自己破坏了。而且主副本一被改写，5 章案例中那套"四项独立证据互相印证"的可靠性评估也失去了基线。

**核查**：日志回放类操作只允许在工作副本上做，且挂载前先阻断写通道：

```bash
# 1) 确认这是副本，不是主证据
sha256sum /work/DigiForensics-master.dd /work/DigiForensics-work.dd

# 2) 对工作副本加写保护后再挂载
sudo blockdev --setro /dev/loop2
sudo mount -t ntfs-3g -o ro,noatime /work/part2.dd /mnt/ev
ls -l '/mnt/ev/$LogFile'
sudo umount /mnt/ev

# 3) 主副本全程不挂载
```

"能不能读日志"这个需求，永远应该先问"能不能用 icat 把它提取出来在副本外读"——3.1 的第①步就是纯提取，不需要挂载。

很多"必须挂载"的说法，其实是没试过 `icat`。

<a id="section-23"></a>

#### 陷阱 6：把"日志里没有"当成"没发生过"

**现象**：在某份卷的 `$LogFile` 里搜某个操作的关键字，0 命中，报告写"元数据日志中未发现该文件被删除的记录"。

**原因**：**`$LogFile` 是固定大小的环形缓冲区**（2.1 的关键提醒），空间写满后最早的记录被覆盖。

"日志里没有"因此永远只等于"那条记录已被覆盖或已回收"，不等于"没发生过"。而环形缓冲的实际覆盖窗口受两个因素共同压缩：卷大小决定缓冲区上限，日常写入量决定写满的速度——一台高频使用的机器，几天就能把几 MB 的缓冲区绕满一圈。

**影响**：**把技术能力边界写成了事实否定**。委托方读到"未发现删除记录"，会合理地推断"文件没被删过、是被正常处理掉的"，从而改变整个调查方向。

而"我这里查不到"和"它没发生"之间的距离，比这段文字的长度大得多。

**核查**：**任何基于日志的否定，都要先算出覆盖窗口**：

```bash
# ① 实际体积 vs 配置上限 —— 决定还剩多少历史
ls -l /evidence/LogFile.bin
# ② 覆盖的时间窗口：用能定位到的最老记录反推
istat -o 2048 /work/DigiForensics.dd 2-0-0 | grep -E 'Created|Changed'
#    Changed = 缓冲区末端被写入的时间；缓冲区分片上界 = Created
```

**报告写法**：

> "该卷 `$LogFile` 体积为 `<X>` MB，为配置上限的约 `<Y>%`，**环形缓冲区尚未被填满**；缓冲区可定位的时间窗口为 `<起>` 至 `<止>`。**在 `<起>` 至 `<止>` 窗口内的元数据日志中，未检索到关于 `<操作>` 的记录。该窗口之外的操作记录已被环形缓冲覆盖，本次不可检索。"

注意"尚未填满"与"绕了 N 圈"是两种完全不同的证据强度：前者说明历史完整，后者说明只覆盖最近一小段。

这两个词写反，整段结论就废了。

<a id="section-24"></a>

#### 陷阱 7：用 LSN 的大小直接推断"哪条记录更新"

**现象**：比较 MFT 条目的 LSN 与日志中某操作的 LSN，用大小关系推断"这条记录更早/更晚"，并把它换算成时间线上的先后。

**原因**：LSN 是日志序列号，它表示的是"日志写入的顺序"，不是"墙上时钟的时间"（2.3）。

它的用途非常具体：判断"盘上元数据是否已经包含这条日志描述的改动"（`MFT记录.LSN >= 日志中该操作的LSN`），**这是一个技术一致性判据，不是一个时间判据**。

而 LSN 单调递增这一点**在跨卷、跨镜像之间没有可比性**——换一台机器，LSN 从完全不同的值开始。

**影响**：**用技术序号冒充时间证据**。这类推断一旦被采纳，会污染整条时间线，而它的错误具有隐蔽性：数字确实单调，看起来确实像顺序，实际上只说明顺序，不说明时间。**两个操作在日志里相邻，完全可能相隔数小时**（中间夹着大量无关记录）。

**核查**：LSN 只回答一个问题——盘上状态是否已包含日志改动：

```bash
# 取 MFT 记录头 0x08 的 8 字节 LSN（小端）
xxd -s 8 -l 8 /tmp/mft.bin
```

判读规则只有一条：MFT 条目 LSN 小于日志中该操作的 LSN，说明盘上可能仍是改动前的旧状态——这时要回到 4.1 陷阱 2 的状态判定，**不是去推断时间**。

**时间线必须由 3.4、3.5 的独立来源构建**：`$UsnJrnl` 时间戳、`$MFT` 四时间戳、事件日志、Prefetch。

LSN 出现在报告里的正确位置是"一致性判据"段落，不是"时间线"段落。

<a id="section-25"></a>

#### 陷阱 8：只靠 `$MFT` 时间戳认定"文件被改名过"

**现象**：看到 `report.docx` 的 `Changed` 晚于 `Modified` 9 秒，报告直接写"该文件于该时刻被重命名"。

**原因**：`Changed` 晚于 `Modified` 只能说明"元数据被改过、内容没动"，而元数据改动的原因不止重命名：移动位置、修改权限、增删数据流、改变属性都只更新 `Changed`。

3.5 的判定表把这一条写成了"元数据被改（重命名 / 权限 / ADS / 移动）"——**四个候选原因，现象上完全同构**。而"重命名"之所以吸引人，是因为它恰好能解释案例里新旧两个文件名并存的现象，于是分析员把一个候选当成了结论。

**影响**：**用现象的强度掩盖了归因的不确定性**。报告里"重命名"三个字一旦写进结论，委托方会直接去找"改名的人"；而如果真相是文件被移动了位置，整个责任指向就是错的。

**核查**：**用 `$UsnJrnl` 的原因码把归因做实**——这是 NTFS 环境里认定重命名最可靠的证据（2.5 的成对指纹）：

```bash
# ① 在 USN 日志中找旧名/新名，且必须紧邻
strings -e l -n 4 /evidence/USN.bin | grep -nE '旧名关键词|新名关键词' | head -20
# 14203:季度汇报.docx
# 14204:report.docx        ← 相邻成对

# ② 原因码层面的确认（需结构化解析 USN 记录）
#    0x00001000 OLD_NAME + 0x00002000 NEW_NAME 同时置位 = 一次 rename
```

**只有拿到成对指纹才能写"重命名"**。仅有 `Changed > Modified` 时，报告写法应是：

> "条目 `<号>` 的 `Changed`（`<t1>`）晚于 `Modified`（`<t2>`）`<N>` 秒，表明该文件**元数据被修改而内容未变**。造成元数据变更的原因可能包括重命名、移动、权限变更或数据流增删；本次通过 `$UsnJrnl` 独立验证到 `<已确认 / 未确认>` 的重命名指纹。"

<a id="section-26"></a>

### 4.3 结论表述：阴性发现必须限定范围

<a id="section-27"></a>

#### 陷阱 9：`$UsnJrnl` 提取全为零，判为"USN 日志不存在"

**现象**：`icat` 提取 `$UsnJrnl%3A$J` 得到一个几十 MB 的文件，前若干 KB 正常、后半段全为 0，分析员据此判"USN 日志已被清空或不存在"。

**原因**：**`$UsnJrnl` 的 `$J` 流是稀疏文件**——它的逻辑大小（`$DATA` 记录里的大小字段）反映的是当前 USN 序号决定的逻辑长度，而**实际分配的数据远小于此**，中间部分是空洞。

提取工具按逻辑大小输出，**空洞区就表现为连续的 0**。"尾部为 0"是稀疏文件的正常形态，不是被清空的证据；而 USN 记录是变长结构，实际有效数据通常集中在文件头部的已分配区。

**影响**：把一个正常的稀疏文件形态当成数据灭失，误判为反取证行为。委托方会因此被指向"有人清空了操作日志"，而实际原因只是提取方式与文件布局不匹配——**这是一个会直接导致错误责任指向的结论。**

**核查**：**看有效数据的长度，不看文件的总长度**：

```bash
# ① 定位条目并提取
fls -o 2048 -r -p /work/DigiForensics.dd | grep -i usnjrnl
icat -o 2048 /work/DigiForensics.dd 132-128-0 > /evidence/USN.bin

# ② 找最后一个非零字节位置——这才是实际有效数据长度
python3 - <<'PY'
data = open('/evidence/USN.bin','rb').read()
last = data.rstrip(b'\x00')
print('逻辑大小: %d 字节' % len(data))
print('有效数据末字节偏移: %d' % (len(last) - 1 if last else -1))
PY

# ③ 有效区才是检索对象
strings -e l -n 4 /evidence/USN.bin | grep -nE '旧名|新名' | head -20
```

**判读原则**：有效区有大量结构化记录 → 日志正常，尾部 0 是稀疏空洞；有效区为空或仅几个字节 → 才需要讨论日志被禁用或被截断。

看尾部不算判读，看最后一个非零字节才算。

<a id="section-28"></a>

#### 陷阱 10：在日志里搜到一个名字就断言"该文件存在过"

**现象**：在 `$LogFile` 的 UTF-16 字符串里搜到 `季度汇报.docx`，报告直接写"元数据日志证实该文件曾经存在"。

**原因**：2.6 已经写明这条定性要求——在日志里搜到一个名字，只说明"这个名字曾在元数据日志中出现过"。

它可能是重命名的旧名（说明现在这个名字曾被占用）、可能是已正常删除的文件、也可能是**随机字节恰好解码成可读字符的误报**。

`strings` 没有任何校验能力，它不认识 NTFS 记录边界，也不知道哪些字节是字段、哪些是填充。

**影响**：**单源孤立证据被当成结论**。这类"看起来是硬证据（直接从系统元数据日志读出来的）"反而最危险——它有技术含量，容易被采信，也最容易被推翻。

**核查**：**多源交叉，且至少一条独立于 `$LogFile`**：

| 独立数据源 | 交叉价值 |
|---|---|
| **`$UsnJrnl`** | 结构化记录 + 原因码，能区分"创建/删除/重命名" |
| **当前 `$MFT` 树** | 证明该名字**现在不在这棵树里**（差集才有意义） |
| **`$MFT` 四时间戳** | 提供可核对的窗口 |
| **事件日志 / Prefetch** | 提供时间与主体（若审计策略开启） |

```bash
# 差集：日志里有、当前树里没有
comm -23 /evidence/logfile-names.txt <(cut -d' ' -f7- /evidence/fls-all.txt | sort -u) \
  > /evidence/only-in-logfile.txt
```

**报告写法**："名字 `季度汇报.docx` 出现于 `$LogFile` 与 `$UsnJrnl` **两个相互独立的数据源**，且不存在于当前 `$MFT` 树中。综合判定：该文件曾存在于元数据中，且当前已不在目录树内。具体操作类型（删除 / 重命名 / 移动）由 `$UsnJrnl` 原因码判定为 `<类型>`。"

<a id="section-29"></a>

#### 陷阱 11：只按目录树枚举就判"没有隐藏系统文件"

**现象**：`fls` 输出干净，报告写"该卷未发现异常或隐藏的系统元数据文件"。

**原因**：**NTFS 卷上的系统元数据文件不全在目录树里**。`$MFT`（0）到 `$Extend`（11）是经典系统文件，编号 12–15 是**保留区间**（落在该区间的记录号不对应有效文件），而 Windows 10/11 会在经典编号之外放置若干系统文件（如 `$RSTR`、`$RCDH` 一类），它们不参与常规目录枚举，`fls` 之类的目录遍历工具不会列出它们。

因此"目录里没有"与"MFT 里没有"是两个命题。

**影响**：范围不足的否定性结论。**在本篇语境下它还有一个具体后果**：元数据变化追踪依赖对 MFT 的整体认知，漏掉这些条目意味着对"哪些元数据被谁维护"缺少一层认知，归因时会把系统自身的元数据维护行为误读成第三方行为——这在反取证场景下是双向出错。

**核查**：要否定"MFT 里没有隐藏系统文件"，必须直接遍历 MFT 记录号：

```bash
# 目录遍历看不到它们；要按记录号逐个探
for i in $(seq 12 23); do
  echo "--- record $i ---"
  istat -o 2048 /work/DigiForensics.dd $i-0-0 2>/dev/null | head -5
done
```

**报告写法**："以目录树枚举（`fls` 全量输出）为依据检查，未发现非系统文件的隐藏条目。**MFT 记录号 12–23 区间另行逐条探测**，其中存在 Windows 系统元数据文件 `<列表>`（编号 12–15 为 NTFS 保留区间，不对应有效文件）。**该类文件的存在属系统正常行为，不作为异常指标。**"

<a id="section-30"></a>

#### 陷阱 12：非 Steady State 却不声明状态，直接出时间线

**现象**：镜像为异常关机状态，报告里给出了一条精确到秒的"删除时间"来自 `$UsnJrnl`，全文没有任何关于文件系统状态的说明。

**原因**：这在方法上不算技术错误——**USN 记录自带时间戳，可以直接用**。

问题在于**它省略了一个会改变结论解读方式的前提**：非 Steady State 意味着盘上元数据可能处于中间态，而"USN 说 A 时刻发生了 B 操作"与"盘上现在反映 B 操作的结果"是两件事。不做声明，读者会把 USN 时间当成对现状的完整解释。

**影响**：**报告的可辩护性受损**。对方只需指出"卷处于 dirty 状态，你没有评估日志回放"，整份报告的严谨性就会受到质疑——而这条质疑本身无法通过补写一段说明来消除，只能靠事先就写清。

**核查**：**结论表述与状态判定绑定**，无论结论是否依赖日志：

> "**检材状态**：`<正常关机 / 异常关机>`，卷标记 `<clean / dirty>`，判定为 `<Steady State / 非 Steady State>`。事件日志 `<存在 / 已丢失>`，本次 Steady State 判定依据为 `<指标列表>`。
> **元数据变化结论**：`<结论>`，由 `$UsnJrnl`（原因码 `<码>`）与 `$MFT` 时间戳（`<四时间戳>`）互相印证。
> **不确定性声明**：`<USN 记录时间字段未做结构化解析 / 事件日志缺失 / 无第三个独立时间源>`，因此本报告不声称精确到秒的操作时刻，仅给出 `<时间窗口>`。"

这段声明的价值不在于它说了什么，而在于它标出了结论的边界在哪里——这正是阴性发现与元数据结论唯一能被安全使用的方式。

补写补救不了，只能事先写。

## 五、案例示例

<a id="section-32"></a>

### 5.1 事件日志已丢失时改名的认定：四项独立证据互相印证

**场景**

查获 Windows 10 笔记本（NTFS，簇大小 4096）。委托要求：确认 `C:\Users\Public\report.docx` 是否被改名后重新归档，并给出操作时间。镜像 `DigiForensics.dd`（raw，500 GB），NTFS 分区起始扇区 2048。**事件日志已随系统重装丢失**。

委托方要一个确定的操作时间。选择这一路径的依据是常规的"Shutdown Event ID 6006/6008 + $UsnJrnl"双源印证法在这里少了一条腿——必须靠剩下的工件重建，并且明确交代缺了什么。

**处置过程**

**第 1 步 · 判断文件系统状态**：

```bash
icat -o 2048 /work/DigiForensics.dd 2-0-0 > /evidence/LogFile.bin
ls -l /evidence/LogFile.bin        # 1.9 MB（远小于常见上限 → 未被填满，近期日志在）
fsstat -o 2048 /work/DigiForensics.dd | grep -iE 'dirty|state|logfile'
# 未报 dirty → 文件系统状态干净
```

因事件日志已丢失，**无法用关机事件交叉验证**，改用第二独立指标：`$LogFile` 体积仅为配置上限的约 3%，且 MFT 条目 2 的 `Changed` 时间等于系统最后一次正常活动时间。

**两项指标一致支持 Steady State 判定**，报告中如实写明"缺少事件日志交叉验证"。

第 2 步 · 提取 `$UsnJrnl`（关键动作）：

```bash
fls -o 2048 -r -p /work/DigiForensics.dd | grep -i usnjrnl
# r/r  132-0-0:  $FILE_NAME  38,797,696  2025-09-02 08:14:33  $UsnJrnl%3A$J

icat -o 2048 /work/DigiForensics.dd 132-0-0 > /evidence/USN.bin
ls -l /evidence/USN.bin            # 37 MB，环形缓冲，覆盖最近约 3 天操作
strings -e l -n 4 /evidence/USN.bin | grep -iE 'report|季度|汇总' | sort -u
# 季度汇报.docx          ← 当前树中不存在
# report.docx            ← 当前树中存在
```

两个高度相关的名字在日志中**紧邻出现**，这是重命名序列的典型形态：

```bash
strings -e l -n 4 /evidence/USN.bin | grep -nE '季度汇报\.docx|report\.docx' | head -20
# 14203:季度汇报.docx
# 14204:report.docx          ← 典型的"旧名 + 新名"重命名序列
```

第 3 步 · 用 `$LogFile` 作独立验证：

```bash
strings -e l -n 6 /evidence/LogFile.bin | sort -u > /evidence/logfile-names.txt
comm -23 /evidence/logfile-names.txt <(cut -d' ' -f7- /evidence/fls-all.txt | sort -u) | grep -iE '报告|report'
# 季度汇报.docx          ← 元数据日志中同样出现
```

两个相互独立的数据源（`$UsnJrnl` 与 `$LogFile`）都记录了"季度汇报.docx"这个当前不存在的名字。

这是本案能写到"改名"两个字的基础：少了任一源，都只能写成"曾出现过某个旧名"。

**第 4 步 · 定位当前文件并核对时间戳**：

```bash
fls -o 2048 -r -p /work/DigiForensics.dd | grep -i 'report.docx'
# r/r  11443-128-3:  $FILE_NAME  24576  2025-08-28 16:42:07  report.docx

istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -E 'Created|Modified|Changed|Accessed'
# Created:  2024-03-11 09:22:41    Accessed: 2025-09-02 08:03:11
# Modified: 2025-08-28 16:41:58    Changed:  2025-08-28 16:42:07  ← 晚 9 秒 = 元数据被改
```

`Changed` 晚于 `Modified` 9 秒，与"重命名"特征一致——改 `$FILE_NAME` 会更新 `Changed`，不更新 `Modified`。

**第 5 步 · 确定时间范围（不声称精确时刻）**：USN 记录为变长结构，其时间字段偏移需按版本验证，本案例**未做结构化解析，因此不声称精确到秒的重命名时间**，改用可验证的窗口表述：

```bash
istat -o 2048 /work/DigiForensics.dd 132-0-0 | grep -E 'Created|Changed'
# Created: 2025-08-28 00:00:11（缓冲区起始）   Changed: 2025-09-02 08:14:33（末端）
```

**结论**

能证明重命名事实成立，四项独立证据互相印证：①`$UsnJrnl` 中新旧名紧邻出现；②`$LogFile` 独立记录同一旧名；③`Changed` 晚于 `Modified` 9 秒；④旧名不在当前 `$MFT` 树中。时间窗口收敛到 **2025-08-28 当日**，由 `Changed` 时间与 USN 缓冲区覆盖区间共同界定。

**不能证明**：①本报告**不声称精确操作时刻**——USN 时间字段未解析、事件日志已丢失，缺第三个独立时间源；②**元数据证据 ≠ 内容证据**，结论仅涉及"被改名并归档"，**未涉及内容是否被修改**。

这两条限制必须与结论同页出现。

**误判对照**

最像的误判是把"$UsnJrnl 里旧名和新名紧邻"直接写成"该文件在 2025-08-28 16:42:07 被改名"。

判据要落在两个时间字段的差别上：`$UsnJrnl` 是变长结构记录，其时间戳位于记录体的可变偏移处，不解析就取不到——本案第 2 步用的是 `strings` 关键字搜索，它只能证明"这两个名字在缓冲区里相邻"，不能给出时间。

而 `16:42:07` 这个值来自**当前 MFT 条目的 `Changed` 字段**，它是改名那一刻留下的元数据时间，本身有效，但不能代表 USN 记录的时间。

正确判据是改名时刻用 MFT 的 `Changed`，覆盖区间用 USN 缓冲区边界，两者角色不同不可混用。按错误判据走的代价：委托方拿一个精确到秒的时间去比对门禁或监控，而那 9 秒的精度差会让"人不在场"的论证失效——若对方成功举证该秒内当事人在另一处，整个改名归属的结论链条都会被动摇。

<a id="section-33"></a>

### 5.2 `$LogFile` 只有 1.9 MB 意味着什么：不能当作无操作

**场景**

同一案件中，另一台机器的 `$LogFile` 只有 1.9 MB（配置上限的约 3%），分析员据此判断"这台机器近期几乎没有元数据变更"。委托方恰恰提供了相反的线索：这台机器近期做过大量文件整理。

这条路径值得写下来，是因为"日志很小"最容易被读成"没发生什么"，而它实际只说明"日志没被填满"。

**处置过程**

1. 先确认体积基准，避免拿绝对值当结论：

```bash
icat -o 2048 /work/DigiForensics.dd 2-0-0 | wc -c          # 1.9 MB 当前体积
fsstat -o 2048 /work/DigiForensics.dd | grep -iE 'logfile|cluster'
```

2. 判断它是否已绕回：环形缓冲只有在**写满并绕回**时才会丢弃旧记录；未写满意味着**缓冲区起始位置之后的所有记录都还在**。

```bash
istat -o 2048 /work/DigiForensics.dd 2-0-0 | grep -E 'Created|Changed'
# Created = 缓冲区起始时刻    Changed = 最后一次写入时刻
# 起止区间 = 缓冲区当前实际覆盖的时间窗
```

3. 在这个时间窗内提取名字做差集，`$LogFile` 里没有出现的名字才是"已被覆盖"的：

```bash
strings -e l -n 6 /evidence/LogFile.bin | sort -u > /evidence/logfile-names.txt
comm -23 /evidence/logfile-names.txt <(cut -d' ' -f7- /evidence/fls-all.txt | sort -u)
```

4. 委托方所说的大量整理操作，在缓冲区覆盖的时间窗内确实可见。

**结论**

能证明：`$LogFile` 未被填满，因此其覆盖区间内的元数据变更记录完整保留；该区间内的名字差集可作为"曾存在过的文件名"证据来源。委托方所述的文件整理操作在该区间内可见。

**不能证明**：缓冲区覆盖区间**之外**的任何操作——那些记录已在更早的绕回中被覆盖，物理上不存在了。

这属于**因环形缓冲机制而不可恢复的范围**，须在报告中列明。

**误判对照**

最像的误判是把"$LogFile 只有 1.9 MB"当成"近期无文件操作"。

判据要落到环形缓冲的机制上：`$LogFile` 是固定大小的环形缓冲，它不会因为没操作而缩小，它只有两种状态——没写满（保留从缓冲区起始至今的全部记录）和写满绕回（只保留最近的一个窗口）；1.9 MB 这个数字恰恰说明它是**没写满**，也就是说近期记录一条没丢。

判据还应配一个反向检查：`$LogFile` 为空或极小（远低于 1 MB）才是异常信号，那通常意味着文件系统异常或日志被清。

正确判据是**先判断是否绕回，再据此确定可覆盖的时间窗**。按错误判据走的代价是给出方向性相反的结论——报告写"近期无大量文件操作"，而委托方的证据（理化时间线）指向相反方向，整份报告的元数据部分被整体否信。

<a id="section-34"></a>

### 5.3 反例：把 `$UsnJrnl` 当作已解析出精确时间的证据

**场景**

某次分析中，分析员在 `$UsnJrnl` 里用 `strings` 找到目标文件名后，直接引用同一缓冲区中另一个位置出现的一个 8 字节时间值，写进报告作为"该文件被重命名的时刻是 22:41:33"。复核方按 USN_RECORD_V2 结构解析后发现该值并不属于任何一条有效记录的时间字段。

这条列为反例，是因为它给出的答案看起来精确、格式规范、无法从报告本身看出问题。

**处置过程**

对照点在于"提取到了名字"与"解析出了时间"之间的距离：

```bash
# 只做了这一步：得到的是"字符串在缓冲区里出现过"
strings -e l -n 4 /evidence/USN.bin | grep -i 'report.docx'

# 要得到时间，必须按版本解析记录头：
# USN_RECORD_V2 结构：RecordLength(4) | MajorVersion(2) | MinorVersion(2)
#                      | FileReferenceNumber(8) | ParentFileReferenceNumber(8)
#                     | Usn(8) | TimeStamp(8) | Reason(4) | ...
# 且记录变长，必须先读 RecordLength 才能定位下一条
```

3. 关键自检：`$UsnJrnl` 的前 4 字节不是记录，而是 USN_RECORD_V2 的文件头，从 `0x04` 才是第一条记录；**跳过这一步会导致全部记录错位**。

**结论**

阴性发现：本案该时间值**不能归属于任何一条有效 USN 记录**，从报告中撤回，改为按缓冲区边界给出时间窗口结论。撤回动作本身已记入分析日志。

**误判对照**

最像的误判是把 `strings` 命中的上下文里的时间值当成结构化解析的结果。

判据在数据形态上：`strings` 输出的是连续的 ASCII 序列，它会跨越记录边界，把 A 记录的某个字段尾巴和 B 记录的开头拼在一起——一个 8 字节的 FILETIME 在 `strings -e l` 下恰好可能呈现为可读字符，任何位置出现的"看起来像时间"的数字都可能属于完全无关的记录。

正确判据是只有按 `RecordLength` 逐条走过的记录，其时间戳字段才能引用。按错误判据走的代价：一个来源不明的时间点被写进正式报告，而这类错误在复核时几乎无法自证清白——对方只需问"这个值出自哪条记录的哪个字段"，答不上来整条时间线都要重新核对。

## 六、扩展阅读方向

按"解决什么问题"分成五组。

<a id="section-36"></a>

### 前置基础

- [NTFS 结构与 MFT 解析](filesystem-ntfs-ntfs-master-file-table.md) —— **本篇每个操作都在消费那篇的输出**：LSN 字段位置、`$STANDARD_INFORMATION` 布局、记录号与文件引用号换算。日志解析的难点几乎全在 MFT 侧。
- [文件系统取证总览](filesystem-ntfs-filesystem-forensics-overview.md) —— 确认分区参数（簇大小、`$MFT` 位置）以及"哪些是元数据、哪些是数据"的划分，避免把 `$LogFile` 当成可雕刻的数据区。

<a id="section-37"></a>

### 同层深入

- [UsnJrnl 与文件操作时间线](../../computer/computer-execution/computer-execution-usn-journal-timeline.md) —— **解决原因码怎么落到时间线上**。本篇只做"新旧名相邻出现"这类粗判，原因码全表、记录结构与多条记录合并成一次操作的技术在那篇。
- [NTFS 数据流与隐藏数据](filesystem-ntfs-ntfs-alternate-data-streams.md) —— **解决"日志还原出的元数据指向的文件内容去哪找"**。命名流被删时 `$MFT` 已无记录，日志能补上元数据，但内容仍在数据区那侧。
- [时间戳换算](../../fundamentals/fundamentals-concepts/fundamentals-concepts-timestamps-and-timezones.md) —— **解决"日志里的时间戳该按哪个时区解读"**。FILETIME 是 UTC，USN 记录时间字段另有编码，**把二者当成本地时间会让整条时间线整体偏移**。

<a id="section-38"></a>

### 相邻议题

- [ext4 结构与 inode](../filesystem-unix/filesystem-unix-ext4-inode.md) —— **横向对照"另一个日志型文件系统怎么做同样的事"**。ext3/4 的 journal 是写入日志后原位写回，语义与 NTFS REDOP 相反；同一个问题在两边答案不同，混淆会得出反向结论。
- [系统日志深度分析](../../computer/computer-log/computer-log-system-log-analysis.md) —— **解决"关机状态怎么交叉验证"**。事件日志 6006 / 6008 是判断 Steady State 最可靠的独立指标；该文给的是 Linux 侧方法，Windows 事件日志的对应位置在此类。
- [时间线重建](../../computer/computer-log/computer-log-linux-timeline-reconstruction.md) —— **解决"多个日志源的时间怎么合并"**。本篇产出的是窗口与顺序，跨源归一化与矛盾点处理在那篇。

<a id="section-39"></a>

### 工具与规范

- `icat` 提取记录 2 与记录 132 的完整命令见[命令速查](#section-41)——注意记录 2 的 `$DATA` 与 `$J` 是两个地址，取错一个会拿到全零。
- 报告写法上，"检材状态 / 元数据变化结论 / 不确定性声明"三段式是本篇最值得直接复用的模板，见[案例示例](#section-31)的结论段。**不确定性声明不写，报告在质证环节会被质疑。**
- 证据固定与操作留痕见[取证流程与原则](../../fundamentals/fundamentals-process/fundamentals-process-five-stage-forensics-process.md)——**从日志提取数据同样要哈希固定**，尤其在工具版本不确定时（同一份日志不同解析器输出可能不同）。

<a id="section-40"></a>

### 判据与反例

- **判据一**：元数据结论必须两个独立源支撑。`$UsnJrnl` 与 `$LogFile` 互为独立；**同一源里"名字出现两次"不算两处证据**。
- **判据二**：非 Steady State 时的还原结论强度降级。未提交事务意味着日志里混有未落盘的操作，直接当作事实写入会出错。
- **反例一**：把"报告里说本报告不声称精确时刻"理解成免责套话而略去。**这句话本身就是要交付的结论强度声明**，省略它等于让读者自行高估精度。
- **反例二**：日志里捞到一个已不存在的文件名，就写"该文件曾存在并被删除"。也可能是改名、也可能是移动到别处、也可能是本就在另一个卷——三种解释不能只挑一种写。
- **反例三**：把元数据证据升格成内容证据。"`Changed` 晚于 `Modified` 9 秒支持重命名"是对的；"因此文件内容未被修改"是错的——**内容改完再改名，元数据会同时更新**。
- **反例四**：用 `strings` 捞出 USN 里的文件名就宣称拿到了操作时间。**`strings` 只能出名字，出不来时间**；时间在变长结构的字段里，未解析就声明时间就是编造。

## 七、命令速查

```bash
# ===== 环境 =====
sudo apt install sleuthkit ntfs-3g e2fsprogs file xxd
# -o 2048 为 NTFS 分区起始扇区，替换为 mmls 实际值

# ===== 判断 Steady State =====
icat -o 2048 /work/DigiForensics.dd 2-0-0 > /evidence/LogFile.bin   # MFT 记录 2
ls -l /evidence/LogFile.bin                                            # 体积 vs 上限 → 是否被覆盖
fsstat -o 2048 /work/DigiForensics.dd | grep -iE 'dirty|state|logfile'
# 交叉验证：Windows 事件日志 Event ID 6006(正常关机) / 6008(异常关机)

# ===== 日志内容直读（不依赖结构解析）=====
strings -e l -n 6 /evidence/LogFile.bin | sort -u > /evidence/logfile-names.txt
comm -23 /evidence/logfile-names.txt <(cut -d' ' -f7- /evidence/fls-all.txt | sort -u) \
     > /evidence/only-in-logfile.txt        # 日志中有、当前树中无的名字
xxd -l 4096 /evidence/LogFile.bin | head -40  # 粗看 LSN 序列（字段位置需按版本验证）

# ===== MFT 条目的 LSN =====
dd if=/work/DigiForensics.dd bs=1024 skip=$((526336/512 + 11443)) count=1 of=/tmp/mft.bin status=none
xxd -s 8 -l 8 /tmp/mft.bin                  # MFT 记录头 0x08 处 8 字节 LSN（小端）

# ===== $UsnJrnl（实战主力）=====
fls -o 2048 -r -p /work/DigiForensics.dd | grep -i usnjrnl    # 名称含 $UsnJrnl%3A$J
icat -o 2048 /work/DigiForensics.dd 132-0-0 > /evidence/USN.bin
istat -o 2048 /work/DigiForensics.dd 132-0-0 | grep -E 'Created|Changed'   # 覆盖时间窗口
strings -e l -n 4 /evidence/USN.bin | sort | uniq -c | sort -rn | head -40
strings -e l -n 4 /evidence/USN.bin | grep -nE '旧名|新名关键词'   # 紧邻成对 = 重命名指纹

# ===== 时间戳追踪（不依赖日志）=====
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -E 'Created|Modified|Accessed|Changed'
#   Changed ≫ Modified  → 元数据被改（重命名/权限/ADS）
#   Changed < Created   → 时间戳被篡改或时钟异常（正常系统不会出现）

# ===== 工作副本挂载（仅当工具支持时；严禁主副本）=====
sudo mount -t ntfs-3g -o ro,noatime /work/part2.dd /mnt/ev
ls -l '/mnt/ev/$LogFile'
sudo umount /mnt/ev
```

```powershell
# ===== Windows：查询日志相关状态 =====
fsutil usn queryJournal C:            # USN 日志大小与 Next Usn
fsutil dirty query C:                 # 卷脏标志（dirty = 非 Steady State）
```

> **说明**：`$LogFile` 内部记录的字节级布局随 Windows 版本变化，本篇刻意不提供偏移表。上述命令中唯一给出确定偏移的是 **MFT 记录头的 LSN（0x08，8 字节）**——它属于 MFT 记录结构而非日志内部结构，跨版本稳定。任何涉及 `$LogFile` 内部字段的位置，都应以所用解析工具对该版本镜像的实际输出为准。
