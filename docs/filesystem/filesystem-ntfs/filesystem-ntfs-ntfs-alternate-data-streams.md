# NTFS 数据流（ADS）与隐藏数据

<a id="section-1"></a>

## 一、概述

NTFS 上"一个文件"并不等于"一份内容"。同一个文件对象可以挂载**多个独立的 `$DATA` 流**：一个是匿名流（文件名能看到的那份），其余全是命名流（Named Stream），通过 `文件名:流名` 访问。

由此产生一个反直觉的事实：`dir` 看到的文件清单与磁盘上实际存在的数据流数量完全不对应。一个 0 字节的 `readme.txt` 可以在磁盘上带着 2 MB 的 `readme.txt:hidden` 流——资源管理器、多数取证工具的默认视图、`ls` 全都看不见它。

更麻烦的是三条：**命名流大小上限等于卷大小**（可远超主文件）、**各流的数据区域彼此独立，但共享同一条 MFT 记录的生命周期**（删除整个文件会连同全部命名流一起删除；只有单独删除某条命名流才只删该流）、**默认流可以是空的**（内容挪进命名流即可规避"按大小"的内容检查）。

这一层挖掘在分析环节的扩展挖掘阶段，位置是 [NTFS 结构与 MFT 解析](filesystem-ntfs-ntfs-master-file-table.md) 之后——那里读的是 `$DATA` 属性的正常形态，这里读的是它能承载的东西。往下的空间是四个逐层加深的藏匿层次：

| 层次            | 机制         | 隐蔽性   | 检出难度                  |
| ------------- | ---------- | ----- | --------------------- |
| 命名流（ADS）      | 文件系统原生特性   | ★★★   | ★★ `istat` / `fls` 可查 |
| `$I30` 索引目录   | 目录项的排序结构   | ★★★   | ★★★ 需解析 `INDX`        |
| Slack / 未分配空间 | 簇内 / 空闲簇残留 | ★★★★  | ★★★ 需按块提取 + 搜索        |
| 隐写术           | 合法格式内嵌密文   | ★★★★★ | ★★★★★ 需格式感知           |

**这个顺序本身就是检出成本递增的顺序**。前两层是确定性的（枚举即可），第三层需要提取加搜索，第四层需要格式知识。报告里把这四层的覆盖情况分别写清，比笼统说一句"已全面检查"有用得多。

上游是元数据判读。下游两个方向：找到载体之后的内容提取与验证，以及——如果检出的是恶意载荷，如何在不做在线分析的前提下完成定性（这属于内容边界，这里只讲检出与提取）。

落到具体证据上：

- **`文件名:流名` 的访问语法** —— 命名流的标识方式。**流名几乎可含任意字符**，历史上存在 `file.txt:..\..\dir` 形式的路径穿越用法，**不要假设流名是干净的**
- `file.txt:Zone.Identifier` —— 浏览器下载文件的系统标记，含 ZoneId 与来源 URL。**这是正常现象，不是恶意证据**。判断 ADS 是否恶意必须提取内容并验证
- **`file.txt:$DATA`** —— 等价于默认流，某些工具的显式写法
- **`$I30` 索引与 `INDX` 缓冲区** —— 目录项的排序结构。**`INDX` 不是 MFT 记录**（`istat` 里 MagNum 字段区分），这是[NTFS 结构与 MFT 解析](filesystem-ntfs-ntfs-master-file-table.md)2.2 那张魔数表里最容易误判的一项
- **Slack space** —— 文件长度不是簇大小整数倍时尾部剩余的字节。**在已分配簇内部**，`blkls` 不含此项，需按簇读取后自行截取
- **未分配空间** —— 空闲簇与空闲簇链，`blkls` 直接输出。**与 slack 的区别很重要**：前者在文件系统外部，后者在内
- `DigiForensics.dd` 的 `blkls -o 2048` 输出 —— 未分配块提取。注意**卷层的未分配与文件系统层的未分配是两回事**
- **隐写载体** —— PNG 的 `IEND` 之后、JPEG 的 `FFD9`（`EOI`）之后、GIF 的 `0x3B` 之后、PDF 的 `%%EOF` 之后、BMP 声明尺寸小于实际大小、OLE 复合文档的未使用流。它们的共同点是文件本身完全正常，双击能打开，校验和也正确

走完这一层能回答的是这些：一个文件对象到底带几个数据流、目录里哪些条目是"幽灵文件"、slack 与未分配空间该分别怎么提取、以及**为什么"文件被覆盖"不等于"旧版本彻底消失"**（slack 里往往还残留更早版本的内容）。

2.4 讲了 slack 为什么有东西：文件系统只把"声明长度"以外的部分当作可复用，**读取旧内容前不会清零**。同理，删除文件的真实过程有四步，**第四步"簇内数据本身不被清零"才是取证的根本前提**——内容还在，只是"不再被任何文件引用"。

有几件事不归这一层管：**提取出来的内容说明什么**，解读要看具体载体类型；**这是不是恶意载荷的定性**，2.6 那句区分最重要——"PNG 的 `IEND` 之后有数据"是客观事实；"这是攻击者藏的命令"需要提取、解码、验证，这两层在报告里必须分开写；**簇链已经断了怎么恢复文件**走文件雕刻路线，见[文件雕刻与签名恢复](../filesystem-unix/filesystem-unix-file-carving-and-signature-recovery.md)；**加密流怎么读**看属性标志里的加密位，见[EFS 文件系统加密取证](../../crypto/crypto-volume/crypto-volume-efs.md)。

往下读之前必须先掌握 [NTFS 结构与 MFT 解析](filesystem-ntfs-ntfs-master-file-table.md)——**这里的每一层都建立在 MFT 属性结构之上**：命名流是 `$DATA` 属性的名称字段、`$I30` 是目录的 `$DATA` 内容、slack 依赖 `$DATA` 声明长度与簇大小。

另外需要**十六进制查看与搜索的基本功**（`xxd`、`strings`、`grep -aob`）——核心操作大量是"提取一块区域然后搜关键字"，这个动作本身不难，但**偏移算错就读到别的地方去了**。

四层机制的检出原理在[核心原理](#section-2)，对应的命令链在[操作步骤](#section-9)。准备动手前建议先扫一遍[常见陷阱](#section-16)——需特别检查提取结果的对象类型，避免将不同数据流混同。完整走一遍的参考流程见[案例示例](#section-34)，四层命令的直接抄写见[命令速查](#section-44)。

## 二、核心原理

<a id="section-3"></a>

### 2.1 `$DATA` 属性：匿名流与命名流

回到 MFT 的 `$DATA` 属性（类型 0x80），它的**名称字段**决定了它是哪一个流：

| 类型           | 名称长度字段       | 访问语法                               | 内容                   |
| ------------ | ------------ | ---------------------------------- | -------------------- |
| **匿名流（默认流）** | **0**        | `type report.docx`                 | 文件的正文，**每个文件有且仅有一个** |
| **命名流（ADS）** | > 0，UTF-16LE | `type report.docx:Zone.Identifier` | 附加内容，可为任意大小          |

**关键点**：

1. **命名流名几乎可含任意字符**（历史上存在 `file.txt:..\..\dir` 形式的路径穿越用法），**不要假设流名是干净的**。
2. **命名流大小上限 = 卷大小**，可远超主文件；**各流的数据区域彼此独立，但共享同一条 MFT 记录**——删除整个文件会连同全部命名流一并删除（微软《File streams》：*"When delete access is requested on a file, the operating system checks for delete access on all open streams in a file"*），只有单独删除某条命名流才只删该流。
3. **默认流可以是空的**（0 字节）——内容挪进命名流即可规避"按大小"的内容检查。
4. "备用数据流"是历史遗留叫法：早期服务 Macintosh 双机互联，现被大量滥用为隐藏载体。

| 流名约定                       | 常见用途                                    |
| -------------------------- | --------------------------------------- |
| `file.txt:$DATA`           | 等价于默认流，某些工具的显式写法                        |
| `file.txt:Zone.Identifier` | 浏览器下载文件的系统标记，含 ZoneId 与来源 URL（**正常现象**） |
| `file.txt:$J` / 其他自定义名     | 恶意载荷、配置、加密容器                            |

> **注意**：`Zone.Identifier` 是**正常现象**，不是恶意证据。判断 ADS 是否恶意必须**提取内容并验证**，不能仅凭"存在 ADS"定性。

<a id="section-4"></a>

### 2.2 命名流对系统工具的可见性

**哪些工具能看到 ADS，哪些看不到**——这决定了"用常规方法查过"到底意味着什么：

| 工具/接口                    | 默认流 | 命名流                       |
| ------------------------ | --- | ------------------------- |
| Windows 资源管理器            | ✅   | ❌ 完全不可见                   |
| `dir`（cmd 默认）            | ✅   | ❌（需 `/r` 参数）              |
| PowerShell `Get-Content` | ✅   | ✅ 用 `-Stream` 参数（PS 5.0+） |
| Python `open()`          | ✅   | ✅ 传 `file:stream` 路径      |
| `fls` / `istat`（TSK）     | ✅   | ✅ 列出 `file.txt$DATA` 形式条目 |
| Autopsy / FTK Imager     | ✅   | ✅ 需切到数据流视图                |
| 多数"快速取证"脚本               | ✅   | ❌ 常漏                      |

```powershell
# Windows 原生枚举 ADS（PowerShell 5.0+）
Get-Item -Path 'C:\inetpub\wwwroot\default.aspx' -Stream *
Get-Content -Path 'C:\inetpub\wwwroot\default.aspx' -Stream 'hidden'
```

**取证含义**："常规文件遍历没发现异常"不能作为"无隐藏数据"的结论。 判定必须基于 `istat` 的属性列表（见操作步骤 3.2），而不是文件管理器视图。

<a id="section-5"></a>

### 2.3 `$I30`：把目录变成排序索引

NTFS 的目录不只是"文件名列表"，它同时是一个 **B+ 树索引**，索引内容存在名为 `$I30` 的**命名 `$DATA` 流**里（这是一个例外：通常 `$DATA` 存内容，但目录的 `$DATA` 存的是 `$I30` 索引）。

索引记录（`INDX` 缓冲区）的关键点：

| 项目   | 说明                              |
| ---- | ------------------------------- |
| 魔数   | `INDX`（49 4E 44 58）             |
| 作用   | 让 `dir` 能按名字排序、让查找 O(log n)     |
| 存储位置 | 目录 MFT 记录的 `$DATA` 命名流 `$I30`   |
| 条目内容 | 文件名（8.3 名 + Win32 名）、MFT 引用、时间戳 |

**取证价值与风险**：

- **价值**：删文件时 `$MFT` 条目被标记删除，但 **`$I30` 索引条目可能仍残留**——它提供了"目录里曾经有过哪些文件名"的独立线索。
- **风险**：索引与 `$MFT` 可能**不一致**。工具改名后只改 `$MFT` 不改索引（反取证常见做法），会出现**"目录树里没有、但索引里有"**的幽灵文件——这正是"文件被隐藏"的检测信号。
- **必须提取原始 `INDX` 缓冲区人工比对**，因为主流工具通常只呈现 `$MFT` 视角。

```bash
icat -o 2048 /work/DigiForensics.dd 5-0-0 > /tmp/root-i30.bin   # 目录的 $DATA 流就是 $I30
xxd -l 4 /tmp/root-i30.bin     # 期望看到 49 4E 44 58 = "INDX"
```

<a id="section-6"></a>

### 2.4 Slack Space：簇内的"边角料"

若文件长度不是簇大小的整数倍，**尾部剩余字节就是 slack**：

```
簇 0（4096 字节）
┌────────────────────────────────────────┐
│ 文件数据 3500 字节（$DATA 声明的真实大小）│
├────────────────────────────────────────┤ ← slack：596 字节
│ ★ 前一个文件的残影 / 已删文件 / 密钥    │
└────────────────────────────────────────┘
```

**为什么 slack 里有东西**：文件系统只把"声明长度"以外的部分当作可复用，**读取旧内容前不会清零**，所以前一次占用该簇的文件内容会原样留在 slack。检出方法是逐簇提取 slack 做关键字/结构搜索。**注意陷阱**：文件被覆盖时，slack 里往往还残留**更早版本**的内容。

**Slack 与"未分配空间"的区别很重要**：

|      | Slack space             | 未分配空间（unallocated） |
| ---- | ----------------------- | ------------------ |
| 所在   | **已分配簇内部**              | 空闲簇 / 空闲簇链         |
| 提取方式 | `blkls` 不含此项，需按簇读取后自行截取 | `blkls` 直接输出       |
| 常见误区 | 以为"文件内容之外没东西"           | 以为"只有删掉的文件才在这"     |

<a id="section-7"></a>

### 2.5 未分配空间与文件残留

删除一个文件的真实过程（NTFS）：① `$MFT` 条目在用位归零，条目内容**通常不擦除**；② `$I30` 索引对应条目被标记无效；③ **数据簇在 `$Bitmap` 中被标记为空闲**；④ **簇内数据本身不被清零**。

第 ④ 步是取证的根本前提：**内容还在，只是"不再被任何文件引用"**。三种提取范围：

```bash
blkls -o 2048 /work/DigiForensics.dd > /tmp/unalloc.bin                    # ① 文件系统内未分配块
grep -aob 'target-string' /work/DigiForensics.dd | head                     # ② 全镜像搜索（含分区间隙）
blkls -o 2048 -l /work/DigiForensics.dd | head                             # ③ 列出各数据单元的时间戳与归属
```

> **`blkls` 选项别记混**：`-l` 是以 time machine 格式**列出**数据单元信息（时间戳 + 所在文件），`-s` 是**只输出 slack 空间**。想拿"哪些块空闲"不能靠 `-s 1-2` 这种位置参数——`blkls` 的 `start-stop` 是**块号范围**，不是"输出类型选择器"。查某簇当前是否空闲用 `blkstat`。

<a id="section-8"></a>

### 2.6 隐写术基础：格式内的合法藏身处

前四层都是"文件系统层面的藏匿"。隐写术不同：**它把数据藏在文件格式的合法空白处**，文件本身完全正常，双击能打开，校验和（若有）也正确。

| 载体                 | 藏匿位置                 | 典型容量 | 检出手段                                         |
| ------------------ | -------------------- | ---- | -------------------------------------------- |
| **PNG**            | `IEND` 块之后追加任意数据     | 无限   | `file` 报 "data after IEND"；检查 `IEND` 是否在文件末尾 |
| **JPEG**           | `EOI` 标记（`FFD9`）之后追加 | 无限   | 搜索 `FFD9` 是否在文件末尾                            |
| **JPEG**           | EXIF 段中的厂商私有区域       | KB 级 | EXIF 字段异常长/异常值                               |
| **GIF**            | Trailer `0x3B` 之后    | 无限   | 尾字节检查                                        |
| **PDF**            | `%%EOF` 之后、增量更新区     | 无限   | `%%EOF` 后有数据；对象代数递增                          |
| **BMP**            | 文件头声明尺寸 < 实际文件大小     | 无限   | 像素数据量 > 声明值                                  |
| **Office 97-2003** | OLE 复合文档未使用的流        | 不定   | 用 `oletools` 逐流枚举                            |
| **MP3 / 视频**       | 标签区扩展字段              | KB 级 | 帧结构边界检查                                      |

> **重要区别**：隐写术的"发现"与"证明"是两件事。"PNG 的 `IEND` 之后有数据"是客观事实；**"这是攻击者藏的命令"需要提取、解码、验证**。报告中必须区分这两层。

## 三、操作步骤

<a id="section-10"></a>

### 3.1 第 1 步：确认卷与基本参数

```bash
mmls /work/DigiForensics.dd                              # 分区布局
fsstat -o 2048 /work/DigiForensics.dd | grep -iE 'cluster|serial'   # 簇大小、序列号
```

<a id="section-11"></a>

### 3.2 第 2 步：全量扫描命名流（本篇核心步骤）

`fls` 把命名流显示为 `文件名$流名`（用 `$` 代替 `:`，因 `:` 在路径中非法）：

```bash
fls -o 2048 -r -p /work/DigiForensics.dd > /evidence/fls-all.txt
grep -E '\$[^/]*$' /evidence/fls-all.txt | head -50
# r/r  11443-128-4:  $FILE_NAME   24576  2024-06-02 14:07:19  report.docx
# r/r  11443-129-4:  $FILE_NAME  917504  2024-06-02 14:07:22  report.docx$hidden
#                       ↑ 同一 MFT 条目，属性 ID 不同 → 命名流，917 KB
```

**判定要点**：

| 观察                                                  | 含义                   |
| --------------------------------------------------- | -------------------- |
| 同一 MFT 条目号 + 不同属性 ID（`11443-128-4` / `11443-129-4`） | **同文件的不同 `$DATA` 流** |
| 流名 `$DATA`                                          | 显式写出的默认流，等价于匿名流      |
| 流名 `Zone.Identifier`                                | 系统正常添加，**非恶意**       |
| 主文件极小但命名流很大                                         | 典型的载荷藏匿形态，需提取内容      |

**排除系统正常流**：

```bash
grep -oE '\$[A-Za-z0-9_.$-]+$' /evidence/fls-all.txt | sort | uniq -c | sort -rn | head -20
# 大量 $DATA / Zone.Identifier 属正常；孤立的陌生流名才是重点
```

<a id="section-12"></a>

### 3.3 第 3 步：提取命名流内容并验证

```bash
# 提取指定命名流（属性 ID 从 fls 输出取得）
icat -o 2048 /work/DigiForensics.dd 11443-129-4 > /tmp/stream-hidden.bin

# 三个验证动作，缺一不可
file /tmp/stream-hidden.bin                    # ① 类型判断
sha256sum /tmp/stream-hidden.bin               # ② 固定证据
xxd -l 64 /tmp/stream-hidden.bin               # ③ 人工确认头部
```

**`icat` 提取的三个常见问题**：

| 问题              | 原因       | 处理                  |
| --------------- | -------- | ------------------- |
| 提取内容全 0         | **成因待定**：稀疏未分配区 / 压缩 / 新分配区 / 原内容即全零 / 被覆盖 / 主动清零 | **不可单点归因**，逐项排除后再写结论 |
| 长度小于 `istat` 声明 | 部分簇被覆盖   | 记录覆盖比例              |
| 提取到别的文件内容       | 属性 ID 写错 | 回查 `fls`/`istat` 确认 |

<a id="section-13"></a>

### 3.4 第 4 步：提取 `$I30` 并检查"幽灵文件"

```bash
icat -o 2048 /work/DigiForensics.dd 5-0-0 > /tmp/root-i30.bin
xxd -l 4 /tmp/root-i30.bin              # 期望 49 4E 44 58 = "INDX"
strings -e l /tmp/root-i30.bin | sort -u > /evidence/i30-names.txt
comm -23 /evidence/i30-names.txt <(cut -d' ' -f7- /evidence/fls-all.txt | sort -u) > /evidence/ghost-files.txt
# 左侧输出 = 只在 $I30 里、不在 $MFT 树里的名字 = 幽灵文件候选
```


**验证要求**：每个名字必须**人工复核**——索引里也会残留正常删除过的旧名。"在 `$I30` 中但不在 `$MFT` 树中"是"被隐藏的强信号"，不是"已被删除的证明"。

<a id="section-14"></a>

### 3.5 第 5 步：Slack 空间提取

Slack 不由 TSK 直接输出，需按簇自行计算（读取整簇，减去 `$DATA` 声明长度）：

```bash
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -E 'Size|MFT Cluster|Runs'   # 先取 Size 与簇号
dd if=/work/DigiForensics.dd bs=512 skip=$((2048 + 252*8)) count=8 of=/tmp/cluster0.bin status=none
dd if=/tmp/cluster0.bin of=/tmp/slack0.bin bs=1 skip=3500 count=596 status=none   # 3500+596=4096
strings -n 6 /tmp/slack0.bin | head -20
```

**批量提取思路**：遍历已分配簇 → 用 `$MFT` 中各文件声明大小计算 slack 区间 → 统一做关键字搜索与熵值分析。**耗时，通常只针对可疑目录或大文件进行。**

<a id="section-15"></a>

### 3.6 第 6 步：未分配空间与隐写检查

```bash
# ① 未分配空间关键字搜索
blkls -o 2048 /work/DigiForensics.dd | strings -n 20 | grep -iE 'password|PRIVATE KEY'

# ② PNG：IEND 块应正好收尾。IEND 块 = 4(长度)+4(类型)+0(数据)+4(CRC) = 12 字节
#    判据是「IEND 块之后还剩多少字节」，不是「IEND 出现在哪个偏移」
f=/evidence/suspect.png
sz=$(wc -c < "$f" | tr -d ' ')
typeoff=$(grep -abo 'IEND' "$f" | tail -1 | cut -d: -f1)   # 取最后一次出现，避开偶然字节命中
tail=$(( sz - (typeoff - 4) - 12 ))
[ "$tail" -eq 0 ] && echo "IEND 收尾，正常" || echo "IEND 之后还有 $tail 字节 → 疑似追加隐写"

# ③ JPEG：EOI(ffd9) 应在文件末尾    # ④ PDF：%%EOF 应在文件末尾
tail -c 16 /evidence/suspect.jpg | xxd -p
tail -c 32 /evidence/suspect.pdf | strings
```

> **PNG 检查的常见错法**：`xxd -p "$f" | tr -d '\n' | grep -bo '49454e44ae426082'` 返回的是**十六进制字符流的字符位置**，不是文件字节偏移（偏移要除以 2）。更关键的是它**对正常文件和隐写文件返回同一个值**——因为 `IEND` 在两种文件里都出现在同一位置，区别只在它后面还有没有数据。这个写法无法区分正常与隐写，必须改成"比较 IEND 块末尾与文件大小"。

## 四、常见陷阱

本章按「ADS 识别 → 提取与验证 → `$I30` 与 slack → 隐写检查与结论表述」归组，每条给出：现象、为什么会误判、误判代价、正确做法。  
★ 标记表示该操作会导致原始检材永久灭失或不可逆改变，执行前必须停下来确认。

<a id="section-17"></a>

### 4.1 ADS 识别：看不见不等于不存在

<a id="section-18"></a>

#### 陷阱 1：★ 用资源管理器或 `dir` 查过就写"未发现异常数据流"

**现象**：用文件管理器逐个查看 web 目录下的文件，"没有看到任何异常"，报告写"该目录未发现隐藏数据"。

**原因**：**Windows 资源管理器对命名流完全不可见**（2.2 的对照表）——它只呈现默认流。而 `dir`（cmd 默认）也看不到，**必须加 `/r` 参数**。更关键的是：ADS 的数据在磁盘上是完整存在的簇链，`$MFT` 里有独立记录，卷占用里也计算在内。它不是"藏起来"在某个不可见的角落，而是**系统绝大多数接口都不展示它**。"文件管理器里看不到"与"磁盘上不存在"是两个完全不同的命题。

**影响**：委托方说"已清理干净"、分析员用常规方式确认"确实干净"、报告据此结案——而后门就在 `$J` 流里躺着，占着 41 KB 的真实磁盘空间。案例里那个 webshell 正是这样被发现的：**它从未在文件列表里出现过**。

**核查**：判定必须基于 `istat` 的属性列表，而不是任何文件浏览器（2.2 已明确）：

```bash
# 关键：用 fls 全量输出找流名标记
fls -o 2048 -r -p /work/DigiForensics.dd > /evidence/fls-all.txt
# 命名流显示为 文件名$流名（用 $ 代替 :）
grep -E '\$[^/]*$' /evidence/fls-all.txt | head -50
```

**同一 MFT 条目号 + 不同属性 ID** 是判定同文件不同 `$DATA` 流的依据（3.2 的判定要点）：

```text
r/r  88214-3-4:  $FILE_NAME   2638   2025-08-14 02:11:04  default.aspx
r/r  88214-4-4:  $FILE_NAME  41277   2025-08-14 02:11:07  default.aspx$J
#     ↑ 同一 MFT 条目 88214，属性 ID 3 与 4 不同 → 命名流，41 KB
```

在报告里，"用常规方式检查未发现"必须改写成"以 `fls` 全量输出与 `istat` 属性列表为依据检查"，否则这个否定结论在方法上不成立。

<a id="section-19"></a>

#### 陷阱 2：把 `Zone.Identifier` 判为恶意证据

**现象**：扫描发现大量 `Zone.Identifier` 流，报告写"web 目录存在大量可疑命名流，疑似被篡改"。

**原因**：`Zone.Identifier` 是 Windows 正常添加的系统标记流，内容是 ZoneId 与来源 URL（2.1 的流名约定表）。**每一个从浏览器下载的文件都有它**——这是 NTFS 的正常行为，与恶意无关。而"发现了不认识的流名"这个直觉很容易跳过"这个流名是不是已知的系统流"这一步。

**影响**：**假阳性会淹没真信号**。如果报告里写着"大量可疑命名流"，那么真正那个孤立的 `$J` 就被稀释了——而 `$J` 出现的形式恰恰是"数量极少、与系统流名单无关"。反过来，这种误判也会损害报告的专业性：把系统正常行为当异常，专业读者会质疑整份报告的判读标准。

**核查**：先做流名频次统计，把系统正常流排除掉，剩下的才是重点（3.2 的排除步骤）：

```bash
grep -oE '\$[A-Za-z0-9_.$-]+$' /evidence/fls-all.txt | sort | uniq -c | sort -rn | head -20
#  4821 $DATA                ← 正常（TSK 对默认流的显式标注）
#     2 Zone.Identifier      ← 系统正常
#     1 $J                   ← 孤立 → 重点
```

判读原则：孤立 + 出现位置敏感 + 体积异常，三项同时成立才升级为可疑。 案例里 `$J` 命中这三项：只出现 1 次、位于 `/inetpub/wwwroot/`、41 KB 挂在 2.6 KB 的主文件上。而 4821 个 `$DATA` 和 2 个 `Zone.Identifier` 是噪声。

<a id="section-20"></a>

#### 陷阱 3：主文件很小、命名流很大，判为"误报/工具解析错误"

**现象**：某文件主数据流 2.6 KB，命名流 41 KB，分析员认为属性 ID 写错了、工具读错了，删掉该条目不作分析。

**原因**：**"主文件极小但命名流很大"是典型的载荷藏匿形态**（3.2 的判定要点表）。**这个形态在统计上是有意义的**——正常的 ADS（`Zone.Identifier`）都是几十到几百字节，**41 KB 远超正常量级**。而"工具解析错误"这个替代解释虽然可能，但需要证据支撑，不能仅凭"看起来不合理"就采用。在反取证场景下，"不合理"恰恰是最需要解释的现象。

**影响**：**把唯一的证据当成解析错误丢掉**。案例里那个 `default.aspx` 就是这个形态——而它的主文件内容是清白的正常页面，**唯一有价值的信息全在命名流里**。

**核查**：**提取出来看，不要预判**：

```bash
istat -o 2048 /work/DigiForensics.dd 88214-4-4
icat -o 2048 /work/DigiForensics.dd 88214-4-4 > /tmp/stream-J.bin
sha256sum /tmp/stream-J.bin
file /tmp/stream-J.bin          # → PHP script text
head -5 /tmp/stream-J.bin
# <?php
# @eval($_POST['cmd']);
```

**"提取并验证"是唯一能定性的动作**（2.1 的强调：判断 ADS 是否恶意必须**提取内容并验证**，不能仅凭"存在 ADS"定性）。**注意这与陷阱 2 方向相反**——存在不证明恶意，但**存在且内容异常就必须提取**。

<a id="section-21"></a>

### 4.2 提取与验证

<a id="section-22"></a>

#### 陷阱 4：★ 提取出的流全为 0，报告写"该流已被清空"

**现象**：`icat` 提取某命名流，得到全 0 内容，报告写"该流已被清空，无残留内容"。

**原因**：提取到全 0 **本身不能确定成因**（3.3 的问题表）。全零至少有五种合法来源，**必须逐项排除后才能归因**：

| 候选成因 | 判据 | 排除方法 |
|---|---|---|
| **稀疏文件的未分配区** | NTFS 稀疏文件对零区域**不写盘**，读取时直接返回零 | 检查该流是否 `FILE_ATTRIBUTE_SPARSE_FILE` |
| **NTFS 压缩流** | 压缩单元内未使用的空间读出为零 | 检查 `FILE_ATTRIBUTE_COMPRESSED` |
| **新分配/新扩展的簇** | 超出有效数据长度（VDL）的部分可能未初始化 | 比对 `$STANDARD_INFORMATION` 的 `EndOfFile` 与簇实际容量 |
| **原内容本就全零** | 例如以零填充创建的标记流 | 无技术手段可区分，需回到内容语义判断 |
| **被后续写入覆盖** | 簇释放后被重新分配给新数据 | 查 `$Bitmap` 当前状态 + 其他文件的簇占用 |
| **主动清零** | 有意擦除 | 需行为证据支撑，不可仅凭数据形态认定 |

> **★ 最常见的误判是把稀疏文件当成"被覆盖"。** 微软《Sparse Files》明确：稀疏文件在零区域**不写入磁盘**，文件系统维护一份零位置清单，读取时按清单返回相应的零。这意味着一个**从未被写过、也从未被删除过**的稀疏流，提取出来同样是全 0。把它写成"被覆盖、不可恢复"是错误的成因认定。

删除文件时 NTFS 会把数据簇在 `$Bitmap` 中标记为空闲，但**空闲只说明"当前"未被占用，不等于"已被复用"**——可能只是刚删除尚未有新数据写入。要证明"被复用"，需要**该簇已被其他文件实际占用**这一独立证据。

**"簇被复用"与"该流曾被清空"是两件事**：前者说明数据被后续写入覆盖，后者说明有人主动做了擦除。**而两者的取证含义完全不同**——前者是自然衰减，后者是人为行为。

**影响**：**"被清空"是一个关于人为行为的指控性结论**，它暗示有人刻意擦除痕迹。而真相是磁盘空间被正常使用了。在报告里，"该流已被清空"会让委托方去追查一个不存在的"清除动作"，而真正的覆盖者（某个无关的业务文件）永远不会被找到。

**核查**：区分"主动清零"与"被后续写入覆盖"，判据是簇的分配状态：

```bash
# 1) 查该 $DATA 属性的簇链
istat -o 2048 /work/DigiForensics.dd 88214-4-4 | grep -i 'Runs:'
# 2) 逐个查询这些簇当前是否仍被占用（blkstat 报告 Allocated: yes/no）
blkstat -o 2048 /work/DigiForensics.dd 252 253
# Allocated: no  → 该簇已释放；是否被复用还要看当前由哪个文件占用
# Allocated: yes → 簇仍属于本文件，全零更可能是稀疏/压缩/主动清零
# 3) 若已释放，用 blkls -l 反查该块归属，看是否已被其他文件接管
blkls -o 2048 -l /work/DigiForensics.dd | grep -i '252'
# 若内容全 0 且簇仍标记为本文件占用 → 才可能是主动清零（极罕见）
```

**报告写法**："该命名流的数据簇（`<簇列表>`）当前在 `$Bitmap` 中标记为空闲，提取内容为全 0。**全 0 的成因不能仅凭该观察确定**——需先排除稀疏文件未分配区、NTFS 压缩、超出有效数据长度的新分配区、原内容即全零等合法来源；若已确认该流不具稀疏与压缩属性、且全零区域超出有效数据长度，才可进一步评估被后续写入覆盖的可能。**本项不足以认定'被主动清零'，也不足以直接认定'已被覆盖'。**"

<a id="section-23"></a>

#### 陷阱 5：属性 ID 写错，提取到别的文件内容

**现象**：`icat` 提取命名流，得到的却是一个完全不相干的文件内容，判为"该流内容异常"。

**原因**：属性 ID 必须从 `fls`/`istat` 的实际输出取得，不能凭印象或推算（3.3 的问题表）——同一 MFT 条目下每个 `$DATA` 实例有不同的属性 ID（案例里 `88214-3-4` 与 `88214-4-4` 是主数据流与 `$J`，`88214-5-4` 若存在就是第三个流）。TSK 会为跨 MFT 记录的属性重新分配唯一 ID，所以推算是不可靠的。而"提取到别的文件内容"这个现象，同样可能是属性 ID 写错造成的——**它不证明提取成功，也不证明流内容异常。**

**影响**：**把错误提取的内容当作证据**——它可能与该文件毫无关系，一旦写进报告就是一条无法辩护的"发现"（而实际内容属于别的文件）。这类错误在报告里完全看不出来，因为内容本身是真实存在的文件。

**核查**：**属性 ID 三处交叉核对，且提取后做内容归属验证**：

```bash
# 1) fls 输出里找该文件的所有条目
grep -E 'default\.aspx' /evidence/fls-all.txt
# r/r  88214-3-4:  ...  default.aspx
# r/r  88214-4-4:  ...  default.aspx$J
# 2) istat 列出该条目的全部属性，逐个对照
istat -o 2048 /work/DigiForensics.dd 88214-4-4
# 3) 提取后验证内容是否与流名/上下文相符
icat -o 2048 /work/DigiForensics.dd 88214-4-4 > /tmp/stream-J.bin
file /tmp/stream-J.bin && head -3 /tmp/stream-J.bin
```

三条记录（MFT 条目号、属性 ID、流名）必须两两对应。"内容看起来奇怪"不能替代"内容确实属于这个流"的验证。

<a id="section-24"></a>

#### 陷阱 6：★ 用 `dir` 或第三方脚本枚举，就把结论写成"无 ADS"

**现象**：批量脚本用 `os.listdir` 遍历目录、检查文件属性后输出"无异常"，报告据此结论。

**原因**：2.2 的对照表把这件事说得很直接：**多数"快速取证"脚本看不到命名流**。原因不是脚本写得不好，而是它们调用的是"按文件名取默认流"的接口——而 ADS 在这些接口里根本不是一等公民。此外还有一层：**默认流可以是空的**（0 字节），**内容全挪进命名流即可规避"按大小"的内容检查**（2.1 第 3 点）。一个"大小正常、格式正常、内容正常"的文件，完全可以藏着一个主数据流为空而命名流是完整载荷的版本。

**影响**：**这与陷阱 1 是同一类错误的不同入口**——用批量脚本"检查过全部文件"是一个看起来很有说服力的方法论描述，**但它的方法本身有结构性盲区**。而"全量检查过，未发现异常"这种表述可信度很高，**读者不会想到这个"全量"是有边界的**。

**核查**：ADS 检查必须以 `fls` 全量输出 + `istat` 属性列表为依据，并在报告里写明这一点。同时**不要依赖文件大小判断**：

```bash
# 正确：全量 fls 找流名标记，而不是逐文件看大小
fls -o 2048 -r -p /work/DigiForensics.dd | grep -E '\$[^/]*$' | \
  awk '{print $2}' | sort -u
# 关注：同一 MFT 条目出现多个不同属性 ID 的情况
```

**报告的方法论段落里要写清**："本次隐藏数据检查以 Sleuth Kit `fls` 全量目录树输出中的流名标记与 `istat` 属性列表为依据，覆盖命名流、匿名流与 `$I30` 索引。**未使用文件浏览器或目录遍历脚本作为判定依据**，因其不呈现命名流。"

<a id="section-25"></a>

### 4.3 `$I30` 与 slack

<a id="section-26"></a>

#### 陷阱 7：把 `$I30` 幽灵文件直接写成"被隐藏的文件"

**现象**：`comm` 对比出若干个只在 `$I30` 索引里、不在 `$MFT` 树里的名字，报告写"发现 `<N>` 个被隐藏的文件"。

**原因**：**索引里也会残留正常删除过的旧名**（3.4 的验证要求）。$I30 索引条目在被删除时只是被标记无效，内容通常还在——**这与"文件被隐藏"是完全不同的机制**。真正的"隐藏"是**故意让索引与 `$MFT`不一致**（工具改名后只改`$MFT` 不改索引，这是反取证常见做法），而**普通的删除也会在索引里留下痕迹**。这两者在"索引里有、`$MFT\` 树里没有"这个现象上完全一致。

**影响**：**"被隐藏"是一个指控性结论**——它意味着有人刻意掩盖了这些文件的存在。**对方只需说明"这些文件是正常删除的"就能推翻它**。而更实际的问题是：这个结论会引导调查去找"隐藏者"，而真正该关注的是"这些文件的内容去哪了"。

**核查**：每个名字必须人工复核，并区分"已删除"与"被隐藏"：

```bash
# 提取 $I30 并列出全部名字
icat -o 2048 /work/DigiForensics.dd 88210-0-0 > /tmp/www-i30.bin
xxd -l 4 /tmp/www-i30.bin              # 期望 4949 4E44 58 = "INDX"
strings -e l /tmp/www-i30.bin | sort -u > /evidence/i30-names.txt
# 与 $MFT 树对比
comm -23 /evidence/i30-names.txt <(cut -d' ' -f7- /evidence/fls-all.txt | sort -u) \
  > /evidence/ghost-files.txt
```

**区分依据**：

| 现象                                                | 判读             |
| ------------------------------------------------- | -------------- |
| 名字在 `$I30` 中，**且** `$MFT` 记录仍在用（`fls` 未标 deleted） | **高度可疑，指向被隐藏** |
| 名字在 `$I30` 中，`$MFT` 记录**已标删除**                    | **正常删除残留**     |
| 名字在 `$I30` 中，**且**数据簇已被复用                         | 内容不可恢复，仅作线索    |

**报告写法**（案例的处理方式）："`$I30` 中另有 2 个文件名（`shell.aspx`、`cmd.php`）在 `$MFT` 树中不存在，**列为线索**；经查其数据簇已被后续写入复用，**内容无法恢复**。本项**不构成'文件被隐藏'的认定**，亦不构成对已删除文件的证明。"

<a id="section-27"></a>

#### 陷阱 8：★ 用 `blkls` 找 slack，结论必然是"没找到"

**现象**：对可疑目录执行 `blkls` 提取未分配空间做关键字搜索，无命中，据此报告"该目录无残留内容"。

**原因**：`blkls` 输出的是文件系统内未分配块，不包含 slack（2.4 的区别表）。**slack 位于已分配簇内部**——是文件声明长度之外、但仍在已分配簇里的那段字节。它是已分配空间，文件系统认为它"属于某个文件"，`blkls` 天然不会输出它。 用 `blkls` 找 slack 就像用 `ls` 找文件内容——**工具用错了地方，而工具没有报错**。

**影响**：**一个仍然存在于已分配簇中的旧内容被漏掉**。这在"文件被覆盖但更早版本仍在 slack 里"的场景下是关键的（2.4 的注意：文件被覆盖时 slack 里往往还残留**更早版本**的内容）。**这是"以为自己找过了"的典型形态**——搜索确实执行了，只是搜的是错误的范围。

**核查**：**slack 需按簇自行计算**（3.5）：

```bash
# 1) 先取该文件的声明大小与簇链
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -E 'Size|Runs'
# Size: 24576  → 3500 字节的场景：读整簇 4096，减去 3500
# 2) 读整簇
dd if=/work/DigiForensics.dd bs=512 skip=$((2048 + 252*8)) count=8 of=/tmp/cluster0.bin status=none
# 3) 自行截取 slack（3500 之后到 4096）
dd if=/tmp/cluster0.bin of=/tmp/slack0.bin bs=1 skip=3500 count=596 status=none
# 4) 搜索
strings -n 6 /tmp/slack0.bin | head -20
```

**批量提取的思路**：遍历已分配簇 → 用 `$MFT` 中各文件声明大小计算 slack 区间 → 统一做关键字搜索与熵值分析。**注意耗时，通常只针对可疑目录或大文件进行**（3.5 已说明）。报告里要写明"本次 slack 检查覆盖了哪些文件的哪些簇"——因为它天然无法全量覆盖。

<a id="section-28"></a>

#### 陷阱 9：把 slack 内容直接归属为"该文件的历史版本"

**现象**：在某文件的 slack 里搜到一段文本，报告写"该文件曾包含这段内容，后被覆盖"。

**原因**：**slack 里的内容不一定是该文件的历史版本**。它是**前一次占用该簇的文件**的残留（2.4 的原理）——也就是说，slack 属于"上一个租户"，不是"这个文件的过去"。当文件被覆盖写、但新内容比旧内容短时，旧内容的尾部会留在 slack 里——**这才是"历史版本"的情形**。而在文件被删除后由别的文件占用该簇的情况下，**slack 里的东西属于那个新文件之前的存在**。

**影响**：**错误的内容归属**。在案件里，"某文件曾包含某段文本"是一个关于文件内容历史的断言，**它可能被用来支持"该文件曾包含涉案信息"的结论**。而如果那段文本其实来自另一个文件，这个推论就是错的。

**核查**：**归属判断要基于覆盖模式**：

```bash
# ① 当前文件声明大小 vs 簇大小
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -i size     # Size: 3500
# 簇大小
fsstat -o 2048 /work/DigiForensics.dd | grep -i 'cluster size'       # 4096
# ② slack = 3500..4096
# ③ 判断：若 slack 尾部能与该文件已知内容（如文件头/结构）衔接
#    → 支持"同文件更早版本"
# ④ 若 slack 起始就是完整的其他文件头（PK/PDF/PNG magic）
#    → 属于"前一个占用该簇的文件"，与本文件无关
dd if=/tmp/slack0.bin bs=1 count=8 status=none | xxd -l 8
# 若显示 504b 0304 = "PK.." → 是另一个 ZIP/OOXML 文件的残留
```

**报告写法**："该簇 slack（偏移 3500–4096）中检出 ZIP 文件头（`PK\x03\x04`），**该内容属于先前占用此簇的其他文件，与本文件无关**。"——**把排除结论写清楚，比含糊地"发现残留"好得多。**

<a id="section-29"></a>

### 4.4 隐写检查与结论表述

<a id="section-30"></a>

#### 陷阱 10：★ 隐写检查只看文件头魔数，不查尾标记

**现象**：对一个 PNG 做了 `xxd` 检查，看到开头是合法 PNG 魔数，判定"该 PNG 无隐藏数据"。

**原因**：隐写术的常见手法是在文件格式的合法位置之后追加数据（2.6）——**文件本身完全正常，双击能打开，校验和也正确**。而**只看文件头的话，任何追加数据都检测不到**：魔数在开头，后面追加什么都行。**判定必须看格式的终止标记位置**（3.6 的三种检查）：

```bash
# ② PNG：IEND(49454e44ae426082) 后面还有数据 → 追加了内容
xxd -p /evidence/suspect.png | tr -d '\
' | grep -bo '49454e44ae426082' | head
# ③ JPEG：EOI(ffd9) 应在文件末尾
tail -c 16 /evidence/suspect.jpg | xxd -p
# ④ PDF：%%EOF 应在文件末尾
tail -c 32 /evidence/suspect.pdf | strings
```


**影响**：**"无隐藏数据"是一个关于文件完整性的否定性结论**，而它在报告里常被用来支撑"该文件是原始版本"这类更强的结论。一旦追加数据被发现，之前所有基于该文件的推论都要重新检查。

**核查**：**三种格式的尾标记检查都要做，且检查逻辑写清楚**（PNG 的 IEND 偏移应当"接近文件末尾"而非"等于"——IEND 之后还有 4 字节 CRC，所以判断标准是 IEND 位置 + 12 字节 ≈ 文件大小）：

```bash
# PNG：IEND chunk = 4 字节长度 + "IEND" + 4 字节 CRC = 12 字节
python3 -c "
import sys
d = open('/evidence/suspect.png','rb').read()
i = d.find(b'\x49\x45\x4e\x44\xae\x42\x60\x82')
print('IEND 结束位置:', i+8, '文件大小:', len(d))
print('追加字节数:', len(d)-(i+8) if i>=0 else 'IEND 未找到')
"
# JPEG：最后一个 ffd9 之后应无数据
# PDF：最后一个 %%EOF 之后应只有空白
```

**报告里写明检查了哪些文件、结论如何**，而不是一句"未发现异常"。

<a id="section-31"></a>

#### 陷阱 11：★ 把命名流的内容归属为"该文件是 webshell"

**现象**：提取出 `$J` 流内容是 PHP webshell，报告结论写"`default.aspx` 是 webshell"。

**原因**：**主文件与命名流是两个独立的数据流，内容互不相关**（2.1 第 2 点：各流的数据区域彼此独立）。案例里主文件只有 2.6 KB、格式正常、功能正常——**它是清白的**。"这个文件有一个装了 webshell 的命名流"与"这个文件是 webshell"是两个不同的命题，而后者在技术上是错的。在正常页面上挂 webshell 流的手法，目的恰恰是让文件看起来正常——这正是反取证的思路。

**影响**：**结论指向了错误的对象**。委托方据此去修 `default.aspx` 那个文件，而**真正需要处理的是流**（删掉 ADS 但保留原文件内容）。更实质的问题是**举证责任**：如果这是诉讼证据，"该文件是恶意程序"这个结论一旦被推翻（主文件内容清白），**整份报告的可信度都会受牵连**。

**核查**：**结论精确到机制层面**（案例结论的处理方式）：

> "**发现并提取了 webshell 内容**：`default.aspx` 于 2025-08-14 02:11:07 被附加 41,277 字节命名流 `$J`，流内容为可执行 PHP webshell（`@eval($_POST['cmd'])` 形式），已提取并固定 SHA256。  
> 主文件 `default.aspx`（2,638 字节）内容经提取验证为正常页面，不含恶意代码。  
> 本项结论为'该文件被附加了承载 webshell 的命名流'，**不构成'该文件本身是 webshell'的认定**。"

**这四项要素缺一不可**：机制（附加了命名流）、载体（流名与大小）、内容（提取并固定）、**排除项（主文件清白）**。**最后一条是最容易被省略、也最关键的一条。**

<a id="section-32"></a>

#### 陷阱 12：只查一个藏匿层次就写"未发现其他后门"

**现象**：提取完 `$J` 流的内容后，报告结论"该服务器被植入 webshell"，但没有检查 `$I30`、未分配空间、其他文件。

**原因**：**NTFS 上的藏匿层次是分层的**——ADS 只是其中一层。2.3/2.4/2.5/2.6 已经列全了：命名流与匿名流、`$I30` 索引不一致、**slack space**、未分配空间、以及格式级隐写。**找到一处不代表只有一处**——而攻击者通常会**故意留下多处**（一处被发现后，其余的作为后备）。案例里同一个 web 根目录下，`$I30` 里还有两个幽灵文件名、未分配空间里还有两处 `@eval` 残留。

**影响**：**"已清除全部后门"是一个关于安全状态的强结论**。委托方据此关闭安全事件、恢复服务、对外通报——**而残留的后门在几天后重新上线**。这是安全事件处置里代价最高的一类误判，因为它会触发一连串不可逆的决策。

**核查**：**逐层检查，每层都要有结论**（3.6 与案例第 3 步的结构）：

```bash
# ① 命名流
fls -o 2048 -r -p /work/DigiForensics.dd | grep -E '\$[^/]*$'
# ② $I30 幽灵文件
icat -o 2048 /work/DigiForensics.dd 88210-0-0 | strings -e l | grep -iE 'aspx|php|asp'
# ③ 未分配空间
blkls -o 2048 /work/DigiForensics.dd | strings -n 20 | grep -c '@eval'
#   → 3 处命中：1 处为刚提取的 $J，另 2 处为已删除文件残留
# ④ slack（按簇计算，见 3.5）
# ⑤ 格式级隐写（PNG/JPEG/PDF 尾标记检查）
```

**报告要逐层给状态**：

| 层次        | 检查方式                      | 本案结果                     |
| --------- | ------------------------- | ------------------------ |
| 命名流       | `fls` 流名标记 + `istat` 属性列表 | 1 个（`$J`，41 KB，webshell） |
| `$I30` 索引 | 提取索引与 `$MFT` 树对比          | 2 个幽灵文件名，内容不可恢复          |
| 未分配空间     | `blkls` + 关键字搜索           | 2 处 `@eval` 残留（已删除文件）    |
| slack     | 按簇计算                      | 本次未覆盖 `<说明原因>`           |
| 格式隐写      | 尾标记位置检查                   | `<逐文件结论>`                |

**未覆盖的层次要写明原因**（时间、工具限制、范围过大），**留空白的层次在报告里等于"没查"**。

<a id="section-33"></a>

#### 陷阱 13：报告里出现未脱敏的载荷内容

**现象**：把提取出的 PHP webshell 全文（含 `@eval($_POST['cmd'])` 及后续 base64 逻辑）原样贴进报告正文。

**原因**：**贴出来是为了"让结论具体"**——而全文确实最有说服力。但**这内容是一个可直接执行的攻击载荷**，且报告是传播范围最广的那份文件。

**影响**：**载荷进入报告 = 攻击工具进入广泛传阅的文档**。如果被广泛传阅，任何拿到报告的人都获得了这个 webshell 的完整实现。**这已经不是取证问题，而是一次新的安全事件**——而责任在报告作者。

**核查**：**报告正文写机制与关键特征，完整载荷单独封存**：

- 正文写：流名、大小、SHA256、**关键特征的有限描述**（如"以 `@eval($_POST[...])` 接收参数执行"）；
- 完整载荷：单独加密归档，**受控调阅**；
- 复现方式：写明提取命令与偏移（`icat -o 2048 88214-4-4`），**任何有权限的人都能复现**——这比贴全文更严谨，因为它同时证明了可复现性与最小披露。

案例里 `head -5` 展示了前几行是合适的做法——它足以说明性质，不需要全文。

## 五、案例示例

<a id="section-35"></a>

### 5.1 41 KB 的命名流：Webshell 藏在 default.aspx 的 ADS 里

**场景**

查获某公司 Windows Server 2016（IIS 服务器），委托方称 web 目录曾被植入后门但已"清理干净"。镜像 `DigiForensics.dd`（raw，240 GB），NTFS 分区起始扇区 2048，簇大小 4096。委托方要确认"是否真的清理干净了"。选择这一路径的依据是清理工具通常处理主数据流，而命名 ADS 会被完整跳过——它就在同一个 MFT 条目里，不需要任何文件系统层面的技巧就能藏住。

**处置过程**

**第 1 步 · 全量扫描命名流**：

```bash
fls -o 2048 -r -p /work/DigiForensics.dd > /evidence/fls-all.txt
grep -oE '\$[A-Za-z0-9_.$-]+$' /evidence/fls-all.txt | sort | uniq -c | sort -rn | head
#  4821 $DATA                ← 正常（TSK 对默认流的显式标注）
#     2 Zone.Identifier      ← 系统正常
#     1 $J                   ← 孤立，出现在 /inetpub/wwwroot/ 下 → 重点
```

`$J` 出现在 web 根目录，**不在系统正常流名单内**。定位到具体条目：

```bash
grep -E 'default\.aspx' /evidence/fls-all.txt
# r/r  88214-3-4:   $FILE_NAME  2638   2025-08-14 02:11:04  default.aspx
# r/r  88214-4-4:   $FILE_NAME  41277  2025-08-14 02:11:07  default.aspx$J
```

同一 MFT 条目 `88214`，属性 ID 分别为 3 和 4——确认 `default.aspx` 挂着 41 KB 的命名流 `$J`，而主文件只有 2.6 KB。

**第 2 步 · 提取并验证**：

```bash
istat -o 2048 /work/DigiForensics.dd 88214-4-4
icat -o 2048 /work/DigiForensics.dd 88214-4-4 > /tmp/stream-J.bin
sha256sum /tmp/stream-J.bin
file /tmp/stream-J.bin          # → PHP script text
head -5 /tmp/stream-J.bin
# <?php
# @eval($_POST['cmd']);
# ...（后随大量 base64 解码逻辑）
```

内容是可直接执行的 PHP 代码，且以 `@eval($_POST[...])` 形式接收参数——符合 webshell 的典型结构。

**第 3 步 · 检查其他藏匿层次（不能只查一处）**：

```bash
# ① web 根目录的 $I30 幽灵文件
icat -o 2048 /work/DigiForensics.dd 88210-0-0 > /tmp/www-i30.bin
xxd -l 4 /tmp/www-i30.bin       # 49 4e 44 58 = "INDX"
strings -e l /tmp/www-i30.bin | grep -iE 'aspx|php|asp'
# → "shell.aspx"、"cmd.php" 两个名字在 $MFT 树中不存在 → 幽灵文件候选

# ② 已删除文件是否仍在未分配空间
blkls -o 2048 /work/DigiForensics.dd | strings -n 20 | grep -c '@eval'
# → 3 处命中：1 处为刚提取的 $J，另 2 处为已删除文件残留

# ③ 提取出的每个 PNG 执行 IEND 检查
```

**第 4 步 · 关联攻击时间线**：

```bash
istat -o 2048 /work/DigiForensics.dd 88214-3-4 | grep -E 'Created|Modified|Changed'
# Created:  2024-11-02 09:14:07（default.aspx 正常创建）
# Modified: 2025-08-14 02:11:04    Changed: 2025-08-14 02:11:07  ← 与命名流写入吻合
```

**结论**

能证明：`default.aspx` 于 **2025-08-14 02:11:07** 被附加 41,277 字节命名流 `$J`，内容为可执行 PHP webshell（已提取并固定 SHA256）。同一 MFT 条目下并存匿名流（2.6 KB）与命名流（41 KB），**属文件系统级证据，非推测**；主文件 `Changed` 与命名流写入时间相差 3 秒，**时间戳互相印证**。

**不能证明**：①`$I30` 中另有 2 个"幽灵文件名"（`shell.aspx`、`cmd.php`）**仅作线索**——数据簇已被复用，内容无法恢复；②未分配空间中另 2 处 `@eval` 残留是否为同一 webshell 的不同副本，未做内容比对。

**误判对照**

最像的误判是写"该文件是 webshell"。判据要划清主文件与命名流的界限：`default.aspx` 的匿名数据流内容是 2.6 KB 的正常页面代码，webshell 在它的第二个命名流 `$J` 里——两者是不同的数据流，属性 ID 分别为 3 和 4。结论必须表述为「**发现并提取了 webshell 内容**」，而不是"该文件是 webshell"，因为后者在语义上把一个清白的文件说成了恶意文件。正确判据是任何涉及 NTFS 的内容认定都要先明确"取的是哪个流的内容"。按错误判据走的代价：委托方按"default.aspx 是 webshell"去追查该页面的作者，而实际的植入者使用的是 ADS 特性——这个误判会把调查方向从"谁附加了流"引向"谁写了页面"，追错人且难以纠正。

<a id="section-36"></a>

### 5.2 全量扫描命名流为什么必须先统计再逐个看

**场景**

同一案件中，`fls` 全量输出 100 万余行，直接逐行搜索 `default.aspx` 找不到任何可疑流，因为 TSK 默认输出里命名流的呈现方式需要特定匹配。选择这一路径的依据是 **ADS 的发现率极依赖搜索策略**——逐文件查看必然遗漏，而先统计能一步定位异常。

**处置过程**

1. 先统计所有流名的出现频次，异常值自己会浮出来：

```bash
grep -oE '\$[A-Za-z0-9_.$-]+$' /evidence/fls-all.txt | sort | uniq -c | sort -rn | head
```

```text
4821 $DATA              ← 正常量级（TSK 对默认数据流的显式标注）
   2 Zone.Identifier    ← 系统正常（NTFS 的备用数据流标记下载来源）
   1 $J                 ← 只有 1 个，名字也不常见 → 必须追
```

1. 关键在于 `sort | uniq -c` 这个动作：它把"哪些名字出现了多少次"变成一张可排序的表，**低频项自动沉到表尾**。
2. 顺着异常项回溯到具体的 MFT 坐标，再做内容确认。

**结论**

能证明：全卷 4821 个文件中，只有 1 个挂了非常规命名流 `$J`，坐标为 `88214-4-4`。这个"1"的稀缺性本身就是判断依据——它不是某个常见系统流的变体。

**不能证明**：**不能证明其他文件没有被检测到**——若某流的文件名恰好与系统常见名相同（如有人也建了一个叫 `Zone.Identifier` 的流），它在统计表里会并入正常项。**未覆盖范围**是这类同名伪装，本案未做"同名流内容比对"这一项检查。

**误判对照**

最像的误判是逐个文件 `istat` 检查有无 ADS，或用 `grep 'default.aspx'` 直接搜。判据要落在"检出策略"上：NTFS 允许的命名流数量不限，长度可达数十 MB，而 `fls` 的默认输出对匿名流与命名流的呈现格式不同——不先做流名频次统计，就无从知道该往哪个方向找；且逐文件检查 4821 个文件在实践中不可行。正确判据是先建立流名的分布表，再按"数量异常 + 名称异常"双条件筛出候选。按错误判据走的代价：漏检，而漏检在安全事件里是**最容易被当作"确实不存在"的那一类结果**——委托方拿着"未发现其他后门"的结论关闭了调查，而真正的第二份 payload 仍挂在某个叫 `Zone.Identifier` 的流里。

<a id="section-37"></a>

### 5.3 反例：`0xE5` 幽灵文件名的处理方式

**场景**

另一批检查中，`$I30` 索引里出现了 `shell.aspx` 与 `cmd.php` 两个名字，但 `fls` 全量输出中查不到它们。分析员在报告中直接写"发现两个已删除的后门文件"。这条列为反例，是因为 NTFS 的目录索引（`$I30`）是 B+ 树，删除时索引项会留下标记而名字字节往往仍在——能看到名字，不等于内容还在。

**处置过程**

对照点在于"名字可见"与"内容可取"之间的距离：

```bash
# 名字仍在索引中
icat -o 2048 /work/DigiForensics.dd 88210-0-0 > /tmp/www-i30.bin
xxd -l 4 /tmp/www-i30.bin                          # 49 4e 44 58 = "INDX"
strings -e l /tmp/www-i30.bin | grep -iE 'aspx|php'
# → "shell.aspx"、"cmd.php"

# 但内容呢？
icat -o 2048 /work/DigiForensics.dd <对应的 inode> 2>&1
# → 报 invalid metadata record / 数据簇已被复用 → 取不到
```

```text
$f / %I30 中名字仍在的三种可能：
  ① 条目被标记删除但索引节点尚未被清理复用  → 内容可能还在
  ② 内容已被释放并分配给其他文件           → 名字是残留，内容是别人的数据
  ③ 内容被覆盖                             → 名字是残留，内容为空
判断依据必须来自 MFT 条目本身（InUse 位 + 数据块地址是否有效），
不能来自"索引里还有这个名字"。
```

**结论**

阴性发现：`$I30` 中的 `shell.aspx`、`cmd.php` 为**幽灵文件候选**，本次**未能提取其内容**，仅作线索记录。**未覆盖范围**包括它们原始内容——数据簇已被复用，属物理上不可恢复。

**误判对照**

最像的误判是"索引里有名字 + `strings` 能看到内容特征 = 找到了已删除的后门文件"。判据要落在索引结构的性质上：`$I30` 是目录索引，它的存在目的是加速名字查找，删除文件时索引项的处理与数据流无关；能看到名字只能证明"这个索引节点还没被清理或被复用"，而内容是否还在取决于该文件对应的 MFT 条目是否还有有效的数据块映射。

判据还应配一个反向检查：`$I30` 里出现的名字与 `fls` 全量输出的差集，恰好就是索引残留——这个差集的存在本身就是"索引不可信"的证据。正确判据是名字线索要落到 MFT 条目与数据块上才能升级为结论。按错误判据走的代价：报告声称"发现两个已删除的后门"，而实际上取不到任何内容；

委托方按此追查文件名相似的其他机器设备，方向完全偏离——"发现了名字"与"发现了文件"之间隔着一个数据块的有效性。

### 工具与规范

- `fls` / `istat` / `icat` / `blkls` 的组合用法见[命令速查](#section-44)——本篇的四层检查是四条独立命令链，参数差异只在 `-o` 与地址写法上，值得对照着跑一遍。
- 报告写法上，逐层覆盖状态的写法（哪些层查了、哪些层没查、为什么没查）可参考 [NTFS 案例](#section-34)里的表；**留空白的层次在报告里等于没查**。
- 提取物的固定流程与授权边界见[取证流程与原则](../../fundamentals/fundamentals-process/fundamentals-process-five-stage-forensics-process.md)——从隐藏区域取出的内容同样是证据，**先固定哈希再解读**，顺序不能反。

<a id="section-43"></a>

### 判据与反例

- **判据**：是否"存在恶意内容"要分两层表述。第一层是客观事实（"PNG 的 `IEND` 之后有 4 KB 数据"），第二层才是定性（"这是攻击者藏的命令"）。**报告里两层必须分行写**，合成一句就是把推断当事实。
- **反例一**：`Zone.Identifier` 是浏览器下载时的系统正常标记，出现即报警是误判；判据应是**流名 + 内容特征 + 上下文**三者结合。
- **反例二**："文件被覆盖了"不等于旧内容消失——slack 里往往还有更早版本。这一条容易让人反过来过度宣称"已恢复原始文件"，同样是不合格的结论强度。
- **反例三**：在时间受限的委托里只查了命名流就写"未发现隐藏文件"。**覆盖面不足的阴性结论没有证明力**，必须写成"仅覆盖命名流层，其余三层未检查"。
- **反例四**：把"在命名流中提取到可执行 PHP 代码"直接写成"该文件是 webshell"。主文件内容是清白的、41 KB 载荷挂在命名流上，两者不是同一对象；**混为一谈会让当事人对被入侵范围产生错误判断**。
- **判据补充**：slack 的长度依赖簇大小与声明长度的差值，换一个卷（簇 4 KB → 8 KB）同样的提取偏移就失效。报告里记提取结论时应同时记下簇大小，否则结论无法复现。

## 七、命令速查

```bash
# ===== 环境 =====
sudo apt install sleuthkit file xxd binutils
# -o 2048 为 NTFS 分区起始扇区，替换为 mmls 实际值

# ===== 命名流：全量发现 =====
fls -o 2048 -r -p /work/DigiForensics.dd > /evidence/fls-all.txt
grep -E '\$[^/]*$' /evidence/fls-all.txt | head -50          # 所有命名流
grep -oE '\$[A-Za-z0-9_.$-]+$' /evidence/fls-all.txt | sort | uniq -c | sort -rn | head
# 同一 MFT 条目 + 不同属性 ID（如 11443-128-4 / 11443-129-4）= 同文件的多个 $DATA 流

# ===== 命名流：提取与验证 =====
istat -o 2048 /work/DigiForensics.dd 11443-129-4            # 属性列表与流名
icat  -o 2048 /work/DigiForensics.dd 11443-129-4 > /tmp/stream.bin
file /tmp/stream.bin && sha256sum /tmp/stream.bin && xxd -l 64 /tmp/stream.bin

# ===== $I30 索引：幽灵文件检测 =====
icat -o 2048 /work/DigiForensics.dd 5-0-0 > /tmp/root-i30.bin
xxd -l 4 /tmp/root-i30.bin                                   # 期望 49 4E 44 58 = "INDX"
strings -e l /tmp/root-i30.bin | sort -u > /evidence/i30-names.txt
comm -23 /evidence/i30-names.txt <(cut -d' ' -f7- /evidence/fls-all.txt | sort -u) > /evidence/ghost.txt

# ===== Slack 空间 =====
# 文件大小 3500、簇 4096 → slack 为簇内 3500 之后的 596 字节
dd if=/work/DigiForensics.dd bs=512 skip=$((2048 + 252*8)) count=8 of=/tmp/cluster0.bin status=none
dd if=/tmp/cluster0.bin of=/tmp/slack0.bin bs=1 skip=3500 count=596 status=none
strings -n 6 /tmp/slack0.bin

# ===== 未分配空间 =====
blkls -o 2048 /work/DigiForensics.dd | strings -n 20 | grep -iE 'password|PRIVATE KEY'
grep -aob 'target-string' /work/DigiForensics.dd | head          # 全镜像搜索
blkls -o 2048 -l /work/DigiForensics.dd | head -20               # 列出数据单元的时间戳与归属

# ===== 隐写检查（追加型）=====
# PNG：IEND 块(12 字节)之后是否还有数据
f=/evidence/suspect.png; sz=$(wc -c < "$f" | tr -d ' ')
typeoff=$(grep -abo 'IEND' "$f" | tail -1 | cut -d: -f1)
tail=$(( sz - (typeoff - 4) - 12 ))
[ "$tail" -eq 0 ] && echo "PNG 正常" || echo "IEND 之后还有 $tail 字节 → 疑似隐写"
tail -c 16 /evidence/suspect.jpg | xxd -p                                          # JPEG FFD9 应在末尾
tail -c 32 /evidence/suspect.pdf | strings                                           # PDF %%EOF 应在末尾
```

```powershell
# ===== Windows 原生枚举 ADS =====
Get-Item 'C:\inetpub\wwwroot\default.aspx' -Stream *
Get-Content -Path 'C:\inetpub\wwwroot\default.aspx' -Stream 'hidden'
```
