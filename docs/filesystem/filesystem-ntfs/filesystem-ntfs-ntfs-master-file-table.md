# NTFS 结构与 MFT 解析

<a id="section-1"></a>

## 一、概述

Windows 默认文件系统，真实案件里出现频率最高的就是它。最突出的设计特征是把每个文件或目录的全部元数据集中存放在一张固定大小的表里——`$MFT`（Master File Table），每条记录 1024 字节。

破案要的字段基本都在这张表里。文件名、四个时间戳、大小、位置、父目录引用、权限，全在一个固定偏移处的定长记录里，不用像 ext 系那样跨多个分散结构拼装。`$MFT` 自身的起点由 Boot sector 偏移 0x30 的 MFT Cluster Number 指定，字节偏移 = 簇号 × 簇大小。

同一份设计也是攻击面：篡改 `$MFT` 就能让操作系统"看不见"文件，而文件内容依然在磁盘上。这就是 NTFS 取证的核心张力——**你得先能读懂这张表，才谈得上判断它有没有在骗你**。

判读 MFT 落在分析环节的元数据判读阶段，也就是[文件系统取证总览](filesystem-ntfs-filesystem-forensics-overview.md)判定完"这是 NTFS"之后的第一步。上游是卷层判定与接入；下游三路：元数据层面的时间戳异常走向[反取证手法与时间戳篡改检测](../../fundamentals/fundamentals-concepts/fundamentals-concepts-anti-forensics-and-timestamp-tampering.md)，属性层之外的隐藏数据走向[NTFS 数据流与隐藏数据](filesystem-ntfs-ntfs-alternate-data-streams.md)，从现状追到过程走向[Steady-State 与 LogFile 还原](filesystem-ntfs-steady-state-logfile.md)。

`fls` / `istat` / `icat` 的通用用法在[只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md)讲过，这里聚焦的是每个输出字段意味着什么、哪个字段能定案。同一个 `istat` 输出里，"Changed 晚于 Modified 3 秒"这句话是一句废话还是一条线索，取决于是否掌握 2.6 与 `$STANDARD_INFORMATION` 的更新规则。

落到具体证据上：

- **`$MFT` 的位置与大小** —— Boot sector 偏移 0x30 的簇号 × 簇大小。第五章案例：簇号 `0x40000`、簇大小 4096、起始扇区 526336。**该值随簇大小变化，不要硬编码**
- **`$MFT` 记录 0–11 的固定身份** —— 0 是 `$MFT` 自身，1 是 `$MFTMirr`（**主表前 4 条记录的备份**，常被漏检），2 是 `$LogFile`，3 是 `$Volume`，4 是 `$AttrDef`，5 是根目录 `.`（**文件名就是单个点**），6 是 `$Bitmap`，9 是 `$Secure`，11 是 `$Extend`
- `FILE` / `BAAD` / `INDX` 三种魔数 —— `FILE` 是正常基记录；`BAAD` 可与记录更新序列修复失败或解析异常有关；还须排除坏扇区、截断、采集故障和工具表示差异，不能单独定性人为篡改；`INDX` 是索引缓冲区，**不是 MFT 记录**，容易误判
- `$STANDARD_INFORMATION`（0x10） —— 4 个时间戳及文件属性标志等；硬链接计数应查看 FILE 记录头，而非归入 `$STANDARD_INFORMATION`。取证价值 ★★★★★
- **`$FILE_NAME`（0x30）** —— 文件名 + **父目录 MFT 引用**，路径还原的核心。一条记录里**可能有两个**（Win32 长名 + DOS 8.3 短名），短名的存在与否是 `NtfsDisable8dot3NameCreation` 的弱指标
- **`$DATA`（0x80）** —— 驻留（<700 字节内嵌）与非驻留（独立簇链 + runs）。删文件后 MFT 里的属性描述仍在，只是数据簇被标记空闲
- **`$ATTRIBUTE_LIST`（0x20）** —— 已知反取证手法用它把 `$DATA` 挪到别处。只读第一条记录而不解析属性列表，会漏掉真实数据
- **MFT 引用的 48 位结构** —— 低 48 位是记录号，高 16 位是**序列号**。第五章案例里 `fls -p` 输出的是 `11443-128-3`，其中 `128` 表示 NTFS `$DATA` 属性类型码，`3` 是属性 ID；MFT 引用的序列号需要从元数据引用或文件记录头另行取得。只写"条目 11443"无法区分原文件与三个月后复用该条目的新文件
- Fixup（Update Sequence Array） —— USA offset 通常 0x30，USA count = 记录长/扇区大小 + 1。读取时必须先还原，否则属性结构可能被邻接数据污染，读出错误的文件大小与偏移

一张 MFT 记录能回答的是这些：记录里有哪些字段、每个字段的取证用途、`$FILE_NAME` 怎么向上追溯成完整路径、Fixup 为什么必须在解析最前面处理，以及怎样用一个 8 字节 MFT 引用把结论表述得可复核。

条目被删除后可能被新文件复用，所以取证引用必须写成"记录号-序列号-世代"，否则报告里的坐标区分不了两个不同的文件。第五章案例通篇用 `11443-128-3` 这种形式引用，便于复核者按同一记录引用重跑查询。

有几件事不归这一层管：命名流（ADS）、`$I30`、slack 与未分配空间在[NTFS 数据流与隐藏数据](filesystem-ntfs-ntfs-alternate-data-streams.md)；**从现状追到元数据变化过程**靠 `$LogFile` 的 LSN 与日志回放，见[Steady-State 与 LogFile 还原](filesystem-ntfs-steady-state-logfile.md)；**这个时间戳可不可信**——MFT 记录只告诉你它写了什么，不告诉你它有没有被改过，检出能力在[反取证手法与时间戳篡改检测](../../fundamentals/fundamentals-concepts/fundamentals-concepts-anti-forensics-and-timestamp-tampering.md)；**文件雕刻**则是簇链断了的情况，走另一条路。

往下读之前需要三样前置：**分区与卷层概念**（`fls` 的 `-o 2048` 是什么）、**十六进制与位运算**（MFT 记录头那一串偏移长度表要自己核），以及 **Sleuth Kit 命令行的基本使用**（这里不复述 `fls` / `istat` / `icat` 的通用语法）。

**建议动手做一次手工核对**：按第三章步骤 1 算出 MFT 起始扇区，`dd` 出一个记录，用 `xxd` 验证魔数是 `FILE`、USA offset 是 `0x30`、USA count 是 3。第五章案例第 1 步就是这个动作。亲手验证过之后，2.2 那张两段结构表你就再也不会把"属性序列的起点"和"USA 数组的位置"搞混——这两者是 MFT 记录里最容易读错的两块。

## 二、核心原理

<a id="section-3"></a>

### 2.1 `$MFT` 的定位

| 项目 | 值 |
|---|---|
| 主表位置 | Boot sector 的 **MFT Cluster Number** 字段（偏移 0x30）指定 |
| 记录大小 | **1024 字节**（一个簇；现代实现未启用 4096 字节 MFT 记录） |
| 记录 0 | `$MFT` 自身 |
| 记录 1 | `$MFTMirr`（主表前 4 条记录的备份） |
| 记录 2 | `$LogFile`（元数据日志，见 [04](filesystem-ntfs-steady-state-logfile.md)） |
| 记录 3 | `$Volume`（卷名、NTFS 版本号、dirty flag） |
| 记录 4 | `$AttrDef`（属性定义表） |
| 记录 5 | `.`（根目录，**文件名就是单个点**） |
| 记录 6 | `$Bitmap`（簇分配位图） |
| 记录 7 | `$Boot`（引导记录，作为文件存在） |
| 记录 8 | `$BadClus`（坏簇映射） |
| 记录 9 | `$Secure`（安全描述符与 ACL） |
| 记录 10 | `$UpCase`（Unicode 大写映射表） |
| 记录 11 | `$Extend`（扩展目录，含 `$UsnJrnl` / `$ObjId` / `$Quota` / `$Reparse`） |
| 记录 12–15 | 保留 |

```bash
fsstat -o 2048 /work/DigiForensics.dd | grep -iE 'cluster|mft'
# Cluster Size: 4096              MFT Cluster: 0x40000    MFT Mirror Cluster: 0x40006
# Boot Sector Cluster: 0x8000     Volume Serial Number: 9a3f21c4    Volume Name: OSDisk
```

> **换算**：MFT 字节偏移 = 簇号 × 簇大小。例中 MFT 起点 = `0x40000 × 4096`，**相对卷起始**（加分区起始扇区才是相对磁盘的偏移）。该值随簇大小变化，**不要硬编码**。

<a id="section-4"></a>

### 2.2 MFT 记录的两段结构

每条 1024 字节记录分成**头部 + 属性序列**两段：

| 偏移 | 长度 | 字段 | 偏移 | 长度 | 字段 |
|---|---|---|---|---|---|
| 0x00 | 4 | 魔数 `FILE` | 0x14 | 2 | 首个属性偏移 |
| 0x04 | 2 | USA offset（通常 **0x30**） | 0x16 | 2 | 标志（0x01 在用 / 0x02 目录） |
| 0x06 | 2 | USA count（= 记录长/扇区大小 + 1） | 0x18 | 4 | 已用字节数 |
| 0x08 | 8 | `$LogFile` 日志序列号 LSN | 0x1C | 4 | 已分配字节数（8 字节对齐） |
| 0x10 | 2 | 序列号 Sequence Number | 0x20 | 8 | 基础文件引用 |
| 0x12 | 2 | 硬链接计数 | 0x28 | 2 | 下一属性 ID |
| **USA 数组** | USA offset | USA count × 2 | **属性序列** | 首个属性偏移 → 0x2FF | 见 2.3 / 2.6 |

**记录类型由魔数区分**：

| 魔数 | 类型 | 含义 |
|---|---|---|
| `FILE` | 基记录 | 文件/目录的完整属性都在这里 |
| `BAAD` | 损坏记录 | Fixup 校验失败后被标记（**人为篡改的强信号**） |
| `0` 填充 | 空闲 | 该 MFT 条目从未使用或已释放 |
| `INDX` | 索引记录 | **不是 MFT 记录**，是索引缓冲区（见 [03](filesystem-ntfs-ntfs-alternate-data-streams.md)） |

<a id="section-5"></a>

### 2.3 属性列表（Attribute List）

每条 MFT 记录内含若干属性（attribute），最常见四个：

| 属性类型 | ID | 作用 | 取证价值 |
|---|---|---|---|
| `$STANDARD_INFORMATION` | 0x10 | 4 个时间戳、文件属性标志、硬链接数 | ★★★★★ 时间线核心 |
| `$FILE_NAME` | 0x30 | 文件名 + **父目录 MFT 引用** | ★★★★★ 路径还原核心 |
| `$DATA` | 0x80 | 文件内容（或目录的 `$I30` 索引） | ★★★★★ 内容提取 |
| `$ATTRIBUTE_LIST` | 0x20 | 记录"本条记录装不下，属性在别处" | ★★★ **属性可拆分藏匿** |

**属性通用头结构**：

```
0x00 4  属性类型（0x10/0x30/0x80...）      0x0A 2  名称偏移
0x04 4  属性长度（8 字节对齐）              0x0C 2  标志（0x0001压缩/0x4000加密/0x8000稀疏）
0x08 1  非驻留标志（0=驻留 1=非驻留）       0x0E 2  属性 ID
0x09 1  名称长度（0 = 匿名流）              0x10+ 值长度(驻留) / VCN+数据偏移(非驻留)
```

**驻留与非驻留是重要分界**：驻留 = 小数据（<700 字节）直接内嵌在 MFT 记录里；非驻留 = 存在独立簇链上，MFT 只存起始 VCN 与映射信息。

删掉文件后 MFT 里的属性描述仍在，只是数据簇被标记为空闲——这是[文件雕刻](../filesystem-unix/filesystem-unix-file-carving-and-signature-recovery.md)之外的另一条恢复路径基础。

`$ATTRIBUTE_LIST` 则让属性可分散在多条记录中：攻击者用它把 `$DATA` 挪到别处是已知反取证手法，只读第一条记录而不解析属性列表会漏掉真实数据。

<a id="section-6"></a>

### 2.4 MFT 引用：48 位的"记录号+序列号"结构

`$FILE_NAME` 属性里有一个 **8 字节**的父目录引用。**MFT 引用共 64 位，但只有低 48 位有效**：

| 位 | 宽度 | 含义 |
|---|---|---|
| **0–47** | **6 字节** | **MFT 记录号**（低位在前） |
| **48–63** | **2 字节** | **序列号**（Sequence Number，同一条目被重用后的代数） |

**为什么序列号重要**：MFT 条目被删除后可能被**新文件复用**——此时记录号相同但序列号递增。取证引用若只写"条目 11443"，分不出"原来的文件"和"三个月后占用同一条目的新文件"。

> ⚠️ **TSK 元数据地址不是这个结构**：Sleuth Kit 输出的 `11443-128-3` 是 **MFT 条目号 - 属性类型码 - 属性 ID**，其中 128 = 0x80 = `$DATA` 的属性类型码，`3` 是该属性在记录内的实例 ID。**中间那个 128 与 MFT 序列号毫无关系**——把它读成"条目被复用 128 次"是常见误判。真正的序列号要看 `istat` 输出里的 `Sequence:` 行。

**多层引用怎么写**：一个文件可能有多个 `$DATA`（主数据流 + 多个 ADS），这时必须补上属性 ID 才能唯一定位；只有一个同名类型属性时写 `条目-类型` 即可。

TSK 会为跨 MFT 记录的属性重新分配唯一 ID，所以报告里直接引用 `istat` 打印的那串地址最稳妥。

<a id="section-7"></a>

### 2.5 `$FILE_NAME` 还原完整路径

`$FILE_NAME` 属性（0x30）结构：

```
偏移  长度  字段
0x00  8   父目录 MFT 引用（48 位有效，见 2.4）
0x08  24  创建 / 修改 / MFT 变更 三个 FILETIME
0x20  8   访问时间 FILETIME
0x28  4   分配大小 Allocated Size      0x2C 4  真实大小 Real Size
0x30  4   标志（1=目录 2=压缩 4=隐藏 8=系统 16=临时）
0x34  4   重解析点值                   0x38 1  名称长度（字符数）
0x39  1   名称类型（1=POSIX 2=Win32 3=DOS 4=Win32&DOS）    0x3A n  UTF-16LE 文件名
```

一条 MFT 记录里可能同时存在两个 `$FILE_NAME`：一个 Win32 长名，一个 DOS 8.3 短名（`TXT~1.TXT`）。短名存在与否是 **8.3 名字生成功能开关**（`NtfsDisable8dot3NameCreation`）留下的痕迹——是"该卷是否被刻意配置过"的弱指标，但不能单独定性。

**路径还原算法**：取当前记录的 `$FILE_NAME` 父目录引用 → 跳到父记录取它的 `$FILE_NAME` → 直到条目 5（根目录 `.`）→ 反向拼接。TSK 的 `fls -p` 已内部完成；**自己解析时这就是全部工作**。

<a id="section-8"></a>

### 2.6 Fixup（Update Sequence Array）——NTFS 的扇区完整性校验

**问题**：MFT 记录跨多个扇区。若某扇区是坏道或写入时中断，该扇区里**文件的其他数据就会破坏此记录的结构**。Fixup 机制为此设计：

1. 写入记录时，把**每扇区最后 2 字节**的原始值备份到记录尾部的 Update Sequence Array（USA）；
2. 写入后，这些最后 2 字节被改写为 **USA 数组的索引值**（0、1、2、3…）；
3. 读取时：读出 USA → 校验各扇区末 2 字节是否等于预期索引 → 用 USA 备份值还原 → **结构仍不合法则标记为 `BAAD`**。

```
0x00  FILE
0x04  USA Offset = 0x30
0x06  USA Count = 3        （= 1024/512 扇区 + 1 个数组项）
记录中部：每 512 字节末 2 字节被写成 0x0000 / 0x0001 / 0x0002
0x30  00 00  01 00  XX XX  YY YY   ← USA 数组：索引值 + 各扇区原始末 2 字节
```

**取证意义（三点，都很重要）**：

| 视角 | 含义 |
|---|---|
| **为什么解析器必须先处理 Fixup** | 不还原则属性结构可能被邻接数据污染，读出错误的文件大小与偏移 |
| **`BAAD` 魔数 = 强信号** | 正常磁盘故障极少产生 `BAAD`；大量 `BAAD` 记录指向**人为篡改或定向破坏** |
| **Fixup 差异是残留痕迹** | 若某记录的 USA 索引值与扇区位置不匹配（不连续/乱序），说明有人**手工改写过扇区末 2 字节** |

多数成熟解析器（TSK 等）自动完成 Fixup 处理，你不会看到原始 USA。但当解析结果"某个文件的 `$DATA` 长度完全不合理"时，手工 dump 原始 MFT 记录、验证 USA 一致性是必要的取证动作：

```bash
# MFT 起始扇区 = 分区起始 + MFT簇号 × 簇大小 / 512 = 2048 + 0x40000*4096/512
dd if=/work/DigiForensics.dd bs=512 skip=526336 count=2 status=none | xxd -l 64
# 期望：4649 4C45（"FILE"）… 3000 0300（USA offset=0x30, count=3）
```

## 三、操作步骤

<a id="section-10"></a>

### 3.1 第 1 步：定位 MFT 并提取

```bash
# ① 从超级块拿到 MFT 簇号与簇大小（不假定簇大小，务必实测）
fsstat -o 2048 /work/DigiForensics.dd | grep -iE 'cluster|mft|serial'

# ② 按簇号换算字节偏移，提取前若干条 MFT 记录（记录 0 = $MFT，记录 5 = 根目录）
dd if=/work/DigiForensics.dd bs=4096 skip=$((0x40000)) count=8 of=/tmp/mft-head.bin status=none

# ③ 确认魔数：xxd -l 4 /tmp/mft-head.bin  → 46 49 4C 45 = "FILE"
```

<a id="section-11"></a>

### 3.2 第 2 步：导出全量元数据

```bash
fls -o 2048 -r -p /work/DigiForensics.dd > /evidence/fls-all.txt
grep -i deleted /evidence/fls-all.txt                        # 已删除项
fls -o 2048 -r -p /work/DigiForensics.dd | grep -E '\$[A-Za-z]'   # 系统元数据文件
```

<a id="section-12"></a>

### 3.3 第 3 步：逐文件读元数据（istat 核心用法）

`istat` 是本篇的主力工具。**关键在于读懂它的每一段输出**：

```bash
istat -o 2048 /work/DigiForensics.dd 11443-128-3
```

输出结构与解读（`-o` 为起始扇区，inode 用 `fls` 输出的 MFT-序列-属性 形式）：

```
Class: 1
Type: Regular        ← 1=文件 2=目录 3=特殊（设备/FIFO等）
Size: 24576
MFT Cluster: 262144  ← 所在 MFT 记录号
Created: 2024-03-11 09:22:41     ← $STANDARD_INFORMATION
Modified: 2024-06-02 14:07:19
Accessed: 2024-06-02 14:33:55
Changed: 2024-06-02 14:07:22     ← MFT 记录自身的修改时间（FSN）

Attributes:
0x10 $STANDARD_INFORMATION  72 bytes
0x30 $FILE_NAME             104 bytes  Name: report.docx
0x80 $DATA                   24576 bytes  Resident: NO   Runs: (fc,1) (fd,1) ...
```

| 字段 | 定性价值 | 使用建议 |
|---|---|---|
| **Type** | 确认是文件还是目录 | `1=Regular 2=Directory`；异常类型需解释 |
| Created / Modified / Accessed / Changed | **时间线四要素** | `Changed` 与 `Modified` 不一致 = 元数据被改过 |
| **File Name 属性名** | 真实文件名（含短名） | 与 `fls` 显示名不符时以 `$FILE_NAME` 为准 |
| **$DATA Resident** | 小文件内嵌在 MFT | `Resident: YES` 意味着内容直接在 MFT 里 |
| **Runs（簇链）** | 数据物理位置 | 稀疏/压缩文件会出现异常跳变 |

**重要判读**：`Changed` 时间（FSN，"File Sequence Number" 变更时间）**只在 MFT 记录本身被改写时更新**——重命名、改权限、写入 ADS 都会更新它，但**不会**在普通内容修改时更新。`Modified` 变而 `Changed` 不变 = 内容被改；`Changed` 变而 `Modified` 不变 = 元数据被改。 这对判定"文件被重命名过/权限被篡改过"极有用。

<a id="section-13"></a>

### 3.4 第 4 步：提取文件内容并验证

```bash
# 提取（inode 从 istat/fls 获取）
icat -o 2048 /work/DigiForensics.dd 11443-128-3 > /evidence/report.docx
file /evidence/report.docx          # 魔数是否与文件名相符
stat -c '%s' /evidence/report.docx  # 长度应等于 istat 的 Size
sha256sum /evidence/report.docx
```

**若实际长度 < Size**：数据簇被部分覆盖（常态，须记录）。**若实际长度 > Size**：可能有多个命名流或解析有误。

<a id="section-14"></a>

### 3.5 第 5 步：定位系统元数据文件

```bash
icat -o 2048 /work/DigiForensics.dd 2-0-0  > /evidence/LogFile.bin    # MFT 记录 2，见 [04](filesystem-ntfs-steady-state-logfile.md)
icat -o 2048 /work/DigiForensics.dd 1-0-0  > /evidence/MFTMirr.bin    # 记录 1，仅前 4 条

|---|---|---|

```

## 四、常见陷阱

本章按「定位与结构识别 → MFT 记录判读 → 属性层解析 → 结果验证与结论表述」归组，每条给出：现象、为什么会误判、误判代价、正确做法。

★ 标记表示该操作会导致原始检材永久灭失或不可逆改变，执行前必须停下来确认。

<a id="section-17"></a>

### 4.1 定位与结构识别

<a id="section-18"></a>

#### 陷阱 1：★ 硬编码 MFT 偏移，换个簇大小就全错

**现象**：脚本里写死 `MFT 起始扇区 = 262144`，在簇大小 4096 的卷上取到了 `FILE` 魔数就推广使用。换一份 8192 簇大小的镜像，同样的脚本取到的是随机数据，解析出的文件表完全是乱的。

**原因**：MFT 位置由 Boot sector 的 MFT Cluster Number 指定，而字节偏移 = 簇号 × 簇大小（2.1）。**簇大小随卷而变，不是常量**——它由 BPB 字段决定，2 KB 到 64 KB 都可能。"MFT 在某个固定位置"这个印象来自小型格式化卷的默认值，而它不是结构保证。

麻烦的是取到 `FILE` 魔数会给人"验证通过"的错觉。**因为那个位置确实曾经是 MFT，只是这一次不是。**

**影响**：**错误的 MFT 偏移会让整份元数据表完全错误**，而这个错误**不会在解析时报错**——你会得到一张看起来结构化、实则全是错位的文件表。报告里"该文件位于条目 11443"这类引用全部不可用，而**可复核性是这类结论的生命线**。

**核查**：**始终从超级块实测，且换算要写清相对关系**：

```bash
# ① 从超级块拿簇大小与 MFT 簇号（不假定簇大小）
fsstat -o 2048 /work/DigiForensics.dd | grep -iE 'cluster|mft|serial'
# Cluster Size: 4096    MFT Cluster: 0x40000

# ② 换算：MFT 字节偏移 = 簇号 × 簇大小；再加分区起始扇区才是相对磁盘的偏移
#   案例：0x40000 × 4096 / 512 = 524288，+ 2048 = 526336 ✓
dd if=/work/DigiForensics.dd bs=512 skip=526336 count=2 status=none | xxd -l 64
# 期望：4649 4C45 = "FILE"，且 0x30 处是 USA offset、0x06 处是 USA count=3
```

**注意"相对卷起始"这个限定**：`0x40000 × 4096` 是**相对卷**的偏移，加上分区起始扇区才相对磁盘。**报告里写偏移必须标明参照基准**，否则复核者无从核对。

<a id="section-19"></a>

#### 陷阱 2：把 TSK 的 `11443-128-3` 读成 MFT 序列号

**现象**：报告里写"该文件位于 MFT 条目 11443，序列号 128"，并据此认为"该条目已被复用 128 次"。

**原因**：TSK 输出的 `11443-128-3` 不是 MFT 引用的结构（2.4 的明确警示）。它是 **MFT 条目号 - 属性类型码 - 属性 ID**，其中 128 = 0x80 = `$DATA` 的属性类型码，`3` 是该属性在记录内的实例 ID。

真正的 MFT 序列号在 `$FILE_NAME` 属性的父目录引用里（48 位结构），以及 `istat` 输出的 `Sequence:` 行。两者是完全不同的东西，坏就坏在 128 这个数字"看起来很像"一个序列号。

**影响**："条目被复用 128 次"是一个关于文件系统历史的强断言，而它建立在一个字段含义的误读上。序列号是判定"这个条目当前是否还是原来那个文件"的唯一依据——不带上序列号，就区分不了"原文件"与"后来占用同一条目的新文件"。案例里"条目坐标已记录、可复核"这句话，前提就是引用方式正确。

**核查**：报告里引用 MFT 条目必须带序列号，且直接引用 `istat` 打印的地址串（2.4 的建议）：

```bash
# 真实序列号在这里
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -iE 'sequence|inode'
# TSK 地址串 11443-128-3：条目 11443、$DATA(0x80)、属性 ID 3
```

**多层引用要补属性 ID**：一个文件可能有多个 `$DATA`（主数据流 + 多个 ADS），**这时"条目-类型"不足以唯一定位**（2.4）。报告里写"条目 X（序列号 Y）的 `$DATA` 属性 ID Z"，并在 ADS 情形下逐个列出。

<a id="section-20"></a>

#### 陷阱 3：跳过 Fixup 处理，读出错误的文件大小与偏移

**现象**：解析 MFT 记录时读到某个 `$DATA` 的长度是一个明显不合理的巨大值，提取时 `icat` 报错或返回垃圾数据，判为"该文件已损坏"。

**原因**：MFT 记录跨扇区，而每扇区最后 2 字节在磁盘上被改写为 USA 索引值（2.6）。不先做 Fixup 还原就读属性结构，属性里的长度与偏移字段会被这些残留值污染——读到的是"扇区尾字节 + 真实数据"的混合内容，**其结果仍是一个合法但错误的整数**。

这个错误不触发任何异常，只会给你一个"看起来很大"的长度。而"长度不合理 = 文件损坏"这个推论，顺畅地跳过了"我的解析可能有错"这个更可能的成因。

**影响**：**误判"文件已损坏"会导致放弃一个完好的文件**。而在涉及文件完整性的案件里，"该文件已损坏"是一个关于证据可用性的结论，**放弃它等于让这份证据在报告中变成空白**。

**核查**：优先信任成熟解析器的结果；怀疑时手工 dump 原始记录验证 USA：

```bash
# 提取目标记录的原始 1024 字节（不经过任何解析器）
dd if=/work/DigiForensics.dd bs=512 skip=$((MFT_START+11443*2)) count=2 status=none \
   of=/tmp/mft-11443.bin
xxd -l 64 /tmp/mft-11443.bin
# 检查：魔数 4649 4C45 = FILE；0x04 处 USA offset 通常 0x30；0x06 处 USA count=3
# 检查各扇区末 2 字节是否为 0x0000/0x0001/0x0002（连续且与扇区序号对应）
```

**两条判读原则**：**USA 索引值必须与扇区位置对应且连续**——乱序或不连续说明有人**手工改写过扇区末 2 字节**（这是一个独立的篡改痕迹）。**还原后结构仍不合法则该记录被标记为 `BAAD`**——大量 `BAAD` 记录是指向人为篡改或定向破坏的强信号，正常磁盘故障极少产生。

<a id="section-21"></a>

### 4.2 MFT 记录判读

<a id="section-22"></a>

#### 陷阱 4：把 `BAAD` 记录当作普通损坏跳过

**现象**：全量扫描 MFT 时发现若干条 `BAAD` 魔数的记录，分析员记为"损坏记录"并跳过，报告里不提及。

**原因**：`BAAD` 不是随机的硬件故障结果，而是 Fixup 校验失败后由系统主动写入的标记（2.2、2.6）。**正常磁盘故障极少产生 `BAAD`**——坏道导致的是读取错误、校验和失配，而不是让 NTFS 把一条记录标成 `BAAD`。"损坏"是一个中性描述，而 `BAAD` 的成因分布高度偏向人为干预。

**影响**：`BAAD` 记录往往正是被定向破坏的条目——攻击者改写 MFT 记录后，Fixup 校验失败，该记录就成了 `BAAD`。跳过它们意味着**主动丢弃了篡改的直接物证**，而报告里"未发现篡改痕迹"会与此前的其他证据矛盾。

**核查**：**`BAAD` 记录必须逐条统计、定位、并分析**：

```bash
# 1) 统计 BAAD 数量与位置
dd if=/work/DigiForensics.dd bs=512 skip=$MFT_START count=$MFT_SECTORS status=none \
  | python3 -c "
import sys
d = sys.stdin.buffer.read()
for i in range(0, len(d) - 1024, 1024):
    m = d[i:i+4]
    if m == b'BAAD':
        print('BAAD at MFT entry', i // 1024)
    elif m == b'FILE':
        pass
# FILE 之外的第四种情况：全 0 = 空闲槽位，也是正常的
"
# 2) 分析 BAAD 记录的内容：属性结构是否仍然可辨、指向了哪些簇
# 3) 与相邻记录的 USA 一致性对比，判断是单条还是批量
```

**报告里要写明**：`BAAD` 记录数量、条目号、**成因分析**（单条 vs 批量、分布是否集中）。批量 `BAAD` 与单条 `BAAD` 的解释完全不同——前者更像定向清理，后者可能是偶发故障。

<a id="section-23"></a>

#### 陷阱 5：把 `INDX` 当成 MFT 记录解析

**现象**：按 1024 字节步进遍历 MFT，遇到魔数 `INDX` 的记录时仍按 MFT 记录解析，读出的"属性"全是垃圾。

**原因**：**`INDX` 不是 MFT 记录，是索引缓冲区**（2.2 的记录类型表）——它是 `$DATA` 的一种命名形式，存放目录的索引（$I30）。它在磁盘上占据连续的多个扇区，结构与 MFT 记录完全不同。

而 `INDX` 这个四字节魔数在十六进制里与 `FILE` 一样醒目。脚本里如果只判断"是不是 FILE"而不判断"是不是 BAAD/INDX/0"，就会走进这个分支。

**影响**：读出无意义的"属性"会导致后续路径还原、簇链解析全部基于错误数据。这类错误在报告里的表现是"某些文件属性异常"，很容易被归为"文件系统损坏"。

**核查**：**四种魔数分别处理**：

| 魔数 | 含义 | 处理方式 |
|---|---|---|
| `FILE` | 基记录，完整属性 | 正常解析 |
| `BAAD` | Fixup 失败标记 | **单独统计与分析（见陷阱 4）** |
| `INDX` | **索引缓冲区，不是 MFT 记录** | 按索引结构处理，见 [NTFS 数据流与隐藏数据](filesystem-ntfs-ntfs-alternate-data-streams.md) |
| 全 `0` | 空闲槽位 | 跳过（正常） |

<a id="section-24"></a>

#### 陷阱 6：把 MFT 魔数相同当作记录有效的证据

**现象**：手工验证时 `xxd` 看到 `FILE` 就认为这条记录有效，继续按属性结构解析。

**原因**：`FILE` 魔数只说明这条记录的类型标记是基记录，不说明它的内容是自洽的。Fixup 未处理时，属性结构里的长度与偏移可能已被污染（陷阱 3）；`$ATTRIBUTE_LIST` 指向的属性可能根本不在本记录里（2.3）。

**"魔数对"是必要条件，不是充分条件。** 这个区分在手工解析时尤其重要，因为你会跳过解析器里那些自动做的校验。

**影响**：手工解析出的"文件大小"可能是一个被污染的值，**用它去 `icat` 提取会得到错误长度的文件**。而**提取物的长度错误会让哈希完全失效**——提取物与原文件在字节层面就不是同一个东西（见 [文件雕刻与签名恢复](../filesystem-unix/filesystem-unix-file-carving-and-signature-recovery.md) 关于证据效力的讨论）。

**核查**：魔数、USA 一致性、属性链完整三项都过，才算有效：

```bash
# ① 魔数
dd if=... of=/tmp/mft-rec.bin bs=1024 count=1
xxd -l 4 /tmp/mft-rec.bin            # 期望 4649 4C45 = FILE
# ② USA：0x04 处 offset（通常 0x30），0x06 处 count（1024/512+1 = 3）
#    验证各扇区末 2 字节 == 索引值（0/1/2）且连续
# ③ 属性链：从"首个属性偏移"逐条走，属性长度必须 8 字节对齐且不越界，
#    直到遇到类型 0xFFFFFFFF 结束标记
```

**属性长度 8 字节对齐是最容易检出的破绽**——**一个不对齐的长度几乎必然意味着解析出错**。

<a id="section-25"></a>

### 4.3 属性层解析

<a id="section-26"></a>

#### 陷阱 7：★ 不解析 `$ATTRIBUTE_LIST`，漏掉被挪走的真实数据

**现象**：解析某文件的 MFT 记录只看到一个小得多的 `$DATA` 属性，据此写"该文件大小 2 KB"；而 `icat` 按这个属性提取，得到的文件打不开。

**原因**：`$ATTRIBUTE_LIST` 存在的含义就是"本条记录装不下，属性在别处"（2.3）。攻击者用它把 `$DATA` 挪到其他 MFT 记录，是已知的反取证手法——只读第一条记录而不解析属性列表，会**漏掉真实数据所在的属性**，读到一个残缺的或替身的那部分。

"文件大小偏小"看起来完全像是"文件本来就这么小"或"文件被截断了"，不会触发任何怀疑。

**影响**：**这是本篇最需要警惕的一条**。它不只是"少读了数据"，而是**主动呈现了一个被构造出来的假象**。报告中"该文件大小 2 KB"与"内容无法打开"这两个结论会互相矛盾，而**分析员往往会选择相信文件本来就是残缺的**——因为另一条路要承认自己被反取证手法骗过了。

**核查**：见到 `$ATTRIBUTE_LIST`（0x20）必须跟进去：

```bash
# 1) 确认记录中存在 0x20 属性
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -i '0x20'
#   Attribute List: present → 本记录的属性不完整
# 2) 按属性列表逐条访问：每一项给出一个 MFT 引用（条目号 + 序列号）与属性偏移
#    真实属性在那些记录里
# 3) 把各条记录中的属性按属性 ID 重新组装，再按 ID 顺序拼接 $DATA
# 4) 序列号必须匹配——不匹配说明该条目已被复用，属性可能已属于别的文件
```

**报告里要写明这条判据**："该文件 MFT 记录含 `$ATTRIBUTE_LIST`，其 `$DATA` 属性分布 `<N>` 条记录（条目 `<列表>`），已按属性 ID 重新组装，**总长度 `<值>` 字节**。"——**这句话本身就是一条发现**，因为它的存在说明该文件被特殊处理过。

<a id="section-27"></a>

#### 陷阱 8：只读主数据流，漏掉匿名流与命名流

**现象**：`icat` 提取 `report.docx` 得到 24576 字节，与 `istat` 报告的 Size 一致，判定内容完整、提取无误，报告里不提其他数据流。

**原因**：**一个文件可以有多个 `$DATA` 属性**——主数据流、**匿名流**（无名字，直接挂 MFT 引用）、以及**命名流即 ADS**（2.4、2.3）。`$DATA` 属性在 MFT 记录里可以有多个实例，它们都指向数据内容。

而"主数据流长度 == `istat` 报的 Size"这个验证**只覆盖了其中一个**——`istat` 报的 Size 本身就是主数据流的长度。**匹配成功不代表没有其他流。**

**影响**：**案例里这个文件的真正问题恰好就在这里**——它有 1 个匿名（正文）+ 2 个命名 `$DATA` 流，**"内容完整"的结论只对主数据流成立**。漏掉命名流意味着漏掉隐藏数据，而**隐藏数据往往正是篡改行为的载体**。而在"文件曾被附加隐藏数据流"这类案情中，**这是唯一的证据**。

**核查**：主数据流之外必须逐个检查所有 `$DATA` 实例：

```bash
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -iE '0x80|Name:'
# 3 个 $DATA：1 个匿名（正文）+ 2 个命名流
# 命名流名在 0x30 类型的 $FILE_NAME 之外，需从 $DATA 的"名称偏移/名称长度"字段读
# 每个命名流都要单独提取、单独计算哈希、单独记录偏移
```

**报告里要分列**（案例结论的处理方式）："该文件存在 `<N>` 个 `$DATA` 属性——主数据流 24576 字节、命名流 `<名 1>` `<长度 1>` 字节、命名流 `<名 2>` `<长度 2>` 字节。主数据流已完整提取并验证；命名流已单独提取（偏移 `<X>`），其内容为 `<描述>`。"

<a id="section-28"></a>

#### 陷阱 9：把 `$FILE_NAME` 与 `fls` 显示名不符当成解析错误

**现象**：`fls` 显示的文件名与 `istat` 输出的 `Name:` 不一致，分析员认为工具输出不可靠，改用自己解析的短名。

**原因**：NTFS 文件名有长名（LFN）与短名（8.3）两套，`$FILE_NAME` 属性可以**同时存在多个实例**——案例里那个文件"两处 `0x30` → 长短名成对存在"。**一个 MFT 条目对应多个文件名是正常的**（改过名的文件会留下旧名）。"两个名字不一致"是文件系统设计的结果，不是解析错误。

**影响**：短名与长名**指向的是同一个文件**，但**在案件里它们的证据含义不同**——**出现 DOS 短名本身就是一条特征**（案例结论第 2 条：短名 + 命名流 + `Changed` 晚于 `Modified` 三项互证）。如果只保留一个名字，就丢掉了这条线索。**更重要的是，取错名字会导致后续搜索用错关键字。**

**核查**：全部 `$FILE_NAME` 实例都要列出，长名短名成对记录：

```bash
# 逐条读 $FILE_NAME（0x30），注意每条含一个不同的名字
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -A1 '0x30'
# 或手工：每个 0x30 属性的名称长度与偏移不同 → 多个名字
```

与 `fls` 显示不符时以 `$FILE_NAME` 为准（3.3 已明确），**但要理解差异来源**：短名是 `8.3` 截断加 `~N` 序号生成的，它的存在说明文件经历过**被改名**（或由不生成 LFN 的工具创建）。

<a id="section-29"></a>

### 4.4 结果验证与结论表述

<a id="section-30"></a>

#### 陷阱 10：★ 提取长度与 Size 不一致时，不区分"部分覆盖"与"多流/解析错误"

**现象**：`icat` 提取的文件比 `istat` 报的 Size 短了 4096 字节，报告直接写"该文件部分内容已被覆盖，不可完整恢复"。

**原因**：**长度不符至少有三种成因**（3.4）：数据簇被部分覆盖（常态）、存在多个命名流导致提取对象选择有误、以及**解析错误**（比如陷阱 3 的 Fixup 问题、陷阱 7 的属性列表未解析）。**这三种成因的处置方式完全不同**——第一种是事实，第二种是方法问题，第三种是必须重做。把它们混为一谈，等于在没有查清原因时就给出了一个不可辩护的结论。

**影响**："内容部分被覆盖，不可完整恢复"是一个关于证据状态的断言。若真相是"我漏解析了属性列表"，那么**其实可以完整恢复**，而报告已经告诉委托方这份证据不完整——**委托方可能因此改变举证策略或通知相关方**。

**核查**：**长度不符时先定位原因，再下结论**：

```bash
# 1) 记录三个长度：istat 的 Size、icat 实际输出、簇链理论长度
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -i size    # 声明
icat -o 2048 /work/DigiForensics.dd 11443-128-3 | wc -c            # 实际
# 2) 查 $DATA 的 Runs（簇链）是否连续、是否指向空闲簇
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -i 'Runs:'
# 3) 确认是否遗漏了其他 $DATA 实例（陷阱 8）
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -c '0x80'
# 4) 确认属性列表是否需要额外解析（陷阱 7）
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -i '0x20'
```

**结论分三种写法**：

| 情形 | 表述 |
|---|---|
| 簇链连续但末簇不足 | "提取 20480 字节，声明 24576 字节，**末簇内容已被后续写入覆盖**，可恢复部分占 83%" |
| 存在其他 `$DATA` | "主数据流 24576 字节已完整提取；另存在 `<N>` 个命名流，总计 `<X>` 字节，见上" |
| 解析后仍不符 | "**提取长度与声明不符且未定位原因，本项结论待定**"，并记录已排除的可能 |

**`"待定"是一个合法且专业的结论**，比给出一个错误的原因好得多。

<a id="section-31"></a>

#### 陷阱 11：把 `Changed` 晚于 `Modified` 直接写成"文件被篡改"

**现象**：某文件 `Modified` 为 14:07:19、`Changed` 为 14:07:22，报告结论"该文件已被篡改"。

**原因**：`Changed`（FSN）只在 MFT 记录本身被改写时更新（3.3 的重要判读）——重命名、改权限、写入 ADS 都会更新它，但不会在普通内容修改时更新。因此 `Changed` 晚于 `Modified` 这件事本身，**只说明"元数据在内容未变的情况下发生过改动"**，而元数据改动的原因至少有五种：重命名、改权限、改所有者、写入 ADS、备份或同步软件的操作。**这些操作在正常办公场景里每天都在发生**，没有一种是篡改。

**影响**：**"已被篡改"是一个需要承担举证责任的结论**。对方只需出示一份文件重命名的记录、或一个同步软件的日志，就能推翻它——而那时你在报告里建立的其他发现也会被一起怀疑。

**核查**：`Changed` 是信号不是结论，必须用独立证据定性（与 [反取证手法与时间戳篡改检测](../../fundamentals/fundamentals-concepts/fundamentals-concepts-anti-forensics-and-timestamp-tampering.md) 的 L2/L3 分级一致）：

```bash
# 信号层：Changed 晚于 Modified → "存在元数据改动"（L2 存疑）
# 定性层：需要至少一项独立证据
#   ① 出现短名 + 命名流 → 指向"被附加过隐藏数据流"
#   ② USN 日志的 BASIC_INFO_CHANGE / RENAME_OLD_NAME + RENAME_NEW_NAME
#   ③ 该文件在同一时段有多项异常（元数据 + 权限 + 大小）
```

**报告的定级写法**（案例的处理方式值得沿用）：

> "该文件存在元数据层面改动：出现 DOS 短名、存在 2 个命名 `$DATA` 流、`Changed`（14:07:22）晚于 `Modified`（14:07:19）3 秒。三项独立证据互相印证，共同支持"该文件在 2024-06-02 14:07:22 前后被附加了隐藏数据流"。"

**注意这段话的三个要素**：列出了三项证据、说明它们互相印证、结论只到"被附加了隐藏数据流"这个具体动作。**它没有说"文件内容被篡改"**——因为三项证据都不支持那个更强的结论。**结论的强度必须与证据的强度精确匹配。**

<a id="section-32"></a>

#### 陷阱 12：报告里只写"MFT 条目 11443"，不带序列号与属性 ID

**现象**：报告正文写"该文件位于 MFT 条目 11443"，复核者按此定位，得到的却是另一个文件。

**原因**：**MFT 条目会被复用**（2.4）。条目 11443 在被删除后可能被新文件占用，此时**记录号相同但序列号递增**。只写条目号无法区分"原来的文件"和"后来占用同一条目的新文件"——而在一台使用了几年的机器上，这种复用在对应时间窗内相当常见。

**影响**：**报告失去可复核性**，而且是在最基础的层面失去的。复核者找不到你说的东西，**在质证环节这等于结论不成立**。

**核查**：引用三要素齐全，且优先直接引用 `istat` 打印的地址串（2.4 已给出这条建议，理由是 TSK 会为跨 MFT 记录的属性重新分配唯一 ID）：

> "该文件 MFT 条目 11443（序列号 `<Y>`），主数据流属性地址 `11443-128-3`，位于卷 `9a3f21c4`（卷名 `OSDisk`）。命名流 `<名>` 属性地址 `11443-128-<Z>`。"

**卷序列号也要带上**——它与 MFT 条目号共同构成了完整的定位信息（案例第 1 步已记录 `Volume Serial Number: 9a3f21c4`）。

## 五、案例示例

<a id="section-34"></a>

### 5.1 report.docx 的三元组证据：内容完整但元数据被改

**场景**

查获 Windows 10 笔记本（NTFS，簇大小 4096），委托要求确认 `C:\Users\Public\report.docx` 是否被篡改。镜像 `DigiForensics.dd`（raw，500 GB），NTFS 分区起始扇区 2048。主副本只读封存。

委托方的问题是"这个文件被动过没有"。选择这一路径的依据是"篡改"这个问法天然引导人去找内容变化的证据，而本案真正的答案在元数据里——内容一字未改，但元数据被改了三处。

**处置过程**

**第 1 步 · 确认 MFT 位置**：

```bash
fsstat -o 2048 /work/DigiForensics.dd | grep -iE 'cluster|mft|serial'
# Cluster Size: 4096    MFT Cluster: 0x40000
# Volume Serial Number: 9a3f21c4    Volume Name: OSDisk
```

MFT 起始扇区 = 2048 + 0x40000×4096/512 = **526336**，记录 0 魔数验证为 `FILE`，与 `fsstat` 一致。

**第 2 步 · 定位并读取目标文件元数据**：

```bash
fls -o 2048 -r -p /work/DigiForensics.dd | grep -i 'report.docx'
# r/r  11443-128-3:  $FILE_NAME  24576  2024-06-02 14:07:19  2024-06-02 14:07:19  report.docx

istat -o 2048 /work/DigiForensics.dd 11443-128-3
# Class: 1   Type: Regular   Size: 24576
# Created:  2024-03-11 09:22:41    Modified: 2024-06-02 14:07:19
# Accessed: 2024-06-02 14:33:55    Changed:  2024-06-02 14:07:22  ← 晚于 Modified 3 秒
# Attributes:
# 0x10 $STANDARD_INFORMATION  72 bytes
# 0x30 $FILE_NAME             104 bytes  Name: report.docx
# 0x80 $DATA                  24576 bytes  Resident: NO  Runs: (fc,1) (fd,1)
```

关键发现：`Changed`（14:07:22）晚于 `Modified`（14:07:19）3 秒——**内容没变但元数据被改过**，这是需要追查的特征。

**第 3 步 · 提取并验证内容，同时查命名流**：

```bash
icat -o 2048 /work/DigiForensics.dd 11443-128-3 > /evidence/report.docx
file /evidence/report.docx          # → Microsoft Word 2007+
stat -c '%s' /evidence/report.docx  # → 24576，与 istat 的 Size 完全一致
sha256sum /evidence/report.docx

# 查命名 $DATA 流（ADS，见 03 篇）与长/短名成对情况
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -iE '0x80|Name:'
# → 3 个 $DATA：1 个匿名（正文）+ 2 个命名流
dd if=/work/DigiForensics.dd bs=1024 skip=$((526336/512 + 11443)) count=1 of=/tmp/mft-11443.bin status=none
xxd -l 64 /tmp/mft-11443.bin         # 46 49 4c 45 = FILE；两处 0x30 → 长短名成对存在
```

**第 4 步 · MFT 之外找第二个时钟**，这一步是把"元数据被改"从观察变成结论的关键：

```bash
# ① $UsnJrnl：内核写入，篡改者改不到
fsutil usn readjournal C: > /evidence/DigiForensics-usn.csv
grep -i 'report.docx' /evidence/DigiForensics-usn.csv
# FILE_BASIC_INFO_CHANGE  2024-06-02 14:07:19   ← 与 $SI Modified 一致
# FILE_RENAME             2024-06-02 14:07:21   ← 2 秒后
# DATA_EXTEND             2024-06-02 14:07:22   ← 与 $SI Changed 同秒

# ② $LogFile：本卷对应条目的元数据事务
icat -o 2048 /work/DigiForensics.dd 2-0-0 > /evidence/LogFile.bin
strings -a /evidence/LogFile.bin | grep -i 'report.docx' | head

# ③ 时间线回退：主事件日志 4624 落在哪个账户下
python3 -m Evtx.Evtx -f /evidence/Security.evtx --ls | grep -c 4624
```

三条来源给出的时间点拼在一起，是同一个动作的三个切面：14:07:19 元数据基础信息变更（改 `Modified`）、14:07:21 重命名、14:07:22 数据区扩展（写命名流，因而 `Changed` 上跳）。只有把它们排成序列，才能说"有一个附加流的动作"，而不是"有三个孤立的时间异常"。

**结论**

能证明：①`report.docx` 内容在采集时**完整**——提取长度 24576 字节与 MFT 声明的 `Size` 完全一致，可作为证据提交；②存在**元数据层面改动**，四项独立证据互相印证：出现 DOS 短名、出现 2 个命名 `$DATA` 流、`Changed` 晚于 `Modified` 3 秒、`$UsnJrnl` 中 `DATA_EXTEND` 与 `$SI Changed` 落在同一秒，共同支持"该文件在 2024-06-02 14:07:22 前后被附加了隐藏数据流"；③时间戳、条目坐标（MFT 11443）、内容哈希均已记录，可复核。

第②项里 `$UsnJrnl` 这一条的权重最高，因为它由内核直接写入、内容是 FILETIME、且篡改 MFT 的人通常不会想到它。前三项都在 MFT 内部，彼此可能一起被伪造；第四项在 MFT 之外，是唯一的外部锚点。

**不能证明**：**元数据改动不等于内容被篡改**——本案内容一字未变，改的是文件属性本身；也不能仅凭这些特征断定"谁附加的、为什么附加"，那需要与访问记录或其他工件交叉。

未覆盖范围三条：①主事件日志的 4624 查询只做了计数，未按时间窗与账户逐条比对，因此"哪个账户在 14:07 执行"尚未回答；②两个命名流的内容与来源程序未做分析（`Zone.Identifier` 与自定义流的性质完全不同，本案未区分）；③`$UsnJrnl` 的覆盖窗口是 6 月 2 日当天，更早的相关操作不在本次可查范围。

第③项决定了这份结论的时效边界：USN Journal 是环形缓冲区，容量用尽即覆盖。任何基于 `$UsnJrnl` 的时间线结论都必须同时写出它的时间下界，否则半年后这份报告会被当成"该时段无异常"的依据，而那个时段的数据早已被覆盖掉了。

**误判对照**

最像的误判是看到 2 个命名 `$DATA` 流就回答"文件被篡改了"。

判据要划清两层：`$DATA` 流有匿名流与命名流之分，匿名流是文件正文，命名流才是附加数据流；而命名流的存在本身是一个文件系统事实，不说明正文被改动过。真正的内容判据是 `icat` 提取的长度与 `istat` 的 `Size` 是否一致——本案是 24576 = 24576，完全一致。

判据还应包含 `$STANDARD_INFORMATION` 与 `$FILE_NAME` 两套时间戳的差异。`Changed` 晚于 `Modified` 正是"只改元数据不改内容"的典型形态；反过来若是内容篡改，典型形态是 `Modified` 明显异常。

三条判据，按能否推翻"篡改"这个结论排列：

①匿名流长度与 `$SI` 声明的 `Size` 是否相等。`icat` 提取 24576 字节、`istat` 报 `Size: 24576`、`$DATA` 的 `AllocatedSize` 也是 24576，三处一致。内容被改写而长度恰好不变是可能的，但内容被改写后无法通过 `file` 识别为 Word 文档——本案 `file` 输出 `Microsoft Word 2007+`，说明 ZIP 容器头与内部结构完整，改动没到正文。

②`Changed` 与 `Modified` 的相对关系。NTFS 里 `Changed`（`$STANDARD_INFORMATION` 的 MFT 变更时刻）只在元数据被写时更新，`Modified` 只在数据被写时更新。`Changed` 晚于 `Modified` 且两者相差数秒，是"只动元数据"的签名；内容篡改则相反，`Modified` 会跳到操作时刻而 `Changed` 紧随其后（因为内容写也要改元数据），两者几乎同秒。

③**是否存在内容层的写入痕迹**。`$UsnJrnl` 里 14:07:22 那条是 `DATA_EXTEND` 而非 `DATA_TRUNCATION` 或 `WRITE_DATA`。前者对应"在末尾追加新流"，后者才对应"覆盖已有内容"。同一个 MFT 条目上两种原因码的区别，比任何时间戳都更能说明改了什么。

第③条是本案最硬的一条。ADS 的写入在 `$UsnJrnl` 里有专门的原因码，把它与"覆盖正文"的写入区分开只需要看一眼原因码字符串。反过来说，若只跑到 `istat` 就下结论，无论时间戳分析做得多细，都会漏掉这一层。

按错误判据走的代价：委托方拿到"内容被篡改"的结论后对文件作者展开追责，而实际上文件内容从未被改——一个把元数据改动说成内容篡改的结论，会直接指向一个错误的人。

本案的连带代价是委托方据此申请了对作者终端的全面取证。补充分析确认作者当日 14:07 在另一台机器上，命名流是他自己用脚本附加的（内容是内部审批编号，无恶意）。这条纠错花了 9 天，而它本来只需要 3 秒的 `$UsnJrnl` 查询就能避免。

<a id="section-35"></a>

### 5.2 MFT 条目定位的两个坐标：为什么 11443-128-3 少不了一环

**场景**

同一案件中，复核方按报告里的 `11443` 从镜像直接切 MFT 记录，切出来的字节全是 `00`，无法复现。将此情形单列的原因是 MFT 记录号、序列号、属性 ID 三者各管一件事，缺一个就定位不到东西。

**处置过程**

1. `fls` 输出的三段坐标各是什么：

```text
11443      MFT 记录号（entry index）→ 决定第几条记录
-128-      序列号（sequence number）→ 决定这条记录的第几代
-3         属性链中的第几个属性 → 决定取哪个属性
```

2. 手工切记录的算式与验证：

```bash
# 记录起点 = MFT 起始扇区 + 记录号 × 每条记录扇区数
#         = 526336 + 11443 × (4096/512) = 526336 + 91544 = 617880 扇区
dd if=/work/DigiForensics.dd bs=1024 skip=$((526336/512 + 11443)) count=1 of=/tmp/mft-11443.bin status=none
xxd -l 16 /tmp/mft-11443.bin
# 00000000: 4649 4c45  ...                    ← 46 49 4c 45 = "FILE" ✓
```

3. 为什么复核方切出来是全零：他们直接按字节偏移切，没有经过卷起始扇区的换算。

```text
错误算法：skip = 11443 × 8                    ← 忘了 MFT 起始扇区 526336
正确算法：skip = 526336/512 + 11443          ← 两条路径的起点差了一整个分区
```

4. 顺手验证序列号的实际作用，验证方式不是背定义，而是看它怎么变化。给同一条记录做一次"删除后重建"，序列号会递增，而记录号不变：

```text
当前：11443-128-3   （序列号 128，第 3 代）
该条目删除后被新文件复用：11443-129-1   （序列号 129）
fls 输出里若出现 11443-129-1，那是另一个文件，不是本案这份
```

这条验证顺手也回答了复核方第二个问题："报告写 11443，怎么确认现在这条还是它？"——不是靠重新跑 `fls` 看路径（路径可能一致），而是靠 `$STANDARD_INFORMATION` 里的时间戳与本次记录的 `Created` 2024-03-11 09:22:41 对齐。**序列号是代际标识，时间戳是身份标识，两个都要。**

**结论**

能证明：MFT 记录 11443 位于扇区 617880，其起始四字节为 `FILE`，定位可复现。坐标三元组与换算算式均已记录在报告附注中，复核方按此执行可得到相同结果。

**不能证明**：仅凭记录号无法区分记录的当前代与历史代——若该记录曾被复用，同一 `11443` 在不同时间指向不同内容，这需要 `$STANDARD_INFORMATION` 的时间戳辅助判断，本案未涉及记录复用。

补充说明本案的验证边界：卷序列号 `9a3f21c4` 与 MFT 记录号 11443 共同构成完整定位信息，但两者都只在**这一份镜像**内有效。复核方若用另一条采集路径重新镜像同一台机器，卷序列号会变（格式化或重装会重新分配），此时 11443 不再对应同一条记录。坐标的可复现性依赖于同一份镜像，不依赖于同一台机器——这一句必须写进报告，否则复核方第一次用自己的镜像重试就会失败一次。

未覆盖范围：未做跨镜像验证，即未用第二次独立采集的镜像核对该条目坐标是否一致。这类验证成本高（等于重采一次），通常只在委托方明确质疑采集完整性时才做。

**误判对照**

最像的误判是复核方（或分析员自己）把 `11443-128-3` 当成一个字节偏移直接切。

判据要落在 NTFS 的层次上：MFT 是一个位于卷内固定位置的数组，记录号是数组下标而不是文件偏移。要把下标变成偏移，必须先知道卷起始扇区（2048）和 `$MFT` 自身的位置（`fsstat` 报的 `MFT Cluster: 0x40000`），两者缺一不可。

另外序列号 `-128-` 的作用是确认这条记录的第几代——它不参与偏移计算，但在记录被复用时是判断"这条记录后来又变成了别的文件"的唯一依据。正确判据是坐标三元组用于定位与代际判断，偏移换算必须独立走 MFT 起始位置这条路。

三条判据，按能否解释"切出来全零"排列：

①**起点算式里有没有分区偏移**。本案 `fsstat -o 2048` 报的 `MFT Cluster: 0x40000` 是**卷内**簇号，换成绝对扇区要先过一遍分区起点：`2048 + 0x40000×4096/512 = 526336`。复核方直接从 11443×8 切，起点差了 526336×512 ≈ 257 MB，切到的位置与 MFT 毫无关系——那里通常是数据区，全零很正常。

②**每条 MFT 记录占多少扇区**。簇大小 4096 字节，一条记录正好 1 簇 = 8 扇区，所以 `skip = MFT起始扇区/512 + 11443×8` 才对。**这个乘数是 8 而不是 1**，因为 `dd` 的 `bs=1024` 与扇区数不是一回事。复核方若按 `bs=512 skip=11443×8`，起点对但步长错，切出来仍然错位。

③**切出来的前 4 字节是什么**。任何定位正确的结果都以 `46 49 4c 45`（`FILE`）开头。这个 4 字节检查花不到一秒，却能把"偏移算错"和"记录本身损坏"这两件事当场分开——本案三条记录（4、5 号）恰好就是魔数被破坏的 `BAAD`，没有这道检查很容易把它们和"算错偏移"混为一谈。

第③条是本节最实用的一条。前两条都要求事先知道正确算法，第③条只要求知道结果该长什么样。**能廉价验证的东西，就不要靠推理验证。**

按错误判据走的代价是复核方拿不到任何数据，只能选择"无法复现"——而"无法复现"在质证中的后果远比算错偏移严重。

本案复核方第一次就是这么处理的：报告里"无法复现"三个字被直接引用为质疑采集有效性的依据。补交了那 3 行算式之后，同一份镜像、同一台设备、同一份报告，重新验证一次即通过。**而这个问题的全部原因是少写了一个偏移换算步骤。**

### 5.3 反例：把长短名成对出现当成外部证据

**场景**

某次分析中，`report.docx` 同时存在 8.3 短名与长名，分析员将其列为"文件被复制或移动过"的证据，因为"外部程序创建文件时通常只生成短名"。

这条列为反例，是因为长短名成对存在是 NTFS 的常态，几乎每个文件都有，它的证明力接近于零。

**处置过程**

对照点在于普遍性：

```bash
istat -o 2048 /work/DigiForensics.dd 11443-128-3 | grep -c '\$FILE_NAME'
# 2 处：短名 + 长名

# 对照组：全卷绝大多数文件都是这个形态
fls -o 2048 -r -p /work/DigiForensics.dd | grep -c '\$FILE_NAME'
# 该卷中绝大多数活跃文件均有长名 + 8.3 短名成对的两个 $FILE_NAME 属性
```

```text
本案中真正有判别力的不是"有短名"，而是三项：
  ① 2 个命名 $DATA 流（罕见，非默认）
  ② Changed 晚于 Modified 3 秒（指向元数据操作）
  ③ 这两项的记录时间一致（2024-06-02 14:07:2x）
```

再补一条量化对照，把"普遍"这个词落到实处：

```bash
# 全卷命名 $DATA 流的分布
fls -o 2048 -r -p /work/DigiForensics.dd | wc -l          # 活跃文件总数
grep -c 'r/r.*:.*:.*:.*:.*:' /tmp/ads.txt                 # 含命名流的文件数
# 活跃文件 12840，带命名流的文件 37 个 → 占比 0.29%
```

0.29% 与 100% 的对比，比"绝大多数"这种形容有力得多。**一条判据要说服人，得给出它的基础比率**——本案 37/12840 的比例说明命名流在这台机器上是罕见事件，而长短名是 12840/12840。

**结论**

阴性发现：长短名成对这一现象在本卷中**不具备判别力**，因其在活跃文件中属普遍形态（12840 个活跃文件全部具备）。

已从证据链中剔除，不作为支持"文件被复制或移动"的依据。

未覆盖范围：本次统计基于 `fls` 列举的活跃文件，未包含已删除条目（其 `$FILE_NAME` 需从 `$LogFile` 还原）；因此"全卷普遍具备短名"这一表述严格限定在活跃文件集合内。若某个已删除文件只保留了长名，本案未做该项检查。

**误判对照**

最像的误判是把"存在 DOS 短名"当作文件被外部程序创建或移动过的迹象。

判据要落在普遍性上：**NTFS 默认就为每个文件维护 8.3 短名**——创建文件时由文件系统自动生成，与"是谁创建的"无关；即使文件从未被复制或移动，它也一定有短名。所以这项特征在正常文件与被移动文件之间**没有区分度**。

正确判据是**只保留在本卷中罕见、且与委托问题直接相关的特征**（本案是命名 `$DATA` 流的存在与时间差）。

三条判据，把"没有区分度"变成可执行的检查：

①**基础比率**。本卷 12840 个活跃文件全部有短名，比例 100%。一个在全部样本上都出现的特征，其区分度为零——**判别力的上限由它的基础比率决定**，短名的基础比率是 100%，所以它对任何假设都提供不了支持。

②**对照组是否可构造**。写这条结论时必须先跑一次全卷统计，而不是凭经验断言"NTFS 都这样"。`fls` 逐条输出后数一遍，是十几秒的工作；不跑这一遍，"普遍"就只是信念，而复核方只需举出一个反例就够推翻它。

③**同一条目上有没有别的、比率低的特征**。本案同一 MFT 条目 11443 上同时存在命名 `$DATA` 流（0.29%）与 `Changed > Modified`（罕见）。同一对象上多个罕见特征共现，比单个特征加一个常见特征要强得多——这是本案证据能立住的真正原因。

第③条是这一节的落点。剔除短名之后，证据链并没有变弱，因为它从来就不是靠短名撑着的。如果一条结论在剔除某个特征后就塌了，那说明那个特征当时就是唯一的支撑，而它本来就不该被写进去。

按错误判据走的代价：为一个普遍存在的现象配上一个看起来很有说服力的解释，报告因此多出一条"证据"，而复核方只要指出"你卷里 5 万个文件都有短名"，这条证据连同它的推理链一起失效——在取证写作里，无判别力的证据比没有证据更消耗可信度。

本案的实际代价是一次质证会上的当庭质疑。复核方只翻了 30 秒就找到了一个同样有短名、且被认定"从移动硬盘复制而来"的文件——短名在那个文件上同样存在，而它的复制事实另有证据支持。当两条结论共用一个无区分度的特征时，其中一条正确不能救另一条。

### 5.4 判据对撞：`fls` 说路径正常，`$LogFile` 说它被移动过

**场景**

一份 40 MB 的 `DigiForensics-合同终稿.docx` 从 `\\NAS-01\项目A\` 复制到 `C:\Users\Public\`。委托方要确认"该文件是否经由本机"。

`fls -p` 给出的结果很干净：路径是 `C:/Users/Public/DigiForensics-合同终稿.docx`，`$FILE_NAME` 的父目录引用指向条目 96，序列号匹配，四时间戳自洽。两个工具都报"一致"，初看没什么可查的。

但这份文件来自网络盘这件事，在 MFT 里留了痕迹，只是 `fls` 不显示。

**处置过程**

`fls` 只呈现当前有效的路径，**它不呈现移动历史**。移动的证据在 `$LogFile`——NTFS 的事务日志，记录每次元数据修改的旧值与新值：

```bash
# fls 的输出：只有当前路径，无移动痕迹
fls -p -f /case/DigiForensics.dd 11443-128-3
# r/r 11443-128-3: C:/Users/Public/DigiForensics-合同终稿.docx

# 解析 $LogFile（MFT 记录 2），过滤与该条目相关的记录
icat -o 2048 /case/DigiForensics.dd 2-0-0 > /evidence/LogFile.bin
strings -a -t x /evidence/LogFile.bin | grep -i 'NAS-01\|Public' | head
# 0002a41c  \\NAS-01\项目A\DigiForensics-合同终稿.docx
# 0002a5f0  C:\Users\Public\DigiForensics-合同终稿.docx
```

`$LogFile` 的记录是定长二进制，`icat` 取出后用 `strings` 配合十六进制偏移读出前后的成对名称；偏移值即 LSN，可与 [`Steady-State 与 LogFile 还原`](filesystem-ntfs-steady-state-logfile.md) 里的结构对照。

日志给出的是成对的前后值：

```text
LSN 0x0002A41C  UPDATE_FILE_NAME  Entry=11443  Sequence=3
  Old: \\NAS-01\项目A\DigiForensics-合同终稿.docx    (MFT 引用 0x0300_0000_0002C9F4)
  New: C:\Users\Public\DigiForensics-合同终稿.docx    (MFT 引用 0x0300_0000_00000060)
```

两条判据于是正面相撞：

```text
判据 A（fls / $FILE_NAME）→ 现路径为 C:\Users\Public\...，无移动痕迹 → 本机原生成
判据 B（$LogFile）        → 存在 Old → New 的改名记录            → 曾位于 NAS 路径
```

判据 B 对，理由在于 `$FILE_NAME` 的性质：它保存的是**当前有效的那个名字**，改名即覆写同一条属性，旧值不会留在 MFT 里。而 `$LogFile` 保存的是**变更前后的成对值**，移动必然留下旧名。

差别不在谁更准，而在**两者回答的不是同一个问题**：`$FILE_NAME` 回答"现在叫什么"，`$LogFile` 回答"改过什么"。只跑 `fls` 相当于只问了前半个。

补一层确认，避免凭单条记录下结论：

```bash
strings -a -t x /evidence/LogFile.bin | grep -c 'DigiForensics-合同终稿'
# 6 处名称 = 3 次改名 × (旧值+新值)：NAS → 本地临时名 → Public 终稿
```

**结论**

能证明：`DigiForensics-合同终稿.docx`（MFT 条目 11443，序列号 3）在本机发生过两次 `$FILE_NAME` 变更，最终路径为 `C:/Users/Public/`，变更前位于 `\\NAS-01\项目A\`。该文件经由本机成立。

不能证明：文件内容在复制过程中未被改动。`$LogFile` 记录的是元数据事务，`$DATA` 流的数据写入产生另一类记录（`WRITE_DATA`），需单独比对哈希才能定性。

**误判对照**

最像的误判是把"`fls` 与 `istat` 输出全部自洽"读成"该文件未被移动过"。

判据要落在**属性可变性**上：`$FILE_NAME` 是可变属性，改名即覆写，旧名不留存；`fls` 读的是 MFT 当前状态，`$FILE_NAME` 与 `$DATA` 一一对应、时间戳自洽，只能证明**当前内部一致**，而内部一致是文件系统的日常维护结果，不是"没被动过"的证据。

第二种误判是把 `$LogFile` 记录当成"有人在刻意清理痕迹"。判据在于 journaling 是 **NTFS 的默认功能**，为崩溃一致性而设，不是为记录用户操作。本卷 `$LogFile` 大小 38 MB、覆盖正常，恰恰说明它处在系统默认配置下；只有日志被清空或大小异常偏小时，才构成可疑信号。

按错误判据走的代价是双向的。只看 `fls` 会把一份从共享盘拷来的文件误判为本机原始文件，可能给一个实际经手了他人文件的操作员洗清嫌疑；而把正常日志当"人为痕迹"，则会让一条看似有力的证据链整条作废——前一种错判改变结论，后一种只是浪费力气，但后者在实务中更常发生。

### 5.5 阴性结果：8 万个条目里只有 2 个 `BAAD`，但这不构成否定结论

**场景**

委托方的问题是"该分区是否存在批量删除"。分析员逐条校验 MFT 记录，跑完整卷，只找到 2 条 `BAAD` 记录，且都在 `$MFT` 自身附近，指向空闲条目。

初步结论写成"未发现批量删除痕迹"。

**处置过程**

这 2 条 `BAAD` 的分布先看清楚：

```bash
# 逐条校验全卷 MFT 记录头：先定位 $MFT 起点，再按 1 簇一步长扫魔数
dd if=/case/DigiForensics.dd bs=1024 skip=$((526336/512)) count=1 status=none | xxd -l 4
# 4649 4c45                                    ← FILE，起点确认
# 扫描输出（魔数 → 计数）：
# FILE      41877
# BAAD          2    ← 记录号 4、5 附近（$MFT 与 $MFTMirr 区）
# 0 填充    38431    ← 近半数
# INDX         2
```

关键在 `0 填充 = 38431` 这个数——**近半数条目从未使用或已释放**。删除文件的标准动作是把条目内容清成 `0` 填充，而不是留下 `BAAD`：

```text
BAAD   = 魔数被破坏、Fixup 校验失败 → 写入中断或被覆写
0 填充  = 条目被正常释放（删除文件的标准动作）→ 条目内读不到任何文件名
```

判据要对准正确的位置：

```bash
# 已删除条目要从 $LogFile 里找，那里才有旧文件名
icat -o 2048 /case/DigiForensics.dd 2-0-0 > /evidence/LogFile.bin
strings -a -t x /evidence/LogFile.bin | grep -c 'DigiForensics'
# 1843 条，LSN 集中在 2024-06-02 09:14–09:51

strings -a -t x /evidence/LogFile.bin | grep -i 'DigiForensics' | head
```

结论要改写：`BAAD` 少说明**没有大规模覆写式删除**，但删除本身大量发生过——1843 条 `DELETE_ENTRY` 集中在 37 分钟内，这才是删除动作真正的落点。

**结论**

阳性发现：`DigiForensics.dd` 中 80312 个 MFT 条目仅 2 个 `BAAD`，无批量覆写式删除迹象。

阳性发现：`$LogFile` 中检出 1843 条 `DELETE_ENTRY`，LSN 区间 `0x00018F20`–`0x0001C4A8`，对应 2024-06-02 09:14–09:51 的 37 分钟窗口。这是删除动作的实际证据。

阴性发现：**无法就该卷更早时间是否发生过批量删除给出判断**。`$LogFile` 容量覆盖 38 MB，本次删除恰在覆盖范围内；超出覆盖范围的历史删除不留任何记录。这是日志容量决定的，不是本次分析漏掉的。

**误判对照**

最像的误判是把"只有 2 个 `BAAD`"读成"没有批量删除"。

判据要落在**两种释放路径的字节特征**上：删除文件是把条目清成 `0` 填充并递增序列号，`$MFT` 里不保留任何文件名痕迹；`BAAD` 指魔数被破坏、Fixup 校验不过的记录，指向写入中断或覆写。产生条件不同，把 `BAAD` 计数当删除计数，等于在一种残留里找另一种。

第二种误判是拿 `$LogFile` 的记录数当"被删文件数"。判据在于 `DELETE_ENTRY` 的粒度是**事务**而非文件：一次删除操作可能包含多条记录，含多个 ADS 的文件也会产生多条。1843 是事务计数，不是文件计数，报告里必须写清这一层。

按错误判据走的代价是漏掉整个删除事件。若停在"无 `BAAD` = 无删除"，那 37 分钟内被删掉的全部文件都会从结论里消失，窗口内的连带影响（索引未重建、`$UsnJrnl` 有对应条目）根本不会被提到。阴性结论的危险不在于它错得离谱，而在于它听起来足够谨慎、足够专业，于是一直没人去复查。

### 前置基础：先把工具和卷层跑通

- [只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md) —— **本篇的第一条前提**。`fls` / `istat` / `icat` 的通用用法在那儿，本篇讲的是输出字段的解读。`-o` 参数给错则后面全错
- [文件系统取证总览](filesystem-ntfs-filesystem-forensics-overview.md) —— 判定这是 NTFS 的那一步。**`NTFS    ` 签名在卷起始偏移 3**，不是磁盘起始
- [时间戳换算](../../fundamentals/fundamentals-concepts/fundamentals-concepts-timestamps-and-timezones.md) —— `$STANDARD_INFORMATION` 里那四个 FILETIME 的换算。FILETIME 是 1601 年起、100 纳秒，读错纪元的误差是天文数字

<a id="section-41"></a>

### 同层深入：MFT 之外的 NTFS 能力

本篇 2.3 那句"删掉文件后 MFT 里的属性描述仍在，只是数据簇被标记为空闲"，后面那几篇就是在这个基础上继续挖：

- [NTFS 数据流与隐藏数据](filesystem-ntfs-ntfs-alternate-data-streams.md) —— ADS（命名流）、`$I30` 索引目录、slack space、未分配空间。2.3 提到的 `$ATTRIBUTE_LIST` 藏匿手法，那里讲怎么检出
- [Steady-State 与 LogFile 还原](filesystem-ntfs-steady-state-logfile.md) —— 本篇第 2 条 MFT 记录就是 `$LogFile`。**MFT 告诉你现状，日志告诉你过程**，这是 NTFS 独有的两种能力分工
- [EFS 文件系统加密取证](../../crypto/crypto-volume/crypto-volume-efs.md) —— 2.3 那串标志里的 `0x4000` 就是 EFS。它与 BitLocker 不同，是文件级的，所以同一卷上可能有明文也有密文
- [文件头与文件签名](filesystem-ntfs-file-headers-and-signatures.md) —— `icat` 提取出内容之后，判定它实际是什么格式。**`$DATA` 说它多大，签名说它是什么**

<a id="section-42"></a>

### 交叉验证：MFT 内部的一致性不够

- [反取证手法与时间戳篡改检测](../../fundamentals/fundamentals-concepts/fundamentals-concepts-anti-forensics-and-timestamp-tampering.md) —— **本篇最重要的一条链接**。那篇的核心结论是"MFT 内部的一致性检查最多只能把文件判为存疑，要坐实篡改必须引入 MFT 之外的独立时钟"。本篇读懂了 MFT，就具备了理解那个结论的前提
- [UsnJrnl 与文件操作时间线](../../computer/computer-execution/computer-execution-usn-journal-timeline.md) —— **内核写入的日志，篡改者改不到**。它补齐 MFT 缺失的时间精度与原因码，那篇 3.3 是本篇结论的自然延伸
- [Prefetch 深度解析](../../computer/computer-execution/computer-execution-prefetch.md) 与 [ShimCache 与 Amcache](../../computer/computer-execution/computer-execution-shimcache-amcache.md) —— 同一类思路的另外两个独立时钟来源
- `$MFTMirr` 对照 —— 它是 `$MFT` 前 4 条记录的备份，可以拿来做逐字节比对。2.1 提到它的存在，本篇未展开比对方法；这个动作在发现 `$MFT` 被篡改时很有用，属于动手类技巧

<a id="section-43"></a>

### 判据与反例：MFT 特有的误判

- 日志语义对照 —— `$LogFile` 与 ext4 journal 都是事务日志，但覆盖范围不同。本篇讲 NTFS 侧的 MFT，日志的通用机制（REDOP / UNDO / 事务）在 [Steady-State 与 LogFile 还原](filesystem-ntfs-steady-state-logfile.md) 的 2.3
- 重解析点滥用 —— `IOXSLD` / `APPEXEC_LINK` 可指向任意内容，挂载点目录可"接"到别的卷。这类手法会让 `fls` 输出的路径与实际数据位置脱节，本篇 2.5 讲 `$FILE_NAME` 标志时那一项（`0x34` 重解析点值）就是它的落点
- [取证技能树](../../fundamentals/fundamentals-process/fundamentals-process-forensics-learning-path.md) —— 本篇对应 L1 底层"文件系统"模块。2.2 那句"L1 的标志是能手绘 MFT 记录结构"，本篇就是那份图的来源
- [术语查表](https://www.digiforensics.cn/wiki/digiforensics-glossary)—— `MFT` / `Fixup` / `USA` / `Run List` / `Attribute` 的定义。`Attribute` 在 NTFS 里是 MFT 记录内的组成单元，在 Windows API 里是文件系统的另一套概念，术语表里两者的区分值得确认。

## 七、命令速查

```bash
# ===== 环境 =====
sudo apt install sleuthkit xxd file
# 下列命令中 -o 2048 为 NTFS 分区起始扇区，替换为 mmls 实际值

# ===== 定位 MFT =====
fsstat -o 2048 /work/DigiForensics.dd | grep -iE 'cluster size|mft cluster|serial'
# MFT 字节偏移 = MFT Cluster × Cluster Size（相对卷起始）

# ===== 原始 MFT 记录检查（观察魔数与 USA）=====
# MFT 起始扇区 526336 → 换算为 1024 块 = 1028
dd if=/work/DigiForensics.dd bs=1024 skip=$((526336/512 + 11443)) count=1 of=/tmp/mft.bin status=none
xxd -l 128 /tmp/mft.bin     # 46 49 4C 45 = "FILE"；30 00 03 00 = USA offset=0x30, count=3

# ===== 元数据导出 =====
fls -o 2048 -r -p /work/DigiForensics.dd > /evidence/fls-all.txt
grep -i deleted /evidence/fls-all.txt                # 已删除项
fls -o 2048 -r -p /work/DigiForensics.dd | grep -E '\$[A-Za-z]'   # 系统元数据文件

# ===== 逐文件元数据（核心）=====
istat -o 2048 /work/DigiForensics.dd 11443-128-3      # 四个时间戳 + 属性列表 + 簇链
# Created/Modified/Accessed/Changed 横向对比：
#   Modified 变而 Changed 不变 → 内容被改
#   Changed  变而 Modified 不变 → 元数据被改（重命名/权限/ADS）

# ===== 提取与验证 =====
icat -o 2048 /work/DigiForensics.dd 11443-128-3 > /evidence/report.docx
file /evidence/report.docx                            # 魔数是否与文件名相符
stat -c '%s' /evidence/report.docx                    # 长度应等于 istat 的 Size
sha256sum /evidence/report.docx

# ===== 关键系统文件 =====
icat -o 2048 /work/DigiForensics.dd 2-0-0   > /evidence/LogFile.bin      # MFT 记录 2
icat -o 2048 /work/DigiForensics.dd 1-0-0   > /evidence/MFTMirr.bin      # MFT 记录 1
icat -o 2048 /work/DigiForensics.dd 24-0-0  > /evidence/Secure.bin       # 安全描述符
# $UsnJrnl：先 fls 查 inode（名称含 $UsnJrnl%3A$J），再 icat 提取
```
