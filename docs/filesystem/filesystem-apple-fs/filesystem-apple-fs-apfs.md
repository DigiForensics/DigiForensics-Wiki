# APFS 容器与快照

<a id="section-1"></a>

## 一、概述

APFS 分析需要区分容器与卷，并结合 B-tree、快照和写时复制机制定位文件。容器布局、快照状态及加密配置会影响可提取的数据范围。

| 新问题 | 取证后果 |
|---|---|
| 一个分区里挤了多个卷（系统卷、数据卷、恢复卷、预启动、VM 卷） | 拿分区偏移当卷偏移解析，结果全错 |
| 元数据只有一棵 B-tree | 定位一个文件要理解 B-tree 节点结构，**"查表"思路失效** |
| 原生快照 + 写时复制 | 删除的文件可能**根本没被删**，只是被标记为"不属于当前快照" |

第三条是核心，也是接手 APFS 检材时最先要建立的认识。两者都靠元数据的"账面"与数据块的"实存"分离来保留已删数据，但保留机制不同。NTFS 删除时数据簇进入空闲位图，**元数据（`$MFT` 记录）本身同样被标记删除**，只能靠 `$LogFile` 回放或未分配空间扫描捞回，且常失败；APFS 的"删除"则只是在元数据 B-tree 里移除一个目录项指针，配合多个 checkpoint 同时保留，**可以按删除前的 xid 重新走一遍树把状态读出来**，无需依赖回放技巧。数据块方面两者在未被后续写入覆盖前都不会被抹除。

换个角度说：APFS 把"看到删除前状态"从**需要技巧才能做到**（NTFS 的 `$LogFile` 回放）变成了**按 checkpoint 直接可读**——这才是 APFS 在删除恢复上的实质优势。不过"可逆"要留个前提：块没被后续写入冲掉才算。

FileVault 是否开启应按设备逐一核实。在配备 Apple 芯片或 T2 芯片的 Mac 上，底层卷加密与 FileVault 的用户凭据保护属于不同层次；不能从 macOS 版本或 APFS 格式推断 FileVault 状态。参见 [Apple：FileVault 卷加密](https://support.apple.com/en-gb/guide/security/sec4c6dc1b6e/web)。

这一层在**分析环节的格式解析阶段**，位置是"卷层之后、目录树之前"。上游是[文件系统取证总览](../filesystem-ntfs/filesystem-ntfs-filesystem-forensics-overview.md)的第 3 步"逐卷判定文件系统类型"——如果那一步把 APFS 容器当成一个卷，一开始就走错了。

先后关系不是形式问题。2.1 那句话是全篇的判断原则：APFS 上唯一稳定的"外部可见面"是容器超级块和卷列表，所以第一步永远是**读容器，而不是读卷**。第三章步骤 1 标题里"不是卷"三个字，就是这个原则的操作化。

下游三件事：快照枚举结果决定你能看到几个时间点的系统状态（步骤 3）；FileVault 密钥处理决定内容能不能读（步骤 4）；提取与验证决定结论能不能写（步骤 5）。macOS 侧的工件分析在别处成篇——[FSEvents 与时间机器](../../computer/computer-log-persistence/computer-log-persistence-fsevents.md) 与 [Spotlight 索引与元数据](../../computer/computer-plist-spotlight/computer-plist-spotlight-spotlight.md) 都建立在这一层建立的空间与时间坐标之上。

落到具体证据上：

- **`NXSB` 容器超级块** —— 位于**分区 + 32** 字节处，签名 `4e58 5342`。**不受 FileVault 影响**——否则系统无法挂载。块大小字段在紧邻位置（第五章案例里读到 4096）
- **卷列表** —— 在 `NXSB` 内部，同样不受加密影响。第五章案例里读到 6 个卷：`Macintosh HD`（oid=2, block_addr=40）、`Macintosh HD - Data`（oid=3, block_addr=80）、`Preboot`、`VM` 等
- **`APSB` 卷超级块** —— 位于各卷起点，签名 `4150 5342`。**部分字段可见**（如最后挂载/创建时间），其余加密
- B-tree 节点 / 文件名 / 时间戳 / 文件内容 —— **全部加密**。这是 2.5 那张表的分界线所在
- **checkpoint 描述符** —— 卷内，**加密**。它维护"哪个块属于哪个事务状态"，理解它才能正确判断快照
- **系统自动本地快照** —— 第五章案例在无密钥情况下成功枚举出 3 个（`xid=4/9/15`），最新一个 2024-08-21，**距设备扣押仅 8 天**
- **`VM` 卷** —— 交换内容所在。这是一个独立的卷，不在 `Macintosh HD - Data` 里，这也是"容器 ≠ 卷"的直接体现
- **`DigiForensics.dd`** —— raw APFS 容器镜像。**它是容器镜像，不是某个卷的镜像**，第五章案例里容器分区起始扇区是 775920，所有偏移都要加上这个基址

走完这一层能判断的是这些：为什么必须先读容器再读卷、无密钥时 APFS 上哪些问题仍然能可靠回答，以及——同样重要的——**哪些表述在无密钥时绝对不能写**。

没有密钥，**仍然能可靠地**回答："这是不是 APFS 卷、容器里有几个卷、每卷多少块、卷的最后挂载时间"。**回答不了**："有哪些文件、文件名是什么、什么时候改的、内容是什么"。所以报告里必须把**结构性结论**（无密钥也成立）与**内容性结论**（需密钥）分开写。2.5 那句"不要犯的错"值得单独强调：把"读不出文件名"写成"卷内无数据"或"已被彻底擦除"，这两种表述在法律和事实层面都站不住。

有几件事不归这一层管：**没有密钥时怎么拿到密钥**，FileVault 的密钥层级与恢复密钥途径是加密篇的领域；**Time Machine 备份集怎么解析**，增量备份链是独立的一套结构；**macOS 的应用层工件**，统一日志、LaunchAgents、Keychain 那些在 macOS 板块各篇；**Btrfs / ZFS 的快照机制**，同为 CoW 但容器结构与快照语义不同，不能直接套用这里的判据。

往下读之前需要三样前置：**GPT 分区结构**（全程在"分区 + 偏移"上计算）、**十六进制分析**（`NXSB` / `APSB` 的字节判定靠这个）、以及**只读挂载规范**（为什么不能直接 `mount` 一个 APFS 容器去读——见[只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md)）。

还有一个心理前提要提前打好：你需要接受"这一层大部分场景下你能做的事比想象中少"。第五章那个案例里，无密钥能给出的最强结构性结论是"3 个快照、最新一个距扣押 8 天"。委托方真正要的"某文件是否存在、最后修改时间"，回答不了。先接受这个上限，再看这一层能给你什么。

## 二、核心原理

<a id="section-3"></a>

### 2.1 两层结构：容器（Container）不等于卷（Volume）

APFS 上最容易搞错的一点，是把 `NXSB` 和 `APSB` 当成同一层的两个名字。它们不是——**混淆会导致偏移全错**。

```
GPT 分区 (通常是分区 2)
┌──────────────────────────────────────────────────────┐
│  APFS 容器 (Container)  ← 魔数 NXSB，偏移 32 (0x20)  │
│  ┌────────────────────────────────────────────────┐  │
│  │ 卷 0: Macintosh HD       ← 魔数 APSB（卷首）   │  │
│  │ 卷 1: Macintosh HD - Data                      │  │
│  │ 卷 2: Preboot                                   │  │
│  │ 卷 3: Recovery                                  │  │
│  │ 卷 4: VM（交换，m 独立）                        │  │
│  │ 卷 5: Preboot Recovery / VM 各自独立            │  │
│  └────────────────────────────────────────────────┘  │
│  物理块池：容器内所有卷共享同一批块，块被统一分配    │
└──────────────────────────────────────────────────────┘
```

| 概念 | 魔数 | 位置 | 作用 |
|---|---|---|---|
| **容器超级块 `NXSB`** | `NXSB` | **分区起始 + 32（0x20）** | 定义**整个物理块池**的大小、块大小、**卷的个数与各卷 oid/xid** |
| **卷超级块 `APSB`** | `APSB` | **每个卷自己的起点** | 定义该卷的**文件系统参数**（inode 数、块数、根目录 xid、checkpoint 描述符） |

破案时先问一个具体问题：**这个卷有多少块？** 报告里"Macintosh HD - Data 占 3.2 TB"这句话的数据来自 `NXSB` 的 `nx_block_count`——它描述的是整个容器能用的块数，而每个 `APSB` 里的 `apfs_phys_obj_count` 是这个卷自己占的块数。两者不在一个量级上，因为共享池里还塞着别的卷。

答完这个才轮到偏移。所有偏移换算的基准是块大小，而这个字段**写在 `NXSB` 里**（案例读到 4096），不在 `APSB` 里。

```bash
# ① 确认容器在（NXSB 在偏移 32，不是 0）
xxd -s 32 -l 4 /work/DigiForensics.dd
# 期望：4e 58 53 42 = "NXSB"

# ② 关键：APSB 绝对不在分区起始，它在卷的物理块边界上
#    卷起点必须从 NXSB 里的 volno[].block_addr 读取，不能猜
xxd -l 4096 -s $(( 40 * 4096 )) /work/DigiForensics.dd | head -3
# 若在某个 4096 倍数偏移看到 41 50 53 42 = "APSB"，该偏移即卷起点
```

> **最常见的错误**：默认"分区起始就是卷起始"，去分区起始找 `APSB`，什么都没找到就判定"未格式化"。**实际差值可能很大**（系统卷之后还有预启动卷、恢复卷等）。

<a id="section-4"></a>

### 2.2 元数据是一棵 B-tree（不是一张表）

NTFS 有 `$MFT`、ext4 有 inode 表，APFS 两者都没有——所有文件、目录、符号链接的元数据统一存进一棵平衡 B-tree 的叶节点里（因此常被称为 **octree**，因为 8 个指针字段）。

```
B-tree 根节点
┌─────────┬─────────┬─────────┬─────────┬─────────┬─────────┬─────────┬─────────┐
│ p0      │ p1      │ p2      │ p3      │ p4      │ p5      │ p6      │ p7      │
└────┬────┴────┬────┴────┬────┴────┬────┴─────────┴─────────┴─────────┴─────────┘
     │         │         │         │            （深度 > 0 = 索引节点，继续下钻）
     ▼         ▼         ▼         ▼
  ┌───────┐ ┌───────┐ ┌───────┐ ┌───────┐
  │ 内部节点│ │ ...   │ │ 内部节点│ │  ...   │      深度 0 = 叶节点
  │ (summary)│      │ │      │ │      │
  └───────┘ └───────┘ └───────┘ └───────┘
                    │
                    ▼  （只有叶节点存真实记录）
  ┌──────────────────────────────────────────────────┐
  │ oid │ 记录类型 → 文件名 | 父 oid | 时间戳 | extents… │  ← 每条 kvo 记录
  └──────────────────────────────────────────────────┘
```

| 关键设计 | 说明 | 取证影响 |
|---|---|---|
| **统一 key-value-object** | 任何对象都是「键值对列表」，没有"文件类型"之分 | 解析器要按 `type` 字段区分，**不能靠位置猜** |
| **叶节点才存完整记录** | 内部节点只存摘要（key 范围 + 子指针） | **只读第一层会漏掉绝大部分文件** |
| **可变长记录 + 校验和** | 记录内有 `crc32c` 校验 | 校验失败 = 该区被改写或损坏，是重要的取证信号 |
| **CoW：节点不可原地修改** | 改一个字节 → 复制整条路径到新块 | **旧块内容保留在原处**，直到被后续写入覆盖 |

**CoW 是本篇最重要的取证机制**。先看它救回来的东西：改一个字节，整条路径复制到新块，**旧块内容原样留在原处**，直到被后续写入覆盖。所以"某个文件被改过"的老版本，可能完整躺在未被覆盖的旧块里。这是 APFS 相对 NTFS 的一个独特优势。

但要注意反向陷阱。**同一份内容可能在盘上存在多个物理副本**——CoW 的副产品。直接按签名在原始镜像上做文件雕刻（见 [10](../filesystem-unix/filesystem-unix-file-carving-and-signature-recovery.md)）会**重复命中同一内容 N 次**。做 carving 时必须做**哈希去重**——同一个特性既是取证优势，也是噪声来源。

<a id="section-5"></a>

### 2.3 checkpoint：维护"哪个块属于哪个事务状态"

APFS 没有 NTFS 那种"可回放的变更日志"。它的做法是**周期性写一个 checkpoint**，记录当前整个文件系统的**映射状态**：

| checkpoint 字段 | 作用 | 取证价值 |
|---|---|---|
| `checkpoint descriptor` | B-tree 叶节点指针数组 | **指向当前最新的叶节点集合** |
| `mapped_block_count` | 已映射块总数 | 与 `apfs_phys_obj_count` 比对可发现**悬挂块** |
| `ckp_xid` | checkpoint 事务号 | **单调递增的版本标识** |
| `next_ckp_id` | 下一个 checkpoint 的位置 | 顺此可串起所有 checkpoint，构成时间序列 |
| `ckp_maybe_zap` | 标记"此 checkpoint 之后数据需谨慎" | 非 0 = 系统关机时此 checkpoint 正在使用，是未完成写入的信号 |

**取证逻辑**：`next_ckp_id` 是一条**单向链表**，从最新 checkpoint 往回走，能枚举出设备历史上所有 checkpoint 及其事务号。

这在概念上比 NTFS 的日志更直接。**不需要回放，直接挑一个时刻的快照来读。**

而且同时保留多个 checkpoint 是 APFS 的常态。这意味着你可以读取"删除发生之前"的 checkpoint 状态——在 NTFS 上这需要 `$LogFile` 回放这类技巧，且常常失败；APFS 是按 checkpoint 直接可读，这是机制上的差别，不是"NTFS 完全做不到"。

<a id="section-6"></a>

### 2.4 快照的取证用途

快照（Snapshot）记录的是某个 xid（事务号）时刻的卷状态。它是**元数据层面的时间定格**，与备份文件不同——所有文件的元数据仍在 B-tree 里，只是**树被组织成了"当前状态"和"快照状态"两个视角**。

| 特性 | 说明 |
|---|---|
| **CoW 支撑** | 快照创建后，被快照覆盖的块**不原地写**，而是写到新块 → **旧数据存活** |
| **元数据共享** | 未修改的文件，快照与当前版本**共用同一份数据块**，几乎不占空间 |
| **系统自动创建** | macOS 定期（通常每日）自动创建本地快照，**不限于 Time Machine** |
| **可被用户创建** | 手动快照、第三方工具快照 |
| **Time Machine 快照** | **共享同一套 APFS 快照机制**，只是由 TM 服务触发 |

**取证的三个用途**：

**（1）删除前状态可直接读取**。这是最强的一条。

NTFS 上"恢复删除文件"依赖 `$LogFile` 回放或未分配空间扫描，复杂且常失败；APFS 上则是**换一个 xid 重新走一遍 B-tree**。文件可能好好地躺在那里：

```bash
# 列出容器内所有快照及其 xid
apfsutil /work/DigiForensics.dd
```

（2）Time Machine 备份与本地快照同构。因为 Time Machine 用的就是 APFS 快照，所以："最后一次自动备份是什么时候"这个问题，在 APFS 上可以通过枚举快照创建时间直接回答——不需要去解析 Time Machine 的 `.tmbackup` 元数据库。

**（3）跨卷观察同一个动作**。一个用户动作（比如删除文件）会同时改动多个卷的元数据。快照让你能**对比同一时刻不同卷的状态**，还原"这个操作牵涉哪些卷"。

> **关键提醒**：快照保护的是**已被快照覆盖的块不被原地改写**，但**不阻止新数据写入这些块**。如果设备在删除后继续被大量使用（装软件、下载文件、跑系统更新），旧块会被**后来的写入覆盖**，快照对应的物理内容随之消失。**快照的价值随"删除后使用时长"快速衰减**——这是评估检材时必须问的问题（关机距今多久）。

<a id="section-7"></a>

### 2.5 加密边界：哪些结构在加密层之外

| 结构 | 偏移 | 是否受 FileVault 影响 |
|---|---|---|
| `NXSB` 容器超级块 | 分区 + 32 | ❌ **不受影响**（否则无法挂载） |
| 卷列表 / 各卷 oid、xid | `NXSB` 内部 | ❌ **不受影响** |
| `APSB` 卷超级块头部 | 各卷起点 | ⚠️ 部分字段可见 |
| **B-tree 节点 / 文件名 / 时间戳** | 卷内 | ✅ **全部加密** |
| **文件内容** | 卷内 | ✅ **全部加密** |
| checkpoint 描述符 | 卷内 | ✅ 加密 |

**这个边界是 APFS 取证最实用的知识**。

没有密钥时，你**仍然能可靠地**回答："这是不是一个 APFS 卷？容器里有几个卷？每个卷多少块？卷的最后一次挂载/创建时间（部分字段在 APSB 头部）？"

回答不了的是："有哪些文件、文件名是什么、什么时候改的、内容是什么。"

因此报告里必须明确区分："结构性结论"（无密钥也成立）与"内容性结论"（需密钥）。

**不要犯的错**：把"读不出文件名"写成"卷内无数据"或"已被彻底擦除"。这两种表述在法律和事实层面都站不住。

## 三、操作步骤

<a id="section-9"></a>

### 3.1 第 1 步：定位容器（不是卷）

```bash
# ① 确认镜像类型与分区布局
mmls /work/DigiForensics.dd
# Slot 01 Start: 0000002048 (0x800)
# Slot 02 Start: 0000785920 (0xF0000)  ← APFS 容器所在

# ② 在容器分区起始 + 32 找 NXSB（关键偏移，不是 0）
xxd -s $((775920*512 + 32)) -l 32 /work/DigiForensics.dd
# 000f7fa0: 4e58 5342 0000 0001 0000 0010 3bf1 3f00  NXSB............><
#           ↑魔数      ↑版本        ↑块大小 4096

# ③ TSK 侧独立判定（fsstat 对 APFS 支持有限，但能确认卷起点）
fsstat -o 775920 /work/DigiForensics.dd | head -20
```

<a id="section-10"></a>

### 3.2 第 2 步：读容器与卷列表

```bash
# apfsutil 是 apfs-fuse 项目附带的容器信息工具
# -o 指定分区内偏移（字节），使其可直接作用于分区镜像
apfsutil -o $((775920*512)) /work/DigiForensics.dd
```

输出需重点核对：

| 字段 | 含义 | 取证价值 |
|---|---|---|
| `Block size` | 物理块大小（常见 4096） | 所有偏移换算的基准，**必须实测** |
| `NXSB block count` | 容器总块数 | 算容器总容量 |
| `Volume 0 (oid=1, ...)` | 各卷 oid / xid / 名称 | **卷标识，报告引用时必须写全** |
| 各卷 `Block count` | 该卷占块数 | 与物理占用交叉验证 |

**手工定位各卷起点**：把上面的卷 `block_addr` 换成字节偏移，用 `xxd` 找 `APSB` 验证。

```bash
# 逐个候选块扫描 APSB（块大小按实测值取 4096）
for blk in 40 80 120; do
  sig=$(dd if=/work/DigiForensics.dd bs=4096 skip=$blk count=1 status=none | xxd -p -l 4)
  [ "$sig" = "41505342" ] && echo "APSB found at block $blk (offset $((blk*4096)))"
done
# 41505342 = "APSB"
```

<a id="section-11"></a>

### 3.3 第 3 步：列出并访问快照

```bash
# 列出容器内全部快照（xid 是挂载快照的标识）
apfsutil -o $((775920*512)) /work/DigiForensics.dd | grep -iA5 'snapshot'

# 挂载指定卷的指定快照（只读 FUSE）
mkdir -p /mnt/apfs-cur /mnt/apfs-snap

# 挂当前状态（卷 1 = 数据卷）
apfs-fuse -o vol=1,uid=0,gid=0,ro /dev/loop0 /mnt/apfs-cur

# 挂快照（snap=<xid>，xid 从上一步得到）
apfs-fuse -o vol=1,snap=4 /dev/loop0 /mnt/apfs-snap

# 卸载（务必显式卸载，不要直接关机或拔线）
fusermount -u /mnt/apfs-snap && fusermount -u /mnt/apfs-cur
```

> ⚠️ **`ro` 不是可选项。** FUSE 挂载一旦以读写方式打开，驱动或系统可能对卷做**日志/checkpoint 相关写入**，污染证据。**挂载前应对工作副本做哈希基线，挂载后再比一次**：

```bash
sha256sum /work/DigiForensics-work.dd > /evidence/baseline.sha256   # 挂载前
# ……挂载、读取、卸载……
sha256sum -c /evidence/baseline.sha256                                # 挂载后
# 若提示 FAILED → 镜像被改写，处置流程存在缺陷
```

<a id="section-12"></a>

### 3.4 第 4 步：加密卷的密钥处理

```bash
# ① 交互式输入密码（apfs-fuse 会提示）
apfs-fuse -o vol=1 /dev/loop0 /mnt/apfs-cur
# Passphrase: ********

# ② 用恢复密钥（Personal Recovery Key，XXX-XXX-... 形式）
apfs-fuse -r "XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX" -o vol=1 /dev/loop0 /mnt/apfs-cur

# ③ 或用 pass= 挂载选项（不推荐：密码会进 shell 历史与进程列表）
#    生产环境务必用交互式或 -r，且 -r 的值同样敏感
```

**密钥材料的处置规范**：

| 动作 | 要求 |
|---|---|
| 获取途径 | 委托人当面提供、备份恢复密钥、或依法提取 |
| 存放 | 独立加密介质，**不得写入案件目录** |
| 记录 | 在证据链中登记"何时、何人、以何方式获得密钥"，**但不记录密钥本身** |
| 导出 | 例外情况才导出，导出件命名 `DigiForensics-masterkey.bin` 并单独封存 |
| 报告 | **只写"已使用合法取得的密钥解密"，不写密钥字符串** |

> **`-r` 传的是恢复密钥，不是任意密码**（`-o pass=` 才是传密码）。两者都能解密，但恢复密钥的获取路径（Apple ID 账户）通常更明确，**在证据链上更容易说明来源**。

<a id="section-13"></a>

### 3.5 第 5 步：提取与验证

```bash
# 导出目标目录（只读挂载后的常规拷贝，保留路径结构）
cp -rp --preserve=timestamps /mnt/apfs-cur/Users/suspect/Documents /evidence/Documents

# 验证：逐文件哈希 + 与文件系统元数据交叉核对
find /evidence/Documents -type f -exec sha256sum {} \; > /evidence/carved-hashes.txt
wc -l /evidence/carved-hashes.txt

# 时间戳核对（APFS 的 birthtime/modified 可直接用 stat 读）
stat /evidence/Documents/report.pdf
# Birth: 2024-05-11 09:33:02   ← btime
# Access: 2024-06-20 22:14:51
# Modify: 2024-06-20 22:10:03
```

**关键验证原则**：从 APFS 读出的时间戳**只证明"文件系统记录的修改时间"**，不证明"内容何时产生"。**内容产生时间要用内容内嵌时间**（如 PDF 的 CreationDate、JPEG 的 EXIF DateTimeOriginal）交叉验证。两者不一致本身就是有价值的发现。

## 四、常见陷阱

本章按「格式与结构识别 → 结构解析 → 取证语义 → 误报来源与结论表述」归组，每条给出：现象、为什么会误判、误判代价、正确做法。
★ 标记表示该操作会导致原始检材永久灭失或不可逆改变，执行前必须停下来确认。

<a id="section-15"></a>

### 4.1 格式与结构识别

<a id="section-16"></a>

#### 陷阱 1：★ 设备通电状态下做物理镜像

**现象**：MacBook 处于登录或开机状态，直接用 `dd`/`dcfldd` 读整盘，耗时数小时，得到的镜像在解析时出现元数据不一致。

**原因**：**APFS 的元数据在运行时持续变动**——系统会自动创建快照、运行垃圾回收、维护 checkpoint 与块映射。读盘是一个持续数小时的过程，期间映射表被改写了无数次，而镜像里的元数据是这些状态的混合采样：快照链表可能自相矛盾，块映射可能指向尚未写完的块，checkpoint 字段可能处于 `ckp_maybe_zap` 标记的中间态。这与 NTFS 上"元数据表相对静态"的情况不同——APFS 上"读到一致快照"这件事本身需要设备处于静止状态。

**影响**：一是**解析结果不可靠**——文件列表、块映射都可能是错的，而错误无法从镜像内部检测出来。

二是**物理镜像法在这个前提下失效**，白等几小时。

三是**通电状态下的读取本身会改变证据**：系统可能因为挂载了外部介质、启动了索引而写入新数据，等于在扣押后仍让设备继续活动。

**核查**：**能关机就关机，镜像必须在断电状态下制作**。不能关机时（设备是运行中的服务器、无法停机的终端等）**明确采用逻辑提取，并在报告中声明这个限制**——声明比假装做了物理镜像重要得多：

```bash
# 正确顺序：关机断电 → 再接入 → 再镜像
# 若确需运行中提取，用逻辑方式（dmde、lively、目标机上的取证脚本），
# 并在报告中写明："本镜像为逻辑提取，非物理镜像；因设备运行中，
# 部分元数据可能处于不一致状态。"
```

**评估委托方需求时要问的第一个问题**："扣押时设备是开机还是关机状态"——它决定了这件案子在方法上有没有先天缺陷。

<a id="section-17"></a>

#### 陷阱 2：在分区起始找 `APSB`，没找到就判"未格式化"

**现象**：在 GPT 的 APFS 分区起始处查 `APSB` 魔数，没有命中，报告写"该分区未格式化或数据已清除"。

**原因**：`APSB` 不在分区起始，它在各个卷自己的物理块边界上（2.1）。一个 APFS 容器里挤着多个卷（系统卷、数据卷、`Preboot`、`Recovery`、`VM` 等），卷起点必须从 `NXSB` 里的卷列表读 `block_addr`，不能猜。而 `NXSB` 本身在**分区起始 + 32 字节**处，不在偏移 0——两个偏移错误叠在一起，就会在正确的地方什么都没找到。

**影响**："未格式化"或"数据已清除"是关于事实的最强结论之一。

它意味着设备上不存在用户数据。委托方据此关闭调查、通知义务评估停止。

而真相只是偏移算错了——这类错误在几秒内就能纠正，代价却可能是整个案件方向。

**核查**：**严格按两级定位，先容器后卷**：

```bash
# ① 容器：NXSB 在分区起始 + 32（不是 0）
mmls /work/DigiForensics.dd                       # 先拿到 APFS 容器分区的起始扇区
xxd -s $((775920*512 + 32)) -l 4 /work/DigiForensics.dd
# 期望：4e 58 53 42 = "NXSB"

# ② 卷：从 NXSB 的卷列表读 block_addr，换算成字节偏移
apfsutil -o $((775920*512)) /work/DigiForensics.dd | grep -i volume
# 案例：Volume 2 (oid=3, name='Macintosh HD - Data', block_addr=80)

# ③ 验证：该偏移处必须出现 APSB
dd if=/work/DigiForensics.dd bs=4096 skip=80 count=1 status=none | xxd -l 16
# 期望：4150 5342 = "APSB"
```

**第 ③ 步是不可跳过的交叉验证**——`block_addr` 指向的位置确实有 `APSB`，才说明卷列表读对了。没有验证就往下走，后面每一个文件路径都是不可靠的。

<a id="section-18"></a>

#### 陷阱 3：把 `NXSB` 当成卷超级块

**现象**：脚本在分区起始 + 32 读到 `NXSB`，直接把它当作文件系统超级块解析文件数、inode 数、根目录，得到的数值明显不合理。

**原因**：`NXSB` 与 `APSB` 是两个不同层级的结构（2.1 的核心区分）。`NXSB` 定义的是**整个物理块池**的大小、块大小、卷的个数与各卷标识；`APSB` 定义的才是**某个卷的文件系统参数**（文件数、inode 数、根目录 xid、checkpoint 描述符）。

把容器级字段当卷级字段读，得到的每一个数值都是"另一个实体的量"。

麻烦的是，错误的数据往往还能"看起来合理"——它同样是一个正整数。

**影响**：产出的**每一个派生结论都建立在错位的数据上**。更麻烦的是这类错误**不会在解析时报错**——工具照样给你文件列表，只是这个列表对应的是错误的卷或错误的范围。

**核查**：**先建立层级概念，再动手**。判断依据是字段名而非位置猜：

| 要读的字段 | 去哪个超级块 |
|---|---|
| 块大小、容器总块数、卷个数、各卷 oid/xid/block_addr | **`NXSB`**（容器层） |
| 该卷的文件数、inode 数、根目录 xid、checkpoint 描述符 | **`APSB`**（卷层） |

```bash
# 块大小必须从 NXSB 实测，不要假设 4096
apfsutil -o $((775920*512)) /work/DigiForensics.dd | grep -i 'block size'
# 卷起点 = block_addr × 实测块大小
```

**所有偏移换算都以实测块大小为基准**——写死 4096 是最常见的隐性错误（案例里恰好是 4096，但这不能作为假设的理由）。

<a id="section-19"></a>

#### 陷阱 4：用 ext4/NTFS 解析器读 APFS

**现象**：拿 TSK 的 `fls`/`fsstat` 直接对 APFS 容器跑，列出的目录几乎为空并伴随大量报错，分析员判为"数据已被擦除"。

**原因**：**TSK 对 APFS 的支持极其有限**。APFS 没有 `inode 表`也没有 `MFT`，全部元数据在一棵 B-tree 里，而 TSK 需要的正是"从一张表里按序号取记录"这个模型。

工具读不到内容不是数据不存在，而是**它找错了结构**。

而"目录空 + 大量报错"这个现象组合，在直觉上很容易被归到"数据被清空"——报错信息被当成了关于数据状态的证据，而它实际只说明工具不适用。

**影响**：把"解析器不适用"当成"数据已擦除"，会得出一个无法辩护的否定性结论。

而且这个结论一旦写进报告，后续有人用正确工具解析出大量文件时，你要面对一份曾经断言"数据已清除"的报告。

**核查**：**先验魔数，再选工具**：

```bash
# 1) 先确认是不是 APFS
xxd -s $((OFF+32)) -l 4 /work/DigiForensics.dd     # 期望 "NXSB"
# 2) 确认是 APFS 之后，必须用支持 APFS 的工具
apfsutil -o $OFF /work/DigiForensics.dd             # apfs-fuse 项目附带
# 3) fsstat 对 APFS 只能用于确认卷起点，不能用于文件枚举
fsstat -o $APFS_PART /work/DigiForensics.dd | head -20
```

**判读纪律**：**工具报错信息不是关于数据状态的证据**。当同一个命令在别的镜像上正常工作、只有这台报错时，先怀疑工具适用性，而不是数据。

<a id="section-20"></a>

### 4.2 结构解析

<a id="section-21"></a>

#### 陷阱 5：只读 B-tree 第一层就列文件

**现象**：解析 B-tree 时只读取了根节点与第一层内部节点，得到几十条记录就认为"该卷只有这么多文件"。

**原因**：APFS 的 B-tree 是多层的，内部节点只存摘要（2.2）——键值范围加子指针，**真实记录全在叶节点里**。深度为 0 的节点才是叶节点，深度大于 0 的都是索引节点。

**只读第一层等于只看了目录的前几层目录名。**

而且内部节点里的记录看起来也是"文件"的样子（有 oid、有 key），**很容易被误当成文件清单**。

**影响**：**文件数量被严重低估**。

一份"该卷共 N 个文件"的清单如果少了两个数量级，它不能用来支撑任何关于"这台机器上有什么"的结论——**而这类清单经常被用来论证"没有异常文件"**。

**核查**：**递归下钻到叶节点（深度 0）**，并核对遍历的完整性：

```bash
# 用 apfs-dump 导出结构，递归遍历
apfs-dump-quick /dev/loop0 /tmp/apfs-structure.txt
# 统计时应覆盖全部叶节点，而不是第一层
wc -l /tmp/apfs-structure.txt
```

**完整性校验的两个参照**：`APSB` 里的文件数 / inode 数是上限参考，实际遍历数与之比对能发现漏读；B-tree 内部节点的记录数与叶节点记录数差异巨大——如果你的清单数接近内部节点量级，几乎可以肯定是没下钻。

<a id="section-22"></a>

#### 陷阱 6：★ FUSE 挂载用了读写方式，checkpoint 被改写

**现象**：用 `apfs-fuse` 挂载镜像读取文件，过程中没有加 `ro`，卸载后校验镜像哈希，发现与基线不符。

**原因**：FUSE 挂载一旦以读写方式打开，驱动或系统可能对卷做 checkpoint 相关的写入（3.3 的警告）。`apfs-fuse` 提供了只读模式，**但"读"和"只读"在这个工具上不是同一件事**——不加 `ro` 时它的行为接近于一次"验证性挂载"，而验证本身可能触发元数据更新。**这一类写操作在系统层面不显眼**：不会产生明显的日志，不会在文件列表里留下新文件，只是超级块或映射区有几个字节变了。

**影响**：**这是对检材的实质改动，而且极易漏检**。后果是双重的。

一是原始检材被污染，后续所有基于它的结论都要额外论证。

二是**污染痕迹本身就是辩护方的攻击点**——"该镜像在分析期间被修改过"足以让质证时的可信度大幅下降。而且这个改动**通常只有主动做哈希比对才能发现**，而多数人不会做。

**核查**：**`ro` 不可选项，挂载前后各做一次哈希**：

```bash
# 挂载前基线
sha256sum /work/DigiForensics-work.dd > /evidence/baseline.sha256

# 挂载时强制只读
apfs-fuse -o vol=2,ro /dev/loop0 /mnt/apfs-cur
apfs-fuse -o vol=2,ro,snap=15 /dev/loop0 /mnt/apfs-snap

# 读取完成后显式卸载，不要直接关机或拔线
fusermount -u /mnt/apfs-snap; fusermount -u /mnt/apfs-cur

# 挂载后校验——若提示 FAILED，说明处置流程有缺陷
sha256sum -c /evidence/baseline.sha256
```

**注意操作的对象是工作副本**：基线哈希要打在 `DigiForensics-work.dd` 上，**不是原始 `DigiForensics.dd`**——原始镜像连挂载都不该有。

<a id="section-23"></a>

#### 陷阱 7：对镜像直接 carving，CoW 副本导致大量重复

**现象**：在 APFS 镜像上跑文件雕刻，`report.pdf` 命中 400 多次，提取出来 400 个"不同路径下的同一文件"，报告体积暴涨。

**原因**：CoW 意味着同一份内容可能在盘上存在多个物理副本（2.2 的反向陷阱）。修改一个字节会复制整条路径到新块，**旧块内容保留在原处**——而未修改的文件在多个快照之间**共用同一份数据块**，加上空间回收前的残留副本，同一文件内容会散落在多处。按签名做雕刻的逻辑是"看到 magic 就切一个文件出来"，它无法知道这几个物理位置其实是同一份逻辑文件。

**影响**：一是**提取物数量被放大几十到几百倍**，浪费存储与后续比对时间。

二是**这些重复项在时间线上会产生假的"多份副本"**，可能被误读为"文件被多台设备持有"或"存在多个用户副本"。

**核查**：**carving 后必须按哈希去重**，并把物理副本数作为独立信息保留：

```bash
# 提取后按内容哈希去重——这是唯一可靠的判据（路径与时间戳都不可靠）
find /evidence/carved -type f -exec sha256sum {} \; | sort > /tmp/hashes.txt
# 统计唯一内容数
cut -d' ' -f1 /tmp/hashes.txt | sort -u | wc -l
# 统计物理命中数
wc -l /tmp/hashes.txt
```

**两者的差值本身是有价值的信息**：它反映了这个卷上内容被复制的程度，在涉及"数据被多处留存"的案情里有直接意义。

<a id="section-24"></a>

### 4.3 取证语义

<a id="section-25"></a>

#### 陷阱 8：★ 以为快照能无限期保护数据，不评估"删除后使用时长"

**现象**：报告里写"因存在系统自动快照，删除的文件可恢复"，但委托方实际拿回去一恢复，发现那个文件不在任何快照里。

**原因**：快照保护的是"已被快照覆盖的块不被原地改写"，但它不阻止新数据写入这些块（2.4 的关键提醒）。**快照占的是逻辑视图，不是物理保留**——共享池里的块只要被后续写入覆盖，快照所指向的内容就消失了。所以快照的价值随"删除动作之后的设备使用时长"快速衰减：装软件、下载文件、跑系统更新、哪怕只是正常的日常使用，都可能把旧块冲掉。

**影响**：这是一个**关于"可恢复性"的承诺**。委托方可能基于它推迟通知义务的履行、放弃其他取证途径，甚至向数据主体作出"数据可以恢复"的判断。

**当承诺不兑现时，损失的不只是这个结论的可信度**——还有依赖它做出的实际决策。

**核查**：**评估快照价值时必须先问三个问题**：删除动作发生在什么时间（只能给区间）、最后一个快照是什么时间、设备在那之后被使用了多久（扣押时间 − 快照时间）。案例里这三个数字是：快照 xid=15 创建于 2024-08-21，文件修改于 2024-08-19，扣押于 2024-08-29——距扣押仅 8 天，块大概率尚未被覆盖。8 天与 8 个月的结论完全不同。

**报告表述**："该文件在快照 xid=15（2024-08-21 创建）中完整存在，与扣押日相隔 8 天。该结论的有效性依赖于物理块未被后续写入覆盖，本案时间跨度下该条件成立（表现为可正常读取并通过哈希验证）。"

<a id="section-26"></a>

#### 陷阱 9：把"读不出文件名"写成"卷内无数据"或"已被彻底擦除"

**现象**：无 FileVault 密钥，分析员在当前状态下列不出任何文件名，报告写"该卷数据已被擦除"。

**原因**：**加密不可读与数据不存在是完全不同的两件事**（2.5 的加密边界）。`NXSB`、卷列表、各卷 oid 与块数**都在加密层之外**——否则系统无法挂载；加密的是 B-tree 节点、文件名、时间戳与文件内容。"列不出文件"只证明"元数据在加密层之内且我没有密钥"，它不携带关于数据是否存在的任何信息。

**影响**：**"已被彻底擦除"是一个关于事实的最强结论**，法律风险极高。

设备"已擦除"会直接影响委托方的责任判定、通知义务与诉讼策略。而这个结论在取得密钥后往往立刻被推翻——案例里一提供恢复密钥，文件就在那里。

**核查**：**报告里把结构性结论与内容性结论严格分开**（2.5 已给出这个区分）：

```bash
# 无密钥时能可靠回答的：
#   是否 APFS 容器？容器里有几个卷？各卷多少块？块大小多少？
apfsutil -o $OFF /work/DigiForensics.dd
#   以及：最后一次挂载/创建时间（APSB 头部的部分字段）
```

**报告写法**：

> "在无 FileVault 密钥的条件下，本项分析可确认：`<容器/卷的客观信息>`。
> 受 FileVault 加密影响、本次未能读取的内容：文件名、目录结构、文件时间戳、文件内容。
> **本结论不表明该卷内不存在用户数据。** 需取得合法密钥后重新分析。"

"读不出"与"不存在"之间隔着一个密钥，而那个密钥通常就在委托方手里。

<a id="section-27"></a>

#### 陷阱 10：把提取件的时间戳当作内容产生时间

**现象**：快照里取出一个 PDF，其文件系统修改时间为 2024-08-19，报告据此写"该文件系 2024-08-19 生成"。

**原因**：文件系统时间戳只证明"文件系统记录的修改时间"，不证明"内容何时产生"（3.5 的关键验证原则）。复制、解压、下载、另存都会推进 mtime 而不改变内容的产生时间。**两个来源的时间不一致本身是有价值的发现**——它可能说明文件被移动过、被某个工具处理过，或者内嵌元数据被刻意修改过。

**影响**：在需要证明"文档何时形成"的场景里，这个时间可能是关键证据。用文件系统时间代替内容产生时间，等于用了一个可以低成本伪造的证据。

而且一旦对方指出"复制操作也会改 mtime"，基于该时间的全部推论都要重做。

**核查**：**双来源交叉验证，差异本身就是发现**：

```bash
# 来源一：文件系统（APFS 的 btime/mtime 可直接读）
stat /evidence/合同扫描件.pdf | grep -iE 'Birth|Modify'
# 来源二：内容内嵌时间
exiftool /evidence/合同扫描件.pdf | grep -iE 'Create|Modify'
# PDF 的 CreationDate、Office 文档的核心属性、JPEG 的 EXIF DateTimeOriginal
```

**报告写法**（按案例第 2 条结论的逻辑）："文件系统修改时间 2024-08-19 16:22:07，PDF 内嵌创建时间 2024-08-19 15:58:33，两者同日且逻辑顺序自洽，支持'该文件于 8 月 19 日生成并保存、之后未再修改'。"**逻辑顺序自洽比数值接近更有说服力**——内嵌创建时间早于文件系统修改时间是正常的内容生成过程，反过来才需要解释。

<a id="section-28"></a>

#### 陷阱 11：★ 在报告中记录密钥字符串，或用 `-o pass=` 传密码

**现象**：命令历史或报告附件里出现了完整的 FileVault 恢复密钥，或者在分析机上用 `-o pass=<密码>` 挂载。

**原因**：用命令行传密码是加密卷分析的常规写法，**看上去是最方便的方式**。但它会同时进入**shell 历史文件与进程列表**——`ps aux` 对同机器上的其他用户可见。而恢复密钥的获取路径（Apple ID 账户）是**需要向法庭说明来源的证据链环节**，密钥字符串一旦扩散，"从哪拿到的"这个问题就会变得难以回答。

**影响**：密钥泄露意味着**卷的全部内容对持有者开放**。更重要的是举证责任的损失——**报告里写了密钥，等于无法证明密钥来源的合法性**。而"依法取得的密钥"这句话需要具体来源支撑，写在报告里的字符串无法自证来源。

**核查**：用交互式或 `-r`，且报告里只写"已使用合法取得的密钥"（3.4 的处置规范）：

```bash
# 交互式：密码不进历史也不进进程列表
apfs-fuse -o vol=1 /dev/loop0 /mnt/apfs-cur
# Passphrase: ********

# -r 传恢复密钥（来源更明确，证据链上更容易说明）
apfs-fuse -r "<恢复密钥>" -o vol=1 /dev/loop0 /mnt/apfs-cur
# 绝不用 -o pass=<密码>
```

证据链中登记"何时、何人、以何方式获得密钥"，但不登记密钥本身。导出件若确有必要，命名 `DigiForensics-masterkey.bin` 并单独封存。

### 4.4 误报来源与结论表述

<a id="section-30"></a>

#### 陷阱 12：★ 忽略 `VM` 卷，丢掉换出内容

**现象**：只解析了 `Macintosh HD` 与 `Macintosh HD - Data`，报告未提及内存换出内容。

**原因**：**APFS 布局里有一个独立的 `VM` 卷**（案例里 oid=12），交换内容在其中。它是"卷列表里的一条"而不是"某个目录下的一个文件"——不做卷级枚举就看不到它，而多数工具在指定 `-o vol=N` 时默认只处理数据卷。"卷列表里有一个名字很不起眼的卷"很容易在读报告时被人跳过。

**影响**：换出文件是**已关闭进程内存的残留**，可能包含加密前的明文、未落盘的临时数据、以及密钥材料——**它的价值密度往往高于普通文档**。漏掉它可能正好漏掉案件的核心证据。

**核查**：卷列表里的每个条目都要单独处理或明确记录"未处理及原因"：

```bash
# 容器层枚举——不要跳过任何一个卷
apfsutil -o $OFF /work/DigiForensics.dd | grep -iE 'volume|oid'
# 逐卷处理：系统卷、数据卷、Preboot、Recovery、VM 各自独立
apfs-fuse -o vol=<VM卷的volno>,ro /dev/loop0 /mnt/apfs-vm
```

**报告里对每个卷给出状态**（已分析 / 因加密未分析 / 因工具不支持未分析），**不留空白**。

<a id="section-31"></a>

#### 陷阱 13：★ 报告里引用文件时不写卷标识

**现象**：报告写"在 `/Users/suspect/Documents/合同扫描件.pdf` 发现目标文件"，但没有写明它来自哪个卷、哪个快照。

**原因**：APFS 上同一个路径可以存在于多个卷、多个快照中——数据卷有当前状态和若干快照，路径字符串完全相同。在没有卷标识的情况下，"某文件"这个引用是无法复核的：复核者不知道该去哪个卷、哪个 xid 里找，也不知道他找到的是不是同一个对象。

**影响**：**报告失去可复核性**。在质证或同行复核环节，**无法定位的证据等同于不存在**——复核者找不到它，就无法确认你找到了。

案例结论第 4 条专门说明了这一点：提取件来自快照，其元数据反映的是快照时刻的状态。"取自快照 xid=15"与"取自当前卷"是两份不同的证据。

**核查**：引用一律写成「卷名/oid + 路径 + 时间戳」，涉及快照时必须带 xid：

> "在卷 `Macintosh HD - Data`（oid=3）路径 `/Users/suspect/Documents/合同扫描件.pdf`、**快照 xid=15（2024-08-21 创建）** 中发现该文件，大小 2841024 字节，修改时间 2024-08-19 16:22:07。该文件在当前卷状态下已不存在。"

**"取自快照"这个限定必须出现在每一次引用里**——它同时说明了内容状态和提取语境，缺一不可。

<a id="section-32"></a>

#### 陷阱 14：把删除时间写成精确时间点

**现象**：在快照 xid=15 中发现文件、当前状态中没有，报告写"该文件于 2024-08-21 03:15 被删除"。

**原因**：**APFS 不保留"删除动作"这个事件本身**——B-tree 里只有结果（目录项指针被移除）没有时间戳。快照的创建时间是"这个状态被定格的时间"，不是"删除发生的时间"。删除动作发生在两次快照之间，**任何精确到某一时刻的说法都是编造的**。而"删除发生在 8 月 21 日凌晨 3:15"这种表述看起来精确专业，极易被接受进报告。

**影响**：**一个虚构的精确时间点会被当作事实使用**。它可能成为"谁在什么时候删除了文件"这类指控的唯一时间依据。

而精确到分钟的删除时间一旦被对方指出无来源支撑，**基于它构建的整条行为链都会被动摇**。

**核查**：**删除时间只能给区间，两端都由独立事件界定**：

> "可确定该文件在**当前卷状态下已不存在**，但在快照 xid=15（2024-08-21 03:15:40 创建）中完整存在。因此删除动作发生在 2024-08-21 03:15:40 之后、至扣押日 2024-08-29 之间。"

案例结论第 3 条正是这个表述方式。区间的下界来自"快照里有"（删除晚于快照创建），上界来自"当前状态没有"（删除早于扣押）——两个端点各有独立来源，这才是可辩护的结论。**任何想把区间收窄的尝试都需要新的独立证据**（例如其他卷的元数据、FSEvents 记录）。

## 五、案例示例

<a id="section-34"></a>

### 5.1 被删 PDF 在 8 天前的快照里：APFS 删除时间的表述纪律

**场景**

查获一台 MacBook Pro（M1，macOS 14，已知 FileVault 开启），委托要求确认 `/Users/suspect/Documents/合同扫描件.pdf` 是否存在、其最后修改时间，以及删除文件是否可恢复。

镜像 `DigiForensics.dd`（raw APFS 容器镜像，980 GB），容器分区起始扇区 775920。

委托方想知道"这份合同什么时候被删的"。

选择这一路径的依据是**无密钥也能确定的事远多于有密钥才能确定的事**——而其中最关键的一项是快照存在性，它决定了后续所有工作的可行性。

**处置过程**

第 1 步 · 无密钥下的结构性判断（这一步的结论不依赖密钥）：

```bash
xxd -s $((775920*512 + 32)) -l 32 /work/DigiForensics.dd
# 000f7fa0: 4e58 5342 0000 0001 0000 0010 3bf1 3f00  NXSB...........>.<
#           ↑NXSB 确认        ↑块大小 4096

apfsutil -o $((775920*512)) /work/DigiForensics.dd
# NXSB Block Count: 256000000
# Volume 1 (oid=2, name='Macintosh HD', block_addr=40)
# Volume 2 (oid=3, name='Macintosh HD - Data', block_addr=80)
# Volume 5 (oid=7, name='Preboot', ...)
# Volume 8 (oid=12, name='VM', ...)
```

结构性结论（可写入报告）：确认为 APFS 容器，物理块大小 4096，共 6 个卷，其中 `Macintosh HD - Data`（oid=3）从块 80 起，另存在**独立的 `VM` 卷**（换出内容所在）。

**第 2 步 · 定位卷超级块**：

```bash
dd if=/work/DigiForensics.dd bs=4096 skip=80 count=1 status=none | xxd -l 16
# 00014000: 4150 5342 0000 0000 0000 0001 0c00 0000  APSB............
#           ↑APSB 位于块 80，与卷列表 block_addr 一致 ✓
```

第 3 步 · 快照枚举（这一项在无密钥时也必须尝试）：

```bash
apfsutil -o $((775920*512)) /work/DigiForensics.dd | grep -iB1 -A4 'snapshot'
# Snapshots in volume 'Macintosh HD - Data':
#   xid=4  created 2024-06-28 03:14:22   (系统自动)
#   xid=9  created 2024-07-19 03:11:07   (系统自动)
#   xid=15 created 2024-08-21 03:15:40   (系统自动)
```

关键发现：卷内有 **3 个系统自动创建的本地快照**，最新一个为 2024-08-21。委托方提供的设备于 **2024-08-29 扣押**——即**最后一次快照距扣押仅 8 天**。

**第 4 步 · 取得密钥后比对当前状态与快照状态**：

```bash
mkdir -p /mnt/cur /mnt/snap
sha256sum /work/DigiForensics-work.dd > /evidence/baseline.sha256

apfs-fuse -r "XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX" -o vol=2 /dev/loop0 /mnt/cur
apfs-fuse -r "XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX" -o vol=2,snap=15 /dev/loop0 /mnt/snap

# 当前状态 vs 最新快照（xid=15）
ls -l /mnt/cur/Users/suspect/Documents/  | grep -i 合同
ls -l /mnt/snap/Users/suspect/Documents/ | grep -i 合同
# 当前：  （无匹配）
# 快照：  -rw-r--r-- 1 user staff 2841024 2024-08-19 16:22:07 合同扫描件.pdf
```

**第 5 步 · 提取并交叉验证**：

```bash
cp -p /mnt/snap/Users/suspect/Documents/合同扫描件.pdf /evidence/
sha256sum /evidence/合同扫描件.pdf
ls -l /evidence/合同扫描件.pdf                      # 2841024 字节，与目录项一致 ✓

# 内嵌时间 vs 文件系统时间（两项独立来源）
exiftool /evidence/合同扫描件.pdf | grep -iE 'Create|Modify'
# Create Date : 2024-08-19 15:58:33      ← PDF 内嵌
stat /evidence/合同扫描件.pdf | grep -i modify
# Modify: 2024-08-19 16:22:07             ← 文件系统 btime/mtime
```

```bash
# 卸载并校验镜像未被改写
fusermount -u /mnt/snap; fusermount -u /mnt/cur
sha256sum -c /evidence/baseline.sha256
# /work/DigiForensics-work.dd: OK     ← 全程只读 ✓
```

**结论**

能证明：①文件已从当前状态删除，但在系统自动快照 xid=15（2024-08-21 创建）中完整存在，大小与目录项记录一致；②时间线双来源印证——文件系统修改时间 2024-08-19 16:22:07 与 PDF 内嵌创建时间 2024-08-19 15:58:33 **同日、逻辑顺序自洽**，支持"该文件在 8 月 19 日生成并保存、之后未再修改"；③镜像经挂载前后哈希比对确认未被修改。

**不能证明**：①删除时间只能界定在 2024-08-21（快照 xid=15 之后）至 2024-08-29（扣押日）之间——**APFS 不保留"删除动作"这个事件本身**，B-tree 中只有结果没有时间戳，区间结论必须如此表述，**不可写成某个精确时间点**；②提取件的性质要写明：该文件是从**快照**读出的内容，其自身元数据来自快照所反映的当时状态，报告中应写"取自快照 xid=15"而非"取自当前卷"。

**误判对照**

最像的误判是把快照里的文件修改时间 2024-08-19 16:22:07 当成"删除时间"。判据要划清两个时间的语义：`Modify` 是文件内容最后一次写入的时刻，而删除是在文件系统层面移除目录项的动作，APFS 的 B-tree 记录里删除只体现为当前状态中查不到这个名字，没有任何时间戳随这次操作写入。

能确定删除时间的只有两个边界：快照 xid=15 创建于 2024-08-21 03:15:40（当时文件还在），扣押日 2024-08-29（当时文件已不在）。正确判据是"快照证明某时刻存在"与"扣押证明某时刻不存在"，两者围成一个区间，中间的任何精确时刻都不可知。按错误判据走的代价是委托方拿 08-19 16:22 去比对监控或门禁——若那个时刻当事人在场，"删除行为"的时间归属就完全错了，而 APFS 侧没有任何数据能支持那个精确值，一旦被指出，整份报告的时间线都要重做。

<a id="section-35"></a>

### 5.2 三个系统自动快照的存在本身就改变案件性质

**场景**

同一案件的委托方在得知快照信息后追问：那三个快照是什么时候创建的、为什么是系统自动的、能不能说明有人在操作机器。

将此情形单列的原因是快照的时间分布与创建原因，本身就是一条独立于文件内容的证据线。

**处置过程**

1. 先看分布，而不是逐个追问：

```bash
apfsutil -o $((775920*512)) /work/DigiForensics.dd | grep -iA5 'snapshot'
# xid=4   2024-06-28 03:14:22
# xid=9   2024-07-19 03:11:07
# xid=15  2024-08-21 03:15:40
```

2. 与文件系统活动周期比对：

```bash
istat -o 80 /work/DigiForensics.dd 2-0-0 | grep -E 'Created|Changed'
# 卷自身的写入时间跨度与快照时间是否落在同一活动期
```

3. 记录三个可写入报告的事实：快照数量为 3、全部标记为系统自动、最新一个距扣押 8 天。

**结论**

能证明：该卷存在 3 个系统自动创建的本地快照，时间间隔约 3 周（06-28、07-19、08-21），间隔规整说明它们跟随的是系统的自动维护周期，而非人为触发——人为触发的时间不会呈现这种规律性。

**不能证明**：不能证明设备在这 8 天内未被使用。系统快照的保留策略由磁盘空间决定，快照的存在与"是否有人开机"是两件事。

**误判对照**

最像的误判是把三个快照的时间点当成"有人操作机器的三个时刻"。判据落在间隔的规律性上：三个时间点的间隔是 21 天与 33 天，落在 APFS 本地快照按剩余空间触发的常见周期范围内，且三者的秒级时间都在凌晨 03:11–03:15 这个窗口——这正是 macOS 在空闲时段执行本地快照任务的特征。人为主动创建的快照不会这样分布。正确判据是**先看分布形态，再谈成因**。按错误判据走的代价是把系统维护行为记成"可疑活动"，委托方据此把时间线上的 8 月 21 日凌晨标为可疑时段——而那台机器上当时可能根本没人。

<a id="section-36"></a>

### 5.3 反例：跳过无密钥阶段直接要求密钥

**场景**

某次 APFS 案件中，团队一上来就向委托方索要 FileVault 恢复密钥，在等待密钥的三天里没有做任何结构分析。密钥到手后发现文件系统的卷布局与快照情况需要重做判断，因为"哪一卷才是用户数据卷"此前并不清楚。

这条列为反例，是因为无密钥阶段的分析成本极低、信息量却很大，而它被整段跳过了。

**处置过程**

对照点在于无密钥阶段能拿到什么：

```bash
# 无密钥即可完成，且不需要任何解密
xxd -s $((分区偏移*512 + 32)) -l 32 /work/DigiForensics.dd    # NXSB 魔数 + 块大小
apfsutil -o $((分区偏移*512)) /work/DigiForensics.dd           # 卷清单、各卷块地址、卷名
apfsutil -o $((分区偏移*512)) /work/DigiForensics.dd | grep -iA5 snapshot  # 快照列表与时间
dd if=/work/DigiForensics.dd bs=4096 skip=<卷块地址> count=1 status=none | xxd -l 16  # APSB 校验
```

四项全部**只读且不需要密钥**。

**结论**

阴性发现：在本案中，无密钥阶段本可在三天等待期内确定卷布局（6 个卷）、用户数据卷位置（oid=3，块 80）、快照数量与最新快照时间（2024-08-21）。**未覆盖的代价是三天时间与后续一次判断返工**。

**误判对照**

最像的误判是"没有密钥什么也做不了，等拿到再说"。判据在于APFS 容器头（NXSB）、容器块位图、卷超级块（APSB）这三类元数据本身不加密，真正加密的是各卷的文件内容；所以"看不到文件内容"与"不知道卷结构"是两回事。正确判据是**把"需要密钥"限定到文件内容读取这一个环节**，其余结构判断不受影响。按错误判据走的代价：三天里本可以推进的工作全部停滞，而更实际的问题是——如果无密钥阶段就发现存在 8 天前的快照，就可以提前告知委托方"及时提供密钥的重要性在于文件可能只在快照里"，从而影响委托方的响应优先级。

## 六、扩展阅读方向

APFS 的困难不在解析，在于**它把"能不能读"这个问题提前到了所有解析动作之前**。下面几组按当下卡在哪一步分组。

<a id="section-38"></a>

### 前置基础：把卷和容器分清是一切的前提

- [文件系统取证总览](../filesystem-ntfs/filesystem-ntfs-filesystem-forensics-overview.md) —— **本篇最重要的一条链接**。那篇第 3 步是"逐卷判定文件系统类型"，如果那一步把 APFS 容器当成一个卷，本篇从第一步就全错。卷层与容器层的关系在那篇讲得更完整
- [NTFS 结构与 MFT 解析](../filesystem-ntfs/filesystem-ntfs-ntfs-master-file-table.md) —— NTFS 与 APFS 的对照读物。读完本篇再看 NTFS 的 `$MFT` 记录结构，会发现两者其实是同一个思路的两种实现：都是把元数据组织成可定位的结构。区别在于 NTFS 是定长记录、APFS 是 B-tree
- [Steady-State 与 LogFile 还原](../filesystem-ntfs/filesystem-ntfs-steady-state-logfile.md) —— **本篇快照能力的 NTFS 对偶**。NTFS 那边靠 `$LogFile` 的 LSN 追踪元数据变化，APFS 这边靠快照与 CoW。**两个机制的取证价值相似，实现方式完全不同**
- [只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md) —— 挂载一个 APFS 容器去读看似省事，**实际会触发挂载计数更新与日志写入**。本篇全程用 `apfsutil` 离线解析，正是为了避开这个

<a id="section-39"></a>

### 同层深入：其他 CoW 文件系统与相邻格式

- [F2FS 结构](../filesystem-mobile-fs/filesystem-mobile-fs-f2fs.md) —— 移动端最接近 CoW 语义的文件系统。**它也有日志与检查点机制**，但快照能力与 APFS 不是一回事，判据不能照搬
- [ext4 结构与 inode](../filesystem-unix/filesystem-unix-ext4-inode.md) —— 2.2 那句"NTFS 与 APFS 在元数据删除记录上的差别"在 ext4 侧的对应物是 journal。三种文件系统的删除语义差别，是本篇结论能成立的前提
- [文件头与文件签名](../filesystem-ntfs/filesystem-ntfs-file-headers-and-signatures.md) —— 第三章步骤 1 里 `xxd` 读出 `4e58 5342` 那一步的依据。判定 `NXSB` / `APSB` 就是魔数识别

### 相邻议题：密钥与 macOS 工件

- [BitLocker 全卷加密取证](../../crypto/crypto-volume/crypto-volume-bitlocker.md) —— **Windows 侧最接近的对偶问题**。两者的共同点是"没有密钥则内容不可读"，不同点是密钥层级设计。理解 BitLocker 那篇的密钥层级思路，会帮你理解 FileVault 的 KEK/VEK 分层
- [FSEvents 与时间机器](../../computer/computer-log-persistence/computer-log-persistence-fsevents.md) —— `fseventsd` 记录、DocumentRevisions 与 Time Machine 备份集。**时间机器的快照与本篇的本地快照是两套东西**，前者可导出、后者在容器内
- [Spotlight 索引与元数据](../../computer/computer-plist-spotlight/computer-plist-spotlight-spotlight.md) —— 用 `mdfind` 检索已删除文件残留。**索引本身也可能成为证据来源**，尽管它有自己的局限
- [macOS 取证工件地图](../../computer/computer-security/computer-security-security-artifact-map.md) —— 统一日志、LaunchDaemons 与 FileVault 的完整工件清单。**需要一份全局清单时看这篇**
- [内存中的凭据与密钥](../../memory/memory-artifact/memory-artifact-memory-credentials-and-keys.md) —— 第五章那个独立的 `VM` 卷装的是交换内容。**swap 文件与内存转储的交叉验证方法在那篇**，本篇只负责告诉你这个卷在哪、有多大

## 七、命令速查

```bash
# ===== 环境 =====
sudo apt install sleuthkit xxd file
# apfs-fuse 需自行编译（提供只读 FUSE 驱动），源码包在 apfs-fuse 项目主页获取：
#   依赖 libfuse-dev libicu-dev zlib1g-dev libbz2-dev cmake g++
#   tar xzf apfs-fuse-<版本>.tar.gz && cd apfs-fuse-<版本>
#   mkdir build && cd build && cmake .. && make
# 产物在 build/bin/：apfs-fuse、apfsutil、apfs-dump-quick

# ===== 第 1 步：定位容器（NXSB @ 分区+32）=====
mmls /work/DigiForensics.dd
APFS_PART=775920                      # mmls 实际输出的 APFS 容器分区起始扇区
OFF=$((APFS_PART*512))
xxd -s $((OFF+32)) -l 32 /work/DigiForensics.dd     # 期望 4e585342 = "NXSB"
fsstat -o $APFS_PART /work/DigiForensics.dd | head -20

# ===== 第 2 步：容器与卷列表 =====
apfsutil -o $OFF /work/DigiForensics.dd
# 核对：Block size、各卷 oid/name/block_addr、容器总块数
# 卷起点 = block_addr × Block size（块大小从输出实测，不要假设 4096）

# 手工验证 APSB
dd if=/work/DigiForensics.dd bs=4096 skip=80 count=1 status=none | xxd -l 16
# 期望 41505342 = "APSB"

# ===== 第 3 步：快照（APFS 取证的核心）=====
apfsutil -o $OFF /work/DigiForensics.dd | grep -iA4 'snapshot'   # 列 xid 与创建时间

mkdir -p /mnt/apfs-cur /mnt/apfs-snap
# 挂载前基线哈希（必做）
sha256sum /work/DigiForensics-work.dd > /evidence/baseline.sha256

# 当前状态（vol= 卷号；务必 ro）
apfs-fuse -o vol=2,ro /dev/loop0 /mnt/apfs-cur
# 指定快照（xid 来自上一步）
apfs-fuse -o vol=2,ro,snap=15 /dev/loop0 /mnt/apfs-snap

# 卸载 + 校验未改写
fusermount -u /mnt/apfs-snap; fusermount -u /mnt/apfs-cur
sha256sum -c /evidence/baseline.sha256

# ===== 第 4 步：加密卷 =====
apfs-fuse -o vol=2 /dev/loop0 /mnt/apfs-cur                # 交互式输入密码
apfs-fuse -r "XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XXXX" \
          -o vol=2 /dev/loop0 /mnt/apfs-cur                # -r = 恢复密钥(PRK)
# 不要用 -o pass= 明文传密码（会进 shell 历史与进程列表）

# ===== 第 5 步：提取与验证 =====
cp -rp --preserve=timestamps /mnt/apfs-snap/Users/suspect/Documents /evidence/Documents
find /evidence/Documents -type f -exec sha256sum {} \; > /evidence/hashes.txt
stat /evidence/Documents/report.pdf                        # Birth/Access/Modify
exiftool /evidence/Documents/report.pdf | grep -iE 'Create|Modify'   # 内嵌时间交叉验证

# ===== 排障 =====
apfs-fuse -d 1 -o vol=2 /dev/loop0 /mnt/apfs-cur           # 调试输出（1=错误 2=通用 4=目录 8=压缩 16=加密⚠)
apfs-dump-quick /dev/loop0 /tmp/apfs-structure.txt        # 导出管理结构快照（可能达数百 MB）
# 加密卷读不出内容时：先确认是否 T2 硬件加密（该驱动不支持），再考虑密钥获取
```
