# Exchange 与邮件数据恢复

> 原文链接：[DigiForensics Wiki · 在线阅读](https://www.digiforensics.cn/wiki/server-log-exchange)

<a id="section-1"></a>

## 一、概述

**邮件是企业取证里价值最高、也最难取到的一类证据。**

它能直接回答"谁在什么时间与什么人就什么内容通信"——账号日志、聊天记录都替代不了这种直接证据。

一个人可以删掉浏览记录、清理浏览器存储，但邮件往来本身就构成"关系存在"和"内容知情"的证据。

**难在哪儿？难在格式，不难在权限。**

你完全有权限访问 `...\V15\MailDB\<GUID>\Mailbox Database.edb`，但**普通工具打不开它**——它既不是 SQLite，也不是任何公开标准格式。

Exchange 从 2007 版起把邮箱数据存进 **ESE 数据库**（与 Windows 的 `ESENT.DLL` 同源），而它的 DATA/LVAL 页**可以是 LZX 或 RLE 压缩存储的**。

结果是：即便找到号称支持 ESE 的工具，面对压缩页时也可能**只读得出结构、读不出内容**。

这构成本篇的核心矛盾：数据就在那里（有权限、有文件），但读不出来（格式封闭 + 压缩）。

更危险的是——为了读出来而"修复"数据库的常规做法，会永久破坏证据。

**在取证流程中的位置**：本篇属于**分析环的高价值支线**，与 Web 攻击链的还原往往并行但独立。

**它最大的特殊性在于体积**：Exchange 的 `.edb` 是 P3 级工件（数十至数百 GB），**必须单独规划提取**，见 [00 篇的取证优先级](server-log-server-artifact-map.md)。上游依赖 NTFS 层面的定位与提取能力；下游支撑"通信关系图"与数据外传的认定。

**涉及的证据形态**：

| 形态 | 位置 | 取证价值 |
|---|---|---|
| **邮箱数据库** | `C:\Program Files\Microsoft\Exchange Server\V15\MailDB\<GUID>\Mailbox Database.edb` | ★★★★★ 收发件人与时间 |
| **传输数据库** | 同目录 `Transport Database.edb` | ★★★ 队列与路由 |
| **事务日志** | 同 GUID 目录下的 `Logs\`（`E01.log` 等事务日志 + `E01.chk` 检查点） | ★★★★ **未落盘事务的恢复来源** |
| **传输日志** | `V15\TransportRoles\Logs\Role_*.log` | ★★★★★ **比 `.edb` 易读得多** |
| **客户端 PST** | `%LOCALAPPDATA%\Microsoft\Outlook\` | ★★★★★ **不受 ESE LZX 压缩影响，可完整导出附件**（OST 只是缓存，受离线时间窗限制） |
| **邮件头 `Received:` 链** | 任何留存的一封邮件原文 | ★★★★★ **独立于数据库，与压缩无关** |
| **网关/反垃圾日志** | 网关服务器、Anti-Spam 目录 | ★★★ 收发记录与拦截情况 |
| **OWA 浏览器缓存** | 用户浏览器缓存 | ★★ 轻量版邮件内容 |

> ★★ **本篇最被低估的证据是邮件头。** `Received:` 链是**投递过程中每跳追加的明文头**，记录了每跳的服务器名、接收时间戳、客户端 IP。它不经过数据库压缩——所以即使 `.edb` 完全无法解析，只要有邮件原文（哪怕只是客户端里的邮件、转发件、打印件、网关日志里的一行），就能还原完整路径。
>
> **★ 判读方向（先记这一条，其余都从它推导）**：RFC 5321 §4.4 规定接收服务器必须把 `Received` **前插到头部**、且不得改动已有的行。因此这个栈是**倒序**的——**最上面一条是最后一跳（离你最近）**，**最下面一条是第一跳（发件方所在）**。所以：`自上而下 = 收件方 → 发件方`，时间戳**自上而下递减（越靠上越晚）是正常的**；要按时间顺序读投递路径，必须**自下而上**读，此时时间戳应**单调递增**。反过来（靠上更早）才需要解释。

某人某时收发过某封邮件；邮件的正文与附件；**完整的投递路径与每跳时间戳、客户端 IP**（这一项独立于数据库）；已删除邮件"曾经存在过"的事实；传输队列的投递结果与失败原因；邮件数据是否被外传。

**附件常常无法完整恢复**（在 LVAL/溢出页且可能压缩）；**已删除邮件可能只剩字节**（slack 空间被复用后，**能证明"曾经存在"不证明"内容是什么"**）；**服务器 `.edb` 未必覆盖全部邮件**（用户可能用移动端或本地缓存，服务器只有副本）；**时间下限**（循环日志最老的文件会被 checkpoint 覆盖）。

**操作纪律（本篇最需要记住的一条）**：`esentutl` 的使用顺序是先 `/mh` 读状态（只读）→ 再 `/y` 复制工作副本 → 最后才在副本上考虑修复。

绝不直接对原始 `.edb` 执行任何写操作或修复。 详见 [4.1 写操作边界](#section-19)。

**内容边界（本篇的红线）**：邮件内容是企业个人信息中敏感度最高的一类。**提取与呈现都要最小化**——只取与委托范围相关的邮件，宁少勿全；报告中的正文与附件内容应**脱敏呈现并登记密级**；涉及第三方（收发件人不是本案当事人）的邮件内容，**只保留证明案件事实所必需的部分**。相关授权要求见扩展阅读中的合规条目。

**读者前提**：需要 Windows 文件系统取证能力（定位、复制、哈希固定）、数据库基础概念（页、事务日志、slack space）、邮件协议（SMTP/MAPI）基本原理。建议先按 [3.6 第 6 步](#section-17) 的思路评估替代路径——很多案件的邮件证据在用户 PST、网关日志或某一封转发出去的邮件里，找到它可能只需要一次 `grep`，而解析 `.edb` 需要专用工具、几十 GB 空间和数天时间。

## 二、核心原理

<a id="section-3"></a>

### 2.1 Exchange 版本与数据库布局

Exchange 的数据库布局随版本变化很大。**先确认版本，这是第一步。**

| 版本 | 主要数据库文件 | 路径 | 说明 |
|---|---|---|---|
| **Exchange 2013+** | `Mailbox Database.edb` | `C:\Program Files\Microsoft\Exchange Server\V15\MailDB\<GUID>\` | 邮箱数据库（每个数据库组一个 GUID 目录） |
| | `Transport Database.edb` | 同上目录或独立路径 | 传输队列与路由 |
| | `Logs\` 子目录 | 同一 GUID 目录下 | `E01.log` 等事务日志、`E01.chk` 检查点 |
| | `WLSV*.edb` | 索引相关 | 名称因角色而异 |
| **Exchange 2010** | `Mailbox Database.edb` | `V14\MailDB\<GUID>\` | 结构与 2013 接近 |
| **Exchange 2007** | `Store01.edb` 等 | `V12\MailDB\<store>\<GUID>\` | **文件名是 `StoreNN.edb`**，与 2013+ 不同 |
| **Exchange 2003 及更早** | `MDB.edb` | `MailDB\<storage group>\<store>\MDB.edb` | 旧结构 |
| **客户端 PST** | 用户的 `.pst` | `%LOCALAPPDATA%\Microsoft\Outlook\` 或网络盘 | **PST 是可移植容器，不受 ESE LZX 压缩影响**；OST 受缓存时间窗限制，不保证完整 |
| **客户端 OST** | 用户的 `.ost` | 同上（也可由注册表 `HKCU\Software\Microsoft\Office\<ver>\Outlook\forceOSTPath` 改路径） | **缓存副本，非完整邮箱**：受"保持离线"时间窗限制，且绑定原账户/profile，不能当备份 |

> **★ 三个必须先确认的事实**：
> 1. **文件名随版本变**：Exchange 2013+ 是 `Mailbox Database.edb`（有空格），2007 是 `Store01.edb`。**按固定文件名搜索会漏。** 用 `*.edb` 递归搜整个数据库目录。
> 2. **每个数据库组有自己的 GUID 子目录**：`MailDB\<GUID>\Mailbox Database.edb`。GUID 随数据库组创建，**重建数据库会换新 GUID**——旧 GUID 目录还在但不再使用，本身是"数据库曾被重建"的线索。
> 3. **日志在 `Logs\` 子目录**，且日志文件巨大（每个通常 1024 MB）。完整提取一个邮箱数据库（含日志）可能是几十到几百 GB（见 [01](server-log-server-artifact-map.md) 的 P3 优先级）。

<a id="section-4"></a>

### 2.2 ★ ESE 数据库机制：页、事务日志与 slack space

ESE 是一个**分页（page-based）的嵌入式事务数据库**。理解三个概念就够了，剩下的取证特性都由它们推出来。

**① 页（Page）与页类型**

| 页类型 | 作用 | 取证意义 |
|---|---|---|
| **Database（DB）页** | 数据库头：格式版本、根页指针、LSN | **读出它就知道版本与状态**（`/mh` 读的就是它） |
| **Catalog（CAT）页** | 表目录：有哪些表、列定义、索引 | **不读它就无法知道 `.edb` 里有什么表** |
| **Data（DATA）页** | 实际记录数据 | 邮件正文、收件人、附件元数据在此 |
| **Index（INDX）页** | B 树索引 | 索引损坏但数据页完好时，仍可能恢复数据 |
| **Long Value（LVAL）页** | 大字段（正文、附件）的溢出存储 | **附件常在这里** |

② 事务日志（transaction log / `.log`）：为什么 ESE 可以"回滚恢复"

ESE 采用预写日志（Write-Ahead Logging）机制：任何数据页被修改前，对应的修改记录先写入事务日志文件（`E00.log`、`E0100000001.log`…），**修改是否已落盘到 `.edb` 由检查点文件（`E00.chk`）标记**。

这个机制决定了取证上的一个基本事实：**数据页上的内容永远可能落后于日志。**

```
修改数据页 → 先写事务日志（记录旧值/新值）→ 再改数据页 → 检查点推进，标记该事务已落盘
崩溃恢复   → 读日志，把未落盘的修改回滚（UNDO）
```

**取证含义**：

| 事实 | 取证价值 |
|---|---|
| 日志**先于**数据页写入（预写日志） | 决定了"文件里的内容"是不是最新状态 |
| 异常关闭（**dirty shutdown**）后日志里**可能含比数据页更新的数据** | **日志是独立证据源**，可能含主库没有的记录 |
| 循环日志中**最老的文件可能被 checkpoint 覆盖** | 决定可恢复的邮件时间下限 |
| `/mh` 的 `Log Time` 与 `Last Update Time` 不一致 | **说明未正常关闭**，可能需要修复 |

> **★ 关键推论**：**不要只提 `.edb` 文件。** 同一目录下的 `Logs\` 子目录是**独立的、常常被忽略的证据源**。在某些情况下，日志里能恢复出主库文件里已经没有的邮件记录。

③ Slack space：为什么"删掉的邮件还能找到一部分"

删除一封邮件不会擦除数据页上的原始字节，只是在记录层把它标记为"已删除"（tombstone / 变长字段的重置）。

原始字节通常仍留在页内的 slack 空间（未使用区），直到那个页被新数据覆写。

| 项目 | 说明 |
|---|---|
| **未分配页（unallocated page）** | 整个页已不属于任何表，**整页可雕刻** |
| **slack space（页内未使用区）** | 页已分配但内部有空洞，**只能按页提取后手工搜索** |
| **复用的时机** | 页内新数据写入时**才会覆写** slack。**邮件删除后立即未复用 → 字节完好** |
| **取证手段** | 先在 NTFS 层把 `.edb` **文件整体**提取出来（`esentutl /y` 字节级复制或 `icat`），再在**数据库文件内部**按内容签名与关键字搜索 |

> **★ 取证手段的关键限制**：ESE 的未分配页与 slack 都是**已分配 `.edb` 文件内部的页**，它们对文件系统层工具**不可见**。`blkls`、`tsk_recover` 这类工具只能作用于**磁盘镜像的未分配簇**，作用不到 `.edb` 的页边界上——拿不到"ESE 未分配页"，只能拿到"NTFS 未分配簇"。要按 ESE 页提取，必须先有 `.edb` 文件，再用 ESE 专用工具（如 libyal 的 `esedbinfo` 系列）解析其页结构。

> **★ 与 Web 取证的连接**：这就是 [04](server-log-web-attack-trace-reconstruction.md) 2.7 节说的同一件事——**删除抹掉的是"目录项"，不是"数据"**。区别在于 ESE 的 slack 在**数据库文件内部**，需要 ESE 专用工具才能按页提取；NTFS 的 slack 在**磁盘未分配空间**，用 `blkls` 就能拿到。

<a id="section-5"></a>

### 2.3 ★★ LZX / RLE 压缩：Exchange 数据恢复的主要障碍

**这是本篇最需要提前认知的技术事实**，因为它决定了你会不会在工具上浪费时间。

| 事实 | 影响 |
|---|---|
| ESE 的 **DATA / LVAL 页可以配置为压缩存储**（LZX 或 RLE） | 记录不是明文，而是压缩流 |
| Exchange 2013+ 邮箱数据库默认启用压缩 | 2013+ 的数据库建库默认开启压缩，取证时会遇到 |
| **压缩页无法用通用工具解析** | 用 SQLite 工具打开只会得到"文件不是数据库" |
| **支持 ESE ≠ 支持 LZX** | 能读表结构和部分记录，但**长正文/附件为空或乱码** |

**这就是"为什么通用数据库工具完全无效"的技术原因**：

| 工具类型 | 结果 |
|---|---|
| `sqlite3`、DB Browser 类 | **完全打不开**——ESE 文件头与 SQLite 完全不同 |
| 十六进制编辑器 | 能看到明文片段，但**结构被打散，无法确定边界与含义** |
| 通用文本搜索（`grep`/`strings`） | **只能命中未压缩页里的记录**；压缩页里的正文**全部漏掉** |
| 支持 ESE 但不支持 LZX 的解析器 | 能读表结构、记录头，**但正文字段为空** |

> **★ 实务建议**：在报告和方案阶段就要明确写清"**本环境是否支持 LZX 解压**"。如果工具链不支持，应尽早转向 2.7 节的**替代证据路径**（客户端 PST、邮件网关日志、`Received:` 链），而不是反复在不同解析器之间碰壁。**邮件正文的取证不应该是"工具试错"的过程。**

<a id="section-6"></a>

### 2.4 ★ `esentutl` 详解：先读状态，再复制，最后才谈修复

`esentutl.exe`（`%windir%\System32\`）是 Windows 自带的 ESE 维护工具。

它同时具备读取和改写能力——这正是它的取证风险所在。

| 开关 | 作用 | 是否修改数据库 | 取证用法 |
|---|---|---|---|
| **`/mh <file>`** | **读数据库头，打印状态报告**（`/m` = File Dump，`h` = header） | **否（只读）** | ★★★ **第一步必做**：是否干净关闭、页大小、版本 |
| **`/y <src> /d <dst>`** | **复制数据库文件** | 源**否** | ★★★ **第二步必做**：制作工作副本 |
| **`/k <file>`** | **Checksum：逐页校验和**，验证物理完整性 | 否（只读） | ★★★ 在**副本**上做；报页级错误说明底层损坏 |
| **`/g <file>`** | **Integrity：完整性检查**，查逻辑与结构错误 | 否（只读） | ★★★ 在**副本**上做；`Dirty Shutdown` 时应先 `/r` 再 `/g` |
| **`/r <file>`** | **Recovery：软修复**（重放日志、回滚未提交事务） | **是，明显修改文件** | ★ 在**副本**上做，**且必须先留哈希** |
| **`/p <file>`** | **Repair：硬修复**，删除无法读取的页 | **是，且可能丢数据** | ✗ **取证高危**（见陷阱表） |
| `/d` | Defragmentation：碎片整理 | 是（重写全库） | ✗ **取证禁用** |

> **★ 三条模式名极易记混，这是本节最需要记住的**：
>
> | 开关 | 名字 | 记忆锚点 |
> |---|---|---|
> | `/k` | **C**hecksum | **K** = 校验和（check） |
> | `/g` | **G**o/integrity | **G** = 全库结构检查 |
> | `/p` | **P**atch/repair | **P** 是**破坏性**修复，会删页 |
> | `/r` | **R**ecovery | 软修复，**不删数据** |
> | `/d` | **D**efragment | 碎片整理，**重写全库** |
>
> **只读的三条是 `/mh`、`/k`、`/g`**——**取证早期只应使用这三者**。凡涉及 `/r`、`/p`、`/d` 的操作，一律**先复制副本**。

**★ 四个关键判读点（`/mh` 输出的核心字段）**：

| 字段 | 健康值 | 异常含义 |
|---|---|---|
| `State:` | `Clean Shutdown` | `Dirty Shutdown` = **未正常关闭**，日志与数据页可能不一致 |
| `Log Time:` vs `Last Update Time:` | 两者**接近** | **差距大 → 日志更新，可能有未回滚的修改**，可考虑 `/r` |
| `Format Version:` | 与目标 Exchange 版本匹配 | 版本跨度过大 → 需确认是否升过级 |
| `Last Update Time:` | 越新越好 | **过旧 = 数据库可能长时间未更新甚至已废弃** |

> **★ 最关键的操作纪律（务必写进工作记录）**：
>
> **提取路径**：`/mh`（只读）→ `/y` 复制出工作副本 → 在**副本**上做 `/k`、`/g`，确有必要时才 `/r`。
>
> **绝对顺序错误**：`esentutl /r "D:\Exchange\Mailbox Database.edb"` 直接对原始文件操作 → **修改原始数据库、破坏证据完整性、且不可逆**。即便现场是从镜像里提取出来的文件，**它仍是原始证据**。

"只在副本上操作、把原始状态单独存档"这个规矩并非 ESE 独有。

InnoDB 的 redo/undo 与 binlog 如何在不写回原始文件的前提下取证，可参考 [MySQL 数据库取证](../../mobile/mobile-database/mobile-database-mysql.md)。

> **每次操作前后都要记录 SHA-256**，否则无法证明副本与原件的对应关系。

<a id="section-7"></a>

### 2.5 标准流程：先 `/mh` 读状态，再复制，需要时才修复

```
① 确认版本与路径
   → 递归找 *.edb（不按固定文件名搜）
② 只读状态检查  esentutl /mh  <file>
   → 看 State / Log Time / Last Update Time / Format Version
   → 记录输出（★ 这是原始健康状态，修复后就没了）
③ 复制工作副本    esentutl /y <src> /d <dst>
   → 对副本计算 SHA-256，与原件比对必须一致
④ 只读校验（副本）esentutl /k <副本>    ← 逐页校验和
                esentutl /g <副本>    ← 完整性检查
   → 两者的区别见 2.4 记忆锚点表
⑤ 软修复（可选）  esentutl /r <副本>     ← ★ Dirty Shutdown 时的标准处置
   → 修复后重新 /mh + 重算哈希（★ 证明副本已被修改）
⑥ 专用工具解析    支持 ESE + LZX 的工具
   → 导出可引用的证据格式（CSV / 报告）
```

> **★ 为什么第 ② 步的输出要单独存档**：`/r` 修复会抹掉"原始状态是 Dirty Shutdown"这个事实。而"数据库异常关闭"本身就是一条证据——它可能意味着管理员强杀了服务、断电、或攻击者关停 Exchange 规避日志。**修复前的状态报告是原始证据的一部分。**
>
> **★ 注意顺序**：官方建议在 `Dirty Shutdown` 状态下**先 `/r` 再 `/g`**，因为不先完成恢复就直接做完整性检查，结果不可靠。`/k`（逐页校验和）不受此限制，可随时做。

<a id="section-8"></a>

### 2.6 可用工具与其能力边界

| 工具 | 适用对象 | 能力与边界 |
|---|---|---|
| **libesedb**（`esedbexport` / `esedbinfo`） | `.edb`（ESE） | 跨平台；`esedbinfo` 列表与记录数，`esedbexport` 按表导出。**对 LZX 支持有限**，长正文/附件常为空 |
| **PST 解析器**（如 `pffexport` 一类） | `.pst` | 专处理 PST（非 ESE）。**能完整导出邮件与附件**，常比服务器 `.edb` 更实用 |
| **Exchange 原生命令**（`Get-Mailbox` 等） | **活系统** | 只能在**运行中的服务器**上导出 PST，**离线镜像不可用** |
| **十六进制 + 关键字搜索** | 任意 | **只能命中未压缩页**，作交叉验证的**补充**手段 |
| **VEST 类 ESE 工具** | `.edb` / `.pst` | 商业取证套件中的 ESE 组件，**通常对 LZX 支持较完整**；需在方案阶段确认授权 |

> **★ 选型原则**：**先确认"是否支持 LZX"，再选工具**。选一个不支持压缩的解析器，然后花三天分析"为什么附件都是空的"，是这类案件最常见的时间浪费。

<a id="section-9"></a>

### 2.7 ★ 取证价值与限度

**能证明什么**（服务器 `.edb` 可用时）：

| 结论 | 证据强度 |
|---|---|
| 某人某时**收到/发送**了某封邮件 | ★★★★（时间、收发件人、主题可固定） |
| 邮件的**正文内容** | ★★★（取决于压缩支持，见 2.3） |
| 邮件的**附件内容** | ★★（常因压缩/溢出页难以完整恢复） |
| 邮件的**传输路径** | ★★★★★（★ `Received:` 链，**独立于数据库，与压缩无关**） |

> **★★ 邮件头是本篇最被低估的证据。** `Received:` 链是**投递过程中每跳追加的明文头**，记录了：每一跳的服务器名/主机名、接收时间戳、客户端 IP。**它不经过数据库压缩，所以即使 `.edb` 完全无法解析，只要有邮件原文（哪怕只是客户端里的邮件、转发件、打印件、网关日志里的一行），就能还原完整路径。
>
> **判读方法**：**读的方向就是时间的反方向。** RFC 5321 §4.4 要求接收方**前插** `Received` 头，所以**最上面一条是最后一跳**、**最下面一条是第一跳（发件方）**。
>
> | 读法 | 方向 | 时间戳应当 |
> |---|---|---|
> | 自上而下（看"离我最近的服务器"） | 收件方 → 发件方 | **递减**（越靠上越晚）——这是正常的 |
> | 自下而上（还原投递顺序） | 发件方 → 收件方 | **单调递增**——这是正常的 |
>
> **所以"时间戳递减"本身不是伪造迹象，它只是倒序栈的正常表现。** 需要解释的是**异常**：自下而上读时出现**回退**（某跳时间戳早于它下面那一跳）、时钟跳变过大、或某一跳的 `by` 主机名/IP 与拓扑矛盾。伪造者可插入伪造的 `Received` 行，但**只有他之上、由你方可信边界写入的那些行是可信的**——最靠上的若干条由你自己的服务器追加，无法被发件方伪造。
>
> **★ 同一原则决定了哪一行的 IP 最可信**：`Received` 行由**接收方**写入，行内**方括号里的对端 IP** 是接收方实际观察到的连接源地址，**可信度最高**；而 `from` 后面那个不带括号的 HELO 名由发件方自报，**可任意伪造**。

**限度（必须写进报告）**：

| 限度 | 原因 |
|---|---|
| **附件常难完整恢复** | 附件在 LVAL/溢出页，且可能压缩 |
| **已删除邮件可能只余字节** | slack 空间可能被复用，**能证明"曾经存在"不证明"内容是什么"** |
| **日志覆盖决定时间下限** | 循环日志最老的文件被 checkpoint 覆盖 |
| **服务器 `.edb` 未必覆盖全部邮件** | 用户可能用 Outlook 缓存在 PST、或用移动端**——服务器只有副本** |

<a id="section-10"></a>

### 2.8 替代证据路径：很多案件的根本解法在服务器之外

这是本篇**最实用的一节**。当服务器 `.edb` 走不通时，这些路径往往能给出同样有效的结论，且技术门槛低得多。

| 路径 | 位置 | 能证明什么 | 取证难度 |
|---|---|---|---|
| **客户端 OST/PST** | `%LOCALAPPDATA%\Microsoft\Outlook\` | **PST 可完整导出邮件与附件**（不受 ESE LZX 压缩影响）；**OST 只是缓存**，受离线时间窗限制 | ★★ 需定位用户配置目录 |
| **★ 邮件头 `Received:` 链** | 任何留存的一封邮件原文 | **完整投递路径、每跳时间戳、客户端 IP** | ★★★ **最易被忽略，价值最高** |
| **Exchange 传输日志** | `V15\TransportRoles\Logs\Role_*.log` | 传输队列、投递结果、`Received:` 头 | ★★ |
| **邮件网关/反垃圾日志** | 网关服务器、Anti-Spam 目录 | 收发记录、主题、附件名、拦截情况 | ★★ |
| **OWA 浏览器缓存** | 用户浏览器缓存（[浏览器取证](../../computer/computer-browser-behavior/computer-browser-behavior-browser-forensics.md)） | 轻量版邮件内容 | ★★★ |

```powershell
# 客户端 PST/OST：从镜像中定位（★ PST 可完整导出；OST 只是缓存，受离线时间窗限制）
Get-ChildItem 'C:\Users\*\AppData\Local\Microsoft\Outlook' -Recurse -File -ErrorAction SilentlyContinue |
  Select-Object FullName, Length, CreationTimeUtc, LastWriteTimeUtc

# Exchange 传输日志（★ 记录投递结果，比 .edb 易读得多）
Get-ChildItem 'C:\Program Files\Microsoft\Exchange Server\V15\TransportRoles\Logs' -File -ErrorAction SilentlyContinue |
  Select-Object Name, Length, LastWriteTimeUtc | Sort-Object LastWriteTimeUtc -Descending | Select-Object -First 20
```

> **★ 实务建议**：拿到"疑似邮件相关的委托"时，**第一件事是评估替代路径，而不是直奔 `.edb`**。很多案件的邮件证据其实在用户 PST、网关日志或某一封转发出去的邮件里——找到它可能只需要一次 `grep`，而解析 `.edb` 需要专用工具、几十 GB 空间和数天时间。

## 三、操作步骤

<a id="section-12"></a>

### 3.1 第 1 步：定位数据库与版本（只读）

```bash
# 递归搜全部 .edb（★ 不按固定文件名搜，文件名随版本变化）
fls -o 2048 -r -p /work/DigiForensics.dd > /work/filelist.txt
grep -iE 'Mailbox Database\.edb|Store[0-9]+\.edb|Transport Database\.edb|MDB\.edb' /work/filelist.txt
grep -iE 'MailDB/[^/]+/[0-9A-Fa-f-]{36}/Logs/.*\.log$' /work/filelist.txt | head -20
```

```powershell
# 活系统：确认版本与实际路径
Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Exchange Server\V15\Setup' -ErrorAction SilentlyContinue |
  Select-Object ProductVersion, Role, ActiveDirectoryRole
Get-Service -Name 'MSExchange*' | Select-Object Name, Status, StartType
```

**验证**：`V15` 对应 Exchange 2013–2019，`V14` 是 2010，`V12` 是 2007。**版本决定文件名与可用的解析工具。** 注意 `MailDB\<GUID>\` 目录名——多 GUID 说明存在多个数据库组。

<a id="section-13"></a>

### 3.2 第 2 步：`/mh` 读取状态（★ 只读，原始健康状态）

```cmd
:: 在 Windows 上执行；路径含空格必须加引号
esentutl /mh "D:\evidence\Mailbox Database.edb"
esentutl /mh "D:\evidence\Transport Database.edb"
```

> **★ `/mh` 只接受数据库文件，不接受日志文件。** 微软 ESEUtil 官方文档规定各开关的文件类型必须对应，用错开关输出无效或直接报错：
>
> | 开关 | 作用对象 |
> |---|---|
> | `/mh` | 数据库头 → `filename.edb` / `filename.stm` / `filename.pat` |
> | `/mk` | 检查点文件头 → `filename.chk` |
> | `/ml` | 事务日志头 → `filename.log` |
> | `/mm` | 元数据转储（表与索引清单）→ **`.edb`** |
> | `/ms` | 空间占用转储（`/mm` + 空间列）→ **`.edb`** |
>
> 所以对 `E0100000001.log` 要用 `/ml`（只读 dump），**不能**用 `/mh`（那是数据库/流文件/Patch 文件的头），也不能用 `/mm`（`/mm` 是数据库元数据清单，不是日志）。用错开关会报错，或输出乱码式的错误信息。

若要读出日志内**具体的事务记录**（而不只是文件头），`/c` 是 `/ml` 的子选项，且**必须带目标文件名**：

```bash
esentutl /ml E0100000001.log                 # 只看日志头
esentutl /ml E0100000001.log /c E01.csv     # 把该日志的事务记录 dump 成 CSV
```

注意 `/c` 后面是**输出文件**，不是布尔开关。写成 `esentutl /m E01.log /c` 缺少 mode-modifier 且 `/c` 无参数，属于误用。

`/ml` 还带一个 `/x` 选项，允许修复日志末尾的 torn write——它**要求对日志文件有写权限**，因此只在副本上做，绝不能对原始检材执行。

对日志执行任何写操作（如用 `/r` 回滚或重放事务）都必须先在副本上做。

输出里**必须记录**的字段：

| 字段 | 记什么 |
|---|---|
| `State:` | `Clean Shutdown` / `Dirty Shutdown` |
| `Log Time:` | 与 `Last Update Time` 对比 |
| `Last Update Time:` | 数据最后更新时间 |
| `Format Version:` | 与 Exchange 版本匹配性 |
| `Database Log Size:` / `Available Log Space:` | 判断日志与 slack 规模 |
| `Current Page Size:` | 页大小（通常 4096） |

> **★ 把这一步的输出单独存成文件**（如 `mh-mailbox-before.txt`）。修复后原始状态就不可得，而"异常关闭"本身可能是证据（见 2.5）。

**验证**：若 `State: Dirty Shutdown`，说明数据库**未正常关闭**。这可能是断电、强杀服务，也可能是**人为关停以规避记录**——**是结论，不是故障**。

<a id="section-14"></a>

### 3.3 第 3 步：复制工作副本（★ 绝不直接对原始文件操作）

```cmd
:: 方式一：esentutl 复制（推荐，字节级复制，可带 /o 抑制 logo）
esentutl /y "D:\evidence\Mailbox Database.edb" /d "D:\work\Mailbox Database.edb" /o

:: 复制后立即核对哈希并登记
certutil -hashfile "D:\evidence\Mailbox Database.edb" SHA256 > D:\work\hash-original.txt
certutil -hashfile "D:\work\Mailbox Database.edb" SHA256 > D:\work\hash-copy.txt
fc /b D:\work\hash-original.txt D:\work\hash-copy.txt
```

```powershell
# PowerShell 侧记录（★ 修改前后的哈希都要留）
Get-FileHash 'D:\evidence\Mailbox Database.edb' -Algorithm SHA256 |
  Format-List Path, Hash
Get-FileHash 'D:\work\Mailbox Database.edb' -Algorithm SHA256 | Format-List Path, Hash
```

**验证**：副本与原件哈希**必须一致**（`/y` 是字节级复制）。若不一致，立即排查并重新复制。

> **★ 磁盘空间提醒**：一个邮箱数据库可能是**数十到数百 GB**，加上 `Logs\` 目录往往还要同等空间。**动手前先确认可用空间**（见 [01](server-log-server-artifact-map.md) 的 P3 说明）。

<a id="section-15"></a>

### 3.4 第 4 步：一致性检查与（必要时）修复——只在副本上

```cmd
:: 4.1 先做两项只读校验（★ /k 逐页校验和、/g 完整性检查，都不改文件）
esentutl /k "D:\work\Mailbox Database.edb"
esentutl /g "D:\work\Mailbox Database.edb"

:: 4.2 若是 Dirty Shutdown，标准处置是软修复 → 只在副本上
esentutl /r "D:\work\Mailbox Database.edb"

:: 4.3 修复后再做一次完整性检查（★ 官方建议：先 /r 再 /g）
esentutl /g "D:\work\Mailbox Database.edb"

:: 4.4 重新读状态 + 重新算哈希（★ 证明副本已被修改）
esentutl /mh "D:\work\Mailbox Database.edb"
certutil -hashfile "D:\work\Mailbox Database.edb" SHA256
```

> **★★ 操作风险提醒**：
>
> `/r`（软修复）、`/p`（硬修复）、`/d`（碎片整理）都会改写数据库文件。
> - `/r` 重放日志、回滚未提交事务——**文件字节被改写**；
> - `/p` 更进一步，**会删除无法读取的页**——**可能造成数据丢失**；
> - `/d` 重写整个库以回收空间。
>
> **对原始证据直接执行，会破坏完整性且不可逆。**
>
> **正确顺序永远是**：`/mh`（只读留证）→ `/y`（复制）→ 记录哈希 → **在副本上** `/k`、`/g` → 确有必要才 `/r` → 再次记录哈希。
>
> **报告中必须同时给出原件哈希与副本哈希**，并注明"原件全程未修改"。

<a id="section-16"></a>

### 3.5 第 5 步：解析与导出（用支持 LZX 的工具）

```bash
# libesedb（Ubuntu/CentOS：apt install libesedb-utils）
esedbinfo "D:/work/Mailbox Database.edb"                    # 先看有哪些表、多少记录
esedbexport "D:/work/Mailbox Database.edb" -t <表名> -f csv  # 按表导出
# ★ 若正文/附件字段为空 → 极可能是 LZX 压缩未解（见 2.3），换工具而非反复重试

# 未分配页雕刻（★ 与 NTFS 同理，只是位置在数据库文件内部）
blkls -o 2048 /work/DigiForensics.dd > /work/unalloc.raw
foremost -i /work/unalloc.raw                              # 或 testdisk / scalpel
strings -n 8 /work/unalloc.raw | grep -iE '发票|合同|password|账号'
```

**验证**：导出的记录数应与 `esedbinfo` 报告的一致。若某表记录数正常但长字段全空，几乎可确定是压缩问题——这本身就是一条可写入报告的技术结论。

<a id="section-17"></a>

### 3.6 第 6 步：走替代路径（当 `.edb` 走不通时）

```bash
# 6.1 找客户端 PST/OST（★ PST 不受 ESE 压缩影响，常能完整导出附件）
fls -o 2048 -r -p /work/DigiForensics.dd | grep -iE 'AppData/Local/Microsoft/Outlook/.*\.(pst|ost)$'
icat -o 2048 /work/DigiForensics.dd <inode> > /evidence/user-mailbox.pst

# 6.2 找邮件网关 / 传输日志里的邮件头（★ Received: 链就在这里）
icat -o 2048 /work/DigiForensics.dd <inode-transportlog> > /evidence/TransportRole.log
grep -iE '^Received:|Subject:' /evidence/TransportRole.log | head -40

# 6.3 找转发/留存的邮件原文（★ 任何一封就能还原完整投递路径）
grep -rliE 'Received:.*(digiforensics|mail)' /evidence/ | head
```

**验证**：从任意一封邮件原文提取 `Received:` 链，**自下而上（发件方 → 收件方）**排列各跳时间戳，应**单调递增**（越往下越早）。若某跳时间戳**回退**（比它下面那一跳还早）或出现时钟跳变，**该跳需要解释**——可能是时钟不同步，也可能是插入的伪造 `Received` 行，是报告要点。反过来，直接自上而下读时看到时间戳递减是**正常**的，不要当成异常。

## 四、常见陷阱

邮件数据存储的取证有一个别的领域少有的特征：

数据库文件本身携带了自身的完整性状态，而且这个状态会在任何修复操作后永久消失。

也就是说，你对检材做的第一个写操作，可能就毁掉了最关键的那条证据。

本章按**写操作边界、模式名与工具选型、提取范围、内容证据** 四组拆开。

<a id="section-19"></a>

### 4.1 写操作边界

<a id="section-20"></a>

#### 陷阱 1：对原始数据库直接跑修复类操作 ★

**现象**

拿到数据库文件，为了让它能被工具读取，
直接跑了一个"修复"或"整理碎片"的操作。

**原因**

数据库文件里有一类**状态标记**记录了它上次是否正常关闭。
**这个标记在任何修复或整理操作之后都会被清除。**
它可能是判断「这封邮件在事发前是否已不可读」的唯一依据。

也就是说，修复前后的数据库在**证据价值上是两个不同的东西**，虽然内容看起来一样。

而且这类操作并不总是无损的：其中有一种会**删除无法解析的页**，这些页里可能有可恢复的邮件片段。

**影响**

**不可逆。** 原始状态信息永久丢失，且无法向委托方解释
「这个状态为什么和文档里写的不一样」——因为已经看不到了。
如果这一页里恰好有未发送的草稿或未删除的残留内容，这些内容也一并消失。

**核查**

**固定顺序，不可颠倒：**

1. **先做状态检查并存档输出** —— 这一步必须在任何其他操作之前
2. **对原始文件计算哈希并记录**
3. **制作工作副本**（保留原始文件不动）
4. **在副本上做需要写入的操作**，且把操作类型记录在案

关键在于第 1 步的产物：**状态检查的输出要作为附件归档**，它是「修复前」的原始状态证据。

做完这一步之后，原始数据库就算被动了，关键信息也已经保存下来了。

<a id="section-21"></a>

#### 陷阱 2：把写模式与只读模式记混

**现象**

凭印象记住了一条命令的用途，用在了错误的位置。

**原因**

这类工具提供多个模式，**其中大部分是只读的，只有一两个会写**。

但它们的名称容易混淆——有的名字看起来像"查看"，实际含义是"检查并修复"；有的名字很短，但对应的操作很重。

**凭印象记模式的失败率很高**，因为这类工具的模式命名不一定符合直觉，而且不同版本之间还可能有差异。

**影响**

**在原始检材上执行了写操作。** 不可逆，且无法察觉（命令不会提示"你已经改动了文件"）。

**核查**

**只依赖只读模式，把它们记成一张表背下来。**

只读的那几个用途是明确的、可枚举的：

- **状态检查**（输出健康状态与是否正常关闭）—— 第一个必须做
- **一致性检查**（校验页结构）
- **页映射输出**（导出页布局，用于后续只读解析）

**破坏性的那两个直接禁用**：一个是硬修复（会删页），一个是碎片整理（会重写数据）。

除此之外，每次在副本上执行任何写操作前，先查该命令的文档确认它是只读的。

不要凭记忆，不要凭命令名的直觉。

<a id="section-22"></a>

#### 陷阱 3：修复之后才记录原始状态

**现象**

先跑了修复，然后想起来应该先记录一下原始状态，
但这时候已经查不到了。

**原因**

这就是陷阱 1 的直接后果。

修复操作会清除状态标记，**这个信息是单向丢失的**——没有任何工具能恢复它。

**影响**

「这个数据库上次是否正常关闭」这个问题变成了**无法回答**。

而这个问题在很多场景下是关键的：如果它是非正常关闭，那么数据库末尾的部分内容可能处于不一致状态，这部分数据的可信度需要降级。

**核查**

把状态检查放在工作流的第一步，而不是「想起来再做」。

具体做法：

1. 拿到文件，先算哈希
2. 跑状态检查，**把输出重定向到文件**
3. 对这个输出文件也算哈希
4. 然后才开始后续任何操作

这三步加起来不到一分钟，但它保住了一条不可再生的证据。

**顺序是唯一有效的保护。** 任何「先做别的，回头再补」的想法在这里都不成立。

<a id="section-23"></a>

### 4.2 工具选型

<a id="section-24"></a>

#### 陷阱 4：用通用数据库工具打开

**现象**

看到「这是个数据库文件」，用熟悉的通用数据库工具去打开，
结果报「不是有效的数据库」。

**原因**

这是一种专有的数据库格式，与常见的关系型数据库文件头完全不同。 两种格式的相似性只有「都是文件」，其他都不一样。

**影响**

浪费大量时间在「为什么打不开」上，并且可能误以为文件已损坏——实际上它完全正常，只是用错了工具。

**核查**

**用支持该格式的专用工具。** 判断依据：

- 该格式有自己的规范文档与专门的解析工具生态
- 工具选型时确认它支持你面对的**具体版本**——
  不同版本在页格式、压缩算法上有差异
- 遇到打不开的情况，先确认**文件是否完整**（哈希对不对、
  是否提取完整），再考虑版本兼容问题

**不要因为一个工具打不开就断定文件有问题。**
先排除工具版本与格式支持的问题。

<a id="section-25"></a>

#### 陷阱 5：忽略页级压缩

**现象**

用工具读出了记录，字段内容是一片乱码，
判断为文件损坏。

**原因**

**这个格式支持页级压缩**，较新版本默认开启。

工具支持这个数据库格式，不等于它支持这个数据库格式的压缩方式。 两者是不同的能力，缺一不可。

如果工具不处理压缩，它读出来的是压缩流的内容，自然是乱码——**但文件完全正常**。

**影响**

把完好文件判为损坏。而且这个判断一旦做出，
后续所有针对"修复"的动作都是错的（参见陷阱 1）。

**核查**

**工具选型阶段就确认压缩支持。** 具体查两件事：

1. 工具文档里是否明确支持该数据库版本的压缩方式
2. 如果不确定，用一个**已知完好**的同类文件做测试——
   能正确读出内容，说明工具的解压能力没问题

如果工具确实不支持，**不要试图手工解压**——手工处理的正确性无法验证，产生的输出不可作为证据。

应该换工具。

<a id="section-26"></a>

#### 陷阱 6：把未分配空间的字节当邮件内容

**现象**

在数据库文件里找到一段看起来像邮件正文的字节，
报告写「恢复出邮件内容 X」。

**原因**

数据库文件里的未分配空间是**曾经使用过、后来被标记为空闲的区域**。
里面确实可能残留着已删除记录的内容字节，但：

- 那段字节**可能已经被新数据部分覆盖**
- 即使没被覆盖，**字节的连续性与完整性无法保证** ——
  页内的空闲块可能只是碎片化的几段，中间有空洞
- **这些字节没有结构信息** —— 没有记录边界、没有字段定义，所谓的"邮件正文"只是看起来像

**影响**

把字节碎片当成可用的邮件内容报告出去。
这类内容一旦被对方引用，而后续复核发现无法复现，
报告的可信度会整体受损。

**核查**

**严格区分两类表述**，这是硬要求：

- **存在性（强证据）**：数据库的记录中显示某个邮箱/文件夹/条目
  曾存在，包含大小、时间等元数据。结论写「该位置曾存在邮件记录」
- **内容（弱证据）**：从未分配空间提取到字节片段，
  包含 X 特征。结论写「在文件的 Y 位置提取到 Z 字节，
  其内容特征与 W 一致，因该区域已被标记空闲且可能被部分覆盖，
  **本结论为推测性**」

**弱证据只能作为线索，不能作为内容结论。**
如果需要坐实内容，必须找到独立的完整副本：
备份、其他用户的本地副本、客户端设备、日志里的内容输出。

<a id="section-27"></a>

### 4.3 提取范围与遗漏

<a id="section-28"></a>

#### 陷阱 7：只提取数据库目录，不提取日志目录

**现象**

按数据库的常规位置提取完文件就开始分析，
报告里完全没有提到日志目录。

**原因**

该产品会维护自己的日志目录，与数据库文件在不同的位置。

这些日志记录的是数据库的维护操作：备份、检查、重启、索引操作、**以及失败的操作尝试**。

关键在于：**失败的操作会留下记录**。

如果事发前后有过针对该数据库的操作尝试——哪怕是失败的——日志里可能有线索，而数据库里完全没有痕迹。

**影响**

漏掉一个可能包含操作记录的独立证据源。

这是**提取范围不完整**，不是分析深度不够。

**核查**

**数据库目录与日志目录一起提取，缺一不可。**

在提取清单里明确列出两个位置，并分别计算哈希。
在报告里说明：

> 本次提取包含：数据库文件 N 个（路径写明，逐一计算哈希）、
> 日志文件 M 个（路径写明）、运行时配置与检查点文件。
> 提取采用只读方式，提取前对源文件计算哈希，提取后对副本计算哈希并比对。

如果因故未能提取日志目录，这必须进「取证局限」章节。
一个没被提取的证据源，在报告里等同于「不存在这个证据源」。

<a id="section-29"></a>

#### 陷阱 8：漏掉历史目录

**现象**

按当前配置指向的位置提取了数据库文件，
没有注意到还有其他目录存在。

**原因**

重建操作会生成新的标识目录，旧的目录仍然留在磁盘上。 这在历史上是常见操作的副作用：存储重组、切换到新版本、故障恢复后重建。

旧目录里的数据库可能包含**更完整或更早的内容**——特别是重建之后的那个，可能缺少重建前的某些记录。

**影响**

只拿到了数据的一个子集，而没意识到存在其他部分。
这属于「不知道自己漏了什么」，比明确知道漏了更难发现。

**核查**

**枚举目标目录下的全部子目录，不按配置猜路径。**

具体做法：列出该父目录下的**所有**子目录（不只是当前配置指向的那一个），
对每一个都：

1. 记录其名称、创建与修改时间
2. 检查是否包含数据库文件
3. 与当前使用的那个做对比（文件大小、时间范围、记录数）

在报告里产出一张表：

> 存储目录下发现 K 个标识目录，其中 1 个为当前活动库，
> K−1 个为历史残留（最早创建于 X，最晚修改于 Y）。
> 本次已对全部 K 个目录中的数据库文件进行分析。
> 历史库中包含当前库已不存在的记录 X 条（涉及时间范围 Y 至 Z）。

**这一步做与不做，报告的价值差别很大。**
做了，是完整分析；没做，是「分析了当前状态」。

<a id="section-30"></a>

#### 陷阱 9：按固定文件名搜索

**现象**

按一个从某处看来的文件名去搜索，没找到，结论写「无邮件数据」。

**原因**

**不同版本的默认文件名不同**，而且**用户可以在配置里改**。

用一个固定文件名搜索，覆盖面完全依赖于运气。

**影响**

明明有数据却报告说没有。这是提取阶段的失败，而且很难在后续被纠正。

**核查**

**递归搜索所有数据库扩展名的文件，不依赖文件名。**

具体做法：

1. 在服务器上按扩展名递归查找，得到完整文件清单
2. 每个文件都计算哈希
3. 用状态检查逐个确认它是不是有效的数据库
4. 分析时**不依赖文件名**，通过数据库内部信息确认它对应哪个邮箱

**文件名不可信，数据库内部的信息才可信。**
有些文件被改过名，但里面的邮箱信息是完整的。

<a id="section-31"></a>

#### 陷阱 10：提取前不确认磁盘空间

**现象**

直接开始提取，过程中磁盘写满。

**原因**

**单个数据库文件可能非常大**，加上日志目录、运行时文件、多个历史目录，**总量可能达到数百 GB**。

在容量规划不明的机器上直接提取，很容易在半途耗尽空间。

**影响**

提取中断，可能留下**不完整的工作副本**。
更麻烦的是：不完整副本看起来是完整的（有文件、有大小），
后续分析会基于它得出错误结论。

**核查**

**提取前评估，先算后提。**

1. 列出全部待提取文件，**统计总大小**
2. 检查目标卷的可用空间
3. 空间不足时的选择顺序：
   - 优先提取目标时段相关的文件（按文件内的时间范围筛选）
   - 完整提取日志目录（体积通常小，价值密度高）
   - 历史目录可先做文件头检查，记录元数据，暂不完整提取

在报告里写明提取策略与取舍：
`目标卷可用空间 X GB，待提取文件总大小 Y GB（K 个）。
本次完整提取 M 个；其中 N 个大文件采用按时段筛选方式提取，
筛选规则为 <规则>；未提取的文件清单与原因见附录。`

「没有提取」和「提取了但不含目标时段」是两回事，报告里要分开写。

<a id="section-32"></a>

### 4.4 邮件头的价值与报告纪律

<a id="section-33"></a>

#### 陷阱 11：忽略邮件头信息链

**现象**

从数据库里恢复出部分邮件内容，据此分析邮件流转路径。

**原因**

**每一封邮件都带有一串接收与中转记录**，记录了它经过了哪些服务器、每个环节的时间。

**这个信息链不受数据库层面的压缩或页格式影响**——它以明文形式存在于邮件的原始内容里。

也就是说，即使数据库内容恢复得不完整，只要能提取到任何一封邮件的原文，路径信息通常就是完整的。

而如果只依赖数据库结构做路径分析，在内容恢复不完整时会直接卡住。

**影响**

把最有价值的证据放在最容易被忽略的位置。
路径分析要么做不出来，要么做得残缺。

**核查**

任何一封提取到的邮件，都要完整提取原文，包括全部头字段。

提取时注意：

1. 头字段在邮件原文的**最前面**，即使正文残缺，头部通常完整
2. 时间字段可能有多个时区标注，**要逐个记录，不要统一假设**
3. 中转记录里的服务器标识，**用来构建流转图**
4. 头里的时间与数据库记录的时间**对照检查**，
   差异本身就是信息

在报告里把邮件头的分析单列一节，
并明确写出数据来源是「邮件原文头部」而不是「数据库结构」。

**这两条路径的证据强度不同，报告里要分开写。**

<a id="section-34"></a>

#### 陷阱 12：只看服务器上的数据

**现象**

分析完服务器上的数据库，报告写「已获取该邮箱的邮件数据」。

**原因**

**邮件数据是分布式的。** 同一封邮件在多处存在副本：

- 服务器上的数据库（可能被策略清理过，比如按时间自动清除）
- **用户本地的副本**（客户端软件会在本地保留一段时间）
- 归档系统里的副本
- 备份介质里的副本

**服务器上的副本不一定是完整的**——自动清理策略、时间限制、空间管理都可能导致早期邮件已不在服务器上。

而用户本地的副本可能保留了服务器上已经没有的内容，包括附件。

**影响**

把「服务器上有的」当成「全部的」。
后续对方拿出本地副本里的邮件，会反过来质疑报告的完整性。

**核查**

**把数据来源列成清单，逐个说明获取情况。**

在报告里写明：

> **数据来源清单**
>
> | 来源 | 位置 | 获取情况 | 覆盖时间范围 |
> |---|---|---|---|
> | 服务器数据库 | 路径写明 | 完整提取 | X 至 Y |
> | 历史数据库目录 | K 个目录 | 完整提取 | X 至 Y |
> | 服务器日志目录 | 路径写明 | 完整提取 | X 至 Y |
> | 用户本地副本 | 路径写明（若有访问权） | 已提取 / 未获授权 / 不存在 | — |
> | 备份介质 | — | 未获取（原因：需要 X 授权） | — |

**没有获取的来源也要列出来并写明原因。**
这样报告的边界是清楚的，委托方能判断是否需要补充授权。

<a id="section-35"></a>

#### 陷阱 13：报告不写取证局限

**现象**

报告写完发现清单就结束了。

**原因**

邮件数据还原的局限特别多，而且每一项都很实质：

- **附件往往无法恢复** —— 附件单独存储，删除后可能只剩元数据
- **已删除内容只剩字节** —— 且可能被覆盖
- **日志有覆盖周期** —— 早于某时刻的操作记录已不存在
- **客户端副本未获取** —— 需要额外授权或设备已不可用
- **未分配空间被复用** —— 部分内容永久丢失
- **加密或受保护的数据** —— 可能需要额外条件

一份不说这些的报告，读者会以为「报告里的邮件就是全部」。

**影响**

结论被过度外推。

特别是「未发现某封邮件」这句话，在不说清边界的情况下会被读成「这封邮件不存在」，而实际可能是「服务器副本已清理，本地副本未获取」。

**核查**

**「取证局限」是与「发现清单」平级的独立章节。** 逐项写清：

- **能力边界**：内容恢复到什么程度、附件的处理情况
- **覆盖限制**：日志的时间范围、清理策略
- **未获取项**：需要额外授权的数据源，逐项列出
- **推测性结论**：哪些结论基于弱证据（如陷阱 6 的字节提取）

阴性结论的写法：

> **在服务器 X 的 K 个数据库目录（N 个文件，均已完整提取）
> 及日志目录内，未发现时间范围 X 至 Y 期间涉及收件人 Y 的邮件记录。**
>
> 该结论的边界：
> - 服务器侧邮件可能因自动清理策略已不在当前库中
>   （策略：按时间清理，本库最早记录为 X）
> - 用户本地副本本次未获取（需额外授权）
> - 备份介质本次未获取（需额外授权）
> - 已删除邮件仅余字节碎片，且可能被部分覆盖
> - 部分邮件的附件无法恢复，不排除附件中含相关信息
>
> **本次结论不能推论该邮件在上述范围外不存在。**

这个模板可以直接套用到所有涉及「未发现」的结论上。
阴性发现的能力边界与操作能力是两回事——
一份把边界画清楚的阴性结论，同样是有价值的工作成果。

## 五、案例示例

<a id="section-37"></a>

### 5.1 Dirty Shutdown 状态存档与原件只读纪律

**场景**

查获一台 Exchange 2016 服务器（`digiforensics.example.com` 邮件域），镜像 `DigiForensics.dd`（raw，2 TB，NTFS 起始扇区 2048），已关机。委托方要求查明"财务部 `user01` 是否在 2024-11-10 至 11-14 期间外泄了客户清单附件"。邮箱数据库体积 180 GB。

这条路径值得先走，是因为 Exchange 的 ESE 数据库有一个**不可逆的状态**：它被修复过的瞬间，"异常关闭"这个线索就永久消失了。

修复前未固定原始文件，可能丢失本可用于分析的数据。

所以第一步不是解析、不是恢复，而是**记录状态**。

**处置过程**

**第 1 步 · 定位与版本确认**

```bash
fls -o 2048 -r -p /work/DigiForensics.dd > /work/filelist.txt
grep -iE 'Mailbox Database\.edb' /work/filelist.txt
grep -oE 'MailDB/[0-9A-Fa-f-]{36}/' /work/filelist.txt | sort -u
# 仅一个 GUID：7f3a9c2e-...  → 单数据库组，无重建痕迹
icat -o 2048 /work/DigiForensics.dd <inode-edb> > '/evidence/Mailbox Database.edb'
icat -o 2048 /work/DigiForensics.dd <inode-e01> > /evidence/E01.log
ls -lh /evidence/
```

**发现 1**：`V15` 路径结构 + `Mailbox Database.edb` 文件名 → Exchange 2013–2019（本案为 2016）。**只有一个 GUID 目录**，无数据库重建痕迹。数据库 180 GB，日志目录另有 40 GB。

第 2 步 · `/mh` 只读状态检查（存档优先）

```cmd
esentutl /mh "D:\evidence\Mailbox Database.edb" > D:\work\mh-mailbox-before.txt 2>&1
```

```
State: Dirty Shutdown
Log Time: 11/14/2024 03:47:12 PM
Last Update Time: 11/14/2024 03:41:55 PM
Format Version: 196613
Database Log Size: 41943040
```

**发现 2**：`State: Dirty Shutdown`——数据库未正常关闭。 且 `Log Time`（03:47:12）**晚于** `Last Update Time`（03:41:55）约 5 分钟。

**这说明关停前后有未回滚的修改。**

结合 Web 侧同一时段的记录（[04](server-log-web-attack-trace-reconstruction.md) 中该服务器 11-14 03:44:58 出现 1102 清日志事件），**这个时间点高度可疑**。

但 `/mh` 本身不能证明原因，只能证明状态异常。

> **★ 纪律执行**：此刻 `mh-mailbox-before.txt` 已存档。后续任何修复都会抹掉这个状态，文件必须与报告一起归档。

**第 3 步 · 复制工作副本**

```cmd
esentutl /y "D:\evidence\Mailbox Database.edb" /d "D:\work\Mailbox Database.edb" /o
certutil -hashfile "D:\evidence\Mailbox Database.edb" SHA256
certutil -hashfile "D:\work\Mailbox Database.edb" SHA256
```

```
原件 3f9a...c21d
副本 3f9a...c21d      ← 一致
```

**发现 3**：副本与原件哈希**完全一致**，副本可用。原件哈希 `3f9a...c21d` 写入报告，声明原件全程只读。

**第 4 步 · 一致性检查、修复、再次取证**

```cmd
esentutl /k "D:\work\Mailbox Database.edb"          :: 逐页校验和（只读）
esentutl /r "D:\work\Mailbox Database.edb"          :: Dirty Shutdown 转软修复（改文件）
esentutl /g "D:\work\Mailbox Database.edb"          :: 修复后再做完整性检查
esentutl /mh "D:\work\Mailbox Database.edb" > D:\work\mh-mailbox-after.txt 2>&1
certutil -hashfile "D:\work\Mailbox Database.edb" SHA256
```

```
副本(修复后) 8b2e...47aa      ← 与原件不同，证明副本已被修改，原件未动
State: Clean Shutdown
```

**发现 4**：修复使副本从 `Dirty Shutdown` 变为 `Clean Shutdown`，哈希也变了。

这验证了那条纪律的意义：若不先做副本，这个 180 GB 证据文件就被改掉了，"原本异常关闭"这个线索将永久消失。

**结论**

| 结论 | 支撑 | 强度 |
|---|---|---|
| 邮箱数据库在 11-14 03:47 非正常关闭 | `/mh` `State: Dirty Shutdown`，`Log Time` 晚于 `Last Update Time` 约 5 分钟 | **强**（原始状态已存档） |
| 关停前存在未回滚的修改 | `Log Time` 与 `Last Update Time` 的倒挂 | 强（**只说明有未回滚事务**） |
| 关停由人工作出 | 同一时段 Web 侧 `1102` 清日志事件 | 中（**两台机器的时间相关性，非因果**） |
| 关停动因是否与入侵相关 | `/mh` 不含操作者信息 | **不可判，须查 Windows 事件日志** |
| 原件未被改动 | 修复后副本哈希 `8b2e...47aa` 与原件 `3f9a...c21d` 不同 | **强（原件哈希已入报告）** |

**本节能证明**：数据库在特定时点处于未正常关闭状态、且该状态已被独立存档、原件未被任何修复动作触碰。
**本节不能证明**：关停的执行者、关停是否属于入侵链的一环、未回滚事务的内容。

**误判对照**

1. **先修复再取证，事后用记忆描述原始状态**。判据是**状态的单向性**：`Dirty Shutdown` 是**一次性可观测状态**——`/r` 一旦执行，它就永久变成 `Clean Shutdown`，没有任何后续手段能从修复后的文件里反推出"它曾经是脏的"。本案唯一能支撑该结论的证据就是第 2 步那份 `mh-mailbox-before.txt` 文本文件。**代价**：这是 Exchange 取证里最典型、也最难挽回的失误——修复后的数据库一切正常、可读、内容完整，看起来什么异常都没有，而报告里写"未发现异常"；等到委托方追问"那 03:47 为什么关了"，**已经没有任何东西可以回答了**。
2. 把 `Log Time` 晚于 `Last Update Time` 解释成"时间被篡改"。判据是**这两个字段的语义**：`Last Update Time` 是**最后一次事务提交**的时间，`Log Time` 是**日志文件最后写入**的时间——**日志写入晚于事务提交是 ESE 的正常行为**（事务提交后仍有日志刷盘、缓存、关停流程）。倒挂只说明"关停时有未回滚的事务"，不说明任何时间字段被改过。 **代价**：把时间倒挂写成"时间戳被篡改"，会把一起数据泄露案误导成一起反取证技术对抗案，**排查方向整个跑偏**，而实际上只需要去看 03:41–03:47 之间的事务日志。
3. 看到同一时段另一台机器有 `1102` 清日志，就认定两件事有因果关系。判据是**相关与因果的边界**：本案 `1102` 出现在 Web 服务器上，脏关闭出现在**邮件服务器**上，**两者只有时间相关性**。要主张因果，需要**同机证据**（该邮件服务器自身的事件日志、操作账户）或**执行关系**（同一账户在两台机器上的登录记录）。**代价**：把跨机的时间相关性写成因果，会在委托方对质时暴露——**"你的因果证据在哪"是没有答案的**，整份报告的关联分析都会被重新审视。

**按错误判据走的代价**：第 1 条踩中直接导致一条证据永久消失，且事后无法向委托方解释；第 2、3 条踩中则会让报告的分析方向偏离真实问题，**而委托方已经基于这份报告向监管或客户作出了通报**。

### 5.2 ESE 压缩导致正文为空时的证据路径切换

**场景**

同一委托的后半段。第 1 步记录完数据库状态后，委托方最关心的问题还没回答：`user01` 的邮件正文与附件到底能不能读出来。 工具能解析结构，但正文与附件字段大面积为空。

将此情形单列的原因是**"字段为空"有两种完全不同的成因**——一种是数据本来就没写进去，一种是数据在但解压不出来。

这两者决定了整份报告能不能回答"外泄了什么内容"。

**在判定成因之前，不能把空字段读成"没有附件"。**

**处置过程**

**第 5 步 · 解析与空字段成因判定**

```bash
esedbinfo "D:/work/Mailbox Database.edb"
# 表：/folders  记录数 18422
# 表：messages 记录数 2098331
esedbexport "D:/work/Mailbox Database.edb" -t messages -f csv > /evidence/messages-partial.csv
```

**发现 5**：`messages` 表共 **209 万条**记录，**结构解析正常**（记录数、`/folders` 表都可读）；但导出的记录中，`body` 与 `attachments` 字段大量为空，仅短主题非空。

**这是典型的 LZX 压缩未解表现**——工具支持 ESE 但不支持 Exchange 2016 的默认压缩。

**判定依据**：**结构层可读 + 变长字段层为空**，且空值不是"长度为 0 的合法空字段"而是"解压失败后的默认值"。

如果数据本来没写入，空字段应当表现为内容合法的空串；这里表现为"整层都空且长度分布异常一致"，指向解压而非缺失。

**第 6 步 · 转向未压缩的替代载体**

```bash
grep -iE 'MailDB/.*/Logs/.*\.log$' /work/filelist.txt | head
icat -o 2048 /work/DigiForensics.dd <inode-transportlog> > /evidence/TransportRole.log
grep -iE '发票|清单|customer|客户' /evidence/TransportRole.log | head -20
```

```powershell
Get-ChildItem 'C:\Users\user01\AppData\Local\Microsoft\Outlook' -File |
  Select-Object Name, Length, LastWriteTimeUtc
# outlook.pst  4.2 GB  2024-11-13 22:14  ★
```

**发现 6**：传输日志中检索到 11-12 至 11-14 期间多封主题含"客户清单"的邮件记录，且完整保留了 `Received:` 头（含每跳服务器名、接收时间戳、客户端 IP）。同时在 `user01` 的 Outlook 目录找到 **4.2 GB 的 `outlook.pst`**——**PST 不受 ESE 压缩影响**。

第 7 步 · 用 Received 链验证投递方向与时间真实性

```
Received: from MAIL01.corp.example.com (10.10.1.31) by MX02.example.com; Mon, 11 Nov 2024 23:14:07 +0800
Received: from DESKTOP-7H2K9.corp.example.com (10.10.3.87) by MAIL01.corp.example.com; Mon, 11 Nov 2024 23:13:55 +0800
```

**发现 7**：时间戳自上而下递减（23:14:07 → 23:13:55），符合正常投递链，**暂无伪造迹象**。

同时暴露了发件客户端的 IP `10.10.3.87` 与主机名 `DESKTOP-7H2K9`——这是数据库压缩问题下依然拿到的关键证据。

**第 8 步 · 从 PST 侧取正文与附件**

```bash
icat -o 2048 /work/DigiForensics.dd <inode-pst> > /evidence/outlook.pst
sha256sum /evidence/outlook.pst
pffexport /evidence/outlook.pst > /evidence/pst-index.csv
grep -c '客户清单' /evidence/pst-index.csv
# 27
```

**发现 8**：PST 侧索引中命中 27 条与"客户清单"相关的邮件项——正文层在 PST 这个未压缩载体上是可读的。这确认了"内容存在"，也确认了数据库侧的空字段是解压失败而非数据缺失。

**结论**

| 结论 | 支撑 | 强度 |
|---|---|---|
| 数据库侧 `body`/`attachments` 为空是**解压失败**而非数据缺失 | 结构层可读（209 万条）+ 空值分布异常一致 + PST 侧同内容可读 | **强**（跨载体互证） |
| 11-11 至 11-14 存在多封"客户清单"主题邮件 | 传输日志 + PST 索引 27 条命中 | **强** |
| 投递链时间戳未见伪造 | `Received:` 自上而下递减 23:14:07 → 23:13:55 | 中（**未逐跳核对各跳时钟**） |
| 发件端为内网主机 `DESKTOP-7H2K9` / `10.10.3.87` | 第二跳 `Received:` 头原文 | 强（**但归属主体未确认**） |
| 是否发生外发至外部域 | 传输日志检索范围内**未见外部 `Received` 跳** | 中（**限定于已检索关键词**） |
| `user01` 的主观意图 | 日志无该字段 | **不可判** |

**限定范围**：「`TransportRole.log` 已检索关键词集合（发票/清单/customer/客户）、PST 内 27 条命中项、11-11 至 11-14」。

**未覆盖**：11-10 至 11-14 之间主题不含上述关键词的邮件；**无附件或附件名不含关键词的邮件**；`user01` 以外的邮箱；**外部收件方的日志**（不在本机检材内）；PST 中已删除项的内容（需另做雕刻）。

**误判对照**

1. **把解压失败导致的空字段读成"这封邮件没有附件"**。判据是**结构层与变长字段层的分层结果**：`messages` 表 209 万条记录**结构完整可读**、`/folders` 表正常，只有 `body` 与 `attachments` 这两层为空。数据未写入时，空值会散布于各类记录；解压失败时，空值会整层一致地出现。 本案正是后者，且 PST 侧同样内容可读，**构成跨载体互证**。**代价**：这是最容易造成**反向误判**的一种错误——报告会写"未发现任何附件外发"，**给委托方一个虚假的安全结论**，而实际上这些附件只是读不出来。
2. 因为工具"不支持压缩"就停下，转而汇报"邮件内容无法取证"。判据是**检材里是否存在未压缩的等价载体**：Exchange 邮件的同一份内容会同时存在于**服务器数据库（ESE + LZX）**、**传输角色日志（明文头信息）**与**客户端 PST（未压缩或轻压缩）**。本案三条路径中两条可读，**"数据库读不出正文"从不等于"内容不可得"**。**代价**：过早收手会让委托方误以为关键证据已灭失，**从而放弃进一步排查**——而实际情况是换个载体就能拿到。
3. 看到 `Received:` 头就当作可信的时间证据。判据是**递减性检查**：本案两条时间戳自上而下**递减**（23:14:07 → 23:13:55），**这符合真实投递链的物理约束**；若出现**递增或时间倒挂**，才说明存在头注入。但要注意递减只证明"形式合理"，不证明"内容真实"——每一跳的时钟是否同步、`DESKTOP-7H2K9` 的 `Received` 头是否由客户端自己生成，都需要主机侧证据佐证。**代价**：把"形式合理"写成"已验证未篡改"，会在对方拿主机日志质疑时失去退路。

**按错误判据走的代价**：第 1 条与第 2 条叠加，会产出一份"既读不出内容、又没有做替代载体排查"的报告——**内容其实可读，取证方却交付了"不可取证"的结论**，这是专业性与可信度的双重损失。第 3 条踩中则会让委托方把一条形式上合规的邮件链当作定案依据，**而它在司法场景下不足以独立支撑真实性主张**。

### 5.3 反例 4.2 GB 的 PST 不能证明数据已经外泄

**场景**

同一委托的最后一个问题。第 8 步拿到 4.2 GB 的 `outlook.pst`，委托方看到体积就说"这么大的本地副本，说明数据早就被拉下来了"。

这条路径值得写，是因为**体积本身就是一种诱导性证据**：4.2 GB 这个数字在任何报告里都很有说服力，但它回答不了委托方真正的问题——**数据是"被拉走了"还是"本来就在这里正常工作"。**

邮件客户端本地存储大，是正常业务的常态，不是异常信号。

**处置过程**

**第 9 步 · 拉取 PST 内的邮件项分布**

```bash
grep -v '^#' /evidence/pst-index.csv |
  awk -F',' '{print $5}' | sort | uniq -c | sort -rn | head -6
# 118204  INBOX
#  41266  Sent Items
#  12038  Finance Reports
#   8814  Archive 2019
#   2206  Archive 2020
#    317  Archive 2021
```

**发现 1**：总量集中在 `INBOX` 与 `Sent Items`（合计近 16 万项），且存在多个按年命名的归档文件夹。

**这是典型的长期正常使用形态**——4.2 GB 由多年累积的正常邮件构成。

第 10 步 · 看"客户清单"相关项的分布而不是总量

```bash
grep '客户清单' /evidence/pst-index.csv |
  awk -F',' '{print $3, $6}' | sort | uniq -c | sort -rn | head -10
#   9  Finance Reports   2024-09-02
#   7  Finance Reports   2024-10-11
#   5  INBOX             2024-10-28
#   4  Sent Items        2024-11-12
#   2  Sent Items        2024-11-13
```

**发现 2**：27 条命中项分布在 5 个月、3 个文件夹中，最早一条是 2024-09-02——跨越了委托方关注的 11-10 至 11-14 时间窗。

若这 27 条是"外泄的证据"，它们不可能早于事件发生。 这直接否定了"这些内容是后来被集中拉取进来的"这一推断。

**第 11 步 · 检查是否存在大体积异常附件**

```bash
grep '客户清单' /evidence/pst-index.csv |
  awk -F',' '$4+0 > 10485760 {print $1, $4}' | head
# （无输出）
```

**发现 3**：**没有任何一条相关邮件的附件超过 10 MB**——不存在"一次性打包外传"的形态特征。

**第 12 步 · 用同步状态判断本地副本性质**

```powershell
Get-ChildItem 'C:\Users\user01\AppData\Local\Microsoft\Outlook' -File |
  Select Name, Length, LastWriteTimeUtc
# outlook.pst  4.2 GB  2024-11-13 22:14
```

**发现 4**：**单个 `.pst` 文件、无 `.ost`**——`.ost` 是服务器邮箱的本地缓存，`.pst` 是**长期归档副本**。

这一形态本身说明该副本是"用户主动保留的本地副本"，而非同步产生的缓存。

**结论**

| 结论 | 支撑 | 强度 |
|---|---|---|
| PST 的 4.2 GB 由多年正常邮件累积构成 | 16 万项集中于 INBOX/Sent，另有 4 个年度归档目录 | 强 |
| 27 条相关邮件早于委托时间窗（最早 2024-09-02） | 时间分布跨 5 个月、3 个目录 | **强（直接否定"事后拉取"）** |
| 未发现集中外传的形态特征 | 无单条附件 > 10 MB | 中（**仅覆盖已命中的 27 条**） |
| PST 是本地长期归档副本 | 单 `.pst`、无 `.ost` | 中（**未确认创建者与用途**） |
| `user01` 是否实际外发过客户清单 | 传输日志与 PST **均无外部投递记录** | **在本检材范围内未见证据** |

**限定范围**：「`outlook.pst` 单个文件、27 条"客户清单"命中项、附件体积阈值 10 MB」。

**未覆盖**：**PST 内部已删除项**（需雕刻未分配空间）；**其他用户目录**下的 Outlook 数据；**外部邮件系统**的投递记录；2024-09-02 之前的邮件（**若已被 Exchange 保留策略清理则不可查**）；**关键字未覆盖的邮件主题与附件名**。

**误判对照**

1. **把 PST 体积当作异常指标**。判据是**内容的年代分布**：本案 4.2 GB 的主体是 INBOX 与 Sent Items 的 16 万项历史邮件，`Archive 2019/2020/2021` 三个年度目录都在列——"大"是多年正常使用的必然结果，不是被批量拉取的特征。真正有判别力的是**时间分布**：27 条相关项横跨 5 个月，**最早的早于事件窗**。**代价**：把体积写成"数据已被大规模拉取"，会让委托方对内网员工产生**没有证据支撑的怀疑**，而这条结论在任何一个数据分布图上都会被立刻推翻。
2. **用"没有大附件"来证明没有外泄**。判据是**外泄形态的多样性**：批量打包会留下大附件，但逐封转发、转发到外部草稿箱后同步、或外发为普通大小附件，都不会产生大文件。本案 10 MB 的阈值只覆盖了 27 条命中项，"无大附件"是这 27 条的属性，不是整体行为的排除。**代价**：把一条不充分的阴性证据写成排除性结论，恰好在"没有大附件"这种最容易被攻击者规避的维度上给出错误的安全感。
3. 把"在本检材范围内未见外部投递记录"写成"未发生外泄"。判据是**证据载体的边界**：服务器传输日志记录的是**经过本服务器**的投递；外部 MTA 的日志、收件方邮箱、外部归档服务都不在这份检材里。**外泄行为的终点在本机之外。** **代价**：这是最难纠正的一种错误表述——它读起来严谨、有范围限定，但在引用时极易被简化成"没有外泄"，而一旦外部配合方提供记录推翻它，报告的"限定范围"不会随之被引用，**只有结论会被记住**。

**按错误判据走的代价**：本条的意义在于示范**阴性结论的正确写法**。委托方问的是"是否外泄"，正确回答不是"没有"也不是"无法判断"，而是——"在本机传输日志与 `user01` 的 PST 中，未检索到 11-10 至 11-14 期间将客户清单附件投递至外部域的记录；27 条相关邮件的时间分布横跨 2024-09-02 至 11-13，早于事件窗，不支持事后集中拉取。未覆盖范围包括外部 MTA 与收件方侧记录、未命中关键字的邮件、以及 PST 内已删除项。" 这样的回答既回答了问题，又不会被任何一侧的复核推翻。

## 七、命令速查

```cmd
:: ===== 第 1 步：定位（Linux 侧，注意文件名随版本变化）=====
:: fls -o 2048 -r -p /work/DigiForensics.dd > /work/filelist.txt
:: grep -iE 'Mailbox Database\.edb|Store[0-9]+\.edb|MDB\.edb' /work/filelist.txt
:: grep -oE 'MailDB/[0-9A-Fa-f-]{36}/' /work/filelist.txt | sort -u   :: 多 GUID = 曾重建数据库
:: icat -o 2048 /work/DigiForensics.dd <inode> > /evidence/Mailbox Database.edb

:: ===== 第 2 步：★ /mh 只读状态（必须先存档，修复后就没了）=====
esentutl /mh "D:\evidence\Mailbox Database.edb" > D:\work\mh-before.txt 2>&1
:: 关注：State（Clean/Dirty Shutdown）、Log Time vs Last Update Time、Format Version
:: Dirty Shutdown = 未正常关闭，是结论不是故障

:: ===== 第 3 步：★ 复制工作副本（绝不直接对原件操作）=====
esentutl /y "D:\evidence\Mailbox Database.edb" /d "D:\work\Mailbox Database.edb" /o
certutil -hashfile "D:\evidence\Mailbox Database.edb" SHA256 > D:\work\hash-original.txt
certutil -hashfile "D:\work\Mailbox Database.edb" SHA256     > D:\work\hash-copy.txt
fc /b D:\work\hash-original.txt D:\work\hash-copy.txt      :: 必须一致

:: ===== 第 4 步：校验与修复（★ 只在副本上）=====
esentutl /k "D:\work\Mailbox Database.edb"    :: /k = Checksum，逐页校验和（只读）
esentutl /g "D:\work\Mailbox Database.edb"    :: /g = Integrity，完整性检查（只读）
esentutl /r "D:\work\Mailbox Database.edb"    :: /r = Recovery 软修复（★ 改文件；Dirty Shutdown 的标准处置）
esentutl /g "D:\work\Mailbox Database.edb"    :: ★ 官方建议：先 /r 再 /g
esentutl /mh "D:\work\Mailbox Database.edb" > D:\work\mh-after.txt 2>&1
certutil -hashfile "D:\work\Mailbox Database.edb" SHA256     :: 修复后哈希必变，证明原件未动
:: ★ 取证禁用：/p（破坏性 Repair，会删页丢数据）与 /d（碎片整理，重写全库）

:: ===== 第 5 步：解析（★ 选型前先确认支持 LZX 压缩）=====
esedbinfo "D:/work/Mailbox Database.edb"
esedbexport "D:/work/Mailbox Database.edb" -t messages -f csv > /evidence/messages.csv
:: 记录数正常但正文/附件全空 = 压缩未解，换工具而不是反复重试

:: ===== 未分配页与关键字（★ 与 NTFS 同理，位置在数据库文件内部）=====
blkls -o 2048 /work/DigiForensics.dd > /work/unalloc.raw
foremost -i /work/unalloc.raw
strings -n 8 /work/unalloc.raw | grep -iE '发票|合同|客户清单'
```

```powershell
# ===== 客户端 PST/OST（★ 不受 ESE 压缩影响，常能完整导出附件）=====
Get-ChildItem 'C:\Users\*\AppData\Local\Microsoft\Outlook' -Recurse -File -ErrorAction SilentlyContinue |
  Select-Object FullName, Length, CreationTimeUtc, LastWriteTimeUtc

# ===== Exchange 传输日志（★ 比 .edb 易读，含完整 Received: 头）=====
Get-ChildItem 'C:\Program Files\Microsoft\Exchange Server\V15\TransportRoles\Logs' -File `
  -ErrorAction SilentlyContinue | Select-Object Name, Length, LastWriteTimeUtc |
  Sort-Object LastWriteTimeUtc -Descending | Select-Object -First 20
Select-String -Path 'C:\...\TransportRoles\Logs\Role_*.log' -Pattern 'Subject:' |
  Select-Object -First 20 Line

# ===== 版本与角色确认 =====
Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Exchange Server\V15\Setup' -ErrorAction SilentlyContinue |
  Select-Object ProductVersion, Role, ActiveDirectoryRole
Get-Service -Name 'MSExchange*' | Select-Object Name, Status, StartType

# ===== ★ Received: 链判读 =====
# 栈是倒序的（RFC 5321 §4.4：接收方前插）：
#   自上而下 = 收件方 → 发件方，时间戳递减 = 正常
#   自下而上 = 发件方 → 收件方，时间戳单调递增 = 正常
# 真正的异常：自下而上读时出现时间戳回退，或时钟跳变过大。
```
