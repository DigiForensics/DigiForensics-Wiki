# SIM 卡 / UICC 的读取与取证分析

> 原文链接：[DigiForensics Wiki · 在线阅读](https://www.digiforensics.cn/wiki/mobile-sim-sim)

<a id="section-1"></a>

## 一、概述

SIM 卡是移动设备里**容易被忽视、但单件信息密度较高**的证物。

它不是"存储通讯录的小芯片"，而是一张遵循 GSM 11.11 标准的**智能卡（smart card）**。

智能卡在网络侧的身份是唯一凭证——没有它，手机连不上任何基站。运营商必须靠它完成鉴权，于是它得把三件事存下来：这张卡属于哪个国家、哪家网络、哪个用户，以及最近一次注册到哪个位置区。

这份清单是运营商在网络侧写下来的，不是用户能编辑的。

**没有把它纳入检材会怎样**：位置类结论会失去一条来自卡侧的独立旁证。手机本机的定位缓存，应用能覆盖，系统日志能清理。而 SIM 卡上的位置值由网络侧驱动写入，用户正常操作清不掉。

只有手机本机数据时，"这台设备当时在哪个区域"往往只有一个来源。SIM 卡数据一进来，整个结论的强度就变了。

**在取证流程中的位置**：本篇属于**独立的证据线**，与设备取证平行，不从属于它。

特点是**受设备状态影响较小**。手机锁屏、加密、应用数据全在 FBE 密钥后面，SIM 卡照样能读。设备侧全面受阻的时候，这常常是可用的一条路径。

它同时是**身份关联的枢纽**。IMSI 与 ICCID 是把卡的记录、手机本机的账号、流量会话串成同一个人的关键标识。

**SIM 卡取证的三个特点**：

1. **物理尺寸极小，结构化程度高**。25mm × 15mm 的卡片里装着几十个结构化文件，涵盖身份标识、网络参数、联系人、短信，以及最后一次注册的位置区。
2. **它是"运营商视角的设备快照"**。手机本机日志可能被用户清理、可能被应用覆盖，但卡内位置值由网络侧驱动写入，用户无法正常清除——这使它成为位置类证据里可靠度较高的一类。**但它只有一个值，没有历史**，所以"快照"这个词比"轨迹"准确。
3. **它只反映"插卡的那张卡"，不反映设备全貌**。eSIM、双卡双待、换卡换机都会让 SIM 卡证据与设备证据脱节，必须与其他工件交叉验证。

涉及的证据形态里，有几个标识符必须按原样写进报告：

| 形态 | 具体位置 | 结构特征 |
|---|---|---|
| 物理载体 | UICC 卡的 8 触点（ISO/IEC 7816） | **C4 是 I/O 数据通道，剪掉就读不出任何数据** |
| 文件树 | `MF`（`3F00`）→ `ADF`（USIM 用 AID `A0000000871004`）→ `DF` → `EF` | 树形，遵循 ISO 7816-4 |
| 应用目录 | USIM 应用 AID = `A0000000871004`，SIM 应用 AID = `A0000000871002` | 现代 4G/5G 读的是 USIM，不是老的 SIM |
| 身份标识 | `ICCID`（卡号）、`IMSI`（用户标识）、`MSISDN`（手机号） | 归属判断与交叉关联的入口 |
| 网络标识 | `MCC` / `MNC` / `LAI` / `TMSI` | **LAI = 小区 ID + LAC**，位置分析的载体 |
| 联系人与短信 | `EF` 下的联系人文件、短信文件（SMS 在 `SIM`/`USIM` 应用下） | 读取受访问保护约束 |
| 访问保护 | `PIN` / `PUK` / `CHV` | **错误次数超限会永久锁卡**——不可逆，见 [4.2](#section-24) |
| 物理转储 | 卡片的完整物理镜像 | 用于留存与复核，见 [3.7](#section-17) |

这张卡属于哪个国家、哪家运营商、哪个用户、最后一次注册到哪个位置区，卡内联系人与短信，以及这张卡与手边这台设备是否匹配。

用户用这张卡做过什么。它只记录卡侧状态，不记录使用行为。也答不了**精确位置**——LAI 到小区，不到坐标。答不了持卡人身份，IMSI 属于一个号段，不是一个人。基站侧的通话与上网记录同样答不了，**那属于运营商侧数据，需另行授权调取，不在卡上**。

**本文不做的事**：不提供 PIN/PUK 的爆破或绕过方法。**错误尝试次数超限会永久锁卡**——这既是技术事实，也是法律边界：解锁必须由有权知道密码的人完成，或在有明确授权的前提下进行，并遵循最小化原则。**不做卡的克隆或复制**，涉及他人通信身份，性质远重于数据取证。

**读者前提**：需要 GSM 网络的基本概念（基站、小区、鉴权）、ISO 7816 的分层文件模型，以及硬件操作能力（读卡器选择、触点识别）。工具只需一支支持 USIM 的读卡器与对应软件。

建议先读 [4.2 解锁操作](#section-24)——该节涉及本篇唯一一类不可逆操作。其余操作出错尚可补救，这一项不能。

## 二、核心原理

<a id="section-3"></a>

### 2.1 UICC 与 SIM 的关系

严格说，手机里插的是 **UICC**（Universal Integrated Circuit Card，通用集成电路卡），"SIM 卡"是通俗叫法。UICC 是物理载体，上面可以运行多个应用，其中之一是 **SIM**（Subscriber Identity Module，用户身份模块）。

```text
UICC（物理卡）
 ├── SIM（GSM 应用）      ← 2G/3G 通用
 ├── USIM（UMTS 应用）    ← 3G/4G 通用，文件名为 USIM
 ├── USIM2（第二张 USIM） ← 双卡设备
 └── 其他应用（出行卡、银行卡等）
```

这个区分有实际意义：现代 4G/5G 网络读的是 USIM 应用，不是老的 SIM 应用。

工具在读取时先读 ATR 判断卡内有哪些应用，再按 AID 逐个 SELECT。

`3G00` 与 `2G00` 不是文件 ID，而是某些工具对 AID 的简写（分别指 USIM 与 SIM 应用）。标准的 AID 是：

| 应用 | AID |
|---|---|
| SIM（GSM） | `A0000000871002` |
| USIM | `A0000000871004` |

SELECT 之后，`DF(GSM)` 与 `DF(USIM)` **都挂在 `7F20` 下**，靠当前选中的 AID 区分看到的内容。

所以**读卡工具必须支持 USIM**。只支持老 SIM 的工具会读不到现代字段（`6FE3` EPSLOCI、`6F08`/`6F09` 密钥等），或者只能读到 GSM 时代的 `KC`。

<a id="section-4"></a>

### 2.2 物理规格与针脚定义

| 项目 | 规格 |
|---|---|
| 早期全尺寸卡 | 85mm × 54mm × 0.76mm |
| 标准卡（ID-1） | **25mm × 15mm × 0.76mm** |
| 微型卡（ID-000） | 15mm × 12mm |
| 卡端 | **8 个触点**（ISO/IEC 7816 定义） |
| 工作电压 | 1.8V / 3.0V（由复位应答中的电压指示字节决定） |

ID-1 卡的 8 触点功能如下，**取卡时按触点排布是唯一的物理线索**：

| 触点 | 名称 | 功能 |
|---|---|---|
| C1 | VCC | 供电（1.8V 或 3.0V） |
| C2 | RST | 复位 |
| C3 | CLK | 时钟 |
| C4 | **I/O** | **数据双向通道** |
| C5 | VPP | 编程电压（现代卡常悬空） |
| C6 | VEE | 地 |
| C7 | RST2 | 第二复位（备用） |
| C8 | CLK2 | 第二时钟（备用） |

物理截取 SIM 卡的常见做法是从手机中取出卡，剪成小片保留触点。

剪掉了 C4（I/O），卡就读不出任何数据——**这是 SIM 取证常见的硬件级失败原因。** 剪之前必须确认数据触点保留。

<a id="section-5"></a>

### 2.3 层级文件系统

SIM 卡的内部文件是**三层树形结构**，遵循 ISO 7816-4：

```text
MF（Master File，主文件，3F00）  ← 根
 ├── DF（Dedicated File，专用文件）  ← 目录
 │    ├── EF（Elementary File，基本文件）  ← 数据实际存放处
 │    └── DF（可嵌套）
 └── EF
```

常见的专用文件（DF）：

| DF | 文件 ID | 父目录 | 用途 |
|---|---|---|---|
| `EF(DIR)` | `2F00` | MF | UICC 上的**应用目录**，列出卡内装了哪些应用 |
| `DF(GSM)` | `7F20` | **MF** | GSM 应用根目录（SIM 与 USIM 各自的 GSM 分支） |
| `DF(TELECOM)` | `7F10` | **MF** | 电话号码簿与短信等业务文件的父目录 |
| `DF(PHONEBOOK)` | `5F3A` | **DF(TELECOM)** | 联系人目录（USIM 的 PBR 增强结构） |
| `DF(MULTIMEDIA)` | `5F3B` | **DF(TELECOM)** | MMS 目录 |

> `7F10` 和 `7F20` 是 MF 下的平级兄弟，不是父子。 这一点写错会直接导致 SELECT 路径失败：
>
> ```text
> MF 3F00
>  ├── 7F10 DF.TELECOM
>  │    ├── 5F3A DF.PHONEBOOK   （USIM 增强电话簿，内含 4F30 EF.PBR）
>  │    ├── 6F3A EF.ADN
>  │    ├── 6F3B EF.FDN
>  │    └── 6F3C EF.SMS
>  ├── 7F20 DF.GSM
>  │    ├── 6F07 EF.IMSI
>  │    ├── 6F20 EF.Kc        （GSM 侧的 8 字节密钥）
>  │    ├── 6F30 EF.PLMNsel
>  │    └── 6F7E EF.LOCI
>  └── 2FE2 EF.ICCID          ← 注意：ICCID 直接挂在 MF 下，不在上面任何一个目录里
> ```
>
> 完整路径要写全三段：`3F00:7F10:6F3C` 才是 `EF(SMS)` 的定位。写成 `3F00:7F20:6F3C` 会返回 `6A82`（文件不存在）——这是排查方向，不是卡损坏。
>
> **另一层容易混的地方**：USIM 也是一个应用（ADF），选中后它自己有一套根目录，里面同样有 `7F20` 分支。SIM 应用的 `7F20` 和 USIM 应用的 `7F20` 文件 ID 相同、内容不同，靠 SELECT 的 AID 区分。所以工具显示「`7F20` 下是 SIM 还是 USIM 的文件」取决于当前选中的应用，这是正确行为。

EF 按访问结构分四类，取证价值完全不同：

| 类型 | 结构 | 特点 | 取证价值 |
|---|---|---|---|
| **Transparent** | 固定长度 | 固定字节数，读一次全出 | **高**，ICCID / IMSI / PLMN / 位置值都在这类 |
| **Linear fixed** | 线性定长记录 | 每条记录等长 | **高**，ADN/FDN/SMS 属此类，偏移可算 |
| **Cyclic** | 循环记录 | 覆盖写，只留最近 | **中**，LDN 只保最后一次 |
| **TLV / BER** | 变长 TLV | 自描述长度 | 中，配置类参数如 `6F38` UST、`6F4E` 等能力配置 |

**结构类型本身是取证判据**：知道一个 EF 是 linear fixed 还是 cyclic，就知道它的**记录数与单条偏移怎么算**、**哪些位置是空闲槽位**（linear fixed 的空闲记录通常是 `FF` 填充，可据此判断"曾经有过多少条"）。

<a id="section-6"></a>

### 2.4 标识符体系：ICCID / IMSI / MSISDN

这是最容易混淆的一组。**三者完全不同，取证时必须分开记录。**

| 标识 | 全称 | 长度 | 存哪 | 能否唯一定位设备 |
|---|---|---|---|---|
| **ICCID** | Integrated Circuit Card ID | 19–20 位 | 卡内透明文件 | 否，只是卡序列号 |
| **IMSI** | International Mobile Subscriber Identity | 15 位 | SIM/USIM 透明文件 | 是，**全球唯一的用户身份** |
| **MSISDN** | Mobile Subscriber ISDN Number | 号码 | 运营商侧为主 | 否，且**卡上未必有** |

**ICCID 的结构**（以 `89 91 10 1200 00 320451 0` 为例）：

```text
89 91 10 1200 00 320451 0
│  │  │  │    │  │      └─ Luhn 校验位（1 位）
│  │  │  │    │  └──────── 卡序列号（6 位）
│  │  │  │    └─────────── 交换配置码（2 位）
│  │  │  └──────────────── 生产年月 YYYYMM（4 位）
│  │  └─────────────────── 发行方标识号（2 位）
│  └────────────────────── 国家码（2 位）
└───────────────────────── 主行业标识（MII，2 位）
```

前 7 位（MII + 国家码 + 发行方标识）组成 **IIN**（Issuer Identification Number）。

IMSI 的结构：

```text
MCC（3 位） + MNC（2–3 位） + MSIN（其余位数）
│       │          └─ 用户号码，与手机号不同
│       └───────────── 移动网络代码
└───────────────────── 移动国家码
```

IMSI 与手机号（MSISDN）是**两个独立标识**。用户可以换号不换卡，也可以补卡不改号。所以：

- **不能用 IMSI 直接查手机号**，必须通过运营商的 HLR 查询（需授权）
- IMSI 有 15 位，但早期网络存在 14 位的遗留格式，解析时不要假设定长

<a id="section-7"></a>

### 2.5 网络标识：MCC / MNC / LAI / TMSI

这组参数是 SIM 卡上**位置取证的核心**。

| 标识 | 全称 | 含义 |
|---|---|---|
| **MCC** | Mobile Country Code | 3 位国家码（中国 = 460） |
| **MNC** | Mobile Network Code | 2–3 位网络码 |
| **LAI** | Location Area Identity | MCC + MNC + LAC，共 5–6 位 |
| **TMSI** | Temporary Mobile Subscriber Identity | 临时身份，**每次开机重新分配** |
| **RAI** | Routing Area Identity | LAI + Routing Area ID，粒度更细 |

LAI 的取证机制里有一个必须先纠正的误解。

SIM/USIM 卡上不保存 LAI 历史列表，只保存「最后一次」的位置。 这一族文件都是单值透明文件，**每个接入域一个**，覆盖写：

```text
EF(LOCI)  '6F7E'  11 字节  transparent   电路域（CS）
 ├─ 1–4    TMSI（4 字节，按 TS 24.008 编码）
 ├─ 5–9    LAI（5 字节）
 ├─ 10     RFU（GSM 11.11 记为 TMSI TIME）
 └─ 11     Location update status

EF(PSLOCI) '6F73'  14 字节  transparent   分组域（PS）
 ├─ 1–4    P-TMSI
 ├─ 5–7    P-TMSI signature value（3 字节）
 ├─ 8–13   RAI（6 字节 = LAI 5 + RAC 1）
 └─ 14     Routing Area update status

EF(EPSLOCI) '6FE3'  18 字节  transparent   EPS 域（LTE，USIM 侧）
 ├─ 1–12   GUTI（12 字节，取自 TS 24.301 的 EPS mobile identity 部分）
 ├─ 13–17  Last visited registered TAI（5 字节）
 └─ 18     EPS update status
```

LAI 那 5 字节不是「MCC 3 + MNC 2 + LAC 2」按字节平铺，而是三个标识的**紧凑数字打包**：MCC 占 2 字节半、MNC 占 1 字节半（末位按 MNC 位长补 `F`）、LAC 占 2 字节，字节内是**数字 BCD、低半字节在前**。所以「460-00 + LAC 2A10」在文件里占 5 字节而不是 7 字节。TAI 结构同理，是 MCC + MNC + TAC 的同样打包。

> **必须记住的否定性事实：卡上没有"位置历史列表"。**
> 「关机重开机不必扫频、只遍历卡上 LAI 列表逐一问询」这个说法在**终端侧的缓存/内存优化**层面成立，
> 但那**不是卡上存着多条记录**。卡上只有一个当前值，**每次位置更新是覆盖写入**。
> 任何声称"从 SIM 卡读出了 LAI 历史"的结果，**数据一定来自终端或网络侧，不是卡本身**。

两个取证特性直接由这个结构推出来：

1. **覆盖写 → 卡上没有位置历史**。想知道"这台卡去过哪些地方"，卡本身答不了，需要终端日志（基站信息缓存、Cell ID 记录）或运营商侧数据
2. **写入由网络侧驱动 → 用户无法正常清除**。但"无法清除"只对当前值成立

**仍然必须理解的局限**：LAI 精度只到"位置区"级，一个位置区可能覆盖整个城市的一片区域。**LAI 不是 GPS 坐标**，详见 4.3。

**TMSI 的取值有独立价值**：它在每次开机时重新分配。若设备关机后再未启动，TMSI 是陈旧的；若设备一直运行，TMSI 可能仍然有效——**但同样地，卡上只有当前这一份，没有历史**。

<a id="section-8"></a>

### 2.6 访问保护：PIN / PUK / CHV

SIM 卡的访问控制机制，以及**必须严格遵守的操作红线**：

| 机制 | 长度 | 尝试上限 | 失败后果 |
|---|---|---|---|
| **PIN**（CHV1） | 4 位 | **3 次** | 卡被锁定，需 PUK 解锁 |
| **PUK**（CHV2） | 8 位 | **10 次** | **卡永久损坏，需更换** |
| **PIN2** | 4 位 | 3 次 | 需 PUK2 解锁 |

这张表是本篇的操作约束：

> PUK 连错 10 次，SIM 卡会永久失效（bricking）。这不是软件锁定，是芯片级熔断，运营商也无法恢复。
>
> 这意味着：**在授权范围不明确时，绝不能尝试 PIN 解锁。** 三次错误尝试本身就可能造成不可逆后果——如果委托方手上没有 PUK，这张卡就废了。

正确做法，按这个顺序：

1. **先确认授权范围**（见 4.2），书面确认是否允许解锁
2. **优先使用卡内已有的可读数据**——即使不解锁，很多 Transparent 文件的公开部分仍可读取（ICCID 不需要 PIN）
3. **如果委托方能提供 PUK 且明确授权**，再进行尝试，并记录每次尝试

**不要做的事**：写脚本暴力枚举 PIN。4 位 PIN 只有 10000 种，但在 3 次尝试限制下毫无意义——平均要试 5000 次才有一次命中，而卡只给你 3 次。**本文不提供任何绕过尝试次数限制的方法**：这类手段在多数司法辖区属于破坏访问控制的违法行为，即便技术上可行也不应实施。本篇只讨论**在有明确授权的前提下，如何用最少次数完成合法解锁**。

<a id="section-9"></a>

### 2.7 eSIM 与物理 SIM 的差异

现代设备越来越多用 **eSIM**（嵌入式 SIM，UICC 形态的芯片直接焊在主板上，或以封装形式存在）。

取证上的差异是根本性的：

| 维度 | 物理 SIM | eSIM |
|---|---|---|
| 可否取出 | 可取出 | **不可取出** |
| 取证方式 | 读卡器直接读 | 只能从设备侧读 eSIM 管理数据 |
| 换卡后 | 旧卡留存，可独立分析 | 旧配置可能被覆盖 |
| 主要风险 | 物理丢失 | 与主板绑定，设备销毁即不可恢复 |

**eSIM 的取证路径**目前主要靠这几条：

- 设备系统层暴露的 eSIM 配置（Android 的 `euicc` 相关服务、iOS 的 `CoreTelephony` 调试接口）
- 部分厂商的诊断/工程模式
- 运营商侧的 eSIM 平台记录（需运营商配合）

也就是说，eSIM 场景下，SIM 卡取证退化为设备取证的一个子任务，没法像物理卡那样独立获取。

## 三、操作步骤

<a id="section-11"></a>

### 3.1 硬件准备与读卡器选择

**必备器材**：

| 器材 | 规格要求 | 说明 |
|---|---|---|
| SIM 读卡器 | 支持 ISO 7816，支持 1.8V/3.0V 自动切换 | 便宜的 USB 读卡器常不支持 3.0V |
| SIM 卡座 | 带金属压片，接触可靠 | 避免松动导致间歇性读失败 |
| 防静电袋 | — | 防止静电损坏 |
| 相机 | 带微距 | 全程拍照记录 |
| 标签 | 编号 + 日期 | 封存标识 |

读卡器选择盯三个指标：

- **必须支持 UICC 而非只支持旧 SIM**。所谓"GSM 手机读卡器"往往是老式，只读 2G 应用
- **1.8V / 3.0V 双电压**。现代 4G USIM 多为 1.8V，老卡是 3.0V
- **接触式（而非 NFC）**。手机用 NFC 模拟读取的方案兼容性差，且不能保证稳定

取卡流程每一步都要拍照：

```text
1. 记录设备开机状态（若设备在开机，先拍照屏幕）
2. 关机 → 取 SIM 卡托
3. 拍照：卡托在设备中的位置
4. 取出卡 → 立即拍照：卡正反面，ICCID 可见
5. 装入读卡器 → 拍照：连接方式
6. 开始读取
```

**注意**：很多设备在关机状态下取卡会触发"卡未被正确移除"提示，但这不影响卡的电芯供电状态。若设备在开机状态取卡，部分机型会短暂给卡断电，影响数据完整性——**关机取卡是更安全的做法**。

<a id="section-12"></a>

### 3.2 判定是否需要 PIN 解锁

读卡的第一件事是**评估锁定状态**，不是直接尝试解锁。

```bash
# 用 SIM 工具读取卡状态（示例工具名为通用占位）
sim_read --reader /dev/ttyUSB0 --info
```

典型输出：

```text
ATR: 3B 16 94 7E 23 01 00 00 00 00 00 00 00 00 00
Card state: LOCKED (PIN required)
Applications: USIM (3G00)
```

**判定逻辑**：

| ATR / 状态 | 含义 | 行动 |
|---|---|---|
| 无 ATR 或全 FF | 读卡器接触不良 / 卡已损坏 | 检查硬件，不要归因于 PIN |
| ATR 正常 + 状态 LOCKED | 需要 PIN | **先确认授权**，再决定 |
| ATR 正常 + 状态 READY | 无需 PIN | 直接读全部文件 |
| ATR 正常 + 状态 BLOCKED | 已锁死 | 只能 PUK，且记录为状态事实 |

这里有个必须分清的事：**"卡锁了"和"读卡器接触不好"是两回事。**

前者 ATR 正常，后者 ATR 是全 `FF` 或全 `00`。

两种情况的现象都是"读不出数据"，但一个能解锁，一个要换硬件。

<a id="section-13"></a>

### 3.3 提取基础标识信息

不需要 PIN 就能读到的信息，优先提取。表内标为 READ PIN 的文件即使卡未锁定也可能需先验证 CHV1，实际以工具返回为准：

| 文件 | 文件 ID | 内容 | 访问条件 |
|---|---|---|---|
| EF(ICCID) | `2FE2` | 卡序列号，**在 MF 下**（SIM 与 USIM 应用共用这一个） | 无需 PIN |
| EF(SPN) | `6F46` | 运营商名称（`1 至 17` 字节，首字节是显示条件） | 无需 PIN |
| EF(Language Preference) | `6F05` | 语言偏好；`2F05` 是扩展语言偏好（ELP） | 无需 PIN |
| EF(PLMN Selector) | `6F30` | 用户可控 MCC + MNC | 无需 PIN |
| EF(UST) | `6F38` | USIM 服务表：卡**具备**哪些服务 | READ PIN |
| EF(LOCI) | `6F7E` | 最后一次位置区信息 | READ PIN |
| EF(Keys) | `6F08` / `6F09` | 鉴权与完整性密钥 | **NEVER，任何条件下都不返回** |
| EF(EST) | `6F56` | 已启用服务表：这些服务当前是否**生效** | READ PIN |

> **四个易错点**：
> ① PLMN Selector 是 `6F30`。 `2FE3` 不是标准 USIM EF ID。
> ② `6F38` 是 UST，`6F56` 是 EST，两者不是一回事。 UST（USIM Service Table）回答"卡支持什么"，EST（Enabled Services Table）回答"哪些当前启用"——**FDN 是否真的生效要看 EST，不是看 UST**。很多工具把这两张表混报，报告里必须写清是哪一张。
> ③ `EF(Phase Identification)` 是 `6FAE`，但它不能用来判断"这是 SIM 还是 USIM"。 它的取值只有 `01`（Phase 1）、`02`（Phase 2）、`03`（Phase 2+），指的是 GSM 规范演进阶段，与应用类型无关。判断是不是 USIM 应用，要看 ATR、AID、以及 `6F38` / `6F60` 这类 USIM 专属文件是否存在。
> ④ ICCID 在 MF 下，不在 USIM 应用里。 `2FE2` 在 SIM 应用和 USIM 应用下读到的**是同一个文件**——把它写成"USIM 是 `6FE2`、SIM 是 `2FE2`"是凭空构造的差异，`6FE2` 不是 ICCID 的文件 ID。

```bash
# 读取 ICCID（USIM 应用，文件 ID 2FE2）
sim_read --select 3G00 --file 2FE2 --decode iccid

# 读取 PLMN 选择器 → 得到 MCC / MNC（6F30，不是 2FE3）
sim_read --select 3G00 --file 6F30 --decode plmn
# 典型输出：MCC=460  MNC=00  → 中国移动
```

**输出示例**：

```text
ICCID: 89860NXXXXXXXXXXX
  MII      : 89
  Country  : 86  (中国)
  Issuer   : 00
  Issued   : 2105  (2021-05)
  Serial   : XXXXXX
  Checksum : 7   (Luhn 校验通过)

PLMN: 460-00  →  中国移动
```

取证价值判断有三个方向：

- ICCID 的"发行方标识"和"生产年月"能暴露卡的来源——如果是境外代工卡、或者是与设备型号不匹配的卡，值得深挖
- **MCC/MNC 与设备 IMEI 的国家码不一致** → 提示"换卡使用"或"设备来源异常"的可能，可作为涉毒、涉诈案件的切入方向之一
- **ICCID 的 MII 前两位不是 89** → 这不是标准电信卡，可能是其他类型的智能卡（银行卡、公交卡）被误插

<a id="section-14"></a>

### 3.4 提取联系人与拨号记录

联系人存在 SIM 应用的记录型文件里，**大多数情况下需要 PIN**。

**先说清楚哪些是标准文件、哪些不存在**——SIM 的文件体系是封闭的，凭印象写出「已接来电」「未接来电」这类文件名是最常见的错误来源。

| 文件 | 文件 ID | 内容 | 取证注意 |
|---|---|---|---|
| EF(ADN) | `6F3A` | 缩位拨号号码（卡内存储的联系人） | 标准文件，记录型，长度固定 |
| EF(FDN) | `6F3B` | 固定拨号号码 | **受 PIN2 保护**；启用 FDN 后不在表内的号码不允许拨出 |
| EF(LND) | `6F44` | 最后拨出号码 | **循环（cyclic）文件**，只保留最后一次；**卡内无时间戳** |
| EF(SDN) | `6F49` | 服务拨号号码 | 运营商服务号码，部分卡存在 |
| EF(BDN) | `6F4D` | 禁止拨出的号码 | 受 PIN2 保护 |
| EF(EXT1/2/3) | `6F4A` / `6F4B` / `6F4C` | 上述文件的扩展字段 | **不是独立数据**，是 ADN/FDN/LDN 的附加记录 |

> **两个必须记住的否定性事实**：
> ① GSM 11.11 与 3GPP 31.102 里不存在「已接来电」「未接来电」这类文件。 SIM 卡不存储通话历史——呼叫记录由终端（手机）保存，不在卡上。工具若声称从卡里读出 MBN（已接来电）或 MISS（未接来电），**那是从手机侧数据取的名字，不是卡内文件**。
> `6F3B` 是 FDN，不是 MBN；`6F44` 才是 LDN；`6F4B` 是 EXT2（FDN 的扩展），不是 LDN。 这三个 ID 记错会导致读错文件，而工具往往不报错。

```bash
# 读取联系人（记录型文件，需 PIN）
sim_read --select 3G00 --file 6F3A --pin 1234 --decode adn
# 最后拨出号码
sim_read --select 3G00 --file 6F44 --pin 1234 --decode lnd
```

取证要点三条：

1. **ADN 与手机本地联系人分开记录**。SIM 卡上的联系人通常数量少（受卡内空间限制），多见于早期导入或手动添加，与手机通讯录可能不一致。**不一致本身就是发现**——比如卡里有但手机里没有的名字，指向卡被换过或数据被清理过
2. **LND 是循环文件且无时间戳**。标准 SIM 卡只保留最后一次拨出的号码本身，**不存通话时间**。如果工具输出了时间，那是从手机侧日志取的，**不要误标为卡内数据**
3. **FDN 受 PIN2 保护**。FDN 里是运营商限制的号码，通常是紧急号码，也可能被人为利用存储敏感号码。**PIN2 拿不到不影响其余文件可读**——不要因为 FDN 读不了就停止整个提取流程

<a id="section-15"></a>

### 3.5 提取短信

短信存两个地方，很容易混：

| 位置 | 文件 ID | 特点 |
|---|---|---|
| **卡内 EF(SMS)** | `6F3C` | 记录型，**固定 176 字节/条**；容量通常很小（几十条上限），且**运营商可能不支持存储** |
| **手机系统短信库** | 见 [Android 数据存储总览](../mobile-android/mobile-android-android-data-storage-overview.md) / [iOS 备份与沙盒提取](../mobile-ios/mobile-ios-ios-backup-and-sandbox-extraction.md) | **多数短信在这里** |

> **`6FC5` 不是短信文件。** 它是 **PLMN Network Name**（网络名，透明文件）——
> 按 UST 的服务号 45 归在"网络配置"这一类，与短消息毫无关系。
> 而 `6F5C` 是 Maximum value of Hyperframe number（超高帧号计数器上限），
> `6F5B` 是 Hyperframe number 本身——**这两个也是真实存在的 ID，但同样与短信无关**。
> 把 `6F3C` 和这几个值混着写，工具不会报错，只会安静地返回完全无关的数据。
> 短信侧真正相关的另外两个标准文件是 `6F43`（EF(SMSS)，短信状态指示）与
> `6F47`（EF(SMSR)，短信状态报告）——**记的是状态，不是内容**。

```bash
# 读卡上短信
sim_read --select 3G00 --file 6F3C --pin 1234 --decode sms
```

**EF(SMS) 的第一个字节是状态位**，这一点在取证时很有用：它标记该条是「网络下发/UE 发出」、是否已读、是否待发送。**状态位为空的记录通常意味着空间预留而非已删除**——把这个误读成「短信被删除」是一个常见错误。

**必须写进报告的关键限制**：

> SIM 卡上短信数量少或不完整是正常现象，不能据此认为"短信已被删除"。
> 原因有三：① 卡上短信存储空间只有几百字节到几 KB；② 多数运营商已不支持短信写入卡；③ 手机收到短信后默认存到本机，卡上只留最早的一批。
>
> 因此"卡上无短信"**只说明卡上没有**，真正的短信证据要从手机侧取。

这条限制在 [4.3](#section-27) 展开。

<a id="section-16"></a>

### 3.6 提取位置信息：只取最后一次注册

这一步的现实产出比预期低，原因在 2.5 已经说明：卡上只存当前值。 这一节只能给你最后一次注册位置，**给不了任何轨迹**。

```bash
# GSM / UMTS 侧：最后一次位置区
sim_read --select 3G00 --file 6F7E --decode loci

# LTE 侧：最后一次跟踪区（GUTI + TAI）
sim_read --select 3G00 --file 6FE3 --decode epsloci

# GPRS 分组域：P-TMSI + 路由区
sim_read --select 3G00 --file 6F73 --decode psloci
```

典型输出：

```text
EF(LOCI) '6F7E'  11 字节
  TMSI              : F0F1F2F3
  LAI               : 460001234
    MCC/MNC         : 460-00
    LAC             : 1234
  Location update status : 00  (updated)

EF(EPSLOCI) '6FE3'  18 字节
  GUTI              : ...
  Last visited TAI  : 46000-0A1B2
  EPS update status : 00  (updated)
```

分析要点三条：

1. 先看 `Location update status`。它标明该位置值是否已被网络确认。若显示未更新或不允许，该 LAI 可能仍是旧值，**不能当成设备最后所在位置的可靠证据**
2. **`6F7E` 与 `6FE3` 的粒度不同**。前者是位置区（LAC），后者是 LTE 跟踪区（TAC），**跟踪区通常更大**。两个值不一致是正常的（设备可能跨 RAT 驻留），不要当成矛盾
3. **没有时间戳，只有顺序**。即便是与终端数据关联推时间，**精度也取决于外部日志**，卡本身给不出任何时间信息

> **关于"想拿到更多位置历史"**：卡上没有。要么从**终端侧**取（Android 的 `cell_history`/`getAllCellInfo` 类数据、基带日志、iOS 的无线诊断日志），要么走**运营商侧**调取。前者是本项目的相邻议题，见扩展阅读；后者需要单独授权。
>
> **阴性结论的写法**：不能写"卡上未发现历史位置记录"（暗示应该有），应写"`EF(LOCI)` 为单值透明文件，按 3GPP 规范不含历史记录；卡内位置证据的覆盖范围仅为最后一次注册位置，历史位置需终端侧数据"。

关联分析要靠外部数据。拿到 LAI 后，可通过公开的 LAC 分配表或运营商资料把 LAC 转换为实际区域名（`1234` → 某市某区）。这一步**需要外部数据支撑**，在报告中应说明数据来源与查询时间。

<a id="section-17"></a>

### 3.7 物理转储与镜像留存

逻辑提取做完之后，若案件需要保全原始状态或后续深度分析，可做**物理转储**（读取卡片的完整 EEPROM 内容）。

前提条件有三个：

- 读卡器必须支持**时钟安全域（Secure Messaging）**或明确的 EEPROM 读取命令
- 部分现代 USIM 出于安全设计，**物理读取被完全封锁**——这不是工具问题，是芯片设计
- 需要在合法授权下进行

```bash
# 物理转储（仅部分卡型支持）
sim_read --dump eeprom --out DigiForensics-sim.bin --select 3G00
sha256sum DigiForensics-sim.bin
```

取证规范：

1. 转储前记录卡的 ATR、ICCID
2. 转储后计算哈希
3. **转储过程本身可能修改卡的内部计数器**（见 4.6），必须在报告中说明
4. 保留原始 `.bin` 与工具输出的日志，作为过程凭据

**物理转储不可行怎么办**（部分现代 USIM 属于此列）：改为保留三样东西——完整文件树遍历输出、每个 EF 的原始十六进制 dump、读取日志。这三样足以支撑复核。

## 四、常见陷阱

SIM 卡的陷阱有一个共同来源：它的可读范围由卡的访问控制状态决定，而这个状态在读卡器上只呈现为一个词。 「读不出数据」这个现象，背后可能是 PIN 锁定、PUK 锁定、卡已损坏、读卡器接触不良、以及本来就没有那类数据——五种成因的处置动作完全不同，而现象一样。

本章按认证与识别 → 解锁操作 → 结论表述 → 硬件与数据完整性 → 工具与版本归组。

<a id="section-19"></a>

### 4.1 认证与识别误判

<a id="section-20"></a>

#### 把 ICCID 当成手机号

**现象**：报告里写"经 SIM 卡取证，涉案号码为 8986110XXXXXXXXX"，把 ICCID 写进"手机号"栏。协查函也按这个号码发出去。

**原因**：ICCID 是**卡的硬件序列号**，IMSI 是**用户身份**，MSISDN 才是手机号。三者由不同主体分配、存储在不同位置。ICCID 印在卡面上、看起来像"一串号码"，很容易被误当联系方式填进表格。更隐蔽的是它的结构：ICCID 以 `89` 开头（MII 标识电信卡），后面是国码、发行方标识、生产年月、流水号与 Luhn 校验位，**看起来与手机号同样是十进制长串**，而 ICCID 上并不存在可供拨号的结构。

**影响**：**结论方向性错误**。ICCID 被当作手机号写进案件材料，后续的运营商协查、身份关联会全部走偏——运营商拿到一个 ICCID 无法反查出用户。更麻烦的是，IMSI 与 MSISDN 的换号不换卡特性意味着——**用 ICCID 直接反查用户这条路走不通，需要经 IMSI 或 MSISDN 转由运营商侧关联**。

**核查**：**三类标识严格分列，不合并**。报告里应有独立的字段表：

| 字段 | ICCID | IMSI | MSISDN |
|---|---|---|---|
| 来源 | 卡面 / EF(ICCID) | EF(IMSI) | **运营商侧**，卡上未必有 |
| 作用 | 硬件标识 | 用户身份 | 联系号码 |
| 能否据此定位用户 | 否 | **需运营商授权查询** | 否（可被改） |

<a id="section-21"></a>

#### 看到 "SIM" 就认为设备只有一张卡

**现象**：读完一张卡就结束，报告写"该设备使用一张 SIM 卡"。

**原因**：现代设备普遍双卡双待，另有 eSIM。同一台设备可能有 2 张物理卡 + 1 张 eSIM，对应最多 3 个 IMSI。工具读卡的默认行为往往只读第一张。

另一半原因是**卡槽存在但为空**与**卡槽内有卡**在外观上难以区分：卡托取出后若未拍照记录，重新装回时无法确认哪张卡原本在哪个槽位，而两个槽位在后续使用中可能被交换过。

**影响**：**遗漏另一张卡的全部证据**。而另一张卡可能才是涉案号码所在。涉毒、涉诈案件中，"主卡正常、另一张卡有问题"是常见结构——而案发时段的两张卡归属记录会直接决定归属认定方向。

**核查**：**先清点卡的物理数量与位置**，再逐一读取。双卡设备的卡槽通常在机身侧边两处，需分别拍照记录卡位与卡托标识（卡托上常印有 `SIM1` / `SIM2`）。

```text
取证记录必须区分：
  位置 1：机身左侧卡槽（SIM1）  → ICCID 8986...  IMSI 46000...
  位置 2：机身右侧卡槽（SIM2）  → ICCID 8986...  IMSI 46001...
  eSIM（嵌入式）                → 未能独立读取，原因：____

槽位与卡号的对应关系一旦无法当场确定，整条「该号码使用于本机」的结论都不成立。
```

<a id="section-22"></a>

#### 把「卡状态：LOCKED」当成唯一的失败原因

**现象**：读卡器报 `Card state: LOCKED`，分析员在报告里写「因卡处于 PIN 锁定状态，内容不可读」，然后进入等待解锁的流程。

**原因**：**「读不出」有五种成因，而状态字段只覆盖了两种。**

| 现象组合 | 实际含义 | 处置 |
|---|---|---|
| ATR 正常 + `LOCKED` | PIN 保护 | 需授权后解锁 |
| ATR 正常 + `BLOCKED` | **PUK 锁定**（PIN 已耗尽） | 只能 PUK，且 PUK 需持卡人提供 |
| ATR 正常 + `READY` 但目标 EF 返回 `6982`（安全状态不满足） | 应用级或文件级访问保护（FDN 等需 PIN2） | 与 PIN 锁定不同机制 |
| **ATR 全 `FF` 或全 `00`** | **读卡器接触不良 / 卡损坏** | 换硬件，**不要归因于 PIN** |
| ATR 正常 + 目标文件不存在 | **卡内本来就没有这类数据** | 不是锁定问题 |

第五行是最容易漏的一类：`sim_read` 报"文件读取失败"时，工具的笼统措辞常被读成锁定，但它可能只是这张卡的运营商没有写入该 EF。

**影响**：把硬件问题归因成锁定，会让案件卡在一个**根本不存在**的授权环节上——委托方去申请 PUK，而正确动作是换一根读卡器触点或换一个卡槽位，十几分钟就能解决。反之，把「文件不存在」写成「因锁定不可读」，则把一个阴性发现包装成了能力限制，报告的边界被夸大了。

**核查**：**先看 ATR，再看状态，最后才看文件。**

```bash
# ① ATR 全 FF/全 00 → 硬件问题，不是 PIN
sim_read --reader /dev/ttyUSB0 --info
# ATR: FF FF FF FF ...  → 接触不良或卡损坏，换槽位/换读卡器重试

# ② ATR 正常后记录状态，再尝试选应用
sim_read --reader /dev/ttyUSB0 --info
sim_read --reader /dev/ttyUSB0 --select 3G00 --list-files

# ③ 逐个 EF 记录返回码，6982 = 安全状态不满足，其余为文件不存在
```

**每一类文件都要单独记录返回码**，把「因锁定不可读」与「文件不存在」分开列表。这份列表就是报告里的「已提取 / 未提取 / 不适用」三段式。

<a id="section-23"></a>

#### 把「MCC/MNC 与设备 IMEI 国家码不一致」当成换卡的证据

**现象**：卡内 `MCC/MNC` 是 `460-01`，而设备侧读出的 IMEI 的 TAC 段显示为其他来源，报告直接写「该卡非本机原装卡，判定为换卡」。

**原因**：MCC/MNC 只说明卡的注册网络，与卡的生产地、设备的销售地是三件独立的事。

一张合法渠道销售的中国联通卡，装在一台日本市场版本的手机里是完全正常的；而 `460-00`（移动）出现在一台设备上，也不能推出「卡是从别人那里拿来的」——**换卡与漫游在卡上留下的痕迹是一样的**。真正能区分两者的是时间维度：漫游是**同一张卡在不同时期注册到不同网络**，换卡通常伴随 **ICCID 变化**且 LAI 序列里出现 MCC/MNC 跳变而无回落。

**影响**：把「MCC/MNC 不同」写成「判定为换卡」，是对设备与卡的绑定关系做了一个**证据强度不足的断言**。在涉毒、涉诈案件里，「换卡」是重罪认定的支撑点之一，一旦被推翻，同案其他关联认定都会受牵连。

**核查**：换卡的判据是 ICCID 与时间序列，不是 MCC/MNC 本身。

```bash
# ① 取卡的 ICCID 与 位置值（LAI 不带时间戳）
sim_read --select 3G00 --file 2FE2 --decode iccid
sim_read --select 3G00 --file 6F7E --decode lai

# ② 取设备侧 IMEI/LAC，与卡内信息分别记录，不做单点比对
```

结论按两档写：MCC/MNC 与设备国家码不同但无其他异常 → 「卡注册网络与设备来源不一致，成因待定（并行漫游 / 渠道调货 / 换卡均可能）」；ICCID 变化且设备侧记录显示网络跳变与回落 → 「**存在换卡迹象**，ICCID 由 `<A>` 变为 `<B>`，依据为 `<数据源>`」。「不一致」是观察，「换卡」是需要独立证据支撑的推断。

<a id="section-24"></a>

### 4.2 解锁操作（★ 表示不可逆）

<a id="section-25"></a>

#### 未经授权就试 PIN ★★★

**现象**：读卡器显示 LOCKED，分析师直接试了 `0000`（最常见的默认 PIN），又试了 `1234`，第三次尝试后卡被锁定。

**原因**：分析师的常见假设是"默认 PIN 多是 0000 或 1234，试一下无妨"。但**三次机会用完就锁卡**，这不是可以随意消耗的资源。而且不同运营商、不同卡批次的默认 PIN 规则并不统一。

**影响**：**可能造成不可逆后果**。委托方手上没有 PUK，这张卡就锁死了——PUK 虽仍可解锁，但取证成本大幅上升。更麻烦的是，**取证过程中的操作瑕疵会被对方质疑**："为什么在没有授权的情况下尝试解锁？"

**核查**：**顺序不能颠倒**。

```text
1. 先书面确认授权范围是否包含「解锁 SIM」
2. 先读无需 PIN 的内容（ICCID / PLMN / SPN）—— 零风险
3. 确认授权后，优先请委托方向运营商或卡持有人获取 PUK
4. 只有在拿到 PUK 且授权明确时，才进行 PIN 尝试
5. 全程记录每次尝试的时间、次数、结果
```

**剩余次数必须先查再试**。部分卡在未解锁状态下可读到 `CHV1` 的剩余尝试计数器（3.2 节的读取序列里可以体现），拿到这个数字再决定是否尝试，能避免把最后一次机会浪费掉。

<a id="section-26"></a>

#### 认为"锁定只是软件限制，可以绕过"

**现象**：想用工具的"强制读取"或"绕过 PIN"功能直接读全部文件。

**原因**：某些旧卡的 PIN 验证实现确实存在缺陷，工具声称能绕过。但这属于**规避安全机制**，在多数司法辖区本身可能构成违法（相当于非法侵入通信设备），且法院对这种证据的可采性通常持否定态度。

**影响**：**证据可采性存疑，并带来法律风险**。这样取得的数据，在质证时通常难以作为证据使用。

**核查**：**只用授权途径**。委托方无法提供 PUK 时，正确结论是"该卡内容在现有授权下不可读"，并把它写进报告的受限范围一节。

<a id="section-27"></a>

### 4.3 结论表述

<a id="section-28"></a>

#### ★ 只读身份信息就收工

**现象**：ICCID、IMSI、MSISDN 三个号码读出来，报告写"SIM 卡取证完成"。

**原因**：身份信息只是**卡的基础层**。真正有案件价值的往往是内容层：联系人、短信、位置值。而且**卡上内容不完整是常态**——存储空间小、运营商策略差异、设备侧覆盖。

**影响**：**遗漏主要证据**。一份只写了三个号码的 SIM 取证报告，覆盖面与直接向运营商协查取得的内容高度重叠。SIM 卡的独立价值恰恰在于**卡内那些拿不到的内容**。

**核查**：**明确写出检查范围与未覆盖部分**。

```text
✅ 已提取：ICCID、IMSI、MSISDN、MCC/MNC、SPN、EF(LOCI) 当前值
   未提取：联系人（PIN 保护，授权范围不含解锁）
           短信（卡内存储为空，运营商不支持写入）
   未覆盖：eSIM（设备嵌入式，无法独立读取）
           卡的物理转储（该型号 USIM 封锁 EEPROM 读取）

❌ SIM 卡取证已完成，提取到相关信息。
```

<a id="section-29"></a>

#### 把卡内位置值当成行踪轨迹 ★★

**现象**：报告写"根据 SIM 卡 LAI 记录，嫌疑人于 3 月 5 日至 3 月 12 日期间活动于北京市海淀区"，并配上一条按天排列的时间轴。

**原因**：这个结论有**两层问题，第二层更根本**。

**第一层是粒度**：LAI 的精度只到**位置区（LAC）**级，一个 LAC 覆盖的区域可能是几平方公里到几十平方公里。**卡内不存时间戳**，任何时间都只能靠外部数据推。更关键的是**移动网络会复用 LAC**，同一个 LAC 在不同时期可能对应不同的区域配置。

**第二层是根本性的**：**卡上根本没有多条 LAI 记录**。`EF(LOCI)` 是固定 11 字节的单值透明文件，每次位置更新是**覆盖写**。所谓"LAI 列表""按写入顺序的 MCC/MNC 序列"**这个数据结构在 SIM/USIM 上不存在**。

**影响**：这类错误的影响在于**它伪造了一个不存在的证据**。质证时对方只需问一句"这个 LAI 列表从哪来的"，整份报告的数据基础就崩塌了，而不只是某个结论需要修正。而且这类错误难以自查：**工具可能真的会输出一个看起来像列表的东西**（比如把终端缓存误当卡内数据，或把多张卡的记录合并），不核对结构就会照抄。

**核查**：**先确认字段结构，再按粒度表述。**

```text
✅ 卡内 EF(LOCI) 为 11 字节单值透明文件，不含历史记录。
   当前值：MCC/MNC = 460-00，LAC = 1234，
   Location update status = 00（已被网络确认）。
   该值仅代表最后一次注册的位置区，不含时间信息。
   LAC 与实际区域的对应关系需查询运营商分配表，本次未获得，故不给出具体地理位置结论。
   未覆盖：历史位置（需终端侧数据）、精确坐标、具体时间点。

❌ 嫌疑人于 3 月 5 日在北京市海淀区活动。
❌ 卡内 LAI 记录显示 3 月 5 日至 12 日的活动轨迹。
```

**关键一步是核对字段长度**：读到 `6F7E` 时，**输出应当是 11 字节**。如果工具输出了十几行"记录"，那不是卡内数据，立刻停下。

<a id="section-30"></a>

#### 用 eSIM 的 IMSI 去查运营商

**现象**：从设备侧读出 eSIM 的 IMSI，直接按 IMSI 前缀推断这是哪家运营商的卡。

**原因**：eSIM 支持**一张卡对应多个 profile**（多号码 eSIM），且 profile 可远程切换。也就是说，同一个 eSIM 芯片在不同时期可能承载不同运营商的 IMSI。而且 eSIM 的 IMSI 可能在 profile 切换后被覆盖，读到的未必是涉案号码。

**影响**：**关联到了错误的运营商**，进而可能走错协查流程，或者把无关用户的数据纳入调查范围。

**核查**：**明确区分「读到的 IMSI」和「涉案 IMSI」**。eSIM 场景下，必须通过运营商侧的 profile 变更记录来确认时间对应关系，不能仅凭设备上的静态读数下结论。

<a id="section-31"></a>

#### 把「卡内短信少于预期」写成「短信已被删除」

**现象**：卡内 `6F3C` / `6FC5` 里只有 11 条短信，而委托方陈述"收到过上百条"，报告写「卡内短信大部分已被删除，疑为销毁证据」。

**原因**：卡内短信空间本来就很小，而且多数运营商早已不支持写入卡。 手机收到短信后默认写入本机数据库，卡上往往只留最早的一批或根本不留。同时 `EF(LND)`（`6F44`）是**循环文件**，以及线性定长的 `EF(ADN)`、`EF(FDN)`，写满即从头覆盖——所以这两类文件的条数上限由卡的记录数决定，与用户实际行为无关。

另一半原因是**文件系统与应用区的分离**：卡上的记录型文件位于 USIM 应用（`3G00`）下的固定文件 ID，而现代手机从 4G 起大多不再把短信写入 SIM，规范里 `6F3C` 已不是必备文件。因此一张正常的 4G 卡上读不到短信，是规范演进的结果，不是异常。

**影响**：**把正常演进写成了销毁证据**，这是指向性错误。委托方可能据此怀疑持卡人刻意销毁通信记录，而实际上这些短信完整保存在手机侧（见 [3.5 提取短信](#section-15) 的两个存储位置对照）。第五章 5.1 里卡 2 的短信提取量为 11 条，这正是正常量级。

**核查**：**阴性发现先判成因，再谈方向。**

```bash
# ① 文件存在但为空 vs 文件不存在
sim_read --select 3G00 --file 6F3C --decode sms
# 返回 6982 → 安全状态不满足（锁定）；返回 6A82 → 文件不存在（未分配）

# ② 文件存在且有条数时，记录条数与容量上限的关系
```

报告按三档写：文件不存在 → 「**该卡未分配 SMS 存储文件，短信不落地卡**，属 4G 卡的常见形态」；文件存在但为空 → 「**卡内 SMS 文件已分配但无记录**，多数运营商不支持写入卡」；文件存在且条数少于陈述 → 「卡内 SMS 共 `<N>` 条，低于陈述的 `<M>` 条；卡内存储容量上限为 `<上限>` 条且为循环覆盖，超出部分不保留；完整短信记录应以手机侧数据库为准」。**三种情况的处置完全不同，不能都写成「未见异常」。**

<a id="section-32"></a>

#### 把 ICCID 的「发行方标识」读成「运营商归属」

**现象**：ICCID 解析结果显示 `Country: 86 (中国)`、`Issuer: 00`，报告写「该卡为中国移动发行的卡」，并据此把卡片来源与某运营商关联。

**原因**：**ICCID 的字段语义与 IMSI 完全不同。** IMSI 的 `MCC+MNC` 才表示注册网络；ICCID 的结构是 `MII(2) + 国家码(1~3) + 发行方标识(长度可变) + 发行年月 + 流水号 + 校验位`，其中**发行方标识是卡的制造/发行分配号，不是运营网络号**。同一个 `Issuer` 值可以出现在不同 MNO 发行的卡上；反过来，同一运营商发行的卡也可能有不同的发行方标识段。

另一半是**校验位方向**：ICCID 尾部的 Luhn 校验位是**校验 ICCID 自身的**，而 3.3 节示例里 `Checksum: 7 (Luhn 校验通过)` 这类输出容易被读成「校验通过说明卡是真的」——Luhn 只能证明这串数字自洽，与卡的合法性无关。

**影响**：把 ICCID 字段语义映射到运营商，会让「卡的来源」这条线索指向错误主体。在需要证明「该卡由某人申领」的案件里，这个方向的错误会直接推翻归属认定。

**核查**：两个标识体系的字段分开列，运营商判断只用 IMSI。

| 来源 | 字段 | 能得出的结论 |
|---|---|---|
| `EF(ICCID)` | MII / 国家码 / 发行方标识 / 发行年月 | 卡的**制造与发行**信息、生产年月 |
| `EF(PLMN Selector)` + IMSI | MCC + MNC | 卡注册的**移动网络**归属 |

发行年月可作为卡的时间下界（「该卡生产于 `<年月>`，因此该卡的申领时间不早于此时」），这是它真正有用的地方；**运营商归属只认 IMSI 的 MCC/MNC**。

<a id="section-33"></a>

### 4.4 硬件与数据完整性

<a id="section-34"></a>

#### 读卡器操作改动了卡上的计数器 ★

**现象**：读取过程中卡的 ATR 或某些文件值发生了变化，比如 SIM 卡的 `Phase Identification`，或某些运营商自定义的接入计数器。

**原因**：ISO 7816 规范本身就包含会改变卡状态的命令。`SELECT` 某些文件会更新卡内的"最后访问时间"，`STATUS UPDATE` 可能改变 PIN 剩余尝试次数的影子计数。分析师通常认为"读卡是只读操作"，但这在智能卡上**不成立**。

另一半是**读卡器侧的会话状态**：接触不良导致的断连会产生异常终止，卡可能把这次会话计入失败计数或锁定状态；反复插拔同一张卡同样会留下痕迹。

**影响**：**卡上某些字段被改写，且不可还原**。案件争点若涉及"这张卡什么时候被访问过"，这类计数器本身就是证据。

**核查**：**接受这个事实并如实记录**。

```text
✅ 读取完成后对同一张卡二次读取，比对前后差异，
   观察到 EF(Phase Identification) 由 20 变为 21，
   该变化系 ISO 7816 规范定义的 STATUS UPDATE 副作用，
   非人为改动，已在报告局限性一节说明。

❌ 读取过程完全无损。（这是不成立的表述）
```

**在能物理转储的前提下**，先做完整 dump 再做逻辑读取，可以把这类副作用限制在最小范围。

<a id="section-35"></a>

#### 忘记报告 eSIM 设备没有物理卡

**现象**：设备是 eSIM-only（无卡槽机型），报告却写"该设备未发现 SIM 卡"，并据此推断"设备可能未联网使用"。

**原因**：**eSIM 无卡槽是设计如此，不是异常**。报告应说明"该设备使用嵌入式 SIM，无可提取的物理卡"，而不是"未发现 SIM 卡"——后者暗示这是异常状态。

**影响**：**引导出错误的推论**。调查人员若据此怀疑设备未联网，那是建立在错误前提上的判断。

**核查**：**区分三种情况并分别表述**。

| 情况 | 正确表述 |
|---|---|
| eSIM-only 机型 | 该设备为嵌入式 SIM 设计，无物理卡槽 |
| 有卡槽但卡已取出 | 物理卡槽为空，槽内无 SIM 卡 |
| 有卡槽且卡在位，但读不出 | 读卡失败，原因：接触不良 / 卡损坏（待确认） |

<a id="section-36"></a>

#### 把「物理转储失败」写成「卡内数据已灭失」

**现象**：执行 EEPROM 转储失败（工具报不支持，或返回 `6982`），报告写「该卡原始数据不可得，内容已永久丢失」。

**原因**：EEPROM 读取被封锁是芯片的安全设计，与卡的逻辑内容是否还在盘上是两回事。 现代 USIM 的安全域与部分卡型的物理读取限制，使得转储在相当一部分生产卡上不可行——这是常见形态。而逻辑读取仍可完成：`EF(ICCID)`（`2FE2`，MF 下）、`EF(PLMN Selector)`（`6F30`）、`EF(SPN)`（`6F46`）按规范是 ALWAYS 可读，`EF(LOCI)`（`6F7E`）等是 READ PIN——**解锁后可读**。

**影响**：**把能力边界写成了证据灭失**。委托方据此认为该卡的所有内容都已不可得，从而放弃补充调证（比如向运营商申请注册记录与开通记录），而实际上还有一整条可行路径。

**核查**：区分「物理转储不可行」与「逻辑内容不可读」，并给出替代保全物。

> **必须一起说明的是 `EF(Keys)`：`6F08` / `6F09`（Kc、Kc\*/Ki）的访问条件是 NEVER。**
> 卡片**没有任何 APDU 能把它们读出来**——这不是权限不够，是协议里根本没有这条路径。
> 这一条要写进报告的「不可获取清单」，而不是留白：它决定了"能不能做离线密钥推导"这个问题有确定答案。

```bash
# 逻辑读取已能覆盖的范围（无需物理转储）
sim_read --select 3G00 --file 2FE2 --decode iccid    # ICCID
sim_read --select 3G00 --file 6F7E --decode loci      # 最后一次位置值
```

转储不可行时，按 3.7 节的替代方案保全三样东西——完整文件树遍历输出、每个 EF 的原始十六进制 dump、读取日志。报告按两档写：转储成功 → 「已保全物理镜像 `<文件名>`，SHA-256 `<值>`」；转储不可行 → 「**该卡型物理读取被芯片设计封锁，物理镜像不可得**；已保全逻辑读取全量记录（文件树 + 各 EF 十六进制 + 读取日志），足以支撑复核；**未覆盖：卡内未被读取命令访问到的存储区**」。最后那半句是必须写的——它明确了这条路径的实际边界。

<a id="section-37"></a>

### 4.5 工具与版本

<a id="section-38"></a>

#### 用只支持老 SIM 的工具读 USIM

**现象**：工具报"卡内无 IMSI"或"未找到 USIM 应用"，实际上卡是正常的 4G USIM。

**原因**：早期工具针对 GSM 的 SIM 应用开发，读的是 `2G00` 目录。现代网络用 USIM 应用（在 `3G00`），文件 ID 从 `2xxx` 变成 `6xxx`。工具能读到卡、能列出文件，但读不到你需要的字段，且不报错。

**影响**：**误判为"卡内无该数据"**，再往下一步就误判成"设备未注册网络"了。

**核查**：**先看 ATR 判断卡的世代**，再用支持 USIM 的工具。ATR 的第 4–5 字节历史字节里包含 TC（协议传输能力）信息，可判断是否为 UICC。

```text
✅ 工具输出 ATR 3B 16 94 7E 23 01 …，应用列表包含 3G00 (USIM)。
   使用支持 USIM 的读取命令访问 6xxx 文件 ID，
   成功提取 IMSI。

❌ 未提取到 IMSI。（未说明是工具不支持 USIM）
```

报告规范：**工具名 + 版本号 + 能力范围**三者缺一不可。工具不支持某类卡时，必须在报告里明说，不能只写"未提取到"。

<a id="section-39"></a>

#### 只读了一个应用（`2G00` 或 `3G00`）就收工

**现象**：工具报告「已读取 USIM 应用下的文件」，分析员据此写「卡内文件已全部提取」；或者反过来，只读了 `2G00` 下的文件就断言「卡内无该数据」。

**原因**：一张 UICC 卡上可能同时激活多个应用，各自持有独立的文件树——SIM 应用、USIM 应用，部分卡还带测试应用、运营商私有应用。除 MF 下的公共文件外，同一类信息在不同应用下的文件 ID 往往不同：例如 PLMN 选择器在 GSM 应用侧是 `6F20` 下的 `6F30`，而用户可控的带接入技术版本是 `6F60`；`KC` 在 GSM 侧是 `6F20`，`Kc/Ki` 在 USIM 侧是 `6F08`。在 USIM 应用下没读到某个文件，不代表 SIM 应用下也没有——尤其是 GSM 遗留字段，它们常常只存在于其中一个应用。

另一半原因是**文件树遍历深度不足**：只列了根目录（MF）下的 DF，没有进各 DF 内部逐个列 EF，于是报告里的「文件清单」实际只是一个路径骨架。

**影响**：漏读导致的阴性结论无法自证——对方只需问「你遍历了几层、应用选的是哪个」，整个阴性发现就失去支撑。这类错误在双应用卡上较易发生。

**核查**：**应用逐个选，文件树逐层列，逐项记录返回码。**

```bash
# ① 先列应用，确认本卡激活了哪些
sim_read --list-apps
# 典型：2G00 (SIM) / 3G00 (USIM) / 4G00 (ISIM，部分运营商)

# ② 每个应用分别做全树遍历，不只列根目录
sim_read --select 3G00 --list-files --recursive
sim_read --select 2G00 --list-files --recursive

# ③ 关键字段在两个应用下都查一次，对比取值
sim_read --select 3G00 --file 2FE2 --decode iccid
sim_read --select 2G00 --file 2FE2 --decode iccid
```

**两处取值不一致本身就是一条发现**（说明有应用层面的数据不一致，值得记录而非择一采用）。报告里写「已在 `<N>` 个应用下完成全树遍历，共访问 `<M>` 个 EF，其中 `<K>` 个返回 `6A82`（文件不存在）」——这个「访问了多少、找到多少」的结构比「已全部提取」这句话有用得多。

## 五、案例示例

<a id="section-41"></a>

### 5.1 双卡涉诈设备的 SIM 位置证据与授权边界

**场景**

一台涉案 Android 11 智能手机被扣押，内含两张 SIM 卡。

检方需要证明嫌疑人**在特定时段出现在案发地**。

委托方随案附了一张纸条："两张卡都试一下 PIN，破解了就完事。"

这句话如果被执行，本案最重要的合规风险就产生了——卡 1 处于 PIN 锁定状态，而授权范围明确不含解锁。

**处置过程**

第一步，物理固定：

```text
设备：Android 11 智能手机，双卡双待
拍照记录：开机状态、卡托位置、取出过程、两张卡的正反面
卡 1：槽位标识 SIM1（左槽），ICCID 可见
卡 2：槽位标识 SIM2（右槽），ICCID 可见
```

第二步，读取卡 1 并当场确认授权边界：

```text
ATR 正常，应用列表含 3G00 (USIM)
卡状态：LOCKED（需要 PIN）
  → 委托方书面确认：授权范围不含解锁
  → 不尝试 PIN
  → 仅读取公开 Transparent 文件
```

这个判断必须写在处置记录的最前面，而不是事后补记。 试 PIN 与不试 PIN 的差别不只是"有没有成功"，而是**有没有合法授权**。

第三步，卡 1 的提取结果：

| 项 | 值 |
|---|---|
| ICCID | 8986001234567890123 |
| MCC/MNC | 460-01（中国联通） |
| SPN | 中国联通 |
| EF(LOCI) | LAC `2A10`（最后一次注册位置，**无历史**） |
| 联系人 | **未能提取**（PIN 保护） |
| 短信 | **未能提取**（PIN 保护） |

第四步，卡 2 的提取结果：

| 项 | 值 |
|---|---|
| ICCID | 8986009876543210987 |
| MCC/MNC | 460-00（中国移动） |
| SPN | 中国移动 |
| 状态 | READY（无需 PIN） |
| 联系人 | 23 条 |
| 最近拨号 | 1 条（EF(LND) 为循环文件，仅存最后一次） |
| 短信 | 卡内 11 条 |

第五步，位置信息 —— **注意它能提供的东西比直觉少得多**：

| 卡 | 文件 | MCC+MNC | LAC | 说明 |
|---|---|---|---|---|
| 卡 1 | `EF(LOCI)` `6F7E` | 460-01 | 2A10 | 最后一次注册位置，**卡上仅此一条** |
| 卡 2 | `EF(LOCI)` `6F7E` | 460-00 | 1B05 | 最后一次注册位置 |

三点判读：

- **每张卡只有一个位置值，不是列表**。`6F7E` 是固定 11 字节的单值透明文件，**卡上不存在位置历史**——报告里若出现"LAI 列表共 7 条"，那不是卡内数据
- 卡 1 与卡 2 的 MCC/MNC 不同，这是正常的。两张卡分属不同运营商本来就是常态，**不能据此推出"换卡"或"异常"**
- **LAC 需要外部数据才能落地成地名**。本次未获得运营商 LAC 分配表，因此**不给出具体地理位置结论**

第六步，交叉验证与谨慎推论：

```text
卡 1 当前值：460-01 / LAC 2A10
卡 2 当前值：460-00 / LAC 1B05

→ 两张卡各自最后一次注册在各自的网络上，这是双卡设备的正常状态
→ ★ 卡内数据无法回答"两张卡是否被调换过"——那需要 ICCID 变更记录、
   设备侧基带日志，或运营商侧的换卡记录
→ 未覆盖：任一卡的历史位置、精确坐标、时间信息（全部不在卡上）
```

**这一处值得单独强调**：本案最容易犯的错，是把卡 2 的 `460-00` 读成"出现在卡 1 的记录里"，从而推出换卡或套牌。**卡 1 上从来没有卡 2 的网络记录**——每张卡只记自己的最后一次注册网络。

**结论**

| 结论 | 支撑证据 | 强度 |
|---|---|---|
| 设备内两张 SIM 卡的身份已固定 | ICCID ×2、槽位、MCC/MNC ×2 | 强 |
| 卡 1 处于 PIN 锁定，授权范围不含解锁 | 委托方书面确认 | 强 |
| 卡 1 的联系人与短信层未获取 | PIN 保护 | 强 |
| 卡 2 的联系人 23 条、短信 11 条、最近拨号 1 条 | 无锁状态直接读取 | 强 |
| 卡 1 的 `EF(LOCI)` 返回 11 字节，是单值而非列表 | 文件类型与返回长度 | 强 |
| 卡内位置值不含时间戳 | 卡内文件结构 | 强 |

**能证明的**：两张卡的标识与所属网络、**各自最后一次注册的位置区**、卡 2 的通讯录与卡内短信。

**不能证明的**：
- **不能证明持卡人在任何具体日期出现在案发地。** LAI 无时间戳，这是本案最硬的限制
- **不能证明 LAC 2A10 对应哪个地理区域。** 需运营商的 LAC 分配表，本次未获得
- **不能证明换卡或换机行为发生。** 卡 1 的位置值只有一条，且与卡 2 属不同网络——这在双卡设备上是常态，不构成任何异常信号
- **不能证明卡 1 的联系人与短信不存在。** 只能说明未获取

**未覆盖范围**：卡 1 的 PIN 保护层、EEPROM 物理转储（该型号 USIM 已封锁原始读取）、LAC 地理对照表、SIM Toolkit 应用层、以及运营商侧的 IMEI 与卡号绑定关系。

**误判对照**

**其一，把卡内位置值当成一条轨迹。**

**卡上没有轨迹，只有一次快照。**

`EF(LOCI)` 是固定 11 字节的单值透明文件（`6F7E`），每次位置更新覆盖写入。「LAI 列表」「最近若干个去重条目」「环形列表」这些描述在 SIM/USIM 上都不对应任何实际数据结构——那是终端侧缓存或网络侧日志的特征。

判据是**字段长度与文件类型**，这是可以直接核对的：

| 项 | 实际值 | 若报告里出现则说明 |
|---|---|---|
| 文件类型 | `transparent`（单值） | —— |
| 文件长度 | **11 字节** | —— |
| 记录条数 | **1 条** | 数据不来自卡本身 |
| 时间戳 | **无** | 任何时间都来自外部推断 |

**核对动作只有一步**：读 `6F7E` 时看返回长度。**11 字节是卡内数据；十几行"记录"一定不是。**

按错误判据走，报告里会出现"该卡曾接入 LAC 2A10 与 3F22"这类表述——**而卡上从来没有 3F22 这个值**。委托方据此画行军轨迹，辩护方一核对就发现整条轨迹没有数据基础。

其二，把 `FFFFFFFF/FFFF` 当成一个真实位置。

卡刚激活、尚未成功注册时，`MCC/MNC/LAC` 可能全为 `FFFF`。它的含义是"从未成功注册到任何网络"，**不是"在某个地方"**。

| 项 | 初始值 | 正常值 |
|---|---|---|
| MCC | `FFFF` | 如 `460` |
| MNC | `FFFF` | 如 `01` |
| LAC | `FFFF` | 如 `2A10` |

判据是"MCC 与 MNC 全为 F 时该值无效"。这类值必须在报告中保留但明确标注"初始值，未构成有效位置证据"，不能静默删除——静默删除会让读者无法复核分析方是否真的看到了它。

同时要看 `Location update status`（第 11 字节）：显示未更新或不允许时，该 LAI 可能仍是旧值，**不能当成设备最后所在位置的可靠证据**。

按错误判据走，报告里就冒出"该卡曾接入 MCC=FFFF 的网络"这种无意义表述。委托方一看会怀疑卡被漫游到境外，调查方向当场偏掉。

**其三，把卡内位置值当作带时间的轨迹。**

卡内位置值**记录位置与网络标识，但不记录时间**。这是它在本案中最关键的一点。

| 证据源 | 位置 | 时间 | 覆盖范围 |
|---|---|---|---|
| **卡内 `EF(LOCI)`** | 有（LAC，单值） | **无** | 仅最后一次注册 |
| 卡内 `EF(EPSLOCI)` `6FE3` | 有（TAI，粒度更粗） | **无** | 仅最后一次 LTE 驻留 |
| 运营商基站明细 | 有 | **有** | 需单独授权 |
| 手机侧基站信息缓存 | 部分 | 部分 | **历史位置只能从这里来** |

委托方要证明的是"在特定时段出现在案发地"，而卡内只能证明"最后一次注册在某个 LAC"。 缺了时间这一维，"最后一次"与"案发时段"之间的差距可能是数年。

因此本案的正确产出是"卡 1 最后注册于 LAC 2A10，卡 2 最后注册于 LAC 1B05，两者均无时间信息"，以及"要把它落到具体时段，需向运营商调取基站明细或从终端侧取基站历史"。

按错误判据走，报告会把卡内位置值直接对应到委托方的"特定时段"，拼出一条看似完整、实则没有时间支撑、也没有第二条数据的轨迹。委托方据此起诉，辩护方一核对就发现整条对不上。

**其四，把"PIN 试不出来"当作"没试"。**

委托方希望试 PIN。分析方若在未获书面授权的情况下尝试，即便全部失败，也构成程序瑕疵 —— **"没成功"不等于"可以做"**。

判据是**PIN 相关动作的授权要求**：

| 动作 | 是否需要单独授权 | 理由 |
|---|---|---|
| 读取 Transparent 文件 | 否 | 属公开数据 |
| 尝试 PIN | **是** | 属对通信内容的技术破解 |
| 申请运营商协助解锁 | **是** | 需法律文书 |
| 委托方书面确认不含解锁 | — | **本案已有** |

本案已获得"授权范围不含解锁"的书面确认，这条记录本身就是一项交付成果 —— 它记录了分析方在明知可以尝试的情况下选择不尝试。

按错误判据走，分析方为"帮委托方多找点东西"而试了 PIN。试失败，程序瑕疵补不回来；试成功，取得的数据可能因程序违法被整体排除。

**两种结果都会带来不可逆的损失。**

**其五，把卡内短信数量当成短信全貌。**

卡 2 的卡内短信只有 11 条，看起来"很少"。但这与实际收到的短信总量没有对应关系。

判据是**短信的两侧存储**：

| 位置 | 说明 |
|---|---|
| SIM 卡内存储 | 容量极小，通常几十条；且需按卡状态解锁 |
| 手机侧存储 | 系统应用数据库中的完整记录 |

卡内 11 条通常是"未读或未同步到手机"的那部分，甚至可能只是运营商侧残留的少量记录。真正有价值的短信在手机侧，而手机侧的取证需要设备解锁 —— 那属于另一条授权路径。

按错误判据走，委托方看到"卡内仅 11 条短信"，就认为嫌疑人只收到 11 条。这跟委托方掌握的通话与转账流水对不上，进而质疑卡 2 的归属。

<a id="section-42"></a>

### 5.2 设备卡号与网络的错配作为间接发现

**场景**

承接 5.1。检方在分析卡 1 时注意到一组不一致：卡的发行方标识段、SPN、IMSI 前缀与手机的 IMEI 所属地区**分属三个不同国家或地区**。

检方的问题是："这能不能定性为跨境电信诈骗？"

本案的核心是区分"观察"与"推论"，以及给一条有价值的间接发现标上它真实的证据强度。

**处置过程**

第一步，把四项观察逐条列出，**全部是可从检材直接读出的事实**：

```text
观察 1：卡 1 的 ICCID 发行方标识段为境外 MII（89 0X，非中国大陆 89860）
观察 2：卡 1 的 SPN 为境外运营商名称
观察 3：手机 IMEI 的 TAC 段对应机型为某国行版本
观察 4：卡 1 的 IMSI 前缀为 901-YY（第三国网络）
```

第二步，逐项判定每个字段的语义，避免把不同性质的标识混为一谈：

| 字段 | 标识的是什么 | 本案读数 | 语义 |
|---|---|---|---|
| ICCID 前 7–8 位 | **卡的发行方** | `89 0X` | 卡由境外运营商发行 |
| MCC/MNC | **卡注册的网络** | `901-YY` | 归属第三国网络 |
| SPN | **卡上存储的网络名** | 境外运营商名 | 与 ICCID 一致 |
| IMEI 的 TAC | **手机的出厂地** | 国行版本 | 设备在中国大陆生产 |

注意 `MCC/MNC = 901-YY` 这个读数很反常：`901` 在标准分配中不是常见的商用移动网号段。这类异常读数应被单独记录，而不是当作普通的境外网络处理。

第三步，把"三地不匹配"这一观察写清：

```text
设备、SIM 卡、号段分属三个不同国家或地区：
  设备制造地：中国大陆
  卡发行地：境外（ICCID 89 0X）
  卡注册网络：第三国（MCC/MNC 901-YY，异常读数）
```

第四步，逐条列出这一观察的全部可能解释：

| 可能解释 | 与观察的契合度 |
|---|---|
| 跨境电信诈骗 | 契合，但不是唯一解释 |
| 机主长期境外居住或工作 | 契合 |
| 商务出差频繁，使用境外漫游卡 | 契合 |
| 卡为代购或二手购入 | 契合 |
| 涉事后卡被调换 | 契合 |
| 号码被用于某种非本地业务（境外呼叫卡） | 契合 |

**这六种解释都不能排除。** 因此本案的正确产出是记录这一观察及其解释空间，而不是定性。

第五步，写明需要哪些外部证据才能收敛：

```text
收敛所需证据（均需另行调取）：
- IMEI 的实际使用地与驻留基站（运营商侧）
- IMSI 对应号码的开通地与实名信息（运营商侧）
- 资金流向中接收方所在地（支付或银行侧）
- 案发地周边基站的 SIM 卡注册记录（运营商侧）
```

**结论**

| 结论 | 支撑证据 | 强度 |
|---|---|---|
| 设备制造地、卡发行地、卡注册网络三者不一致 | ICCID 前缀、TAC、SPN 三源印证 | 强 |
| `MCC/MNC = 901-YY` 属异常读数 | 标准分配中非常见商用网号段 | 中（需以权威分配表核对，本次未获得） |
| 该不一致符合跨境电信诈骗的常见特征 | 统计意义上的类比 | **弱（类比，非证明）** |
| 不能仅凭 SIM 数据定性 | 存在六种同样契合的解释 | 强（否证结论） |

**能证明的**：三项标识字段的读数及其相互不一致。

**不能证明的**：
- **不能证明本案属跨境电信诈骗。** 六种解释中五种与合法场景同样契合
- **不能证明 `901-YY` 是有效网段。** 需以权威分配表核对，本次未获得
- **不能证明持卡人有跨境经历。** 卡可以是他人代为办理或购入
- 不能把这条观察与 5.1 的 LAI 第 5 条串成同一结论。 两者分属不同证据层

**未覆盖范围**：MCC/MNC 权威分配表、IMEI 实际使用地、号码开户信息、资金流向、案发地基站注册记录。

**误判对照**

**其一，把"三地不匹配"直接定性为跨境诈骗。**

检方的问题里已经预设了结论，而观察恰好符合这个预设。这是需要警惕的一种推理结构。

判据是**"类比证据"的正确用法**：

| 用途 | 是否成立 |
|---|---|
| 说明案件**具备**跨境特征 | 成立 |
| 说明案件**属于**跨境诈骗 | **不成立** |

**判据是问一句："这个观察有多少种解释？"** 本案六种，且五种是完全正常的商业场景。当正常解释与异常解释的契合度相同时，观察只能用于缩小范围，不能用于定性。

按错误判据走，报告就把类比写成了定性，检方据此推进起诉。而辩方只需举出"机主在境外工作三年"这一例，整条证据链就动摇了。

**这是容易被推翻、也较伤专业信誉的错误类型。**

其二，把 ICCID 前缀、MCC/MNC、SPN 当成同一个信息。

三个字段看起来都在说"这张卡属于哪里"，但它们的含义并不相同。

判据是**三类标识的归属对象**：

| 字段 | 归属对象 | 是否随漫游改变 |
|---|---|---|
| ICCID 前缀 | **发卡的运营商** | 不变 |
| SPN | 卡上存储的**网络名** | 卡写入后通常不变 |
| **MCC/MNC（`EF(PLMN Selector)` 静态读数）** | 卡**偏好注册到的网络** | 随写入变化 |
| **MCC/MNC（`EF(LOCI)` 等位置文件）** | **最后一次成功注册到的网络** | 每次更新覆盖写入 |

最关键的一点：卡内位置值是"最后一次注册"的快照，不是当前状态。 5.1 中卡 1 的 `EF(LOCI)` 记录 `460-01`，它说明卡**最后一次成功注册到**该网络；它既不说明卡现在在哪，也不包含任何更早的记录。

按错误判据走，报告会写"该卡注册网络为境外"，而实际当前注册在境内，或者反过来。这类错误在两份证据对质时立刻暴露，还牵连其他结论的可信度。

**其三，把 `901-YY` 当作普通的境外网号。**

`901` 不在常见的商用移动网号段分配内。这个读数有两种可能，都必须记下来：

| 可能 | 含义 |
|---|---|
| 非标准或特殊用途号段 | 需要专门核对分配表 |
| 读取或解析异常 | 部分工具对某些卡的读数不稳定 |

判据是**异常读数必须单独成条**：

```bash
# 换工具复读一次
$ atc -i card1.atr -d 901
$ python3 sim_read.py card1.bin --plmn
```

同一个字段用两个工具读出不同值时，正确表述是"读数存在工具间差异，待确认"，而不是任选一个写进报告。 本案 `MCC/MNC` 的 LAI 记录里只出现 `460-01` 与 `460-00`，**没有出现 `901`** —— 这个不一致本身就说明该读数需要复核。

按错误判据走，一个可能读错的值被当成关键证据写进报告。委托方据此向司法部门提交"卡注册于第三国网络"这一事实主张——而其他来源的证据（LAI）完全不支持。

**其四，把一项间接发现当作独立佐证。**

"三地不匹配"看起来信息量很大，但它与 5.1 的其他发现**并非互相独立**。

判据是**独立性要看数据的生成方**：

| 发现 | 数据源 | 与 5.1 是否独立 |
|---|---|---|
| 卡 1 的 `EF(LOCI)` 为 `460-01` / LAC `2A10` | 卡 1 的位置文件 | — |
| 卡 2 的 `EF(PLMN Selector)` 为 `460-00` | 卡 2 的静态标识 | 独立 |
| 卡 1 的 `EF(PLMN Selector)` 读数为 `901-YY` | 卡 1 的静态标识 | **部分独立** |
| IMEI 的 TAC 为国行 | 手机 IMEI | **完全独立** |

卡 1 的静态标识与位置文件都来自同一张卡，两者的信息在很大程度上重叠——`EF(LOCI)` 记录的正是这张卡最后一次注册到的网络，与 `EF(PLMN Selector)` 的取值描述的是同一维度。把它们当成两次印证，会造成"证据强度被高估"。

按错误判据走，报告写"三项独立证据共同指向跨境情形"，而其中两项来自同一张卡。委托方据此高估了结论的可靠性。

需要补充的是，这两项之间的重叠程度取决于它们的取值是否真的不同：若 `EF(PLMN Selector)` 与 `EF(LOCI)` 记录同一网络，两者是同一事实的两次呈现；若取值不同，则构成两条独立观察，但方向仍受同一张卡的写入控制。

**其五，把"间接发现"写成结论段。**

**观察与推论必须分栏，这是报告写作的硬性要求**：

```markdown
【观察】
- 卡 1 的 ICCID 前缀为 89 0X
- 卡 1 的 SPN 为境外运营商名称
- 手机 IMEI 的 TAC 对应国行机型
- 卡 1 的 MCC/MNC 读数为 901-YY（异常，待复核）

【推论】
- 三者分属三个不同国家或地区
- 该情形符合跨境业务或跨境犯罪的常见特征

【定性】
本案不具备对该观察进行案件定性的证据条件。
存在至少六种同样契合的解释（列表）。
收敛所需证据见"未覆盖范围"。
```

按错误判据走，报告里只写一段混合内容，读者分不清哪句是从卡上读出来的、哪句是分析方加的。

一旦混淆，观察的可信度会与推论的不可靠性互相拖累，最后两者都不被采信。

## 六、扩展阅读方向

SIM 卡是一条独立且有边界的证据线。往下走有三类延伸——换一种卡形态、往运营商侧延伸、回到设备侧做交叉。

**同层深入：卡的另一种形态与更深的结构**

- [APFS 容器与快照](../../filesystem/filesystem-apple-fs/filesystem-apple-fs-apfs.md) —— 不直接相关，但 eSIM 的内部存储同样是分层结构，理解苹果体系里"结构化分层文件"的共性有助于读 eSIM 相关材料。
- [iOS 系统痕迹与 DFU 恢复](../mobile-ios/mobile-ios-dfu.md) —— iPhone 侧 eSIM 的实际形态与取用限制。它讲了"设备已锁定时哪些痕迹还在、哪些拿不到"的完整边界，与本篇的 eSIM 差异互为参照。

**工具与规范：判据从哪来**

- [GSMA 规范体系](https://www.3gpp.org/) —— 权威依据：GSM 11.11 是 SIM 逻辑结构，31.102 是 USIM，SGP 系列是 eSIM。工具的兼容性、字段语义、哪些文件存在，全部以此为准。 工具报不出某个字段时，先查规范里它属于哪个版本。
- [ICCID / IMSI 号段分配](https://www.itu.int/) —— MCC/MNC 前缀对应国家与运营商，是归属判断的公开依据。IMSI 的国家代码看 MCC，运营商看 MNC。
- **LAC / 小区 ID 分配表** —— 向运营商或公开数据库查询。**这是位置分析的实际卡点**：LAI 能告诉你卡在哪个 LAC，但"这个 LAC 是哪个区"这一层数据公开渠道覆盖有限，通常必须通过运营商渠道获取。

**跨源关联：本卡与其他工件怎么串**

- [Android 数据存储总览](../mobile-android/mobile-android-android-data-storage-overview.md) —— 本篇重要的一组交叉。卡上的 IMSI 与手机本机的应用账号、`packages.xml` 里的安装记录、通话记录里的设备指纹是否能对上，决定了"卡与设备是否匹配"这个结论能不能成立。
- [iOS 备份与沙盒提取](../mobile-ios/mobile-ios-ios-backup-and-sandbox-extraction.md) —— iPhone 侧拿到的账号、通话、位置数据与 IMSI/MSISDN 的对应关系。
- [网络流量与 PCAP 取证](../../memory/memory-network/memory-network-pcap.md) —— IMSI / MSISDN 与蜂窝数据会话的关联。注意边界：LAI 与 TMSI 只存在于卡侧，基站侧的通话与上网记录需另行授权调取，不在卡上也不在流量里。
- [SQLite 基础与结构](../mobile-database/mobile-database-sqlite.md) —— 拿到 IMSI / ICCID 之后，与设备侧数据库里的账号、MAC、设备指纹做交叉匹配。

**判据与反例：这些"卡上没找到"不代表什么**

- [取证流程与原则](../../fundamentals/fundamentals-process/fundamentals-process-five-stage-forensics-process.md) —— 阴性发现的表述规范见该文的原则部分。**卡上没找到某条短信，不能推出"该短信不存在"。**
- [反取证手法与时间戳篡改检测](../../fundamentals/fundamentals-concepts/fundamentals-concepts-anti-forensics-and-timestamp-tampering.md) —— 卡被换掉、卡被注销、以及通过运营商侧停止服务导致的 LAI 停止更新，这些都会让"卡上最新记录停在某时点"看起来像设备停用。这个区分是本篇数据解读的前提之一。
- [时间戳换算](../../fundamentals/fundamentals-concepts/fundamentals-concepts-timestamps-and-timezones.md) —— 卡上时间字段的基准与量级判定。
- [合规授权与法律边界](../../fundamentals/fundamentals-practice/fundamentals-practice-legal-authorization-and-boundaries.md) —— 运营商侧数据调取、PIN 解锁的授权与最小化要求。

## 七、命令速查

```bash
# ===== 读卡器识别 =====
lsusb | grep -iE 'sim|smart.?card|ccid'
pcsc_scan                 # 列出 PC/SC 读卡器与卡内 ATR
# 确认内核 ccidd 正常：systemctl status pcscd

# ===== 基础信息（无需 PIN）=====
# ICCID（EF(ICCID) 在 MF 下，文件 ID 2FE2）
sim_read --select 3G00 --file 2FE2 --decode iccid
sim_read --select 2G00 --file 2FE2 --decode iccid

# PLMN 选择器 → MCC/MNC
sim_read --select 3G00 --file 6F30 --decode plmn

# 服务提供商名称
sim_read --select 3G00 --file 6F46 --decode spn

# 语言偏好 / 阶段标识
sim_read --select 3G00 --file 6F05 --decode language
sim_read --select 3G00 --file 6FAE --decode phase

# ===== 内容提取（需 PIN）=====
# 联系人（ADN）
sim_read --select 3G00 --file 6F3A --pin "$PIN" --decode adn
# 最近拨号（LDN）
sim_read --select 3G00 --file 6F44 --pin "$PIN" --decode ldn
# 短信（EF(SMS)）
sim_read --select 3G00 --file 6F3C --pin "$PIN" --decode sms

# ===== 位置相关 =====
# 最后一次注册位置（★ 单值透明文件 11 字节，卡上无历史）
sim_read --select 3G00 --file 6F7E --decode loci    # LAI + TMSI
sim_read --select 3G00 --file 6FE3 --decode epsloci # LTE TAI + GUTI
sim_read --select 3G00 --file 6F73 --decode psloci # P-TMSI + RAI

# ===== 遍历与留存 =====
# 完整文件树
sim_read --select 3G00 --tree
# 逐文件十六进制导出（留存凭据）
sim_read --select 3G00 --dump-all --out ./DigiForensics-sim-dump/
sha256sum DigiForensics-sim-dump/*.bin

# 物理转储（仅部分卡型支持）
sim_read --dump eeprom --out DigiForensics-sim.bin --select 3G00

# ===== 离线分析原始 dump =====
# 十六进制查看
xxd DigiForensics-sim.bin | head -40
# 提取 ICCID（EF(ICCID)，文件 ID 2FE2，位于 MF 下；末位为 Luhn 校验位）
python3 -c "
d=open('DigiForensics-sim.bin','rb').read()
i=d.find(b'\x6f\xe2')          # 文件 ID 标记
print('EF(ICCID) 段:', d[i:i+40].hex() if i>0 else '未找到')"
# ICCID 为 BCD 半字节编码，转十进制串
python3 -c "
import re
raw='8986001234567890123'
# 校验 Luhn（ICCID 末位为校验位）
def luhn(s):
    t=0
    for i,c in enumerate(reversed(s[:-1])):
        d=int(c)*(2 if i%2 else 1)
        t+=d//10+d%10
    return (10-t%10)%10
print('ICCID 长度', len(raw), '校验位应=', luhn(raw), '实际=', raw[-1])"
```

**通用原则**：所有 SIM 取证命令执行前，先跑 `--tree` 与 `--info` 确认卡状态与文件布局，再针对性读取。**不要在没有确认锁定状态的情况下尝试 PIN。**
