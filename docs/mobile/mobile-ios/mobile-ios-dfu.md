# iOS 系统痕迹与 DFU 恢复

<a id="section-1"></a>

## 一、概述

本篇要处理的是 iOS 取证里风险较高的一块：设备已锁定、备份做不了，但委托方仍希望知道设备上发生过什么。

这个局面下有两个前提必须先说清。它们决定了本篇的写作重点不是"怎么进系统"，而是"哪些事绝对不能做，以及在不能做的情况下还能拿到什么"。

**第一，备份与 DFU 是两件完全不同的事。**

| 误解 | 事实 |
|---|---|
| "进 DFU 就能做备份" | **DFU 模式本身不产生备份** |
| "DFU 可以解锁设备" | **DFU 恢复会清空设备数据** |
| "把设备放 DFU 就锁住证据了" | 恰恰相反——DFU/恢复模式本身不能作为数据保全手段；选择“恢复”或执行某些重刷流程通常会抹除用户数据。普通退出模式是否产生数据变化须结合型号、版本与实际操作记录判断，不能声称异常启动必然触发整机抹除 |

**第二，iOS 版本之间的路径与可用工件差异很大。**

iOS 17 起系统对部分路径与容器做了调整。用 iOS 15 时代的路径去查 iOS 17 的设备，会得出"数据不存在"的错误结论——而实际上是路径变了。

这类错误的杀伤力在于：它不是漏检，是把"没找到"写成了"不存在"。

本篇的核心问题是在"设备已锁定、备份不可用"的前提下，回答两个问题：**系统上还残留着哪些高价值痕迹**，以及 **DFU 究竟在什么情况下、经过什么程序才可以考虑**。

**在取证流程中的位置**：采集环节的边界判定层。

输入是 [iOS 备份与沙盒提取](mobile-ios-ios-backup-and-sandbox-extraction.md) 没能覆盖的部分——备份层通常拿不到 `knowledgeC.db`、通话记录、完整照片，这些只在设备层可见。

输出是**一份明确的能力边界声明**：哪些结论来自备份层、哪些来自设备层、哪些因状态受限不可获取。

这份声明本身是交付物的一部分，不是过程记录。

**涉及的证据形态**（保留真实产品的强制路径与文件名）：

| 形态 | 具体位置 | 说明 |
|---|---|---|
| 设备识别 | `ideviceinfo` 的 `UniqueDeviceID`、`ProductType`、`ProductVersion` | UDID 串联全部检材；`ProductType` 决定 DFU 按键流程 |
| 开机时间锚点 | `ideviceinfo` 的 `TimeIntervalSince1970` | 反映最近一次系统启动，**锁屏状态下可能读不到，读不到本身也是一条记录** |
| 短信 | `/private/var/mobile/Library/SMS/sms.db` | **已加密，需 passcode** |
| 通话记录 | `.../CallHistoryDB/CallHistory.storedata` | 时间、时长、方向 |
| 行为预测痕迹 | `.../CoreDuet/Knowledge/knowledgeC.db` | **被严重低估的一类痕迹**，见 [2.3](#section-5) |
| 系统偏好 | `.../Preferences/com.apple.*.plist` | 网络、定位、Safari 设置 |
| 照片元数据 | `/private/var/mobile/Media/PhotoData/` | EXIF、编辑历史、人脸与场景识别结果 |
| 系统日志 | `/private/var/logs/`、`system_logs.logarchive` | 崩溃、网络、诊断 |

设备最后活跃时间点、曾访问过哪些应用与网站类型、通话对象与时间、照片的拍摄与编辑史、以及**哪些数据因为设备状态拿不到**。

锁屏且未解锁时的数据内容（sms.db 加密需 passcode）；备份时点之后的行为；激活锁状态下的任何用户数据；**绕过激活锁不是本领域的技术问题，而是法律程序问题**。

**内容边界（这一节请务必读完）**：

- 不做越狱、不提供 DFU 绕过、不提供激活锁绕过。 遇到激活锁，正确做法是**如实记录设备状态并启动相应法律程序**，而不是寻找规避手段。任何声称"可以自行绕过激活锁"的第三方服务，其合法性与真实性都应高度怀疑——这也是涉诈案件常见的敲诈话术。
- **DFU 与刷写是本领域不可逆的操作之一。** 本篇给出进入与退出的完整记录要求，**目的是让你能判断它该不该被做、做了之后如何留痕**，而不是鼓励在未备份未授权的情况下尝试。
- 未完成备份、未获得明确授权之前，绝不能把扣押设备置于 DFU 或恢复模式，更不能执行任何刷写或恢复动作。 这不是技术建议，是证据保护的基本要求。很多案件的证据就是这样永久灭失的。

**读者前提**：需要 [iOS 备份与沙盒提取](mobile-ios-ios-backup-and-sandbox-extraction.md) 的备份层认知作为前提（**必须先确认备份确实做不到或覆盖不足**，本篇才是起点）。

还需要 Apple plist 与 SQLite 的基础，以及 [取证流程与原则](../../fundamentals/fundamentals-process/fundamentals-process-five-stage-forensics-process.md) 里不可逆操作的处理纪律。

**另外建议先读 [4.3](#section-27)**——那里集中了不可逆操作相关的陷阱。

## 二、核心原理

<a id="section-3"></a>

### 2.1 设备识别与开机时间

`ideviceinfo` 返回的字段中，有几个对取证意义特殊：

| 字段 | 含义 | 取证价值 |
|---|---|---|
| `UniqueDeviceID` | **UDID**，设备唯一标识 | ★★★★★ 串联该设备的所有检材 |
| `ProductType` | 硬件标识（如 `iPhone14,2`） | ★★★★ **决定 DFU 的进入方式** |
| `ProductVersion` | iOS 版本 | ★★★★★ 决定可用工件与路径 |
| `DeviceName` | 用户自命名 | ★★★ 常含姓名 |
| **`TimeIntervalSince1970`** | **自 1970 年以来的秒数** | ★★★★ **推算最近一次开机时间** |
| `TimeZone` | 时区 | ★★★ 时间线对齐必需 |
| `TotalDiskCapacity` / `TotalSystemCapacity` | 容量 | ★★ 校验备份完整性 |
| `InternationalMobileEquipmentIdentity` | IMEI | ★★★★ 设备标识（部分版本受权限限制） |

`TimeIntervalSince1970` 的价值：它反映的是**最近一次系统启动的时间点**。

开机时间是一条重要的时间线锚点——能界定"设备最后活跃于何时"，也能帮助判断设备是否在扣押前被重启过。

```bash
ideviceinfo | grep -E 'TimeIntervalSince1970|TimeZone|ProductType|UniqueDeviceID'
# TimeIntervalSince1970: 1725039652
# TimeZone: Asia/Shanghai
```

> **重要限制**：`ideviceinfo` 的可用字段**受设备状态与 iOS 版本影响**。未解锁或 iOS 较新时，部分字段返回不了。**拿不到的字段就是拿不到，不要臆造**——报告中应写"该字段在当前连接状态下不可读"。

<a id="section-4"></a>

### 2.2 高价值系统痕迹

以下是 iOS 上被广泛验证有取证价值的痕迹（路径随版本变化，务必实测）：

| 痕迹 | 典型路径 | 内容 | 价值 |
|---|---|---|---|
| **短信** | `/private/var/mobile/Library/SMS/sms.db` | 短信与 iMessage | ★★★★★ **已加密，需 passcode** |
| **通话记录** | `/private/var/mobile/Library/CallHistoryDB/CallHistory.storedata` | 通话时间、时长、方向 | ★★★★★ |
| **通讯录** | `/private/var/mobile/Library/AddressBook/AddressBook.sqlitedb` | 联系人，**含最近联系人** | ★★★★★ |
| **日历** | `/private/var/mobile/Library/Calendar/Calendar.sqlitedb` | 日程、提醒 | ★★★★ |
| **`knowledgeC.db`** | `/private/var/mobile/Library/CoreDuet/Knowledge/knowledgeC.db` | **见 2.3** | ★★★★★ |
| **系统偏好** | `/private/var/mobile/Library/Preferences/com.apple.*.plist` | 网络、定位、Safari 设置 | ★★★★ |
| **照片元数据** | `/private/var/mobile/Media/PhotoData/` | EXIF、编辑历史、**人脸与场景识别** | ★★★★ |
| **DCIM** | `/private/var/mobile/Media/DCIM/` | 原始照片与视频 | ★★★★ |
| **系统日志** | `/private/var/logs/`、`system_logs.logarchive` | 崩溃、网络、诊断 | ★★★ |
| **Safari** | `/private/var/mobile/Library/Safari/` | 历史、书签、缓存 | ★★★ |
| **键盘缓存** | `/private/var/mobile/Library/Keyboard/` | 输入统计、常用短语 | ★★★ |
| **Notes** | `/private/var/mobile/Library/Notes/`（旧版） | 备忘录 | ★★★★ |

```bash
# 备份中可直接查到的痕迹（不需越狱）
sqlite3 Manifest.db "
SELECT domain, relativePath FROM Files
WHERE relativePath LIKE '%knowledgeC%' OR relativePath LIKE '%CallHistory%'
   OR relativePath LIKE '%AddressBook%' OR relativePath LIKE '%sms.db%'
   OR relativePath LIKE '%Calendar%';"
```

> **一个必须知道的现实**：上表中的路径是**设备上的原始路径**，**只有在已越狱设备或物理镜像上才能直接读取**。通过备份（[06](mobile-ios-ios-backup-and-sandbox-extraction.md)）能拿到的是**参与备份的那部分**——`knowledgeC.db`、通话记录、完整照片等**通常不在普通备份范围内**。**报告中必须写清每个结论来自哪一层获取。**

<a id="section-5"></a>

### 2.3 `knowledgeC.db`：被严重低估的痕迹

`knowledgeC.db` 是 iOS 的**行为预测与知识库**（CoreDuet / Knowledge 框架），它缓存了系统学习到的关于用户的大量信息：

| 内容 | 说明 | 取证意义 |
|---|---|---|
| **应用使用记录** | 打开过哪些 App、频次、时段 | **建立使用习惯画像** |
| **搜索关键词** | 系统 Spotlight 中搜索过的词 | **★ 常含用户主动搜索的敏感词** |
| **位置与时间的关联** | 常去地点、到达/离开时间 | **★ 建立行踪模式** |
| **联系人交互频次** | 与谁联系最频繁 | **★ 关系亲疏排序** |
| **邮件/消息实体** | 主题、行踪摘要 | 辅助印证 |

**为什么它特别有价值**：它是**系统自动记录的，不是用户主动创建的**。**用户不会想到去清理它**——因此它常常比聊天记录保存得更久、更完整。

> **一个反直觉的推论**：当某个 App 的聊天数据库已经被清理或加密无法读取时，`knowledgeC.db` 里往往还残留着该 App 的使用记录、搜索关键词、以及从该 App 提取的实体摘要。这构成了"交叉印证"而非"直接证明"，报告中必须严格区分这两者。

<a id="section-6"></a>

### 2.4 iOS 版本差异（必须实测，不能套用）

| 版本 | 变化 | 对取证的影响 |
|---|---|---|
| iOS 13+ | 部分 App 数据迁到 `App Group` 共享容器 | 备份中 `relativePath` 含 `Containers/Shared/AppGroup/` |
| iOS 15+ | 更多 App 转向沙盒化存储 | 部分历史路径失效 |
| **iOS 17+** | **系统部分路径与容器结构调整** | **旧路径假设可能完全失效** |
| iOS 17+ | Safari 相关数据更多走容器化路径 | 需按 BundleID 定位容器 |

**实战原则**：

```bash
# ★ 不要硬编码路径。先列出实际有什么
# 备份中：把所有与目标相关的路径列出来，再逐个确认
sqlite3 Manifest.db "SELECT domain, relativePath FROM Files
WHERE relativePath LIKE '%Safari%' OR domain LIKE 'AppDomain-com.apple.mobilesafari%';"
```

> **本篇无法给出"iOS 17+ 的确切新路径"**，因为具体调整在不同机型与版本上并不完全一致。**正确做法是实测 + 记录**，而不是引用任何"版本对照表"。**这是本篇刻意保留的不确定性，报告中也应如此表述。**

<a id="section-7"></a>

### 2.5 DFU 与恢复模式：必须先讲清后果

DFU 会改写设备上的系统分区状态，属于对检材的写入操作。接入方式、只读优先原则与移动取证箱的要求见[取证装备与写保护器](../../fundamentals/fundamentals-practice/fundamentals-practice-forensics-equipment-and-write-blockers.md)。

这两种模式完全不是一回事，按键流程也完全不同，绝不可混记。

| 对比项 | **DFU**（Device Firmware Update） | **恢复模式**（Recovery Mode） |
|---|---|---|
| 层级 | **固件/引导加载层**，不启动 iOS 本体 | **系统层**，已启动最小 iOS 组件，能与电脑交互 |
| 是否加载 iOS | 否 | 是（精简环境） |
| 主机端可用的工具 | 刷写/固件类工具 | `ideviceinfo` 可用；AFC 通道与 `idevicebackup2` 是否可用取决于设备实际状态，见下 |
| 能否做加密备份 | **不能** | **不能**（无用户数据，无密钥材料可用） |
| 主要用途 | 刷固件、恢复固件、诊断 | 恢复系统、重装、诊断 |
| 对数据的影响 | 刷写即清空 | 恢复/重装即清空 |

> 恢复模式的能力边界必须按实际状态收窄，不能笼统说"工具都能用"：
> 恢复模式下的可用性取决于三件事——**① 设备是否已通过安全验证**（未解锁则 `lockdownd` 不接受会话，表现为 `Could not connect to lockdownd`）；**② AFC 通道是否已建立**（依赖设备与主机配对状态）；**③ 具体 iOS 版本与工具版本**。
> 实操上：先用 `ideviceinfo` 探测，能返回机型即基本可用；返回 `Could not connect to lockdownd` 就说明会话建不起来，AFC 与备份类工具都不要再尝试。 任何"恢复模式下可以取出沙盒数据"的说法都应视为错误。

> ⚠️⚠️ **要强调的一条警告**：
> **进入 DFU 或恢复模式本身不会立刻清除数据**，真正不可逆的是**后续的刷写、恢复、重装动作**——这些操作会重写系统分区并抹除用户数据。此外，DFU/恢复模式本身不能作为数据保全手段；选择“恢复”或执行某些重刷流程通常会抹除用户数据。普通退出模式是否产生数据变化须结合型号、版本与实际操作记录判断，不能声称异常启动必然触发整机抹除（Erase All Content and Settings），这是设备的保护性重置行为。
>
> 因此在未完成备份、未获得明确授权之前，绝不能把扣押设备置于这两种模式，更不能执行任何刷写或恢复动作。 这不是技术建议，而是**证据保护的基本要求**——很多案件的证据就是这样永久灭失的。

iPhone 8 及以后与 iPhone 7 及以前，进入 DFU 的按键流程完全不同：

| 机型 | 进入 **DFU** | 退出 DFU |
|---|---|---|
| **iPhone 8 / X 及以后**（Face ID 机型，**无物理 Home 键**） | **1)** 电脑已识别设备后用工具触发；**2)** 快速按住**侧边键** 2 秒 → 不松手**追加按住音量下**约 4 秒 → **松开侧边键**，**继续只按住音量下**约 10 秒（**屏幕保持全黑**，这是判据） | 按住**侧边键 + 音量上**，直到出现 Apple 标志 |
| **iPhone 7 / 7 Plus 及更早**（有 Home 键） | **1)** 同时按住**电源键（或侧边键）+ 音量下**；**2)** 保持约 8–10 秒，看到 Apple 标志后**松开电源/侧边键**，**继续只按住音量下**约 8 秒（**屏幕变黑**是判据） | **按住电源键 + Home 键**，直到出现 Apple 标志 |

**两者的关键差异（务必记牢）**：iPhone 8+ 是先侧边键、再追加音量下（串行），全程无 Apple 标志直接黑屏；iPhone 7 及更早是电源键与音量下同时按（并行），先出现 Apple 标志随后黑屏。

> iPhone 8 及以后没有物理 Home 键，因此「按住 Home 键」这套流程完全不适用。 用 iPhone 7 的方法操作 iPhone 8+ 会**直接进入恢复模式或正常启动**，而这两种情况都不是 DFU。
>
> 另外：上述为通行的参考时序，具体秒数在不同 iOS 版本与工具链下存在差异。 iPhone 15 及以后的机型在部分地区已进一步调整按键组合。实机操作前应查阅对应机型与当前 iOS 版本的官方指引，并在检查笔录中记录每一步按键与屏幕状态。

<a id="section-8"></a>

### 2.6 设备锁与激活锁

| 机制 | 说明 | 取证影响 |
|---|---|---|
| **锁屏密码（passcode）** | 解锁设备、启用部分数据类 | 备份需要它；部分数据需要它 |
| **激活锁（Activation Lock）** | 绑定 Apple ID 的设备锁 | **需 Apple ID 与密码才能解除** |
| **MDM 远程管理** | 企业设备可远程锁定/抹除 | **扣押后企业可能远程执行，影响证据** |

> ⚠️ **激活锁的法律现实**：绕过激活锁在多数司法辖区都需要走官方的司法协助/法律程序，由 Apple 或执法机关依申请处理。任何声称"可以自行绕过激活锁"的第三方服务，其合法性与真实性都应高度怀疑——这也是涉诈案件中常见的敲诈话术。
>
> **取证中的正确做法**：遇到激活锁，**如实记录设备状态并启动相应法律程序**，而不是寻找规避手段。这既是法律要求，也是保护检材不被第三方工具破坏的考虑。

## 三、操作步骤

<a id="section-10"></a>

### 第 1 步：设备识别与状态固定

```bash
sudo apt install libimobiledevice-utils usbmuxd
sudo usbmuxd &

idevice_id -l
ideviceinfo > device-info.txt
grep -E 'UniqueDeviceID|ProductType|ProductVersion|DeviceName|TimeIntervalSince1970|TimeZone' \
  device-info.txt
sha256sum device-info.txt | tee device-info.sha256
```

```bash
# 换算最近一次开机时间（Python 避免时区歧义）
python3 - <<'PY'
import datetime, subprocess, re
out = subprocess.run(["ideviceinfo"], capture_output=True, text=True).stdout
m = re.search(r"TimeIntervalSince1970:\s*(\d+)", out)
t = re.search(r"TimeZone:\s*(\S+)", out)
if m:
    ts = int(m.group(1))
    tz = t.group(1) if t else "UTC"
    print("TimeZone:", tz)
    print("UTC   :", datetime.datetime.utcfromtimestamp(ts))
    print("Local :", datetime.datetime.fromtimestamp(ts))
PY
```

<a id="section-11"></a>

### 第 2 步：判断设备可用层级

```bash
# 能否备份（最基本的能力探测）
ideviceinfo >/dev/null 2>&1 && echo "可通信" || echo "不可通信"

# 备份是否需要口令
idevicebackup2 -i backup /tmp/probe-backup/ 2>&1 | head -5
# 提示 "Please enter backup password" → 加密备份
# 提示 "backup is encrypted"   → 同样

# 激活锁状态（若已启用，部分字段会显示 ActivationState）
ideviceinfo | grep -iE 'Activation|ProductType|ProductVersion'
```

| 结果 | 结论 |
|---|---|
| 能通信 + 提示输入备份口令 | 设备已解锁且信任，备份为加密 |
| 能通信 + 备份直接完成 | 备份未加密（但可能不含 Keychain） |
| `ActivationState: Activated` | 激活锁已激活，**解除需 Apple ID 与法律程序** |
| 无法通信 | 未解锁 / 未信任 / 连接异常，**不要尝试 DFU** |

<a id="section-12"></a>

### 第 3 步：执行备份（DFU 之前的必要动作）

```bash
mkdir -p /work/ios-backup
idevicebackup2 -i backup /work/ios-backup/ 2>&1 | tee backup.log
tail -5 backup.log
du -sh /work/ios-backup/*/
```

**备份完成后的立即核对**（这决定了是否具备做进一步操作的前提）：

```bash
BK=$(ls -d /work/ios-backup/*/ | head -1)
plutil -p $BK/Info.plist | grep -E 'Last Backup Date|Device Name'
plutil -p $BK/Status.plist | grep IsFullBackup
ls $BK/Manifest.db && echo "Manifest.db 存在 ✓"
find $BK -type f | wc -l
```

> 只有当备份完成、且 `Status.plist` 显示正常、`Manifest.db` 存在时，才具备进入下一步讨论的前提。"未完成备份就进 DFU"的后果无法挽回。

<a id="section-13"></a>

### 第 4 步：痕迹清点与 `knowledgeC.db` 分析

```bash
# ① 能从备份查到的痕迹
sqlite3 $BK/Manifest.db "
SELECT domain, relativePath FROM Files
WHERE relativePath LIKE '%knowledgeC%'  OR relativePath LIKE '%CallHistory%'
   OR relativePath LIKE '%AddressBook%' OR relativePath LIKE '%Calendar%'
   OR relativePath LIKE '%sms.db%'      OR relativePath LIKE '%PhotoData%'
ORDER BY domain, relativePath;"

# ② 已越狱设备上的系统痕迹（合法授权前提下）
idevicefs -u /private/var/mobile/Library/CoreDuet/Knowledge/ ls
idevicefs -u /private/var/mobile/Library/SMS ls
```

拿到 `knowledgeC.db` 后（**先看结构，不要直接 `SELECT *`**）：

```bash
sqlite3 knowledgeC.db ".tables"
sqlite3 -header -column knowledgeC.db "
SELECT ZKEY, ZVALUE FROM ZENTITY
WHERE ZKEY LIKE '%search%' OR ZVALUE LIKE '%关键词%' LIMIT 20;"   -- 表名随版本变化
strings -n 6 knowledgeC.db | grep -iE 'com\.[a-z]+\.[a-z]+' | sort | uniq -c | sort -rn | head -20
# → 应用 BundleID 及其出现频次，反映使用强度
```

> **`knowledgeC.db` 的分析纪律**：它记录的是**系统推断与缓存**，**不等于用户的实际行为**。报告中应写「该数据库记录了……」，而不是「用户做了……」。 这一措辞差别在法律场景中很重要。

<a id="section-14"></a>

### 第 5 步：若确需 DFU——进入与退出的完整记录

> ⚠️ **前置条件（三条全部满足才可进行）**：
> 1. **备份已完成并验证**（第 3 步的核对全部通过）；
> 2. **已获得书面授权**明确允许进入 DFU；
> 3. **已评估数据损失风险**并记录评估结论。

```bash
# ① 进入前完整记录设备状态
ideviceinfo > pre-dfu-state.txt && sha256sum pre-dfu-state.txt

# ② 用工具或按键触发（见 2.5），判据是「iOS 未启动 + 屏幕全黑」
#    iPhone 8+（无 Home 键）：按住 侧边键 2 秒 → 不松手追加按住 音量下 约 4 秒
#               → 松开 侧边键，继续只按住 音量下 约 10 秒 → 屏幕应全黑
#    iPhone 7 及更早（有 Home 键）：同时按住 电源键 + 音量下 8–10 秒
#               → 出现 Apple 标志后 松开 电源键，继续只按住 音量下 约 8 秒 → 屏幕转黑
ideviceinfo 2>&1 | head -5     # 连不上属正常：DFU 下 lockdownd 不运行
date -Is | tee dfu-entry-time.txt

# ③ 执行目标操作（具体命令因目的而异，此处不复述破坏性操作）

# ④ 退出 DFU（务必记录时间）
#    iPhone 8+：按住 侧边键 + 音量上，直到出现 Apple 标志
#    iPhone 7 及更早：按住 电源键 + Home 键，直到出现 Apple 标志
date -Is | tee dfu-exit-time.txt
ideviceinfo 2>&1 | head -5
```

<a id="section-15"></a>

### 第 6 步：退出后的验证（必做）

```bash
# ① 确认设备仍可通信
idevice_id -l && ideviceinfo | grep ProductVersion

# ② 确认激活锁状态未被改变
ideviceinfo | grep -i Activation

# ③ 确认备份仍完整
sqlite3 $BK/Manifest.db "PRAGMA integrity_check;"
find $BK -type f | wc -l

# ④ 重新获取设备状态，与 DFU 前对比
ideviceinfo > post-dfu-state.txt
diff pre-dfu-state.txt post-dfu-state.txt | head -20
# 无关键差异 → 设备状态未发生实质变化 ✓
```

## 四、常见陷阱

<a id="section-17"></a>

### 4.1 状态判定与能力边界

<a id="section-18"></a>

#### 陷阱 1：把"设备已扣押"等同于"设备可通信"

**现象**：接到委托后直接执行备份命令，失败后报告写"设备无法连接，疑似损坏"，进而考虑用 DFU 等其他方式。

**原因**：**设备不可通信的原因通常是状态性的，不是损坏性的**。

锁屏未解锁、屏幕上的"信任此电脑"提示未被确认、USB 连接不稳定、线缆供电不足、`usbmuxd` 未运行，都会表现为"连不上"。

而真正的硬件损坏在现象上反而更具体：识别到但传输中断、反复掉盘。

把"我连不上"直接归因到最严重的解释，却没有先排除最常见的几种——这是误判的来源。

**影响**：**可能引导出错误的技术路线**。

如果因此转向 DFU，而真实原因只是忘了点"信任"或 `usbmuxd` 没跑，那么一次完全不必要的、有数据风险的处置就发生了。

**核查**：按状态性原因逐项排除，并如实记录"不可读"而非"损坏"。

```bash
sudo usbmuxd &                        # ★ 不跑会直接报 no device found
idevice_id -l                         # 能否枚举到设备
ideviceinfo 2>&1 | head -5
# Could not connect to lockdownd  → 未解锁 / 未信任 / 会话建不起来
```

报告中的表述应为："`<工具>` 在 `<时间>` 的返回结果为 `<原始信息>`，据此判断设备处于 `<未解锁/未信任/连接异常>` 状态，不构成设备硬件损坏的证据；该状态下相关字段不可读。"

<a id="section-19"></a>

#### 陷阱 2：把"字段不可读"补写成推测值

**现象**：`ideviceinfo` 未返回 `TimeIntervalSince1970`，分析师根据其他线索"推断"设备最近开机时间约为某日，写进了时间线。

**原因**：`ideviceinfo` 的可用字段受设备状态与 iOS 版本共同影响。锁屏状态下部分字段直接不返回。

未解锁时，设备不会、也不应该告诉分析机"我什么时候开的机"。**拿不到的字段就是拿不到**，任何"推断"都是在无来源的情况下造一个数字出来。

**影响**：**时间线中出现一个无来源的锚点**。

开机时间在时间线推理中作用很大——界定最后活跃时段、发现扣押前的重启。一旦这个锚点是编的，后续所有基于它的推论都会跟着错，而报告上它与其他实测字段长得一样。

**核查**：**不可读就记为不可读，并把它本身作为状态证据**。

```bash
grep -E 'TimeIntervalSince1970' device-info.txt
# 无输出 → 在当前连接状态下不可读
```

报告句式："`TimeIntervalSince1970` **在当前连接状态下未返回**，据此**无法给出最近一次开机时间**。该字段不可读本身说明设备处于 `<锁屏/受限连接>` 状态，应在设备解锁后补取。"

把"没取到"变成一条有价值的观察，而不是一个需要填补的空白。

<a id="section-20"></a>

#### 陷阱 3：把 DFU 或恢复模式当作备份手段

**现象**：正常模式下备份失败（设备锁屏），分析师提议"放进 DFU 再试试备份"，理由是"DFU 是更底层的方式"。

**原因**：DFU 是固件/引导加载层，iOS 本体根本没有启动，没有用户数据，也没有加密备份所需的密钥材料。

恢复模式虽然启动了精简 iOS 组件，但同样没有用户数据。

两种模式**都不能产生备份**。

而且"DFU 下 `ideviceinfo` 完全无响应"这一点本身就是判据：如果分析师发现设备还有响应，那说明根本不在 DFU 里。

**影响**：**用一个不可能成功的方案消耗委托方的时间与信任**。

更实际的风险是：为了"试试看"而把设备置于这两种模式，而从这两种模式启动回正常系统时若启动被判定为异常，iOS 可能触发「抹掉所有内容和设置」。

**核查**：备份只能在正常模式、设备已解锁、已信任的条件下完成，这一点没有替代方案。

| 模式 | `ideviceinfo` | 能否备份 | 能否取用户数据 |
|---|---|---|---|
| 正常模式（已解锁+已信任） | 返回完整字段 | **可以** | 备份范围内可以 |
| 正常模式（锁屏） | 报 `Could not connect to lockdownd` | 不可以 | 不可以 |
| 恢复模式 | 通常可返回机型 | **不可以** | **不可以**（无用户数据） |
| DFU | **完全无响应** | **不可以** | **不可以** |

**恢复模式下的能力必须按实际状态收窄**：它能否建立 AFC 通道取决于设备是否已通过安全验证、是否已与主机配对、以及 iOS 与工具版本。

先用 `ideviceinfo` 探测，返回机型即基本可用；返回 `Could not connect to lockdownd` 就说明会话建不起来，AFC 与备份类工具都不要再尝试。

<a id="section-21"></a>

#### 陷阱 4：混淆 DFU 与恢复模式

**现象**：检查笔录里写"设备已进入 DFU"，但同页又记录了"`ideviceinfo` 返回了机型与版本"，两处记录互相矛盾。

**原因**：**这两个模式的主机端可观测特征截然不同**。

DFU 下 `lockdownd` 不运行，主机端工具**完全无响应**。恢复模式下已启动最小 iOS 组件，`ideviceinfo` 通常能返回机型。

两者的按键流程也完全不同。分析师若只记了个"低层模式"的模糊说法，事后无法还原当时到底处于哪一种。

**影响**：**检查笔录失去证据价值**。

DFU 属于对检材状态有影响的操作。事后若说不清"当时到底是哪个模式、屏幕什么状态、按了哪些键、持续多久"，整个处置过程的合规性都无法自证。

**核查**：用主机端可观测特征反证模式，并逐步记录按键与屏幕状态。

```bash
# 进入后立即探测：这一条输出直接决定当前是哪种模式
ideviceinfo 2>&1 | head -5
# 有机型输出 → 恢复模式；完全无响应 → DFU
```

检查笔录必须包含：机型（`ProductType`）、按键序列与每步的屏幕状态、进入与退出的精确时间、主机端工具的探测结果。

并注意 DFU 的判据是"iOS 未启动 + 屏幕全黑"——DFU 下 iOS 根本不启动，不会出现 Apple 标志。若看到 Logo，说明走的不是 DFU 那条路径。

<a id="section-22"></a>

### 4.2 机型路径与痕迹解读

<a id="section-23"></a>

#### 陷阱 5：用 iPhone 7 的按键方法操作 iPhone 8 及以后机型

**现象**：分析师凭记忆操作一台 iPhone 14，按住电源键 + Home 键，结果设备进入了恢复模式或干脆正常启动了，随后设备状态与预期不符。

**原因**：iPhone 8 及以后（Face ID 机型）没有物理 Home 键，iPhone 7 那套"电源键 + Home 键"的流程从根上不适用。

而两代的正确流程不只是"按键不同"，连**逻辑顺序都不同**：8+ 是**先侧边键、再追加音量下（串行）**，全程无 Apple 标志直接黑屏；7 系及更早是**电源键与音量下同时按（并行）**，先出现 Apple 标志随后黑屏。

"DFU 进入方法"被当成一条固定知识记着，而它实际是**按机型分叉的**——误判就是这么来的。

**影响**：**设备进入了一个非预期模式**，而此时若继续按原计划操作，后果不可控。

此外，**"我以为进了 DFU"这个误判会贯穿后续所有操作**。

**核查**：先读 `ProductType` 确认机型代际，再查对应版本的官方指引。

| 机型 | 进入 DFU | 退出 DFU |
|---|---|---|
| **iPhone 8 / X 及以后**（无物理 Home 键） | 侧边键 2 秒 → 不松手追加音量下约 4 秒 → **松开侧边键**，继续只按音量下约 10 秒（**全程屏幕全黑**） | 侧边键 + 音量上，直到出现 Apple 标志 |
| **iPhone 7 / 7 Plus 及更早**（有 Home 键） | 同时按住电源/侧边键 + 音量下，保持约 8–10 秒 → 见 Apple 标志后**松开电源键**，继续只按音量下约 8 秒（**屏幕转黑**） | 电源键 + Home 键，直到出现 Apple 标志 |

```bash
ideviceinfo | grep ProductType       # iPhone14,5 → 属 iPhone 8 及以后
```

> 具体时序在不同 iOS 版本与工具链下存在差异，部分地区的新机型还可能进一步调整。实机操作前应查阅对应机型与当前 iOS 版本的官方指引，并把每一步按键与屏幕状态记入检查笔录。参考时序不是操作依据。

<a id="section-24"></a>

#### 陷阱 6：硬编码 iOS 路径，把"路径变了"当成"数据不存在"

**现象**：按 iOS 15 时代的路径去查一台 iOS 17 设备，`/private/var/mobile/Library/Safari/` 下什么都没有，报告写"该设备未访问过目标网站"。

**原因**：iOS 13 起部分 App 数据迁到 `App Group` 共享容器，15 起更多 App 转向沙盒化存储，17 起系统部分路径与容器结构进一步调整。

结果是旧路径失效，而**新的确切路径在不同机型与版本上并不完全一致**——没有任何一张"版本对照表"能覆盖全部情况。

把某篇文章里抄来的路径当成事实，这是误判的来源。

**影响**：**制造出一条无法支撑的否定结论**。

而"未访问过"是比"存在访问记录"更需要证据的陈述——证明一件积极事实需要证据，证明一件否定事实需要穷尽的检索。

**核查**：**先列出实际有什么，再解读；路径假设必须实测确认**。

```bash
# 备份中：把所有相关路径列出来，再逐个确认
sqlite3 Manifest.db "SELECT domain, relativePath FROM Files
WHERE relativePath LIKE '%Safari%' OR domain LIKE 'AppDomain-com.apple.mobilesafari%';"

# 已越狱或物理镜像：先列目录，不假设结构
idevicefs -u /private/var/mobile/Library/ ls
```

**这是本篇刻意保留的不确定性**：iOS 17+ 的确切新路径无法在通用文档中给出，正确做法是**实测并把实测结果写进报告**，而不是引用任何版本对照表。

若某路径在本检材上不存在，报告必须写"**该路径在本设备与版本上未出现**"，而不是"数据不存在"。

<a id="section-25"></a>

#### 陷阱 7：把 `knowledgeC.db` 的内容当作用户行为证据

**现象**：从 `knowledgeC.db` 中检索到某 App 的 BundleID 与搜索关键词，报告写"用户于某日搜索了某关键词"、"用户频繁使用某应用"。

**原因**：`knowledgeC.db` 记录的是系统推断与缓存，不是用户主动创建的行为记录。

其中的实体是 CoreDuet 框架从各种来源（Spotlight、通知、通讯录交叉引用、第三方 SDK 提供的"知识"）聚合推断出来的，可能来自**其他 App 提交的上下文**，而不是用户在涉案 App 内的实际操作。

系统还可能在用户从未打开某 App 时就记录了它的存在。

**影响**：**在措辞层面就把推断写成了事实**。

这类差异在法律场景中非常关键——"该数据库记录了……"是可接受的证据表述，而"用户做了……"是超出材料支持范围的断言，且难以撤回。

**核查**：**用记录性措辞，并标注来源层级**。

| 不可接受 | 可接受 |
|---|---|
| "用户搜索了 X" | "**该数据库记录了**与 X 相关的搜索条目" |
| "用户频繁使用某 App" | "**系统中存在**该 App 的知识条目，频次为 N" |
| "用户与某人关系密切" | "**系统记录了**二者的交互条目" |

```bash
# 先看结构，不要直接 SELECT *
sqlite3 knowledgeC.db ".tables"
# 表名随版本变化，实际以 .tables 输出为准
```

同时要区分证据类型：`knowledgeC.db` 与某个 App 的聊天记录**相互印证**时属于**交叉印证**，而它**单独存在时只说明系统层面有该记录**。报告必须把这两者明确区分开。

<a id="section-26"></a>

#### 陷阱 8：忽略"备份层"与"文件系统层"的区别

**现象**：报告在"痕迹清单"中列了 `knowledgeC.db`、通话记录、完整照片元数据等条目，并统一按"已获取"处理，而这些条目实际并不在普通备份范围内。

**原因**：2.2 表格里的路径是设备上的原始路径，只有在已越狱设备或物理镜像上才能直接读取。

通过备份能拿到的只是**参与备份的那部分**。`knowledgeC.db`、通话记录、完整照片元数据等**通常不在普通备份范围内**。

两者的获取层级不同，报告却混在同一张表里，读者无法区分哪些是本次真实拿到的、哪些只是"理论上存在"。

**影响**：**报告的覆盖范围被系统性高估**。

委托方会按这份清单安排下一步工作，而这些数据实际并不在手上。

**核查**：痕迹清单必须带"获取层级"列，并在结论中写明每条来自哪一层。

| 痕迹 | 普通备份 | 越狱/物理镜像 | 本案状态 |
|---|---|---|---|
| 短信、通讯录、日历、Safari | 通常可见 | 可见 | **以 `Manifest.db` 实测为准** |
| 通话记录 `CallHistory.storedata` | 通常不可见 | 可见 | **实测确认，不套用惯例** |
| `knowledgeC.db` | 通常不可见 | 可见 | 同上 |
| 完整照片元数据与 EXIF | 部分可见 | 可见 | 同上 |
| Keychain | 不可见 | 可见 | 同上 |

```bash
# 在备份中逐项实测，而不是套用"通常可见/不可见"的结论
sqlite3 Manifest.db "SELECT domain, relativePath FROM Files
WHERE relativePath LIKE '%knowledgeC%' OR relativePath LIKE '%CallHistory%'
   OR relativePath LIKE '%AddressBook%' OR relativePath LIKE '%sms.db%';"
```

**报告规范**：每条痕迹结论后标注"来源：备份层 / 已越狱设备 / 物理镜像 / 未获取"，并附实测查询命令。

<a id="section-27"></a>

### 4.3 ★ 不可逆操作与外部干预

<a id="section-28"></a>

#### 陷阱 9：★ 未完成备份就把设备置于 DFU 或恢复模式

**现象**：正常模式下备份失败，分析师未与委托方确认，直接把设备放入 DFU 模式准备刷写；或虽进入 DFU 但未执行刷写，退出后设备触发了「抹掉所有内容和设置」。

**原因**：这里有两层误解。

**第一层**是把"进入 DFU"当成无害的准备动作。实际上**进入本身就会改变设备状态**，而从这两种模式启动回正常系统时，**若启动被判定为异常，iOS 可能触发保护性重置**。

**第二层**是认为"只要不刷写就没事"。刷写、恢复、重装才是不可逆的真正环节，进入模式与退出过程本身同样有风险。

"设备已经锁了，再进一层模式不会更糟"——设备状态的恶化恰恰从这里开始。

**影响**：**这是难以补救的错误。**

如果设备此前未备份，全部本地数据可能一次性灭失，且**无法通过任何技术手段恢复**。

委托方的损失不可弥补，而分析师的操作在事后很难被认定为"合理尝试"。

**核查**：**三条前置条件全部满足才可进行，且过程必须完整记录**。

```
1. 备份已完成并验证（Manifest.db 存在、Status.plist 正常、integrity_check 通过）
2. 已获得书面授权，明确允许进入 DFU
3. 已评估数据损失风险并记录评估结论
```

```bash
# 进入前：完整固定状态
ideviceinfo > pre-dfu-state.txt && sha256sum pre-dfu-state.txt
# 过程中：记录进入与退出的精确时间
date -Is | tee dfu-entry-time.txt
date -Is | tee dfu-exit-time.txt
# 退出后：必须做 diff 验证（见陷阱 10）
```

**流程纪律**：任何涉及可能不可逆的处置，必须先在报告中说明后果、取得书面授权，再执行；这不是技术建议，而是证据保护的基本要求。

<a id="section-29"></a>

#### 陷阱 10：退出 DFU 后不做状态验证

**现象**：从 DFU 退出后，分析师只确认了"设备能开机"，就认为处置完成、检材状态正常。

**原因**：**设备能开机与设备状态未变是两件事**。

保护性重置的执行痕迹——名称被清空、激活锁状态异常、已装应用消失、连接需要重新信任——不一定表现为"开不了机"，而更像"能开机但一切重新开始"。

而如果分析师在报告里写了"设备状态正常"，这份记录就会成为唯一的现场状态证明。一旦事后发现异常，无法自证。

**影响**：**失去"检材状态未被实质改变"这一结论的证据基础**。

这一条在质证时是直接被问的："你怎么证明进入 DFU 前后设备状态一致？"

**核查**：进入前后各取一次完整状态并做 diff，差异逐项解释。

```bash
# 进入前
ideviceinfo > pre-dfu-state.txt && sha256sum pre-dfu-state.txt

# 退出后（必做）
ideviceinfo > post-dfu-state.txt
diff pre-dfu-state.txt post-dfu-state.txt | head -20
# 无关键差异 → 设备状态未发生实质变化 ✓

# 三项独立确认
idevice_id -l && ideviceinfo | grep ProductVersion   # 可通信
ideviceinfo | grep -i Activation                       # 激活锁状态未变
sqlite3 $BK/Manifest.db "PRAGMA integrity_check;"       # 备份仍完整
```

**diff 结果必须写入检查笔录**，并逐项解释任何差异的来源。若确实出现了状态变化（如 `DeviceName` 被清空），**如实记录并说明可能原因，不做推断**。

<a id="section-30"></a>

#### 陷阱 11：把"无法获取"写成"未发现"

**现象**：设备处于锁屏状态、备份无法建立，Safari 历史与通话记录都取不到，报告结论写"未发现该设备访问过目标网站、未发现与该号码的通话记录"。

**原因**：**"未发现"与"无法获取"在法律上有本质区别**。

前者是"检索了、没有"，后者是"没能检索"。

本案中设备根本无法建立备份会话——**检索从未发生**，因此"未发现"是一个在事实层面错误的陈述。

两者在文字上相似，都读作"没有"，这是误判的来源。

**影响**：**这类错误表述可能直接改变案件走向**。

一份写着"未发现通话记录"的报告，会让调查方相信该通话不存在；而实际情况只是设备被锁住了。

这类结论一旦被依赖，纠正成本极高。

**核查**：**四种状态必须严格区分，报告用词一一对应**。

| 状态 | 含义 | 报告用词 |
|---|---|---|
| **不可达** | 无权限、无路径，检索未发生 | "**无法获取**" / "**不可达**" |
| **未检查** | 可达但未执行 | "**未纳入本次分析**" |
| **部分覆盖** | 检查了但范围有限 | "**在 `<范围>` 内未发现**" |
| **未发现** | 已穷尽检索 | "**在 `<范围>` 内未发现**，`<未覆盖项>`" |

本案的标准句式：

> **无法获取**（非"未发现"）：设备处于锁屏状态，无法建立备份会话，Safari 历史、通话记录、通讯录等痕迹本次均不可达，检索未发生。`knowledgeC.db` 等非备份范围内的痕迹亦需解锁后方可评估。
> **效力上限**：本报告不对该设备是否访问过目标网站、是否与特定号码通话作任何事实性陈述。

在无法获取的项上给出否定结论，是本篇需要重点防范的误判。

<a id="section-31"></a>

#### 陷阱 12：在 MDM 远程管理设备上直接操作

**现象**：扣获一台企业 MDM 管理范围的设备，分析师按常规流程连接、备份，过程中企业 IT 部门远程执行了锁定或抹除。

**原因**：MDM 设备可被企业远程锁定或抹除，而这个动作可以在扣押后的任意时刻发生。

进度焦虑（"要快"）与证据保护要求（"必须有记录"）在这里形成直接冲突，而**远程抹除往往在数分钟内就能完成**。

反过来说，拖延也有代价——企业可能因为设备丢失而主动抹除。

**影响**：**数据在分析开始前就消失了**，且事后无法区分"本来就没有"与"被远程抹除"。

若报告未记录这一风险，委托方还会质疑"为什么没在有效期内完成"。

**核查**：尽快完成基础备份，但每一步都要有记录，并主动确认管理状态。

```bash
# 连接即确认：设备名常见为组织名，ActivationLock 为 MDM 特征
ideviceinfo | grep -iE 'DeviceName|ProductType|Activation'
# "某某公司 iPhone" 之类命名 → 疑似 MDM 管理设备
```

检查笔录须记录：扣押时间、设备接入时间、备份开始与完成时间、与委托方确认管理状态的沟通记录。发现 MDM 特征时应立即告知委托方并确认企业侧是否会执行远程抹除，把"时间窗"作为正式记录项。

<a id="section-32"></a>

#### 陷阱 13：试图自行绕过激活锁

**现象**：遇到 Activation Lock 已启用的设备，分析师或委托方开始寻找"第三方绕过服务"。

**原因**：绕过激活锁在多数司法辖区都需要走官方的司法协助或法律程序，由 Apple 或执法机关依申请处理，不存在合法的自助路径。

而"可自行绕过"的说法在涉诈案件中是常见的敲诈话术——目标往往不是解锁，而是骗取设备、支付费用或套取个人信息。

**影响**：**检材落入第三方手中不可控**，且这类接触本身就可能构成问题。

更实际的是，即使付了钱，对方交付的往往是无效方法或根本不存在的数据。

**核查**：**如实记录状态并启动法律程序，不尝试任何规避手段**。

| 机制 | 解除条件 | 取证处置 |
|---|---|---|
| 锁屏密码 | 需口令 | 由机主或通过合法途径提供 |
| **激活锁** | **需 Apple ID + 密码 + 法律程序** | **记录状态，启动官方申请** |
| MDM 远程管理 | 企业侧可远程锁定/抹除 | 确认管理状态与时间窗 |

```bash
ideviceinfo | grep -i Activation
# ActivationState: Activated   → 激活锁已启用
```

**报告须写明**：激活锁状态、解除所需条件、以及"**本案不尝试任何规避手段**"这一决定及其理由。

同时**明确告知委托方不应为"解锁"而擦除或刷写设备**——那既解决不了激活锁，又会销毁全部本地数据。

<a id="section-33"></a>

### 4.4 结论表述

<a id="section-34"></a>

#### 陷阱 14：把"设备名异常"等微弱观察过度推断

**现象**：发现 `DeviceName` 已被清空（显示为"的 iPhone"），报告写"该设备疑似被重置或转手"。

**原因**：**`DeviceName` 异常的原因非常多**——用户手动改名、抹掉后重设、企业 MDM 统一定制、系统升级后的默认值、他人代为设置。

仅凭名称这一个字段无法区分这些情况。

"异常状态必然对应某种事件"——这个直觉不成立。**一个字段的异常只能证明该字段异常。**

**影响**：**在报告中写入无依据的事件推断**。

若该推断被采信并影响"设备何时脱离原主"这类判断，方向可能完全错误。

**核查**：**只陈述观察到的事实，异常的成因列为待查项**。

```bash
ideviceinfo | grep DeviceName
# DeviceName: 的 iPhone    ← 名称已被清空，无用户信息
```

报告句式："`DeviceName` 当前显示为默认值，**未包含用户可识别信息**。该状态可能由重命名、抹除后重设、企业 MDM 定制或系统默认等多种原因造成，本检材不足以区分。记录为观察项，**成因待委托方补充信息后判断**。"

**配套的处置要求**：`DeviceName`、`Info.plist` 中的应用列表等含个人信息的内容，**按委托要求脱敏**——对外版本使用占位符，内部材料保留为线索并注明来源。

**范围、方法、未覆盖范围、效力上限**——这四项是本篇全部"未获取""不可达""无法判定"类陈述的统一交付标准。

当设备因状态限制而无法取证时，一份说清"为什么取不到、取不到什么、依法如何继续"的报告，其价值高于一份勉强拼凑的、数据来源却讲不清的报告。

## 五、案例示例

<a id="section-36"></a>

### 5.1 锁屏加激活锁设备的委托可达性评估

**场景**

查获一台 iPhone 14（`iPhone14,5`，iOS 17.2），设备已锁屏，**已激活 Activation Lock**。委托要求查明检材在特定时段是否访问过某网站、是否与特定号码通话。

委托方在送检时附了一张纸，上面写着"可越狱"，理由是"听说现在的手机都能绕过锁屏"。

本案的正确产出不是数据，而是一份说清楚"什么拿得到、什么拿不到、为什么拿不到、怎样合法地拿到"的评估。 委托方那句"可越狱"如果不先纠正，后面的动作会直接毁掉设备上仅存的东西。

**处置过程**

第一步，设备识别与状态固定 —— **先把设备身份固定下来，这是唯一一定能拿到的成果**：

```bash
$ idevice_id -l
00008020-001A2B3C4D5E6F70

$ ideviceinfo > device-info.txt
$ grep -E 'UniqueDeviceID|ProductType|ProductVersion|DeviceName|TimeZone' device-info.txt
UniqueDeviceID: 00008020-001A2B3C4D5E6F70
ProductType:    iPhone14,5
ProductVersion: 17.2
DeviceName:     的 iPhone
TimeZone:       Asia/Shanghai

$ sha256sum device-info.txt
```

`TimeIntervalSince1970` **未返回**。这个"取不到"本身就是一条记录 —— 它说明当前连接处于受限状态，而不是设备没有这个值。

第二步，能力与状态判定：

```bash
$ ideviceinfo | grep -iE 'ActivationState|ProductVersion|ProductType'
ActivationState: Activated          ← 激活锁已启用

$ idevicebackup2 -i backup /tmp/probe/ 2>&1 | head -3
Could not connect to lockdownd       ← 设备锁定，无法建立备份会话
```

| 发现 | 含义 | 行动 |
|---|---|---|
| `ActivationState: Activated` | **激活锁已启用** | 解除需 Apple ID + 密码，且需法律程序 |
| 无法建立备份会话 | **设备锁屏** | 逻辑层备份不可得 |
| `DeviceName` 已清空 | 用户曾抹掉或更换过设备的痕迹 | **记录为发现，不作过度推断** |

第三步，把三项委托要求逐条映射到可达性：

| 委托要求 | 当前可达性 | 原因 |
|---|---|---|
| 是否访问过某网站 | **不可达** | Safari 历史需备份或文件系统访问 |
| 是否与某号码通话 | **不可达** | `CallHistory.storedata` 不在普通备份内，需解锁或越狱 |
| 其他旁证 | **有限** | 仅有本机 `ideviceinfo` 输出 |

**判据是"数据在哪一层"**：Safari 历史与通话记录都在**文件系统层或越狱层**，逻辑层备份覆盖不到。**不是"权限不够"，是"这个层级根本没有"。**

第四步，对 DFU 做风险评估并明确不执行：

| 评估项 | 结论 |
|---|---|
| 是否已有可用备份 | **无**（设备锁屏，无法备份） |
| DFU 的数据后果 | 执行恢复将清空数据；退出时可能触发抹掉所有内容和设置 |
| 目标机型 | `iPhone14,5`，**属 iPhone 8 及以后** |
| 适用进入方式 | iPhone 8+ 按键组合，**iPhone 7 及以前方法不适用** |
| 激活锁影响 | 即使 DFU 成功，激活锁仍需 Apple ID 与法律程序 |
| **综合结论** | 不执行。DFU 无法解决核心障碍，却会造成不可逆数据损失 |

第五步，给出合法途径与可交付成果：

合法途径有三：

① 由委托方主管机关依法向 Apple 提交 Activation Lock 相关申请；
② 机主自愿配合（提供 Apple ID 与密码，或提供已解锁设备）；
③ 在相应法律程序与管辖权依据下调取机主 Apple ID 关联的 iCloud 备份。

```bash
# 可交付成果：设备身份 + 可复现的状态证明
$ grep -E 'ProductType|ProductVersion|UniqueDeviceID|TimeZone|Activation' device-info.txt
$ sha256sum device-info.txt
$ ideviceinfo | grep -iE 'DeviceName|TotalDiskCapacity|TimeIntervalSince1970'
```

**结论**

| 结论 | 支撑证据 | 强度 |
|---|---|---|
| 设备身份已确定并固定 | `iPhone14,5` / iOS 17.2 / UDID / `Asia/Shanghai`，已哈希 | 强 |
| Activation Lock 已启用 | `ActivationState: Activated` | 强 |
| 逻辑层备份不可得 | `Could not connect to lockdownd` | 强 |
| 三项委托要求在当前条件下均不可达 | 数据所在层级与当前可达层级的映射 | 强 |
| DFU 不予执行 | 无法解决激活锁 + 数据全损风险 + 机型方法不适用 | 强 |
| `DeviceName` 已被清空 | `ideviceinfo` 输出 | 中（原因不可判定） |

**能证明的**：设备型号、系统版本、UDID、时区、激活锁状态、以及当前条件下取不到哪些数据。

**不能证明的**：
- **不能证明设备被重置或转手。** `DeviceName` 清空的原因很多，本案无判据
- **不能给出开机时间。** `TimeIntervalSince1970` 在锁屏状态下不可读
- **不能证明设备上没有相关访问或通话。** 只能说在当前层级取不到
- **不能证明任何数据已被销毁。** 也可能是从未产生过

**未覆盖范围**：文件系统层与越狱层数据、Keychain、iCloud 侧数据、已删除文件残留、以及 `TimeIntervalSince1970`（锁屏不可读）。

**误判对照**

**其一，把"可越狱"当成可执行的取证方案。**

委托方送检单上写着"可越狱"。这句话在技术语境下几乎总是错的。

判据是**越狱的前置条件清单**：

| 条件 | 本案 |
|---|---|
| 设备已解锁 | **否**，锁屏 |
| 能建立 lockdown 会话 | **否**，连接被拒 |
| 激活锁已解除 | **否**，`Activated` |
| 具备对应机型漏洞的利用条件 | **不评估**（本案不涉及） |

**三项必要条件全部不满足。** 更重要的是，**越狱的通常前置步骤是抹除设备**（`Erase All Content and Settings` 后再走恢复模式），这一步本身就销毁数据。

"技术上存在某条路径"与"该路径适用于本案检材"是两回事。 报告应直接写明条件不满足，而不是留一个"理论可行"的尾巴。

按错误判据走的代价：委托方按"可越狱"推进，第一步就执行了抹除操作，设备上仅存的数据全部消失，且不可逆。

**其二，把 DFU 当成解锁手段。**

这是本案的核心技术误判。DFU 是**恢复模式**，不是解锁模式。

判据是**两个机制解决的问题完全不同**：

| 机制 | 解决的问题 | 对激活锁的效果 |
|---|---|---|
| 越狱 | 绕过沙盒与系统限制 | 需激活锁已解除才可行 |
| **恢复模式刷写** | **重装系统固件** | **激活锁依然存在** |
| 激活锁 | 云端绑定设备与 Apple ID | 只能由机主或 Apple 凭证明解除 |

恢复模式执行后设备会回到"需输入 Apple ID 密码才能激活"的状态，与送检时的 `Activated` 状态相比，数据没了、障碍还在。

判据是**问一个问题**：这个动作做完之后，我原来解决不了的那个问题解决了吗？本案答案是没有。不解决核心障碍的动作，无论技术难度多低，都不执行。

按错误判据走的代价：设备被刷机，本地数据全失，而激活锁问题原封不动。委托方不仅拿不到数据，还失去了后续通过合法途径取数的可能性 —— 因为 iCloud 备份可能被刷机动作触发删除。

**其三，把机型方法用错。**

`iPhone14,5` 属 iPhone 8 及以后。按 iPhone 7 及以前的按键时序操作，在新机型上不会有任何效果。

判据是**按机型代次查对应方法**：

| 机型代次 | 进入方式 |
|---|---|
| iPhone 6s 及以前 | 电源 + 音量键组合（方法 A） |
| iPhone 7 / 7 Plus | 电源 + 音量下（方法 B，专用按键） |
| **iPhone 8 及以后** | **侧边按钮与音量上**（方法 C） |

**三代的操作完全不同，混用不会报错，只会无效。** 判据是任何操作前先确认 `ProductType` 的代次，而不是照抄网上的步骤。

按错误判据走的代价：按错误时序操作后设备正常开机，未进入恢复模式，分析方误以为"方法无效"，实际是机型方法用错。更糟的情况是长按组合触发了强制重启，白白消耗了电量与窗口期。

**其四，把"无法获取"写成"未发现"。**

这两个表述在法律上有本质区别。

判据是**阴性结论的两种成因与措辞对应**：

| 成因 | 正确措辞 | 含义 |
|---|---|---|
| 查了，没有 | **未发现** | 数据可能存在，取到了但没有 |
| 根本没取到 | **无法获取 / 不可达** | 数据是否存在未知 |

本案三项委托要求全部属于后者。**写成"未发现"，等于替委托方做了一个否定性结论**，而分析方根本没有能力做这个结论。

按错误判据走的代价：委托方拿"未发现访问记录"去做无罪推定或责任排除，而分析方实际连数据都没看到。一个本应指向"继续争取解锁"的结论，被写成了"到此为止"。

其五，把 `DeviceName` 被清空当成设备被重置的证据。

`DeviceName` 显示为"的 iPhone"，看起来像是被清空了。但"清空"的原因至少有五种。

判据是**清空的可能来源**：

| 可能来源 | 判据 |
|---|---|
| 执行过抹除全部内容与设置 | 需查 `ActivationRecord` 或首次开机日志 |
| 用户手动改过名称 | 常见，无痕迹 |
| 二手购入后未命名 | 常见，无痕迹 |
| 由 MDM 或配置描述文件设置 | 需查配置描述文件 |
| 因激活锁状态而被系统隐藏 | **本案即可能如此** |

本案 `ActivationState: Activated` 状态下，名称字段被系统按激活锁策略处理的可能性无法排除。 因此正确的记录方式是"观察到 `DeviceName` 为空的 iPhone"，而不是"设备被抹除过"。

按错误判据走的代价：报告认定"设备被重置，说明持有人试图销毁证据"，委托方据此把调查方向对准特定时间段，而真实的抹除可能发生在完全不同的时间点，甚至从未发生。

### 5.2 可交付成果的哈希固定与后续串联

**场景**

承接 5.1。委托方虽接受了"当前不可达"的结论，但仍要求："那至少给我一份能用的东西，证明这台设备就是被扣的那台。"

这个要求看似简单，但委托方同时提出了一条看似合理的补充："把这次连上的所有输出都存一份，包括那些没取到的字段。"—— 这里藏着一个坑：把取不到的字段写成空值保存，等于制造了一份"设备无该数据"的假记录。

**处置过程**

第一步，把成果拆成"已取得"与"未取得"两栏，避免混在一起：

```text
# 已取得（obtained.txt）
UniqueDeviceID: 00008020-001A2B3C4D5E6F70
ProductType:    iPhone14,5
ProductVersion: 17.2
TimeZone:       Asia/Shanghai
TotalDiskCapacity: 128038873472
ActivationState: Activated
```

```text
# 未取得（unavailable.txt）
TimeIntervalSince1970   ← 锁屏状态下不可读
DeviceName              ← 返回空字符串（激活锁状态下可能被隐藏）
BatteryLevel            ← 受限连接下不可读
BasebandVersion         ← 受限连接下不可读
```

**第二份清单是关键。** 它明确区分"这个字段没有值"与"这个字段取不到"，避免日后被误读。

第二步，对已取得的字段做哈希固定，并写清采集条件：

```bash
$ {
    echo "# 采集条件"
    echo "# 时间: 2024-11-18T14:32:07+08:00"
    echo "# 连接: USB 受限（lockdownd 未接受备份会话）"
    echo "# 工具: libimobiledevice 1.3.0 / ideviceinfo"
    echo "# 设备状态: 锁屏，ActivationState=Activated"
    echo
    cat obtained.txt
  } > device-state-20241118.txt

$ sha256sum device-state-20241118.txt | tee device-state-20241118.sha256
```

哈希固定的对象必须是"带采集条件的快照"，不是裸的字段列表。 裸列表脱离采集环境后无法自证。

第三步，把设备标识与委托方送检单做逐项对账：

```bash
$ printf '%-14s | %-28s | %-28s | %s\
' 字段 送检单 本次采集 比对
$ printf -- '---------------+----------------------------+----------------------------+--------\
'
$ [ "00008020-001A2B3C4D5E6F70" = "00008020-001A2B3C4D5E6F70" ] \
    && echo "UDID | 00008020-001A2B3C4D5E6F70 | 00008020-001A2B3C4D5E6F70 | 一致"
```

| 字段 | 送检单 | 本次采集 | 是否一致 |
|---|---|---|---|
| 设备品牌 | Apple | Apple | 一致 |
| 设备型号 | iPhone14,5 | iPhone14,5 | 一致 |
| 系统版本 | 17.2 | 17.2 | 一致 |
| UDID | 00008020-001A2B3C4D5E6F70 | 00008020-001A2B3C4D5E6F70 | **一致** |
| 送检机身号 | FX29K0LM3XYZ | （本次不可读） | **不可比对** |

**UDID 是本次唯一能与送检单精确对应的字段。** 机身号在受限连接下不可读，因此对账只能覆盖四项 —— **这个"只覆盖四项"必须在报告中说明**，否则会让人误以为已全面核对。

第四步，为后续串联预留锚点：

```text
anchors.json
{
  "captured_at": "2024-11-18T14:32:07+08:00",
  "udid": "00008020-001A2B3C4D5E6F70",
  "product_type": "iPhone14,5",
  "product_version": "17.2",
  "timezone": "Asia/Shanghai",
  "total_disk_capacity": 128038873472,
  "activation_state": "Activated",
  "note": "锁定状态下的可取得字段集合，日后解锁后逐项比对以确认同一设备"
}
```

`TotalDiskCapacity` 是一个特别有用的锚点：它是硬件属性，不随系统重装而变。若日后设备被重置，UDID 保留但容量等字段会变，比对结果能说明设备状态发生过变化。

**结论**

| 结论 | 支撑证据 | 强度 |
|---|---|---|
| 本次采集与送检单记载在四项上完全一致 | 品牌/型号/版本/UDID 逐项对账 | 强 |
| UDID 是唯一可精确对应的标识 | 其余字段或不可读或不参与比对 | 强 |
| 机身号本次不可读，对账未覆盖该字段 | 对账表中该行为"不可比对" | 强 |
| 采集快照已哈希固定且含采集条件 | `device-state-20241118.sha256` | 强 |
| 已建立可跨阶段比对的锚点集合 | `anchors.json` | 强 |
| 该成果在设备解锁后依然有效 | 锚点字段与连接状态无关 | 强 |

**能证明的**：该设备与送检单记载为同一台设备（就四项可读字段而言）、以及本次采集的完整条件与完整性。

**不能证明的**：
- **不能证明机身号与送检单一致。** 该字段本次不可读
- **不能证明设备内数据与送检时一致。** 本次未取得任何数据内容
- **不能证明设备未被重置。** 本次无判据

**未覆盖范围**：机身号、基带信息、电池状态、开机时间、以及全部用户数据。

**误判对照**

**其一，把取不到的字段写成空值保存。**

委托方要求"把这次连上的所有输出都存一份"。如果直接存 `ideviceinfo` 的原始输出，`DeviceName` 会是空字符串，而 `TimeIntervalSince1970` 那一行根本不存在。

判据是**两种"空"的区别**：

| 情形 | 表现 | 语义 |
|---|---|---|
| 字段值为空字符串 | `DeviceName: ` | 该字段值就是空 |
| 字段未被返回 | 输出中无该行 | 该字段取不到 |

这两种"空"在存档里如果不做区分，日后会被读成同一个意思。 本案把 `unavailable.txt` 单独成册，并在采集说明中写明"受限连接下不可读"，就是为了消除这个歧义。

按错误判据走的代价：日后委托方拿到这份记录，看到 `DeviceName` 为空，写成"设备无用户命名信息"，而实际是该字段在激活锁状态下被系统隐藏。**结论方向完全相反。**

**其二，把裸字段列表当作可采信的状态证明。**

如果只存一份字段列表，不带采集条件，这份东西的证明力接近于零。

判据是**状态证明的三要素**：

| 要素 | 内容 | 缺失后果 |
|---|---|---|
| 采集时间 | 何时取得 | 无法判断时效 |
| 采集条件 | 连接方式、设备状态、工具版本 | 无法复现，无法判断可信度 |
| 采集对象 | 完整输出或字段清单 | 无法确认字段是否被裁剪 |

"设备是 iPhone 14、iOS 17.2、已激活"这句话，在没有采集条件时只是一句转述；在有采集条件与哈希时是一份可质证的记录。

按错误判据走的代价：委托方在另一场诉讼中引用这份记录，对方质疑"你怎么知道当时是锁屏状态、怎么知道没被改过"，分析方无法自证，证据被排除。

**其三，把 UDID 当作可以更换或复制的标识。**

`UniqueDeviceID` 常被当作设备唯一标识，但它在不同语境下的稳定性并不一致。

判据是**三类 Apple 标识的稳定性**：

| 标识 | 稳定性 |
|---|---|
| `UniqueDeviceID`（UDID/序列号派生） | 硬件绑定，**不随抹除改变** |
| `ProductType` / `ProductVersion` | 硬件绑定，但版本会随升级变 |
| iCloud 账号 | 抹除后可在新机重新登录 |

**UDID 稳定这一点正是它的价值所在**：它能证明"这是同一台物理设备"，即使设备已被重置或转手。

但要同时说明它的局限：**UDID 是设备标识，不是持有人标识。** 掌握这台设备的人可能已更换，UDID 无法说明当前使用者的身份。

按错误判据走的代价：委托方用 UDID 去查"这台设备 2024 年 11 月的持有人是谁"，需要运营商或平台侧数据支撑，仅凭 UDID 查不到。**技术标识不能替代归属证据。**

**其四，把"对账一致"当成"设备状态未变"。**

四项字段一致，只能说明"这是同一台型号、同一台设备"，不能说明"机内数据未变"。

判据是**对账能覆盖与不能覆盖的**：

| 能覆盖 | 不能覆盖 |
|---|---|
| 设备同一性 | 机内数据是否变更 |
| 型号与当前系统版本 | 送检后是否被刷机 |
| 时区配置 | 是否被重置 |
| 容量等硬件属性 | 是否被解锁过 |

**容量字段是个例外**：它属于硬件属性，不随系统重装变化，因此它一致只能佐证"是同一台硬件"，**不能佐证"系统未变"**。系统版本 `17.2` 才是反映系统状态的字段，它与送检单一致，才说明系统版本未变。

按错误判据走的代价：报告写"设备状态与送检时一致"，委托方据此认为设备数据可与送检时的认知对齐，而实际系统可能已被刷机、数据已变。

**其五，把锚点集合当成完整指纹。**

`anchors.json` 只有六项，委托方希望"再多给几项以便日后比对"。

判据是**锚点字段的三条选取标准**：

| 标准 | 说明 |
|---|---|
| 不随系统状态改变 | 容量、UDID 符合；系统版本**不符合** |
| 在受限连接下可读 | 部分字段在锁定时不返回 |
| 组合后唯一性足够 | 单字段不足以定案，需组合 |

**系统版本不满足第一条**（升级即变），但它仍然有价值 —— 因为它的**变化**本身就是信号。

因此锚点集合的正确用法是"逐项比对，关注变化的方向"，而不是"全部一致才认定为同一台"。若日后 UDID 与容量一致而系统版本从 17.2 变为 17.5，说明设备被升级过；这不否定设备同一性，反而是一个**有价值的发现**。

按错误判据走的代价：日后系统升级导致版本字段不一致，委托方据此否定设备同一性，把同一台设备的锚点当作不可用，错过了"设备被升级过"这条线索。

### 5.3 iCloud 调取与本地数据的归属边界

**场景**

承接 5.1 与 5.2。委托方接受了锁屏不可达的结论，随即提出第三条路："他有一个 iCloud 账号，你们去把云上的备份拉下来不就行了？"

委托方的推理是"手机锁了但云上没锁"。这个推理方向没错，但里面有一个必须先讲清楚的前提：

iCloud 备份是"某个时间点的副本"，不是"这台设备的全部内容"。

把它当成后者，会得出关于设备状态的错误结论。

**处置过程**

第一步，先把"云上有什么"这件事与"要查的事"逐条对齐 —— 委托问题指向的时间点，是否落在备份的时间点覆盖范围内：

| 委托问题 | 设备本地状态 | iCloud 可能提供 | 是否可直接回答 |
|---|---|---|---|
| 事发前是否访问某网站 | 不可达 | 最近一次备份时刻的 Safari 历史 | **仅当备份时刻覆盖到事发前** |
| 是否与某号码通话 | 不可达 | 备份内的通话记录 | 需备份在事发前完成 |
| 事发后是否有新活动 | 不可达 | 最近备份之后的内容 | **不可得** |

关键判据：iCloud 备份只保留"最后一次备份时刻"的状态。 备份之后设备上的任何变化（包括新增与删除）都不在云端。

第二步，在取得合法授权的前提下确认云端可用性 —— **先确认调取权限合法，再谈技术动作**：

```text
前置条件（须全部满足，缺一不可）：
1. 由委托方主管机关依法出具的法律文书，明确载明 Apple ID 归属与调取范围
2. 机主 Apple ID 的账号归属证明，或法院/主管机关确认的账号主体
3. 调取范围、时间区间的书面界定
4. 委托方对所调取数据用途的书面确认
```

**这四项属法律程序问题，不是技术问题。** 在四项齐备之前，本报告不对任何云端调取动作给出指导。

第三步，把 iCloud 备份与设备本地数据的能力差异写清楚 —— **这是本案第二个核心结论**：

| 数据类型 | 设备本地（解锁后） | iCloud 备份 |
|---|---|---|
| 短信、通话记录 | 可得 | **可得（备份时刻）** |
| 应用数据 | 部分可得 | 部分可得 |
| 已删除数据 | **可能可得**（文件系统层残留） | **不可得**（备份只存现存文件） |
| 备份后新增数据 | 可得 | **不可得** |
| Keychain | 部分可得 | 部分可得 |
| 恢复模式可取而备份不可取的系统区域 | 部分 | 不可得 |

**容易被误读的是"已删除数据"这一行**：本地文件系统层可能残留已删除文件，而 iCloud 备份只会同步现存文件。若调查方向是"某人删除了什么"，云端备份可能恰恰是看不见的那一侧。

第四步，把阴性结论的范围钉死 —— 本案第三个也是必须写明的核心结论：

```bash
# 本次实际执行过的检查
$ idevice_id -l
$ ideviceinfo > device-info.txt
$ idevicebackup2 -i backup /tmp/probe/
$ sha256sum device-info.txt device-state-20241118.txt
```

```text
本次未覆盖范围：
- 设备本地全部数据（锁定，全部未取得）
- iCloud 侧全部数据（未获授权，未调取）
- 运营商侧通话与短信记录（未申请）
- 设备自 2024-11-18 送检之后的任何状态变化
- 送检单记载机身号与设备的对应关系（该字段不可读）
```

**结论**

| 结论 | 支撑证据 | 强度 |
|---|---|---|
| iCloud 备份只反映最后备份时刻的状态 | 备份语义 | 强 |
| 委托问题能否由 iCloud 回答取决于备份时刻 | 备份时刻与事发时刻的对照 | 强 |
| iCloud 无法提供"已删除数据" | 备份只同步现存文件 | 强 |
| 云端调取需四项法律前置条件 | 法律程序要求 | 强 |
| 本案未执行任何云端调取 | 未获授权 | 强 |

**阴性结论（严格限定）**：

> 在**设备受限连接层**、2024-11-18 14:32:07 这一次 `ideviceinfo` 调用的范围内，仅取得设备身份与状态类字段；**未取得任何用户数据内容**，包括 Safari 历史、通话记录、通讯录与短信。
>
> 该阴性结论**不构成"设备上不存在相关记录"的证据**：用户数据位于文件系统层与越狱层，本案未到达该层级；同时本地文件系统层可能存在的已删除数据残留，本案亦未检索。
>
> 未覆盖路径见上列各项，另含 iCloud 侧（未获授权）、运营商侧（未申请）、送检后的状态变化、以及不可读的机身号。

**能证明的**：设备身份与状态、本案实际检查了什么与没检查什么、以及 iCloud 与本地数据在能力上的差异。

**不能证明的**：
- **不能证明设备上没有相关访问或通话记录。** 本案未到达数据所在层级
- **不能证明 iCloud 侧是否有相关记录。** 未获授权，未调取
- **不能证明数据已被销毁。** 也可能从未产生

**未覆盖范围**：本地文件系统层、越狱层、已删除文件残留、iCloud、运营商侧、送检后状态变化、机身号。

**误判对照**

其一，把 iCloud 备份当成"设备的全部内容"。

委托方问"去把云上的备份拉下来"。这个说法隐含了一个错误前提：备份等于设备。

判据是**备份的时间截断性质**：

| 性质 | 含义 |
|---|---|
| 备份是**某时刻的快照** | 只反映备份执行那一刻的设备状态 |
| 备份**不记录变化历史** | 备份后新增、修改、删除的内容都不在其中 |
| 备份**不含已删除文件** | 本地可能残留的删除项，云端没有 |

**最直接的自检是问一句："备份是什么时候做的？"** 如果备份时刻晚于事发时刻，可以回答事发前的状态；如果早于事发时刻，答案就是"不可得"。本案委托方从未确认过这一点。

按错误判据走的代价：委托方拿到一份 2024-10 的备份，看到没有相关记录，写成"未发现该访问"，而实际访问发生在 10 月之后。一份时间点不对的备份，比没有备份更容易制造错误结论。

其二，把"已删除数据"归到 iCloud 能取到的一侧。

这是方向性错误，且不易察觉。

判据是**删除数据的两侧分布**：

| 侧 | 删除数据是否可得 | 机制 |
|---|---|---|
| 设备文件系统层 | **可能可得** | APFS 空闲区与卷快照中可能残留 |
| iCloud 备份 | **不可得** | 同步的是"当前存在的文件" |

因此如果委托问题是"某人删除了什么"，云端备份很可能恰恰是看不到的那一侧。 备份里没有某文件，可能是因为它从备份时刻起就不存在，与"有人在事发时删除了它"完全是两回事。

判据是**删除类问题必须回到时间轴上看**：该文件在备份时刻是否存在？如果备份时刻它就不在，那备份无法回答任何删除问题。

按错误判据走的代价：调查方向被带到"云上没有就是没删过"，而真正的删除痕迹在设备文件系统层，从未被检索。

**其三，把"技术上可调取"当作"应当调取"。**

iCloud 调取在技术上并非不可能，但这属于需要法律文书支撑的动作。

判据是**调取动作的前置条件清单**：

| 条件 | 性质 |
|---|---|
| 法律文书 | 法律问题 |
| Apple ID 归属证明 | 法律问题 |
| 范围与时间区间界定 | 法律问题 |
| 用途书面确认 | 法律问题 |
| 云端数据加密与密钥获取 | 技术问题 |

**四项法律条件与技术实现是两层。** 前者未齐备时讨论后者，属于越界。

报告应只写"若四项法律条件齐备，可考虑经由云端调取补充"，不写具体操作步骤。 这不是保守，而是因为没有授权的调取其结果本身不可采信。

按错误判据走的代价：委托方或分析方先做了调取再补手续，数据一旦进入工作区，其合法性已被污染 —— 后续无论多努力都无法追溯为合法取得。**取证程序上的瑕疵无法事后补救。**

**其四，把"三层来源的阴性结论"合并成一句。**

本案有三层来源：本地文件系统层、iCloud、运营商侧。委托方希望报告里写一句"三层均未发现相关记录"。

判据是**每层来源的状态必须分别记录**：

| 来源 | 本案状态 |
|---|---|
| 设备本地 | **未到达该层级**，无数据 |
| iCloud | **未获授权**，无数据 |
| 运营商侧 | **未申请**，无数据 |

**三层都是"没查"，没有一层是"查了没有"。** 把三者合并成"均未发现"，等于把"未查"表述成"未发现"，这正是本篇反复要防的那个错误。

正确表述是：

> 本次调查未到达设备文件系统层、未获授权调取 iCloud、未向运营商提出申请，**三层来源均未获取数据**，因此无法就"是否存在相关记录"作出任何判断。

按错误判据走的代价：委托方把"三层均未发现"作为无相关记录的依据提交给法庭，而实际上三层都没有被真正检验过。**这已不是措辞不当，而是结论实质错误。**

**其五，把"当前不可达"写成"永久不可达"。**

报告如实写了不可达，但委托方据此认为"那就到此为止了"。

判据是**可达性的三种状态**：

| 状态 | 含义 | 后续动作 |
|---|---|---|
| **永久不可达** | 数据已销毁或不存在 | 结案 |
| **当前不可达** | 现在取不到，条件变化后可取 | **等待条件** |
| **本层不可达** | 换一层可达 | 换路径 |

本案属第三类的组合：本地层需解锁、越狱层需前置条件、云端需授权。**三种路径都存在，各自缺的是不同的东西。**

因此报告必须写清**每条路径缺什么、由谁提供**，而不只是写"不可达"：

```text
待办事项：
- 若机主自愿提供 Apple ID 与密码 → 可达 iCloud 与逻辑备份
- 若 Apple 激活锁申请获批 → 可解锁并取得完整备份
- 若案件涉及通信秘密，需向运营商提出司法申请 → 可得运营商侧记录
```

按错误判据走的代价：委托方看到"不可达"就终止调查，而实际上三条路径中任意一条的推进都可能让调查继续 —— 报告的价值本应体现在指明可走的路，而不是宣布走不通。

## 六、扩展阅读方向

本篇停在"能力边界判定"这个位置。下面几组延伸按三条线索分组：同一层痕迹读得更深、换一条路拿到数据、以及不可逆动作的规范。

**痕迹深挖：设备层拿到之后怎么读**

- [iOS 备份与沙盒提取](mobile-ios-ios-backup-and-sandbox-extraction.md) —— **本篇的默认起点**。备份层的 `Manifest.db` 索引、加密备份的密钥结构、per-file 的 `Info.plist`。**很多被写进"不可获取"的痕迹，其实备份里就有**，先查再放弃。
- [Keychain 与 Safari 痕迹](../../computer/computer-security/computer-security-keychain-safari.md) —— Safari 历史、书签、下载记录与 Keybag 条目的解析思路。备份层能拿到部分，设备层更完整。
- [plist 与偏好设置](../../computer/computer-plist-spotlight/computer-plist-spotlight-plist.md) —— `com.apple.*.plist` 的二进制 plist 与 NSKeyedArchiver 解析方法，本篇路径清单里那些文件都要用到。
- [APFS 容器与快照](../../filesystem/filesystem-apple-fs/filesystem-apple-fs-apfs.md) —— **iOS 与 macOS 共用的底层结构**。快照意味着"某文件的旧版本"在设备上可能仍可恢复，备份层完全看不到这一层。

**另一条路：备份层走不通时的替代**

- [Android 数据存储总览](../mobile-android/mobile-android-android-data-storage-overview.md) —— 跨平台案件里常见的情形：一台 iPhone 锁死，但配对的 Android 机、同账号的云端、SIM 卡都还有出口。
- [SIM 卡取证](../mobile-sim/mobile-sim-sim.md) —— 最独立的一条证据线。**它不受设备锁状态影响**，能独立证明"这张卡在这个时期处于活动状态"。
- [远程勘验与在线取证](../../imaging/imaging-acquire/imaging-acquire-remote-evidence-collection.md) —— 设备不便移交时的替代路径，以及它在证据能力上的折损。
- [取证装备与写保护器](../../fundamentals/fundamentals-practice/fundamentals-practice-forensics-equipment-and-write-blockers.md) —— 现场接入方式、只读优先原则与移动取证箱要求。本篇涉及硬件连接的地方都引用它。

**时间线还原：把痕迹串成顺序**

- [FSEvents 与时间机器](../../computer/computer-log-persistence/computer-log-persistence-fsevents.md) —— 文件变动记录的还原思路，同样适用于 iOS 侧痕迹的时间排序。
- [时间戳换算](../../fundamentals/fundamentals-concepts/fundamentals-concepts-timestamps-and-timezones.md) —— Apple 生态的 Cocoa 时间基准（2001-01-01），**漏掉换算会让整条时间线偏 31 年**。
- [反取证手法与时间戳篡改检测](../../fundamentals/fundamentals-concepts/fundamentals-concepts-anti-forensics-and-timestamp-tampering.md) —— 设备时间被改、痕迹被批量清理的识别。"抹掉所有内容和设置"本身就是一种反取证行为，它的痕迹识不要在这一篇。

**不可逆动作与结论表述**

- [取证流程与原则](../../fundamentals/fundamentals-process/fundamentals-process-five-stage-forensics-process.md) —— 本篇所有"绝不能做"的判断依据。
- [合规授权与法律边界](../../fundamentals/fundamentals-practice/fundamentals-practice-legal-authorization-and-boundaries.md) —— 激活锁的司法协助流程、iCloud 调取的法律文书要求。
- [证据保管链与委托证明](../../fundamentals/fundamentals-chain/fundamentals-chain-chain-of-custody-and-authorization.md) —— MDM 远程抹除、外部干预这类情况的记录要求。
- [SQLite 基础与结构](../mobile-database/mobile-database-sqlite.md) —— `sms.db`、`AddressBook.sqlitedb`、`knowledgeC.db` 全都是 SQLite，**先读这篇再动手**。

## 七、命令速查

```bash
# ===== 环境与设备识别 =====
sudo apt install libimobiledevice-utils usbmuxd
sudo usbmuxd &                                   # ★ 不跑会报 no device found
idevice_id -l
ideviceinfo > device-info.txt && sha256sum device-info.txt
grep -E 'UniqueDeviceID|ProductType|ProductVersion|DeviceName|TimeZone|TimeIntervalSince1970' device-info.txt
grep -i ActivationState device-info.txt          # 激活锁状态
# 开机时间 = TimeIntervalSince1970 的秒值；锁屏时该字段可能不可读

# ===== 能力探测与备份（DFU 的必要前提）=====
idevicebackup2 -i backup /tmp/probe/ 2>&1 | head -3     # Could not connect to lockdownd → 锁屏
mkdir -p /work/ios-backup
idevicebackup2 -i backup /work/ios-backup/ 2>&1 | tee backup.log   # 交互式输入口令
BK=$(ls -d /work/ios-backup/*/ | head -1)
plutil -p $BK/Info.plist  | grep -E 'Last Backup Date|Device Name'
plutil -p $BK/Status.plist | grep IsFullBackup
ls $BK/Manifest.db && sqlite3 $BK/Manifest.db "PRAGMA integrity_check;"

# ===== 痕迹清点（备份 + 已越狱/物理镜像两条路径）=====
sqlite3 $BK/Manifest.db "SELECT domain, relativePath FROM Files
WHERE relativePath LIKE '%knowledgeC%' OR relativePath LIKE '%CallHistory%'
   OR relativePath LIKE '%AddressBook%' OR relativePath LIKE '%Calendar%'
   OR relativePath LIKE '%sms.db%'    OR relativePath LIKE '%PhotoData%';"
# 常见原始路径（需越狱或物理镜像才能直读）：
#   /private/var/mobile/Library/SMS/sms.db
#   /private/var/mobile/Library/CallHistoryDB/CallHistory.storedata
#   /private/var/mobile/Library/AddressBook/AddressBook.sqlitedb
#   /private/var/mobile/Library/Calendar/Calendar.sqlitedb
#   /private/var/mobile/Library/CoreDuet/Knowledge/knowledgeC.db   ★
idevicefs -u /private/var/mobile/Library/CoreDuet/Knowledge/ ls

# ===== knowledgeC.db 分析 =====
sqlite3 knowledgeC.db ".tables"                 # 先看结构，不直接 SELECT *
strings -n 6 knowledgeC.db | grep -oE 'com\.[a-z0-9]+\.[a-z0-9]+' | sort | uniq -c | sort -rn | head
# 注意措辞：写「系统记录了…」，不写「用户做了…」

# ===== DFU（★ 仅在备份完成 + 书面授权 + 风险评估后）=====
ideviceinfo > pre-dfu-state.txt && sha256sum pre-dfu-state.txt
# iPhone 8 及以后：按住侧边键 2 秒 → 追加音量下 4 秒 → 松开侧边键、继续按音量下约 10 秒（全程无 Logo）
# iPhone 7 及更早：同时按住 电源键 + 音量下 8–10 秒 → 见 Apple 标志后松开电源键、继续按音量下约 8 秒
# 退出：iPhone 8+ 按 侧边键+音量上；iPhone 7 及更早按 电源键+Home
date -Is | tee dfu-entry-time.txt
# …… 目标操作 ……
date -Is | tee dfu-exit-time.txt
ideviceinfo > post-dfu-state.txt && diff pre-dfu-state.txt post-dfu-state.txt | head
sqlite3 $BK/Manifest.db "PRAGMA integrity_check;"        # 退出后确认备份仍完整

# ===== 激活锁 =====
# 官方绕过需法律文书，由委托方主管机关依法向 Apple 提出
# 不使用任何第三方「绕过服务」（合法性与真实性均无保障）
```
