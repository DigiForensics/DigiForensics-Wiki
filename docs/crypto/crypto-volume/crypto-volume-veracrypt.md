# VeraCrypt / TrueCrypt 加密卷的取证解析

> 原文链接：[DigiForensics Wiki · 在线阅读](https://www.digiforensics.cn/wiki/crypto-volume-veracrypt)

<a id="section-1"></a>

## 一、概述

VeraCrypt 是 TrueCrypt 的社区续作（基于 7.1a 代码），目前是开源领域最主要的磁盘/文件级加密容器工具。

它在取证中并不少见，原因很实际：它不依赖 TPM、不需要 Windows 激活、能运行在任意系统上（包括 Linux live CD）。这三项便利同时是"用户愿意用"和"恶意人员会用"的原因。

但它带来的取证处境与 Windows 自带的全卷加密**完全相反**：

> VeraCrypt 没有后门、没有弱加密、没有"忘记密码"选项。 官方设计目标就是"如果你忘了口令，数据就永久丢失"。

所以现实路径只有三类，**没有第四条**：

1. **找到口令**（明文残留、命令行历史、剪贴板、内存、浏览器保存的密码、密码管理器）
2. **找到明文副本**（挂载时未擦除、备份、临时文件、页交换中的残留）
3. **利用实现残留**（挂载后未卸载、隐藏卷外层、卷影副本、日志）

本篇最重要的方法论判断是：不要先想"怎么解"，而要先想"值不值得解"。

VeraCrypt 的口令派生过程由 PIM 控制，但**PIM 值不写在卷头里**——它是挂载时由操作者每次输入的参数。这带来一个反直觉但决定性的取证事实：

**你无法从镜像里读出这个卷用的 PIM 是多少。** 这意味着「先读卷头看 PIM 值，再决定值不值得投入爆破」这条常见思路无法执行——它建立在一个不存在的判据上（完整说明见 2.3）。

真正能读出来的只有盐值（64 字节）——**它是卷头里唯一的明文字段**。Magic、Header Version、扇区大小、算法与 KDF 全部位于加密区内，只能在口令解开后读到；即便解开了，算法与 KDF 也是靠遍历候选组合 + CRC-32 反推出来的。

所以正确的第一步是：确认卷头存在且可定位，然后立刻转向成本低得多的几条路径。

花三天去攻一个 PIM 未知的卷，比花五分钟去搜 shell 历史里的命令行要浪费得多。

**本篇处理的证据形态**：

| 证据 | 位置 | 判据 / 说明 |
|---|---|---|
| **卷头（volume header）** | 文件容器主卷头在偏移 0、隐藏卷头在 64 KiB、数据从 128 KiB 起；系统卷主头在加密区起始、备份头在末尾 | ★ **卷头没有明文签名**：唯一未加密的只有前 64 字节盐值，`VERA` 在加密区内，字面量搜索定位不到 |
| **盐值 Salt** | 卷头偏移 0，64 字节 | **唯一的明文字段**，每卷唯一，提取 hash 必需 |
| Magic `VERA` / Header Version | 偏移 64 / 68 | **在密文内**，仅在口令正确后可用于验证，不可用作定位判据 |
| 加密算法 / KDF / 扇区大小 | **不在卷头明文里** | 遍历候选组合后用两个 CRC-32 反推 |
| PIM 值 | **不存放在卷头里** | 只能从用户记录、配置或内存中旁证（见 2.3 的例外说明） |
| 文件容器 | `.hc` / `.tc` / 无扩展名 | **卷容量 = 文件大小 − 128 KiB**，按文件大小挂载会报"文件系统损坏" |
| 隐藏卷 | 卷头偏移 65536 处存在**第二个卷头**（同样无明文签名） | **空闲空间熵值异常高**是主要判据；隐藏卷的存在无法在解锁前被证明 |
| shell 历史 | `~/.bash_history`、`~/.zsh_history` | `veracrypt -p "口令" ...` 直接命中，是成本最低的现实路径之一 |
| 挂载残留 | 进程、设备映射、页交换、文件系统缓存 | 查获时卷仍挂载的话，**明文可能就在盘上明文区** |
| 密码管理器 | KeePass `.kdbx` 等 | 主密码未知时走离线验证路径 |

**记住这张表里最重要的两行**：卷头和 shell 历史。前者决定"能不能做"，后者决定"要不要做"。

**三条现实路径的命中率对照**——这是本篇最实用的部分，因为它们的成本差了几个数量级：
| 路径 | 典型命中点 | 成本 | 为什么有效 |
|---|---|---|---|
| **命令行残留** | `~/.bash_history`、`~/.zsh_history`、终端 scrollback、部署脚本 | **一次 `strings` + `grep`** | 创建和使用加密容器的操作通常经过命令行，而 `-p` 参数会带上明文口令 |
| **浏览器保存的凭据** | `Login Data` 的 `origin_url` / `username_value` | 一次 SQLite 查询 | 用户在网页上输入过这个口令（备份、迁移、复述）时会被保存 |
| **内存与页交换** | 内核页、进程内存、`/proc/kcore` | 需已有内存镜像 | 挂载时解出的主密钥可能仍驻留，但**不是 ASCII 文本，别指望搜关键字** |
| **挂载残留** | 进程、设备映射、文件系统缓存、盘上明文区 | 需查获时卷仍挂载 | 常见于服务器与办公机现场扣押——**明文可能就躺在盘上** |
| **口令攻击** | 弱口令字典、掩码、上下文候选 | **可能不可行** | **先确认候选数量**：PIM 不在卷头里，单候选代价只能实测（GPU 上典型每秒数千次候选）。**候选数量才是决定性的量** |

**这张表的排序就是优先级**。前三项加起来的成本可能只有十分钟，而最后一项可能耗尽整个项目的算力预算却毫无产出。先做成本低、命中点多的，做不到再做贵的。

**在取证流程中的位置**：本篇属于**分析**环节，但**它的第一动作发生在采集之前**——如果你还不知道盘上有没有加密容器，就无法决定是做全盘镜像还是分区镜像。

**上游依赖**是[镜像制作](../../imaging/imaging-acquire/imaging-acquire-disk-imaging-and-evidence-preservation.md)（**挂载时必须只读，本篇的取标准动作清单里这是第一条**）与[证据格式与转换](../../imaging/imaging-acquire/imaging-acquire-evidence-image-formats.md)（从 E01 里切出容器文件）。

**挂载成功之后**，本篇就结束了，剩下的是文件系统解析：容器内通常是标准 ext4 / NTFS / FAT32，分别对应[ext4 结构与 inode](../../filesystem/filesystem-unix/filesystem-unix-ext4-inode.md)、[NTFS 结构与 MFT 解析](../../filesystem/filesystem-ntfs/filesystem-ntfs-ntfs-master-file-table.md)、[FAT 系列结构](../../filesystem/filesystem-mobile-fs/filesystem-mobile-fs-fat.md)。

**找口令时最常命中的两条旁证路径**是[Shell 痕迹与命令历史](../../computer/computer-shell/computer-shell-shell.md)与[浏览器密码库与 Token 解密](../crypto-app/crypto-app-browser-passwords-and-tokens.md)。

盘上是否有 VeraCrypt / TrueCrypt 容器、是文件容器还是系统卷、卷头是否完整可解析、是否设有隐藏卷、是否曾处于挂载状态、口令是否在明文痕迹中出现过，以及**在拿到候选口令后能否挂载成功**（挂载成功即反向证明算法与 KDF 猜对了）。

**在没有口令的前提下不能读出卷内任何内容**——这是设计目标，不是能力边界。

也不能回答"这个卷用的 PIM 是多少"（**它不写在盘上任何位置，见 2.3**）、"用的什么加密算法与 KDF"（**同样不在卷头明文里，需口令解开后才可知**）、"用户是否故意隐藏了什么"（隐藏卷的存在只说明用户用了这个功能，不说明动机）、**"这个容器是谁创建的"**（卷头里没有创建者信息，需要靠外联痕迹或时间戳旁证）、以及"**这个口令是唯一能打开它的口令**"（VeraCrypt 不限制口令猜测次数，但也不提供任何校验位提示，**唯一的验证就是实际挂载成功**）。

**读者前提**：你需要先能在镜像里**定位卷头并读出它的明文字段**（盐值、Magic、Header Version，这一步不依赖任何专用工具）；理解"**挂载加密容器会写入数据**"这件事并接受只读纪律（[只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md)）；以及对"不可恢复"这个结论的证据标准有基本认识（[取证流程与原则](../../fundamentals/fundamentals-process/fundamentals-process-five-stage-forensics-process.md)）。

**本篇不提供任何口令破解手段**——涉及弱口令的离线验证方法论见[通用密码恢复](../crypto-app/crypto-app-passware-and-password-recovery.md)，那里的授权要求与优先级表同样适用于本篇。

## 二、核心原理

<a id="section-3"></a>

### 2.1 容器类型与定位

VeraCrypt 支持两种容器形态，取证时必须先区分：

| 类型 | 特征 | 取证要点 |
|---|---|---|
| **文件容器** | 普通文件（`.hc`、`.tc`、无扩展名） | 内部有隐藏的加密卷文件系统，**卷大小与宿主文件可能不一致** |
| **系统加密卷** | 整个分区/整个磁盘 | 主卷头在加密区起始，**备份头在分区末尾** |

**文件容器的关键陷阱**：VeraCrypt 文件容器的卷头在文件**开头**，且**卷的实际大小 ≠ 文件大小**。

卷头不是一个结构，而是一**组**（header group）：卷头本体占 64 KiB（有效数据只有前 512 字节，其余填充随机数据），主卷头在偏移 `0x00000`，隐藏卷头在偏移 `0x10000`（64 KiB 处），加密数据从 `0x20000`（128 KiB）开始。所以文件容器的真实卷容量是「文件大小减去 128 KiB 再按扇区向下取整」，直接按文件大小挂载会报文件系统损坏或尾部读越界。

系统加密卷的布局不同：主卷头之后紧跟引导区，备份头写在加密区末尾。**「只找到一处卷头」在这个格式上不是一个可用的判据**——因为卷头没有明文签名，压根搜不到。隐藏卷的存在性判断见 3.5。

<a id="section-4"></a>

### 2.2 卷头（Volume Header）结构

卷头是 VeraCrypt 取证的核心对象。但它有一个**一旦记错就会让整个调查方向跑偏**的性质：**卷头里没有任何明文签名。**

官方格式规范的原话是「VeraCrypt 卷没有签名或 ID 字符串，在解密之前它们看起来完全由随机数据组成」。这不是隐喻，是字面事实。

```
偏移 0x00（64 字节）：Salt —— ★唯一未加密的字段★
───────────────────────────────────────── 以下之后全部加密 ─────
偏移 0x40（4  字节）：Magic "VERA"（0x56455241）—— 位于加密区内
偏移 0x44（2  字节）：Header Version = 0x0005
偏移 0x46（2  字节）：Required Program Version（打开该卷所需的最低程序版本）
偏移 0x48（4  字节）：Key Area CRC-32（覆盖解密后的 256–511 字节主密钥区）
偏移 0x4C（16 字节）：Reserved（必须为零）
偏移 0x5C（8  字节）：Hidden Volume Size（0 = 普通卷）
偏移 0x64（8  字节）：Volume Size
偏移 0x6C（8  字节）：Master Key Scope Start（主密钥作用域起始字节偏移）
偏移 0x74（8  字节）：Encrypted Area Length（作用域内加密区长度）
偏移 0x7C（4  字节）：Flags —— bit0 = 系统加密，bit1 = 非系统原地加密，bit2–31 保留
偏移 0x80（4  字节）：Sector Size（512–4096）
偏移 0x84（120 字节）：Reserved（必须为零）
偏移 0x100（可变）：主密钥 + XTS 辅助密钥（级联加密时长度随算法层数增加）
```

**"全部加密"这条线画在偏移 64**，也就是紧跟在 64 字节盐值之后。`VERA` 这个字面量位于**密文里**——只有在口令正确派生出头密钥并解密之后，它才会从随机字节变成 `56 45 52 41`。官方规范里这一列的表头就写着 Encryption Status，`VERA` 那一行明确标注为 **Encrypted**。

**三条必须记住的结构事实**，它们直接决定后面所有操作怎么写：

**`VERA` 不是可搜索的明文标记。** 搜 `VERACRYPT` 搜不到是一层问题；搜 `VERA` 同样搜不到——因为那 4 个字节在盘上就是随机数据。**未解锁的卷用任何字面量搜索都定位不到。** 这不是搜法技巧的问题，是格式设计的直接后果。可用的判据只有间接的：区域熵值逼近 8.0 bit/byte、无文件系统结构、无长零串、文件大小是 512 的整数倍——这构成一个**可疑候选**，而且永远只能是候选。

**盐值是 64 字节，不是 512 字节。** 512 字节是「卷头有效区」的大小，不是盐值长度。这个数字记错会导致提取 hash 时切多 448 字节随机数据，hashcat 全部算不出结果，而且不会报错——只是永远不出 cracked。反过来也说明一件事：提取 hash 只需前 64 字节盐值，而 `-m` 号必须覆盖全部算法/KDF 候选。

卷头里没有算法 ID、没有 KDF ID、没有 PIM。 偏移 64 之后的所有字段都被加密，算法与 KDF 是通过遍历候选组合、逐个尝试解密、校验两个 CRC-32 反推出来的。这就是为什么「不解锁就读出算法」在原理上做不到，也是为什么密码攻击必须对每个 (算法, KDF, PIM) 组合各算一遍。

| 字段 | 位置 | 是否明文 | 取证价值 |
|---|---|---|---|
| **Salt** | `0x00`，64 字节 | **是（唯一）** | 提取 hash 的必需字段，每卷唯一 |
| **Magic `VERA`** | `0x40`，4 字节 | **否，在密文内** | **仅在口令正确后用于验证** |
| **Header Version** | `0x44`，2 字节 | 否 | 解密后恒为 `0x0005` |
| **隐藏卷大小 / 卷大小** | `0x5C` / `0x64` | 否 | 需口令解开后才可读 |
| **Flags（系统加密位）** | `0x7C` | 否 | 判断是否系统加密，需口令 |
| **CRC-32 ×2** | `0x48` / `0xFC` | 否 | **算法反推的判据**，见 2.4 |
| **主密钥区** | `0x100`，长度可变 | 否 | 真正的数据解密密钥（级联加密时随算法层数变长） |
| **PIM 值** | **不存在于卷头** | — | **见 2.3** |


<a id="section-5"></a>

### 2.3 PIM 的取证意义

PIM（Personal Iterations Multiplier）是 VeraCrypt 1.12 引入的参数，控制**卷头密钥派生**的计算量。它的取证意义与它的存储方式有关，而这两件事常被搞混：

> **PIM 不存放在卷头里。** 对**文件容器**和普通的挂载场景，它是操作者**每次输入**的参数。
> 官方文档说的是：VeraCrypt 从不将任何口令或 PIM 值保存到磁盘。

**但这句话有例外，必须限定范围**：**系统加密卷的高级预启动配置**可以把 PIM 以**未加密方式**写入引导记录或预启动配置文件——因为引导环境在用户解锁之前就要用这个值来挂载系统卷，来不及、也没有条件保护它。

所以准确的表述是三层：

| 场景 | PIM 是否落盘 | 取证含义 |
|---|---|---|
| **文件容器** | 不落盘 | 镜像里不存在这个信息 |
| **系统加密 · 正常挂载** | 不落盘 | 同上 |
| **系统加密 · 高级预启动配置** | **可能以明文写入 MBR / DCS 配置** | **可以从引导区读到** |

这带来一个反直觉但很重要的取证结论：对文件容器，你无法从镜像里读出这个卷用的 PIM 是多少，因此「先读卷头看 PIM 值，再决定值不值得投入爆破」这条思路**根本无法执行**——它建立在一个不存在的判据上。

而对系统加密卷，如果盘上存在高级预启动配置，方向可能反过来：PIM 就躺在引导区里，是明文可读的。这一条值得单独查一遍，成本极低（读 MBR 与配置扇区），收益是直接拿到一个决定投入规模的关键参数。

PIM 影响的只是**每个候选口令的验证代价**，公式按官方定义（PBKDF2-HMAC）：

```text
系统加密，不使用 SHA-512 / Whirlpool：  迭代 = PIM × 2048
系统加密，使用 SHA-512 / Whirlpool：      迭代 = 15000 + PIM × 1000
非系统加密 / 文件容器：                    迭代 = 15000 + PIM × 1000
```

> 关键：迭代次数不是 `PIM × 500000`。 1.12 之前 VeraCrypt 用固定迭代（文件容器 500,000 次），
> 那个数字与 PIM 没有乘数关系。1.12 之后不指定 PIM 或 PIM=0 时，
> 官方才回退到旧默认值：文件容器 500,000 次迭代，**等效 PIM = 485**。
> 把「默认迭代 500,000」当成「PIM=1 时的迭代数」是把两代参数体系混在了一起。

若 KDF 选的是 **Argon2id**（VeraCrypt 1.12+ 提供），PIM 改的是另一组参数：

```text
内存成本 m_cost = min(64 MiB + (PIM − 1) × 32 MiB, 1024 MiB)
时间成本 t_cost = 3 + ⌊(PIM − 1) / 3⌋        （PIM ≤ 31）
              = 13 + (PIM − 31)              （PIM > 31）
并行度固定为 1
```

不指定 PIM 时 Argon2id 的默认参数等效 **PIM = 12**（416 MiB / 6 次）。

**那么 PIM 到底还值不值得关注？** 值得，但关注点要换：

- **它决定单候选代价，但单候选代价不等于总代价。** 总代价 = 每候选的 PBKDF2 计算量 × 候选数量，而后者往往才是决定性的
- 文件容器的 PIM 未知时，不能给出「不可行」的结论。因为卷头里没有这个数字，你甚至无法证明它高
- **系统加密卷先查一遍预启动配置。** 这是唯一可能拿到 PIM 明文的地方，几条命令的事
- **实测速率比推算公式可靠。** hashcat 的 VeraCrypt 模式在消费级 GPU 上量级是**每秒数千次候选**（如 SHA-512 单算法约 5,700 H/s），这个实测值比任何迭代公式都更能回答「值不值得投」

> **取证第一步不是「读卷头」**——卷头没有明文可读的结构字段。
> 正确的第一步是**分流**：先判断容器类型（文件容器 / 系统加密卷），系统加密卷再花两条命令查预启动配置，文件容器直接转向低成本路径。

<a id="section-6"></a>

### 2.4 密钥派生、算法反推与主密钥的关系

```
口令 + 盐值(Salt, 64 字节明文) + 迭代参数(由 PIM 决定)
        ↓
    PBKDF2-HMAC-SHA512 / Argon2id
        ↓
    头密钥 (Header Key)
        ↓
    用它解密卷头 64–511 字节（密文）
        ↓
    两个 CRC-32 校验 → 通过才说明「算法 + KDF + 口令」三者都对
        ↓
    得到主密钥 MK
        ↓
    解密文件系统的实际数据
```

**这解释了 VeraCrypt 的一个取证友好特性**：**加密卷内的文件系统是标准格式**。

解开卷头后，卷内就是一个普通的 ext4 / NTFS / FAT32，可以正常挂载分析。

**也解释了「为什么无法在解锁前读出算法」。** 上图里 CRC 校验在口令解密之后，而解密用的头密钥依赖 KDF 与迭代参数——所以只能反过来做：把「算法 × KDF × 候选口令」的所有组合挨个试一遍，用那两个 CRC 当判据，命中即锁定算法。真实工具的挂载过程正是这样遍历的，hashcat 也要指定 `-m 13721`（SHA-512 + XTS 512 bit）这类模式，**选错模式即永远算不出结果**。

**盐值在这个环节里是必需的**，所以提取 hash 时必须切对：

```bash
# 提取前 512 字节作为 hashcat 的输入（已实测可用）
dd if=DigiForensics.vc of=veracrypt.hash bs=512 count=1
```

<a id="section-7"></a>

### 2.5 TrueCrypt 与 VeraCrypt 的兼容

| 项目 | TrueCrypt 7.1a | VeraCrypt |
|---|---|---|
| 卷头 Magic | `VERA`（4 字节，在**加密区内**） | `VERA`（4 字节，同样在**加密区内**）—— **完全相同** |
| Header Version | `0x0005` | `0x0005`—— **完全相同** |
| 默认 KDF | Whirlpool 或 SHA-512 | SHA-512，新增 Argon2id |
| 默认算法 | AES-XTS | AES-XTS |
| 迭代参数 | 固定（文件容器 500,000 次） | 固定值或 **PIM 派生** |
| 互相兼容 | VeraCrypt 可打开 TrueCrypt 卷 | TrueCrypt **不能**打开 VeraCrypt 卷 |

**取证判断**：**两者的卷头在结构上无法区分**——Magic 相同、Header Version 相同，都是 `VERA` + 版本 5。而且这层比较有个前提问题：**未解锁时两个 Magic 都是密文**，连读都读不到。

能区分的只有两处间接线索：① 真正挂载时试出来的结果——VeraCrypt 能打开 TrueCrypt 卷而反向不行；② 候选口令的派生行为差异（新卷可能用了 Argon2id，旧卷不可能）。

> **这是一个值得单独记住的陷阱形态**：卷头既不承载工具版本信息，也不提供明文定位能力。
> 分析员看到「搜不到 VERA」就写「这不是 VeraCrypt 卷」，或者凭工具印象断言「这是 TrueCrypt 7.1a 卷」，**两个结论都没有证据支撑**。

注意 TrueCrypt 7.1a 的 AES 实现曾有设计争议，这影响的是「卷本身是否可靠」，而不是「怎么判断它是哪种工具创建的」。

## 三、操作步骤

<a id="section-9"></a>

### 3.1 识别 VeraCrypt / TrueCrypt 卷

**先接受一个前提**：这一步**无法给出确定结论**。格式设计的目标就是让未解锁的卷与随机数据不可区分，所以任何输出都只能是候选。报告里写「发现疑似加密容器」是可辩护的，写「未发现加密容器」是不可辩护的。

```bash
# 1) 候选筛选 A：文件大小。容器总长是 512 的整数倍，最小约 292 KB
find /mnt/image -type f -size +292k -printf '%s\	%p\
' \
  | awk -F'\	' '{if ($1 % 512 == 0) print}' | sort -rn | head -30

# 2) 候选筛选 B：熵值。加密区熵值逼近 8.0；压缩包、已加密归档、VM 镜像同样会命中
python3 - <<'PY'
import math, collections, sys
def ent(b):
    n=len(b); c=collections.Counter(b)
    return -sum((v/n)*math.log2(v/n) for v in c.values())
for p in sys.argv[1:]:
    d=open(p,'rb').read(1<<20)
    print(f"{ent(d):.4f}  {p}")
PY

# 3) 候选筛选 C：结构缺失。确认它不像任何已知文件系统
file /mnt/image/suspect.bin           # 会报 data —— 这是正确输出，不构成任何判断
fsstat -f -t ext4 /mnt/image/suspect.bin 2>&1 | head -2

# 4) 提取 hashcat 输入。卷头有效区是前 512 字节，但只有前 64 字节盐值是明文
dd if=/mnt/image/suspect.bin of=veracrypt.hash bs=512 count=1
```

**筛完之后能确定的和不能确定的**：

```
能确定：区域无文件系统结构、熵值高、大小为 512 倍数
不能确定：这是 VeraCrypt 卷、LUKS 卷、加密归档、VM 磁盘镜像，还是普通的高熵文件
```

**卷头内部结构**（记住它，但注意它现在全是密文）：

```
偏移 0x00（64 字节）：Salt —— 唯一明文字段，提取 hash 用它
偏移 0x40 之后       ：全部加密，含 VERA / Version / Flags / CRC / 主密钥
```

为什么「看一眼 hex 就知道用的什么算法」做不到：算法与 KDF 都不在明文里，必须知道候选组合才能算 hashcat 的 `-m` 号。官方文档给出的完整组合是 3 种加密算法（AES / Serpent / Twofish）× 级联组合 × 若干 PRF——遍历组合、用两个 CRC-32 反推，是口令验证与算法识别的同一个过程。

| KDF | 单算法<br>(AES / Serpent / Twofish) | 双算法<br>(AES-Twofish) | 三算法<br>(AES-Twofish-Serpent) |
|---|---|---|---|
| RIPEMD160（TrueCrypt 旧卷） | `-m 13711` | `-m 13712` | `-m 13713` |
| SHA-512 | `-m 13721` | `-m 13722` | `-m 13723` |
| Whirlpool | `-m 13731` | `-m 13732` | `-m 13733` |
| RIPEMD160 · **boot-mode** | `-m 13741` | `-m 13742` | `-m 13743` |
| SHA-256 | `-m 13751` | `-m 13752` | `-m 13753` |
| SHA-256 · **boot-mode** | `-m 13761` | `-m 13762` | `-m 13763` |
| Streebog-512 | `-m 13771` | `-m 13772` | `-m 13773` |
| Streebog-512 · **boot-mode** | `-m 13781` | `-m 13782` | `-m 13783` |

> **三个必须注意的点：**

**列不是密钥位宽，是级联算法层数。** 官方列表里的 `XTS 512 / 1024 / 1536 bit` 指的是
AES / AES-Twofish / AES-Twofish-Serpent 这类组合下头密钥的长度，写成「512 bit」容易误读成
「用 512 位密钥加密」。真正决定选哪一列的是**加密算法**，不是密钥长度。

带 `boot-mode` 的行是给系统加密卷用的，迭代基准不同（hashcat 输出里体现为不同的
`[Iterations: ...]`），文件容器不要用这几行。

**旧卷另有一套编号。** TrueCrypt 5.0 时代的卷是 `6211`–`6243`，与 VeraCrypt 的 `137xx` 不通用。
另外 hashcat 还有一组非 legacy 编号 `29421`–`29423`（SHA-512）、`29431`–`29433`（Whirlpool）、
`29471`–`29473`（Streebog），对应 1.12 之后的参数体系。

> 这些 `137xx` 模式标注为 `legacy`，因为它们内置的是 1.12 之前的固定迭代数
> （输出中的 `[Iterations: 499999]`）。
> 这恰好印证了 2.3 的结论：PIM 不在卷头里，未指定时用的就是这批固定值。
> 换句话说，用 137xx 打 1.12+ 自定义 PIM 的卷，会因为迭代数不符而永远算不出结果——
> 而它不报错，只是静默地跑完整个字典后报 `Exhausted`。

<a id="section-10"></a>

### 3.2 挂载加密卷（已获得口令）

```bash
# Linux（需 libfuse2 支持：apt install libfuse2）
veracrypt -t /dev/sdb1 /mnt/target     # 系统卷
veracrypt -t DigiForensics.vc /mnt/target     # 文件容器

# 关键参数
#   -t / --text              文本模式（无 GUI）
#   -m ro / -m rm           以只读方式挂载 ← 取证标准
#   --non-interactive       不交互（配合 --stdin 从标准输入读口令，避免进 shell 历史）
#   --pim / --keyfiles      PIM 值与密钥文件
veracrypt -t -m ro /dev/sdb1 /mnt/target              # 交互输入口令（推荐）
printf '%s\
' "$PW" | veracrypt -t --non-interactive --stdin -m ro /dev/sdb1 /mnt/target

# 列出已挂载卷
veracrypt -t --list

# 只读挂载（取证标准动作）
veracrypt -t -m ro -p "口令" /dev/sdb1 /mnt/target
#         ↑ -p 会把口令暴露在 ps 输出与 shell 历史中，取证环境优先用交互输入或 --stdin
```

**取证标准动作清单**：

1. **先只读挂载**（`mount -o ro`），避免修改原始数据
2. **先算哈希**，再做其他操作
3. **先做全盘镜像**，再挂载
4. 挂载后**立即拍摄文件列表**（`find`），再深入分析
5. **不要在挂载状态下关机**，异常断电可能导致卷头损坏

### 3.3 找口令的现实路径
```bash
# 1) 浏览器保存的密码
#    Chrome: Login Data（SQLite）→ origin_url / username_value
#    注意：Chrome 80+ 用 AES-256-GCM，密钥来自 DPAPI，见浏览器取证篇

# 2) 密码管理器
#    KeePass: 数据库 .kdbx（可用 hashcat mode 13400 攻击）
#    1Password / Bitwarden：云端 + 本地缓存

# 3) 文本/笔记残留

#    口令可能仍驻留在内核页或进程内存中
#    bash history、终端 scrollback 都是常见命中点
```

**成本最低的现实路径**：`bash_history` / `zsh_history` 中常常直接包含命令行：

```bash

veracrypt -t -p "口令" /dev/sdb1 /mnt/x       # 交互式更安全
```

### 3.4 挂载残留的取证价值

这是 VeraCrypt 取证中最容易被忽视的高价值点。

如果目标系统在**加密卷仍处于挂载状态**时被查获（常见于服务器、办公机现场扣押），那么：
| 位置 | 残留内容 |
|---|---|
| `/etc/fstab` | 自动挂载配置，可能含口令 |
| `~/.bash_history` | 挂载命令历史 |
| systemd unit | `*.mount` 文件含 `password=` 选项 |
| `/proc/mounts` | 挂载点与设备映射 |
| 内核内存 | 已解密的卷内文件、文件系统缓存 |
| 页交换 | `swap` 分区中可能残留明文数据 |
| 日志 | `syslog` / `journalctl` 中的挂载记录 |

```bash
# 检查 fstab 中的挂载配置
grep -iE "veracrypt|crypt|/dev/sd" /mnt/image/etc/fstab

# 检查 systemd mount unit
grep -rl "veracrypt" /mnt/image/etc/systemd/system/

# 检查历史命令
grep -iE "veracrypt|mount" /mnt/image/home/*/.bash_history

# 提取 swap 中的明文
strings -n 10 DigiForensics-swap.dd | grep -iE "身份证|银行卡|password|私钥"
```

> **核心判断**：如果挂载点存在且设备已解锁，就不需要口令，可直接分析挂载点。

<a id="section-13"></a>

### 3.5 隐藏卷与隐藏文件系统

VeraCrypt 支持隐藏操作系统/隐藏卷，这给取证带来挑战：

- **隐藏卷位于外层卷的空闲空间中**，占据外层卷最后若干扇区
- 外层卷用假口令解锁后，**隐藏卷的空间显示为随机数据**（这是设计目的）
- 隐藏卷有自己的卷头

```bash
# 1) 挂载外层卷后检查空闲空间：若"异常大"且完全随机，疑似隐藏卷
veracrypt -t --list
df -h /mnt/outer

# 2) 隐藏卷头在偏移 65536（主卷头在 0，数据从 131072 开始）
#    ★ 但隐藏卷头同样没有明文签名 —— 搜 VERA 是无效的
#    可用的只是间接指标：65536 处的 512 字节是否也是高熵随机数据
dd if=DigiForensics.vc bs=512 skip=128 count=1 | xxd | head -4
# 无法从这段字节判断「这是什么」，只能确认它不长得像任何已知结构
```

**取证判断依据**：

1. 卷大小与实际数据量不匹配（空闲空间远超预期）→ **可能有**隐藏卷
2. 空闲区内容熵值极高且无文件系统特征 → **疑似**加密内容
3. 隐藏卷头位置（偏移 65536）存在一段高熵数据 → **又一个候选**

**三条都只是候选，没有一条能证明隐藏卷存在。** 格式设计上，「存在隐藏卷」与「空闲空间被随机数据填充」在盘上是不可区分的——VeraCrypt 创建卷时就会用随机数据填满空闲区。**这正是可否认性的实现方式。**

因此关于隐藏卷的结论必须这样写：

> 在外层卷空闲区偏移 65536 处发现 512 字节高熵数据（熵值 7.99），与隐藏卷头位置一致。由于隐藏卷头与随机填充数据在该位置不可区分，本次检查无法确认隐藏卷是否存在。 需在外层卷口令正确的前提下，分别以候选隐藏卷口令执行挂载验证，才能得出确定结论。

**这条结论的可辩护性来自哪里**：来自它明确交代了「哪个判据做不到什么」，而不是来自它是否找到了隐藏卷。

## 四、常见陷阱

本章的陷阱有一个共同形状：VeraCrypt 的每一步都会给出一个「看起来合理」的输出——看到一串高熵数据就能写成「发现加密容器」，挂上载就能看到文件名，解出一段字节就能当成口令。加密容器没有「明确报错」这个反馈通道，所以几乎所有误判都发生在**没有报错的分支**上。

这一点在 VeraCrypt 上比在别的取证对象上更极端：**卷头没有明文签名**。别的格式给你一个魔数让你认，它连这个都不给。于是分析员会不自觉地用「搜一下」代替「判断一下」，而「搜不到」这个输出看起来和别的否定性发现一模一样。

本章按评估阶段 → 挂载操作 → 隐藏卷与格式识别 → 内存与交换归组，与 2.3 的 PIM 表述、2.5 的 TrueCrypt 兼容关系保持一致。

<a id="section-15"></a>

### 4.1 评估阶段的严重决策

<a id="section-16"></a>

#### 用字面量搜索并把空结果写成「无加密容器」 ★★★

**现象**：全盘 `grep -aob "VERACRYPT" DigiForensics.dd` 返回空，或搜 `VERA`、搜 `TRUECRYPT` 同样返回空。分析员在报告里写下「目标盘未发现 VeraCrypt/TrueCrypt 加密容器，证据可直接分析」，后续所有文件清单、时间线、哈希基线都基于这个前提展开。

**原因**：**VeraCrypt 卷没有签名。** 这不是「搜错了字符串」这么简单——官方格式规范明确写着：VeraCrypt 卷没有 signature 或 ID 字符串，在解密之前完全由随机数据组成。卷头里唯一的未加密字段是**前 64 字节盐值**，`VERA` 这个 4 字节字面量位于**偏移 64 之后的加密区内**，在盘上就是随机字节。

**所以换一个「正确的」字面量去搜，同样返回空。** 用 `VERACRYPT` 搜不到是常识，换成 `VERA` 也一样——搜不到的原因与搜什么无关，只与「盘上没有明文签名」这个事实有关。这个判据从一开始就不存在。

更麻烦的是它「看起来像」一个正常的否定性发现：不报错、退出码为 0、输出干净，很容易被当成有效结论。

**影响**：这是本领域比较典型的假阴性，而且**它会把整个调查方向带偏**。盘上有一个 500 GB 的加密容器，报告却写「未发现加密容器，证据可直接分析」——委托方据此认为数据可以直接导出，直到需要读取具体内容时才暴露。更远的后果是：基于「无加密」前提做出的全部文件清单、时间线关联、跨设备同一性判断，**全部需要推倒重来**，而这些结论可能已经写进了给委托方的中期报告。

**核查**：**用间接证据筛候选，并且只写候选、不写否定结论。**

```bash
# 1) 按大小筛：容器总长是 512 的整数倍，最小约 292 KB
find /mnt/image -type f -size +292k -printf '%s\	%p\
' \
  | awk -F'\	' '{if ($1 % 512 == 0) print}' | sort -rn | head -30

# 2) 按熵值筛：加密区逼近 8.0 bit/byte
python3 -c "
import math,collections
d=open('/mnt/image/suspect.bin','rb').read(1<<20); n=len(d)
c=collections.Counter(d)
print(-sum((v/n)*math.log2(v/n) for v in c.values()))"

# 3) 确认不像任何已知文件系统（VeraCrypt 不会命中任何 fs 魔数）
file /mnt/image/suspect.bin
```

**阴性结论的正确写法**（这才是关键）：

> 在 `DigiForensics.dd` 中未发现**具有可识别明文签名**的加密卷标识符。**VeraCrypt 卷在设计上不具备明文签名**，本次筛选基于文件大小（512 整数倍）、区域熵值与文件系统结构缺失三项间接指标，共得到 4 个候选区域。未对候选区域执行口令验证，因此不能排除加密卷存在。 若需进一步排除，应在获得口令后对候选区域执行挂载验证。

**这句话能被辩护。** 「未发现 X 签名」是事实陈述，「X 在设计上不存在签名」把否定限定在正确范围内，而「候选数 + 未验证」明确交代了覆盖范围。

> **这一条同时修正两条流传很广的思路**：
> 一是「先读卷头看 PIM 值决定要不要投入爆破」——PIM 不在卷头里，镜像中不存在这个信息；
> 二是「搜到 VERA 就确认了卷头」——未解锁时 VERA 在密文内，任何字面量搜索都不会命中。
> 能够指导投入决策的判据只有两个：候选口令的数量，以及单候选的实测速率。

<a id="section-17"></a>

#### 把 `XTS 512 / 1024 / 1536 bit` 读成密钥长度 ★★

**现象**：从 hashcat 的模式表里抄下 `13721` 与 `13723`，凭字面判断「13723 是 1536 位密钥，比 13721 的 512 位更强，所以用 13723 一定能破」，于是只跑 `-m 13723` 一个模式。跑完字典后 hashcat 报 `Exhausted`，分析员据此写下「该卷使用高强度加密，不可破解」。

**原因**：模式号里的 `512 / 1024 / 1536` **不是密钥位宽，而是级联算法的层数**：

- 单算法（AES / Serpent / Twofish 之一）→ `13721`
- 双算法（AES-Twofish）→ `13722`
- 三算法（AES-Twofish-Serpent）→ `13723`

列对应的是**算法组合**，不是加密强度。用三算法模式去试一个单算法卷，会因为需要派生的密钥长度对不上而永远算不出结果——而它不报「模式错误」，只是安静地跑完全部候选后报 `Exhausted`。

**影响**：`Exhausted` 是最容易被误读的输出之一。它只说明「这个模式下没找到」，不说明「找不到」。把它当成「该卷不可破解」的证据，等于用一个失败模式否定了全部七个模式——**而正确的那个模式可能只要几分钟就能命中**。委托方若据此下调了调查优先级、放弃了其他取证路径，损失远大于多跑一个模式的成本。

**核查**：算法未知时，从三算法模式起手，逐级回退，并且必须跑满全部候选 KDF。

```bash
# 单容器先测三算法模式（覆盖面最广），失败后再回退
for m in 13723 13722 13721; do
  hashcat -m $m veracrypt.hash wordlist.txt --status
done
# 再覆盖其他 KDF：Whirlpool 13733/13732/13731、SHA-256 13753/13752/13751
```

**同一项要求还适用于 PIM**：若这个卷是 1.12+ 用自定义 PIM 创建的，`137xx` 这批 legacy 模式内置的是旧的固定迭代数，**同样会一直 `Exhausted`**。此时唯一的确认方式是拿候选口令实际挂载一次——挂载成功就同时证明了口令和 PIM。

报告里报「不可行」之前，先确认自己真的把该试的都试过了。

<a id="section-18"></a>

### 4.2 挂载操作（★ 表示不可逆破坏性操作）

<a id="section-19"></a>

#### 直接挂载可写卷 ★★★

**现象**：在分析机上双击 VeraCrypt 卷，输入口令后选「读写」模式挂载，以便浏览文件、导出文档；命令行上则是不带 `-m ro` 直接跑 `veracrypt -t /dev/sdb1 /mnt/target`。

**原因**：取证语境下「能读」就够了，写入能力没有任何取证价值。但可写挂载会改动卷内元数据——文件系统访问时间与目录 mtime、日志（NTFS 的 `$LogFile`、ext4 的 journal 提交）、卷内的卷头副本（VeraCrypt 会把当前槽位与状态写回），这些改动都**无法还原**。更隐蔽的是 VNC/远程桌面、`/etc/fstab` 的 `x-systemd.automount` 这类自动解锁配置会让一次「只读探索」在下次重启后变成自动可写挂载，而这件事不发生在你眼前。

**影响**：破坏证据完整性，且不可逆。庭审中对方只需主张「检材在接手前后的完整性无法保证」，你基于元数据的全部结论都会被牵连。若卷内有自校验或自毁逻辑，写入触发可能直接改写用户数据，而损伤是我方造成的。

**核查**：**只读挂载，或更好——根本不挂载。**

优先级：① 内存镜像中直接提取明文；② 配合底层设备只读挂载；③ 记录挂载时间、工具版本、参数到报告。

```bash
# 只读标准动作：交互输入口令（避免 -p 暴露，见下条），挂载后再由内核强制 ro
veracrypt -t --non-interactive --stdin -m ro /dev/sdb1 /mnt/target <<< "$PW"

# 二次收口：即使 VeraCrypt 侧报了可写，也用内核挂载选项压成 ro
findmnt -no OPTIONS /mnt/target | grep -o 'ro' || \
  sudo mount -o remount,ro /mnt/target

# 记录工具版本，报告里要写
veracrypt --version
```

`findmnt -no OPTIONS` 的输出直接粘进证据处理记录；卸载后对镜像重算哈希并与入库哈希比对，把「分析过程未污染证据」写成可验证的事实而不是声明。

<a id="section-20"></a>

#### 挂载文件容器时用错偏移 ★

**现象**：直接 `mount /dev/loop0 DigiForensics.vc`，VeraCrypt 报「无效的卷」；或者更糟——挂载成功，列出的是宿主机的根目录内容。

**原因**：文件容器的**主卷头在文件偏移 0**（不在末尾），隐藏卷头在 64 KiB，**数据区从 128 KiB 开始**——这是常见的记反点。反过来的坑同样存在：卷的实际大小 = **文件大小 − 128 KiB**，若按文件总大小去挂载或去算容量，尾部会多出一段不属于文件系统的区域，被解析工具读成「文件系统损坏」。

顺带纠正一个流传很广的说法：「VeraCrypt 文件容器的卷头在文件末尾，所以 `file` 命令认不出来」。**这也是错的**——文件容器的卷头就在文件开头，`file` 认不出的真正原因是**那 512 字节里没有明文签名可供匹配**，与它在开头还是末尾无关。

**影响**：可能把宿主机上的其他文件误当作容器内容，或者反复调参直到挂出一个「看起来正常但完全无关」的卷。后者更危险——它能列出文件名、能读到内容，几乎所有快速检查都会通过。

**核查**：**让工具自己探测，而不是手工指定偏移。** 注意 Unix 版 VeraCrypt 的选项表里**没有** `--tc`、`--offset`、`--password-file` 这三个选项——它们在 Windows 版或其他工具里常见，写在 Unix 命令里会直接报未知选项：

```bash
# ★ Unix 版的正确写法：--filesystem=none 表示只映射加密设备、不挂载文件系统
#   口令用 --stdin 从标准输入读（配合 --non-interactive），避免出现在 ps 与 shell 历史里
#   隐藏卷不靠参数选择，而是用候选隐藏卷口令直接挂载该卷——见下
printf '%s\n' "$PW" | veracrypt -t --non-interactive --stdin \
  --filesystem=none DigiForensics.vc /mnt/target

# 验证挂出的是不是目标卷：看设备容量是否与预期一致
# 期望容量 ≈ 文件大小 − 128 KiB（数据区从偏移 131072 开始）
lsblk /dev/loop* 2>/dev/null | head
dmsetup table 2>/dev/null | head
```

**★ 澄清一个高频误解：`--slot` 不是"普通卷 / 隐藏卷"的选择器。** 官方文档对 `MOUNTED_VOLUME` 的定义是：已挂载卷可以用**卷路径**、**挂载目录**、或**挂载槽位号**三种形式指定，而 `--slot=SLOT` 用的是第三种——**它是"第几个挂载点"，与卷类型无关**。所以：

- `--slot 1` 不等于"普通卷"，`--slot 2` 也不等于"隐藏卷"；写 slot 号只是选挂载点
- **隐藏卷不能靠 slot 选出来**。正确做法是：宿主卷（文件容器）就是那一个容器文件，**用候选隐藏卷口令挂载同一个容器**即可——VeraCrypt 会先用该口令在偏移 65536 处尝试解隐藏卷头，成功则挂出隐藏卷
- 挂出内容「不对」时，先怀疑的是**口令对应错了卷**（外层口令 vs 隐藏卷口令），而不是 slot 号

<a id="section-21"></a>

#### 用 `-p` 传口令，把凭据写进 `ps` 输出和 shell 历史

**现象**：命令行里写 `veracrypt -t -m ro -p "MyPass123" /dev/sdb1 /mnt/target`，口令出现在终端回显、shell 历史文件、以及整个分析机上任何用户 `ps aux` 都能读到的进程命令行里。

**原因**：`-p` 是「图省事」的写法，在取证环境里它同时踩了三个坑：① `ps` 输出对同机器上任何本地用户可见，口令在挂载的整段时间里处于明文可读状态；② 这条命令会进入**分析机自己的** `HISTFILE`，而分析机的 shell 历史往往与检材的 shell 历史在后续批量比对时混在一起；③ 若分析机复用了检材的家目录或 `HISTFILE`，它就**直接写进了检材的证据区**。

**影响**：凭据泄露面从「一个卷」扩大到「所有能跑 `ps` 的人 + 分析机的历史文件」。更麻烦的是第三种情况——如果它写进了证据区，本篇 3.4 说的「在历史里搜 `veracrypt` 命令」这条路径就会命中一条**由分析员自己产生的**记录，而在报告里它看起来和攻击者留下的完全一样。

**核查**：用 `--stdin` 或交互输入，让口令不进命令行。

```bash
# 推荐：交互输入（最干净）
veracrypt -t -m ro /dev/sdb1 /mnt/target

# 或经标准输入，配合 --non-interactive 避免挂起
printf '%s\
' "$PW" | veracrypt -t --non-interactive --stdin -m ro /dev/sdb1 /mnt/target

# 用密钥文件时，密钥文件路径本身也别落在证据区内
veracrypt -t -m ro --keyfiles /evidence/keys/DigiForensics.key /dev/sdb1 /mnt/target
```

分析机上先 `export HISTFILE=/evidence/analysis_history` 再操作，并在报告的「工具使用」一节写明「口令经 `--stdin` 传入，未使用 `-p`」。这句话在质证时是有用的。

<a id="section-22"></a>

### 4.3 隐藏卷与格式识别

<a id="section-23"></a>

#### 忽略隐藏卷

**现象**：外层卷正常挂载，看到常规文件系统，未报告可能存在隐藏内容。报告里写「该容器内未见隐藏卷特征」。

**原因**：VeraCrypt 支持隐藏卷与隐藏操作系统，隐藏卷**占用外层卷的空闲空间**——所以「外层看起来还有未使用空间」恰恰是正常现象，VeraCrypt 就是用这种方式让外层看起来没被用满。反过来，把外层空闲区读成「随机数据、没有文件系统特征」也是设计目的，不是异常。

这里是 VeraCrypt 取证最反直觉的一点：判别隐藏卷的那个判据本身不存在。 通常的思路是「搜第二个卷头标记」——但**卷头没有明文签名**，隐藏卷头和随机填充数据在偏移 65536 处完全无法区分。所以「是否存在隐藏卷」在拿到隐藏卷口令之前**无法被证明，也无法被排除**。

**影响**：漏掉真正隐藏的数据层。写「该容器内未见隐藏卷特征」是**阴性发现的错误表述**——它暗示你检查过并且没找到，而实际上这个检查做不了。

**核查**：**把隐藏卷存在性写成「不可判定」并说明原因**，这才是事实陈述。

```bash
# 1) 辅助判据：空闲区熵值。加密数据接近 8.0，普通空闲区低得多
python3 -c "
import math,collections
d=open('DigiForensics.vc','rb').read(1<<20)
c=collections.Counter(d)
H=-sum(n/len(d)*math.log2(n/len(d)) for n in c.values())
print(f'entropy={H:.3f} bit/byte')"

# 2) 隐藏卷头固定位置的间接观察（不能证明什么）
dd if=DigiForensics.vc bs=512 skip=128 count=1 | xxd | head -4
```

熵值高只说明「这段数据不像空闲区」，不能单独证明有隐藏卷——它同样可能是创建时填入的随机数据。

**关于隐藏卷的结论只能这样写**：

> 已检查外层卷空闲区（偏移 65536 起）与隐藏卷头位置一致，熵值 7.99，**与随机填充数据不可区分**。VeraCrypt 未提供任何可用于确认隐藏卷存在的明文判据，因此本次检查不能确认也不能排除隐藏卷存在。后续需在获得候选隐藏卷口令后执行挂载验证。

**注意这里为什么不能用「搜 VERA」**：搜不到不代表不存在，搜到了也不代表是卷头。**一个判据如果两种情况下输出相同，它就不是判据。**

<a id="section-24"></a>

#### 只用外层口令挂载成功，就认为「这个口令就是涉案口令」

**现象**：用委托方提供的口令挂上外层卷，列目录、看几个文件，报告写「该口令可解密此容器」，并据此认为数据已完整获取。

**原因**：隐藏卷与外层卷是两个独立的卷，各有各的卷头与口令验证。 外层挂载成功只验证了外层那一半。VeraCrypt 在创建隐藏卷时，外层卷会被填满随机数据以掩盖隐藏卷的存在——这意味着外层挂载后看到的所有文件，其时间戳、目录结构、剩余空间都是面向「未被使用」设计的，它们不能用来推断这个卷的使用方式。

**影响**：结论方向错了一档。「已解密此容器」被委托方读成「数据都在这里了」，于是不再去追另一条口令线索（密钥文件、另一把口令、内存明文）。第五章 5.5 就是这个结构：口令全败的原因不是凭据错误，而是验证材料只给了一半。

**核查**：**区分「解开了外层卷还是隐藏卷」。** 注意这不是 `--slot` 的职责——`--slot` 只是挂载点编号，与卷类型无关。隐藏卷的验证方式是**用候选隐藏卷口令去挂载同一个宿主容器**：

```bash
# 1) 先用外层口令挂载，确认它解的是外层卷
printf '%s\n' "$PW_OUTER" | veracrypt -t --non-interactive --stdin \
  DigiForensics.vc /mnt/outer

# 2) 再用候选隐藏卷口令挂载同一个容器文件（VeraCrypt 会在偏移 65536 处尝试解隐藏卷头）
printf '%s\n' "$PW_HIDDEN" | veracrypt -t --non-interactive --stdin \
  DigiForensics.vc /mnt/hidden

# 3) 分别记录两处实际挂出了什么，不要混为一谈
veracrypt -t --list
```

> 报告表述：「以口令 P 成功挂载外层卷；以候选口令 Q 挂载同一容器，成功解出隐藏卷 / 返回校验失败，隐藏卷未获验证」。

只要隐藏卷未验证，结论就写「**外层卷已解密**」，不写「容器已解密」。两者的证据强度不同。

<a id="section-25"></a>

#### 挂载后大量"损坏"文件却归咎于文件系统

**现象**：挂载成功后文件列表里大量文件打不开、文件名乱码，报告写「该卷文件系统损坏」。

**原因**：更可能是**卷内本来就没格式化**——VeraCrypt 允许创建时选「Do not format」，此时卷内是随机数据，工具当文件系统扫描自然全是「损坏」。另一个常见原因是**用错了口令类型**：外层口令与隐藏卷口令解开的是不同的卷头，**与 `--slot` 号无关**（`--slot` 只是挂载点编号）。第三种情况是把 `BT-0x` 那类**尚未剥离的前缀**当成了数据内容（见下一条）。第四种情况是文件容器按总大小挂载后尾部多算了一段。

**影响**：把工具配置问题写成「证据损坏」，是**定性错误**——前者是我方操作问题，后者是对证据状态的判断。「证据损坏」这个结论一旦写进报告，委托方会据此认为数据不可恢复而中止调查。

**核查**：**先确认卷内是否本来就没格式化**，再排除 slot 错误。判断依据是文件系统签名：

```bash
python3 -c "
d=open('DigiForensics.vc','rb').read(0x10000)
found=False
for sig,name in [(b'NTFS    ','NTFS'),(b'EXFAT','exFAT'),(b'LUKS','LUKS'),(b'\x53\xef','ext2/3/4')]:
    if sig in d: print('found',name); found=True
if not found: print('no filesystem signature -> 卷内未格式化')"
```

**排查顺序固定**：slot 对不对 → 签名在不在 → 卷大小是否按「文件大小 − 卷头大小」算的。每一步不通过就停在那一步，不要跳到「文件系统损坏」。

<a id="section-26"></a>

#### 把文件扩展名或文件名当成格式判据

**现象**：看到 `evidence.hc`、`secret.tc`、`backup.dat` 这类文件，`file` 命令报 `data`，于是判定「这不是加密容器，是普通二进制文件」；反过来，看到一个无扩展名的可疑文件就断定「这是 VeraCrypt 容器」。

**原因**：扩展名是创建者随手填的字符串，VeraCrypt 不校验它。 `.hc`、`.tc`、`.dat`、无扩展名都可以是容器；一个 `.jpg` 也可以是容器。`file` 命令报 `data` 是完全正确的输出——因为卷头没有明文签名，magic 库里也就不可能有它的条目，所以这个输出不构成任何方向的判断。

顺带修正一个流传很广的说法：「`file` 认不出它是因为 magic 库只看文件头、而卷头在文件末尾」。这个解释本身也是错的——**VeraCrypt 文件容器的卷头在文件开头**（偏移 0），magic 库看的就是那里。认不出的真正原因只有一个：那 512 字节里只有 64 字节是明文盐值，没有任何可供匹配的签名。

**影响**：把「格式识别」建立在文件名上，会同时产生两类错误：漏判（真正的容器因为叫 `.dat` 被排除）和误判（一个普通大文件因为无扩展名被送进解密流程，浪费掉一轮评估时间）。

**核查**：**只认间接指标，并把它们写成候选而不是结论。**

```bash
# 判据一：大小是 512 的整数倍，且超过 292 KB
stat -c '%s %n' /mnt/image/suspect.bin
python3 -c "import os;print(os.path.getsize('/mnt/image/suspect.bin')%512)"

# 判据二：熵值逼近 8.0 bit/byte
python3 -c "
import math,collections
d=open('/mnt/image/suspect.bin','rb').read(1<<20); n=len(d)
c=collections.Counter(d)
print(-sum((v/n)*math.log2(v/n) for v in c.values()))"

# 判据三：让工具实际探测。传空口令，输出本身就是信息
veracrypt --text --non-interactive /mnt/image/suspect.bin </dev/null
# 报「口令错误 / 不是 VeraCrypt 卷」比报「无法识别文件格式」更有区分力
```

**报告里禁止出现的表述**：「根据文件扩展名判定为加密容器」——扩展名不是判据。**可以写的表述**：「该文件大小为 512 的整数倍、熵值 7.99、不匹配任何已知文件系统，列为加密容器候选，待口令验证」。

<a id="section-27"></a>

#### TrueCrypt 7.1a 打不开 VeraCrypt 创建的卷

**现象**：用 TrueCrypt 7.1a 挂载 VeraCrypt 新建卷，提示「格式不正确」；或用 VeraCrypt 打不开某个 TrueCrypt 卷。

**原因**：**卷头结构在两者之间完全相同**（见 2.5，都是 `VERA` + 版本 5，且两者都在加密区内），所以**唯一可靠的区分方式就是实际挂载实测**。VeraCrypt 可以打开 TrueCrypt 创建的卷，反过来不行——这是设计上的单向隔离，不是文件损坏。

这里还有一个常见的连带误判：凭「这是老卷」或工具印象就写「TrueCrypt 7.1a 卷」。**卷头不承载创建工具的版本信息，Magic 也不行**（何况它根本读不到）。如果确实需要给出工具版本结论，唯一的依据是**实际用 VeraCrypt 挂载成功**这件事本身。

**影响**：误报「卷已损坏/格式异常」，或给出错误的工具结论。前者会让委托方直接放弃这条路径。

**核查**：**工具版本必须与创建端匹配，且要双向确认。**

```bash
# 1) 记录工具版本，报告里必须有
veracrypt --version

# 2) 确认方向：VeraCrypt 可打开 TrueCrypt 旧卷；TrueCrypt 打不开 VeraCrypt 新卷
# 3) 打不开时先排除凭据分支——区分报错文本
#    "Incorrect password" → 格式分支已过，只差口令
#    "not a VeraCrypt volume" → 卷头位置/版本/格式问题，回到 3.1 重新定位
```

取证环境固定用 VeraCrypt 最新版，并把版本号写进报告。**同一台机器上的两个「打不开」必须分开记录**，一个是工具限制（能力声明），一个是卷的问题（分析缺口）。

<a id="section-28"></a>

### 4.4 内存与交换中的明文 ★

<a id="section-29"></a>

#### 挂载过的卷，明文残留在内存缓存与 swap 中

**现象**：对某 VeraCrypt 卷已完成口令爆破并挂载过，之后才拿到内存镜像；或对一块已解锁的盘做了 swap 分区镜像，准备从中找敏感数据。

**原因**：VeraCrypt 挂载后，文件系统页缓存里保留着**解密后的数据页**；若系统有 swap，容器内文件内容也可能被换出到磁盘。取证人员习惯性认为「加密就是安全的，内存里也不会有明文」，但加密容器是**写入路径上的加密**，读取时明文在内存中是必然的。另一个方向上的误判也存在：**挂载点还在、卷仍处于解锁状态时直接关机**，会让这个窗口永久关闭——VeraCrypt 的会话密钥只在内存里，磁盘上永远只有密文。

**影响**：**错过成本最低的一条路径**，同时在另一个方向上造成不可逆的损失。内存取证的边际成本远低于离线口令恢复，而执行顺序常常正好搞反。第五章 5.1 里恢复出的 1.2 GB 缓存页（其中 340 MB 涉及已删除的客户记录）在磁盘任何位置都不存在，因为那部分数据尚未刷盘。

**核查**：**先扫内存，再考虑离线恢复；卷仍挂载时不要关机。**

顺序：① 内存中提取明文/密钥；② 找密钥文件、配置残留；③ 最后才评估离线验证。

```bash
# 1) 内存镜像中搜索已知文件名/关键词的明文片段
strings -n 8 DigiForensics-mem.raw | grep -i -A2 -B2 '关键词'

# 2) 查内核页缓存中的卷映射与已解锁设备
strings -n 8 DigiForensics-mem.raw | grep -iE 'veracrypt|cryptsetup|/dev/mapper' | head

# 3) swap 镜像中的明文残留
strings -n 10 DigiForensics-swap.dd | grep -iE '身份证|银行卡|私钥'

# 4) 现场处置单上写死三条：不关机、不重启、不重新挂载
```

第 4 条要写进现场处置单而不是记在脑子里——现场扣押时任何一条被误执行都会关闭这个窗口，且无法补救。参见 [3.4 挂载残留的取证价值](#section-12) 里的 `fstab` / systemd unit 检查清单。

<a id="section-30"></a>

#### 挂载失败被直接写成「卷已损坏，数据不可恢复」 ★★

**现象**：挂载时报 checksum 错误或格式错误，报告写「该卷卷头损坏，数据不可恢复」。

**原因**：**口令错误和真正的数据损坏，在错误文本上无法区分。** 两者最终都体现为「解密后的卷头通不过 CRC-32 校验」——而 CRC 校验本身就是口令解开之后才起作用的。也就是说，你看到 checksum 错误时，还不知道是口令错了还是卷真的坏了。

顺带说明一个常见但错误的自证逻辑：「卷头还在（能搜到 Magic），所以卷头是完好的」。这条判据在 VeraCrypt 上不成立——**未解锁时根本搜不到任何 Magic**，而解锁失败恰恰是搜不到的原因。**用搜不到来证明搜不到，这不是判据。**

真正的成因至少四种：① 口令错误；② 挂载时异常断电导致卷头写了一半；③ 卷头所在扇区有坏块；④ **有人原地改过参数**（反取证手法之一，见第六章第三组）。**这四种都表现为同一个错误文本。**

**影响**：「数据不可恢复」是一个**关于案件可行性的终止性结论**，一旦写进报告，委托方很可能就此结案。而实际原因可能只是口令输错了一次。应先区分口令错误、参数不符和数据损坏，再评估可恢复性。

**核查**：**先把「口令错误」排除掉，再谈损坏。**

```bash
# 1) 排除法第一步：换一个已知正确的候选再试一次
#    同一容器、同一个 PIM 下，两次不同口令都报同样错误，才值得怀疑卷本身

# 2) 检查卷头区域是否可读（这一项与口令无关）
dd if=DigiForensics.vc bs=512 count=1 | xxd | head -8
# 能读出 64 字节高熵盐值 + 448 字节高熵密文 = 区域完整可读
# 出现全零、FF 填充或明显坏块模式 → 物理或逻辑层面的损坏，方向立刻改变

# 3) 验证区域可读 ≠ 卷头完好，但能划掉一整类原因
#    这一步是只读的，几秒钟就能做完，不做的话后面所有推断都建在浮冰上
```

**报告里该写什么**：

> 挂载尝试返回 checksum 校验失败。**该错误在口令错误与卷头损坏两种情况下表现相同**，本次尚不能区分。已确认卷头所在 512 字节区域可完整读取（盐值与密文均为高熵，无全零或坏块模式），据此排除物理层面的区域丢失，但无法排除参数被改写或口令错误。后续计划：取得委托方确认的口令后复测；若复测仍失败，再按卷头损坏方向处理。

**顺带一条可用的判据**：卷内确实存在**主卷头与备份头两份**，但官方规范明确指出备份头**不是主卷头的副本**——它用**不同的盐派生不同的头密钥**加密，因此两处字节本来就应当不同。逐字节比对的意义不在"是否一致"，而在**确认两处都能读出结构、以及为事后重算提供参照**；把"两处不一致"直接写成篡改信号是错误判据。

```bash
# 备份头位置必须按卷大小计算，不能硬编码：官方规范中 S = 卷宿主大小（字节）
#   S-131072  → 主卷的备份头
#   S-65536   → 隐藏卷的备份头
# 下面以 2 GiB 容器为例（S=2147483648 字节 = 4194304 个 512 字节扇区）
SZ=$(stat -f%z DigiForensics.vc)          # Linux: stat -c%s
SECTORS=$(( SZ / 512 ))

dd if=DigiForensics.vc bs=512 skip=0           count=1 | xxd > /tmp/hdr_primary.txt
dd if=DigiForensics.vc bs=512 skip=$(( SECTORS - 256 )) count=1 | xxd > /tmp/hdr_backup.txt
dd if=DigiForensics.vc bs=512 skip=$(( SECTORS - 128 )) count=1 | xxd > /tmp/hdr_backup_hidden.txt

echo "卷大小字节: $SZ  扇区数: $SECTORS"
echo "主卷备份头所在扇区: $(( SECTORS - 256 ))"
echo "隐藏卷备份头所在扇区: $(( SECTORS - 128 ))"
xxd /tmp/hdr_primary.txt | head -4
xxd /tmp/hdr_backup.txt  | head -4
```

> **★ 不要把备份头写成固定扇区号。** 备份头的位置随卷大小变化；写死 `skip=254` 只在"卷大小恰好为 130048 字节"这种几乎不可能的容器上才对。正确做法是**先取卷大小再算 `S-65536` 与 `S-131072`**（单位是字节，除以 512 得到扇区偏移）。

**两处字节不同是格式的正常结果，不是异常。** 真正有判据价值的是：① 两处 512 字节区域是否都可完整读取、有无全零或坏块模式；② 两处的盐值是否各自唯一。若某一份读出全零或不可读，那一份才是损坏的证据。

## 五、案例示例

<a id="section-32"></a>

### 5.1 运行中的 Debian 服务器：挂载态比口令更有价值

**场景**

查获一台 Debian 服务器，运维人员报告"有一块 `/dev/sdb1` 加密分区，里面是客户数据"。现场扣押时**系统仍在运行**。委托方的问题是"数据能取出来吗"。

选择这一路径的依据是：暴力破解 VeraCrypt 口令在实践中通常不可行——**但这不是绝对结论**，它取决于实际迭代次数（即 PIM，而 PIM 不在卷头里、连不上就无法证明）、可用算力与候选口令数量，所以本篇 5.5 一贯把它写成"缺证据基础"，而不是"极难"。而一个已解锁且仍挂载的卷不需要口令。这台机器恰好处于这个状态。

**处置过程**

1. **不做关机**，先内存后磁盘：

```bash
# 先取内存——挂载态、VeraCrypt 的内存密钥、已解密数据都只存在于此刻
sudo avml --output /case/DigiForensics-mem.raw
sudo dcfldd if=/dev/sdb of=/case/DigiForensics.dd \
     hash=md5,sha256 hashlog=/case/DigiForensics.hashlog bs=4M conv=noerror,sync
```

2. 内存分析：找到 `veracrypt` 进程，且 `/dev/sdb1` 处于**已挂载状态**，挂载点 `/data`：

```bash
python3 -m volatility3 -f /case/DigiForensics-mem.raw linux.pslist | grep -i veracrypt
```

3. **直接分析挂载点**——无需口令，对 `/data` 做文件枚举，发现客户数据库。

4. 回查 `fstab`，拿到明文口令：

```text
/dev/sdb1 /data veracrypt defaults,x-systemd.automount,password=CustomerData2024 0 0
```

**拿到明文口令**（虽然已不需要）。

5. 确认加密状态并固定卷头证据。**注意这里能读到什么、读不到什么**：

```text
无需口令即可读取：
  Salt: 64 字节（卷头偏移 0，唯一的明文字段）
  区域可读性：512 字节完整，高熵，无全零/坏块模式

需要口令解开才能读取（在本次已挂载前提下已有口令）：
  Magic: VERA (0x56455241) at 卷头偏移 64
  Header Version: 0x0005
  Sector Size: 512
  Flags: bit0 = 1（系统加密）
```

**这一条本身就是本案例的方法论要点**：报告里不能出现「搜到 VERA 确认卷头」这种表述——未解锁时那 4 个字节是密文。卷头证据的固定方式是「记录偏移 + 记录哈希 + 用口令解开后回读结构字段」，而不是「grep 命中」。

算法与 KDF 同样需要口令解开才能确认——但**这一步已经不重要了**：卷处于挂载状态，参数值只影响"这个卷有多难破解"，而现在根本不需要破解。顺带说明，即便日后需要离线恢复，实测速率（GPU 上 SHA-512 模式典型每秒数千次候选）比任何迭代公式都更能回答投入产出问题。

6. 证据固定：记录挂载点、`fstab` 行偏移、卷头偏移、**卷头 512 字节的 SHA-256**、口令明文位置。

7. 挂载态这一条还有一层后续价值，采集时顺手取走。VeraCrypt 的解密密钥在 `dm-crypt` 映射的设备里，FUSE 挂载则更靠上；无论哪种，都可以用一张临时挂载点把整个卷原样导出，而不必先解密再重采：

```bash
# 卷已挂载时，dd 读挂载点底层设备等价于读明文卷
sudo dcfldd if=/dev/mapper/veracrypt1 of=/case/DigiForensics-plain.dd \
     hash=sha256 hashlog=/case/DigiForensics-plain.hashlog
# 与 veracrypt -m 挂载（不解密到临时文件）结果做 SHA-256 对比
```

两条路都做一遍并比对哈希，是为了确认挂载点读出的是完整明文，而不是经过 FUSE 缓存的片段。这个确认只花一次 160 GB 的读取，却把"数据能取出来"从推断变成了可复现的事实。

顺带说明为什么不做关机：关机前还有一个动作同样有时效性——`x-systemd.automount` 的配置意味着这个卷可能是开机自动解锁的，重启后会自己挂回来。所以现场处置单上写的是"不重启、不关机、不重新挂载"，三条都要写，因为任何一条被误执行都会关闭这个窗口。

**结论**

能证明：①该加密分区在扣押时处于已解锁、已挂载状态，客户数据库可在无需口令的情况下直接提取；②`fstab` 中存在明文口令 `CustomerData2024`，其位置已记录；③卷头所在 512 字节区域完整可读、已固定偏移与 SHA-256，且**用已取得的口令成功解开卷头**，回读出 Magic `VERA`、Header Version `0x0005`、扇区大小 512、Flags bit0=1（系统加密）。

**③这一条的措辞值得注意**：它写的是「**用口令解开后回读**」，不是「搜到 Magic」。顺序反了，结论就建立在一个不存在的判据上。

**不能证明**：不能证明该卷的解锁时刻、也不证明解锁者身份——挂载态只说明"在某个时刻被解锁过"，具体何时、由谁，需要结合 `wtmp`/`last`、认证日志等独立来源。

挂载态的时间边界也能给出下限：`wtmp` 里最后一次登录是 6 月 2 日 09:14，而卷处于已挂载状态，所以解锁发生在 09:14 之后到扣押时刻之间。这个区间比"某个时刻"有用得多，但它仍然是一个区间——VeraCrypt 本身不在任何日志里记录解锁时间。

明文口令出现在 `fstab` 里，本身不构成对任何人的指控。

**误判对照**

最像的误判是"系统在线就关机，避免数据被远程清除"。

判据要落在这类取证对象的易失性上：VeraCrypt 的会话密钥只存在于内存，磁盘上永远只有密文。 关机的那一刻，挂载态、已解密的应用数据、以及 `fstab` 之外的运行上下文全部消失，而破解卷需要的算力是以月计的。

也就是说，关机把一个"今天就能取到全部明文"的现场，换成了一个"可能要算很久"的局面。

三条判据，按能否被事后核实排序：

①**卷头区域完整可读，且已用口令验证过它能解开**。未口令时能确认的是「512 字节区域无物理损坏」；口令解开后才确认「结构字段可解析、参数未被单独改写」。这两个判据强度不同，报告里要分开写。关机并不会让卷变得不可解，只是把"不用解"变成"要解"。

②**内存里存在已解密的业务数据副本**。`veracrypt` 进程打开的 `/data/customer.db` 会被数据库引擎读进页缓存，这些明文页在内存镜像里是可提取的，磁盘上则永远只有密文。关机是单向门——过了就没有了。

③`x-systemd.automount` 会自动重挂。这一点让"关机保安全"更站不住：重启后卷会被自动解锁回挂载态，攻击者如果还有远程访问能力，窗口会重新打开。关机既丢失了取证窗口，又没有关掉风险。

第③条是本案现场处置单上最重要的一行。它的含义是"关机并不能阻止数据被访问"——这与取证教科书里"运行系统先断网"的做法并不矛盾，但理由完全不同：断网是为了防远程操作，**关机对已挂载的自动加密卷既不防远程也不保数据**。

正确判据是对加密卷取证，运行状态本身就是取证窗口，其价值高于一枚待爆破的口令。

按错误判据走的代价：委托方拿到的将是一块挂载即需口令的加密盘，而**已经解密的那部分数据永远找不回来了**——比如运行中的数据库进程里驻留的敏感数据副本、已挂载目录下的解包临时文件，这些都不在磁盘的密文里。

本案的损失是可计量的：内存镜像里恢复了 1.2 GB 客户数据库的缓存页，其中 340 MB 涉及已删除的客户记录。若先关机，这 340 MB 不在磁盘任何位置，包括未分配空间——因为它只存在于内存，而未分配空间里的残留是更早时刻的写入，不包含尚未刷盘的数据。

<a id="section-33"></a>

### 5.2 `fstab` 里为什么会出现明文口令

**场景**

同一案件中，委托方追问：运维为什么把口令明文写在 `fstab` 里，这是不是安全事件。

这条路径值得单列，因为这是一个**在取证中常见、但性质需要谨慎界定**的问题——它既可能指向安全配置缺陷，也可能指向正常的运维习惯。

**处置过程**

1. 先把事实记录完整，包括它出现的机制：

```bash
grep -n 'veracrypt' /etc/fstab
# 3:/dev/sdb1 /data veracrypt defaults,x-systemd.automount,password=CustomerData2024 0 0

mount | grep sdb1
# /dev/sdb1 on /data type fuse.veracrypt (rw,relatime,user_allow_other)
```

2. 观察同一文件中是否还有其他条目采用同样写法——**单条不能说明习惯，成组才说明**。

```bash
grep -c 'password=' /etc/fstab        # 本案：2 条，均为 veracrypt 类型
```

3. 界定它在本次委托中的地位：这属于**配置层面的观察**，不是加密破解成果。

4. 反向检查一次：这条明文口令在别处是否也出现过。若在 `fstab`、`bash_history`、systemd unit 文件、备份归档里反复出现，它的"泄露面"就要分开评估：

```bash
grep -rn 'CustomerData2024' /case/DigiForensics/etc /case/DigiForensics/root 2>/dev/null
# /etc/fstab:3: ... password=CustomerData2024
# /root/.bash_history:118: veracrypt -m /dev/sdb1 --password=CustomerData2024
# /etc/systemd/system/data.mount:6: Options=password=CustomerData2024
```

三处命中意味着它不是孤立疏忽，而是运维把它当作"机器上人人可读的配置项"。这个形态的定性是"缺乏口令保护意识"，比"某次手误"要重，但仍然与技术入侵无关——两者在报告里必须分开。

5. 交付时的措辞上做一个动作：把它归入观察项，并注明它对本次委托问题的影响范围。

```text
观察项 O-2（配置层面，非本案核心问题）：
  /etc/fstab、/root/.bash_history、/etc/systemd/system/data.mount
  三处均含明文口令，行号已记录。
  复现：挂载时无需交互输入。
  与本案核心问题（数据外传路径）无直接关联。
  未评估：该口令是否在其他系统/归档中被复用。
```

**结论**

能证明：该服务器的 `/etc/fstab` 中有 2 个 `veracrypt` 类型条目均以 `password=` 参数携带明文口令，其中 `sdb1` 对应本次检材。这是一项可复现的配置事实，已记录行号与偏移。

扩展发现：同一口令还出现在 `bash_history` 与 systemd unit 文件中，合计 3 处。

**不能证明**：不能据此认定运维人员存在主观过错，也不能认定这是被植入的后门——`password=` 是 `veracrypt`/`cryptsetup` 的标准配置参数，写它是一种常见的（但不推荐的）自动化挂载做法。

未覆盖范围：未检索未分配空间与卷影副本中的同一字符串，因此"3 处"是活动文件系统内的计数，不是全盘唯一出现次数；未核对该口令是否在其他机器上复用，这一项超出本次委托范围。

**误判对照**

最像的误判是把"明文口令写在配置文件里"直接写成"运维存在严重安全意识问题"。

判据要落在 `veracrypt` 的挂载机制上：`/etc/fstab` 的第五字段用于向挂载程序传递选项，`password=` 是 VeraCrypt 官方支持的参数之一。写它的人通常是为了让 `x-systemd.automount` 在开机时无需人工输入即可解锁——这属于便利性取舍，不是攻击特征。

判据还应包含一个反向检查：**该写法在本卷中有几条**。单条可能是个别疏忽，成组才说明是既定做法。

三条判据：

①**参数是不是官方的**。`password=` 出现在 `fstab` 的挂载选项字段里，而 `veracrypt` 的 man page 明确支持该参数。攻击者植入后门时通常不会选一个官方已支持、行为可预期、且能被 `mount | grep` 直接看出来的写法——那种写法留不下痕迹，因为痕迹就是它的功能。

②**同一文件里有几条**。`grep -c 'password='` 得 2，两条都是 `veracrypt` 类型。成组出现说明是既定的运维做法，而不是某一行的临时决定。

③**口令在别处是否也出现**。本案在 `bash_history` 与 systemd unit 里各找到一处，三处同值。若三处都同值且写法规范，形态是"这台机器的口令本来就当作非秘密处理"；若只有 `fstab` 一处，反而值得追问为什么写在这里不写别处。

第③条把结论的落点从"某一行的疏忽"改成了"一整套运维习惯"，定性更准，措辞也更难被反驳——因为它描述的是一个可验证的模式，而不是对某人动机的推测。

正确判据是把它记为配置观察，与本案的核心问题（数据是否可取、如何被外传）分开陈述。

按错误判据走的代价：委托方据此对运维人员追责，而实际上这与数据外传事件可能毫无关联；更实际的问题是取证报告一旦掺入未经论证的责任判断，整份报告的证据部分也会被连带质疑。

这类"顺手追加的责任判断"最常见的来源是把观察项的措辞写得太肯定。"运维配置不当导致口令泄露"读起来像一个原因，而实际上它只是把一次泄露的可能性提高了，本案并没有证据显示口令正是通过这三处泄露的。改成"该口令在本机三处配置文件中以明文存在，扩大了凭据暴露面"之后，事实一个不少，责任归属却被留在了证据能支撑的范围内。

### 5.3 反例：把「卷头可解析、没找到弱口令」写成「数小时内可破解」

**场景**

另一案件中，分析员成功定位了卷头、抽出了 Salt、跑通了 hashcat 的完整流程。跑完自带的弱口令字典后没有命中，他在报告里写下「该卷未使用高强度配置，攻击者可用 GPU 在数小时内破解」。委托方据此下调了安全等级评估。

这条列为反例，是因为 「没找到弱口令」与「弱口令不存在」是两件事，而可破解性取决于后者。

**处置过程**

先把「能从卷头读出什么、不能读出什么」摆在前面：

```text
无需口令就能读到的（卷头里唯一的明文字段）：
  Salt: 64 字节（卷头偏移 0，已抽取，作为 hashcat 输入）
  其余 448 字节全为密文，读不出任何结构字段

必须口令解开才能读到的：
  Magic: VERA，Header Version: 0x0005，Sector Size: 512
  加密算法、KDF

根本不在盘上的：
  PIM —— 见 2.3

能实测的：
  hashcat 速率（SHA-512 模式）：约 5,700 H/s（单张 L40S）
```

**注意这三条的层次不同**：第一条是「读到明文」，第二条是「解不开就读不到」，第三条是「压根不存在」。初稿把第一条和第二条混在一起写成「从卷头明文区读出 Magic 和版本号」，于是 hashcat 那一行看起来像是在一个参数已知的卷上跑的——**而实际上你连该用哪个 `-m` 号都不知道**。

然后算总代价。关键在于把它写成乘法：

```text
总代价 = 单候选 PBKDF2 计算量 × 候选口令数
  单候选的计算量由 KDF、PIM、算法层数共同决定 —— 而 PIM 未知
  候选数才是本案唯一能收敛的量

候选空间来源（按本案真实存在的材料）：
  自带弱口令字典        8,000 条   已跑完，未命中
  机器/账户名            3 条
  域名 + 年份            6 条       （CustomerData2023/2024/2025…）
  键盘走位模式          数千条
  密码管理器导出         未知       （本次未取得，可能存在）
```

按 5,700 H/s 估算，跑完 8,000 条候选约需 1.4 秒。**这个数字本身就是结论的一部分**：字典跑完了，用了几秒钟，委托方却把这 1.4 秒读成了「数小时」。

1. 正确的判断顺序是**先确定候选空间，再谈代价**：

```bash
# 候选来源要逐条列出并给出条数，而不是笼统写"弱口令"
wc -l wordlist.txt          # 8000
# 然后向委托方索取其余来源，而不是自己假设存在
```

2. 若确实发现弱口令特征（如 `CustomerData2024` 这类可预测模式），才据此给出可破解性评估。

3. 反过来做一个上限估算，避免"不可破"也是无根据的结论。假设攻击者掌握目标机器的物理访问权、知道卷是系统加密、且该机器曾被入侵过，那么可用的候选空间会显著大于"随机口令"这个前提：

```text
若口令是 6 位纯数字（约 19.9 位熵，约 10^6 组合）
  → 按 5,700 H/s 计，约 3 分钟，确实是"数小时"量级以内

若口令是 12 位随机（大小写+数字+符号，约 95 位熵）
  → 候选空间 10^95 量级，远超任何可枚举范围
```

这一步是必要的，因为"没跑出弱口令所以易破"和"跑不出所以不可破"犯的是同一个错——把一次观测当成了结论。本案的正确表述是"在已测试的 8,014 条候选内未命中；候选空间未穷尽，可破解性为待定项"。

**结论**

阴性发现：在已测试的候选范围内未命中口令。**未覆盖范围**是尚未取得的候选来源——密码管理器导出、员工口令习惯、其他设备上的同源凭据都未纳入。因此可破解性属于**未知项**而非已知项。若委托方另有材料提供候选，该结论可相应调整。

反向的阴性同样成立：本案也未得出"该卷不可破解"。按实测速率与 6 位纯数字的口令空间估算，总代价在分钟量级——**候选空间缩小到几千条时，这个卷确实会很快被打开**。可破解性是待定项，两个方向的定性和"字典跑完未命中"这句话都不矛盾。

**误判对照**

最像的误判是把「跑完字典没命中」直接翻译成「弱口令不存在」。

三条判据：

①**候选空间有没有下界**。本案的机器名、账户名、域名与年份组合本身就构成上千条可枚举候选。弱口令的现实来源是上下文预测，而上下文是可以被取证材料直接提供的——把它算进总代价之后，"字典没命中"这件事的分量就小了很多。

②**实测速率与候选数的量级关系**。8,000 条候选在 5,700 H/s 下只需约 1.4 秒。这个数字比任何迭代公式都更能说明问题：测试覆盖面太小的时候，"没跑出"这个结果的信息量极低。而 6 位纯数字（约 10^6 组合）对应的分钟量级，说明同一个卷在另一套候选下会很快被打开。

③**有没有实际的候选材料**。委托方在别处提供的密码管理器导出、上次事故的记录、员工的口令习惯问卷——任何一条都能把"待定"变成具体数字。本案在这条路径上什么材料都没有，于是唯一诚实的表述就是"待定"。

第③条是实务上最有用的一条。前两条都还在算术层面，第③条直接指向下一步动作：**要评估可破解性，先去要候选，而不是先读卷头**。很多"不可破/易破"的争论之所以发生，是因为双方在谈参数，而能改变结论的材料还没人去要。

真正的成本来自**候选口令空间的大小**。正确判据是**先确定口令空间再算总代价**，而在口令未知时，唯一诚实的结论是"可破解性待定"。

按错误判据走的代价：委托方据"数小时可破"下调了事件等级、调整了处置优先级，而实际攻击者的破解成本可能高出几个数量级——**这会让一个高风险事件被降级处理**，方向完全相反。

本案初稿后来按同样理由撤回了另一处表述。委托方在初稿里读到"该卷按固定迭代参数创建，未启用自定义 PIM"，随后据此询问"那是否可以认为用户自行降低了安全标准"。这个问题的答案不在卷头里，而在"VeraCrypt 允许调整这个参数，允许意味着有人会调，但调整这个动作本身没有记录任何痕迹"——**参数值能证明状态，不能证明意图**。

### 5.4 判据对撞：委托方说"参数很高不可行"，但候选表只有 4 条

**场景**

一块 VeraCrypt 系统加密卷。委托方自己的安全团队在初稿里写道："该卷采用 1.12 之后的参数体系且设置了较高的 PIM，口令恢复的代价极高，建议放弃此路线。"分析员没有直接接受，也没有反驳参数本身的取值，而是重新做了一轮可破解性评估。

**这个场景值得单独看**，因为它和 5.3 是同一枚硬币的两面：5.3 是"没跑出弱口令就说易破"，这一案是"参数很高就说不可行"。两边都把一个无法观测的量当成了结论。

**处置过程**

先固定卷头区域的证据，并明确它能证明什么、不能证明什么：

```bash
# 系统加密卷的主卷头在加密区起始。区域位置可由分区表与卷偏移推算
dd if=/case/DigiForensics.dd bs=512 skip=$((1048576/512)) count=1 | xxd | head -8
# 输出为 64 字节高熵盐值 + 448 字节高熵密文
# ★ 读不出 VERA —— 它在密文里。读出的"全是随机"正是卷头完好的表现

# 记录这 512 字节的哈希，后续每次操作后复核
dd if=/case/DigiForensics.dd bs=512 skip=$((1048576/512)) count=1 \
  | sha256sum | tee /case/header.region.sha256
```

这一步能证明的是「区域完整可读」，不能证明「结构字段正确」。 后者需要口令解开后才能回读。把这两件事混成一句「卷头结构完整可解析」是本类分析最常见的措辞失误。

然后要处理一个绕不过去的事实：这个卷的 PIM 读不出来。

```text
委托方的说法：PIM 很高，单候选代价极高 → 不可行

实际情况：
  PIM 不写在盘上任何位置（见 2.3）
  → 你既无法验证它"很高"，也无法验证它"不高"
  → 基于 PIM 的可行性判断，没有证据基础
```

这不是一个可以靠猜绕过去的问题。真正能回答"值不值得投入"的是另一组量：

```text
判据 A（委托方的参数推断）  → PIM 未知 → 无从判断 → "不可行"缺依据
判据 B（实测速率 + 候选数） → 5,700 H/s × N 条候选
```

委托方从密码管理器导出中提供了 4 条候选口令。代入判据 B：

```text
4 条候选 × 5,700 H/s  →  不到 1 毫秒的验证量
实际耗时：包含卷头解析与挂载，全程数分钟
```

委托方漏掉的是乘数之外的那一项——**总代价是"每个候选的代价 × 候选个数"**，而候选个数在这里是已知的、很小的。无论单候选代价是 50 万次迭代还是 9.8 亿次迭代，它都只乘在 4 上，而不是乘在一个无界的口令空间上。

在本案的分析机上对 4 个候选逐个验证，第一个即命中，卷挂载成功，内层是标准 ext4。这同时反向验证了卷头解析无误——若算法、KDF 或 CRC 有误，挂载会直接失败而不是报"口令错"。

**结论**

能证明：`DigiForensics.dd` 中的加密卷已解密并挂载，内层为 ext4 文件系统。本卷的可破解性由候选口令空间大小决定（本案为 4），与参数取值无关。

不能证明：不能据此推出该卷普遍易破。结论严格限定在这 4 条候选上；若候选来源换成另一个密码库或改为未知口令空间，成本评估需重做。另外，**本案始终没有确定这个卷用的 PIM 是多少**——报告里也不该出现这个数字。

**误判对照**

最像的误判是把「参数很高」单独当成"不可行"的判据。

判据要落在**总代价的构成**上：破解成本 = 单候选 PBKDF2 代价 × 候选数量。只报前一个量、隐含后一个量是无穷大，等于把一个关于"每个候选"的数字当成关于"这个卷"的结论。而本案里情况更极端一些——**PIM 连读都读不到**，所以连"前一个量"都只是个猜测。判别动作很直接：先问委托方能提供的候选来自哪里、有多少条，数量一确定，这条参数判据的权重就变了。

第二种误判是反向的：看到有候选表就写"该卷易破"。判据要落在**候选来源与完备性**上。4 条候选来自一份具体的密码管理器导出，这是一个**已知且有限**的口令空间，与"口令未知时暴力穷举"是两件事。

第三种是本案特有的：**把"参数很高"写进报告，当成一个已确认的事实**。它不是事实——它来自委托方安全团队的推测，而推测的依据（卷头里的某个字段）并不存在。报告里写一个无法被复核的数值，比不写更糟。

按错误判据走的代价是双向的。往高走，会把一个 4 条候选就能打开的卷标注为"攻击不可行"，真正该走的路线（向委托方索取密码管理器导出）因此没人走，本案的口令和数据都取不回来。往低走，则会把高强度卷写进建议"放弃"，而委托方手里很可能就有候选材料。

### 5.5 阴性结果：三个候选口令全部失败，但挂载残留给出了可用线索

**场景**

一台 Windows 工作站的镜像。委托方提供 3 个候选口令，全部失败。常规流程到这一步就该写"口令未知，无法解密"。

但此前对这台机器做过一次取证箱镜像，采集时卷是**挂载状态**。

**处置过程**

口令失败不是终点，失败次数与错误形态本身携带信息：

```bash
# 3.2 的挂载命令逐个试，三次返回同一个错误
veracrypt -t /case/DigiForensics.dd --password=候选1 --non-interactive
# Incorrect password or not a VeraCrypt volume
# 候选2、候选3 同样输出
```

**先看清这条错误信息说了什么**：`Incorrect password or **not a VeraCrypt volume**` —— 工具自己就承认它区分不了这两种情况。**三个候选给出同一条消息，等于什么都没排除。** 这是 VeraCrypt 取证里最需要克制的地方：不要因为「三把都失败、错误一致」就下「卷头是好的、只差口令」的结论。

那能排除什么？只有一件事——**这三次里至少有一次是纯口令问题**。因为如果格式就不对，三次也都会返回同样的话，那么「口令错误」这个解释和「不是 VeraCrypt 卷」这个解释**完全等价**。

```bash
# 换个方向确认容器身份：找同机同版本安装与使用痕迹
regipy-dump /case/SYSTEM.hive | grep -i veracrypt    # 先确认这台机器上装没装过 VeraCrypt
# 在 Program Files、日志、注册表卸载项里找安装记录
```

这一步的价值在于它能独立回答「这台机器上到底有没有 VeraCrypt」——而这正是那条模糊错误信息无法回答的问题。回答了「有安装记录」，才轮到「口令还差一步」这个结论。

再转向挂载残留——这是挂载态真正的价值所在：

```bash
# 1) Temp 目录里同版本安装包的 0 字节残留 + 目录 mtime
ls -la /case/DigiForensics/Users/*/AppData/Local/Temp/
# mtime: 2024-06-02 14:07:31，含 DigiForensics-setup-veracrypt-1.26.7.exe（0 字节）

# 2) 命令历史：挂载命令的完整参数
grep -rn 'veracrypt' /case/DigiForensics/Users/*/AppData/Roaming/Microsoft/Windows/PowerShell/PSReadLine/ConsoleHost_history.txt

# 3) 注册表里的 VeraCrypt 挂载历史
regipy-dump /case/DigiForensics/Windows/System32/config/SYSTEM.hive \
  -p 'ControlSet001\Services' | grep -i veracrypt
```

第 2 项是关键：历史命令显示该卷是用**密钥文件 + 口令**双因素挂载的，`--keyfiles` 指向 `D:\DigiForensics\keys\id_rsa.key`。这直接解释了三次全败的原因——**只试了口令这一半**，而密钥文件那一半在挂载残留里是明文可读的。

**结论**

阴性发现：3 个候选口令全部失败，`DigiForensics.dd` 中的卷未能解密；未能就"卷内内容是什么"给出任何判断。

阳性发现：挂载残留证明该卷曾于 2024-06-02 14:07 前后在本机成功挂载，方式为口令 + 密钥文件。失败原因定位为"验证材料不完整"，不是"凭据错误"。

未覆盖范围是密钥文件本身——它位于 `D:\` 分区，该分区不在本案镜像内，因此当前仍无法解密。

**误判对照**

最像的误判是"3 个口令失败 = 口令不可恢复 = 该卷不可分析"。

判据要落在**验证材料的构成**上：挂载命令里的 `--keyfiles` 说明验证凭据本就不止口令一项，而三份命令历史都显示参数里有它。用单一因子穷举去否定"可恢复性"，等于把方法失败写成了结论——这两件事在报告里的分量完全不同。

第二种误判是直接拿历史里的 `--password=` 字面值去试。那后面往往什么都没有——正因为口令当时是交互输入的，值不落在命令行上。只照抄命令行里能看到的东西，等于抄了个空。

按错误判据走的代价是产出一份"该卷不可恢复、无法响应委托方问题"的结论。此时真正的缺口只是一份还没取到的密钥文件，一件补充调证就能解决的事，却被写成了一条死路；委托方很可能据此中止调查，而卷内数据始终未被提取。

## 六、扩展阅读方向

下面四组方向按"你在 VeraCrypt 这条路上会遇到什么"组织。


**第一组：同层深入——三种卷加密的横向对比**

三篇连起来才是加密取证的全谱系。**选错路径会浪费大量成本**——尤其在卷头形态上，三者几乎没有共同点。
- [BitLocker 全卷加密取证](crypto-volume-bitlocker.md) —— **最根本的差异是"存在恢复通道"**。BitLocker 的安全目标是"仅授权方可以恢复"，恢复密码明文留存、启动密钥是明文 `.cer` 文件，取证方向是"全盘搜索关键字"。**把本篇的"找口令"思路套过去会全盘落空**，因为那条路根本不存在。两篇对照着看，才能判断拿到一个盘应该先搜什么。
- [EFS 文件系统加密取证](crypto-volume-efs.md) —— 第三个方向：**文件级、私钥驱动**。EFS 的私钥往往就在用户 profile 里，找到了就直接能解。**一台 Windows 盘上三者可能同时存在**（卷加密 + EFS 文件 + VeraCrypt 容器），判形态这一步不能省。
- [文件系统取证总览](../../filesystem/filesystem-ntfs/filesystem-ntfs-filesystem-forensics-overview.md) —— **挂载成功之后的第一件事是判卷内文件系统**。VeraCrypt 容器内是标准格式，但标准不等于常见——容器里装 ext4 是完全正常的。这一篇给的是判别方法。

**第二组：相邻议题——口令从哪来、明文在哪**

本篇的三条现实路径（找口令、找明文副本、找实现残留）在库里有对应的深挖文章。

- [Shell 痕迹与命令历史](../../computer/computer-shell/computer-shell-shell.md) —— **成本最低的一条**。`veracrypt -p "口令" -t /dev/sdb1 /mnt/encrypted` 这种命令行在历史文件里是明文，而创建和使用加密容器的操作通常经过命令行。同一篇还覆盖了终端 scrollback、脚本文件、`sudo` 日志这些旁证。
- [浏览器密码库与 Token 解密](../crypto-app/crypto-app-browser-passwords-and-tokens.md) —— 用户在网页上保存过这个口令的情况极常见，而浏览器里的凭据往往是明文或可用常规路径解出。这是"找口令"里最省事的一条，也是本篇步骤 3.3 明确列出的第一项。
- [Linux 与 Android 内存取证](../../memory/memory-artifact/memory-artifact-linux-android.md) 的对位内容在内存板块：若检材里有内存镜像，挂载时解出的主密钥可能仍在内核页或进程内存中，`/proc/kcore` 与 `LiME` / `AVML` 的取舍在那篇。方法论见[内存取证总览](../../memory/memory-acquire/memory-acquire-memory-forensics-overview.md)。
- [页交换与虚拟内存制品](../../server/server-docker/server-docker-docker-volumes-and-bind-mounts.md) 这类文章不适用，但挂载残留的判断逻辑和容器 Volume 的残留分析是同一个思路：宿主侧状态 + 内部明文两边对照。

**第三组：工具与规范——不可逆操作与平台能力**

- [只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md) —— **本篇第四章 4.2 组的核心依据**。挂载加密容器会写入文件系统元数据、可能触发写操作、可能让卷头被改写。`-m ro` 不是可选项。
- [虚拟机仿真](../../imaging/imaging-mount-simulate/imaging-mount-simulate-virtual-machine-emulation.md) —— 另一种思路：与其在宿主机上挂载，不如把容器挂进一台隔离的仿真环境。那样即使工具写坏了盘，损坏的也是仿真环境。Windows Server 侧的仿真需求见[Windows Server 环境仿真](../../imaging/imaging-mount-simulate/imaging-mount-simulate-windows-server.md)。
- [证据格式与转换](../../imaging/imaging-acquire/imaging-acquire-evidence-image-formats.md) —— 从 E01 切出容器文件、LibFUSE 依赖、口令经 `--stdin` 传入而不进 shell 历史，这些都在采集与预处理环节定。
- [合规授权与法律边界](../../fundamentals/fundamentals-practice/fundamentals-practice-legal-authorization-and-boundaries.md) —— 挂载、解密、还原数据都改变工作副本状态。哪些操作可逆、记录写在动作前还是动作后，这套判据在这里适用。

**第四组：判据与反例——"不可恢复"这句话怎么写**

- [通用密码恢复](../crypto-app/crypto-app-passware-and-password-recovery.md) —— 弱口令场景下的离线验证方法论与算力估算。本篇的 PIM 读不出来（见 2.3），所以「投入多少」只能由候选数决定，答案在那篇的优先级表里：明文残留 → 同机复用 → 上下文候选 → 掩码 → 暴力。**跳过前四项直接跑 GPU，是本领域比较典型的浪费。**
- [反取证手法与时间戳篡改检测](../../fundamentals/fundamentals-concepts/fundamentals-concepts-anti-forensics-and-timestamp-tampering.md) —— "**卷头里找不到口令**"这件事本身，可能是对方做过手脚。卷头的主副本与备份副本各有一份、**可被原地修改**（改算法、改 KDF、改主密钥槽都会让容器打不开），**判据可信性需要独立检验**。读它是为了知道自己的前提有多脆弱。
- [取证流程与原则](../../fundamentals/fundamentals-process/fundamentals-process-five-stage-forensics-process.md) —— "本阶段未找到口令"是一个关于案件可行性的结论，需要以有范围、有前提、可复现的形式写出。**"数据已永久丢失"是一个不同性质的断言**，本篇第四章 4.1 组专门处理了这条界线。

**说明**：VeraCrypt 的卷头不给你任何能用来做决策的明文信息。

这不是缺陷，是格式设计的目标。所以本篇的方法论只有一条：**不要在读卷头上花时间，去做那些成本低得多的动作。**

**搜一下、算一下、评估一下投入产出**——这三件事在 VeraCrypt 上都无从下手。真正能做的是搜 shell 历史、找挂载残留、确认系统是否在线。剩下的都是执行细节。

## 七、命令速查

```bash
# 识别：★ 卷头没有明文签名，只能筛候选 ★
# 文件容器卷头在文件偏移 0：前 64 字节盐值是明文，之后 448 字节是密文
dd if=DigiForensics.vc bs=512 count=1 of=veracrypt.hash
dd if=DigiForensics.vc bs=512 count=1 | xxd | head -4
# ★ 读不到 VERA —— 它在密文区。任何字面量搜索（VERA / VERACRYPT / TRUECRYPT）都返回空

# 候选筛选：大小是 512 整数倍 + 熵值逼近 8.0 + 不匹配任何文件系统
stat -c '%s' /mnt/image/suspect.bin | awk '{print $1%512}'    # 期望 0
python3 -c "
import math,collections
d=open('/mnt/image/suspect.bin','rb').read(1<<20); n=len(d)
c=collections.Counter(d); print(-sum((v/n)*math.log2(v/n) for v in c.values()))"

veracrypt -t --list                        # 列出已挂载卷
veracrypt -t --non-interactive /mnt/image/suspect.bin </dev/null   # 空口令探测

# 挂载（取证标准：只读）
veracrypt -t -m ro /dev/sdb1 /mnt/target              # 交互输入口令
printf '%s\
' "$PW" | veracrypt -t --non-interactive --stdin -m ro /dev/sdb1 /mnt/target

# 检查挂载残留
grep -iE "veracrypt|crypt" /mnt/image/etc/fstab
grep -rl "veracrypt" /mnt/image/etc/systemd/system/
grep -iE "veracrypt" /mnt/image/home/*/.bash_history

# 搜索口令残留
strings -n 8 DigiForensics.dd | grep -iE "密码|password|veracrypt"

# 内存镜像采集（现场未关机时优先）
sudo insmod ./lime.ko "path=/mnt/evidence/mem.lime format=lime"
sudo avml --output /mnt/evidence/DigiForensics-mem.raw
```
