# 证据保管链与委托证明

<a id="section-1"></a>

## 一、概述

`sha256sum` 能证明"这串字节从 3 月 15 日到现在没变过"。它证明不了另一件事：这串字节是从哪个设备上、什么时间、由谁、以什么授权取下来的。

技术上这两件事毫无关系，法庭上却必须一起成立。对方律师只需要问一句："这份镜像在 3 月 5 日到 3 月 18 日之间在谁手上。"答不上来，前面所有哈希、所有解析、所有结论都可能被打回重来。

第五章的 13 天保管空档用于说明这一问题。交接表、签字、封条与录像记录资料的来源和流转；文件内容及哈希校验不能替代这些过程记录。

保管链不属于流程中的某一环，它横跨全程。从受理检材的第一分钟开始记录，到意见书盖章结束才闭合。对应关系说白了就是：受理对应采集环节的收尾，每次分析前后对应分析环节，出具文书对应报告环节。4.1 那条讲得更直白——受理时不计算源哈希，缺陷从此处开始就无法补救。后面的每一环都在错误的基础上叠加，越往后越说不清。

上游有三件事决定台账长什么样。[取证流程与原则](../fundamentals-process/fundamentals-process-five-stage-forensics-process.md) 决定你有多少个节点要记录；[哈希与完整性校验](../fundamentals-concepts/fundamentals-concepts-hashes-and-integrity-verification.md) 提供链上那个"技术兜底"性质的锚点；

[合规授权与法律边界](../fundamentals-practice/fundamentals-practice-legal-authorization-and-boundaries.md) 决定你有没有资格记录。没有授权，台账记得再规范也不解决问题。

下游有两件事。[证据文件格式](fundamentals-chain-dd-e01-aff4-evidence-formats.md)决定受理时拿到的是 `DigiForensics.dd` 还是 `DigiForensics.E01`，这两种情况下"受理哈希"算在哪个对象上完全不同；[取证概念与分类](../fundamentals-concepts/fundamentals-concepts-digital-forensics-concepts.md)给出文书类型与证据类别的对应关系。

落到纸面上，要处理的物件有确定的格式。保管链台账以证据编号为行，字段固定为时间（精确到分）、移交方、接收方、用途、哈希值、签名，只写日期不写时间是无效记录。

委托书 / 授权书由委托人签署，内容是委托事项、检材清单、权限范围、期限，它不是"授权使用"的凭据，两者法律定位不同（陷阱 2）。鉴定意见书 / 检验报告由鉴定人签署，核心是"这些数据说明什么"，必须写明局限性。

受理记录由检验方签署，固定的是"我收到了什么、状态如何"：检材状态、封条编号、哈希值、异常情况。封条与封装袋跨缝粘贴，横跨袋口与袋体，二次封装时原封条不得丢弃，它是过程证据。

`H_recv.sha256` 与 `hash_chain.log` 是受理哈希与分析前后哈希的追加日志，案例里让那 13 天空档变得可辩护的就是这个文件。`udevadm info --query=property` 的输出是受理时抓的设备型号与序列号，用于把台账里的"某某牌移动硬盘"落到唯一一台具体设备。

这些物件能回答的问题相当具体。一份保管链记录在质证中能不能站住，看的是要素是否齐全、链条是否闭合；三类文书该由谁签；发现封条破损时第一步该做什么；记录有瑕疵的情况下还能靠什么补救。

数据本身有没有被改过是哈希的活，保管链只负责保证那个哈希被记下来了；技术分析怎么做，保管链对镜像里有什么内容毫不关心；取证的合法性边界——授权要件缺失、非法获取的排除规则——属于[合规授权与法律边界](../fundamentals-practice/fundamentals-practice-legal-authorization-and-boundaries.md)；鉴定意见书的正式格式各机构、各地区不同，保管链只讲结构要素，格式规定要查本机构的规范文本。

上手之前需要先理解三件事：哈希能证明什么（见[哈希与完整性校验](../fundamentals-concepts/fundamentals-concepts-hashes-and-integrity-verification.md)）、取证流程有哪几个阶段（见[取证流程与原则](../fundamentals-process/fundamentals-process-five-stage-forensics-process.md)）、以及只读接入为什么是纪律（见[只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md)）。

本章依赖的实践经验：接过真实检材、亲手做过哈希校验。4.4 节讲的都是实操中才会遇到的情形。

## 二、核心原理

<a id="section-3"></a>

### 2.1 保管链的定义与四要素

**保管链（Chain of Custody）**是指证据自固定之日至呈堂之止，为防止调换、遗失、毁损而采取的保管措施与记录。

| 要素 | 记录内容 | 常见缺失 |
|---|---|---|
| **谁（Who）** | 交接双方姓名、单位、职务、签名 | 只写单位不写个人 |
| **何时（When）** | 交接的准确日期与时间 | 只写日期不写时间 |
| **何地（Where）** | 交接地点 | 完全不记录 |
| **做什么（What）** | 本次操作性质（封存/移交/检验/归还） | 笼统写"移交" |

> **核心要求**：保管链必须**闭合且连续**。任何一段无人负责的空白期，都是对方质疑"此期间数据可能被修改"的入口。

<a id="section-4"></a>

### 2.2 电子证据保管链的三个特殊点

| 特殊点 | 传统物证 | 电子证据 |
|---|---|---|
| **易被复制** | 物理上唯一 | 可无限复制，需说明副本关系 |
| **易被访问** | 拿走了就没了 | 封存的硬盘仍可被通电访问 |
| **可被验证** | 靠封条 | 靠**哈希**，可数学证明未变 |

正因如此，电子证据的保管链文档中必须包含哈希值，而且要与委托方、送检方、检验方各自掌握的记录对得上。

这就是"三段哈希"：

```text
送检方（扣押时计算）  H_send
                        ↓
检验方（受理时计算）  H_recv     ← H_send == H_recv 是受理的前提
                        ↓
检验方（检验后计算）  H_after   ← H_recv == H_after 是分析未改动的证明
```

<a id="section-5"></a>

### 2.3 三类文书的关系

初学者常把委托书、鉴定意见书、检验报告混为一谈。三者的法律定位完全不同：

| 文书 | 签署人 | 解决的问题 | 关键要素 |
|---|---|---|---|
| **委托书/授权书** | 委托人（通常是委托方或办案单位） | "我请你做什么" | 委托事项、检材清单、权限范围、期限 |
| **受理/检验记录** | 检验方 | "我收到了什么、状态如何" | 检材状态、封条编号、哈希值、异常情况 |
| **鉴定意见书** | 鉴定人 | "这些数据说明什么" | 检材、检验过程、分析意见、**局限性** |

三者的关系是：**委托书授权 → 受理记录固定 → 意见书定论**。缺任何一环，链条都不完整。

> ⚠️ **实务提醒**：文书格式的具体要求因地区、机构、业务类型而异，**以本机构规范、当地司法实践和最新法规要求为准**。下文只给结构要素，不代替正式格式规定。

<a id="section-6"></a>

### 2.4 封装与封条

| 要点 | 做法 | 理由 |
|---|---|---|
| **封装材料** | 防拆封条 + 硬质封装袋/盒 | 便于观察是否被开启 |
| **封条信息** | 案件编号、检材名称、封装人、日期、签名 | 封条即保管链的物理载体 |
| **跨缝粘贴** | 封条横跨袋口与袋体 | 任何开启都会破坏封条 |
| **二次封装** | 分析后重新封装并记录 | 原封条不得丢弃，作为过程证据 |
| **影像留存** | 封装全过程拍照 | 封条破损争议时的旁证 |

**封条破损或丢失怎么处理**：先停下来，别拆。

```text
1. 立即停止操作
2. 拍照记录破损状态
3. 通知委托方/办案人员
4. 在记录中如实写明发现时间与状态
5. 由双方共同拆封并签字确认
```

自行拆封后再"补一个记录"，质证时几乎无法自证。

<a id="section-7"></a>

### 2.5 保管链的常见断点类型

| 类型 | 表现 | 后果 |
|---|---|---|
| **时间断点** | 3 月 5 日到 3 月 18 日无记录 | 最严重——无从证明期间状态 |
| **主体断点** | 移交到某部门，未写具体人 | 无法定位责任人 |
| **操作未记录** | 期间做过分析但没写 | 对方可主张数据已被污染 |
| **哈希缺失** | 受理时未算哈希 | 无法证明镜像与原始检材一致 |
| **封装未记录** | 拆封装没签字 | 争议时无法证明拆封合法 |

## 三、操作步骤

<a id="section-9"></a>

### 步骤 1：受理检材时建立基线

**这是整个保管链的起点，哈希必须在此计算**：

```bash
# 1) 记录检材标识
lsblk -o NAME,SIZE,MODEL,SERIAL,TYPE

# 2) 检查封装与封条（拍照存档）
# 3) 记录开机状态（指示灯、屏幕）

# 4) 计算并记录哈希 —— 若为已封存的镜像文件
sha256sum DigiForensics.dd | tee /case/H_recv.sha256
md5sum    DigiForensics.dd | tee -a /case/H_recv.sha256

# 5) 若为原始介质（尚未镜像），先记录设备信息，镜像后按板块 2 流程走
```

把哈希值写进受理记录，并**请委托方当场确认签字**。

<a id="section-10"></a>

### 步骤 2：建立保管链台账

```text
保管链记录（示例格式）

案件编号：2024-DG-001
检材编号：DG-001-01
检材名称：笔记本电脑（Laptop）
检材特征：型号 XXX，序列号 XXXXXXXXX，容量 512GB

序号 | 日期时间 | 交出方 | 接收方 | 地点 | 事由 | 封条号 | 签名
1    | 03-15 09:20 | 张某(委托方) | 李某(检验方) | 委托方办公室 | 送检 | A-001 | ...
2    | 03-15 14:00 | 李某 | 李某 | 检验方实验室 | 封存 | A-001 | ...
3    | 03-16 10:30 | 李某 | 王某(复核) | 检验方实验室 | 检验 | A-002 | ...
4    | 03-25 16:00 | 王某 | 张某(委托方) | 检验方实验室 | 归还 | A-003 | ...
```

> 💡 **实用建议**：台账用电子表格维护，**每次操作后立即录入**。事后补记的时间经常与实际不符，反而制造矛盾。

<a id="section-11"></a>

### 步骤 3：封装

```text
封装流程
1  核对检材与台账记录一致
2  装入封装袋，排出空气
3  封条横跨袋口，注明案件编号、检材号、封装人、日期
4  封装人签名
5  拍照（正反面、封条特写）
6  台账登记本次封装
```

<a id="section-12"></a>

### 步骤 4：每次分析前后记录哈希

```bash
# 分析前
sha256sum DigiForensics.dd >> /case/hash_chain.log
echo "分析前: $(date)" >> /case/hash_chain.log

# ... 执行分析 ...

# 分析后
sha256sum DigiForensics.dd >> /case/hash_chain.log
echo "分析后: $(date)" >> /case/hash_chain.log
```

<a id="section-13"></a>

### 步骤 5：发现封条异常时的处置

```text
发现封条破损
  ↓
立即停止一切操作，不要通电，不要拆封
  ↓
拍照：破损位置、整体状态、当前摆放位置
  ↓
通知委托方/办案人员到场
  ↓
双方共同在场拆封，各执一份记录
  ↓
在保管链台账中如实写明：
   发现时间、发现人、破损描述、处置方式、在场人员
  ↓
重新封装（新封条号），旧封条留存
```

<a id="section-14"></a>

### 步骤 6：出具文书

按第三节的三类文书分别准备。鉴定意见书的关键是**局限性章节**必须写：

```text
局限性声明（示例）
1. 本次检验仅针对检材 DG-001-01 镜像文件进行，未接触原始存储介质。
2. 检材到所时封装完好，海绵 3 月 15 日 09:20 送达。
3. 因检材为关机状态，未能提取内存中的易失数据。
4. 因 X 部件损坏，偏移 0x1A2F00000 附近约 0.5GB 数据无法读取。
5. 本意见仅基于所提取数据作出，对未提取部分不作判断。
```

## 四、常见陷阱

<a id="section-16"></a>

### 4.1 受理环节（缺陷从这里开始就无法补救）

<a id="section-17"></a>

#### 受理时不计算源哈希 ★

**现象**：设备到手直接开始采集，直到写报告时才对着采集镜像算一次 SHA-256，台账上只有镜像的哈希。

**原因**：受理哈希是**保管链的起点**。

没有它，就无法证明"采集出来的镜像忠实反映了委托方交付的那块原始介质"。中间这段时间里设备是否被替换、是否被通电、是否被改动，完全没有客观记录。

取证人员往往认为"采集时的哈希已经覆盖了"。可采集工具算的是它读到的字节流；读到的到底是不是原始介质本身，得靠受理哈希来锚定。

**影响**：**这是保管链上最大的、也最难事后补救的漏洞**。

质证时对方只需一问"你如何证明镜像对应的是我方交付的那台设备"，整条链就断了。而且它是证据性的缺陷——不是记录格式不规范，是缺少关键事实。

**核查**：**先哈希、再通电、再采集**，顺序不可颠倒。

受理时即对交付的原始介质计算哈希，并当场录像或双人在场见证。原始介质因为通电而可能被改写（SSD 的磨损均衡、写缓存、TRIM），**通电前不哈希，之后就再也拿不到原始状态了**。

```bash
# 受理环节：先算哈希（此时设备尚未通电，dd 只读不写）
sha256sum /dev/sdX | tee 受理哈希.txt
# 记录设备型号、序列号、接口、封条编号、交付人
```

<a id="section-18"></a>

#### 把委托书当作授权使用

**现象**：拿到委托书，上面写着"委托贵机构对某设备进行取证"，于是开始了解封、挂载、恢复文件。

**原因**：委托书表达的是"请你做事"，**不必然包含"你可以处置我的数据"**。

委托关系与处理权限是两个独立问题。很多委托书里根本没有写明是否允许解密数据、是否允许登录对方账号、是否允许把数据带出原环境。取证人员默认"收了委托书就等于什么都能做"。

**影响**：**可能构成违法或违约**。

擅自解密他人设备、越权访问他人账户，取证结论不但会被排除，还可能引发独立的责任后果。

**核查**：**权限范围必须在委托书中逐项写明**。至少明确四点：① 是否允许解密与挂载；② 是否允许访问云账户或第三方服务；③ 数据可否带离现场或出境；④ 哪些数据不得处理。

授权范围模糊时，先问再动手，并把沟通记录附入案卷。

<a id="section-19"></a>

### 4.2 台账记录

<a id="section-20"></a>

#### 事后补记台账

**现象**：交接时没来得及填台账，事后回忆补上，日期写了当天，但时间填的是"大概上午"。

**原因**：补记的时间与实际操作时间不符，这在质证中是明显破绽。

台账的核心价值不是"有个记录"，而是"记录的时刻是真实的"。事后补记破坏的正是这一点。填写台账时人是匆忙的，事后补记人是回忆的，两者性质完全不同。

**影响**：**整个台账的真实性被质疑**。

对方一旦指出"这张台账是补的"，前面所有真实记录的可信度都会一起下降。一处污染拖垮全表。

**核查**：**当场记录，当场签字**。台账设计成可以快速勾选的形式（预印选项 + 空格填时间），降低现场填写成本。

实在来不及的，**先记下关键要素——时间、人、动作——再补格式**，并在补记处注明"补记"及原因。

<a id="section-21"></a>

#### 只写日期不写时间

**现象**：台账上写"2026-03-15 接收"，没有具体时刻。

**原因**：跨夜或多人交接的场景下，只有日期无法确定顺序。

"15 日接收、15 日采集、15 日移交"——到底是先接收还是先采集？而保管链的核心恰恰是顺序连续性。缺少时刻，链条上就出现了无法闭合的时间模糊区。

**影响**：顺序无法证明连续，链条实质断裂。

这是形式问题，但直接决定保管链是否成立。

**核查**：**精确到分钟**，格式统一为 `YYYY-MM-DD HH:MM`。涉及多动作时统一使用 24 小时制，避免"上午/下午"造成的歧义。

<a id="section-22"></a>

#### 台账只写单位不写个人

**现象**：移交人一栏写"XX 派出所"，接收人一栏写"XX 鉴定中心"。

**原因**：保管链要求的是特定的人——谁做了这个动作。

单位不能作为行为主体，因为它无法承担"谁实施了"这一责任。"单位"是场所概念，"人"才是主体。写单位在实践中通常是因为现场没人愿意留下个人签名。

**影响**：**责任主体缺失**。

一旦出现争议，无法定位责任人，也无法传唤特定人员作证。链条的连续性依赖于"同一个人承认前后两次动作"，而不是"同一个单位"。

**核查**：**落实到具体自然人**，签名 + 单位盖章双要素。

人员变动时（新接手人经手）必须逐次记录交接双方，不能因为"还是同一个单位"就沿用。

<a id="section-23"></a>

#### 封条编号不记录

**现象**：封装时贴了封条，但台账上没有封条编号。

**原因**：封条编号是唯一能跨环节指向同一个物理封存物的标识。

不记录编号，事后就无法回答两个问题：这次封装用的是哪个封条？后来拆的是不是同一张？编号缺失导致封条这个物证无法与保管链记录对应，等于封存环节没有留下可验证的痕迹。

**影响**：封存这一环失去可验证性。对方质疑"封条是否被更换"时，我方拿不出任何反驳材料。

**核查**：**封条编号在封装时记录，并拍照留存**。封条设计成带唯一编号和签名栏的一次性封条，撕毁即失效。拆封时由双方共同核对编号并签字确认。

<a id="section-24"></a>

### 4.3 拆封与封装（★ 表示不可逆或极难补救）

<a id="section-25"></a>

#### 自行拆封后补记录

**现象**：为图方便，自己拆开封条开始分析，事后才在台账上写"拆封检查"。

**原因**：**拆封是保管链上最敏感的环节**。它的证据价值完全来自"由谁、在什么时间、在谁见证下打开"这一组事实的真实性。

自行拆封后补记，等于声称这几个事实成立，却没有任何客观材料支撑。

**影响**：**几乎无法自证**。

质证方只需追问一句"为什么拆封没有第二人见证"，这一环的独立性就已经丧失。后面所有环节都要跟着解释。

**核查**：**必须双方在场**。拆封前核对封条编号 → 双方签字 → 录像或拍照 → 拆封 → 立即记录拆封时刻。

条件不允许时，至少要有第二人在场见证并签字。

<a id="section-26"></a>

#### 分析后不重新封装 ★

**现象**：拆封分析后，让设备保持在拆封状态，或随手放在工作台上。

**原因**：分析结束后没有重新封装，等于**封存环节在链尾缺失**。前台的所有封装工作被最后一次拆封抵消——链条的起点和终点必须有封闭状态，缺一端就不成链。

**影响**：**过程链在末端断裂**。末端交接记录缺失，使前面的保管记录无法与接收情况对应。

**核查**：**分析结束立即重新封装**，使用新的封条，记录新封条编号、封装时刻、封装人。**封条号不复用**——这是判断是否违规拆封的简单方法。

<a id="section-27"></a>

#### 原始介质反复通电 ★

**现象**：封存后为了"确认一下设备型号"再次接通设备读信息，前后数次。

**原因**：SSD 内部的磨损均衡、FTL 映射、写缓存与 TRIM 都会在通电时改变用户数据区的逻辑映射。HDD 在某些状态下读取也可能触发待处理写入。

此外，通电行为本身在保管链上属于未记录的接触。

**影响**：**原始状态被永久改变，且不可检测**。

这种改变不会体现在任何日志里。之后所有基于"原始镜像"的分析，都建立在一个已经变化过的数据源上。如果案件涉及"嫌疑人是否看到过这份数据"这类时序问题，通电可能直接抹掉关键证据。

**核查**：**封存后禁止通电**。确需确认型号信息的，在受理环节就完成并记录。

封存后若不得不再通电，必须完整记录时间、原因、操作人，并评估对数据的影响，在报告中主动说明。

主动说明的通电是瑕疵，未说明的通电是疑点。

<a id="section-28"></a>

### 4.4 结论表述

<a id="section-29"></a>

#### 用"未发现"这种绝对表述

**现象**：报告写"未发现删除痕迹"、"未发现外传行为"。

**原因**：取证工作的检查范围永远是有限的——你只查了分配空间、只查了已知应用、只查了特定时间窗。"未发现"会被读成"不存在"，但你实际表达的只是"在我检查的范围内没看到"。这是取证报告里最普遍、也最容易被专业质证方攻击的表述。

**影响**：**结论强度超出证据支撑范围**。一旦被指出"你凭什么说没发现"，我方的可信度受损，而且这类问题会连带引出"那你的检查方法是否充分"的追问。

**核查**：**写清范围和局限**。标准表述是"在 X 检查范围（分配空间、应用 Y、时间窗 Z）内未发现 W"，并在报告中单独设一节列出**未覆盖的范围**。

```text
✅ 在用户 Bob 账户 NTFS 分配空间、Chrome/Edge 已知痕迹路径，
   以及 2026-03-01 至 2026-03-15 时间窗内，未发现指向 target-site.example
   的浏览记录或下载残留。

❌ 未发现访问 target-site.example 的痕迹。
```

<a id="section-30"></a>

### 4.5 工具行为与哈希语义

前四组讲的是记录规范，这一组讲**工具给出的数字本身**——哈希与校验工具在特定条件下会给出"成功"的假象，而掩盖了它没有覆盖的事实。

<a id="section-31"></a>

#### 陷阱 11：把镜像文件的哈希一致当成"原始检材未被改动"

**现象**：受理时对镜像文件算了一个 SHA-256，检验结束前再算一次，两次一致，台账写「镜像完整性校验通过，检验过程未改动证据」，这一条被当作保管链闭合的证明。

**原因**：两段哈希都是对同一个镜像文件算的，它证明的是"分析期间镜像文件没变"，而不是"这个镜像忠实反映了送检的原始介质"。 这两件事之间隔着一整步——**采集过程**。镜像是在采集工具的控制下生成的，如果采集时发生了目标盘跳读、设备重试导致的重读、线缆接触不良、或者采集工具本身有缺陷，得到的镜像就是不完整的，而**后续任何一次哈希校验都无法发现它**——因为两次比对的都是那个已经错了的产物。**这就是"三段哈希"里第一段的意义所在**：`H_send` 必须在**送检方扣押原始介质时**由送检方算出，它锚定的是原始介质本身，而不是我方采集出来的结果。

**影响**：这条错误最麻烦的地方在于它**看起来已经回答了质证方的问题**。对方问"你如何证明镜像对应的是我方交付的那台设备"，台账上有一对一致的哈希，看起来答案就在那儿。而实际上这个答案是空的——质证只需追问一句"这两次哈希是谁算的、算的是原始设备还是你采集出来的文件"，整套论证就垮了。**它比没有记录更糟**：没有记录只是空白，而错误记录会给出一个看似已被填补的缺口，让评审误以为该环节已完成而不去追问。

**核查**：把三段哈希的"计算者"和"计算对象"在台账里写清楚，而不是只写数值。每个哈希值后面标注：`H_send` 由送检方在扣押时对**原始介质**计算、`H_recv` 由检验方受理时对**交付的镜像文件**计算、`H_after` 为检验后对**同一镜像文件**复算。

```bash
# 受理：先记录交付物的哈希，并注明交付物形态（原始介质 / 已是镜像）
sha256sum DigiForensics.dd | tee /case/H_recv.sha256
# 台账必须写明：对象=DigiForensics.dd（委托方交付的镜像），计算者=检验方，时间=…

# 送检方侧的 H_send 不由我方产生，需在受理时核对其存在且一致
# 若委托方未提供 H_send，这就是一条要写进报告的链条缺口
```

**表述模板**：「检验期间对镜像文件复算的哈希与受理时一致（`H_recv == H_after`），**证明分析过程未改动镜像**；送检方对原始介质的 `H_send` 未提供，故镜像与原始介质的对应关系无法由我方验证。」——这一句必须写出来，不能因为两段哈希一致就认为整个闭环完成。

<a id="section-32"></a>

#### 陷阱 12：把多算法哈希"都算一遍"当成覆盖充分

**现象**：受理时同时算了 MD5、SHA-1、SHA-256 三种哈希，写进台账并在报告中称「已采用多种哈希算法交叉验证，完整性保障充分」。

**原因**：多个算法的"一致性证明"强度完全相同——它们各自独立地覆盖了同一种失效模式，也就是传输与存储过程中的意外损坏或无意的数据改动。而针对"恶意构造碰撞"这个真正的威胁，只有足够长的摘要才有用。 MD5 与 SHA-1 的碰撞都已被实际演示，**它们对恶意碰撞毫无抵抗能力**；把它们算进去提供的是一种"多算法冗余"的错觉——看起来有三重保障，实际上三重保障抗的是同一个失效模式。

**影响**：这会让评审对完整性论证产生不当的信心。委托方若据此认为"既然有多重哈希，即使数据被改动也能被发现"，那么一旦我方（或第三方）在后续环节出错，**委托方的质疑会被认为缺乏依据**——而实际上那个质疑是完全成立的。这种"看起来比实际更严谨"的表述，在专业评审面前是减分的：它属于对自身结论强度的过度声称。

**核查**：**按用途选算法，而不是堆数量**。受理时的作用是"锚定状态"，MD5 有历史兼容价值（可与委托方既有记录比对），但**证明完整性的正式依据应是 SHA-256 或更强**；SHA-1 与 MD5 若要保留，必须在台账里注明它们仅作兼容比对，不作为完整性结论的依据。

```bash
# 正式完整性依据
sha256sum DigiForensics.dd | tee /case/H_recv.sha256
# 兼容比对项（若与委托方既有记录需要对齐）
md5sum DigiForensics.dd | tee /case/H_recv.md5.compat
```

**表达到位**：「完整性验证以 **SHA-256** 为准（`H_recv`）；同时记录 MD5 以便与委托方既有材料对齐，**该值不单独作为完整性结论依据**。」

<a id="section-33"></a>

#### 陷阱 13：把工作副本上的哈希一致当成副本与母本一致

**现象**：制作了工作副本用于分析（挂载、提取、挂载另一点位等），事后对工作副本算哈希，与母本镜像一致，台账记录「工作副本完整」。

**原因**：工作副本与母本是两个独立的文件对象，它们的"一致"必须靠一次独立的比对建立，不能靠"我以为我是复制出来的"。 具体会出问题的环节：① **转存工具的静默截断**——空间不足或文件大小限制可能导致复制未完成，而多数复制工具**不报错也不改变退出码**（`cp` 在磁盘满时通常会报错，但通过脚本/管道/网络传输时未必）；② **稀疏文件的处理差异**——以 `cp --sparse=always` 之类的选项复制时，稀疏区域与非稀疏区域的实际字节布局不同但内容相同，此时**哈希一致而布局不一致**，反过来若选错选项则内容可能真的不同而哈希不一致；③ **压缩或转换式转存**（写成 `.e01`、压缩成 `.gz`、转成 VMDK）之后再算哈希，**对象已经不是同一个文件**，哈希必然不同；④ **FUSE 挂载后向镜像回写**——挂载点配置不当（未加 `-o ro`）时，任何对挂载点的写操作都会落到镜像文件上，**这个改动在挂载期间不会显式提示**。

**影响**：分析结论全部建立在"我分析的就是送检的那份数据"这个前提上。如果工作副本实际是不完整的或被改过的，那么所有分析结论的有效性都不成立——而且这条错误在报告里完全看不出来，因为一切读起来都正常。**更严重的情况是镜像被写坏**：写回原始镜像属于不可逆的检材损坏，而这个损坏是静默发生的，直到委托方复核哈希时才会暴露，那时已经无法解释是什么造成的。

**核查**：副本制作后立即独立校验一次，且这次校验要成为台账里的一行：

```bash
# 制作副本
cp --reflink=auto /evidence/DigiForensics.dd /evidence/DigiForensics-work.dd

# 立刻独立校验（这一步不能省，也不能省到分析结束后才做）
sha256sum /evidence/DigiForensics-work.dd
# 与母本哈希逐字符比对，不只看大小是否一致
sha256sum /evidence/DigiForensics.dd | cut -d' ' -f1 > /tmp/a
sha256sum /evidence/DigiForensics-work.dd | cut -d' ' -f1 > /tmp/b
cmp /tmp/a /tmp/b && echo "副本与母本一致" || echo "★ 不一致，停止分析"
```

**挂载纪律同源**：挂载一律加只读参数（`mount -o ro,noload`、`-o ro,loop,noatime` 等），并在台账记录所用挂载参数，**这是防止镜像被回写的实际手段**，参见[只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md)。校验必须放在"开始分析之前"，放在分析之后就无法区分是复制出错还是分析过程污染了它。

<a id="section-34"></a>

#### 陷阱 14：把 `md5sum` 校验的比对当成内容完整性验证

**现象**：用某个校验工具对提取出的可疑文件做 MD5 比对，与威胁情报库里的哈希匹配上了，于是结论写「该文件与已知恶意样本一致」。

**原因**：MD5 值一致只能证明"两个文件的摘要相同"，而在恶意构造面前这不是同一件事。 MD5 碰撞已被实际构造并演示，攻击者可以做出**与任意给定文件 MD5 相同的不同文件**。此外还有几个语义层面的混淆：① MD5 在工具里的角色常常不是"完整性"而是"快速查重"（用它做批量样本去重），把它解读成安全属性是一次语义升格；② **不同来源给出的 MD5 可能指的不是同一段内容**——附件本体与附件解包后的主程序、被截断的前缀与完整文件，MD5 都可以不同，用错对象会比对不上或比对到错误的对象；③ **哈希值本身没有出处标注**——一个 MD5 出现在报告里，若不写明是"什么文件的 MD5"、用什么算法算的（有些工具默认 MD5、有些默认 SHA-1）、以及**它是从哪来的**，读者无法复核。

**影响**：这是"归因过度"类错误的具体形态。**把摘要一致当作样本同一性认定**，会让报告把一台机器上的文件直接归因到某个已知攻击组织或工具家族，而这个结论在专业评审面前站不住——攻击方构造一次 MD5 碰撞的成本极低，且已有公开实现。一旦该结论被质疑，基于它的所有归因推断（攻击者身份、组织关联、事件关联）都会连带失效。

**核查**：**区分三种哈希用途，各有各的表述**：

| 用途 | 合适的算法 | 表述 |
|---|---|---|
| 保管链完整性 | **SHA-256** | 「`H_recv == H_after`，分析过程未改动镜像」 |
| 样本同一性认定 | **SHA-256**（可与公开样本库的多算法值同时列出） | 「该文件 SHA-256 与样本库中 `<名称>` 一致」 |
| 批量去重 | MD5 可用 | 「用于批量比对去重」，**不作为定性依据** |

**样本比对的最低表述要求**：写清哈希算法、完整哈希值、**该值对应的文件路径与大小**、以及**样本库的名称与版本/查询时间**（样本库在变，今天的"一致"明天可能就不成立）。若只有 MD5，必须标注「仅有 MD5，未取得 SHA-256，同一性认定强度不足」。

```bash
# 认定同一性用强摘要；MD5 仅作辅助
sha256sum /evidence/extracted/DigiForensics-sample.bin
stat -c 'size=%s path=%n' /evidence/extracted/DigiForensics-sample.bin
# 台账/报告里三样都要写：算法、值、对象
```

<a id="section-35"></a>

#### 陷阱 15：把哈希核对通过当成"采集过程已经证明无损"

**现象**：采集完成后校验了镜像哈希（或采集软件自身校验通过），台账写「采集校验通过」，后续所有分析都基于这个前提，报告不再提采集质量这件事。

**原因**：采集工具的校验验证的是"我读到的字节流与我算出的哈希自洽"，它无法验证"我读到的每个字节都是介质上真实的字节"。 采集质量的失效点是硬件与传输环节的，而且**大多是无声的**：坏扇区读取失败被工具按默认值填充、目标盘因为过热或振动产生的间歇性读取错误、USB 转接或线缆导致的信号衰减造成的数据位翻转、SATA/NVMe 的错误纠正掩盖了底层读取偏差、以及目标盘在采集过程中仍处于通电状态时写入导致的前后不一致。这些都不体现为"采集失败"，采集工具照样给你一个哈希。

**影响**：这类问题在数据层面**极难事后发现**——一个被静默填充的坏扇区，在后续所有分析里都表现为"该区域内容是那串填充值"，**而分析者通常会把它当成真实数据解读**。真正的风险是：本案中某个关键结论依赖的区域恰好落在受损范围内，而报告对此毫无声明。**评审无从判断这份检材的数据基础是否可靠**，这是把一个数据质量问题留到了不可挽回的阶段。

**核查**：把采集质量作为独立事项记录，而不是并进"哈希校验通过"里：

```bash
# ① 采集日志中读取错误计数（dd 的 error 统计，或采集软件的错误日志）
dd if=/dev/sdX of=/evidence/DigiForensics.dd bs=4M status=progress 2>&1 | tail -3
# "N+0 records in / N+M records out" 里的 M > 0 即存在读取错误
dmesg | grep -iE 'I/O error|medium error|uncorrectable' # 采集期间的内核 I/O 报错

# ② 与同批次其它镜像或原厂基线比对（若条件允许）
# ③ 全盘坏扇区痕迹检查
```

**报告里应有独立的一段**：「采集过程中读取错误 **`<N>`** 次，集中在 LBA `<区间>`；该区域数据以 `<默认值>` 填充，本报告在涉及该区间的结论中已标注局限。」——没有读取错误也要写「采集过程无读取错误记录」这一句，因为"没检查"和"检查过没问题"是两件事。

<a id="section-36"></a>

#### 陷阱 16：把校验工具的"通过"当成工具确实读完了整个对象

**现象**：用某个校验/读取工具对检材或派生文件做完整性检查，工具报告通过，退出码为 0，分析者据此认为数据完整。

**原因**：工具报告"通过"与"读完了全部内容"之间隔着好几层可能被静默跳过的环节。 最典型的是**稀疏文件与稀疏属性**：以稀疏方式创建的文件逻辑大小远大于实际占用，`cp`、归档工具、镜像工具在处理它时若未显式保留稀疏属性，会**把空洞补零**成实际字节——内容读出来是对的（哈希一致），但**导出后的文件体积可能从几百 MB 变成几十 GB**，磁盘写满、复制中断、或后续步骤超时。**失败信号可能出现在与校验无关的地方**（磁盘满），而校验本身"通过"了。反过来也有：`tar`、数据库类工具在读到**截断**的归档时会报损坏，但**读到**逻辑大小大于实际内容的镜像文件**时可能只读到末尾的错误块**并继续。

**影响**：这类问题的后果分两种，都不好：**一种是把不完整的副本当成完整的分析**，后续提取会遇到截断，得到的结论建立在残缺数据上，而"校验通过"让这个事实很难被发现；**另一种是把完好的数据搞坏**——补零撑爆磁盘导致复制中断，留下一个半成品副本，而此时母本仍然完好、分析仍可进行，但已经浪费了时间且副本状态需要重新确认。后者更隐蔽，因为它不在检材上造成损失。

**核查**：**校验结果与"实际读取量"要分开确认**：

```bash
# ① 逻辑大小 vs 实际占用（差值巨大即稀疏文件）
ls -ls /evidence/DigiForensics.dd
# 格式：第一列 blocks(实际占用 512B 块)，第二列 size(逻辑大小)

# ② 实际读到的字节数应等于逻辑大小
stat -c 'logical=%s' /evidence/DigiForensics.dd
wc -c < /evidence/DigiForensics.dd

# ③ 转移稀疏属性后再校验内容一致
cp --sparse=always /evidence/DigiForensics.dd /evidence/DigiForensics-work.dd
sha256sum /evidence/DigiForensics-work.dd    # 应与母本一致
```

**导出目录的容量要在导出前算好**，不要边导边看。若工具给出了"跳过/截断/填充"类告警，**逐条读告警文本，不要只看退出码**——部分工具把数据损失降级为警告并仍返回 0。

## 五、案例示例

<a id="section-38"></a>

### 5.1 13 天空档：记录断了，哈希一致

**场景**

某地方法院审理一起计算机诈骗案，控方提交的电子证据在质证时被辩方质疑"保管链存在 13 天空档"。第三方鉴定机构需要说明其检验过程的合法性。

委托方的问题很具体：这 13 天里检材有没有被接触、能不能证明数据没变。

选择这一路径的依据是空档本身无法弥补，但数据状态可以被客观验证——而验证它只需要当初算过一次的那个值。

**处置过程**

1. 调取原始台账核对，确认空档真实存在：

```text
受理入库封存：2024-03-15 14:00
再次开封：    2024-03-28 09:00
中间出入库记录：无
```

2. 内部核查查明原因：期间实验室停电 2 次，一次设备维护时曾移动过存储柜。**操作确实发生过，只是没记录。**

这一步的顺序不能颠倒。先承认、先认定事实，再去找原因——反过来先解释原因，等于在暗示这个疏漏是有理由的，而理由本身又要靠旁证支撑，等于凭空多出一条需要证明的东西。本案的教训恰恰出在这里：最初的补充说明把"停电"写在第一段，结果停电证明也成了需要提交的材料，而那份材料晚了两天才找到。

3. 出具补充说明，附上四类客观旁证：

```text
1. 该期间监控录像显示存储柜未被开启（时间戳连续）
2. 维护记录显示设备搬迁由两名工作人员共同完成
3. 该期间未安排任何检验工作（工作日志为空）
4. 出入库登记表显示期间无领用记录
```

4. 对数据完整性做独立验证——**重新计算镜像哈希，与受理时记录的值比对**：

```bash
sha256sum DigiForensics.dd
```

```text
受理时（03-15）: 9f86d081884c7d659a2feaa0c55ad015a...
复核时（06-10）: 9f86d081884c7d659a2feaa0c55ad015a...
                                          ↑ 完全一致
```

5. **把哈希的覆盖对象清点一遍**，这一步不做，补充说明就留了个大洞。同批检材共 3 件，逐一列出各自状态：

```bash
sha256sum DigiForensics.dd DigiForensics.E01 DigiForensics-hdd.img
lsblk -b -o NAME,SIZE,MODEL,SERIAL
```

```text
件 1  DigiForensics.dd     已镜像  受理时算过哈希  覆盖 ✓
件 2  DigiForensics.E01    已镜像  受理时算过哈希  覆盖 ✓
件 3  原始 HDD（未镜像化）  已封存  未算哈希        覆盖 ✗
```

第 3 件是这份补充说明里唯一的真空区：它和前两件封存在同一个柜子里，但哈希对它一无所获。补充说明必须显式承认这一点，否则辩方只需追问"那块原始盘算过哈希吗"，前面的论证会连带被质疑。

**这个清点动作本身就该是标准动作**。受理时把每一件检材的"是否镜像化 / 是否有哈希"列成一张表，13 天后不需要临时回忆、不需要翻档案，当场就能答。事后补做的清点必然遗漏，而遗漏的那一件通常正是对方会问的那一件。

**顺带说一个顺序上的细节**：清点必须在"删残件"这类操作之前做。擦除动作会改变文件系统状态，擦除之后再统计，很容易把"原本有 4 件"算成"一直只有 3 件"——**记录的顺序会影响记录的内容**，这类细节在保管链上和在推理上同样成立。

**同样的道理在取证流程的其他环节也成立**。"先记录、后操作"应当是一条默认规则，而它被执行破坏的次数，远多于它被想起的次数——因为"操作"往往有明确的目标和截止时间，"记录"没有。

**一个能落地的做法**：把"记录"写进操作的同一条命令，而不是当成前置步骤。`cp` 之后紧跟 `sha256sum > 清单`，`rm` 之前先把 `stat` 的输出存下来——当记录是操作的一部分，它就不会被跳过；而当它是操作之前的另一个步骤，它总有一天会被跳过。

6. **从有哈希的那部分反推没有的那部分**，这不严格，但比什么都不说强，前提是必须写明它的性质：3 件中有 2 件逐字节未变；原始盘与镜像是同一次连续采集的产物，采集结束后 2 小时入库；因此第 3 件"未发生改变"是一个**基于采集流程连续性的推定**，不是直接观测结果。

**结论**

能证明：从 03-15 受理到 06-10 复核，`DigiForensics.dd` 的字节内容未发生变化。结合监控与双人搬运记录，**该期间无人接触过检材**。

这个结论的强度完全取决于一个前提：受理时那个哈希值，确实是对这一份镜像、在这个时点算的。

**不能证明**：哈希一致只能说明镜像未变，说明不了镜像内容在受理之前就已经是正确的。空档之前若发生过采集错误，哈希一样一致。

所以本条只能用于回应"空档期间是否被改动"这一个质问，不能扩大表述为"保管链完整"。

还有一个容易被忽略的细节：**哈希的复核时点是 06-10，不是 03-28**。这两个日期之间又过了 74 天，而这 74 天是有完整记录的（有新的出入库与检验记录）。所以真正的证据结构是"13 天空档 + 74 天空白（但有记录）"，而不是一段连续的未知期。这个区分值得在报告里点明——它把"整段期间都无人接触"这种无法证明的全称判断，换成了"两段各自有据、只有中间 13 天无记录"的分段判断。

**这个区分的价值还在于它划出了责任的分界点**。74 天那段有完整记录，意味着期间的每一次开封都有对应的检验工作可以对照；13 天那段没有，意味着这 13 天里检材即使被改过，也没有任何操作会留下痕迹去暴露它。责任的分界落在"有没有操作记录"上，而不是落在"有没有出事"上——这是两种完全不同的取证问题。

**还可以在报告里加一条自查**：把 03-28 那次开封之后的第一项检验工作（做了什么、用了哪个分区、算了哪个哈希）列出来。如果 03-28 之后的第一次开封记录里写着"对 4624 区的文件做了分析"，那么"空档期间是否有人动过数据"这个问题就有了一个间接答案——不是"没被动过"，而是"第一次开封后立刻进行了有特定目的的检验"，这与"有人动完又复原"的模式不符。

这个自查是间接证据，强度有限，但它比空着强。

**误判对照**

辩方与委托方最容易谈成的误判是：因为哈希一致，**空档就不存在了**。判据有三条：

①哈希比对的是 `DigiForensics.dd` 这一个文件，同批 3 件检材中未镜像化的原始介质（件 3）**零覆盖**——它没有受理时的值可比；
②哈希一致性证明的是"字节未变"，不是"操作合规"——停电与搬柜这两件事确实发生过，录像连续只说明柜门未开，不等于柜子没被挪动；
③受理时那个哈希值本身没有被证明是"对这一份镜像、在这个时点算的"，若采集合规性存疑，锚点存疑，后面一切比对都建在流沙上。

正确结论应写成「记录存在瑕疵，以哈希一致与监控旁证说明该期间数据未发生变化」。按错误判据写成「保管链完整无缺失」，代价是复核方发现原始介质本身未被哈希覆盖，直接质疑整份报告的方法论基础。

<a id="section-39"></a>

### 5.2 空档期没有哈希可依：只能靠多源时间线兜底

**场景**

另一起案件中，检材在扣押时只做了磁盘镜像、未记录任何哈希值（当时委托方未要求），在第三方实验室保管 9 天后才移交鉴定机构。移交时双方对"这 9 天里发生了什么"各执一词。将此情形单列的原因是它展示了哈希兜底的边界——**没有事先算过的值，哈希什么也证明不了**。

**处置过程**

1. 先明确告知委托方当前状态：镜像是当时唯一的副本，此后所有完整性论证都只能依赖间接证据。

3. 穷举可用的时间来源，不做主观推定：

```bash
# 镜像内文件系统时间，反映的是最后一次写入而非封存时刻
fls -r -p -o 4624 /mnt/case/DigiForensics.dd | head -5

# 交接双方各自持有的记录
ls -l /case/移交清单.pdf /case/实验室接收登记.csv
```

这一阶段最容易出的错是**先有结论再找证据**。委托方希望证明"没人动过"，于是分析员倾向于把每一项时间证据都往这个方向读。时间早于接收时刻这件事，在"没人动过"和"动过但改了时间"两种情形下都成立，它本身是个**弱证据**——弱证据不必然是坏证据，但不能单独承担结论的重量。把它和其他几项弱证据并列，让它们互相独立地指向同一方向，比把其中一项拔高成主证据要稳得多。

3. 交付时效性成为关键判据：比对镜像内最新文件时间与实验室接收登记时刻，确认接收时刻**晚于**镜像内全部文件时间，从而"接收前"这一段可由文件系统时间兜底。

4. **把阴性结论拆成有界与无界两半**。9 天空档不是一个均匀的时间段，能被证据约束的只有其中一部分：

```text
2024-03-15 扣押 ──── 2024-03-24 移交
   │                        │
   │  A 段：镜像制作中     │  B 段：实验室保管（9 天）
   │  有 dcfldd 日志       │  无任何记录、无哈希
   │  有设备序列号         │
   │  有 UTC 时间戳        │
```

A 段其实是可辩护的——采集日志本身带了制作起止时间，工具进程的输出记录了每一笔写入，这 9 天的绝大部分落在采集过程中。真正无证据覆盖的只有 B 段。把这句写进报告，比笼统说"9 天无法证明"准确得多，也不会连累本可以站住的那一段。

5. **主动去找竞争解释**。阴性结论最怕的是"其实有人动过，只是痕迹没留在你以为的地方"。所以要检查痕迹可能存在的其他位置：

```bash
# 镜像文件本身的 mtime/ctime：若有人拷贝过镜像，ctime 会变
stat DigiForensics.dd
# 输出：Modify 2024-03-15 22:14  Change 2024-03-15 22:14
#      两值相同且接近采集时刻，说明此后无人拷贝或改权限

# 移交介质本身的使用痕迹：文件被打开读过会留 atime
ls -lu --time=atime DigiForensics.dd
```

`Change` 时间（ctime，inode 变更时间）是个好用的探针：任何拷贝、改权限、改属主操作都会刷新它，而普通内容读取不会。如果 `Change` 停在采集时刻，至少可以排除"有人把它拷到别处又拷回来"。

6. 最后一步是把这些拼成结论，**并明确标注哪一段是直接观测、哪一段是推定**。

**这一步的取舍**：三项弱证据（mtime 方向、ctime 未变、工作日志为空）合起来仍然推不出"未被修改"，但它们各自排除了不同的操作路径——mtime 排除了"改内容不改时间"，ctime 排除了"拷贝搬移"，日志排除了"常规渠道的领用"。阴性结论的价值不在于它多强，而在于它**把可能性空间收窄到了具体几条**，让后续调查有明确方向。报告里把三条分别写出来，比合成一句"未发现异常"有用得多。

**结论**

阴性发现：在 9 天空档范围内，**未发现检材内容被修改的迹象**。支撑它的有三项——镜像内所有文件的 mtime 均早于实验室接收登记时刻 11 天；`stat` 显示 `DigiForensics.dd` 的 ctime 停在采集时刻 22:14，此后无 inode 变更；实验室工作日志该期间为空。

**不能证明**这 9 天内有人打开镜像写了内容又还原——文件系统时间可被 `SetFileTime` 任意改写，缺少哈希锚点时这条防线根本不成立。

**未覆盖范围**：A 段（镜像制作过程）有采集日志与设备序列号可依，属可辩护区间；B 段（实验室保管 9 天）无记录、无哈希，是真正的证据真空。此外未覆盖的还有内存、已删除文件残留空间、以及从未纳入镜像的原始介质。

**误判对照**

最容易得出的错误结论是「文件系统时间全部早于接收时刻，因此封存期间数据未被触碰」。判据有三条：

①`fls` 输出的 mtime 是**可被 `SetFileTime` 任意改写**的用户态时间戳，它证明的是"文件自己声称的最后修改时间"，不是"文件内容的实际状态"——改时间戳的成本是毫秒级的；
②本案**没有任何受理时的哈希值**，而哈希正是唯一能替代时间戳的客观锚点，缺了它，整条时间线论证都只是间接推断；
③`mtime 早于接收时刻`这个方向性证明力极弱——它同样兼容"文件在此后被打开、修改、然后把 mtime 改回原值"这一情形，判据无法区分"没动过"与"动过并复原"。

正确判据是**哈希**，而本案恰好没有。所以结论只能停在"未发现修改迹象"这个档次，不能升级为"证明未被修改"。按错误判据写成「已证明封存期间数据未发生变更」，代价是在对方追问"你怎么排除有人改了时间戳"时无从回答，整条论证作废——而且这类案子最常见的结局恰恰是有人改过时间戳。

<a id="section-40"></a>

### 5.3 补充说明怎么写：承认 + 旁证 + 客观验证

**场景**

前面 5.1 的空档最终没有被法庭排除，但机构收到一份反馈意见，要求补充说明的措辞改进。这条路径值得写下来，是因为**补充说明的组织方式本身就是结论强度的一部分**——它体现的是取证机构对自身失误的处理态度。

**处置过程**

把 5.1 的补充说明按三段式重写：

```text
一、承认事实
    2024-03-15 至 2024-03-28 期间，本机构保管台账缺失出入库记录，
    属记录管理疏漏，不作辩解。

二、提供客观旁证（四项，逐项附原始记录复印件编号）
    1. 监控录像（连续时间戳，柜门未开启）
    2. 设备搬迁维护记录（双人签认）
    3. 工作日志（该期间为空，可反证未开展检验）
    4. 出入库登记表（该期间无领用记录）

三、客观技术验证
    受理时与复核时的镜像 SHA-256 完全一致，
    证明该期间镜像数据未发生变化。
```

**两处措辞的改动值得单独说**。第一处是"完全一致"的后面加上了覆盖范围限定：

```text
三、客观技术验证
    受理时与复核时的镜像 SHA-256 完全一致，
    证明该期间镜像数据未发生变化。
    该验证覆盖件 1、件 2；件 3（原始介质）无受理时哈希值，
    其状态系依据采集流程连续性推定，非直接观测。
```

第二处更微妙：三段式原本把"原因"放在第一段（承认事实里顺带提了停电），改进版把原因整体移出正文，只留在附件的核查记录中。理由很简单——原因会招来追问，旁证不会。一份通篇解释停电与设备的说明，读起来像在替自己找理由；把原因归进附件，正文只留可核验的记录编号，辩方能逐条对，对不上就是那一条对不上，不会牵连其余三条。

**还有一条当时漏掉、后来补上的**。补充说明定稿前，实验室负责人提出："03-15 到 03-28 之间柜子被挪过，那四份旁证里有三份是关于'没被打开'的，只有搬迁记录承认了移动——这不等于承认了接触吗？"

这个提问戳中了一个措辞问题：原版四项旁证全部围绕"未接触"组织，反而给人"在回避移动"的感觉。补法不是辩解，而是加第四类旁证——**接触范围的量化**。把搬迁时的操作写成可核验的具体动作，而不是笼统的"移动过"：

```text
五、接触范围的量化（对应搬迁记录）
    1. 搬迁当日柜体封条编号：XF-2024-0311（搬迁前后各一次贴附，编号不同）
    2. 柜内三层结构件随整体移动，未单独开启
    3. 件 1、件 2 位于上层独立抽屉，该抽屉当日未拉出
    4. 搬迁全程 14 分钟，有两名工作人员在场，无第三方接触记录
```

加上这一段之后，四类旁证与搬迁记录的关系从"回避"变成了"解释"——移动确实发生了，但它移动的是一个封条完整、抽屉未开的整体。这一段不增加任何新证据，只是把已有的事实组织成可核验的形式。

**改稿前后的差别可以用一句话检验**：改稿后，辩方随便挑一个句子问"这条能核吗"，答案总是"能，翻到附件第几号"；改稿前，挑到原因段的任何一句，答案都是"这个我们后续补充"。补充说明的可辩护性不取决于说得多，取决于每句话是否都能被对方当场核验。

**一个实用的自检方法**：写完之后把补充说明念给一个不了解案情的人听，凡是他说"这个什么意思"的句子，都要改到不需要背景知识就能懂。本案初稿里"根据 3.1 项交接惯例"这句话就被标了出来——编号是机构内部的，外部读者无从对照，而它恰恰是引用了一份不存在的文件。

**结论**

能证明：机构对疏漏的陈述是可验证的、有原始记录支撑的，而不是事后叙述。三段结构让每一段各自独立成立——删掉任何一段，另外两段仍然完整。

**这份改稿还有一个没写进正文、但被问到的部分**：为什么三个月后才发现空档。答案是台账的"封存状态"字段是手工填的，停电与搬迁都发生在不涉及开柜的场合，而没有任何制度要求"移动存储设备必须记一笔"。

改稿把这句放进了附件的整改建议，因为它属于机构内部管理而非案件事实。**整改建议的写法有个原则：只写能被检查的条款**——"加强管理"不可检查，"移动存储柜位置变更须在 30 分钟内登记并双人签字"可检查。

**不能证明**：这段说明能让台账缺失本身消失——它降低的是被质疑为隐瞒的可能性，而不是补回记录。同样，它也不能证明件 3 那块原始盘未变：这一条写的是"推定"，效力与前两段的实测差一个量级。

**误判对照**

最容易得出的错误结论是「补充说明写得充分，所以保管链可以视为完整」。判据有三条：

①三段式的第一段是**承认事实**，不是消除事实——"属记录管理疏漏"这句话本身把缺失坐实了，写得再得体也不会让它消失；
②第三段的技术验证只覆盖件 1、件 2，件 3 靠推定，而"保管链完整"这个表述是全称判断，**它必须对每一件都成立**；
③四类旁证的性质是"反证接触未发生"，不是"证明接触未发生"——工作日志为空说明没安排工作，录像连续说明柜门没开，两者都只否定了特定接触方式，堵不住其他路径。

常见错误还包括把补充说明写成一份"情况说明"，通篇解释停电、搬迁、设备原因。判据很直接：**主体应当是四项客观旁证，而不是两条客观原因**——原因是解释，旁证才是证据。

按错误判据走的代价是在质证时辩方只需追问"监控录像的编号和出具单位是什么"，答不上来整段说明就失去证明力；反过来，四项旁证各带编号的写法，辩方逐项核对即可，这是补充说明唯一能站住的形态。

## 六、扩展阅读方向

保管链的难点不在记录本身。你往往要等到出事了，才知道自己记漏了什么。

<a id="section-42"></a>

### 前置基础：不先弄清这几件事，台账会记成流水账

- [哈希与完整性校验](../fundamentals-concepts/fundamentals-concepts-hashes-and-integrity-verification.md) —— 保管链上最有价值的一行是哈希值，但它证明什么、不证明什么，必须先清楚。第五章那个"13 天空档靠哈希兜底"的结论，成立的前提是你理解哈希的证明边界。
- [取证流程与原则](../fundamentals-process/fundamentals-process-five-stage-forensics-process.md) —— 保管链的每个节点对应哪个取证阶段，这条映射关系决定了你台账要设几个断点。不是每个阶段都要记录，但每个"证据状态可能改变"的时刻都要。
- [合规授权与法律边界](../fundamentals-practice/fundamentals-practice-legal-authorization-and-boundaries.md) —— 授权要件缺失的法律后果、非法获取证据的排除规则。保管链解决的是"记录"，它解决不了"没资格记录"这个更前置的问题。
- [证据文件格式](fundamentals-chain-dd-e01-aff4-evidence-formats.md) —— 受理时拿到的是 `DigiForensics.dd` 还是 `DigiForensics.E01`，决定了你算的"受理哈希"是哪一个对象。这两个值不是同一个东西，混了会让台账失去锚点作用。

<a id="section-43"></a>

### 同层深入：文书体系的其余环节

- [取证概念与分类](../fundamentals-concepts/fundamentals-concepts-digital-forensics-concepts.md) —— 证据类别（原始件、镜像件、衍生件）决定了你出具的文书叫什么、承载哪些要素。**分不清原始件与衍生件，文书类型就会开错。**
- [取证技能树](../fundamentals-process/fundamentals-process-forensics-learning-path.md) —— 保管链、法规、资质属于"软技能"维度。保管链是软技能里最基础的一环，它决定了法规与资质两项有没有意义。
- 文书格式缺口 —— **本库目前没有专门讲鉴定意见书正式格式的文章**。第 2.3 节只给了要素结构，各机构与各地区的格式规范差异很大，必须查本机构的规范文本，不要照搬任何一家的模板。

<a id="section-44"></a>

### 相邻议题：证据在不同环境下的保管形态

- [镜像制作](../../imaging/imaging-acquire/imaging-acquire-disk-imaging-and-evidence-preservation.md) —— 采集环节是保管链的第一个节点。你在这里做的哈希计算、坏扇区处理、设备信息抓取，直接决定后面台账第一行能填什么。
- [远程勘验与在线取证](../../imaging/imaging-acquire/imaging-acquire-remote-evidence-collection.md) —— 远程采集没有"封条"这个物理载体，**保管链要改用另一种锚定方式**。这是电子证据保管链最容易被套用传统模板而失效的场景。
- [虚拟机仿真](../../imaging/imaging-mount-simulate/imaging-mount-simulate-virtual-machine-emulation.md) —— 仿真期间产生的新数据必须单独登记并定性为"非检材原始内容"。**混进检材引用是比记录瑕疵更难挽回的失误。**
- [取证装备与写保护器](../fundamentals-practice/fundamentals-practice-forensics-equipment-and-write-blockers.md) —— 写保护器是你的技术防线，保管链是你的行政防线。**前者失效时后者是你的第二道保险，但反过来不成立。**

### 判据与反例：站在对方角度审一遍自己的链

- [反取证手法与时间戳篡改检测](../fundamentals-concepts/fundamentals-concepts-anti-forensics-and-timestamp-tampering.md) —— 反取证者删除日志的常见后果是"越抹越明显"（事件日志 104/1102 会被自动记录）。**这条线索反而能用来证明保管期间的异常访问**，与第四章 4.4 的结论表述要求相呼应。

## 七、命令速查

```bash
# 环境：Ubuntu/Debian，核心工具

# 1) 记录检材标识（受理时）
lsblk -o NAME,SIZE,MODEL,SERIAL,TYPE
udevadm info --query=property --name=/dev/sdX | grep -E 'ID_MODEL|ID_SERIAL'

# 2) 受理哈希（必做）
sha256sum DigiForensics.dd | tee H_recv.sha256
md5sum    DigiForensics.dd | tee -a H_recv.sha256

# 3) 维护哈希链（每次分析前后）
sha256sum DigiForensics.dd >> hash_chain.log
echo "分析前: $(date -Iseconds)" >> hash_chain.log
# ... 分析 ...
sha256sum DigiForensics.dd >> hash_chain.log
echo "分析后: $(date -Iseconds)" >> hash_chain.log

# 4) 快速比对两次哈希
awk '{print $1}' H_recv.sha256
sha256sum DigiForensics.dd | awk '{print $1}'

# 5) E01 容器自验证
ewfverify DigiForensics.E01

# 6) 台账时间戳
date -Iseconds
```

```powershell
# Windows：记录设备信息与文件哈希
Get-Disk | Format-Table Number,FriendlyName,SerialNumber,Size,IsReadOnly
Get-FileHash -Algorithm SHA256 -Path "D:\case\DigiForensics.dd"
Get-FileHash -Algorithm MD5    -Path "D:\case\DigiForensics.dd"

# 时间戳（ISO 8601，便于台账记录）
Get-Date -Format "yyyy-MM-ddTHH:mm:ssK"
```
