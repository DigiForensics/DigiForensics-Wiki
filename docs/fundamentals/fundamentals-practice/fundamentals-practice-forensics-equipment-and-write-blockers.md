# 取证装备与写保护器

<a id="section-1"></a>

## 一、概述

取证装备要解决的矛盾很直接：**既要高速读取介质，又绝对不能写入它**。

普通 USB-SATA 硬盘盒做不到——它是一条完整的双向通路，电脑可以往盘里写任何东西。写保护器就是插在中间的那道物理闸门。

一个流传很广的认知偏差，是把只读挂载当成写保护器。`mount -o ro` 是操作系统层面的约束，它可以因为参数写错而失效（NTFS 需要 `noload`、ext4 需要 `noload`），可以被某些驱动绕过，而且某些文件系统挂载时就会更新挂载计数、写日志。写保护器则是电气层就不允许写命令通过。两者不能互相替代，软写保护的五条局限里最后一条最要命：NVMe 没有传统 ATA 命令集，软方案覆盖度差。

写保护器构成采集环节的硬件前置条件。它决定的不是"能不能采到数据"，而是"采到的数据能不能作为证据"。

上游是委托与受理——送检人交来的设备处于什么状态（关机？运行中？已损坏？）直接决定处置顺序。上游还包含[取证流程与原则](../fundamentals-process/fundamentals-process-five-stage-forensics-process.md)确定的原则：**只读接入是纪律，不是偏好**。

下游支撑三件事：[镜像制作](../../imaging/imaging-acquire/imaging-acquire-disk-imaging-and-evidence-preservation.md)是在硬件通道打开之后才开始的事，`dcfldd` 的读取速度受限于所选的写保护器接口；[只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md)是接入后的软件侧约束，与硬件侧构成两道防线；

[证据保管链与委托证明](../fundamentals-chain/fundamentals-chain-chain-of-custody-and-authorization.md)则要把"用什么设备、什么接口采集的"记进去。操作步骤里那些准备动作记录的型号与序列号，就是保管链的锚点。

写保护器本体按接口分为 USB / PCIe / SATA / SAS，以及移动设备用的取证箱，接口类型比品牌更决定成败。

固件层的两条查询命令各对应一套隐藏空间机制。`hdparm -N /dev/sdX` 的输出中 `max sectors` 大于当前可见容量即说明存在 **HPA**（Host Protected Area）；案例里这条命令的输出是"未发现 HPA"，这个否定结论本身就是要写进报告的。`hdparm --dco-identify` 对应 **DCO**（Device Configuration Overlay），另一套隐藏空间的机制。

`DigiForensics.dd` 与 `DigiForensics.map` 是两遍 `ddrescue` 策略的产物。mapfile 证明"哪些区段读不到"，**本身构成证据**——报告里那 0.5 GB 不可读区域就是靠它给出的精确偏移范围。

RAID 成员盘在阵列里处于"非独立"状态，单盘直接读会得到错误数据或报错。移动设备取证箱有四种能力层级：逻辑提取 / 文件系统级提取 / 物理提取 / 云端提取，**文件系统级价值最高**，因为它能拿到已删除内容。防静电装备、USB 线材、电池属于耗材清单里的东西，劣质 USB 线导致供电不足断连，会打断采集产生不完整镜像。

能回答的是这些：手头这个设备该选哪种接口的写保护器、怎么验证写保护真的生效（**不能只看设备灯，要实测**）、怀疑有隐藏空间时怎么查、以及**读取次数本身是稀缺资源时该按什么顺序读**。

不解决的是这些：镜像怎么采、参数怎么定——`dcfldd` / `ddrescue` 的参数与坏扇区策略在[镜像制作](../../imaging/imaging-acquire/imaging-acquire-disk-imaging-and-evidence-preservation.md)；镜像拿到之后怎么分析，那是文件系统篇的事。

手机里的数据怎么取也不在范围内。取证箱的能力层级讲过了，但现代手机的 FBE / Data Protection 让难点从"数据在不在"变成"能不能解锁"，那属于加密范畴，见[BitLocker 全卷加密取证](../../crypto/crypto-volume/crypto-volume-bitlocker.md)与[数据库与配置文件加密](../../crypto/crypto-app/crypto-app-database-configuration-decryption.md)。

RAID 阵列的条带参数怎么重建缺失条带同样超出这一层，这里只到"单盘不能直接读"这一步，更深的部分本库暂无专篇。

先要理解取证流程的阶段划分，以及**为什么只读接入是纪律**。后者不是技术问题而是认知问题：如果你相信"我小心点就没事"，上面每一条都会显得多余。

建议动手接过一次硬盘。纸上读"写保护器"和手上接过一次，感受的差别落在具体动作上，尤其是那个"想验证写保护生效，于是往 `/dev/sdX` 写一个零"的动作：这个动作本身有风险，因为它的正确执行结果就是失败——而失败恰恰是它唯一的有效证据。命令没有指定 `seek`，默认从第 0 扇区开始写，一旦写保护实际未生效，这 512 个零会真的落到原始检材的头部，覆盖 MBR/VBR 或 GPT 头部。

所以这个测试只在两种前提下做：写保护已经通过另一条独立路径确认有效，或者这块盘是可以牺牲的练习盘。正式检材上的确认方式见[第四章](#section-16)对 `Read-only file system` 与设备声明的区分。

## 二、核心原理

<a id="section-3"></a>

### 2.1 两种写保护原理

| 原理 | 机制 | 优点 | 局限 |
|---|---|---|---|
| **只读型（Read-Only）** | 设备**只实现读命令**，写命令被设备固件拒绝 | 不改动设备任何状态，兼容性最好 | 依赖固件正确实现；极少数有实现缺陷的设备 |
| **物理阻断（Blocking）** | 用物理开关或跳线**切断写方向的电气通路** | 与设备固件无关，从硬件层杜绝写入 | 开关被误置是重大风险；需操作前复核 |

> **实务要点**：两种原理的可靠性都很高，但"物理阻断型"多一道人工检查环节。

无论哪种类型，每次使用前都必须用只读测试工具验证——不能假设。

<a id="section-4"></a>

### 2.2 接口类型对照

| 接口 | 适用介质 | 典型速率 | 注意事项 |
|---|---|---|---|
| **USB 3.x** | 2.5"/3.5" SATA 盘、USB 直连盘 | 5–10 Gbps | 通用性最好；供电不足时需外接电源 |
| **SATA** | 2.5"/3.5" HDD/SSD | 6 Gbps | 台式机内直连，稳定高效 |
| **PCIe / NVMe** | M.2、M-key、U.2 NVMe SSD | 3–8 GB/s | 必须确认协议层（NVMe 或 SATA）与 key 规格 |
| **SAS** | 企业级 2.5"/3.5" 盘 | 6–12 Gbps | 服务器场景主流；需 HBA 卡 |
| **IDE/PATA** | 老旧设备 | 100 MB/s | 存量案件仍有；需对应接口 |

> ⚠️ **M.2 的坑**：M.2 是**形态**不是协议。

同样的 M.2 插槽，底层可能是 **NVMe/PCIe** 或 **SATA**。买错协议直接读不出数据。

M-key 支持 NVMe，B-key 多为 SATA——下单前务必核对。

<a id="section-5"></a>

### 2.3 固件层陷阱：HPA 与 DCO

即使完全只读，硬盘固件里仍可能藏着你看不见的空间：

| 机制 | 全称 | 作用 | 取证含义 |
|---|---|---|---|
| **HPA** | Host Protected Area | 固件划出一块"主机保护区"，对 BIOS 不可见 | **可能藏有分区表或数据** |
| **DCO** | Device Configuration Overlay | 类似 HPA 的另一套机制 | 同上 |
| **RAID 元数据** | 阵列配置 | 大型阵列的成员盘是"非独立"状态 | **单盘直接读会得到错误数据或报错** |

```bash
# 检查 HPA —— 可见容量 vs 真实容量
sudo hdparm -N /dev/sdX

# 读全部 IDENTIFY 数据
sudo hdparm -I /dev/sdX

# DCO 设置
sudo hdparm --dco-identify /dev/sdX
```

> 💡 `hdparm -N` 输出中"max sectors"若大于当前可见容量，说明存在 HPA。这**不是造假**，可能是厂商预留或历史遗留，但**必须记录并在报告中说明**。

<a id="section-6"></a>

### 2.4 软镜像的固有局限

所谓"软写保护"指不用硬件设备，靠操作系统层手段限制写入。它的问题在于：

| 局限 | 说明 |
|---|---|
| **挂载即可能写** | 某些文件系统挂载时会更新挂载计数、写入日志 |
| **参数写错就失效** | `mount -o ro` 之外，NTFS 需 `noload`，ext4 需 `noload` |
| **工具可能绕过** | 某些取证工具会尝试修复"错误"，从而写入 |
| **无法覆盖 NVMe** | NVMe 无传统 ATA 命令集，软方案覆盖度差 |
| **日志类设备无法软隔离** | 磁盘阵列控制器、智能卡等 |

**结论**：软写保护可以作为补充，绝不能作为唯一手段。

唯一例外是——镜像已经做好了，只在副本上分析。此时原始介质已封存，软隔离就够了。

<a id="section-7"></a>

### 2.5 移动设备取证箱的工作方式

移动取证与磁盘取证的物理对象完全不同。取证箱（移动取证箱 / 移动数据提取工作站）的核心能力：

| 能力 | 说明 | 意义 |
|---|---|---|
| **逻辑提取** | 读取应用层可见数据 | 快，但拿不到已删除碎片 |
| **文件系统级提取** | 绕过应用锁定，直接读分区 | **能拿到已删除内容**，价值最高 |
| **物理提取** | 整块芯片的比特流 | 最完整，但通常需拆机或专用接口 |
| **云端提取** | 通过账号获取云端数据 | 设备已灭失时的替代路径 |

> **现实约束**：现代手机普遍有**硬件级加密**（Android 的 FBE、iOS 的 Data Protection）。没有正确凭证时，物理镜像拿到的也是密文。

手机取证的难点从"数据在不在"变成了"能不能解锁"——这属于板块 5 的加密范畴。

<a id="section-8"></a>

### 2.6 耗材清单

低层取证的真实成本常被低估：

| 耗材/损耗 | 消耗原因 | 影响 |
|---|---|---|
| **硬盘读写头** | 故障盘反复读取 | **二次读取会加速损坏** |
| **SSD 写入寿命** | 大量小文件写入 | 一般不适用于只读取证 |
| **USB 线材** | 移动硬盘供电不足导致断连 | **频繁断连会打断采集，产生不完整镜像** |
| **防静电装备** | 静电放电损坏主板/内存 | 手机取证中风险最高 |
| **电池损耗** | 设备长时间不通电 | 部分电池老化后充电即危险 |

> **关键实践**：对疑似故障的硬盘，读取次数本身就是稀缺资源。每读一次都可能永久损失数据。

必须先用 `ddrescue` 逻辑读，确认坏道分布后再决定是否深挖。

## 三、操作步骤

<a id="section-10"></a>

### 步骤 1：接写保护器前的准备

```bash
# 1) 记录检材信息（接之前就记录，避免混乱）
lsblk -o NAME,SIZE,MODEL,SERIAL,TYPE

# 2) 确认目标未被挂载
findmnt | grep -E 'sd[a-z]|nvme'

# 3) 记录固件可见容量
sudo hdparm -I /dev/sdX | head -30
sudo hdparm -N /dev/sdX
```

物理层面：

```text
1  取证人员佩戴防静电手环
2  取下检材，记录外观与接口状态
3  检查写保护器开关处于"阻断/只读"位
4  接入写保护器，再接检材（顺序很重要：先接写保护器端）
5  在检材通电前，再次确认开关位置
```

<a id="section-11"></a>

### 步骤 2：验证写保护真的生效

**这一步绝不能跳过**：

```bash
# 确认内核层面设备为只读
lsblk -o NAME,RO,RM,SIZE,MODEL
# RO 列必须为 1

# 尝试写入测试 —— 应该失败
# 把 sdX 换成上面 lsblk 确认的设备路径。若走的是硬件写保护，
# 内核看到的仍是可写块设备，这次写入会真正落盘，
# 因此只在可牺牲的练习盘上执行；正式检材的写保护验收改用 hdparm -I 的写保护位报告。
# 期望结果：Read-only file system（块设备层被拦截）
echo test | sudo tee /dev/sdX >/dev/null && echo "写入成功：写保护未生效" || echo "写入被拒绝：写保护生效"
```

> ⚠️ **注意**：`RO=1` 有时是内核因设备特性（如 USB 直连盘）自动加的保护，**不等于物理写保护**。真正的验证要看写保护器自身的指示与型号规格。

<a id="section-12"></a>

### 步骤 3：执行镜像采集

```bash
# 正常介质
sudo dcfldd if=/dev/sdX of=DigiForensics.dd \
     hash=md5,sha256 hashlog=DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on

# NVMe 设备（注意接口名可能是 /dev/nvme0n1）
sudo dcfldd if=/dev/nvme0n1 of=DigiForensics.dd \
     hash=md5,sha256 hashlog=DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on
```

<a id="section-13"></a>

### 步骤 4：疑似故障盘的处置顺序

```bash
# 第 1 遍：快速读取，不做坏道重试（快，先拿到大部分数据）
sudo ddrescue -n /dev/sdX DigiForensics.dd DigiForensics.map

# 查看坏道分布
ddrescuelog -t DigiForensics.map

# 第 2 遍：只对失败区域重试
sudo ddrescue -d -r3 /dev/sdX DigiForensics.dd DigiForensics.map
```

> 💡 **为什么要分两遍**：`ddrescue -n` 跑得快，能尽快把绝大多数数据救出来并建立 mapfile。之后才针对坏道做耗时的逐块重试。如果一开始就 `-d`，可能耗几天且中途再次损坏。

<a id="section-14"></a>

### 步骤 5：RAID 阵列的处理

```bash
# 识别控制器与阵列状态（需硬件 RAID 卡）
# 先用 lspci 找到 RAID 控制器
lspci | grep -i raid

# 阵列成员的容量与型号通常不一致于单盘标称值
lsblk -o NAME,SIZE,MODEL,SERIAL

# 重要：不要单独读成员盘
# 正确做法：先在原控制器上做一致性备份，或使用阵列卡的镜像功能
```

> ⚠️ **RAID 的常见翻车点**：成员盘单独读出的是**不一致的数据**（因为条带分布在多盘上）。必须由控制器输出逻辑盘，或从其他成员盘补齐缺失条带。

<a id="section-15"></a>

### 步骤 6：移动设备处置

```text
1  记录设备状态：是否开机、锁屏、是否有通知
2  若开机：不要解锁，也不要拔线（可能丢失内存中的会话）
3  评估是否需要内存提取（见板块 8）
4  选择提取方式：逻辑 / 文件系统级 / 物理
5  提取后立即对提取物计算哈希
```

## 四、常见陷阱

取证装备的失误大多不是技术判断错误，而是**把某个"看起来安全"的状态当成了已验证的安全**。一章已经点明核心矛盾：只读挂载是操作系统层面的约束，写保护器是物理层面的约束，**两者不能互相替代**。本章按四个环节展开：硬件连接、写保护验证、固件与容量、故障盘与特殊介质。

★ 标记表示该操作会导致原始检材永久灭失或不可逆改变，执行前必须停下来确认。

<a id="section-17"></a>

### 4.1 硬件连接与选型

<a id="section-18"></a>

#### 陷阱 1：用普通硬盘盒直接接原始检材

**现象**：为了省事，原始硬盘直接插进 USB 硬盘盒就开始 `dcfldd`，采集顺利完成，镜像哈希也算了。

**原因**：USB-SATA 桥接芯片让电脑可以往盘里写，它是一条完整的双向通路。而操作序列里的一切信号都是正常的：设备识别成功、读命令返回数据、哈希能算出来、看不出任何异常。问题在于——桥接芯片的写通道一直存在，`dcfldd` 只是一条读命令，它没写不等于通路没写。而操作系统在这一刻可能正在做的事，完全不在 `dcfldd` 的视野里：文件系统自动挂载触发日志回放、写保护设备被内核尝试重新挂载、日志或缓存落盘。

**影响**：**这是实务中最高频的证据灭失原因**，而且它不留痕迹——事后没有任何一个文件能证明检材被写过，**唯一能证明检材仍然完整的是事前用对了硬件**。更麻烦的是责任归属：镜像"正常采到了"，所有后续结论都会建立在一个原始性存疑的基础上。

**核查**：**原始检材必须经写保护器接入**，且顺序是"先接写保护器端、再接检材"（步骤 1 的物理流程第 4 步明确"顺序很重要"）：

```text
1  取证人员佩戴防静电手环
2  取下检材，记录外观与接口状态
3  检查写保护器开关处于"阻断/只读"位
4  接入写保护器，再接检材（顺序很重要：先接写保护器端）
5  在检材通电前，再次确认开关位置
```

**接之前就先记录，不要接完再想**（步骤 1 的第 1 步就是这个用意）：

```bash
lsblk -o NAME,SIZE,MODEL,SERIAL,TYPE
findmnt | grep -E 'sd[a-z]|nvme'     # 确认目标未被挂载
```

<a id="section-19"></a>

#### 陷阱 2：M.2 插槽买错协议，插上读不出数据

**现象**：按型号买回写保护器，把 NVMe SSD 插上去读不出来，换 SATA SSD 一切正常，型号规格字面上"都是 M.2"。

**原因**：**M.2 是形态不是协议**（2.2 的警示）。同样的 M.2 插槽，底层可能是 **NVMe/PCIe** 也可能是 **SATA**，两者的命令集、物理引脚定义完全不同。采购时"接口类型：M.2"这一栏是满足的，规格表上没有任何一处写着错。

而 PCIe/NVMe 行里那句"必须确认协议层（NVMe 或 SATA）与 key 规格"就是为这件事准备的。

**影响**：**时间与检材机会的双重损失**。

这类问题常在现场才发现，等发现时检材已经从"刚送检"变成"放置了几天"。更麻烦的是它会连带引发二次操作——换设备、重新接线，而每一次重新接线都是一个需要重新记录的环节。

**核查**：采购前核对协议层与 key 规格，而不是核对外形尺寸：

| 判据 | 要点 |
|---|---|
| **协议层** | NVMe/PCIe 与 SATA 完全不同，**不能互换** |
| **key 规格** | M-key 支持 NVMe，B-key 多为 SATA |
| **长度** | 2280 与 2242/2230 长度不同，转接与槽位要匹配 |
| **接口类型行本身** | PCIe/NVMe 行的速率（3–8 GB/s）远高于 SATA，可作旁证 |

装上后第一件事是确认系统识别为 NVMe 而不是退回 USB 桥接：

```bash
lsblk -d -o NAME,MODEL,SERIAL,SIZE
sudo nvme id-ctrl /dev/nvme0     # NVMe 用 nvme 工具，不是 hdparm
```

<a id="section-20"></a>

#### 陷阱 3：USB 供电不足导致长采集中断

**现象**：500 GB 采到 300 GB 左右断连，重插后继续，镜像出现一大段全零；或者同一批案子时好时坏。

**原因**：**USB 供电不足会在长采集中断**（2.6 的耗材表列了这一条），而 2.6 同时指出：频繁断连会打断采集，产生不完整镜像。

桥接芯片在供电跌落时可能降速甚至反复重协商，这个过程"看起来还在工作"——`dcfldd` 的 `status=on` 会持续显示已读字节数在涨，所以人会以为只是慢。

而集线器供电不足这个原因更隐蔽：直插笔记本能用、插集线器就断，而很多人是先试直插再"图省事"加集线器。

**影响**：**一段全零的镜像比一段缺数据的镜像危险得多。**

缺数据时 `dcfldd` 会报错、mapfile 会有记录；而断连后重头写入的部分可能只是稀疏空洞，肉眼扫一遍看不出来，直到某个文件的哈希算不出来。

**核查**：**用外接供电的硬盘盒，不要用集线器**（2.2 的注意事项列里"供电不足时需外接电源"就是这条）：

```bash
# 采集前确认链路与设备识别稳定
lsblk -o NAME,SIZE,MODEL,SERIAL,TYPE
# 长采集用 status=on 观察进度是否有停滞，而不是只等结束
sudo dcfldd if=/dev/sdX of=DigiForensics.dd \
     hash=md5,sha256 hashlog=DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on
```

断连后不要直接续写——`conv=noerror,sync` 掩盖了错误但没有修复空洞。正确做法是重新开始一次完整采集，或者明确改用 `ddrescue` 的 mapfile 机制记录哪些区间没读到。

报告里必须写"采集过程中发生过断连"这一事实，而不是把最终镜像当作一次连续采集的产物。

<a id="section-21"></a>

### 4.2 写保护验证

<a id="section-22"></a>

#### 陷阱 4：★ 跳过"试写失败"这一步就开干

**现象**：接上写保护器，`lsblk` 显示 `RO=1`，直接开始 `dcfldd`。或者写保护器是物理阻断型、开关拨到了"读写"位，采集完才发现。

**原因**：物理阻断型写保护器多一道人工检查环节，而这一道环节正是它与只读型的区别所在（2.1 的实务要点）。

`RO=1` 这个信号看似充分，但它有两个漏洞：一是有些设备（尤其是 USB 直连盘）的 RO 是内核因设备特性自动加的，与写保护器无关；二是开关被误置属于流程失误，不会产生任何系统级告警。

而"设备工作正常、读命令有数据返回"这个现象完全无法区分两种状态。

**影响**：**这一步是"有没有上锁"的分界线**。

跳过它，整个采集过程的原始性都建立在一个未验证的假设上，而且事后无法回溯补救——不像数据缺失有 mapfile 记录，写入没有痕迹。

**核查**：**每次使用写保护器都要验证，不能假设**（2.1 的原话）。而且验证要问"是谁提供的只读"：

```bash
# ① 内核层面设备为只读
lsblk -o NAME,RO,RM,SIZE,MODEL
# RO 列必须为 1

# ② 尝试写入测试 —— 应该失败
# ② 破坏性写测试 —— 必须换同型号可牺牲练习盘做，绝不能对检材做。
#    把练习盘接入同一写保护器后执行下面这条：
printf 'WP-TEST' | sudo dd of=/dev/sdX bs=512 count=1 conv=notrunc
#    被拒 → 写保护器在本链路本机有效；之后检材接入只重复第①步的标识核对。
#    写入成功 → 该链路不可用于采集正式检材，不得用于正式采集。

# ③ 物理阻断型还要额外确认开关位置与型号规格
#    RO=1 有时是内核因设备特性自动加的保护，不等于物理写保护
```

**验证结果要作为记录的一部分写进工作日志**——"写保护器型号 + 序列号 + 开关位置 + 试写失败的报错原文"四项齐全，才是可复核的验证。

只写"已接写保护器"是不充分的。

<a id="section-23"></a>

#### 陷阱 5：把 `mount -o ro` 当成写保护的替代方案

**现象**：不做硬件写保护，改用只读挂载直接分析镜像或分区，认为效果等价。

**原因**：**软写保护的五条局限在 2.4 已经列全**，而其中三条会直接导致写入：挂载即可能写（更新挂载计数、写入日志）、参数写错就失效（NTFS 需 `noload`、ext4 需 `noload`）、某些取证工具会尝试修复"错误"，从而写入。

最后一条最危险——它不是挂载参数能管住的，工具的行为在挂载参数之外。2.4 的结论是"软写保护可以作为补充，绝不能作为唯一手段"。

**影响**：**参数正确但工具越权写入**，这类事件没有任何拦截点。

等发现时元数据已经被改动，而 2.3 强调的 HPA/DCO 那类固件层问题与之无关——这次损失的是文件系统语义，不是容量。

**核查**：**软隔离的前提是"原始介质已封存、只分析副本"**（2.4 明确写了这个唯一例外）：

```bash
# 唯一被认可的软隔离场景：介质已封存，只对副本做只读接入
losetup --find --show --read-only /evidence/DigiForensics.dd
# NTFS 需 noload，ext4 需 noload（2.4 第二行局限）
sudo mount -o ro,noload,noatime /dev/loop0p2 /mnt/case
sudo umount /mnt/case
losetup -d /dev/loop0
```

**对原始介质，软写保护不能替代写保护器。**

而 NVMe 尤其如此：**NVMe 无传统 ATA 命令集，软方案覆盖度差**（2.4 第四行）。

<a id="section-24"></a>

### 4.3 固件、容量与接口命令

<a id="section-25"></a>

#### 陷阱 6：忽略 HPA/DCO，采到的镜像比真实容量小

**现象**：镜像采完，文件系统能解析，但看不到某个分区；或者镜像大小与送检单标称容量对不上，差了一个整数块。

**原因**：**即使完全只读，硬盘固件里仍可能藏着你看不见的空间**（2.3 开篇原话）。HPA（Host Protected Area）是固件划出的一块"主机保护区"，对 BIOS 不可见；DCO 是类似机制。

镜像小是"工具只读了固件愿意给的容量"的结果，而不是物理盘就那么大。而这个现象在采集时没有任何提示——`dcfldd` 读到设备报告的容量就停，所有命令都正常返回。

**影响**：**可能漏掉整个分区**。

这属于"以为采全了"而不是"没采全"，最坏的情况下后续所有分析都建立在一个不完整的检材上，而没有任何环节会报错。

**核查**：**采集前记录固件可见容量，采集后与送检单核对**（步骤 1 的第 3 步就是为此设计的）：

```bash
sudo hdparm -I /dev/sdX | head -30     # 完整 IDENTIFY 数据
sudo hdparm -N /dev/sdX                # HPA：可见容量 vs 真实容量
sudo hdparm --dco-identify /dev/sdX    # DCO 设置
```

判读方式按 2.3 的提示执行：`hdparm -N` 输出中"max sectors"若大于当前可见容量，说明存在 HPA。这"不是造假"，可能是厂商预留或历史遗留，但必须记录并在报告中说明。

案例第 1 步的结果是"型号与序列号与送检单一致，未发现 HPA"——"未发现"这个结论本身也是要写进报告的检查结果。

<a id="section-26"></a>

#### 陷阱 7：对 NVMe 用 `hdparm` 查询固件信息

**现象**：拿到 NVMe SSD，跑 `hdparm -I` 与 `hdparm -N`，输出为空或"command not supported"，于是判断"没有隐藏容量问题"。

**原因**：`hdparm` 走 ATA 命令集，而 NVMe 走的是 NVMe 命令集——两套完全不同的协议。工具无输出不表示设备无异常，只表示这个工具根本不适用于这类设备。

而这正好落进陷阱 6 那个陷阱的变体：把"没查到"当成"没有"。

**影响**：**NVMe 上的 HPA 等价问题不会被检出**。

虽然 NVMe 不用 ATA 的 HPA 机制，但 NSID 可见性、命名空间大小与物理容量的差异同样需要核对，而这条核对在 `hdparm` 无输出后就跳过了。

**核查**：**按介质类型选命令，不要一套命令走天下**：

```bash
# NVMe：用 nvme-cli
lsblk -d -o NAME,MODEL,SERIAL,SIZE
sudo nvme id-ctrl /dev/nvme0
sudo nvme id-namespace /dev/nvme0 -n 1
# 采集命令也走 NVMe 设备节点，不是 sdX
sudo dcfldd if=/dev/nvme0n1 of=DigiForensics.dd \
     hash=md5,sha256 hashlog=DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on
```

"工具无输出"与"检查通过"在报告里必须写成不同的话：前者是"该工具不适用于本介质，NVMe 固件信息未采集"，后者是"已采集，未发现差异"。

<a id="section-27"></a>

### 4.4 故障盘、RAID 与移动设备

<a id="section-28"></a>

#### 陷阱 8：★ 故障盘一上来就深挖，或反复通电

**现象**：看到硬盘读不出数据，直接 `ddrescue -d`（直接模式）长时间反复重试坏道，或者换线换盒重试多次；手机带电拆机取芯片。

**原因**：2.6 的关键实践写得很清楚：对疑似故障的硬盘，读取次数本身就是稀缺资源，每读一次都可能永久损失数据；必须先用 `ddrescue` 逻辑读，确认坏道分布后再决定是否深挖。

而"看到报错就想修好"的直觉恰恰是反的——磁头损伤的盘在机械运动中会持续恶化，无差别深挖加速的是损坏而不是恢复。手机侧则是**锂电池 + 金属工具 = 起火/短路风险**，文章明确要求"必须专业防护"。

**影响**：**把本可恢复的部分数据永久损失掉**。

案例的顺序值得照搬：先 `ddrescue -n` 跑 4 小时拿到 497.4 GB / 500 GB，看清坏道集中在偏移 `0x1A2F00000` 附近且分散在多个小区块（典型磁头损伤特征）之后，才决定用 `-d -r3` 补 2.1 GB。

如果没有第一遍的分布信息，第二遍的目标区域、耗时、风险都无从判断。

**核查**：**两遍策略，先快后慢**：

```bash
# 第 1 遍：快速读取，不做坏道重试（先拿到大部分数据）
sudo ddrescue -n /dev/sdX DigiForensics.dd DigiForensics.map
ddrescuelog -t DigiForensics.map        # 先看坏道分布

# 第 2 遍：只对失败区域重试
sudo ddrescue -d -r3 /dev/sdX DigiForensics.dd DigiForensics.map
```

**注意包名**：Debian/Ubuntu 里 `apt install ddrescue` 装的是**另一个同名无关程序**（`dd_rescue`），它**没有 mapfile 机制**——用错的工具既拿不到坏道分布，也拿不到续传能力，而命令名一模一样，只有 `--help` 输出和 mapfile 有无之别。正确包名是 `gddrescue`：

```bash
ddrescue --version      # 确认是 GNU ddrescue
ls -l DigiForensics.map # 确认 mapfile 真的生成了
```

**移动设备**：先记录状态（是否开机、锁屏、是否有通知），开机状态下**不要解锁、也不要拔线**（可能丢失内存中的会话）；需要拆机取芯片时必须先断开电池并具备专业防护。

<a id="section-29"></a>

#### 陷阱 9：RAID 成员盘单读，得到的是错误数据

**现象**：把 RAID 阵列里的某块成员盘单独接上读，采到"部分数据"，分析后发现文件系统完全无法解析。

**原因**：**成员盘单独读出的是不一致的数据**，因为条带分布在多盘上（步骤 5 的警示）。

这和"取到了部分内容"是完全不同的两件事。条带宽度决定数据在盘间的交错方式，单盘读出来的是每隔 N 个扇段就跳到别的盘的数据。这些字节被错误地拼接在一起，得到的是一份结构上根本不成立的字节流。

**影响**：**误把"错误的完整字节流"当作检材的一部分继续分析**。

这类数据不会报错。`file` 识别不出，文件系统解析失败，分析师很容易归因于"阵列确实损坏了"而停止追查——**而实际上数据在控制器上可能是完好的**。

**核查**：**由控制器输出逻辑盘，或从其他成员盘补齐缺失条带**：

```bash
# 识别控制器与阵列状态（需硬件 RAID 卡）
lspci | grep -i raid
lsblk -o NAME,SIZE,MODEL,SERIAL   # 阵列成员的容量与型号通常不一致于单盘标称值
```

成员盘容量与型号不一致于单盘标称值，本身就是"这是阵列成员"的信号——遇到这种盘，正确动作是回到控制器侧导出，而不是接上写保护器读它。

<a id="section-30"></a>

#### 陷阱 10：把移动设备逻辑提取的结果当成"数据都在这里"

**现象**：用取证箱做完逻辑提取，报告写"已提取设备全部数据"，而委托方关心的已删除内容找不到。

**原因**：**取证的四种层级在 2.5 已经分清**：

- 逻辑提取：读取应用层可见数据，**快，但拿不到已删除碎片**
- 文件系统级提取：绕过应用锁定直接读分区，**能拿到已删除内容，价值最高**
- 物理提取：整块芯片比特流，最完整但通常需拆机
- 云端提取：设备已灭失时的替代路径

**"提取完成"这四个字在四个层级上的含义完全不同**。工具输出的"提取成功"通常只覆盖了应用层。

**影响**：最常见的场景是逻辑提取拿到了通信录、短信、照片，而被删除的聊天记录不在其中。

委托方据此认为"数据已灭失"。实际上它可能仍躺在文件系统的未分配空间里。

**核查**：按委托目标选择层级，并把层级与未覆盖内容一并写入报告：

```text
1  记录设备状态：是否开机、锁屏、是否有通知
2  若开机：不要解锁，也不要拔线（可能丢失内存中的会话）
3  评估是否需要内存提取（见板块 8）
4  选择提取方式：逻辑 / 文件系统级 / 物理
5  提取后立即对提取物计算哈希
```

> "本次提取层级为**文件系统级**（绕过应用锁定直接读分区），可覆盖已删除内容。**未覆盖范围**：① 应用层加密容器内部数据（现代手机普遍有硬件级加密——Android FBE、iOS Data Protection）；② 需要解密的凭证保护数据；③ 芯片级磨损均衡导致的块不可读。**本结论不表明设备内不存在其他数据。**"

**2.5 的现实约束值得单独记下**：没有正确凭证时，物理镜像拿到的也是密文——手机取证的难点从"数据在不在"变成了"能不能解锁"。所以层级选择之前要先回答凭证问题，否则物理提取只是拿到一块密文。

## 五、案例示例

<a id="section-32"></a>

### 5.1 500 GB 故障盘的分区恢复：先判 HPA 再上写保护器

**场景**

查获一块 500 GB 机械硬盘，送检人描述"电脑有时候读不出来"。委托方的问题是：这是硬盘故障还是接口问题，以及**硬盘里的数据能恢复多少**。

送检人的描述指向接口，送检盘本身也确实有物理损伤。两个问题必须分开回答，而判断 HPA 与 DCO 是回答第一个问题的前提。

**处置过程**

1. 预检固件信息，确认型号与序列号与送检单一致，并排除隐藏容量：

```bash
sudo hdparm -I /dev/sdX | head -30
sudo hdparm -N /dev/sdX      # HPA（`max sectors` 与实际容量不符即存在）
```

结果：型号、序列号与送检单一致，**未发现 HPA**，`max sectors` 与标称容量匹配。

2. 接写保护器并**实测验证**生效，而不是相信设备指示灯：

```bash
lsblk -o NAME,RO,RM,SIZE,MODEL      # RO=1
printf 'WP-TEST' | sudo dd of=/dev/sdX bs=512 count=1 conv=notrunc   # 被拒即写保护生效；写入成功即为失效
# 破坏性写测试须换同型号可牺牲练习盘执行，不能指向本行的检材。
# 输出：Read-only file system  ← 写保护生效
```

3. 第一遍快速读取，跳过已知坏区，4 小时完成：

```bash
sudo ddrescue -n /dev/sdX DigiForensics.dd DigiForensics.map
```

得到 497.4 GB，坏道集中在偏移 `0x1A2F00000` 附近。

4. 查看坏道分布，判断损伤形态：

```bash
ddrescuelog -t DigiForensics.map
```

约 2.6 GB 读取失败，**分散在多个小区块**——典型的磁头损伤特征，而非单点连续损坏。

5. 第二遍直接重试失败区，`-d` 让坏区重读、`-r3` 限次防止加重损伤：

```bash
sudo ddrescue -d -r3 /dev/sdX DigiForensics.dd DigiForensics.map
```

补回约 2.1 GB，剩余 0.5 GB 彻底不可读。

6. 把"接口还是盘"这个问题用可复核的方式回答，而不是用描述。第二次采集时换了一个 USB-SATA 桥接芯片，同样的镜像命令读到的是**完全相同的失败偏移**：

```text
第一次  USB桥接A:  失败集中 0x1A2F00000 附近，2.6 GB
第二次  USB桥接B:  失败集中 0x1A2F00000 附近，2.6 GB（偏移逐块一致）
```

这是本案最关键的一次对照。接口问题的表现是随机的、可随更换硬件而变化的；固件损伤的表现是钉死在盘体坐标上的。换硬件不改变结果，等于把接口从嫌疑里排除掉了，而且这个排除不依赖任何一句"看起来像"。

7. 顺序上还有一处必须记进采集记录：`hdparm -I` 与 `hdparm -N` 都在接写保护器之前做。原因是这两个命令要向设备下发读 IDENTIFY 与读 IDENTIFY 的扩展命令（`READ NATIVE MAX ADDRESS`），某些写保护器型号在只读通道下不响应这两条指令。顺序反了，整套设备要拆下来重来，而拆装本身就是一次新的机械风险。

**结论**

能证明：写保护器接入期间原盘未被写入；`DigiForensics.dd` 成功恢复 499.5 GB，mapfile 精确记录了读不到区段的偏移。损伤形态为**分散型**，支持"磁头物理损伤"而非"接口接触不良"——后者不会在盘内产生固定区段的读取失败。

支撑这个定性的是第二次采集：更换桥接芯片后失败偏移逐块一致，接口被排除。

**不能证明**：0.5 GB 内原有什么内容。mapfile 只记录了"这里读不出"，读不出的扇区里可能有关键数据，也可能早已被文件系统标记为坏簇。

未覆盖范围有两条：一是固件层未做 SMART 全项读取（本次只取了 IDENTIFY 与 Native Max），坏扇区增长趋势与温度历史不在结论内；二是未做 0.5 GB 区的低级别磁道级读取尝试，`-r3` 已经是保守设置，若委托人要求提高回收率，可以在**同一块原盘、同一次写保护状态**下再跑一轮更高重试次数的副本采集，但必须记录为新的采集节点。

**误判对照**

最像的误判是把送检人的描述当成诊断结论，写成"接口问题导致无法读取"。

判据在两条独立证据上。

其一，`ddrescuelog` 报告的失败区段是盘内固定偏移（`0x1A2F00000` 附近）且分散成多个小区块。接口故障不会产生这种分布——接口坏了会整盘掉盘或完全读不出，而不是稳定地在某些 LBA 上失败。

其二，第一遍跳过坏区后仍能稳定读出 497.4 GB。若为接口问题，`-n` 策略无从生效。

三条判据，按证明强度排序：

①**换硬件后失败偏移是否改变**。改用第二块桥接芯片、重新插拔、走另一条 USB 口，失败区段的 LBA 列表逐条相同——本案的 0x1A2F00000 附近那批小区块两次完全重合。接口层的故障会随连接状态变化，不会钉在盘体坐标上。

②**失败率随读取次数的走势**。第一次 `-n` 失败 2.6 GB，第二次 `-d -r3` 补回 2.1 GB，剩 0.5 GB。这个"重试能补回八成、最后两成怎么都不行"的形态，是磁头或盘面局部损伤的典型曲线；接口接触不良的失败率会随机波动，不会收敛到一个稳定残值。

③**`-n` 策略是否生效**。如果失败是接口层的，`ddrescue -n` 根本跑不下去——每跳过一次就掉一次盘。而本案 4 小时跑完 497.4 GB，说明读取通道本身是通的，问题只在特定 LBA 上。

第③条容易被跳过，因为它是"程序没报错"这种消极证据。但它恰恰是最难用巧合解释的一条：497.4 GB 的连续成功读取，等于在时间维度上证明接口没有间歇性故障。

正确判据是失败区段是否落在固定 LBA 上，且该 LBA 在更换连接方式后是否保持不变。

按错误判据走的代价：把一块需要更换的送检盘判为"接口松动，重插即可"，检材原样退回。两周后委托方发现盘彻底不通电，全部数据永久丢失——**而那 0.5 GB 里可能正有案件需要的内容**。

这类误判的隐蔽之处在于它给出的建议是可执行的。"重插接口"这个动作会真的做，做完发现好了，于是所有人都认为诊断正确；直到两周后盘彻底掉盘，才回头怀疑当初的判断。而正确处置（保留原盘、按盘体损伤处理、立即做两遍 ddrescue）的成本是高一些的采集时间——两个选项的代价差得很远，但只有后者能保住数据。

### 5.2 HPA 检查漏做：标称 500 GB 实为 160 GB

**场景**

另一块送检盘的送检单标称 500 GB，`lsblk` 也显示 `SIZE=500G`，但镜像做出来文件系统只认到 160 GB 的容量，委托方要求解释另外 360 GB 的去向。

`lsblk` 的容量与文件系统可见容量不一致时，第一反应必须是 HPA，不是"文件系统坏了"。

**处置过程**

1. 不做任何镜像，先查固件层报告的最大扇区数：

```bash
sudo hdparm -N /dev/sdX
```

```text
* SCA   Max sectors        = 312527858/312527858
        size                = 160041885696 bytes
        capacity            = 297272047 sectors
```

标称 500 GB 对应约 976762544 个扇区，而固件报告的最大扇区只有 297272047——**HPA 存在，被隐藏的扇区数约 6.8 亿**。

2. `lsblk` 的显示不可作为判据，因为它读的是 ATA 报告值，与固件层可能被篡改的值一致：

```bash
lsblk -o NAME,SIZE,MODEL      # 依然显示 500G，误导
```

3. 结论落到 DCO/HPA，并明确后续处置需厂商授权解除，否则隐藏区数据无法获取。

4. 顺带把 DCO 也排掉，避免把两种机制混为一谈：

```bash
sudo hdparm -N /dev/sdX | grep -i enabled
# HPA: disabled —— 隐藏区不是被硬件裁掉的，是盘本来就这么大
sudo hdparm --dco-setmax /dev/sdX
# hdparm: SET MAX failed: Bad/missing command
```

第二条命令的存在意义不在于它会成功，而在于它被试过并被记下。HPA 与 DCO 的共同表征是"固件报告的容量小于标称"，但处置路径完全不同：HPA 是 ATA 的 `SET MAX` 命令，理论上可逆；DCO 涉及扇区级参数与 CRC 二次校验，改动会永久写进固件区。分不清这两者时，唯一安全的动作是先做只读探测，不动任何写命令。

5. 交付时的表述要分层，不能只报一个数：

```text
镜像实际容量：160041885696 字节（147.7 GiB）
固件可见扇区：297272047
标称容量对算：976762544 扇区
差值：679490497 扇区 ≈ 339.7 GB
处置：本机构无厂商授权，未尝试 SET MAX
```

**结论**

能证明：该盘存在 HPA，**镜像只能覆盖固件可见的 160 GB**，隐藏区数据在本次采集范围内未被获取。判据是扇区数的直接比对：976762544 vs 297272047，差值约 6.8 亿扇区（约 340 GB）。

**不能证明**：隐藏区内是否有数据、隐藏是否由本案嫌疑人实施。HPA 是硬件层可由厂商工具或固件修改的机制，也可能出于容量标识不符的召回原因被设置。

未覆盖范围有四项，报告里必须逐项列出：①隐藏区约 340 GB 未采集；②DCO 未做完整核查（`--dco-read` 需要设备支持，本案型号不支持）；③未判断 HPA 的设置时间——HPA 修改会留下固件日志，但本盘固件区未做转储，时间无从判断；④未验证固件可见容量与标称容量的差值是否恰好等于某个整数分区大小，若相等则更倾向于原厂配置而非人为设置。

第④条是委托方最想知道的答案，也是本次拿不到的。"是不是有人故意藏起来的"这个问题，本案完全没有回答——回答它需要固件层时间证据，而那不在本次采集范围内。

**误判对照**

本案最容易的错判是把 `lsblk` 的 `500G` 当成标称容量的确认，然后据此怀疑"文件系统只分区了 160 GB"。

判据要落到扇区数：`lsblk` 读的是 ATA IDENTIFY 的报告值，而 HPA 恰恰是在这一层之下由固件裁剪的。两者一致只能证明报告值一致，不能证明实际容量。正确判据是 `hdparm -N` 报出的 `Max sectors` 与标称容量对算的扇区数。

三条判据：

①**扇区数算术**。500 GB 标称按 512 字节扇区算是 `500 × 10^9 / 512 = 976562500`，与本盘对算值 `976762544` 同量级；而 `hdparm -N` 报 `297272047`。两个数字不在一个量级上，任何"文件系统只用了 160 GB"的解释都套不上——文件系统的容量上限由块设备大小决定，不可能比设备小出一个 2.3 倍的整倍数。

②`lsblk` 与 `hdparm -N` 读的不是同一层。前者走 sysfs，后者直接下发 `READ NATIVE MAX ADDRESS`（EXT）。本案 `lsblk` 报 500G 而 `hdparm -N` 报 160 GB，两者矛盾——**这个矛盾本身就是 HPA 存在的证据**，而不是需要消解的不一致。

③**`parted` 的磁盘末尾落在哪里**。`parted unit GB print` 报出的磁盘总大小若等于 160 GB，则确认分区工具也无法看到隐藏区；这与①②互为第三方印证。`lsblk`、`hdparm`、`parted` 三个工具来自不同的代码路径，三者一致地把容量定在 160 GB，而只有标称值和 `lsblk` 的显示值说 500 GB。

第③条是复核时最有说服力的一条。前两条都还可能被解释为"某个工具读错了"，而 `parted` 是完全独立的第三方路径，它也只看到 160 GB，就排除了单一工具故障的可能。

按错误判据走的代价是**丢失 340 GB 数据且无任何告警**。镜像文件大小正常、哈希正常、所有检查通过，唯一暴露问题的是文件系统层面容量对不上。如果分析师把它归因于"分区表如此"，这部分数据就永久消失了。

本案的第二层代价是报告表述：初稿写的是"该盘实际容量 160 GB"。这句话在字面上没错，但它会被读成"这块盘就是 160 GB的盘"，而事实是它是一块被裁剪过的 500 GB 盘。改成"标称 500 GB，固件可见 160 GB，差值 339.7 GB 位于 HPA，本次未采集"之后，同一份数据的表述长度只增加了 30 个字，含义却完全不同。

### 5.3 写保护器指示灯亮了就跳过实测验证

**场景**

某次采集前检查中，写保护器的三个 LED 指示灯全亮，操作员据此判定已生效，直接开始 `ddrescue` 读取。事后复核发现该型号写保护器在某些 USB 转接盒上会因供电不足而误报状态。

**指示灯是设备的自我声明，不是外部验证**。而验证成本只有一条 512 字节的写命令。

**处置过程**

对照点在于"相信声明"与"实测确认"的区别：

```bash
# 仅相信设备声明（不够）
lsblk -o NAME,RO,SIZE,MODEL      # RO=1 由设备告知

# 实测确认：主动尝试写入，被拒才算生效
printf 'WP-TEST' | sudo dd of=/dev/sdX bs=512 count=1 conv=notrunc   # 被拒才算实测确认
# 上面的 RO=1 只是设备声明，这一条才是主动写请求的结果。
# 期望输出：Read-only file system
```

**结论**

阴性发现：在使用该转接盒的采集记录中，**无法仅凭指示灯判断写保护是否真正生效**，必须逐盘执行写入测试。未覆盖范围是未做实测的历史采集批次——这些批次是否受影响，需要另行核对设备型号与供电条件。

那批历史采集最后核了一遍，结论比预想的糟：11 个批次中有 4 个用了同型号转接盒，其中 2 个批次的接线照片里能看到该转接盒的型号标识。照片是唯一可用的证据——采集记录里没有任何一处提到转接盒型号，那两个批次到今天仍无法确认写保护是否生效。

这也是本节最实际的教训：采集记录里没有的东西，事后用多少技术手段都补不回来。核对条件很简单，早期批次靠交接现场的照片，中期批次靠设备借用登记，后期批次才有型号字段。

**误判对照**

最像的误判是把 `lsblk` 的 `RO=1` 当作独立验证。

判据要看这个值从哪来：`RO` 字段反映的是内核根据设备报告的可写属性设置的标志位，而写保护器正是那个上报"不可写"的设备——它报错时 `RO` 也会是 1。

所以 `RO=1` 与"指示灯全亮"是**同一条信息的两次显示，不是两个独立来源**。

三条判据：

①`/sys/block/sdX/ro` 是不是自己设的。`cat /sys/block/sdX/ro` 返回 1 有两种来源：设备上报为只读，或此前有人执行过 `blockdev --setro`。本案的干扰项是后者——脚本里有 `blockdev --setro`，于是无论设备端状态如何，这个值都是 1。要区分只能看设备侧，而设备侧没有命令可问。

②**写测试是否返回了拒绝**。`专用可牺牲测试介质上的受控写请求（不得指向原始检材）` 输出 `Read-only file system` 才是确认。这个结果来自内核块层的 `open(O_WRONLY)` 失败路径，与设备声明无关。注意该命令未指定 `seek`，写入位置是第 0 扇区——它能成立的前提是这次写入根本没有发生；一旦写保护实际未生效，被改写的正是磁盘头部。所以这条判据只在写保护已由另一条独立路径确认、或使用可牺牲练习盘时才能执行。

③**写测试的时间戳是否早于采集**。`dd` 的执行时间必须早于 `dcfldd` 的启动时间，且两者都要写进采集记录。晚于采集执行的测试只能证明"此刻是只读的"，证明不了"采集期间是只读的"。

第③条是这条路径最常被忽略的。验证本身是有效的，位置放错了就变成一条无关记录——而且它看上去和有效的那条长得一模一样。采集记录里如果只有一行"已做写保护验证"，不写时间，事后无法判断它验证的是哪个时刻。

还有一个必须一起记的项：写测试的输出原文要保留，不要只写"通过"。`Read-only file system` 与 `Permission denied` 在结论上等价，但后者意味着拦截发生在别处（SELinux、设备权限、`/dev` 是软链到别的节点），两种情况下的写保护可靠性并不相同。

正确判据是**在可牺牲测试介质上**发起写请求、并被内核块层拒绝——这是唯一来自内核块层、不依赖设备声明的确认。原始检材在任何情况下都不得作为写测试的目标：这条判据成立的前提正是那次写入根本没有发生，一旦写保护实际未生效，被破坏的就是磁盘头部。

按错误判据走的代价：一旦某次转接盒失效，原盘在采集全程处于可写状态，而**没有任何工具会报告异常**。采集照样成功，哈希照样一致，破坏已经发生。

这类损失比"采错了"更难补救。采错数据可以重采，写入污染不能撤销——原盘上可能已经被写入了日志、访问时间、或者更糟的东西，而所有已得出的结论都要重新评估它们是否还成立。

### 5.4 工具翻车：`blockdev --setro` 报成功，写保护器却是断开状态

**场景**

一批 2.5" SATA 盘走 PCIe 底板加写保护器接入。采集脚本里写了 `blockdev --setro /dev/sdX`，日志输出 `blockdev: setting device read-only status succeeded`，后续 `dcfldd` 全程无报错，采集正常结束。

复核采集记录时才发现，那次写保护器的阻断开关被误置在 OFF 位。整批 11 块盘都是在可写状态下完成的采集。

这条值得写出来，是因为软件侧的"成功"和硬件侧的"生效"是两件事，而前者看起来非常像后者。

**处置过程**

先厘清 `blockdev --setro` 实际做了什么。它改的是内核里的一个标志位：

```bash
# 手动置只读 —— 输出 succeeded 并不代表硬件通道被挡住
sudo blockdev --setro /dev/sdX
# blockdev: setting device read-only status succeeded

# 解除也只需一条命令
sudo blockdev --setrw /dev/sdX
```

内核块层据此拒绝 `O_WRONLY` 的 `open()`，但它**不向磁盘发送任何硬件指令**。设备端的写命令通道是否真的断开，完全取决于写保护器那一侧。

验证要分两层，两层都不可省：

```bash
# 第一层：软件路径 —— 主动尝试写入，被拒才说明标志位生效
printf 'WP-TEST' | sudo dd of=/dev/sdX bs=512 count=1 conv=notrunc   # 被拒才说明只读标志在写请求上确实生效
# 期望：Read-only file system

# 第二层：物理路径 —— 确认阻断开关在 ON 位，且走的是写保护器而非普通转接线
cat /sys/block/sdX/ro          # 1 = 内核标志位为只读
lsblk -o NAME,RO,TYPE,SIZE,MODEL
```

第二层没有命令能替代。阻断开关位置、机身上 LED 亮灭、实际走线是否经过写保护器，都只能到设备前确认，并在报告里写成**采集记录的一行**，而不是分析阶段的追补说明。

干扰项还是那个：`RO` 来自设备上报，而 5.3 说过写保护器故障时它照样报 1。所以第二层的价值不在 `RO`，在于它把"设备声明"和"硬件拓扑"拆成了两条互不依赖的记录。

**结论**

阳性发现：本批 11 块盘已完成镜像采集并生成 `DigiForensics.dd`，采集过程无读错误，可用于后续分析。

阴性发现：**无法就"采集期间未被写入"作出任何判断**。写保护当时未启用，因此这个问题对本批检材不成立——不是"已证明未被写入"，是不能这样主张。后续分析须按"来源介质可能已被访问"处理，采集时哈希只能表述为"采集时刻的状态"，不能表述为"扣押时刻的状态"。

**误判对照**

最像的误判是拿 `blockdev --setro` 的 `succeeded` 当作写保护已生效的证据。

判据要落在**这条命令的作用域**上：`blockdev --setro` 修改的是内核 `/sys/block/sdX/ro` 标志位，只能拒绝后续的写系统调用；它不发送任何 ATA/SCSI 命令，无法干预设备侧的写通道。而写保护失效的转接盒多数仍会上报"只读"，于是 `RO=1` 和指示灯一样，都属于**声明**，不是验证。

正确判据是那个拒绝结果，且这条 `dd` 必须写在采集记录里、**执行时间早于 `dcfldd` 启动时间**。晚于采集执行的验证只能证明"此刻是只读的"，证明不了"当时是只读的"。

按错误判据走的代价是整批检材的采集合法性存疑。这条问题不会在技术环节暴露——哈希一致、镜像可读、分析顺利，直到质证时对方调出设备照片与接线记录才发现当时接的是普通转接线。此时要补救只能证明"损坏发生在扣押之后"，而这恰恰是无法证明的部分。

<a id="section-36"></a>

### 5.5 反直觉结论：分区表之外那 40 GB「未使用空间」并不空

**场景**

一块 320 GB 硬盘，`hdparm -I` 报 `LBA user addressable sectors: 625142448`，而分区表最后一个分区结束在 285 GB。中间这 40 GB 从分区表看"没有分配给任何分区"，被现场记录写成"未使用空间，无关数据"。

委托方据此要求确认：无关数据是否可以排除。

**处置过程**

先划清"未分配"和"未使用"这两个完全不同的东西：

```bash
# 分区表末尾与磁盘末尾之间的差值
sudo parted /dev/sdX unit GB print free

# 直接取样那段空间，看是否真的空白
sudo dd if=/dev/sdX bs=512 skip=571000000 count=4 status=none | hexdump -C | head
```

`parted` 输出里 `Free space` 段落在最后一个分区之后、磁盘尾部之前。它不属于任何分区，所以文件系统层的元数据不覆盖它——但这只说明**没有分区表去管它**，不等于内容为空。

这段残留通常来自三处：分区删除后未擦除、分区缩容后留在外侧的旧数据、厂商出厂前的分区布局。删除分区改的是分区表条目（MBR 写扇区 1，GPT 写最后一扇区并重建备份表），不是格式化。

判别动作是分段取样，而不是只看开头：

```text
sector 571000000:  连续 0x00                  → 该处空白
sector 571500000:  NTFS 引导扇区 / ext4 superblock 特征 → 旧分区残留
sector 580000000:  连续 0x00                  → 此处空白
```

这个动作顺带回答 HPA 的问题：若 `hdparm -N` 的 `max sectors` 超过 `parted` 看到的磁盘末尾，"未使用空间"的外边界还要再往外推一层（参见 5.1、5.2）。

**结论**

阳性发现：`DigiForensics.dd` 中 285–305 GB 区段检出 NTFS 引导扇区特征，证实为分区删除或缩容后的旧分区残留；305 GB 至磁盘尾部 320 GB 为全零填充，未检出有效数据。

阴性发现：该区段内未检出完整的文件系统元数据副本，无法据此恢复文件名与目录树。残留的是数据区，不是可解析的文件系统。

**误判对照**

最像的误判是"没有分区 = 没有数据 = 可以从检查范围里划掉"。

判据要落在**分区表语义**上：删除分区只移除分区表条目，不触碰数据区。`parted print free` 报出的 `Free space` 含义是"分区表不管理这段"，与"这段是空的"不是一回事。

第二种误判是取样一次就外推整段。判别动作必须把区段首、中、尾各切一段单独验——空白区间在块设备上是分段的、未必连续，开头 4 MB 为 0x00 不能代表后面 36 MB 也是。

按错误判据走的代价是把可能含业务数据的 40 GB 写进"无关区域"直接排除。更现实的后果是报告里出现一句"该盘 285 GB 之后无数据"，复核方只需在这段里翻出一个可识别文件，这句话就成了最容易被抓住的错误——**否定结论的举证责任和阳性结论一样重**。

还有一条次序上的事值得写进采集记录：查 HPA（`hdparm -N`）必须在**上写保护器之前**做，因为它要向设备下发读 IDENTIFY 命令，某些型号会拒绝在只读通道下响应。查完再接写保护器，顺序反了就得整套拆下来重来。

## 六、扩展阅读方向

装备选型的成本常被低估。下面几组按实际会遇到的场景分组。

<a id="section-38"></a>

### 前置基础：没有这两条纪律，装备再贵也白搭

- [取证流程与原则](../fundamentals-process/fundamentals-process-five-stage-forensics-process.md) —— 只读接入在这里被定义为**纪律**而非偏好。本篇 1.1 讲的那个认知偏差（"只读挂载就够了"），本质上是纪律缺失
- [只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md) —— **与本篇构成两道独立防线**。硬件侧挡住写命令，软件侧挡住挂载副作用，两条都断才算失守。`losetup`、loop 设备的只读接入，以及 `atime` 与日志回放的规避在那篇
- [证据保管链与委托证明](../fundamentals-chain/fundamentals-chain-chain-of-custody-and-authorization.md) —— 第三章步骤 1 记录的型号与序列号最终要落到台账里。装备信息不只是"当时用了什么"，它是事后定位责任人与还原操作环境的唯一凭据

<a id="section-39"></a>

### 同层深入：软镜像与镜像制作

- [镜像制作](../../imaging/imaging-acquire/imaging-acquire-disk-imaging-and-evidence-preservation.md) —— 硬件通道打开之后才是它。两遍 `ddrescue` 策略（先 `-n` 逻辑读看坏道分布，再 `-d -r3` 重试失败区）的完整参数在那里，本篇第五章案例演示了它的效果
- [证据文件格式](../fundamentals-chain/fundamentals-chain-dd-e01-aff4-evidence-formats.md) —— 总线条件与介质容量如何反过来影响格式选择。第五章那个 500 GB 盘恢复出 497.4 GB 之后，选择 E01 还是 DD 是个实际问题
- [远程勘验与在线取证](../../imaging/imaging-acquire/imaging-acquire-remote-evidence-collection.md) —— **没有写保护器可用时的一条替代路径**，代价是证据强度下降。本篇 2.4 讲的"唯一例外是镜像已经做好了"就在那个语境里

<a id="section-40"></a>

### 相邻议题：设备形态的差异

- [内部存储与 SharedPreferences](../../mobile/mobile-android/mobile-android-sharedpreferences.md) —— 本篇 2.5 说的"文件系统级提取能拿到已删除内容"，具体拿到的就是这类目录
- [备份与沙盒提取](../../mobile/mobile-ios/mobile-ios-ios-backup-and-sandbox-extraction.md) —— iOS 侧的提取路径。与 Android 的最大差异是 iOS 的备份机制本身就是一种提取通道
- [TWRP 恢复分区取证与物理镜像提取](../../mobile/mobile-android/mobile-android-twrp.md) —— 移动取证箱能力层级的完整实操：**什么时候逻辑提取就够，什么时候必须物理镜像**
- [BitLocker 全卷加密取证](../../crypto/crypto-volume/crypto-volume-bitlocker.md) —— 写保护器解决的是"不写入"，它解决不了"读出来是密文"。**这是硬件与密码学的分界线**，也是 2.5 提到的那条
- [虚拟机仿真](../../imaging/imaging-mount-simulate/imaging-mount-simulate-virtual-machine-emulation.md) —— 仿真环境的隔离配置。**网络隔离与快照策略决定仿真会不会污染证据**

<a id="section-41"></a>

### 判据与反例：装备用错的几种形态

- [取证工件地图](../../computer/computer-persistence/computer-persistence-persistence-artifact-map.md) —— Linux 侧的只读挂载与接入检查。**本篇讲硬件侧，那篇讲接入后的验证**，两者一起才能证明环境没被污染
- [赛事与靶场](../fundamentals-chain/fundamentals-chain-forensics-competitions-and-practice.md) —— **靶场环境几乎不需要写保护器**。这个差异本身是本篇价值的一个注脚：真实检材与练习镜像的处置标准完全不同
- 移动取证与存储介质缺口 —— Android FBE、iOS Data Protection、提取方式与凭证的关系，本库暂无专篇。本篇 2.5 只给了能力层级表与"难点从数据在不在变成能不能解锁"这个判断，具体机制以各平台的官方安全文档为准
- 存储介质缺口 —— SSD 磨损均衡让"物理偏移"失去意义、TRIM 对已删除数据的影响，本库暂无专篇。这一点在做 SSD 镜像时影响很大：不能假设扇区号与逻辑位置对应
- [术语查表](https://www.digiforensics.cn/wiki/digiforensics-glossary)—— `Write Blocker` / `HPA` / `DCO` / `mdrescue` 的定义。HPA 与 DCO 是两套不同的机制但常被混为一谈，术语表里两者是分列的。

## 七、命令速查

```bash
# 环境：Ubuntu/Debian，apt install dcfldd gddrescue hdparm util-linux nvme-cli
# 注意：Debian/Ubuntu 的正确包名是 gddrescue，装完后命令名为 ddrescue

# 1) 识别检材
lsblk -o NAME,SIZE,MODEL,SERIAL,TYPE,MOUNTPOINTS
udevadm info --query=property --name=/dev/sdX | grep -E 'ID_MODEL|ID_SERIAL'

# 2) 确认只读状态（RO 必须为 1）
lsblk -o NAME,RO,RM,SIZE,MODEL

# 3) 写保护验证（应报 Read-only file system）
printf 'WP-TEST' | sudo dd of=/dev/sdX bs=512 count=1 conv=notrunc   # 须换可牺牲练习盘执行，不得指向本行的检材

# 4) 固件信息与隐藏容量
sudo hdparm -I /dev/sdX
sudo hdparm -N /dev/sdX
sudo hdparm --dco-identify /dev/sdX

# 5) 正常介质采集
sudo dcfldd if=/dev/sdX of=DigiForensics.dd \
     hash=md5,sha256 hashlog=DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on

# 6) NVMe 采集与查询
lsblk -d -o NAME,MODEL,SERIAL,SIZE
sudo nvme id-ctrl /dev/nvme0
sudo dcfldd if=/dev/nvme0n1 of=DigiForensics.dd \
     hash=md5,sha256 hashlog=DigiForensics.hashlog bs=4M conv=noerror,sync status=on

# 7) 故障盘：两遍策略
sudo ddrescue -n /dev/sdX DigiForensics.dd DigiForensics.map
ddrescuelog -t DigiForensics.map
sudo ddrescue -d -r3 /dev/sdX DigiForensics.dd DigiForensics.map

# 8) RAID 控制器识别
lspci | grep -i raid
```
