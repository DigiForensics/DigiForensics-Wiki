# 合规授权与法律边界

> 原文链接：[DigiForensics Wiki · 在线阅读](https://www.digiforensics.cn/wiki/fundamentals-practice-legal-authorization-and-boundaries)

<a id="section-1"></a>

## 一、概述

技术失误大多可以补救——镜像采错了重采，参数填错了重跑，时间戳算错了重新换算。越权取证往往不可挽回，而且它的代价不落在技术层面。

一个典型的翻车场景：技术顾问凭委托人的口头同意，用自己的账号登录对方的云盘拉取数据。技术上零失误，数据也真实，但登录行为本身需要另一重授权。这份证据在质证时可能被整体排除，反过来还构成追责依据。

浓缩成一句就是：**技术正确与程序合法缺一不可，但出错的代价不对称**。技术侧的失误总能补救，而程序违法的后果补救不了。这也是授权审查要排在所有技术动作之前的原因。

授权审查的位置在**受理之前**，是流程的第一道关卡，被标为"最关键的一步"的理由很直接：这一步没过去，后面所有技术工作都建立在无依据的行为之上。它与[取证流程与原则](../fundamentals-process/fundamentals-process-five-stage-forensics-process.md)的分工是明确的——流程篇讲阶段划分与不可逆节点，这里讲每个节点开始之前你要确认什么授权。

三类文书的效力来源完全不同：搜查令 / 委托书 / 授权书分别来自公权力、民事关系、本人同意。这个区分决定了你能碰哪些设备。下游最直接的是[证据保管链与委托证明](../fundamentals-chain/fundamentals-chain-chain-of-custody-and-authorization.md)：这里确认你有权做，那篇记录你做了什么，自查表里"保管过程是否连续"一项明确指向它。再往下是数据处理环节：脱敏、销毁、交付限制。

落到具体物件与动作上，边界要由这几样东西承载。

委托书 / 搜查令 / 授权书 / 知情同意书的效力来源互不通用，"不能互相替代，也不能借用"是边界：**委托方不是设备所有人时，你无权处理该设备**。

授权范围的书面界定要到具体粒度。案例里的修订版授权写到了这个粒度：设备 `Dell Latitude SN=XXXX1234`、渠道（企业邮箱 / 企业网盘 / 企业 IM）、时间范围（2024-01-01 至 2024-03-15），以及一条禁止项——不得调取与该员工无关的第三方通讯内容。**"查一下他的电脑"这种措辞不构成客体明确。**

`DigiForensics.dd` 工作副本同样受保护：不能随意复制、外传、放云端。把数据上传到在线自动化分析服务等同于向第三方披露。脱敏后的报告要事先约定规则，案例里客户名单的身份证号、手机号做了处理，**脱敏规则要在合同里事先约定，不是事后补救**。委托关系结束时按约定销毁或返还并留记录，这一步与保管链闭环。

越界请求的处理方式是**书面说明并要求补充授权**，不是先做了再说。案例里那三条独立证据（邮件发送记录、网盘下载记录、IM 对话）之所以站得住，一半是因为它们各自独立，另一半是因为提取时严格守住了"不得调取与该员工无关的第三方通讯内容"这条边界。

能回答的是这些：一份委托书够不够（对照三个要件逐条查）、搜查令 / 委托书 / 授权书能不能互相顶替、哪些技术手段越了线、以及个人信息的五条处理原则怎么落到具体动作。

不解决的是这些：具体某条法规怎么适用——这里讲的是要件框架与风险类型，**不替代法律意见**，具体案件必须咨询具备资质的法律专业人员；技术手段怎么做，边界内的操作步骤在各技术篇里；技术结论对不对，见[取证概念与分类](../fundamentals-concepts/fundamentals-concepts-digital-forensics-concepts.md)里「技术正确与程序合法缺一不可」那个区分；跨机构协作的责任划分，这里讲了原则性要求，具体协议要按项目签。

本篇不需要技术门槛，但需要一点法律常识——至少要知道"授权委托"和"搜查令"不是一回事、知道自己在做什么角色（受托方 / 办案机关 / 数据主体本人）。

更需要的是**把自己放在被追责的位置上想一遍**：如果你今天做的事明天被质疑，你的授权文书能不能支撑？用他人账号登录对方系统、绕过密码或锁屏、超出授权范围"顺手多看"——这三种行为都不需要任何技术门槛就能犯，反过来说，技术门槛再高也拦不住它们。最容易被带进去的其实是"技术顾问以为在帮客户忙"这个心态。

<a id="section-2"></a>

## 二、核心原理

<a id="section-3"></a>

### 2.1 授权的三个基本要件

无论授权文书叫什么名字，**有效授权都要回答三个问题**：

| 要件 | 内容 | 缺失的后果 |
|---|---|---|
| **主体适格** | 谁有权授权？ | 越权委托，全部取证行为无依据 |
| **客体明确** | 针对哪些设备、数据、账号？ | 范围不明，取证范围失控 |
| **意思表示** | 授权是真实、自愿、明确的？ | 事后被主张"不知情/被胁迫" |

**主体适格**的实务判断：

```text
✓ 企业内部调查     → 通常需企业法定代表人或授权负责人出具
✓ 员工个人设备     → 需设备所有人本人授权（不能凭"公司的电脑"就查个人内容）
✓ 客户委托        → 需有书面委托，且委托事项具体
✓ 办案需要        → 需办案机关的正式手续
✗ "公司是我的"    → 不能推导出可以查其中任何一台设备
✗ 口头同意        → 争议时极难证明，且通常不足以支撑大规模取证
```

**客体明确**是最容易被含糊处理的地方。"查一下他的电脑"是不够的，应明确到：

```text
设备型号 + 序列号 + 容量 + 存放地点
或
云账号 + 账号主体 + 时间范围 + 数据类别
```

<a id="section-4"></a>

### 2.2 三类文书的本质区别

| 文书 | 谁出具 | 授权范围 | 适用场景 |
|---|---|---|---|
| **搜查令/扣押手续** | 有管辖权的办案机关 | 特定地点/设备/账户 | 刑事侦查、刑事司法程序 |
| **委托书/委托合同** | 委托人（可能是任何主体） | 委托人自身的财产或权益范围 | 企业事件、商业维权、个人维权 |
| **授权书/知情同意书** | 数据主体本人 | 本人数据 | 自愿配合、双方约定的场景 |

**关键区别在于"权力的来源"**：

- 搜查令的效力来自**公权力**，可以强制执行；
- 委托书的效力来自**民事关系**，只能在你委托范围内的财产上进行；
- 授权书的效力来自**本人同意**，范围最窄。

> ⚠️ **实务要点**：这三种文书不能互相替代，也不能"借用"。

例如，你有委托方的委托书，但委托方不是那台设备的所有人——此时你无权处理该设备。

**技术手段再强，也不能跨越权限边界。**

<a id="section-5"></a>

### 2.3 未经授权取证的刑事风险

未经授权访问他人计算机信息系统，在我国刑法体系中可能被评价为犯罪行为，典型的评价路径涉及"非法侵入计算机信息系统"类犯罪。判断的核心要素包括：

| 要素 | 说明 |
|---|---|
| **客体** | 是否属于"计算机信息系统"（超出单台生活设备的范围可能不同） |
| **主观状态** | 是否明知无权而访问 |
| **后果/情节** | 是否造成数据丢失、影响系统运行、获取敏感信息 |
| **行为方式** | 是否采用技术手段绕过保护措施 |

**特别值得警惕的三种行为**：

```text
1. 用他人账号登录对方系统 —— 即使对方口头说过"你帮我看看"，
   用他人凭证登录仍可能被认定为非法访问
2. 绕过密码/锁屏/加密 —— 破解行为本身可能构成"非法获取"，
   且与后续取证合法性无关地单独评价
3. 超出授权范围"顺手多看" —— 授权查 A 设备却打开了 B 设备，
   这部分证据很可能被整体排除
```

> **专业机构与个人的区别**：受委托开展工作的专业人员，其行为通常被评价为"履行职务"，但这个前提是委托关系真实、授权范围明确、行为在范围内。

这三个前提任一不成立，风险就回到个人身上。

<a id="section-6"></a>

### 2.4 合法边界内的技术手段

**在合法边界内**，取证人员通常可以做的：

| 手段 | 条件 |
|---|---|
| 对已交付的检材做物理/逻辑镜像 | 有有效授权或扣押手续 |
| 对已交付的数据做解析、解密 | 目的是分析检材本身，且有授权 |
| 破解**检材内部**的加密（BitLocker/EFS/数据库密码） | 目的是打开已合法获取的数据 |
| 对已合法获取的凭证做密码恢复 | 属于打开合法获取的检材 |
| 关键字搜索、数据结构解析、时间线重建 | 纯分析行为，风险最低 |

**绝对不能做的**（无论技术多容易）：

| 禁止行为 | 原因 |
|---|---|
| 未经授权访问他人账号/系统 | 可能构成犯罪 |
| 联网"试探"不属于自己的系统 | 属未授权访问 |
| 在非交付的设备上安装取证工具 | 破坏证据 + 侵权 |
| 向目标系统植入后门或留后门 | 明确违法 |
| 把查获的他人数据用于案件外的用途 | 侵犯隐私与个人信息权益 |
| 公开披露案件中的个人信息 | 违反个人信息保护要求 |

<a id="section-7"></a>

### 2.5 个人信息保护要求

取证过程中接触的**几乎全部数据都可能构成个人信息**。

实务中必须把握几点：

```text
1. 最小必要原则 —— 只提取与案件相关的，不要"能拿就全拿"
2. 目的限定     —— 委托目的是"查 A 事项"，就不要扩大为"了解这个人所有情况"
3. 妥善保管     —— 取证副本同样受保护，不能随意复制、外传、放云端
4. 按约定处理   —— 委托关系结束时按约定销毁或返还，并有记录
5. 报告脱敏     —— 报告中出现身份证号、手机号、住址等，通常应做必要处理
```

> **特别提醒**：把查获数据上传到在线的自动化分析服务、云端转换工具，等同于向第三方披露。取证中这属于常见但严重违规的操作。

<a id="section-8"></a>

### 2.6 证据能力与合法性

即使技术工作完全正确，证据能否被采信还取决于程序合法性。实务中需要自查的点：

| 检查项 | 说明 |
|---|---|
| 取得手段是否合法 | 手续是否完备、范围是否匹配 |
| 保管过程是否连续 | 有无断点（见第 07 篇） |
| 鉴定过程是否可复现 | 工具、版本、参数是否留痕 |
| 结论是否有证据支撑 | 不接受无验证的定性 |
| 局限性是否如实说明 | 不能只说成功、不说失败 |
| 是否尊重合法权利 | 如隐私权、辩护权、异议权 |

> **核心理解**：技术正确与程序合法是两条独立的必要条件，缺一不可。区别不在「哪个更重要」，而在**可补救性**——技术失误可以重做，程序违法的后果无法通过技术手段补救。

这正是本文开头的核心判断。

## 三、操作步骤

<a id="section-10"></a>

### 步骤 1：受理前的授权审查（最关键的一步）

```text
审查清单（逐项打勾，缺一不可）

□ 书面文书（有书面的优于口头的）
□ 主体信息：出具人姓名、身份、职务、与检材的关系
□ 主体资格：是否有权代表检材所有者授权
□ 检材清单：型号 + 序列号 + 容量，逐台列明
□ 授权范围：允许做什么（镜像/分析/解密/提取账号数据）
□ 禁止事项：明确不做什么
□ 保密义务：数据如何保管、报告如何处理
□ 期限与销毁：何时返还或销毁
□ 签章：出具人签名/盖章，日期
```

<a id="section-11"></a>

### 步骤 2：把授权范围转化为操作边界

**这一步是很多事故的根源**——授权书写得含糊，执行时就得自己定规则。

```text
授权书：查该公司的服务器
  ✓ 可以：物理镜像、解析、提取日志、分析 WebShell
  ✗ 不可以：访问其他客户的目录、查员工个人电脑、导出无关业务数据

授权书：查手机中的某 App 数据
  ✓ 可以：整镜像、提取该 App 沙盒、解析其数据库
  ✗ 不可以：查看其他 App 隐私内容、读取与案件无关的通讯录
```

> 💡 **实践建议**：**在动手前把边界写成一页纸，双方确认。**这既是保护自己，也是保护证据的采信。

<a id="section-12"></a>

### 步骤 3：过程记录

```text
每个关键节点记录：依据的授权文书编号与页码 / 执行的具体操作 /
                  操作人、复核人 / 时间、地点 / 产出物及其哈希

关键节点：□ 检材接收（核对手续、封条、哈希）  □ 开始采集（依据哪份文书）
          □ 每次分析（做了什么、为什么）      □ 数据提取范围（提取与排除项）
          □ 报告出具（结论与局限）            □ 检材返还/销毁（记录并签字）
```

<a id="section-13"></a>

### 步骤 4：交付与销毁

```text
1. 交付：按约定格式交付报告与证据清单
2. 确认：委托方签字确认收到
3. 返还检材：如有原介质，核对后返还并签字
4. 销毁副本：按约定销毁工作副本与中间文件
5. 留存记录：销毁动作本身要有记录（谁、何时、销毁了什么）
6. 报告归档：按机构规定归档，设定访问权限
```

<a id="section-14"></a>

### 步骤 5：遇到越界请求时的处理

```text
情况：委托人要求顺便查一下设备里"其他的东西"

正确做法：
1. 指出该请求超出授权范围
2. 说明理由（无授权则无权处理）
3. 提供替代方案（申请补充授权 / 缩小范围）
4. 如对方坚持，记录其坚持的过程
5. 仍不补充授权的，不执行

不要：
✗ "顺手帮个忙"
✗ "反正我已经有权限了"
✗ "就看一下，不会有事"
```

## 四、常见陷阱

技术失误可以补救，越权取证往往不可挽回。第二章末尾那句「**技术正确与程序合法缺一不可，但可补救性不同**」是全篇的判据，下面每一条陷阱都是它的反面写法。

★ 标记表示该操作会构成不可逆的权利损害或使证据永久不可采信，执行前必须停下来确认。

<a id="section-16"></a>

### 4.1 授权要件：主体、客体、意思表示

<a id="section-17"></a>

#### 陷阱 1：★ 口头同意就动手取证

**现象**：委托人口头说"你帮我看看他电脑"，技术顾问带着设备就开始镜像，过程顺利、数据拿到，最后报告出了。

**原因**：授权三要件里"意思表示"这一条写的是**授权是真实、自愿、明确的**，缺失的后果是"事后被主张不知情/被胁迫"。而 2.1 的判断表把口头同意直接列入否定项：争议时极难证明，且通常不足以支撑大规模取证。

动手的那一刻一切信号都是正常的——委托人就站在旁边、口头说了、甚至还在催进度。没有任何技术故障会提示你少了什么东西。

"先做起来、后面补手续"这个想法自我说服力很强：反正数据是真的，反正对方是自愿的。

**影响**：**程序违法的后果往往无法通过技术手段补救**（2.6 的核心判断）。质证时对方只需主张"我从未授权"，你手上没有书面依据，整份证据的采信就悬在对方的一句话上。

而且"先做起来"这个动作本身不可撤回——数据一旦被镜像，权利损害已经发生。

**核查**：**涉及设备与账号的必须书面**，受理前按步骤 1 的清单逐项过：

```text
□ 书面文书（有书面的优于口头的）
□ 主体信息：出具人姓名、身份、职务、与检材的关系
□ 主体资格：是否有权代表检材所有者授权
□ 检材清单：型号 + 序列号 + 容量，逐台列明
□ 授权范围：允许做什么（镜像/分析/解密/提取账号数据）
□ 禁止事项：明确不做什么
□ 保密义务：数据如何保管、报告如何处理
□ 期限与销毁：何时返还或销毁
□ 签章：出具人签名/盖章，日期
```

案例第 1、2 步就是这个动作的完整形态：公司出了盖章委托书，但未明确列出设备序列号、授权事项只写"调查资料外传"，服务商拒绝立即动手并要求补充三项。

口头与含糊都过不了这一关。缺项比没有更危险，因为它看起来已经合规。

<a id="section-18"></a>

#### 陷阱 2：把委托人的委托书当成对他人设备的授权

**现象**：委托人交来一份规范的委托书，要求"取证"，于是对现场所有设备逐一采集，包括不是委托方自己所有的那几台。

**原因**：2.2 的实务要点写得很直白：三种文书不能互相替代，也不能"借用"——你有委托方的委托书，但委托方不是那台设备的所有人，此时你无权处理该设备。

委托关系的效力来自民事关系，只能在委托人自身的财产或权益范围内主张。而在 2.1 的主体适格表里，"公司是我的"这一行明确标了否定：不能推导出可以查其中任何一台设备。

公司所有的机器里可能装着外包人员、客户送修机、前任员工留下的私人设备。每一台的所有权状态都不一样。

**影响**：超出授权范围部分"顺手多看"，这部分证据很可能被整体排除（2.3 第三种警惕行为的原文）。

"整体排除"的影响比"少了几份证据"大得多——它可能牵连本来就合规的那部分。

**核查**：把授权范围落到型号、序列号、容量、存放地点四要素上，逐台核验所有权：

```text
设备型号 + 序列号 + 容量 + 存放地点
或
云账号 + 账号主体 + 时间范围 + 数据类别
```

案例第 3 步的补充授权就是这个收敛过程的成品：设备精确到 `Dell Latitude SN=XXXX1234`，渠道精确到"企业邮箱、企业网盘、企业 IM"，时间范围精确到 `2024-01-01 至 2024-03-15`，禁止事项写明"不得调取与该员工无关的第三方通讯内容"。四项缺一，范围就会在执行时自然膨胀。

<a id="section-19"></a>

#### 陷阱 3：授权事项含糊，执行时变成"能看的都看"

**现象**：委托书写的是"查一下他的电脑"，执行时因为"既然已经镜像了，多看几个目录也没什么"，最后报告里塞进了大量与委托事项无关的内容。

**原因**：2.1 已经点明"客体明确是最容易被含糊处理的地方"。

含糊的授权书在受理时看起来是"有文书"，能通过形式审查。步骤 2 说得更直接：授权书写得含糊，执行时就得自己定规则。

而执行时人天然倾向于往"多查一点"的方向定规则——多查的风险延迟出现（质证时），少查的风险立即出现（委托方不满意），现场只有后者的压力。

**影响**：超出授权的数据即使真实，也可能被整体排除，且构成侵权（2.4 禁止行为表把"把查获的他人数据用于案件外的用途"直接列为违规）。

更实际的问题是报告——委托方只要 A 事项，报告却写满了 B 的隐私，而这个报告本身就含不该被扩散的内容。

**核查**：**在动手前把边界写成一页纸，双方确认**（步骤 2 的实践建议原文）。这一步既是保护自己，也是保护证据的采信：

```text
授权书：查该公司的服务器
  ✓ 可以：物理镜像、解析、提取日志、分析 WebShell
  ✗ 不可以：访问其他客户的目录、查员工个人电脑、导出无关业务数据

授权书：查手机中的某 App 数据
  ✓ 可以：整镜像、提取该 App 沙盒、解析其数据库
  ✗ 不可以：查看其他 App 隐私内容、读取与案件无关的通讯录
```

**边界页要双方签字，并作为工作记录的附件。**

案例第 4、5 步的执行痕迹正是边界的体现：未调取同事个人邮箱内容；与同事相关的对话仅在确与本事项相关的范围内引用。

后者尤其关键——"IM 中同期有一段与同事的对话涉及交接"这条发现，因为只用了与本事项相关的部分，所以能作为证据使用。

<a id="section-20"></a>

### 4.2 执行过程中的越界

<a id="section-21"></a>

#### 陷阱 4：★ 用委托人提供的账号登录目标系统

**现象**：委托人说"账号密码我给你，你登上去把数据导出来"，技术顾问用自己的浏览器登录该云盘/业务系统，下载数据后分析。

**原因**：2.3 把这种行为单列为第一种警惕行为：即使对方口头说过"你帮我看看"，用他人凭证登录仍可能被认定为非法访问。

1.1 那个翻车场景就是它——技术上零失误，数据也真实，但登录行为本身需要另一重授权，这份证据在质证时可能被整体排除，甚至反过来构成对顾问的追责依据。

操作过程完全没有技术异常：登录成功、文件下载正常、账号持有人就在旁边。

"他有权限"与"你有权限"是两个不同命题，而人们在这两个命题之间不做区分。

**影响**：**行为定性可能与"运维访问"完全不同**。

委托人是数据的所有人，但顾问不是系统授权用户；而 2.3 提到的评价要素里"是否采用技术手段绕过保护措施"这一项，在借用凭证的场景下很容易被作此解读。

证据资格与个人责任同时暴露。

**核查**：**要账号内的数据，走"数据交付"而不是"账号访问"**：

| 需求 | 合规路径 |
|---|---|
| 需要邮箱/云盘里的数据 | 请数据主体或管理员**导出交付**（2.4："对已交付的数据做解析、解密"，前提是已交付） |
| 需要验证账号下的历史行为 | 取检材后解析本地客户端的缓存/数据库 |
| 必须访问在线系统 | 由有权主体执行访问并留存记录，顾问只接收其交付物 |

```text
委托方：导出 2024-01-01 至 2024-03-15 的邮件 → 交付压缩包 → 顾问只对交付物做哈希与分析
不采用：委托方给出账号密码 → 顾问登录 → 下载
```

报告里要写明数据来源是"交付物"而不是"登录获取"——这两句话在质证时的分量完全不同。

<a id="section-22"></a>

#### 陷阱 5：为取证而绕过密码、锁屏或加密保护

**现象**：为了打开检材，用技术手段绕过锁屏、破解开机密码，或用注入/hook 类方式导出运行时数据，而没有相应手续或记录。

**原因**：**2.4 把两类行为放进了不同的格子**。

破解**检材内部**的加密（BitLocker/EFS/数据库密码）在合法边界内，条件是"目的是打开已合法获取的数据"；而"绕过密码/锁屏/加密"在 2.3 的第二种警惕行为里，理由是破解行为本身可能构成非法获取，且与后续取证合法性无关地单独评价。

这个区分很容易被忽略，因为两者的操作对象在字面上看起来都是同一台设备上的那个加密。

真正的区别不在技术动作，在于这个设备是否已经合法交付给你。

**影响**：**"与后续取证合法性无关地单独评价"**是这一条最重的地方。

即使检材来源完全合法，破解动作本身可能独立产生责任，而这份责任与案件结论无关，纯粹是自己承担的。

**核查**：**先确认检材的合法来源，再区分加密的层次**：

```text
已合法扣押/交付的检材
  ├─ 全卷加密（BitLocker）  → 可在授权范围内处理（2.4 允许）
  ├─ 文件加密（EFS）        → 可在授权范围内处理
  ├─ 登录凭证（域密码/锁屏）→ 属于"绕过保护措施"，需另有手续并全程记录
  └─ 应用内加密/DRM         → 确认是否落入授权范围
```

**处理过程必须留痕**：2.4 允许解密的前提是"目的是分析检材本身，且有授权"，而"过程记录"本身就是这个前提的证明材料。

步骤 3 的记录格式覆盖了它——每个关键节点记录依据的授权文书编号与页码、执行的具体操作、操作人与复核人、时间地点、产出物及其哈希。

<a id="section-23"></a>

#### 陷阱 6：★ 超范围提取，把"能拿就全拿"当作谨慎

**现象**：镜像已经做完，分析时顺手把整个用户目录、全部浏览器历史、全部聊天记录都过了一遍，报告只用了其中一小部分。

**原因**：2.5 的第一、二条是"最小必要原则——只提取与案件相关的，不要能拿就全拿"和"目的限定——委托目的是查 A 事项，就不要扩大为了解这个人所有情况"。

而在已镜像的检材上提取数据的技术成本几乎为零。成本为零的操作不会被任何技术阻力拦住，拦住它的只能是意识。

步骤 3 有一个专门的关键节点叫"数据提取范围（提取与排除项）"——"排除项"这三个字就是针对这个陷阱设计的。它要求的不只是记做了什么，还要求记没做什么。

**影响**：超出授权的数据即使真实，也可能被整体排除，且构成侵权。

而且"排除项"缺失会在两个方向上出事：委托方看到越界内容会质疑整份报告的边界控制；被提取到的一方（员工、客户、第三方）在不知情的情况下其数据被分析过，这本身是一次权利侵害。

**核查**：**提取前写下范围，提取后对照写排除项**：

```bash
# 提取命令本身带上范围参数，而不是先全导出再筛选
icat -o 2048 /work/DigiForensics.dd 44902-256-3 > /evidence/企业邮箱-导出.eml
# 明确单一对象，而不是通配整个用户目录
```

**工作记录里的写法**：

> "**本次数据提取范围**：企业邮箱（2024-01-01 至 2024-03-15）、企业网盘下载记录、企业 IM 同期对话。
> **明确排除**：员工个人邮箱内容、同事个人设备数据、与本员工无关的第三方通讯内容。上述内容未被镜像后访问、未被解析、未在报告中引用。"

案例第 5 步就是这个格式的实例化。

<a id="section-24"></a>

### 4.3 数据处理与保管

<a id="section-25"></a>

#### 陷阱 7：把检材上传在线工具做转换或自动化分析

**现象**：把镜像片段、数据库、文档上传到在线格式转换网站、在线 OCR、在线沙箱分析，拿到结果后继续工作。

**原因**：2.5 的特别提醒写得很直接：把查获数据上传到在线的自动化分析服务、云端转换工具，等同于向第三方披露。

这一步的触发点通常非常合理——"这个格式我的工具打不开""在线转换更快""沙箱能自动跑一遍"。技术理由是真实的，只是它掩盖了行为性质。

上传的往往只是"一小段"或"一个不含敏感信息的样本"，而这个自我判断很难被验证：你无法知道样本里有没有嵌着另一份数据，也无法知道对方服务端的留存策略。

**影响**：**这是一次不可逆的对外披露**。

数据一旦上传就脱离了控制范围，而披露行为一旦发生，权利损害已经完成，后续任何补救都是事后的。

2.4 禁止行为表里"公开披露案件中的个人信息"与"把查获的他人数据用于案件外的用途"两条都在这个方向上。

**核查**：**本地处理，或使用经审查的自有环境**：

```bash
# 格式转换在本地完成
python3 -c "import olefile; print(olefile.OleFileIO('/work/case.xls').listdir())"
soffice --headless --convert-to csv /work/case.xls --outdir /tmp/case-out

# 自动化分析用本地沙箱（隔离网络、快照可回滚）
sudo cp /work/DigiForensics.dd /tmp/analysis-sandbox.dd
```

**如果确实只能依赖外部服务**（如专用解密服务），需要的是**委托方书面知情同意 + 脱敏 + 最小片段**三项同时具备，而不是默认允许。

"经审查的自有环境"是关键词——自建环境经过审查，公共在线服务没有。

<a id="section-26"></a>

#### 陷阱 8：报告里保留了与案件无关的个人信息

**现象**：报告为了"把事情说清楚"，把通讯录完整列出、身份证号原样呈现、聊天记录里涉及第三方隐私的片段全部摘录。

**原因**：2.5 的第五条是"报告脱敏——报告中出现身份证号、手机号、住址等，通常应做必要处理"。

而"说清楚"这个目标会把脱敏推向反面：分析师担心删掉细节会影响可读性或可复核性，倾向于多贴原始内容。

脱敏的代价是可读性，不脱敏的代价是合规性，而当下的感受往往是"不脱敏更好"。

报告还是流转最广的产物——它会被抄送、归档、可能进入案卷。而附件里的原始截图和摘录比正文更容易被忽略脱敏。

**影响**：报告本身就是一份含个人信息的文档，它会按报告的传播范围扩散。

这违反 2.5 的最小必要与目的限定要求，也可能构成 2.4 禁止行为表中"公开披露案件中的个人信息"所指向的问题。

**核查**：**报告也要做最小化**，脱敏与销毁在合同里事先约定（案例第 6 步的结论要点之一）：

> "报告中客户名单的**身份证号、手机号做了脱敏处理**（保留后四位与前三位，中间以 `*` 替代；完整对照表作为独立附件加密保管，仅供委托方按需调阅）。"
> "**脱敏规则**：与案件结论无关的个人信息一律不出现；与结论相关但涉及第三方隐私的，保留事实要素（时间、行为、对象关系）而隐去身份细节。"

**附件与截图单独过一遍脱敏**——正文往往已经改过，附件经常没有。

<a id="section-27"></a>

#### 陷阱 9：事后补记授权依据，或过程记录留下断点

**现象**：先做了取证，事后委托人补了一份授权书；或者过程记录只记了技术操作，没记依据的是哪份文书、哪一页。

**原因**：步骤 3 要求记录"依据的授权文书编号与页码"——这一项在补记时是补不出来的。

授权书可以补签。但"当时依据哪一版、按哪一页执行"是历史事实，事后填写只能靠记忆，**委托人签的字与分析师回忆的内容之间无法建立对应**。

同一批要求里的"操作人、复核人""时间、地点""产出物及其哈希"如果没同步落盘，保管链就出现断点。2.6 自查表里"保管过程是否连续（有无断点）"查的就是这一项。

**影响**：**程序违法的后果往往无法通过技术手段补救**。

补签的授权书在形式上无懈可击，但它无法解释"为什么先做后签"。这个解释缺口会在质证时被反复追问。

保管链断点则更直接——数据从哪一版检材到哪一版检材的链条断了，中间的结论都失去了落点。

**核查**：**记录与操作同步发生，不是事后补**。每个关键节点一次写完：

```text
每个关键节点记录：依据的授权文书编号与页码 / 执行的具体操作 /
                  操作人、复核人 / 时间、地点 / 产出物及其哈希

关键节点：□ 检材接收（核对手续、封条、哈希）  □ 开始采集（依据哪份文书）
          □ 每次分析（做了什么、为什么）      □ 数据提取范围（提取与排除项）
          □ 报告出具（结论与局限）            □ 检材返还/销毁（记录并签字）
```

**开始采集这一行要写清"依据哪份文书"**——它是把授权与数据绑定的唯一一环，写在这里就不可篡改，写在别处就靠不住。

<a id="section-28"></a>

### 4.4 协作与结论边界

<a id="section-29"></a>

#### 陷阱 10：多人协作时不统一边界

**现象**：团队里 A 负责镜像、B 负责分析、C 负责报告，各自有对范围的不同理解；最后是理解最松的那个成员执行了最敏感的操作。

**原因**：2.3 说明了专业人员行为被评价为"履行职务"的前提：委托关系真实、授权范围明确、行为在范围内——这三个前提任一不成立，风险就回到个人身上。

协作场景下，"范围明确"很容易只存在于文档里，不在每个人脑子里。读过授权书的人按它执行，**没读过的人按自己的理解执行，而后者通常更宽**。

这一条单列，是因为**最危险的操作往往由理解最松的人执行**——不是因为谁越权，是因为谁不知道边界在哪。

**影响**：**责任归属变得模糊且往往指向个人**。

个人行为超出范围时，"委托关系真实、范围明确"两个前提都不成立，2.3 说的"风险回到个人身上"就会兑现。团队整体却不知道这个越界发生过，**因为没有人被告知应该汇报什么**。

**核查**：**边界必须逐人确认，不是逐项目确认**：

```text
□ 每个参与分析的人员都阅读并签认授权范围摘要
□ 每人知悉自己的操作边界与"越界如何上报"的路径
□ 每次分析操作记录执行人与所依据的授权文书页码（步骤 3 要求项）
□ 范围变更（如补充授权）通知到全部参与人，并重新签认
```

**案例第 2 步的价值在这里被放大了**：补充授权不只是补齐了文书，**它同时把范围明确到了可执行的程度**——设备序列号、渠道、时间范围、禁止事项四项，任何一个人拿着这四项都能判断自己的操作是否在范围内。

<a id="section-30"></a>

#### 陷阱 11：把"技术上可行"当成"可以做"

**现象**：知道某项技术手段可行，就认为可以做；委托方或内部有人提出"技术上能搞定"，于是当成方案推进。

**原因**：**能力不等于权限，技术越强越要守住边界**。

这是本章与前面所有技术篇的分界处：前面各篇讨论"能不能做到"，本篇讨论"该不该做"，两者不能互相推导。

技术能力带来的自信会直接削弱边界意识。掌握越稀缺的技术，越容易产生"我做的就是别人做不到的事"的自我期许。

而 2.4 之所以列出"无论技术多容易"这个前提，恰恰是因为技术难度不是法律评价的变量。

**影响**：**这是所有合规陷阱的共同上游**。

前面十条陷阱里，口头授权、借用账号、绕过保护、超范围提取、数据外传、报告失当——每一条在发生的瞬间都伴随着一个"技术上可行"的判断。**把这个判断当成许可，等于取消了整个流程。**

**核查**：每个技术方案先过一遍"合法边界内的技术手段"两张表，把方案动作与表中的条目逐条对：

```text
允许侧（2.4）：
  · 对已交付的检材做物理/逻辑镜像 —— 有有效授权或扣押手续
  · 对已交付的数据做解析、解密 —— 目的是分析检材本身，且有授权
  · 破解检材内部加密（BitLocker/EFS/数据库密码）—— 目的是打开已合法获取的数据
  · 对已合法获取的凭证做密码恢复 —— 属于打开合法获取的检材
  · 关键字搜索、数据结构解析、时间线重建 —— 纯分析行为，风险最低

禁止侧（2.4，无论技术多容易）：
  · 未经授权访问他人账号/系统
  · 联网"试探"不属于自己的系统
  · 在非交付的设备上安装取证工具
  · 向目标系统植入后门或留后门
  · 把查获的他人数据用于案件外的用途
  · 公开披露案件中的个人信息
```

**判断规则**：一个技术动作如果**只能靠禁止侧的手段实现**，那它就不是"待评估的方案"，而是"要换目标或换授权"的理由。**换授权比换手段容易得多。**

<a id="section-31"></a>

#### 陷阱 12：阴性发现写成绝对结论，范围不足却未声明

**现象**：报告写"该设备内未发现外传行为的痕迹"，但没有说明检查了哪些数据、用了什么方法、哪些范围没覆盖。

**原因**：2.6 自查表里有一项是"局限性是否如实说明——不能只说成功、不说失败"。

而在云端与企业系统已成为外传主渠道的背景下，**"未发现"这个表述的隐含含义已经与十年前完全不同**。它听起来像"没有外传行为"，实际含义是"在我检查的范围与方法内没找到证据"。

**这两个含义之间的差距就是整个技术方法论的边界**。检查邮件客户端不等于检查了所有 Web 面板，扫未分配空间不等于覆盖了已 TRIM 的块。

**影响**：这是"结论是否有证据支撑"与"局限性是否如实说明"两项同时失守。

委托方读到"未发现外传痕迹"会推断"没有外传"，从而排除调查方向——而这个方向可能在别的渠道上还有材料。

**核查**：**阴性结论必须限定范围、列出未覆盖对象**：

> "**本次检查范围**：镜像 `DigiForensics.dd`（Dell Latitude SN=XXXX1234）内已分配区的企业邮箱客户端数据、企业网盘同步客户端数据库、企业 IM 本地缓存。
> **检查方法**：关键字检索 + 时间线比对，时间窗 2024-01-01 至 2024-03-15。
> **未覆盖范围**：① 已在服务端删除并同步清除的本地副本；② 未安装客户端的 Web 端操作；③ 已 TRIM 的 SSD 块；④ 未分配空间中碎片化的残留内容；⑤ 委托授权未覆盖的个人渠道。
> 本结论不表明该设备内不存在外传行为，仅表明上述范围内的检查未发现相关痕迹。"

## 五、案例示例

<a id="section-33"></a>

### 5.1 盖章委托书缺少设备序列号：拒绝动手而非先干后补

**场景**

某公司 IT 部门怀疑离职员工在离职前删除了客户资料并外传，希望 IT 服务商协助调查。委托方给了盖章委托书，但授权要素有缺口。委托方的问题是"能不能快点查"。

盖章不等于授权完备。要素缺失时先动手，风险要到流程结束之后才显现，那时已经无法回退。

**处置过程**

1. 审查授权要素，逐项核对发现两处缺口：**未列出设备序列号**，且**授权事项只写"调查资料外传"**，未界定渠道与时间范围。

2. 拒绝立即动手，出具书面补充要求：

```text
需补充三项：
  1. 具体设备序列号（用于与实际扣押物逐一对应）
  2. 渠道范围：是否包含邮件、云盘、IM
  3. "资料外传"的时间范围起止
```

3. 补充授权后执行，范围收敛为可逐条对照的文本：

```text
设备：Dell Latitude SN=XXXX1234
渠道：企业邮箱、企业网盘、企业 IM
时间范围：2024-01-01 至 2024-03-15
禁止：不得调取与该员工无关的第三方通讯内容
```

4. 采集前把 `SN=XXXX1234` 与实物的 `SN` 字段比对一致，才开始物理镜像。

**结论**

能证明：本次全部操作均在书面授权的四要素（设备、渠道、时间范围、禁止项）之内，设备对应关系有据可查。

**补充授权这一步同时保护了委托方与服务商**——它把"查了什么"在动手之前就固定下来，事后无法争议。

**不能证明**：设备之外是否有其他载体（如个人手机、私人云账号）承载了外传行为，授权未覆盖即不在本次结论范围内。

**误判对照**

最像的误判是"先采完再补授权，反正数据在自己手里"。

判据要落在时间顺序上：补充授权的效力在于它划定边界，而边界必须在动手前划定。事后补的授权只能证明"我们最终取得了同意"，不能证明"采集时已经有了同意"——这两者在法律上不是一回事。

正确做法是**收到齐备授权再开机、接写保护器**。

按错误判据走的代价：一旦原委托方事后反悔（内部有人主张调查越权），服务商手上只有一份日期靠后的授权，无法自证采集时合规，整批数据可能面临销毁要求。而此时镜像里已经装满了未授权取得的通讯内容。

<a id="section-34"></a>

### 5.2 三条独立证据的边界：37 封邮件不等于本人操作

**场景**

修订版授权执行后，镜像中发现离职前一周该员工向个人邮箱发送了 37 封含客户名单的邮件，个人网盘有 2 个大批量下载记录，IM 中同期有一段与同事的对话涉及"交接"。委托方的问题是"能认定是他本人干的吗"。

**三条证据同向，仍然不等于完成了人机对应**。这是内部调查最容易滑过去的定性跳跃。

**处置过程**

1. 三条证据分别定位到独立工件，逐一确认载体与时间：

```text
证据 1  Outlook 本地缓存 + 服务器发送日志：37 封，收件人为个人邮箱
证据 2  企业网盘客户端日志：2 次批量下载（清单 4.7 万行）
证据 3  企业 IM 本地记录：与同事对话涉及"交接"，无附件传输记录
```

2. 刻意核对"不是本人"的可能性来源：企业邮箱与 IM 均为域账号，通常存在会话共享或委托访问配置。

3. 报告中把"账号被使用"与"人操作"分开表述，并对第三份设备做归属核实（该设备是否一直由该员工独占使用）。

**结论**

能证明：离职前一周内，该员工账号被用于向个人邮箱发送 37 封含客户名单的邮件，个人网盘账号有 2 次批量下载，企业 IM 中存在涉及交接的对话。三条证据来自**三个独立工件**，同向。

**不能证明**：上述行为的实际操作人是该员工本人。报告结论应表述为「该员工账号在离职前一周内被用于……」并列出未排除的可能：账号共享、委托访问、凭据泄露。委托方要的是"人"的结论，这需要独立的物证或人的证言，不能由账号日志单独推出。

**误判对照**

最容易的误判是把这三条写成"离职员工删除并外传了客户资料"。

判据落在工件性质上：Outlook 本地缓存记录的是"这个 profile 下的会话做了什么"，不记录"是谁敲的键盘"。而域账号在 Outlook 中启用共享邮箱或多账号切换是常见配置。判据还应加上反向检查——是否存在共享配置或他人代为登录的迹象。

正确表述是"账号行为"而非"个人行为"，并在报告中附上人机对应的建议路径。

按错误判据走的代价：内部调查直接形成书面结论后被劳动仲裁采信，而对方只需提交一条"该账号当时被多人共用"的证据，整份报告的处理结论全部推翻。委托方此时已据此做出了处分决定。

<a id="section-35"></a>

### 5.3 报告脱敏与工作副本销毁：写进合同而非事后补救

**场景**

同一案件的交付环节，报告中直接引用了客户名单原文，包含身份证号与手机号；同时分析工作站上留有完整的 37 封邮件副本。委托方的合规部门在交付前提出要求处理。

这条路径单列，是因为它检验的是**数据最小化原则有没有在开工前就写进合同**。

**处置过程**

1. 报告脱敏，保留可核验性而不保留可识别性：

```text
客户名单附件：身份证号保留前 6 后 0，手机号保留前 3 后 0
原始值与脱敏值的对照表：不随报告交付，单独封存于案卷
```

2. 边界内处理第三方内容：未调取同事个人邮箱内容；IM 中涉及同事的对话仅在确与本事项相关的范围内引用，且不做身份延伸分析。

3. 工作副本按合同约定销毁并出具销毁记录：

```text
销毁范围：分析工作站 /case/DigiForensics.dd 及全部衍生副本
销毁方式：文件级安全擦除，非普通删除
见证人：    委托方合规专员 + 服务商项目经理，双人签字
```

**结论**

能证明：交付给委托方的报告不含完整个人标识信息；工作副本已按约定销毁并有双人见证记录。第三方通讯内容未被超出必要范围地调取与引用。

**不能证明**：销毁过程无法自证后未从备份系统恢复——若服务商有自动备份或磁盘快照策略，需要一并纳入销毁范围并在报告中说明。

**误判对照**

最像的误判是把删除报告里的身份证号当成完成了脱敏。

判据要落在"可关联性"上：保留前 6 位、同时全文引用同一份名单，剩下的 4 位与姓名、订单号组合起来仍能唯一定位到具体自然人。脱敏后的数据仍具可识别性。

正确判据是**保留分析所需的最小片段**。本案真正需要证明的是"外传了客户资料"，那么证明"文件行数 4.7 万、字段结构为客户资料模板"就够了，无需携带任何可定位到个人的字段值。

按错误判据走的代价：这份报告本身成为一起新的个人信息泄露事件来源——服务商在处理员工泄密案的同时制造了泄露事故。

本篇以流程与合规为主，以下为"合规前提下"的操作清单模板，
供实际操作时逐项确认留痕。所有命令均须在有效授权范围内使用。
