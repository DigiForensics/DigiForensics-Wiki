# 五阶段流程与基本原则

<a id="section-1"></a>

## 一、概述

电子证据有一个物理世界证据没有的性质：单向衰变。一旦被改写就无法还原，一旦被污染就无法自证。硬盘上的一个扇区被覆盖，原内容不在任何备份里；一份台账漏记一段时间，那段时间的状态永远说不清。

所以保全、采集、检验、分析、报告这五个阶段必须分开，每个阶段回答一个不同的问题：东西在不在原样？能不能完整复制？里面有什么？这些说明什么？怎么让别人相信？阶段划分不是为了流程好看，是为了在每个不可逆节点之前设置验证关卡。

关键在于关卡的前置性质：前一阶段的产出不合格，绝不能进入下一阶段。这句话听起来像常识，实际上是取证实践中最常见的失败模式——采集时没接写保护器，但后面四个阶段照样做完了，只是结论在质证时整体失效。

这套五阶段划分本身构成工作流，它定义所有环节的边界。它是[取证概念与分类](../fundamentals-concepts/fundamentals-concepts-digital-forensics-concepts.md)的展开：那篇说为什么要分阶段，这里说每个阶段做什么、什么算合格。也是[取证技能树](fundamentals-process-forensics-learning-path.md)的骨架——技能树按能力层次组织学习顺序，流程按阶段组织工作顺序，两者交叉起来才是完整的实践路径。

上游是合规约束：[合规授权与法律边界](../fundamentals-practice/fundamentals-practice-legal-authorization-and-boundaries.md)决定你从哪个阶段开始有权工作。没有授权，连保全都不成立。下游是三个具体的执行入口——保全与采集进[镜像制作](../../imaging/imaging-acquire/imaging-acquire-disk-imaging-and-evidence-preservation.md)，检验与分析进[文件系统取证总览](../../filesystem/filesystem-ntfs/filesystem-ntfs-filesystem-forensics-overview.md)，报告阶段的局限性表述则贯穿所有技术篇的第四章。

各阶段的产出物形态有各自的落点。

案件工作目录是后面所有记录的落点，**产物分类放置本身就是可追溯性的物理基础**。现场状态照片、封条与序列号登记是保全阶段的产物，案例里设备到所时是关机状态，这个记录决定了后面"无法提取内存中可能残留的会话信息"这条局限怎么写。

`DigiForensics.dd` 与 `DigiForensics.hashlog` 是采集阶段产物，用 `dcfldd hash=md5,sha256 hashlog=...` 一次完成。哈希必须**边读边算**，因为先读完再回头算哈希覆盖的就不是同一批字节了。

检验阶段的产物是提取出的 `$MFT` / Prefetch / hive / UserAssist。操作日志与工具版本记录覆盖全流程，**这是可追溯性的唯一载体**，也最容易被忽视、最容易被击穿。复核者按同一 SOP 重跑的记录是可重复性的实证形式。`DigiForensics.hashlog` 与 `DigiForensics.dd` 是同一次读操作的两个产物。

能回答的是这些：五个阶段各自的退出条件是什么、采集阶段为什么是"复制"而不是"分析"（三层理由：技术层怕工具 bug、流程层要并行、法律层只需证明副本等于原件）、McCée 原则与黄金规则分别管什么、以及真实性 / 完整性 / 可追溯性三者中哪一个最容易被击穿（可追溯性）。

不解决的是这些：每个阶段具体怎么操作，这里给的是关卡与判据，执行细节在各技术篇；三套原则在具体场景里怎么权衡，例如"若必须动原始数据"与取证效率冲突时怎么办；可重复性的技术实现，自动化程度越高越容易满足这个要求，具体工具选型在各技术篇的第七章；流程合法性的法律依据，见[合规授权与法律边界](../fundamentals-practice/fundamentals-practice-legal-authorization-and-boundaries.md)。

前提是先理解[取证概念与分类](../fundamentals-concepts/fundamentals-concepts-digital-forensics-concepts.md)里"取证与数据恢复不是一回事"那个区分。数据恢复允许反复试错，取证不允许，两者共用同一批命令但正确用法相反。

另外建议完整做过一次真实采集再回头看这套流程。亲手接过写保护器、看着 `dcfldd` 跑完几小时之后，每个"必须"都有对应的具体动作；

## 二、核心原理

<a id="section-3"></a>

### 2.1 五阶段与各自的关卡

| 阶段 | 核心问题 | 关键动作 | 产出物 | 退出条件（验证） |
|---|---|---|---|---|
| **1. 保全 Preservation** | 东西还在不在原样？ | 记录状态、封装、防篡改 | 状态照片、封条编号、保管记录 | 封条编号与委托书一致、状态已留证 |
| **2. 采集 Acquisition** | 能否完整复制？ | 写保护接入、制作镜像、算哈希 | `DigiForensics.dd`、哈希日志 | **源介质哈希 == 镜像哈希** |
| **3. 检验 Examination** | 里面有什么？ | 恢复、提取、筛选、去噪 | 文件清单、关键字命中、解密结果 | 提取物可被独立打开读取 |
| **4. 分析 Analysis** | 这说明什么？ | 关联、推理、构建时间线 | 时间线、行为重建、结论 | 每条结论有第二条独立证据 |
| **5. 报告 Reporting** | 怎么让人相信？ | 撰写、复核、交接 | 鉴定意见书/分析报告 | 复核人签字、无内部矛盾 |

> **阶段不可跳跃，但可迭代**。分析阶段发现需要新数据，回到检验阶段重新提取是正常的；但回到采集阶段重做镜像，通常意味着第一次采集出了问题。

<a id="section-4"></a>

### 2.2 采集阶段的核心：为什么是"复制"而不是"分析"

采集的产物是副本，原始介质在整个流程中始终只读。理由有三层。

```
第 1 层  技术层：分析工具可能有 bug，写入目标会让证据失真
第 2 层  流程层：多个分析员需要并行工作同一份数据
第 3 层  法律层：法庭上只需证明"副本 = 原件"，而非"分析未影响原件"
```

这也解释了为什么哈希校验必须在采集时同步完成——只有"边读边算"才能保证哈希覆盖的是刚读出的那批字节。若先读完再回头算，中间若有写入，哈希就对不上了。

<a id="section-5"></a>

### 2.3 McCée 原则（数字取证的基本原则）

| # | 原则 | 含义 | 在流程中的落点 |
|---|---|---|---|
| 1 | **不改变原始数据** | 任何操作都不得修改原介质 | 写保护器、只读挂载 |
| 2 | **记录所有过程** | 每个步骤、参数、时间都要留痕 | 操作日志、命令历史 |
| 3 | **可重复性** | 另一名合格人员用相同方法应得到相同结果 | SOP 文档、工具版本记录 |
| 4 | **用哈希验证** | 用数学方法证明数据未被改变 | 采集前后双哈希 |

第 3 条是最难落实也最容易被质疑的。"可重复"不等于"结果相同"——自动化程度越高、工具越明确，可重复性越强。手工用十六进制编辑器翻找的结论，很难通过可重复性审查。

四条原则各有一个可以当场检查的落点：第 1 条看挂载点是否 `ro`、采集命令是否只有读通道；第 2 条看操作日志能否还原出"谁在什么时候跑了什么参数"；第 3 条看复核者拿到工具名、版本号、命令行后能否跑出同一结果；第 4 条看 H0 与 H1 是否都留了值。

只做对前三条而漏掉第四条的情况很常见：流程记录很完整，但没有数学证据支撑"数据没变过"，质证时仍然会被追问。

<a id="section-6"></a>

### 2.4 取证黄金规则（Golden Rules）

这组规则偏向"防错"，与 McCée 的"做对"互补：

| 规则 | 说明 |
|---|---|
| **绝不动原始数据** | 任何写入都可能毁灭证据 |
| **若必须动，先想清楚** | 确实需要访问原件时，必须能解释每一步和后果 |
| **全程留痕** | 每一次交接、每一次操作都要能被第三方复现 |
| **由负责人负全责** | 流程合规性由主办人负责，不能有"我以为是同事弄的" |

<a id="section-7"></a>

### 2.5 三大属性：真实性、完整性、可追溯性

这是评价一份电子数据是否"合格"的三个维度：

| 属性 | 含义 | 如何证明 |
|---|---|---|
| **真实性 Authenticity** | 数据确实来自所述来源，未被伪造 | 元数据链、设备绑定、多源印证 |
| **完整性 Integrity** | 数据采集后未被改变 | 哈希校验链（源→镜像→分析后） |
| **可追溯性 Traceability** | 每一步操作都有记录，可被第三方复核 | 保管链文档、操作日志、工具版本 |

> **实务判断**：三者中**可追溯性最容易被忽视，也最容易在质证时被击穿**。哈希只能证明"没变过"，不能证明"没动过手脚"——后者要靠保管链和过程记录。

## 三、操作步骤

<a id="section-9"></a>

### 步骤 1：建立案件工作目录

```bash
# 目录结构固定，避免后续混乱
mkdir -p /case/2024-DG-001/{01_photo,02_acquire,03_examine,04_analysis,05_report}
cd /case/2024-DG-001

# 创建证据登记簿（哈希日志最终落在这里）
printf '%s\
' \
  "案件编号: 2024-DG-001" \
  "检材名称: DigiForensics.dd" \
  "采集时间: <填写>" \
  "采集人: <填写>" > 02_acquire/case.log
```

<a id="section-10"></a>

### 步骤 2：保全（记录状态，固定边界）

```bash
# 1) 核对检材标识
lsblk -o NAME,SIZE,MODEL,SERIAL,TYPE,MOUNTPOINTS

# 2) 确认未挂载——挂载过的分区可能被写入
findmnt | grep -E 'sd[a-z]'

# 3) 记录设备固件层可见容量（应对 HPA/DCO 隐藏容量）
sudo hdparm -I /dev/sdX | head -30
sudo hdparm -N /dev/sdX
```

拍照是必须的：外包装、封条、接口、开机指示灯、屏幕状态。

<a id="section-11"></a>

### 步骤 3：采集（写保护 + 镜像 + 哈希）

```bash
# 硬件写保护器串接后，读取源盘
sudo dcfldd if=/dev/sdX of=02_acquire/DigiForensics.dd \
     hash=md5,sha256 hashlog=02_acquire/DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on

# 独立复算，确认与采集时一致
sha256sum 02_acquire/DigiForensics.dd

# 失败盘改用 ddrescue（详见板块 2）
sudo ddrescue -n /dev/sdX 02_acquire/DigiForensics.dd 02_acquire/DigiForensics.map
sudo ddrescue -d -r3 /dev/sdX 02_acquire/DigiForensics.dd 02_acquire/DigiForensics.map
```

<a id="section-12"></a>

### 步骤 4：检验（先定范围，再动提取）

```text
第 1 步 全局摸底：分区、卷、文件总数、最早/最晚时间
第 2 步 建立基线：确认"正常"是什么样（软件清单、常用账号）
第 3 步 关键字收敛：按案件假设搜索
第 4 步 重点对象深挖：命中文件的元数据、关联对象、时间上下文
```

```bash
# 建立整体时间范围（判断是否需要外部时间基准）
fdisk -l 02_acquire/DigiForensics.dd
```

<a id="section-13"></a>

### 步骤 5：分析（每条结论配一条验证）

以"某文件在案发时间被打开"为例，验证不能只有一条：

```text
证据 1：NTFS 的 $LogFile 中存在对应 MFT 记录修改
证据 2：该文件的 Prefetch/Amcache 有执行痕迹
证据 3：紧邻时段的前后文件访问记录与之吻合
→ 三条独立证据互相印证，结论成立
```

<a id="section-14"></a>

### 步骤 6：报告（让不懂技术的人能读懂）

```text
结构建议：
1  基本情况（检材、委托、检材状态）
2  检验过程（工具、版本、参数、哈希核对结果）
3  检验结果（发现了什么，在什么位置）
4  分析意见（这些发现意味着什么，推理链条）
5  局限性（未能检验的部分、客观限制）
```

**局限性章节是加分项，不是减分项。** 明确写出"因设备处于锁屏状态，未能提取 X 数据"，比隐瞒后被对方发现要好得多。

## 四、常见陷阱

流程类失误有一个共同特征：它们大多发生在"看起来在推进工作"的地方。跳阶段、先分析后校验、边采集边分析——每一种都让人感觉更高效，代价却落在流程的可辩护性上。

2.1 那句话是全篇的基准：前一阶段的产出不合格，绝不能进入下一阶段。本章按阶段边界、采集细节、结论与可追溯性四组展开。

★ 标记表示该操作会造成不可逆的检材改变或证据效力损失，执行前必须停下来确认。

<a id="section-16"></a>

### 4.1 阶段边界

<a id="section-17"></a>

#### 陷阱 1：★ 边采集边分析

**现象**：一边跑 `dcfldd` 采集，同时在另一台机器或同一个源设备上打开分析工具看数据；或者干脆用挂载点当工作目录，采集还在跑就开始翻文件。

**原因**：2.2 讲清了采集产物是副本、原始介质全程只读的三层理由，其中第一层就是"分析工具可能有 bug，写入目标会让证据失真"。

而"边采边看"的吸引力非常具体——你不用等几小时的采集时间就能开始判断方向，这在项目紧张时显得很务实。但它把一个已验证的流程换成了一个未验证的：写保护器此时承受的不只是读命令，还有另一条通路上的访问。

2.4 的黄金规则第一条是"绝不动原始数据"。这里的"动"包括"别人可能在动"。

**影响**：两难境地的核心是证据效力，不是效率。

如果另一路操作写入了任何内容，源介质哈希与镜像哈希就不再匹配，而这个不匹配无法事后解释——你不知道是被分析工具写的，还是被系统自动日志写的。而 2.1 把"源介质哈希 == 镜像哈希"定为采集阶段的退出条件，条件不满足就没有进入下一阶段的资格。

**核查**：采集完成前不做任何分析，且分析永远在副本上进行：

```bash
# 采集期间：本机只做采集，不打开任何分析工具
sudo dcfldd if=/dev/sdX of=02_acquire/DigiForensics.dd \
     hash=md5,sha256 hashlog=02_acquire/DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on

# 采集完成并通过退出条件后：复制工作副本，所有分析在副本上做
sha256sum 02_acquire/DigiForensics.dd
cp --reflink=auto 02_acquire/DigiForensics.dd 04_analysis/DigiForensics-work.dd
sha256sum 04_analysis/DigiForensics-work.dd
```

等待时间可以用于非技术工作：核对委托书、整理检验假设、准备关键字表。这些都不触碰检材。

"等采集"不是流程浪费，是关卡在起作用。

<a id="section-18"></a>

#### 陷阱 2：采集完先分析，校验留到最后

**现象**：镜像做好后直接开始分析，等报告要写了才想起来算哈希，或者只对最终用到的几个文件算哈希。

**原因**：2.2 最后一句是这一条的全部依据——哈希校验必须在采集时同步完成。只有边读边算才能保证哈希覆盖的是刚读出的那批字节；若先读完再回头算，中间若有写入，哈希就对不上了。

这个理由常被忽略，因为"回头算"在多数情况下能得到一个哈希值，而这个值看起来和边算的没有区别。同时"分析完再算"有一种朴素的合理性：反正最终要算一次，顺手就做了。

**影响**：事后哈希无法证明采集时的状态。

它证明的是"现在这个文件没变"，而你需要证明的是"采集时读出来的就是源介质的内容"——这两个命题之间隔着一段无人监督的时间窗口。2.5 把它说得很直接：哈希只能证明"没变过"，不能证明"没动过手脚"。

**核查**：采集时同步算，之后独立复算，两次结果都要留档：

```bash
# ① 采集时：dcfldd 的 hashlog（边读边算）
sudo dcfldd if=/dev/sdX of=02_acquire/DigiForensics.dd \
     hash=md5,sha256 hashlog=02_acquire/DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on

# ② 采集后立即独立复算，与 hashlog 比对
sha256sum 02_acquire/DigiForensics.dd
diff <(awk '{print $1}' 02_acquire/DigiForensics.hashlog | grep -i sha256) \
     <(sha256sum 02_acquire/DigiForensics.dd | awk '{print $1}')
# 无输出 = 一致
```

三次哈希构成 2.5 说的"哈希校验链"：源介质 → 镜像（采集时）→ 分析后。少任何一环，完整性论证就不完整。

<a id="section-19"></a>

#### 陷阱 3：★ 用 `conv=notrunc` 续写，污染镜像

**现象**：目标路径已有一个上次采的 `DigiForensics.dd`，直接用同名路径重采；或者采集到一半中断，重跑时用了 `conv=notrunc` 想接着写。

**原因**：`conv=notrunc` 的语义是"不截断目标文件"——它不会清空原有内容，而是从头覆盖。如果新数据比旧数据短，尾部旧数据就留了下来，形成一份前半新、后半旧的文件。

而文件大小看起来正常、哈希也能算、所有工具都能打开，没有任何一个环节会报错。

真正的问题是这条命令的使用场景很容易理解错：有人以为 `notrunc` 是"断点续传"，实际上是"保留原内容"。

**影响**：一份混合了两次采集内容的镜像，且它的哈希是"正确"的——因为哈希对应的就是这份混合文件。

它会在整个流程里一路通过校验，直到某次分析发现数据自相矛盾，而那时已经很难定位到原因了。2.4 的黄金规则第二条"若必须动，先想清楚"针对的正是这类操作。

**核查**：采集前确认目标路径为空或全新：

```bash
# 采集前检查
ls -l 02_acquire/DigiForensics.dd 2>/dev/null && echo "[-] 目标已存在，改名或删除后再采"

# 断点续采交给 ddrescue 的 mapfile 机制，不靠 notrunc
sudo ddrescue -n /dev/sdX 02_acquire/DigiForensics.dd 02_acquire/DigiForensics.map
sudo ddrescue -d -r3 /dev/sdX 02_acquire/DigiForensics.dd 02_acquire/DigiForensics.map
```

需要保留旧镜像时改名归档，不要覆盖。而且改名要带采集时间与操作人，否则过一段时间就分不清哪个是本次的。

<a id="section-20"></a>

### 4.2 检验与分析阶段

<a id="section-21"></a>

#### 陷阱 4：发现可疑文件就写成"发现"，不做背景排除

**现象**：从镜像里看到一个可疑的可执行文件或脚本，报告直接写"发现恶意程序"。

**原因**：2.1 的检验阶段核心问题是"里面有什么"，而不是"这说明什么"。把两者混同，就会跳过第 2 步"建立基线：确认正常是什么样（软件清单、常用账号）"。

一个 `7z.exe` 出现在用户目录里，在没有软件清单的情况下无法判断它是工具、是攻击者放的、还是系统组件的副本。

可疑性来自预期。而预期一旦先形成，所有后续观察都会被往那个方向解释。

**影响**：结论层级跨越。从"有一个文件"跳到"有恶意行为"，中间需要有归属、时序、意图三个维度的证据，而文件的存在只回答了第一个。

案例第 4 步的三条证据结构正是这个跨越的完整形态：Prefetch 有执行痕迹（有过运行）、注册表有 InstallDate 与 InstallLocation（是安装的）、UserAssist 有执行计数且归在具体账户下（谁用的）。

三条各自回答一个维度，缺一条结论就不完整。

**核查**：按四步顺序走，先基线后关键字（步骤 4 的顺序不能颠倒）：

```text
第 1 步 全局摸底：分区、卷、文件总数、最早/最晚时间
第 2 步 建立基线：确认"正常"是什么样（软件清单、常用账号）
第 3 步 关键字收敛：按案件假设搜索
第 4 步 重点对象深挖：命中文件的元数据、关联对象、时间上下文
```

```bash
# 第 1 步：先建立整体时间范围（判断是否需要外部时间基准）
fdisk -l 02_acquire/DigiForensics.dd
```

判断一个文件是否值得深挖，至少要回答三个问题：它是不是系统/软件自带的（比对基线）、它有没有被运行过（Prefetch/UserAssist/LNK）、它与案件假设的时间窗口是否吻合。

三个都答不上来的文件，只能写"存在"，不能写"发现"。

<a id="section-22"></a>

#### 陷阱 5：多条假设同时追，每条都不深入

**现象**：同时开十几个调查方向——远控木马、WebShell、横向移动、内部邮件外传——每个都搜了几个关键字，然后每个都写一段"未发现明显证据"。

**原因**：分析阶段的退出条件是"每条结论有第二条独立证据"（2.1），这个标准本身就需要深度。而并行追多个假设时，每个假设能分到的注意力只是"搜了几个关键字"——这在方法上等价于没有检验。

多假设并行的自我理由是"避免过早收敛"，而实际上未经检验的假设不构成收敛，只是分散。

**影响**：十个"未发现"凑成一份看起来很全面的报告，而实际上没有任何一个方向被真正检验过。

这种报告的隐蔽性在于它不像"没做"，而像"做了很多"。而且委托方会合理地推断"你们查了这么多方向都没发现"，从而排除那些实际未被检验的方向。

**核查**：锁定优先级，逐个证伪或坐实。优先级的排法不是按"哪个方向最像"，而是按可检验性 + 影响面：

```text
优先级 1：最可能且影响最大的（直接回答委托问题）
优先级 2：能独立验证的（有明确工件，如安装记录、登录记录）
优先级 3：依赖其他结论成立的（放在后面）

每个假设走完一条完整路径：假设 → 可检验工件 → 检验结果 → 结论
走完再开下一个，不要在同一步骤上并行多个假设的零散搜索
```

"未发现"的假设也要写完检验路径。写"检查了 `<工件>` 的 `<位置>`，未发现 `<特征>`"才是合格表述，而"未发现明显证据"不是。

<a id="section-23"></a>

#### 陷阱 6：报告只有结论没有过程

**现象**：报告写"经检验，该设备安装并运行过远控软件"，过程部分只有一句"使用 XXX 工具进行分析"。

**原因**：2.5 的可追溯性是三者中最容易被忽视、也最容易在质证时被击穿的。

而"工具名"这个颗粒度满足不了 McCée 第 3 条（可重复性）。另一名合格人员用相同方法应得到相同结果，这需要的不只是工具，还需要参数、位置、判读标准。

而报告写成结论的样子，恰恰因为结论读起来更像成果：过程是繁琐的、结论是清晰的、委托方通常只关心后者。

**影响**：被质疑时无法自证。

对方问"你怎么确定这个 Prefetch 条目对应那个程序""这个时间戳用的什么时区""你说的第二条独立证据是什么"——这三类问题用"经检验"四个字都答不上来。而过程细节（工具、参数、偏移）恰恰是报告的骨架：没有它，结论在质证时是悬空的。

**核查**：报告结构里过程与结论同级，参数与偏移必须具体：

```text
结构建议：
1  基本情况（检材、委托、检材状态）
2  检验过程（工具、版本、参数、哈希核对结果）
3  检验结果（发现了什么，在什么位置）
4  分析意见（这些发现意味着什么，推理链条）
5  局限性（未能检验的部分、客观限制）
```

第 2 节里"工具、版本"要精确到版本号（见陷阱 7），第 3 节里"在什么位置"要精确到文件路径与偏移：

> "**工具与版本**：`Sleuth Kit 4.12.1`、`Plaso 20240312`。
> **提取位置**：`$MFT` 条目 `88214-128-3`；Prefetch 文件 `C:/Windows/Prefetch/REMOTEADMIN.EXE-*.pf`，Last Run Times 字段偏移 `0x98`（24 字节，MAM 格式）。
> **时区处理**：所有时间取自 NTFS（UTC），报告中同时标注北京时间（UTC+8）。"

**局限性章节是加分项，不是减分项**——案例第 5 步写明"该机器已关机，无法提取内存中可能残留的会话信息"，这句话比隐瞒后被对方发现要好得多。

<a id="section-24"></a>

### 4.3 可追溯性与自证

<a id="section-25"></a>

#### 陷阱 7：不记录工具版本

**现象**：操作日志里写"用 volatility 分析内存"，没有版本号；或者只记了工具名，参数是默认值还是自己改过的没记。

**原因**：工具版本差异可能导致结果无法复现——而这正是 McCée 第 3 条的核心。

省略版本号的理由通常不是偷懒，而是"这个工具我一直用这个版本，没变过"。可复现性审查发生在你之外。

而且工具行为的变化往往不体现在输出格式上：解析器改了一处偏移处理、默认过滤器变了、输出字段顺序调整了。这些都会改变结果，而命令名一模一样。

**影响**：半年后复核时结论站不住。

案例第 5 步"记录了工具名称与版本，供后续复核"是刻意写的——它对应的是可重复性这条最难落实的原则。而真正击穿它的方式不是有人质疑版本，而是复核者按自己装的版本跑一遍，得到的数字不一样。

**核查**：工具名 + 版本号 + 完整命令行三项入档：

```bash
# 命令行历史本身就是最好的记录来源
history | tee 04_analysis/command-log.txt

# 工具版本集中登记一次，作为报告附件
{
  echo "=== 工具清单 ==="
  vol.py --version 2>/dev/null || python3 -m volatility3 --version
  echo "plaso -c /dev/null 2>&1 | head -2"
  echo "tsk_recover -V 2>&1 | head -2"
  echo "fls -V 2>&1 | head -2"
  sqlite3 --version
  python3 --version
} | tee 05_report/tool-versions.txt
```

参数也要记，尤其是非默认参数——`-G 4096` 这种分页大小、自定义的时间过滤、自定义的关键字文件。

默认值可以省略，自定义值必须逐个写出来，因为它们是可重复性审查时最容易被质疑的部分。

<a id="section-26"></a>

#### 陷阱 8：把"分析后哈希一致"当成"检材未被取证动过"

**现象**：采集时算了哈希，分析做完又算一次，一致，报告写"经校验，检材在分析过程中未被修改"。

**原因**：2.5 的实务判断写得很清楚——三者中可追溯性最容易被忽视，也最容易在质证时被击穿。哈希只能证明"没变过"，不能证明"没动过手脚"。

这两句话之间的差距是整个保全环节。如果检材在采集之前就已被修改，哈希从头到尾都会一致——因为哈希记录的是"你拿到手时的状态"，而不是"设备出厂时的状态"。

而"分析后哈希一致"这个动作覆盖的时段只有分析这一段。采集之前的时段，它一个字都没说。

**影响**：把保管链的责任推给了哈希。

而原始状态是由封条和移交记录保证的。2.1 把保全阶段的产出物列为"状态照片、封条编号、保管记录"，退出条件是"封条编号与委托书一致、状态已留证"。这三个产出物才是"采集前"那段的凭证。

**核查**：三段哈希 + 三类凭证分别覆盖三段时段：

| 时段 | 凭证 |
|---|---|
| 扣押到采集之间 | 封条编号、状态照片、移交记录、**委托方签字**（2.1 退出条件） |
| 采集过程 | 采集时同步计算的哈希（源介质 == 镜像） |
| 分析过程 | 分析后复算的哈希 |

```bash
# 报告中的哈希链写法
# 采集时（dcfldd hashlog）：源 /dev/sdX 与镜像 SHA-256 一致 = <值>
# 分析前（工作副本创建）：DigiForensics-work.dd SHA-256 = <值>
# 分析后（复核时复算）：DigiForensics-work.dd SHA-256 = <值>，与分析前一致
```

**措辞也要分层**：

> "**本报告可以证明**：采集与分析过程中数据未被改变（哈希链三段一致）。
> **本报告不能证明**：设备在扣押前是否处于原始状态——该部分由委托方移交时的封条状态与本机构接收时的状态照片共同保证。"

这句话写出来不是示弱，而是把证明责任放在正确的位置——它说明你清楚每份证据能证明什么。

<a id="section-27"></a>

#### 陷阱 9：★ 交接与操作不留痕，或责任人不清

**现象**：检材从委托方转到机构、机构内部转给分析员、最后返还，全程没有签字；或者出了问题问"我以为是同事弄的"。

**原因**：2.4 的黄金规则把责任归属写得很直接：由负责人负全责，流程合规性由主办人负责，不能有"我以为是同事弄的"。

而留痕的心理门槛很低——每次交接只要签个字、写个时间，成本接近零，却恰恰因为成本低而被省略。

另一种形态是"事后补记"：交接确实发生了，但当时没记，事后凭回忆补上。而补记的内容无法与当时的实物状态对应。

**影响**：保管链断点。

2.5 把它列为可追溯性的核心，而断点在质证时是严重的——对方不需要证明你改了数据，只需要指出"从 A 到 B 之间没有记录"，你这一段的结论就落空了。

而且这个损失不可补救。断掉的那一段时间里发生的事，永远无法通过后续记录重建。

**核查**：每个关键节点落一笔，且包含"为什么"：

```text
每个关键节点记录：依据的授权文书编号与页码 / 执行的具体操作 /
                  操作人、复核人 / 时间、地点 / 产出物及其哈希

关键节点：□ 检材接收（核对手续、封条、哈希）  □ 开始采集（依据哪份文书）
          □ 每次分析（做了什么、为什么）      □ 数据提取范围（提取与排除项）
          □ 报告出具（结论与局限）            □ 检材返还/销毁（记录并签字）
```

**"复核人"这一栏不能空。**

2.4 的"全程留痕"要求是"每一次交接、每一次操作都要能被第三方复现"，而复核签字是这条要求唯一可验证的形式——它证明的不是操作正确，而是有人独立确认过这个操作发生过。

<a id="section-28"></a>

#### 陷阱 10：把阶段可迭代当成阶段可跳跃

**现象**：分析中发现需要新数据，直接从分析跳回采集重做镜像；或者反过来，采集还没结束就基于"部分镜像"开始分析。

**原因**：2.1 的注释区分了两种情况——阶段不可跳跃，但可迭代。分析阶段发现需要新数据，回到检验阶段重新提取是正常的；但回到采集阶段重做镜像，通常意味着第一次采集出了问题。

这个区分给了"回退"一个合法出口，而人容易把它读成"阶段之间可以自由往返"。尤其在检验阶段发现"咦这个分区没采到"时，重采的动作看起来只是"补一下"，而实际上它意味着第一次采集的完整性判断是错的。这件事本身需要被记录和解释。

**影响**：回到采集阶段重做镜像却不说明原因，第一次采集的失败就消失在记录里。

而它可能是个真问题：写保护器中途失效、目标路径不对、设备中途重连。不解释就重采，等于把一个已发生的采集缺陷从流程里删掉了。

**核查**：回退要分级，处理方式不同：

| 回退类型 | 触发条件 | 处理方式 |
|---|---|---|
| 迭代（正常） | 分析需要新的提取 | 回到检验阶段，记录"新增提取项与理由" |
| 重做（异常） | 采集完整性存疑 | 回到采集阶段，**先记录第一次采集的问题与原因**，再重采 |
| 跨越（错误） | 采集未完成就分析 | 停止分析，**丢弃基于部分镜像的全部中间结果** |

重做采集时两份镜像都要保留，并写明关系：`DigiForensics-v1.dd`（因 `<原因>` 作废）与 `DigiForensics.dd`（本次有效）。作废的镜像不能删——它记录了流程发生过什么。

## 五、案例示例

<a id="section-30"></a>

### 5.1 关机笔记本上的远控软件：三条独立证据定安装与使用

**场景**

查获一台 Windows 11 笔记本，涉网络诈骗。委托方问三个问题：这台机器上是否安装了远控软件、谁用的、什么时候装的。

这条路径值得走，因为三个问题分别对应存在性、时间点、人机归属三类证据。只有把它们拆开、用不同工件回答，才能避免"用一条日志回答三个问题"。

**处置过程**

1. 保全：设备到所时为关机状态，拍照记录外观与封条，登记序列号。关机状态这一事实本身构成后续结论边界的一部分。

2. 采集：接写保护器并实测验证后制作物理镜像，采集时同步计算双哈希：

```bash
sudo dcfldd if=/dev/sdX of=DigiForensics.dd \
     hash=md5,sha256 hashlog=DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on
```

源介质与镜像 MD5/SHA-256 均一致。

**源介质也要算哈希，这一点经常被跳过**。很多 SOP 只对镜像文件算哈希就完事，但源介质的哈希是唯一能把"这块盘就是这个状态"锚定下来的东西。区别在于：镜像哈希证明的是"我手上这个文件没变"，源介质哈希证明的是"我从盘上读到的东西是什么"。

两者算出来的值**通常并不相同**——`dcfldd` 算的是读出字节流的哈希，与源设备的介质级哈希（有些工具有）不是同一回事。写报告时要说清算的是哪一个，否则复核方拿源盘的哈希来比对镜像值，必然得出"数据不一致"的假结论。

3. 检验：提取 `$MFT`、Prefetch、用户目录、注册表 hives、Amcache、UserAssist。

**检验阶段需确认解析器是否适用**。`$MFT` 有多条解析路径，`UserAssist` 的 ROT13 编码在不同 Windows 版本上处理方式不同，`Amcache` 的 `SHA1` 字段在部分版本上是空值。解析器一个选错，结论就是空的——而空结果和"确实没有"在报告里长得一模一样。

所以每个"未发现"都必须能回答"用的是哪个版本的解析器"。这一条写进报告，是阴性发现能不能站住的分水岭。

4. 分析：三条独立证据分别对应一个问题，同向指向同一程序：

```text
存在性  Amcache 中存在该程序条目，含文件路径与 SHA-1
时间点  SOFTWARE hive 中 InstallDate = 2024-03-05；Prefetch 的 Last Run Times 亦为 03-05
使用者  UserAssist 中该程序执行计数 47，归在 Administrator 账户下
```

5. 交叉验证：复核者按同一 SOP 重跑，得到相同的三组哈希与文件偏移。

**三条证据不是凑出来的，是按"谁先坏"挑的**。远控软件的攻防对抗里，最容易被对手处理的是 Prefetch（清一个目录就干净了）、其次是 UserAssist（同样是注册表，可以选择性删除），最难处理的是 Amcache——它由系统映像加载时自动写入，条目含文件路径与 SHA-1，且不完全受用户控制。

按这个"抗清除能力"排序去选工件，得到的证据组合才有意义：如果三条都选自注册表，而对手清理过注册表，那三条会一起消失，报告就变成"什么都没有"。本案特意让 `Amcache` 承担存在性，正是因为它最难被单独抹掉。

**三条证据的时间点还做了互校**。`Amcache` 条目本身不含时间戳（只有路径与 SHA-1），所以安装时间实际由 `SOFTWARE` 的 `InstallDate` 与 Prefetch 的首次运行时间共同支持。两者独立得出 03-05，这个巧合本身就是对彼此的验证——如果某一条单独给出的时间与另一条差出几天，那就必须去查为什么，而不是挑一个更顺眼的写上去。

```text
InstallDate        2024-03-05 09:12:44
Prefetch 首次运行   2024-03-05 09:14:02   （安装后 78 秒首次启动）
UserAssist 最后运行 2024-04-11 22:31:09
```

78 秒这个间隔符合"双击安装程序 → 安装向导走完 → 自动启动主程序"的行为模式，而不是"先装好、隔天用"——这个细节支持"安装与首次使用为同一次操作"的解读，但它仍然只是解读，不能写成结论。

反过来说，如果三个时间点互相矛盾，处理方式也是一样的。分析员看到 `InstallDate` 是 03-05、Prefetch 首次运行是 02-28 时，第一反应往往是"那大概是之前装过一次被卸载了，又重装"——这是有解释力的假设，但也可能是 `InstallDate` 被改过。区分这两者要靠第四个来源，比如 Uninstall 条目的 `InstallDate` 历史：

```text
SOFTWARE\...\Uninstall\{GUID}\InstallDate   2024-02-28
SOFTWARE\...\Uninstall\{GUID}\UninstallDate 2024-03-05
```

这个组合说明的是"先装后卸、再装"还是"卸载时间被改"，需要 Uninstall 目录里 `UninstallDate` 与文件时间戳一起看。 本案没有走到这一步——三个时间点恰好一致，不一致性分析就成了不必要的复杂化。知道有这条退路，和每次都去走一遍，是两回事。

**结论**

能证明：该远控程序于 2024-03-05 安装到本机，在 Administrator 账户下被启动过至少 47 次。三条证据来自三个独立工件（`Amcache` / `SOFTWARE` / `UserAssist`），结论不依赖单一日志。

不能证明：使用者是自然人本人。`UserAssist` 归属 Administrator 账户，回答的是"哪个账户上下文"，不是"哪个人"——而 Administrator 在多人共用或提权场景下可被多人使用。第三个问题的答案必须留白。

**误判对照**

最容易得出的错误结论是「Administrator 本人操作了 47 次」。判据有三条：

①`UserAssist` 的键名是 `HKEY_USERS\<SID>\...\Win` 形式，记录的是该 SID 上下文下的 GUI 启动次数——它区分的是**账户与登录会话，不区分坐在键盘前的人**；
②`SOFTWARE` 的 `ProfileList` 键把 SID 映射到用户名，但**一个 SID 对应的用户配置可以被多次登录**，若管理员与该用户轮流登录同一账户，计数会累加到同一个 SID 上；
③`UserAssist` 的数据本身可被程序改写（它是普通注册表键，非内核保护区域），而 `Amcache` 的 SHA-1 条目由系统映像加载时自动写入、可信度更高，两者的证据等级本就不同级。

正确判据是 `SOFTWARE` 里的 ProfileList 把 SID 映射到用户名，再用登录会话记录（`ntuser.dat` 中的会话与登录时间）区分人；**在区分出具体自然人之前，结论必须停在账户层面**。

按错误判据走的代价是把账户层面的结论直接落到具体自然人头上。本案若同时存在两个共用该机器的人，这条结论会让其中一人被错误锁定，且报告无法自证——账户证据一旦被当成人的证据，它支持的就不再是"某账户被使用"，而是"某人实施了某行为"，这两者之间的距离比看起来远得多。

### 5.2 关机状态导致内存证据缺失：结论边界要写在报告里

**场景**

同一案件中，委托方追加问题："他当时在跟谁视频通话？屏幕共享里传了什么？"——这类问题只有内存镜像能回答。

这条路径值得单列，因为它检验的是阴性发现的表述纪律：不是技术做不到，而是必须把"做不到"限定清楚，而不是含糊过去。

委托方问的这个问题有个特点：它听起来像技术问题，实际是流程问题。如果检材到所时是关机状态，答案在采集那一刻就已经确定了，后面无论分析做得多细都不可能补上。这类问题必须在受理时就问，而不是分析到一半才发现答不了。

**处置过程**

1. 明确记录设备到所状态，这是所有后续边界的前提：

```text
设备交付状态：关机（电源指示灯灭，封条完整）
未采集：内存镜像（关机设备无内存内容可提取）
```

2. 磁盘上的替代工件与它们的局限：

```bash
# Prefetch 只能给出程序启动时间，不含参数与通信内容
# 页文件/休眠文件可能残留部分内存内容，但状态不可控
```

3. 找一个能证明"确实有通话发生"的旁证，把边界撑开。委托方问的是通话对象，那么答案未必只存在于内存里：

```bash
# 浏览器历史：Zoom/Teams 客户端的下载页与登录页
grep -a 'zoom.us\|teams.microsoft' /mnt/case/browser-history.txt

# 注册表 MRU / RunMRU：程序路径的最近使用
regipy-dump /mnt/case/UsrClass.dat | grep -iE 'Zoom|Teams'

# 日程与邮件：会议邀请、确认邮件
grep -a -i 'meeting ID\|zoom.us' /mnt/case/mbox-export/*.eml | head -20
```

第三项最有价值。若邮件里有带 `meeting ID` 的会议邀请，委托方至少能向服务商凭此调取参会记录——**这把"我们查不到"变成了"这条线索可以走出去"**。一个只能回答"没查到"的阴性发现是死路，能指出下一步从哪里调的阴性发现才是活的。

4. 顺手确认页文件是否真的被覆盖，而不是假定：

```bash
istat /mnt/case/DigiForensics.dd | grep -iE 'pagefile|swapfile|hiberfil'
```

本案三个文件名都在，但 `hiberfil.sys` 的大小为 0——说明设备是正常关机而非休眠，休眠文件从未启用，**内存内容在断电瞬间就彻底消失了，没有部分残留**。这个负面确认必须写进报告：否则"可能有部分页文件残留"这个乐观假设会让委托方一直等一个不会到来的结果。

5. 在报告中以"范围 + 检项 + 未发现 + 未覆盖"四段式写明。

**结论**

阴性发现：在磁盘镜像范围内，未发现可用于还原 2024-03-05 前后通话对象与会话内容的工件（Prefetch 仅含程序名与执行时间，无通信内容）。

未覆盖范围：① 内存中的会话与网络栈状态；② 已关机重启后被覆盖的页文件内容（`hiberfil.sys` 大小为 0，休眠残留可排除）；③ 服务端侧的通话记录（须由服务商或运营商配合调取）。

**未覆盖清单不是可选的**——它把"未发现"从一个技术观察变成一个方法论陈述，而后者才是可辩护的。阴性发现的表达能力与技术操作能力不是同一回事。

清单里第三项是本节唯一带行动建议的一条，值得单独强调：它把一个技术上的死局（内存没了）转成了一个业务上的活路（去调服务商记录）。写阴性发现时问一句"委托方还能去找谁"，通常能救回这条结论的全部价值。

**误判对照**

最像的误判是写"未见异常通话记录"或"分析后未发现远程会话行为"。

判据要划到"有没有可查的对象"上：这句话隐含宣称已检查通话相关工件，而整个检材范围内根本不存在这类工件。判据有三条：

①Prefetch 里确实有 `Zoom.exe` 的执行记录，但它只含程序名与执行时间，**不含任何会话对象信息**——把"有程序"说成"查过通话"是偷换检项；
②第 4 步确认 `hiberfil.sys` 大小为 0、`pagefile.sys` 已被正常关机流程重建，**内存内容在断电时已完全消失**，这不是"暂时没找到"而是"确定没有"；
③委托方的问题指向"当时在跟谁通话"，而本案的检项范围（磁盘静态工件）**在原理上就无法回答实时会话对象**——这类问题的答案只存在于内存或服务端记录中。

正确判据是区分"检查过且没有"与"没有可检查的对象"：报告里只能写「Prefetch 记录该程序被执行过，但不含通话对象信息」。

按错误判据走的代价是委托方据此认为分析已完成、结案并对当事人作出处置，而真正的关键证据在从未被采集的内存里。这个错误在结案后无法补救——它不是结论写错了，而是让一个本该继续查的案子提前结束了。

**受理时怎么问，能避免这个错误**。委托方最初的口头委托是"查这台电脑"，等分析做完才追加"他当时在跟谁视频"。这个顺序对取证方最不利，因为追加的问题恰好落在唯一没采的证据上。

正确的做法是在受理环节把问题清单逼出来，按"数据来源"分类：

```text
请委托方按以下四类列明需求：
  A 类：磁盘静态可查（文件、历史、配置、账户）
  B 类：内存可查（运行进程、网络连接、登录会话、实时通信）
  C 类：需外部配合（运营商、服务商、云平台）
  D 类：仅视频/照片等原始载体可查
```

本案在 A、C 两类上给了结论，B、D 两类给了限定。如果受理时列这张表，委托方大概率会优先选择能开机取证，而那个"跟谁视频"的问题也许就能在 B 类上得到答案。取证方无法自己决定采不采内存——那是成本与授权的事——但**他有责任让对方知道这个选择存在**。

这张表还有个副作用：它让"检材以什么状态交付"从一句描述变成了一个**有后果的决策点**。委托方在签字确认"关机交付"时，实际上确认了 B 类问题不可答；日后没人能说"你们应该早点提醒我"，因为提醒过了，且有签字。

这正是流程规范的实际作用方式——它不阻止人犯错，它让错误在发生时可见，并且可见得足够早。

**受理记录里该有的三行**：

```text
检材交付状态：关机
未采集项：内存（原因：交付时已断电，无可采集内容）
已知不可答问题：实时会话、进程状态、网络连接（清单见附页）
委托方签字确认：________________
```

第三行最容易漏，因为它在受理时显得"太悲观"——写上去像是承认能力不足。但它的实际作用是**把责任边界固定在受理时刻**：此后分析出不来结果，不是因为漏查，而是因为这份清单早就写明了。

### 5.3 反例：采集时未验证写保护器生效，事后哈希一致

**场景**

某次采集，操作员确认写保护器电源灯亮即开始 `dcfldd` 读取，未做写入测试。采集全程无报错、哈希记录完整、后续分析结论也自洽。

数月后因另一案件复核该检材时才发现，写保护器当时实际未生效。

这条列为反例，是因为它不会留下任何痕迹——所有常规检查都会通过。

**处置过程**

对照点在于"事后能否察觉"：

```bash
# 缺失的验证动作，成本是一条 512 字节的写命令。
# 破坏性写测试在专用可牺牲测试介质上做：把同型号练习盘接入同一写保护器，执行
printf 'WP-TEST' | sudo dd of=/dev/sdX bs=512 count=1 conv=notrunc   # 须换可牺牲练习盘执行，不得指向正式检材
# 被写保护器在硬件层拒绝即通过。正式检材一律不作为写测试目标。
# 期望：Read-only file system（或等价的写入失败提示）
```

若未执行此步，后续所有检查（哈希、镜像一致性、文件系统完整性）全部无法发现原盘是否被写入过。

**注意写测试本身也有风险**。对一块**确实**生效的写保护器执行写操作，应该得到 `Read-only file system` 报错；但如果测试时把 `of=` 路径写错，或者设备枚举顺序变化导致 `/dev/sdX` 指向了另一块盘，这条"验证命令"就会变成一次真实的写入。

所以这一步的安全前提是**设备标识已经核对过**，不是"反正有写保护器"。两个防护一起做才成立：

```bash
# 先固化设备标识，再做写测试
lsblk -o NAME,SIZE,MODEL,SERIAL,RO /dev/sdX | tee /evidence/pre-writetest.txt
# 确认 SERIAL 与勘验单一致、容量与预期相符
readlink -f /dev/sdX
printf 'WP-TEST' | sudo dd of=/dev/sdX bs=512 count=1 conv=notrunc   # 预期失败；须换可牺牲练习盘执行，不得指向检材
```

**"预期失败"是这个命令唯一正确的成功形态**。如果它真的写进去了，测试就变成了一次破坏，而这条记录会留在日志里成为最难解释的一项。

**事后能做的补救比想象中少**。发现时原始介质已经发还委托方，理论上还能做的只有两条：向委托方索取发还后的介质重新算一次哈希做比对（但这只能发现发还之后的改动，且会暴露机构自身的操作痕迹），或者调取采集时的机房监控看写保护器是否真被绕过（多数机房监控不覆盖设备层细节）。

两条都很难走通，而它们成立的前提是当初那条写测试命令跑过。一条 512 字节的写命令，是整个保全链上性价比最高的动作。

**结论**

阴性发现：在该批历史采集记录中，无法确认采集期间原盘是否处于写保护状态。未覆盖范围是所有依赖"采集未改动原盘"这一前提得出的结论——这个前提在该批次中没有外部验证支撑。

需要补一句限定：这批检材的**分析结论本身并未发现矛盾**，哈希链完整、工件偏移可复现。因此本次评估的对象不是"哪些结论错了"，而是"哪些结论失去了前提支撑"。这个区分在报告里必须写清楚——前者要推翻结论，后者只需补充限定。

**把哈希节点摊开来看，缺口的位置一目了然**：

| 节点 | 证明什么 | 本案状态 |
|---|---|---|
| 采集时算 | 采集过程读出的字节流内容 | ✅ `hashlog` 完整 |
| 采集后复算 | 镜像文件此后未变 | ✅ 已执行 |
| 分析后复算 | 分析期间未改动镜像 | ✅ 已执行 |
| 采集期间源盘只读 | 采集期间原盘未被写入 | ❌ **无任何记录** |

前三个节点全绿，第四个空白。报告如果只写"完整性校验通过"，读者看到的就是一个全绿的表格，而**真正决定证据效力的恰恰是那个空白格**。把四个节点显式列出来，等于主动告诉复核方"我们知道这里缺什么"，比让他们自己发现要好得多。

**误判对照**

最像的误判是把"哈希记录完整、源介质与镜像一致"当成"采集全程未改动原盘"。判据有三条：

①`dcfldd` 算的是读取过程中源盘当时的内容哈希，它证明镜像与"读取那一刻的盘"一致，证明不了读取期间盘没有变——若采集期间有写入，新内容会被一并读进镜像，哈希依然自洽；
②写保护器是否生效是一条**独立于数据内容的物理事实**，它不会在镜像里留下任何痕迹，也无法通过重算哈希来验证——这是它区别于其他检查的根本原因；
③该批次全部检材的 `lsblk` 输出中 `RO` 列均为 `0`，这说明**至少在采集当时，内核并未把设备标记为只读**——而硬件写保护器正常工作时该列应为 `1`，这条输出构成了反向旁证。

正确判据是：写保护验证必须发生在采集之前，且必须在同一份操作记录里留下输出。

按错误判据走的代价：整批镜像的可用性存疑。而要推翻它需要重新取得原始介质做字节级比对，原始介质往往已发还或已封存，不再具备条件——这是所有流程缺陷中最难事后补救的一种。

### 同层深入：各阶段的具体执行入口

- [镜像制作](../../imaging/imaging-acquire/imaging-acquire-disk-imaging-and-evidence-preservation.md) —— 保全与采集阶段的落地。第三章步骤 3 那条 `dcfldd` 命令的全部参数、坏扇区策略、分窗哈希，在那篇展开
- [取证装备与写保护器](../fundamentals-practice/fundamentals-practice-forensics-equipment-and-write-blockers.md) —— 采集阶段的第一道硬件关卡。"绝不动原始数据"这条黄金规则在这里变成一个物理设备
- [只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md) —— 检验阶段的接入纪律。第二章 2.2 三层理由里的"技术层"说的就是挂载时的写入风险
- [文件系统取证总览](../../filesystem/filesystem-ntfs/filesystem-ntfs-filesystem-forensics-overview.md) —— 检验阶段的第一个动作：确认镜像、解析分区表、判定文件系统类型。第三章步骤 4 说的"先定范围，再动提取"，那篇就是"定范围"本身

<a id="section-36"></a>

### 相邻议题：三大属性各自靠什么证明

第二章 2.5 把真实性、完整性、可追溯性分成三格，各自的证明手段分属不同文章：

- 完整性 —— [哈希与完整性校验](../fundamentals-concepts/fundamentals-concepts-hashes-and-integrity-verification.md)。H0 == H1、H2 == H3 两组相等关系就是完整性的完整证明
- 真实性 —— [证据保管链与委托证明](../fundamentals-chain/fundamentals-chain-chain-of-custody-and-authorization.md)。哈希只能证明"没变过"，不能证明"没动过手脚"，后者要靠保管链
- 可追溯性 —— [证据文件格式](../fundamentals-chain/fundamentals-chain-dd-e01-aff4-evidence-formats.md) 与本篇第三步建立的案件工作目录。**容器内嵌的元数据本身就是可追溯性的一部分**
- 报告阶段 —— [虚拟机仿真](../../imaging/imaging-mount-simulate/imaging-mount-simulate-virtual-machine-emulation.md)。仿真是唯一一个**分析员主动改变检材状态**的环节，它的产出怎么在报告里定性，直接关系到报告的可信度

<a id="section-37"></a>

### 判据与反例：流程被跳过的几种典型形态

- [远程勘验与在线取证](../../imaging/imaging-acquire/imaging-acquire-remote-evidence-collection.md) —— **保全阶段无法完整执行**的场景：设备不能关机、不能拆机。第四章 4.1 讲的"跳过阶段比做错更危险"，在远程场景下不是选择题而是既成事实，**只能靠如实声明降级**
- [反取证手法与时间戳篡改检测](../fundamentals-concepts/fundamentals-concepts-anti-forensics-and-timestamp-tampering.md) —— 第五章案例里那台笔记本**到所时已关机**，所以写不出内存里的会话信息。这个局限不是流程缺陷，是**检材状态的客观结果**，而如实声明它的能力恰恰是可追溯性的体现
- [赛事与靶场](../fundamentals-chain/fundamentals-chain-forensics-competitions-and-practice.md) —— **赛题里五个阶段是压扁的**。没有人给你写保管链，没有人关心可重复性。**这个差异是本篇价值的最好注脚**：从靶场进实战，最先崩的往往正是这里
- [取证装备与写保护器](../fundamentals-practice/fundamentals-practice-forensics-equipment-and-write-blockers.md) —— 采集阶段最常见的实际失败：图快跳过硬件直接软挂载。第二章 2.4 讲的软写保护五条局限，**每一条都在削弱本篇第 1 条 McCée 原则**
- [术语查表](https://www.digiforensics.cn/wiki/digiforensics-glossary)—— `Chain of Custody` / `Acquisition` / `Traceability` / `Authenticity` 的定义。`Integrity` 与 `Authenticity` 在中文里都可能被译成"完整性"，但它们是两个不同的属性，术语表里两者的区分必须看清。

## 七、命令速查

```bash
# 环境：Ubuntu/Debian，apt install dcfldd gddrescue e2fsprogs sleuthkit

# 1) 案件目录
mkdir -p /case/2024-DG-001/{01_photo,02_acquire,03_examine,04_analysis,05_report}

# 2) 识别与状态确认
lsblk -o NAME,SIZE,MODEL,SERIAL,TYPE,MOUNTPOINTS
findmnt | grep -E 'sd[a-z]'
sudo hdparm -N /dev/sdX

# 3) 采集（正常盘）
sudo dcfldd if=/dev/sdX of=DigiForensics.dd \
     hash=md5,sha256 hashlog=DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on

# 4) 采集（失败盘，两遍）
sudo ddrescue -n /dev/sdX DigiForensics.dd DigiForensics.map
sudo ddrescue -d -r3 /dev/sdX DigiForensics.dd DigiForensics.map

# 5) 校验（源 == 镜像）
sha256sum DigiForensics.dd

# 6) 摸底
fdisk -l DigiForensics.dd

# 7) 记录工具版本
dcfldd --version
mmls -V
autopsy --version
```
