# 时间戳换算与时区陷阱

<a id="section-1"></a>

## 一、概述

"该文件于 2024 年 3 月 15 日 14:30 被创建"这句话要成立，必须先回答四个问题：这是什么格式、纪元起点是哪一天、精度是多少、存的是 UTC 还是本地时间。四个问题不回答，那个数字就是废的。

错法不止一种。把 WebKit 微秒当 FILETIME 百纳秒读，结果跑到 1600 多年；把 OLE 浮点天当 Unix 秒读，结果落到 1970 年附近；把目标机本地时间当 UTC 读，整条时间线偏移 8 小时，"深夜不可能作案"这类判断随之作废。

根源在于同一台机器上的不同工件存着纪元、单位和精度各不相同的数值，而它们在十六进制或十进制视图里长得毫无区别。换算是分析环节的第一道工序，位置在"拿到元数据"和"开始重建时间线"之间，任何涉及"先后顺序"的结论都经过这一道。

换算的确定性来自四个换算常量。11644473600 秒是 1601-01-01 到 1970-01-01 的间隔，即 134774 天。978307200 秒是 2001-01-01 到 1970-01-01 的间隔，即 11323 天。25569 天是 1970-01-01 在 OLE 纪元下的计数值。知道 11644473600 等于 134774 天，比背公式管用。

对 2024-03-15 06:30:00 UTC 这个参考时刻，各纪元的取值各不相同。FILETIME 从 1601-01-01 起、单位 100 纳秒，值是 `133549578000000000`，18 位。WebKit 时间同样从 1601-01-01 起但单位是微秒，值是 `13354957800000000`，17 位，与 FILETIME 差正好 10 倍。

CFAbsoluteTime 从 2001-01-01 起、单位秒，值是 `732177000`；.NET Ticks 从 0001-01-01 起、单位 100 纳秒，值是 `638460810000000000`；Unix 与 Unix 毫秒从 1970-01-01 起，值分别是 `1710484200` 与 `1710484200000`；

OLE 自动化时间从 1899-12-30 起、单位浮点天，值是 `45366.27083333`；DOS 时间从 1980-01-01 起、2 秒粒度，值是 `0x586F73C0`。ext4、日志、`Date.now()` 上分别是 Unix 秒与毫秒，量级差 1000 倍。

浏览器历史分两系，同一个"从 1601 年起算"的说法覆盖了两种单位。WebKit 系（Chrome、Edge 的 Chromium 版、Firefox、Safari）把时间存在 SQLite 的 `visit_time` 字段，单位微秒。Trident 系（IE 6–11）的 `index.dat` 里存的就是 FILETIME，单位 100 纳秒。

按微秒读 IE 的记录会跑到 2400 多年，反过来按 100 纳秒读 Chrome 会落到 1610 年前后。两种错误都不报错、不溢出，日期库照常输出一个看起来正常的年份。核对位数是唯一不依赖换算结果的判据：Chrome 侧 17 位，IE 侧 18 位。

OLE 自动化时间有两个坑。纪元是 1899-12-30 不是 1970-01-01，Unix 纪元在 OLE 里等于 `25569.0`；单位是浮点"天"，整数部分是日期，小数是一天内已过的时间比例。看到带小数的五位数（4.5e4 量级）先怀疑它是 OLE 日期。存储格式是 IEEE 754 浮点，"减 25569 再乘 86400"会引入误差：实测 `45366.27083333` 换算得 `06:29:59.999712`，截断成 `45366.270833` 则换算得 `06:29:59`，直接差 1 秒。

所以 OLE 字段只用于日期级推断。

DOS 时间是 FAT/exFAT 目录项里的位域打包，创建/修改/访问各占 4 字节（2 字节时间 + 2 字节日期）。时间域 16 位的布局是 `秒/2 [0:5] | 分 [5:11] | 时 [11:16]`，日期域是 `日 [16:21] | 月 [21:25] | 年-1980 [25:32]`。

四个特征：1980-01-01 起算，存"实际年 − 1980"，最大 127 即 2107；2 秒精度，秒字段 5 位、单位是 2 秒，奇数秒根本无法表示；无时区字段，存本地时间；秒字段上限 31 × 2 = 62 秒，留 60–62 给闰秒进位。同一 2 秒桶里的两个文件显示值相同但实际最多相差 2 秒，这足以推翻"同时创建""先写后拷"这类顺序结论。

解析的正确性用回环自检验证——解包后重新打包与原值比对，`0x586F73C0` 实测得 `2024-03-15 14:30:00`、回环一致。

时区要分三层看。存储层：NTFS 存 UTC、FAT/exFAT 存本地时间、ext4 存 Unix 秒。系统层：时区设置要从 SYSTEM hive 的 `TimeZoneInformation` 键或 `/etc/localtime` 独立取证，不能假设。显示层：报告统一写 UTC 并标注北京时间。

多数应用字段的时区属性构成了一张能否直接转 UTC 的对照表：NTFS/注册表/事件日志、ext4 mtime 可以；FAT/exFAT 目录项、OLE 文档属性不可以。少数应用把本地时间写进了本该存 UTC 的字段，FAT 只是最明显的一类。

位数法只是初筛，18 位既可能是 FILETIME 也可能是 .NET Ticks（纪元差 1601 与 0001，单位相同，位数法区分不了）。`tsconv.py` 把一个值按所有纪元都算一遍，用"合理性"反推正确纪元——只有落在合理年份的那一行才是答案。这个方法在 OLE 与 WebKit 上都成立，只是后者的错误结果落点不同。

换算正确只是前提不是保证。任意程序都能调 `SetFileTime` 改 mtime，也能直接改 SQLite 里的 `visit_time`。时间戳是强关联工具、弱定性工具：它能告诉你先后顺序，不能单独告诉你是谁做的。单个文件内部的时间戳可以互比，跨工件排序需要先统一时区与精度前提。至于亚秒级顺序，FAT 只有 2 秒精度、OLE 有浮点误差，这两类字段上"同一秒内的先后"不可靠。

提取环节有两条操作纪律。SQLite 必须复制到镜像之外再查，在挂载点内执行 `sqlite3` 会按 journal 模式创建 `-journal`/`-wal`/`-shm` 并可能回放 WAL，而镜像目录在很多挂载方案下可写。三个文件必须一起拷，WAL 里的最近写入不在主文件里，漏掉就丢掉"最近没有活动"这段最需要证明的时间窗；

复制后立刻用 `PRAGMA integrity_check;` 验证副本。注册表 hive 的时间值确实是 FILETIME，但 `rip.exe` 输出的十六进制偏移是 hive 内部逻辑位置而非文件字节偏移，直接拿去 `dd` 必然取错。

上游依赖两件事：十六进制与位运算基础，以及对时区基本概念的准确理解。2.6 特别强调系统层的时区要独立取证，报告里必须写"目标机时区由 SYSTEM hive 独立取证确认"，而不是隐含在"换算过了"里。

## 二、核心原理

<a id="section-3"></a>

### 2.1 纪元（Epoch）对照表

这是本篇最重要的一张表。记错纪元是时间戳分析中最常见的一类错误。

| 名称 | 纪元起点 | 单位 | 典型来源 | 2024-03-15 06:30:00 UTC 的值 |
|---|---|---|---|---|
| **FILETIME** | 1601-01-01 | **100 纳秒** | NTFS、注册表、事件日志、**IE 历史** | `133549578000000000` |
| **WebKit 时间** | 1601-01-01 | **微秒** | Chrome、Edge、Firefox 等浏览器的 SQLite | `13354957800000000` |
| **Unix** | 1970-01-01 | 秒 | ext4、绝大多数 Unix 系统与日志 | `1710484200` |
| **Unix 毫秒** | 1970-01-01 | 毫秒 | JavaScript `Date`、大量 Web 日志 | `1710484200000` |
| **CFAbsoluteTime** | 2001-01-01 | 秒（Cocoa） | iOS/macOS 备份、plist | `732177000` |
| **.NET Ticks** | 0001-01-01 | 100 纳秒 | .NET `DateTime` | `638460810000000000` |
| **OLE 自动化时间** | **1899-12-30** | **浮点「天」** | 旧版 Office 文档属性 | `45366.27083333` |
| **DOS 时间** | 1980-01-01 | 2 秒粒度 | FAT/exFAT 目录项 | `0x586F73C0` |

> ⚠️ **最致命的一对**：FILETIME 和 WebKit 都从 1601 年起算，但 FILETIME 是 100 纳秒、WebKit 是微秒，相差正好 10 倍——把 FILETIME 当 WebKit 读会跑到 1600 多年，反过来跑到 2400 多年。数值长度也不同：FILETIME 通常 18 位，WebKit 通常 17 位。
>
> ⚠️ 第二个坑：OLE 自动化时间不是从 1970 年起算，零点是 **1899-12-30**，Unix 纪元在 OLE 里等于 `25569.0` 而不是 `0`。看到带小数的五位数（45366 这种），先怀疑它是 OLE 日期。

<a id="section-4"></a>

### 2.2 关键换算常量

```text
Unix 秒 = FILETIME / 10_000_000  - 11_644_473_600
Unix 秒 = WebKit微秒 / 1_000_000  - 11_644_473_600
Unix 秒 = CFAbsoluteTime          + 978_307_200
Unix 秒 = (OLE浮点天 - 25569.0)   × 86400
```

- **11644473600 秒** = 1601-01-01 到 1970-01-01 的间隔（134774 天）
- **978307200 秒** = 2001-01-01 到 1970-01-01 的间隔（11323 天）
- **25569 天** = 1970-01-01 在 OLE 纪元下的计数值

<a id="section-5"></a>

### 2.3 浏览器两系：WebKit 与 Trident 不要混

浏览器历史是取证常见的工件之一，而它分两大阵营。

| 阵营 | 代表浏览器 | 存储格式 | 纪元 | 单位 |
|---|---|---|---|---|
| **WebKit 系** | Chrome、Edge（Chromium）、Firefox、Safari | SQLite `visit_time` | 1601-01-01 | **微秒** |
| **Trident 系** | Internet Explorer 6–11 | `index.dat` 二进制记录 | 1601-01-01 | **100 纳秒** |

**关键点**：IE 历史记录里的时间值就是 FILETIME（100 纳秒）。

同一个"1601 年起算"的数字，在 Chrome 里要按微秒读，在 IE 里要按 100 纳秒读。弄错就是 10 倍误差——这一条比"WebKit vs FILETIME"更隐蔽，因为很多人只知道 Chrome 那一半。

SQLite 只能直接处理 Unix 秒，WebKit 时间必须先除以 1000000 再减 11644473600，完整查询见步骤 4。

<a id="section-6"></a>

### 2.4 OLE 自动化时间：浮点数带来的精度陷阱

OLE 自动化时间（Office 文档属性常见）是浮点「天」——整数部分是日期，小数是一天内已过的时间比例。两个坑。

坑一：纪元是 1899-12-30，不是 1970。 换算必须减 `25569.0` 再乘 86400。

**坑二：它不是精确值。** 存储格式是 IEEE 754 浮点，"减 25569 再乘 86400"会引入误差。实测：`45366.27083333` 换算得 `06:29:59.999712`；若被截断成 `45366.270833`，换算得 `06:29:59`。直接差 1 秒。

取证含义：OLE 字段上"同一秒内的行为先后"不可靠。把 OLE 只用于日期级推断（哪一天），需要秒级精度时改用 NTFS 时间、事件日志交叉验证。

相关历史坑：早期电子表格软件曾把第 60 天当作 1900-02-29（不存在的闰日），导致 1900 年 3 月 1 日前后日期差 1 天。解析那几年的老文档要留意。

<a id="section-7"></a>

### 2.5 DOS 时间：FAT 文件名的 2 秒精度

FAT/exFAT 目录项里，创建/修改/访问时间各占 4 字节（2 字节时间 + 2 字节日期），位域打包：

```text
时间域 16 位：  秒/2 [0:5] | 分 [5:11] | 时 [11:16]
日期域 16 位：  日 [16:21] | 月 [21:25] | 年-1980 [25:32]
```

四个关键特征：**1980 起算**（存"实际年 − 1980"，最大 127 即 2107）；**2 秒精度**（秒字段 5 位、单位是"2 秒"，奇数秒根本无法表示）；**无时区字段**（存本地时间，目录项里没有 UTC 偏移）；秒字段上限 31 × 2 = 62 秒（留 60–62 供闰秒进位）。

时区陷阱在这里最隐蔽。同一个 FAT 时间戳在不同时区的机器上会被解释成不同的 UTC 时刻。所以从 FAT 卷得出的时间只能表述为"目标机本地时间"，转 UTC 前无法定论。

<a id="section-8"></a>

### 2.6 时区问题与时间戳的局限

时区要分三层看。存储层：NTFS 存 UTC、FAT/exFAT 存本地时间、ext4 存 Unix 秒。系统层：时区设置要从 SYSTEM hive 或 `/etc/localtime` 独立取证，不能假设。显示层：报告统一写 UTC 并标注北京时间。

CST (UTC+8) 无夏令时，标注简单；其他时区需注意夏令时切换。

注意：NTFS、注册表、事件日志虽是 UTC，但少数应用把本地时间写进了本该存 UTC 的字段。

局限同样要认清。文件时间戳可被程序任意修改，访问时间不可靠；FAT 的 2 秒精度和 OLE 的浮点精度都不支持秒级排序；时区错误会整体偏移 8 小时，导致"深夜不可能作案"式的误判。

> **结论**：时间戳是**强关联工具，弱定性工具**。它能告诉你"先后顺序"，不能单独告诉你"是谁做的"。

## 三、操作步骤

<a id="section-10"></a>

### 步骤 1：识别未知时间戳

拿到一个整数，先看位数和数量级：

```text
18 位（1.3e17 附近）→ FILETIME（100 纳秒）或 .NET Ticks（需再判纪元）
17 位（1.3e16 附近）→ WebKit 微秒（Chrome/Edge/Firefox）
13 位（1.7e12 附近）→ Unix 毫秒
10 位（1.7e9  附近）→ Unix 秒
9  位（7.3e8  附近）→ CFAbsoluteTime（2001 年后的秒）
带小数五位（4.5e4）→ OLE 自动化时间（浮点天）
FAT 目录项 4 字节  → DOS 时间（1980 起、2 秒精度）
全 0             → 未初始化/空值
```

位数法只是初筛。18 位既可能是 FILETIME 也可能是 .NET Ticks（纪元差 1601 vs 0001），必须靠合理性判断。

<a id="section-11"></a>

### 步骤 2：使用完整换算脚本

脚本 `tsconv.py`（见第七节）已实际运行验证，把一个值按所有纪元都算一遍，用"合理性"反推正确纪元。

把一个真实采集到的 Chrome `visit_time` 值 `13354957800000000` 喂给它：

```text
$ python3 tsconv.py 13354957800000000
输入十进制值：13354957800000000

  FILETIME / IE        (100ns, 1601起)    -> 1643-04-28 03:03:00 UTC
  WebKit Chrome/Firefox (us,  1601起)     -> 2024-03-15 06:30:00 UTC
  CFAbsoluteTime       (s,    2001起)     -> （超出 datetime 可表示范围，纪元很可能不对）
  Unix 秒              (s,    1970起)      -> （超出 datetime 可表示范围，纪元很可能不对）
  Unix 毫秒            (ms,   1970起)       -> （超出 datetime 可表示范围，纪元很可能不对）
  .NET DateTime ticks  (100ns, 0001起)    -> 0043-04-28 03:03:00 UTC
  OLE Date             (天,  1899-12-30起) -> （超出 datetime 可表示范围，纪元很可能不对）
--------------------------------------------------------------------------
```

> 👆 注意看：只有"WebKit"那一行落在合理年份，其余都跑到 1600/0043 年或直接超范围。
>
> 这就是"用合理性反推纪元"的方法——某个纪元算出明显荒谬的年份，它一定不是对的。反过来喂给它真正的 OLE 值 `45366.27083333`，输出 `2024-03-15 06:29:59`，此时正确纪元就是 OLE。

<a id="section-12"></a>

### 步骤 3：解析 DOS 时间（FAT 目录项）

FAT 目录项里的时间是 4 字节位域，按 2.5 节的布局解包即可。最可靠的验证是回环自检——解包后重新打包与原值比对，一致才说明移位与掩码没写反。脚本 `dostime.py` 见第七节，实测 `0x586F73C0` 得 `2024-03-15 14:30:00`、回环"一致"。

> ⚠️ 回环不一致就说明解析代码有 bug，此时的时间结论一律不可用。

<a id="section-13"></a>

### 步骤 4：从镜像中提取并查询

先取出工件，再按各自的纪元换算。每种来源的纪元不同，不要套同一条公式：

```bash
# 1) 注册表 hive 提取（Windows 时间戳大量存在于其中），提取后搜 QWORD 值按 FILETIME 换算
reged -x DigiForensics.dd "/WINDOWS/system32/config/SYSTEM" /tmp/SYSTEM
rip.exe -p /tmp/SYSTEM -a /tmp/out.txt bcdedit

# 2) 浏览器历史：必须先复制出来，不能在镜像上直接打开
#    WAL/SHM 旁文件必须一并复制，否则最近数据丢失
cp "/mnt/case/.../Default/History" /tmp/History
cp "/mnt/case/.../Default/History-wal" /tmp/ 2>/dev/null
cp "/mnt/case/.../Default/History-shm" /tmp/ 2>/dev/null

# 3) Chrome/Firefox：WebKit 微秒，先除 1000000 再减 11644473600
sqlite3 /tmp/History "
SELECT datetime(visits.visit_time/1000000 - 11644473600,'unixepoch') AS utc, urls.url
FROM visits JOIN urls ON urls.id = visits.url
ORDER BY visits.visit_time DESC LIMIT 20;"

# 4) iOS：plist 的 NSDate（0x33 + 8 字节小端 double）；iMessage 用 CFAbsoluteTime
plutil -convert xml1 -o /tmp/info.plist /mnt/case/iOS/Info.plist
sqlite3 /tmp/chat.db "
SELECT text, datetime(date/1000000000 + 978307200,'unixepoch') AS sent_utc
FROM message ORDER BY date DESC LIMIT 10;"
```

## 四、常见陷阱

时间戳分析的失败几乎从不是"算错了"，而是在算之前就没说清楚这个数字是什么。本章按四个环节展开：先认出纪元与单位，再判断精度能不能支撑你要下的结论，然后是提取与查询时的操作纪律，最后是时区与结论表述。

★ 标记表示该操作会永久改变原始检材的内容或元数据，执行前必须停下来确认。

<a id="section-15"></a>

### 4.1 纪元与单位识别

<a id="section-16"></a>

#### 陷阱 1：把 17 位当 18 位读，FILETIME 与 WebKit 差整整 10 倍

**现象**：报告里出现 `1600 年` 或 `2400 多年` 这样一眼荒谬的时间，根因是把同一台机器上两种 1601 起算的时间混用了。

**原因**：FILETIME 是 1601 年起的 100 纳秒，WebKit 是 1601 年起的微秒，数值只差一个数量级，肉眼几乎一样。

2.1 节强调过"最致命的一对"，但真正让人栽跟头的是 2.3 节补的那一刀：IE 的 `index.dat` 里的时间值就是 FILETIME。

同一个"从 1601 起算"的说法覆盖了三类工件（NTFS、注册表、IE 历史用 FILETIME；Chrome/Edge/Firefox 用微秒）。只记住 Chrome 那一半的人会在 IE 记录上翻车。

**影响**：时间线整体平移 10 倍，事件的先后顺序彻底翻转。后面所有与门禁、通话记录、外部日志的比对全部作废。

而且错误的时间线看起来仍然"自洽"——所有事件都整齐地平移了，不会有任何异常提示你错了。

**核查**：位数只能初筛，纪元必须靠来源和合理性双向确认。17 位（1.3e16 附近）对应 WebKit，18 位（1.3e17 附近）对应 FILETIME。

反过来，把一个值按所有纪元都算一遍，只有落在合理年份的那一行才是答案：

```bash
# 17 位输入（WebKit 值）：按 WebKit 读落在 2024 年，按 FILETIME 读会跑到 4000 年以后
python3 tsconv.py 13354957800000000

# 18 位输入（FILETIME 值）：按 FILETIME 读落在 2024 年
python3 tsconv.py 133549578000000000
```

Chrome / Firefox 的 SQLite 必须显式换算，SQLite 不认 WebKit 纪元：

```sql
SELECT datetime(visits.visit_time/1000000 - 11644473600,'unixepoch') AS utc, urls.url
FROM visits JOIN urls ON urls.id = visits.url
ORDER BY visits.visit_time DESC LIMIT 20;
```

<a id="section-17"></a>

#### 陷阱 2：18 位既当 FILETIME 也当 .NET Ticks

**现象**：同一份数值喂进 `tsconv.py`，FILETIME 行算出 2024 年就下了结论，没意识到 18 位还有第二种解释。

**原因**：步骤 1 的位数法明确写了"18 位既可能是 FILETIME 也可能是 .NET Ticks"，两者纪元差 1601 年与 0001 年。单位相同（都是 100 纳秒），所以位数法区分不了。

`.NET DateTime` 的 `Ticks` 属性、PowerShell 导出的时间值、部分数据库的 datetime2 底层表示都走这一系。而它在业务语境里常被叫做"UTC 时间"，不查文档就会被当成 Unix 系处理。

**影响**：`.NET Ticks` 按 FILETIME 读会落到 0043 年这种一眼荒谬的年份——这种错反而好发现。

真正危险的是把 `.NET Ticks` 当 Unix 毫秒或 Unix 秒读。因为 0001 起算的 100 纳秒数值在某个区间内能落进看似合理的年份，结论就是"差 1600 年但没人觉得不对"。

**核查**：位数法只做第一轮筛查。18 位必须问来源：这个值是从 NTFS 属性读的吗（FILETIME），还是从 .NET 侧导出的（Ticks）？

把两种纪元都算出来，用合理性筛掉。同时注意脚本输出里 `.NET DateTime ticks` 那一行在 2024 年附近的输入下会显示 `0043-04-28`——看到这类结果就说明原值不是 Ticks 系。

<a id="section-18"></a>

#### 陷阱 3：OLE 自动化时间按 Unix 读，或者把 Unix 零点当成 0

**现象**：旧版 Office 文档属性里的 `45366.27083333` 被当成 Unix 秒，算出 1970 年 1 月；或者反过来，某个五位数被直接当 Unix 天处理。

**原因**：OLE 纪元的起点是 1899-12-30，不是 1970-01-01。Unix 纪元在 OLE 坐标里等于 `25569.0` 这个魔数。

而且它的单位是浮点「天」——整数部分是日期、小数是一天内已过的比例。这跟任何"整除一个单位再减一个偏移"的换算习惯都对不上。

**影响**：日期结论整体偏到 1970 年前后，对"这份文档是哪年生成的"这个问题给出完全错误的答案。

更麻烦的是 OLE 字段常是文档的唯一时间来源（老 `.doc` / `.xls` 的文件系统时间可能已被工具重写），一旦它错了就没有第二来源兜底。

**核查**：带小数的五位数（4.5e4 量级）先怀疑 OLE，再按浮点天换算，并始终保留小数位不要截断：

```text
Unix 秒 = (OLE浮点天 - 25569.0) × 86400
```

```bash
# 正解：45366.27083333 -> 2024-03-15 06:29:59 UTC
python3 tsconv.py 45366.27083333
```

<a id="section-19"></a>

#### 陷阱 4：iOS / macOS 工件里 CFAbsoluteTime 被当 Unix 秒

**现象**：`Info.plist` 里的 `NSDate`、iMessage 聊天记录里的时间被解析成 2001 年附近的日期，或者反过来大范围偏移到 2033 年。

**原因**：Apple 生态的 plist `NSDate` 是 8 字节小端 double（`0x33` 前缀），iMessage 的 `message.date` 是 `CFAbsoluteTime`（2001-01-01 起的秒），两者的纪元起点都不是 Unix。

步骤 4 的第 4 条已经给出 `date/1000000000 + 978307200` 这个换算，但它成立的前提是先确认这个字段确实是 CFAbsoluteTime。同一台 iOS 设备上，plist 的 `NSDate`、iMessage 的 `date`、Safari 历史的时间基准并不统一。

**影响**：iOS 案件的时间线整体偏移 31 年，与任何外部证据都无法对齐，最后往往被当成"设备时钟异常"糊弄过去。

**核查**：按字段来源分别换算，不要跨工件套同一条公式。

plist 用 `plutil` 转换后看 `<date>` 的 ISO 输出（它已经处理好基准），iMessage 用 978307200 偏移，并把两者与设备系统时间、该设备的时区设置一起记录。

<a id="section-20"></a>

### 4.2 精度与可用性边界

<a id="section-21"></a>

#### 陷阱 5：拿 OLE 浮点时间断秒级先后

**现象**：两份文档属性显示 `06:29:59` 和 `06:30:00`，报告据此写"攻击者先编辑 A 再编辑 B"。

**原因**：2.4 节实测过：`45366.27083333` 换算得 `06:29:59.999712`，一旦这个值在读取时被截断成 `45366.270833`，结果就是 `06:29:59`。两种截断方式直接差 1 秒。

这是 IEEE 754 双精度的表示误差，不是解析器的 bug。也就是说，OLE 字段本身携带的信息量就不支持"同一秒内的先后"。

**影响**：一个基于 1 秒差的行为顺序结论，在复核时会被推翻。

更糟的是这类结论往往是整个"数据外传"叙事的关键一环。一旦被推翻，前面搭的因果链全部松动。

**核查**：OLE 只用于日期级推断（哪一天、是否在某个时间段内），需要秒级精度时改用 NTFS 时间、事件日志交叉验证。

案例第 4 步就是这个思路：WebKit 值与事件日志的 FILETIME 指向同一秒。两个不同纪元、不同精度的工件互为印证，这才是"准"。

<a id="section-22"></a>

#### 陷阱 6：把 FAT 的 2 秒精度当精确时间做排序

**现象**：exFAT U 盘上两个文件的时间戳显示同一时刻，报告写成"两文件同时写入"，或按显示顺序推断复制先后。

**原因**：2.5 节的位域布局写得很清楚，DOS 时间的时间域 16 位里秒占 `[0:5]`，5 位存的是"秒/2"。奇数秒根本无法表示，秒字段上限是 31×2=62（留 60–62 给闰秒进位）。

这不是精度损失，是表达能力缺失：有 31 个可能值，不是 60 个。

**影响**：同一 2 秒桶里的两个文件，显示值相同但实际最多相差 2 秒。这个差值小到不影响"当天"判断，却足以推翻"同时创建""先写后拷"这类顺序结论。

**核查**：用回环自检确认解析没写反（2.5 节位域打包的正确性验证手段），然后在报告里显式声明精度：

```bash
python3 dostime.py 0x586F73C0   # -> 2024-03-15 14:30:00，回环一致
```

结论表述写成"目标机本地时间 14:30（±2 秒精度）"，不与 UTC 事件做秒级排序。这正是案例第 5 步的处理方式。

<a id="section-23"></a>

#### 陷阱 7：时间戳倒置就直接定性为人为伪造

**现象**：发现 `file.docx` 的修改时间早于它的创建时间，或者同一批文件的 mtime 呈现不自然的整齐分布，报告写"时间戳已被篡改"。

**原因**：时间倒置的技术原因太多了：时区配置错了（整体偏移 8 小时）、系统时钟被 NTP 校正回拨、机器长时间断电导致关机时间戳归零、复制工具用 `cp -p` 保留了源时间、备份还原工具重写了部分字段、程序批量改写时漏掉了 `crtime`。

2.6 节已经列了这一串。在报告里直接跳过技术原因而跳到"人为"，是一个结论跳跃。

**影响**：把系统配置问题写成"反取证痕迹"，会引导出一整套并不存在的对抗行为叙事；反过来，真实的批量篡改也容易被当成普通配置问题放过。

**核查**：先穷举技术原因，再谈人为。

检查顺序：

1. 目标机时区设置（从 SYSTEM hive 或 `/etc/localtime` 独立取证，不要假设）
2. 事件日志 6005/6006/6008 的关机与异常记录
3. 同批文件是否批量呈现同一模式（单个文件倒置是巧合，成片倒置才值得深挖）
4. 文件内部是否有应用层时间（Office 属性、PDF `CreationDate`、SQLite 内部时间）与文件系统时间矛盾

最后一条才是篡改的有力迹象。

<a id="section-24"></a>

### 4.3 提取与查询

<a id="section-25"></a>

#### 陷阱 8：★ 直接在镜像上打开 SQLite，WAL 被写入

**现象**：在挂载的镜像里执行 `sqlite3 .../History "SELECT ..."`，查询结果看起来正常，但镜像哈希和采集时对不上了。

**原因**：SQLite 以读写方式打开数据库文件时，会按 journal 模式在其旁创建 `-journal`、`-wal`、`-shm` 文件并可能回放 WAL。镜像目录在很多挂载方案下是可写的——这一步就是把检材当成工作副本用了。

危险之处在于它"看起来只是一次读取"，直到你比对哈希才发现问题。

**影响**：原始镜像的字节流被改变，整条保管链在这一点上断裂。此前所有基于该镜像的哈希、后续所有基于它的结论都要重新评估；如果镜像本身是唯一副本，原始性无法恢复。

**核查**：提取到镜像之外再查，并且 WAL / SHM 旁文件必须一并复制（漏掉会丢最近数据，案例中提到的正是这一点）：

```bash
# 只读挂载后只做复制，不在挂载点内做任何写入型操作
cp "/mnt/case/.../Default/History"      /tmp/History
cp "/mnt/case/.../Default/History-wal"  /tmp/ 2>/dev/null
cp "/mnt/case/.../Default/History-shm"  /tmp/ 2>/dev/null

# 在 /tmp 副本上查询
sqlite3 /tmp/History "
SELECT datetime(visits.visit_time/1000000 - 11644473600,'unixepoch') AS utc, urls.url
FROM visits JOIN urls ON urls.id = visits.url
ORDER BY visits.visit_time DESC LIMIT 20;"
```

如果确实需要在挂载点内操作，先确认该挂载点的写行为——并且优先用只读块设备或写保护器把这一层挡掉。

<a id="section-26"></a>

#### 陷阱 9：只拷 SQLite 主文件，丢掉最近的数据

**现象**：查出来的浏览记录停在几天前，`visits` 表里没有委托方关心的最近访问；或者 `urls` 表与 `visits` 表的关联对不上，SQL 查询返回空。

**原因**：SQLite 默认的 journal 模式（WAL）下，最近的写入在 `History-wal` 里，主文件只保留了 checkpoint 之后的状态。只拷 `History` 一个文件拷的是一个时间截面的旧版本。`History-shm` 是共享内存索引文件，不拷它则 WAL 索引无法正确重建。脚本里常见的 `2>/dev/null` 会把"文件不存在"和"复制失败"一起吞掉，让人以为旁文件本来就该没有。

**影响**：**"最近没有活动"是一个典型的假阴性**——而它恰恰是案件里最需要被证明或证伪的那一段。WAL 丢失的时间窗通常就是用户最后活跃的那几小时。

**核查**：三个文件一起拷，且不要求内容一致但要求同一时刻。

复制前确认目标浏览器进程已不在运行（读的是已落盘状态），复制后立刻用 `PRAGMA integrity_check;` 验证副本：

```bash
ls -l /tmp/History /tmp/History-wal /tmp/History-shm
sqlite3 /tmp/History "PRAGMA integrity_check;"
```

<a id="section-27"></a>

#### 陷阱 10：注册表 hive 提取后用错偏移，或忘了提全

**现象**：从 hive 里搜出的 QWORD 时间值有一半换算成荒谬年份；或者某项设置值根本没搜到，报告按默认值推断。

**原因**：注册表 hive 的时间值确实是 FILETIME（100 纳秒），但 hive 内部有 `$I30`、`$IK` 等压缩/编码结构。`rip.exe` 等工具输出的偏移是 hive 内部逻辑位置，不是文件字节偏移。

把工具输出的十六进制偏移直接拿去 `dd` 原始文件，必然取到错的东西。

另外时区信息是分散的：系统时区在 SYSTEM hive，机器时区在 `TimeZoneInformation` 键。缺任何一项都会导致后续所有 UTC 转换缺一个基准。

**影响**：技术层面是取到了错误字节；结论层面是"时区为默认"这种假设被当成取证结果写进报告——而时区错了，案例里所有本地时间与 UTC 的比对全部偏移。

**核查**：用工具解析 hive，不要手工切字节。提全后立即验证时区键是否存在，再做换算：

```bash
reged -x DigiForensics.dd "/WINDOWS/system32/config/SYSTEM" /tmp/SYSTEM
rip.exe -p /tmp/SYSTEM -a /tmp/out.txt bcdedit

# 时区必须独立取出，不做"默认 UTC+8"假设
reged -x DigiForensics.dd "/WINDOWS/system32/config/SYSTEM" /tmp/SYSTEM
python3 -c "
import Registry, datetime
k = Registry.Registry('/tmp/SYSTEM').open('ControlSet001\\Control\\TimeZoneInformation')
print('TimeZoneKeyName =', k.value('TimeZoneKeyName').value())
print('StandardName    =', k.value('StandardName').value())
"
```

报告里必须写"目标机时区由 SYSTEM hive 独立取证确认"，而不是隐含在"换算过了"里。

<a id="section-28"></a>

### 4.4 时区与结论表述

<a id="section-29"></a>

#### 陷阱 11：把 FAT 与部分应用字段的本地时间当 UTC

**现象**：U 盘上的文件时间与 Windows 事件日志对不上，差了正好 8 小时，据此得出"深夜无人操作"的结论。

**原因**：2.6 节把时区拆成三层——存储层（NTFS 存 UTC、FAT/exFAT 存本地时间、ext4 存 Unix 秒）、系统层（时区设置要独立取证）、显示层（报告统一写 UTC 并标注北京时间）。

FAT 目录项里根本没有 UTC 偏移字段，存的就是目标机本地时间。而且要留意 2.6 节末尾那句：少数应用把本地时间写进了本该存 UTC 的字段，FAT 只是最明显的一类。

**影响**：8 小时偏移在"深夜 vs 工作时间"这类判断上是决定性的——它能把一条在正常工作时段的浏览行为平移到凌晨，从而支撑一个完全错误的作息推断。

案例第 5、6 步之所以稳妥，正是因为 U 盘时间被单独降级为辅助佐证，只与门禁比"是否落在合理窗口"，不做秒级对齐。

**核查**：先判断字段属于哪一层，再决定能不能转 UTC：

| 存储层 | 字段性质 | 能否直接转 UTC |
|---|---|---|
| NTFS / 注册表 / 事件日志 | UTC | 可以 |
| ext4 mtime | Unix 秒（UTC 基准） | 可以 |
| FAT / exFAT 目录项 | 本地时间，**无偏移字段** | 不可以，只能表述为本地时间 |
| OLE 文档属性 | 无时区语义 | 不可以，只作日期级 |
| 应用层账号 / 应用自记时间 | 不确定 | 需交叉验证 |

对照案例的处理：门禁 14:28 进入、浏览器 14:30（北京时间）活动，**在合理窗口内**——这是"落在窗口"的判断，不是"同一秒"的判断。

<a id="section-30"></a>

#### 陷阱 12：报告只写 `14:30` 不带时区，或夏令时地区算错偏移

**现象**：报告时间线里通篇是 `14:30`、`03:15` 这类无标注时间；跨国案件里把冬夏令时切换前后的时间差按固定偏移算。

**原因**：`14:30` 本身不是有效信息。它可能指 14 个不同的真实时刻（UTC、CST、EST、EDT……）。

而中国无夏令时，标注简单（CST 恒为 UTC+8）。这个便利会让分析者把"中国无夏令时"的直觉带到美国、欧洲的机器上，冬夏令时切换点附近偏差 1 小时。

2.6 节明确说"时区要分三层看"，其中系统层是独立取证对象，不是显示层顺手补的标注。

**影响**：时区标注缺失让外部复核方无法把时间线与自己的记录对齐，等于结论不可用。

夏令时错误则制造出一个不存在的 1 小时时间洞。如果在洞的两端恰好有可疑事件，"不在场"的论证就被这个洞废了。

**核查**：报告里每个时间点要么写明时区，要么在时间线表格的表头统一声明一次。

跨时区案件，对每个来源分别记录其时区与夏令时状态，不做全局统一换算：

> **时间线基准**：所有时间为 UTC，显示列另附北京时间（UTC+8，中国无夏令时）。
> U 盘 FAT 时间因无偏移字段，仅记为"目标机本地时间 14:30（±2 秒）"，不参与 UTC 排序。
> 门禁系统时间 `2024-03-15 14:28 (UTC+8)`，与浏览器活动同窗口。

在证据强度上始终记住 2.6 节末尾的定论：时间戳是强关联工具，弱定性工具。它能告诉你先后顺序，不能单独告诉你是谁做的。

## 五、案例示例

<a id="section-32"></a>

### 5.1 WebKit 与 FILETIME 指向同一秒的交叉印证

**场景**

从一台 Windows 11 电脑的 Chrome 记录中提取到 `visit_time` 原始值 `13354957800000000`，委托方要求确定浏览行为的准确时间并与门禁记录比对；该机还挂载过一个 exFAT U 盘。委托方想知道浏览行为发生在上班期间还是深夜。

选择这一路径的依据是换算对了还只是得到一个数字。只有找到第二个独立来源，才能把它变成一个可信的时刻。

**处置过程**

1. 识别纪元：17 位、1.3e16 量级，判定为 WebKit 微秒（FILETIME 应为 18 位）。

2. 换算验证，把同一个值按所有纪元跑一遍，用合理性定案：

```bash
python3 tsconv.py 13354957800000000
```

只有 WebKit 行落在合理年份，其余行跑到 1600/0043 年或直接超范围。

3. 时区转换与确认。UTC 06:30 对应北京时间 14:30；时区不是假设来的，是从 SYSTEM hive 独立取出的：

```bash
reged -x DigiForensics.dd "/WINDOWS/system32/config/SYSTEM" /tmp/SYSTEM
python3 -c "
import Registry
k = Registry.Registry('/tmp/SYSTEM').open('ControlSet001\\\\Control\\\\TimeZoneInformation')
print('TimeZoneKeyName =', k.value('TimeZoneKeyName').value())
"
# 输出 TimeZoneKeyName = China Standard Time
```

4. 交叉验证（关键一步）：同一时刻的 Windows 事件日志存的是 FILETIME，`133549578000000000` 换算同样得 06:30 UTC，日志显示 14:31 发生屏幕锁定。

两种不同纪元、不同精度、不同来源的工件指向同一秒。

5. U 盘时间单独处理：

```bash
python3 dostime.py 0x586F73C0   # -> 2024-03-15 14:30:00，回环一致
```

6. 比对门禁：门禁显示 14:28 刷卡进入，浏览器活动落在 14:30，在进入办公区的合理窗口内。

7. 补一道反向检查，防止交叉印证本身成为陷阱。事件日志那条记录的时间窗是"14:31 屏幕锁定"，而浏览器侧是"14:30:00 访问"。两者差 61 秒，方向也相反——锁定发生在访问之后。若把这条差异解释成"访问后立刻离席"，就等于用一条精度更粗的日志去否定精度更细的记录。实际形态是 Chrome 的标签页仍在后台，锁屏由空闲策略触发，访问行为与锁屏之间没有因果关系。

```text
14:28:12  门禁刷卡进入
14:30:00  Chrome 访问（WebKit 微秒，精度 1 μs）
14:31:03  Security.evtx 4800 屏幕锁定（FILETIME，精度 100 ns）
```

这三行放在一起才看得出：秒级以下的精度差在这三条记录里根本用不上，而排序结论只需要"访问在锁屏前 63 秒"这一条，精度已经过剩。

**结论**

能证明：该次浏览行为发生在 `2024-03-15 06:30 UTC`（北京时间 14:30），落在门禁刷入后的 2 分钟内，属于上班期间。结论强度来自两个独立来源的相互印证，而不是单条记录的精确换算。

不能证明：换算正确不等于时间戳为真。任一程序都能调 `SetFileTime` 改 mtime，也可以直接改 SQLite 里的 `visit_time`。

本案例的交叉印证能证明"两个工件互相吻合"，不能证明"两个工件都没被改过"。

还有一个更窄的限定值得单独写：U 盘那条 DOS 时间与门禁记录不在同一个时区基准上，因此它没有参与本次时间线排序，只是作为"该时点附近有外接设备接入"的旁证。把三类精度不同的记录排进同一张表时，必须在表头标明每行的时区基准和精度，混排本身就是一种结论。

**误判对照**

本案最容易的误判是把 U 盘的 DOS 时间与门禁做秒级比对，看到三个值都指向 14:30 就写"三者在同一分钟内连续发生"。

判据要落到格式上：FAT 目录项里根本没有 UTC 偏移字段，它存的就是目标机本地时间；且秒字段 5 位、以 2 秒为单位，`0x586F73C0` 的实际含义是 14:30:00 ±2 秒。

三条判据，按强度排序：

①**时区基准不同**。门禁记录的时间基准来自服务器本地时钟（UTC+8），Chrome 的 `visit_time` 存的是 UTC，FAT 目录项存的是 U 盘插入那台机器的本地时间。三者里只有第一项与目标机时区确定重合，第二项需要查 SYSTEM hive 才知道，第三项连目标机是哪台都还没确认。

②**精度不一致，而结论要求的精度超出最弱的一环**。"同一分钟内"这个说法要 60 秒精度，FAT 能给 2 秒，看似够用；可要写"三者在同一分钟内连续发生"里的"连续"，实际是在暗示先后顺序，而顺序需要能区分 14:30:00 与 14:30:02——这正好是 2 秒精度给不出的结论。

③U 盘的那条记录是访问时间还是修改时间，本身没有确认。`0x586F73C0` 被写进哪个位域，决定了它是"这个文件最后一次被读"还是"最后一次被写"。两种含义指向完全不同的行为，而目录项里三个时间域各占 4 字节，看错域位是常见操作。

第③条是复核时真正抓住问题的判据。前两条都还在精度层面讨论，第三条直接质疑"你引用的到底是哪个属性"。U 盘若只是被读取过，插入时间与文件内容毫无关系，整条旁证就只剩下"这台机器当时插过 U 盘"。

正确判据是：只有 NTFS/注册表/事件日志这类存 UTC 的字段才能参与 UTC 排序。FAT 时间只能表述为"目标机本地时间 14:30（±2 秒）"。

按错误判据走的代价是把一个 8 小时时区误差的入口留在报告里。一旦目标机时区不是 UTC+8，14:30 这个数字所指的 UTC 时刻就会整体平移，"上班期间"这个定性随之失效。本案真正的危险还不是这 8 小时，而是三层基准混在一张表里、看上去三者一致——一致得越像真的，越没人会去查基准。

### 5.2 老文档只留 OLE 时间：把秒级结论降级为日期级

**场景**

一台已停用五年的工作站上找到一份 `.xls` 报表，文件系统时间因多次复制已被改写成 2005 年，早不可信。委托方希望确认"这份报表是哪一天生成的"。该文件只剩 Office 文档属性里的一个 OLE 时间值 `45366.27083333`。

选择这一路径的依据是：当唯一时间来源是 OLE 时，正确的做法是主动降低结论精度，而不是想办法把秒级结论做出来。

**处置过程**

1. 明确 OLE 身份并换算，保留小数位不截断：

```bash
python3 tsconv.py 45366.27083333
```

```text
OLE Date (天, 1899-12-30起) -> 2024-03-15 06:29:59 UTC
```

注意实际输出是 `06:29:59.999712` 一类的结果，不是整秒。

2. 做一次截断实验，说明精度边界在哪：

```bash
python3 -c "
import datetime as dt
for v in (45366.27083333, 45366.270833):
    print(v, dt.datetime(1899,12,30,tzinfo=dt.timezone.utc)+dt.timedelta(days=v))
"
# 45366.27083333 -> 2024-03-15 06:29:59.999712
# 45366.270833   -> 2024-03-15 06:29:59
```

3. 在另一份同期文档上找第二个来源做日期级比对（NTFS 时间或事件日志）。

4. 第三来源只能给到月级，这个限制也一并写下来。文档所在的 exFAT 卷上，卷标目录项给出的创建时间是 `2024-05-11`，与 OLE 换算出的 3 月差整整两个月。FAT 侧精度只有 2 秒、且是本地时间，所以它不能用来缩小 OLE 的日期范围，但它能把"文件在 3 月已存在"这个事实钉住——复制行为发生在 5 月，3 月的生成时间不是复制时新写的。

这一步的作用是划掉一类替代解释：如果只拿 OLE 一个值，"这份报表的日期被改过"和"报表确实是那天生成的"无法区分；加上卷创建时间落在 5 月之后，OLE 值与文件系统时间之间的落差就有了合理解释，而不是只能往"篡改"上猜。

**结论**

能证明：该报表的生成日期为 **2024-03-15**（日期级结论可靠）。同期另一份文档的 NTFS 创建时间落在同一日，构成日期级印证。

不能证明生成时刻为 06:30:00——这个精度超出了该字段的携带能力。

限定范围要说清"日期级"是怎么来的：结论日期来自 OLE 浮点值本身，印证来自另两份文档的 NTFS 时间，而不是 OLE 与文件系统时间的吻合。文件系统时间在这个案子里恰好是错的（5 月 11 日），把它当印证来源会得到相反的日期。

未覆盖范围是 OLE 属性的可写性：文档属性可被程序改写，PowerShell 的 `Excel.Application` 脚本能精确写出任意 OLE 值。本案没有做过该文档的 OLE 值与同期模板文档的统计对比，因此"未被改写"这一点是假定，不是验证过的结论。

**误判对照**

最容易的误判是把两个 OLE 值差几秒就写成行为顺序。

判据在 2.4 那组实测上：`45366.27083333` 得 `06:29:59.999712`，一旦读取时被截断成 `45366.270833` 得 `06:29:59`。两种截断方式直接差 1 秒——这是 IEEE 754 的表示误差，不是解析器的 bug。

三条判据，把"差 1 秒"这件事推到具体动作上：

①**小数位被读了几位**。文档属性里存的位数与解析器实际取用的位数未必相同。本案两份 `.xls` 分别是 `45366.27083333`（8 位小数）和 `45366.60416667`（8 位小数），换算后分别落在 `06:29:59.999712` 与 `14:30:00.000048`——第二个已经跨到下午了。两者"差 8 小时"的表象，根源是同一类表示误差。

②**是否做过往返编码验证**。把换算结果重新编码回 OLE 浮点，能回到原值就说明精度没丢。本案第一次尝试时工具输出的小数位比输入少 2 位，往返校验立刻暴露了截断——不做这一步，1 秒的偏差会一路带到报告里。

③**这个字段的属性名是什么**。OLE 文档属性里同时有 `Creation Time`、`Last Save Time`、`Last Print Time`，三者语义完全不同。若两份文档取的不是同一个属性，"差 1 秒"连比较对象都不成立。本案复核时发现其中一份取的是 `Last Print Time`，另一份取的是 `Creation Time`，结论因此被撤回重做。

第③条是本案最耗时的一条，也是最不该省的一条。精度问题可以靠往返校验解决，属性选错只能靠回到文档属性表逐个核对——而这一步在写报告时是最容易被跳过的，因为"时间"两个字看上去已经够了。

正确判据是：OLE 字段的可用精度止于日期级。

按错误判据走的代价是：这类顺序结论常是"先编辑 A 再导出 B"整条数据外传叙事的关键一环。一旦在复核时被指出字段不支持秒级排序，崩掉的不只是一个时间点，而是前后因果链。本案的实际代价是结论撤回、委托方追加了一轮回访取证，问题直指"你们核对文档属性时到底看了哪几个字段"。

### 5.3 反例：拿两个 FAT 文件的显示时间判断"同时写入"

**场景**

一台 exFAT 格式的移动硬盘上，两份文件的解析时间显示完全相同：`2024-03-15 14:30:00`。委托方据此推断"两个文件是被批量一次性写入的"。

这条列为反例，是因为显示值相同恰恰是 DOS 时间设计上的必然结果，不构成任何证据。

**处置过程**

对照点在于精度表达能力与实际含义的差距：

```bash
python3 dostime.py 0x586F73C0
# 解析结果: 2024-03-15 14:30:00
# 注意: 秒字段 5 位、以 2 秒为单位，奇数秒无法表示
# 回环编码: 0x586F73C0  一致
```

往返一致只说明这一条记录解析得对，不说明它记录的是哪一次写入。反例的处置重点在这里：同样一组显示值，落在不同位域上时含义完全不同。

```bash
# 三个时间域分别落在 0x586F73C0 上，只有写入时间这一个才与"被批量写入"相关
fls -m /mnt/case/DigiForensics.dd -o 4624 /i '~$2024Q1.xlsx'
# 访问时间 0x586F73C0  修改时间 0x586F71A0  创建时间 0x586F6C40
```

同一目录项的三个时间域并不相同——它们相差 2 分 40 秒和 3 分 30 秒。把它们当成"同一时刻的三个副本"来读，会凭空造出一段并不存在的时间线。

**结论**

阴性发现：在这两个目录项上，未获得任何关于相对写入顺序的信息。它们的显示时间落在同一个 2 秒桶内，实际时刻可能相差最多 2 秒。

未覆盖范围是 NTFS 日志、上层容器时间戳等可提供亚秒精度的来源。

这个阴性发现的成立范围要说清：结论只针对这两个目录项的显示时间，不针对"文件是否被批量写入"这个问题本身。后者需要另一条路径——目录项里没有批次信息，但簇链分配顺序、目录项在目录中的物理排列、exFAT 的位图变化都留下了各自的痕迹。把顺序问题从"看时间"转到"看结构"，是这个案例真正的价值所在。

**误判对照**

最像的误判是"时间显示一致 = 同时写入"。

判据要落在位域上：时间域 16 位里秒占 `[0:5]`，存的是"秒/2"，可表示的值只有 31 个而不是 60 个。显示值相同是格式的必然，不是巧合的证据。

三条判据：

①**两个值的差是 0 还是小于 2**。真的完全相等在 exFAT 里是常态，但要区分"解析结果相同"与"编码相同"——后者才是位域级的证据。本案把两个目录项的原始 4 字节逐位比对，`0x586F73C0` 与 `0x586F73C0` 完全一致，连高低位都一样，这只能说明两个值来自同一个 2 秒桶。

②**同一目录项的另两个时间域是否也相同**。若创建、修改、访问三域里有任意一个不同，那这两个文件就不是被同一次操作同时写下的。本案 `~$2024Q1.xlsx`（临时锁文件）与正式文件 `2024Q1.xlsx` 的三域值两两不同——这直接否掉了"同时写入"。

③**秒字段的值是奇数倍吗**。若某个原始值秒域存的是奇数（`sec/2` 为奇），它本身就证明了字段被改写或工具解析有误，因为 2 秒粒度只能表达偶数秒。本案检查过全部 6 个目录项，秒域全为偶数，排除了这一类。

第②条是唯一能直接回应委托方问题的一条。①只能说明精度不够，③只能排除一种技术性错误，都不触及"是否被批量写入"。而在 exFAT 上区分"一次写入两份"和"分别写入两份"，靠的是时间域的差异性——只要三域不全等，就不存在"同时"这个结论。

正确判据是先问精度是否支持要下的结论——2 秒精度不支持"同时"，也不支持"先写后拷"。

按错误判据走的代价是把一条顺序结论写进报告。而这类结论只要对方找一个 NTFS 侧的亚秒级来源就会被推翻，且推翻时会连带质疑整份报告的严谨性。本案若真按错误判据走，随后的"批量外发"叙事会把两个毫不相关的文件串成一条链，而拆掉它的成本远高于一开始就只写阴性发现。

### 5.4 工具翻车：`web_history` 导出的一律是微秒，IE 那半边不是

**场景**

一块镜像里同时存在 Chrome 与 IE 的浏览痕迹。分析员用现成脚本批量导出访问时间，得到的表格里时间格式完全统一，看着很干净，直接进了报告的时间线章节。

复核方只问了一句"这两个数字是同一种单位吗"，整张表的时间线作废，需要重做。

**处置过程**

出问题的不是换算，是脚本对所有输入用了同一个除数。分两系处理：

```bash
# Chrome/Edge/Firefox：WebKit 微秒 → Unix 秒
SELECT datetime(visit_time/1000000 - 11644473600, 'unixepoch') AS visit_utc
FROM DigiForensics.visits ORDER BY visit_time;

# IE 6-11：index.dat 里的值就是 FILETIME（100 纳秒），除数是 10^7
python3 -c "
import struct,datetime
v=struct.unpack('<Q', open('/case/DigiForensics.index.dat','rb').read(8))[0]
print(datetime.datetime.utcfromtimestamp(v/10000000000 - 11644473600))"
```

两条路径都除完 11644473600 之后，还要处理时区——两系存的都是 UTC，转北京时要加 8 小时并在报告里标注。

对照点在这里：

| 数据源 | 纪元 | 单位 | 换算式 |
|---|---|---|---|
| Chrome `visits.visit_time` | 1601-01-01 | **微秒** | `÷ 1_000_000 − 11644473600` |
| IE `index.dat` | 1601-01-01 | **100 纳秒** | `÷ 10_000_000 − 11644473600` |

同一张时间线里混着两个除数，肉眼完全看不出来——两系的输出都会被渲染成 `2024-03-15 14:30:00` 这样的正常日期，**没有报错、没有溢出、没有异常值**。这是它比 OLE 误用更难被发现的原因：后者落到 1970 年附近，一眼能看出不对。

补充确认动作是看数值位数：Chrome 侧 `visit_time` 通常 17 位（`13354957800000000`），IE 的 FILETIME 通常 18 位（`133549578000000000`）。位数对不上单位，就对了。

**结论**

能证明：`DigiForensics.dd` 中 Chrome 访问时间按微秒换算后落在 2024-03-15 14:30 UTC 前后，IE 侧按 100 纳秒换算后落在同一时段。两系互相印证，可作为交叉证据。

不能证明：仅凭访问时间无法认定访问行为由本机操作者发起。浏览器配置文件可被其他用户或进程访问，且访问时间本身不记录主体。

数值位数这个判据在实践中比看起来有用，因为它不依赖任何换算结果。复核阶段只拿到一张 CSV 表格时，位数是唯一还能用来自查的信息——`13354957800000000` 与 `133549578000000000` 一眼可分，而换算错出的 2400 年或 1610 年要等到读完才发现。

**结论以外还要写清一件事**：本案两系互相印证成立的前提是两者的访问目标确实重合。Chrome 侧指向公司内网的一个 IP，IE 侧指向同一 IP 的同一路径，但 IE 记录的 `LastWrite` 与 Chrome 的 `visit_time` 差 4 分 20 秒，不构成"同一次访问"的证据，只能构成"同一时段访问过同一资源"的证据。这个区别在措辞上只有四个字，但它决定了结论能不能被复用。

**误判对照**

最像的误判是"脚本导出成功，格式统一，转换没有问题"。

判据要落在**数值位数与除数**上：1601 年起算的两系里，微秒值 17 位、100 纳秒值 18 位，相差整整 10 倍。若把 IE 的 FILETIME 按微秒除，得到的时间会偏移到 2400 多年；若把 Chrome 的微秒值按 100 纳秒除，会落到 1610 年前后。两种错误都不会触发任何异常——除法在数值范围内合法，日期库照常输出一个"看起来正常"的年份。

三条判据，按发现成本排序：

①**位数分布**。导出后先看一列原始值的位数集合。本案 Chrome 侧 41 条记录全是 17 位，IE 侧 23 条全是 18 位——两组泾渭分明，一眼就能看出是两套单位混在一张表里。

②**是否存在跨 10 倍的近邻值**。`13354957800000000` 与 `133549578000000000` 的前 17 位完全相同，只有末位多一个 0。这种"同前缀不同长度"的记录对，是单位错配最可靠的信号——正常数据里不会这么巧。本案正是靠这一对把问题钉死的：它们的差恰好是 10 倍，而两条记录描述的是同一次访问。

③**换算结果的年份跨度**。把所有结果排序，若最小与最大年份相差超过 5 年，几乎必然有单位混用。本案修正后 64 条记录全落在 `2024-03-14` 至 `2024-03-15` 两天内，跨度 1 天；修正前 IE 那半边落在 2415 年前后，跨度 391 年。

第②条值得单独强调，因为它是唯一一条能在**不做任何换算**的前提下成立的判据。①②③都要求先把值变成日期，而错误恰恰发生在变成日期的过程中——在错误的换算结果上做区间检查，只会得到一个"看起来很怪但说得通"的分布。

正确判据是先按数据源定单位，再套换算式，最后统一做时区转换；三步不能合并。

按错误判据走的代价是整条浏览时间线作废重做。更麻烦的是这类错误有传染性——错误的时间线一旦被用来支撑"访问顺序"，后面所有依赖它的时间推理都会跟着歪，且这个偏差在报告里不留痕迹。本案的实际损失是报告的浏览行为章节整章重写，而发现它的不是自己，是复核方的一句提问。

<a id="section-36"></a>

### 5.5 阴性结果：Firefox `places.sqlite` 查无记录，划出的时间窗同样有用

**场景**

委托方的问题很具体：某台机器的浏览器配置目录被删除，怀疑有人用另一台机器的账号登录后清理痕迹。要求判断"被清理的浏览行为发生在什么时段"。

查完镜像后，`places.sqlite` 与 `cookies.sqlite` 都没有留下可用记录。分析员写了"未发现浏览记录"，交差。

**处置过程**

阴性结果本身不能一笔带过，它限定的是范围。把整个用户目录按时间摊开，看哪些来源还有内容：

```bash
# 主历史库：文件是否存在、大小、时间
stat /case/DigiForensics/places.sqlite

# 未分配空间里捞残留的主库片段
blkls -o /case/DigiForensics.dd > /tmp/DigiForensics.unalloc
foremost -t sqlite -i /tmp/DigiForensics.unalloc -o /tmp/DigiForensics.recovered

# 与"目录被删除"这个判断直接相关的旁证
stat /case/DigiForensics/.mozilla/firefox/PROFILESINI.default-release
stat /case/DigiForensics/.mozilla/firefox/2k4jd9xz.default-release/places.sqlite
```

`places.sqlite` 的主库文件已不在目录里，但目录本身的 MFT 条目还在；同目录下 `cookies.sqlite` 与 `favicons.sqlite` 的时间戳共同划出了清理动作所在的时段。这些是 FAT/NTFS 层的时间，不受浏览器库内容缺失的影响。

```text
places.sqlite        主库不存在
cookies.sqlite       3 KB，时间戳 2024-06-02 14:07
favicons.sqlite      0 KB（被清空但文件保留）
PROFILESINI.default-release   内容完整，引用 Profile 路径
```

结论要写成有边界的形状，而不是一句"未发现"。

**结论**

阴性发现：`DigiForensics.dd` 的文件系统层未发现 `places.sqlite` 主库残留，未分配空间仅捞出 2 个不完整 sqlite 片段（均不含完整 `moz_places` 表）。

阳性发现：同目录 `cookies.sqlite` 与 `favicons.sqlite` 的时间戳把清理动作限定在 **2024-06-02 14:00–14:10** 这个十分钟窗内。这是文件系统层的时间戳，不依赖浏览器库内容。

未覆盖范围是该十分钟内浏览器的实际访问内容——数据库内容层面的证据为零，不是"没有访问行为"。

再补一项限定：这两条时间戳是 FAT 侧还是 NTFS 侧，决定了它们能不能进 UTC 时间线。本案该目录在 NTFS 卷上，属性存的是 UTC，与目标机时区无关，因此可以直接落进时间线；若换成 exFAT 侧，同样的两条记录只能表述为"目标机本地时间 14:00–14:10"，且 ±2 秒。这个前置条件在写报告时经常被跳过，跳过之后整条时间线的时区基准就悬空了。

**误判对照**

最像的误判是把"没查到"写成"没有发生"。

判据要落在**证据对象的缺失形态**上：`places.sqlite` 是"文件不存在"，而同一目录下 `favicons.sqlite` 是"文件存在但 0 KB"。前者指向被删除且回收，后者指向文件被创建后清零——两种形态指向不同的操作，若合并成一句"未发现浏览记录"，就把一个可用的时间窗线索也一起丢了。

三种误判各自有各自的判据：

①**"未发现浏览记录"**。判据是文件的存在性形态差异：`places.sqlite` 不在目录列表中，而 `cookies.sqlite`（3 KB）与 `favicons.sqlite`（0 KB）都在。前者是删除的形态，后两者的形态说明配置文件目录本身没有被整体删除——如果整个 Profile 目录被清掉，这两个文件也不会留下。留有 `favicons.sqlite` 这个 0 KB 文件这件事，本身就否掉了"目录被清空"。

②**"`-wal` 里有记录所以内容已恢复"**。`-wal` 通常只含最近几千字节的事务，不含完整表定义。判据是内容而不是文件名：片段里必须能解析出 `CREATE TABLE moz_places` 的页才算主库可读。本案捞出的 2 个片段一个是 4 KB 的空闲页，一个是 `-shm` 的共享内存索引副本，两者都不含表定义，形态上就排除了主库数据。

③**"清理动作发生在 14:00–14:10"**。判据是这十分钟的边界由什么撑起来的：`cookies.sqlite` 的 mtime 是 14:07:41，`favicons.sqlite` 的 mtime 是 14:02:19，两者相距 5 分 22 秒。上下界来自两个不同文件的独立时间戳，而不是同一个文件的推断，所以这个窗是"两个动作分别落在这里"，中间可能什么都不发生。

第③条是这节里最容易被夸大的地方。10 分钟的窗看起来很精确，但它的准确含义只是"两个文件最后被写入的时刻都在这 10 分钟内"，不等于"清理动作持续了 10 分钟"，更不等于"这 10 分钟里没有其他操作"。写报告时把这三种含义混同，是把阴性发现变成过度结论的最常见路径。

按错误判据走的代价是给出"不存在浏览记录"的否定结论。委托方会据此认为该时段无异常活动，而实际上那十分钟里恰恰发生了清理动作——**把最可疑的时段从排查范围里划掉**，比漏查一条记录严重得多。

这道题还牵出一个次序问题：`places.sqlite` 的 `CreationTime` 早于 `LastWriteTime`，说明文件是后来才被删除的，但删除动作本身不会留下时间戳。真正把时间窗划出来的不是主库，是它**旁边那几个幸存的兄弟文件**——阴性证据要靠阳性证据衬出边界，单靠"没有"什么都框不住。

顺带说一个容易顺手做错的动作：往重建出来的 `.sqlite` 上再跑一遍查询。同 5.3 那条路径，可写挂载下 SQLite 会重建 `-wal` 与 `-shm`，把"捞出来的残片"变成"被改过的残片"。捞回来的文件先算哈希存底，再决定要不要打开。

## 六、扩展阅读方向

时间戳换算本身是一套算术，复杂度主要在它的上下游——换算对了不代表时间戳可信，换算与时区都对了也不代表能排序。下面按这条链分组。

<a id="section-38"></a>

### 前置基础：换算对了，结论就成立吗

- [反取证手法与时间戳篡改检测](fundamentals-concepts-anti-forensics-and-timestamp-tampering.md) —— **本篇最重要的下游**。那篇讲"读出来之后怎么发现它在骗你"：FILETIME 与 WebKit 的 10 倍关系决定了篡改时间的落点范围，而要坐实篡改必须引入 MFT 之外的独立时钟。**本篇给你换算，那篇给你怀疑**
- [时间线重建](../../computer/computer-log/computer-log-linux-timeline-reconstruction.md) —— 换算是它的前置工序。那篇解决本篇解决不了的：**跨工件排序**需要先定时区、确认 `relatime` / `noatime` 挂载选项对 atime 的影响、并确认 `crtime` 是否可用
- [UsnJrnl 与文件操作时间线](../../computer/computer-execution/computer-execution-usn-journal-timeline.md) —— Windows 侧的对偶实现。`USN_RECORD_V2` 里的时间同样要经过本篇的换算，**而且它是内核写入的，篡改者改不到**
- [哈希与完整性校验](fundamentals-concepts-hashes-and-integrity-verification.md) —— 两者互为锚点：哈希证明"记录时间的那个文件版本没被换掉"，时间戳回答"它是什么时候的状态"。**只用一个都不够**

<a id="section-39"></a>

### 同层深入：别的工件用什么时间

- [NTFS 结构与 MFT 解析](../../filesystem/filesystem-ntfs/filesystem-ntfs-ntfs-master-file-table.md) —— NTFS 上有**四个**独立时间戳（`$STANDARD_INFORMATION` 与 `$FILE_NAME` 各两个），它们的更新规则不同，这正是篡改检测能力的来源。**本篇只讲怎么读，那里讲怎么判**
- [FAT 系列结构](../../filesystem/filesystem-mobile-fs/filesystem-mobile-fs-fat.md) —— DOS 时间在目录项里的实际位域布局与 32 字节目录结构。本篇 2.5 讲原理，那篇讲怎么扫
- [ext4 结构与 inode](../../filesystem/filesystem-unix/filesystem-unix-ext4-inode.md) —— ext4 的 `crtime` 与纳秒级精度，是现代 Linux 文件系统里精度最高的时间来源
- [浏览器取证](../../computer/computer-browser-behavior/computer-browser-behavior-browser-forensics.md) —— 2.3 那两系（WebKit / Trident）在实际取证里的分野。IE 历史和 Chrome 历史的时间值差 10 倍，这是最容易翻车的一处
- [APFS 容器与快照](../../filesystem/filesystem-apple-fs/filesystem-apple-fs-apfs.md) —— CFAbsoluteTime 与快照时间戳，涉及"哪个版本在某个时刻存在"这类问题

<a id="section-40"></a>

### 相邻议题：时区怎么确定

- [注册表取证](../../computer/computer-registry-log/computer-registry-log-registry-forensics.md) —— Windows 侧时区设置的取证路径，从 SYSTEM hive 里读。本篇 2.6 强调"不能假设"，假设的替代方案就是这里
- [plist 与偏好设置](../../computer/computer-plist-spotlight/computer-plist-spotlight-plist.md) —— macOS 侧同一件事。plist 里的时间字段同样是 CFAbsoluteTime
- [SQLite 基础与结构](../../mobile/mobile-database/mobile-database-sqlite.md) —— SQLite 只能直接处理 Unix 秒，WebKit 时间必须先转换。**浏览器与移动取证都会撞上这个限制**

<a id="section-41"></a>

### 判据与反例：换算对了但仍然错在哪

- [系统日志深度分析](../../computer/computer-log/computer-log-system-log-analysis.md) —— **syslog 有三种时间戳格式**（RFC3164 无年份、RFC3336 带时区、ISO8601），解析前必须先看日志属于哪一种。**带年份与不带的那个差别，直接影响跨年排序**
- [Prefetch 深度解析](../../computer/computer-execution/computer-execution-prefetch.md) —— 内核写入的执行时间，精度高、篡改者改不到。**它是那类"独立时钟"里最可靠的一种**
- [Steady-State 与 LogFile 还原](../../filesystem/filesystem-ntfs/filesystem-ntfs-steady-state-logfile.md) —— `$LogFile` 里的 LSN 能追踪元数据变化过程。**"从现状追到过程"这个能力，只有日志能提供**
- 格式兼容缺口 —— OLE 的 1900-02-29 缺陷、Mac 纪元 1904 的问题，本库暂无专篇。本篇 2.4 只提了前者的一句话背景，处理这类老文档时以相应格式规范文档为准
- [术语查表](https://www.digiforensics.cn/wiki/digiforensics-glossary)—— `FILETIME` / `WebKit Time` / `OLE Automation Time` / `DOS Time` / `CFAbsoluteTime` 的定义边界。五者的纪元与单位必须一次记清，术语表里是并排列出的。

```python
#!/usr/bin/env python3
# tsconv.py —— 多纪元时间戳换算。运行：python3 tsconv.py 13354957800000000
import sys
import datetime as dt

E1970 = dt.datetime(1970, 1, 1, tzinfo=dt.timezone.utc)

# (显示名, 每秒含多少个该单位, 纪元零点)
EPOCHS = [
    ("FILETIME / IE        (100ns, 1601起)", 10_000_000, dt.date(1601, 1, 1)),
    ("WebKit Chrome/Firefox (us,  1601起)", 1_000_000, dt.date(1601, 1, 1)),
    ("CFAbsoluteTime       (s,    2001起)", 1, dt.date(2001, 1, 1)),
    ("Unix 秒              (s,    1970起)", 1, dt.date(1970, 1, 1)),
    ("Unix 毫秒            (ms,   1970起)", 1_000, dt.date(1970, 1, 1)),
    (".NET DateTime ticks  (100ns, 0001起)", 10_000_000, dt.date(1, 1, 1)),
    # OLE 纪元是 1899-12-30（Unix 纪元在此记为 25569 天），单位是「天」
    ("OLE Date             (天,  1899-12-30起)", 1.0 / 86400, dt.date(1899, 12, 30)),
]
# 各纪元零点相对 1970-01-01 的秒偏移（早于 1970 的为负）
OFFSETS = [(z - dt.date(1970, 1, 1)).days * 86400 for _, _, z in EPOCHS]
WIDTH = max(len(n) for n, _, _ in EPOCHS)

def fmt(seconds):
    try:
        return (E1970 + dt.timedelta(seconds=seconds)).strftime(
            "%Y-%m-%d %H:%M:%S UTC")
    except (OverflowError, OSError, ValueError):
        return "（超出 datetime 可表示范围，纪元很可能不对）"

def convert(raw):
    text = raw.strip()
    try:
        value = float(text)
    except ValueError:
        return "输入 {!r}：不是数字".format(text)
    if value == 0.0:
        return "输入 {}\
  -> 全零 / 未初始化，非合法时间，勿转成 1970-01-01".format(text)
    out = ["输入十进制值：{}".format(text), ""]
    for (name, per_second, _), offset in zip(EPOCHS, OFFSETS):
        # 绝对时间 + 纪元偏移 = Unix 秒
        out.append("  {:{w}s} -> {}".format(
            name, fmt(value / per_second + offset), w=WIDTH))
    return "\
".join(out)

if __name__ == "__main__":
    if len(sys.argv) < 2:
        sys.exit("用法: python3 tsconv.py <值> [<值> ...]")
    for arg in sys.argv[1:]:
        print(convert(arg))
        print("-" * 74)
```

```python
# dostime.py —— DOS/FAT 时间戳解析（含回环自检）。用法：python3 dostime.py 0x586F73C0
import sys

def dos_to_fields(v):
    # 时间域 [0:5]秒/2 [5:11]分 [11:16]时；日期域 [16:21]日 [21:25]月 [25:32]年-1980
    return ((v & 0x1F) * 2, (v >> 5) & 0x3F, (v >> 11) & 0x1F,
            (v >> 16) & 0x1F, (v >> 21) & 0x0F, 1980 + ((v >> 25) & 0x7F))

def fields_to_dos(sec, minute, hour, day, mon, year):
    return ((sec // 2) | (minute << 5) | (hour << 11) |
            (day << 16) | (mon << 21) | ((year - 1980) << 25))

def main():
    if len(sys.argv) < 2:
        sys.exit("用法: python3 dostime.py <4字节十六进制或十进制>")
    raw = sys.argv[1]
    v = int(raw, 16) if raw.lower().startswith("0x") else int(raw)
    f = dos_to_fields(v)
    print("原始值: 0x%08X (%d)" % (v, v))
    print("解析结果: %04d-%02d-%02d %02d:%02d:%02d"
          % (f[5], f[4], f[3], f[2], f[1], f[0]))
    print("注意: 秒字段 5 位、以 2 秒为单位，奇数秒无法表示")
    back = fields_to_dos(*f)
    print("回环编码: 0x%08X  %s" % (back, "一致" if back == v else "不一致"))

if __name__ == "__main__":
    main()
```
