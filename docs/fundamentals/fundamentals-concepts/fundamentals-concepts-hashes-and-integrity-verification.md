# 哈希与完整性校验

> 原文链接：[DigiForensics Wiki · 在线阅读](https://www.digiforensics.cn/wiki/fundamentals-concepts-hashes-and-integrity-verification)

<a id="section-1"></a>

## 一、概述

比对 2 TB 的镜像和原始介质是不是同一份，靠逐字节比对要跑几天。哈希把它压成 64 个十六进制字符。

这里有一个必须先分清的区分：取证需要的是哈希函数三个性质里的前两个，不是第三个。确定性和单向性至今完好，前者让你能跨机比对，后者让你无法从哈希反推内容。

抗碰撞性防的是这样一类对手：既能准备两份哈希相同、内容不同的文件，又能让其中一个的文件和另一个文件的哈希值同时进入记录。取证现场常见的情形并不是这样——哈希由取证人自己计算并写进记录，事后篡改数据的人无从影响这个已经落在纸面上的值，他改动文件时必须连哈希一起重算，于是留下的是"新文件的哈希不等于记录值"，这属于确定性和单向性就能发现的情形，不是碰撞。

**这不等于抗碰撞性无关。**当哈希值不是由你独家计算，而是由对方提供、预置或早已在别处登记——送检材料附带的校验值、多方共同持有的哈希、去重系统里的内容指纹——此时能够同时操纵文件与登记值的对手才真正存在，碰撞构造才有意义。取证中凡遇到哈希值**不是你算的**这一情形，就退回抗碰撞性这一侧来评估。

这个区分解释了 2.3 为什么说"MD5 可以用，但不能作为唯一依据"：自带哈希值的材料（例如从对方系统导出的校验文件、镜像分卷附带的 `.md5`）一旦被采信为比对依据，MD5 的碰撞现实就会变成直接风险，而不只是理论上的算法强度问题。

哈希贯穿全流程四个节点，但它不是一个阶段，是一个持续动作。

```
源介质 ──采集──> 镜像 ──复制──> 分析副本 ──分析──> 结论
  H0              H1              H2                H3
   └──── 必须相等 ────┘            └─── 必须相等 ───┘
```

H0 与 H1 相等，证明采集无损；H2 与 H3 相等，证明分析过程没动数据。这两组相等关系是取证的核心证明——第五章案例里四个节点全部记录且一致，支撑的就是这一句话。

两组相等各有各的作用对象。H0 是采集时同步算出的源介质哈希，H1 是事后从已落盘的镜像重新读的，两条读取路径撞在同一个值上，才排除了"写盘时错了一块、而错的那块又被一起算进去了"这种自证。H2 若取自 E01 的内嵌 Hash section，而那个 section 是采集时写进容器的，独立性就只来自 H1 与 H0 的独立读取，不来自它自己。

上游依赖[镜像制作](../../imaging/imaging-acquire/imaging-acquire-disk-imaging-and-evidence-preservation.md)：`dcfldd hash=... hashlog=...` 必须在采集时同步计算，事后对已有镜像补算是另一回事（步骤 1 强调这一点，第四章陷阱 5 会讲为什么补算无效）。`dcfldd` 的价值在于一次读取同时算源和镜像的哈希，避免"dd 完再 sha256sum"造成的二次读盘和中间态风险。

下游支撑[证据保管链与委托证明](../fundamentals-chain/fundamentals-chain-chain-of-custody-and-authorization.md)：链上最有价值的一行就是哈希值，它能证明数据没变，但不能证明数据从哪来。

落到具体产物上，`DigiForensics.hashlog` 是 `dcfldd` 边读边算写出的日志，它是 H0 的唯一来源，事后无法重建。`DigiForensics.dd` 的 `sha256sum` 给出 H1/H2/H3 三个值，它们来自同一个文件，分别在采集完成、分析开始、分析结束时计算。

E01 的 Hash section 是容器内嵌摘要，它针对的是解压后的原始字节流，不是压缩后容器（第四章陷阱 8）。`ewfverify` 的输出提供独立验证通道，与外部记录的哈希互为印证；它不带 `-f` 时用容器内嵌的 MD5 作为默认目标算法。

NSRL / 已知文件库是以 MD5 为主索引的已知文件集合，用途是排除而非证明：命中说明这是常见系统文件，不命中说明它不常见，两者都不能单独定性。哈希值只能在同算法之间比较，用 SHA-256 去查一个 MD5 索引的库，得到的是"无匹配"而不是"不匹配"——两件事的含义完全不同。

空字符串 MD5 `d41d8cd98f00b204e9800998ecf8427e` 常被用作"文件为空"的特征信号。密码哈希（`$1$`/`$5$`/`$6$`/`$argon2` 等前缀）是另一种完全不同的哈希对象，它的用途是路径 B（密码恢复），不是路径 A（完整性验证），第四章陷阱 12 讲的是把两者混用的后果。`hash_chain.log` 是分析前后追加记录的日志文件。

据此可以判断几件事：MD5 现在还能不能用（能，但不能作唯一依据）、为什么 SHA-1 和 MD5 属于同一档、完整一次取证该出现几次哈希（四次）、以及遇到故障盘时怎么用分窗哈希把损坏定位到一个区间。

哈希能证明内容相同，为什么不能证明来源合法，那是保管链的事，见[证据保管链与委托证明](../fundamentals-chain/fundamentals-chain-chain-of-custody-and-authorization.md)；两个文件内容相似但不完全相同怎么判断同源，相似度是另一套判据，见[近似匹配与模糊哈希](fundamentals-concepts-fuzzy-hashing.md)；

SHA-3 / BLAKE3 的性能优势属于格式与工具方向，术语表与官方文档更合适；密码怎么恢复不在这里展开，步骤 6 只讲怎么识别哈希类型与格式，实际恢复强调授权 + 最小化 + 脱敏，见[通用密码恢复](../../crypto/crypto-app/crypto-app-passware-and-password-recovery.md)。

上手前需要先知道取证流程分几个阶段（见[取证流程与原则](../fundamentals-process/fundamentals-process-five-stage-forensics-process.md)），否则"分析前后各算一次"这句话里的"分析"没有边界。另外建议先实际跑过 `sha256sum` 和 `md5sum`，亲手验证 2.2 那张表里 `abc` 的四个哈希值。

这张表的价值在于让你看到 MD5 与 SHA-256 输出长度的真实差异——128 位与 256 位不是"短一点长一点"的关系，抗碰撞空间差 2 的 128 次方倍。

## 二、核心原理

<a id="section-3"></a>

### 2.1 哈希函数的三个性质

| 性质 | 含义 | 取证中的意义 |
|---|---|---|
| **确定性** | 相同输入必得相同输出 | 同一文件任何时候算都一样，可跨机比对 |
| **单向性** | 已知输出难以反推输入 | 无法从哈希"还原"文件，密码才安全 |
| **抗碰撞** | 难以找到两个不同输入产生相同输出 | **已被 MD5 和 SHA-1 攻破**；哈希值由他人提供时直接相关 |

> 关键理解：前两条至今完好，支撑日常取证。抗碰撞性平时用不上，在哈希值由他人提供或早已在别处登记时才会成为决定性判据——这就是 MD5 在取证中仍有位置、却不能单独承担完整性的原因。

<a id="section-4"></a>

### 2.2 四种算法的实测对比

用输入 `abc` 实测（可用 `printf 'abc' | <工具>` 自行验证）：

| 算法 | 输出长度 | `abc` 的实测哈希值 | 状态 |
|---|---|---|---|
| **MD5** | 128 bit (32 字符) | `900150983cd24fb0d6963f7d28e17f72` | 已不安全，见 2.3 |
| **SHA-1** | 160 bit (40 字符) | `a9993e364706816aba3e25717850c26c9cd0d89d` | 已不安全 |
| **SHA-256** | 256 bit (64 字符) | `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad` | **当前推荐** |
| **SHA-512** | 512 bit (128 字符) | `ddaf35a1...454d4423643ce80e2a9ac94fa54ca49f` | 高安全场景 |

空字符串的 MD5 恒为 `d41d8cd98f00b204e9800998ecf8427e`，常被用作"文件为空"的特征信号。

<a id="section-5"></a>

### 2.3 为什么取证要弃用 MD5（但不能全盘否定）

MD5 的问题不在于"能算错"，而在于碰撞可被主动构造。

| 事件 | 含义 |
|---|---|
| 2004 年发现实用碰撞 | 首次证明 MD5 碰撞可行 |
| 2008 年 **SHAttered** | 首个公开的**相同前缀**碰撞，两份不同文件拥有相同 MD5 |
| 2019 年 **chosen-prefix collision** | 更实用的攻击：攻击者可在两个文件**各自前缀后自由插入**碰撞块 |

这意味着什么：如果一份文件被"合法地"修改过，攻击者可以计算出修改后版本的 MD5，使其与原始版本的 MD5 完全相同。于是"源盘 MD5 == 镜像 MD5"这个证明就失效了——两份不同的数据拥有同一个指纹。

> ⚠️ 这正是"为什么现在必须用 SHA-256"的直接原因：SHA-256 目前没有实用的碰撞构造方法。

但 MD5 不是完全无用。以下场景仍然合理：

| 合理场景 | 理由 |
|---|---|
| **兼容历史系统与格式** | E01 早期版本、很多司法鉴定规范、NSRL 等数据库仍以 MD5 为主索引 |
| **快速粗筛** | 计算速度比 SHA-256 快得多，批量扫描上亿文件时先跑 MD5 缩小范围 |
| **交叉校验** | 同时记录 MD5+SHA-256，MD5 作为辅助、便于与外部数据比对 |

> **实务原则**：**新做的案件至少要有 SHA-256**；MD5 可以并列记录，但**不能作为唯一完整性依据**。报告中写"MD5 一致"而没有 SHA-256，在严谨质证时会被追问。

<a id="section-6"></a>

### 2.4 SHA-1 的特殊尴尬地位

SHA-1 情况比 MD5 更微妙。Git 等大量系统仍在用 SHA-1（Git 直到近年才逐步迁移），但它同样有已公开的碰撞构造（SHA-1 is a Shambles 首次展示了实际可行的碰撞）。

结论：取证中 SHA-1 和 MD5 属于同一档，都只能作辅助。若设备/格式只内嵌了 SHA-1，你需要用外部记录的 SHA-256 补齐。

<a id="section-7"></a>

### 2.5 哈希链：一次计算远远不够

一次完整取证应至少出现四次哈希：

```text
H0  源介质哈希       —— 采集时同步计算（dcfldd hash=...）
H1  镜像文件哈希     —— 采集完成立刻计算
      验证：H0 == H1  ← 这一步是取证的核心证明
H2  分析副本哈希     —— 开始分析前计算
H3  分析后哈希       —— 分析结束重新计算
      验证：H2 == H3  ← 证明分析过程没改动数据
```

```
源介质 ──采集──> 镜像 ──复制──> 分析副本 ──分析──> 结论
  H0              H1              H2                H3
   └──── 必须相等 ────┘            └─── 必须相等 ───┘
```

`dcfldd` 的价值就在这里：一次读取同时算源和镜像的哈希，避免"dd 完再 sha256sum"造成的二次读盘和中间态风险。

<a id="section-8"></a>

### 2.6 哈希数据库的实战价值

**已知文件库**是哈希最大的非密码学用途：

| 数据库 | 作用 | 取证用途 |
|---|---|---|
| **NSRL / known-good** | 数亿已知文件的哈希 | 快速排除系统文件，剩余的都是"值得看"的 |
| **malware 库** | 已知恶意样本哈希 | 命中即定性 |
| **本机基线库** | 自己构建（装机即哈希全部文件） | 企业内网取证，发现"非标准"文件 |

效果示例：对一块 500 GB 的镜像做全盘哈希后与 NSRL 比对，通常能过滤掉 60%–80% 的文件——因为绝大多数是操作系统和常用软件自带的。剩下的部分才需要逐个人工审阅。

<a id="section-9"></a>

### 2.7 哈希在密码恢复中的角色

破解的前提永远是"拿到哈希值"。取证中常见的来源有这几处：

| 来源 | 典型哈希类型 | 备注 |
|---|---|---|
| Windows SAM/SYSTEM | NTLM | 需先离线提取 |
| Linux `/etc/shadow` | SHA-512 crypt (`$6$`) 或 bcrypt | 现代发行版多为 SHA-512 |
| 浏览器密码库 | AES 密钥 + DPAPI/Keychain | 见板块 5 |
| 数据库配置 | 明文/salt+hash | 宝塔、WordPress 等 |
| 无线网络 | WPA-PMKID | 需抓取握手/EAPOL |

这是两条完全不同的使用路径。路径 A（证据用途）用哈希证明文件没变，用 `sha256sum`，不涉及破解；路径 B（还原用途）用哈希尝试还原明文密码，用 hashcat/john。

本篇重点讲 A。B 的攻击手法详见板块 5。

## 三、操作步骤

<a id="section-11"></a>

### 步骤 1：采集时同步计算（推荐方式）

```bash
# 一次读盘，同时算源与镜像的哈希 —— 最佳实践
sudo dcfldd if=/dev/sdX of=DigiForensics.dd \
     hash=md5,sha256 hashlog=DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on

# 查看生成的哈希日志
cat DigiForensics.hashlog
```

> 💡 `hashwindow` 参数可让 dcfldd 每 N 字节记一次分窗哈希。**对疑似故障盘很有价值**：如果两次读取同一区段结果不同，能精确定位不稳定区域。

<a id="section-12"></a>

### 步骤 2：独立复算验证

```bash
# 用独立工具复算镜像，确保不是 dcfldd 的 bug
sha256sum DigiForensics.dd
md5sum    DigiForensics.dd

# 对 E01 容器，用容器自身的验证能力
ewfverify DigiForensics.E01
```

两条路径都应通过。若 `dcfldd` 记录值与 `sha256sum` 复算值不一致，说明流程中有问题，必须查明。

<a id="section-13"></a>

### 步骤 3：分析前后各算一次

```bash
# 分析前
sha256sum DigiForensics.dd | tee /case/h_before.txt

# ... 分析操作 ...

# 分析后
sha256sum DigiForensics.dd | tee /case/h_after.txt

# 自动比对
cut -d' ' -f1 /case/h_before.txt
cut -d' ' -f1 /case/h_after.txt
```

<a id="section-14"></a>

### 步骤 4：分窗哈希定位损坏位置

```bash
# 每 512 MB 记一次哈希，用于故障盘的精确定位
sudo dcfldd if=/dev/sdX of=DigiForensics.dd \
     hash=sha256 hashwindow=512M hashlog=DigiForensics.window.log \
     bs=4M conv=noerror,sync status=on

# 比对两次运行的分窗哈希，找出不稳定区段
diff <(awk '{print $1}' run1.window.log) <(awk '{print $1}' run2.window.log)
```

<a id="section-15"></a>

### 步骤 5：批量文件哈希（用于 NSRL 比对）

```bash
# 单文件
sha256sum "/mnt/case/Users/Alice/report.docx"

# 递归整个目录，输出可直接喂给比对工具
find /mnt/case -type f -exec sha256sum {} \; > allfiles.sha256

# 与已知文件库比对（需预先导入 NSRL 到比对数据库）
# 常见工具：hashdeep、hfind（NsrlUpdate 项目）
hfind allfiles.sha256
```

<a id="section-16"></a>

### 步骤 6：识别与破解密码哈希（路径 B）

```bash
# 先识别类型
hashcat --example-hashes | grep -B2 -A2 'NTLM'
hashcat -m 1000 --example-hashes

# 字典攻击
hashcat -m 1000 -a 0 hashes.txt rockyou.txt

# 掩码攻击：密码为 8 位小写字母
hashcat -m 1000 -a 3 hashes.txt '?l?l?l?l?l?l?l?l'

# 中断后恢复（长任务必备）
hashcat -m 1000 --session=dg001 --restore
```

> ⚠️ **合规提示**：破解需在合法授权范围内进行。国内实务中，**对不属于授权检材的凭证进行破解可能涉及刑事责任**。详见本文第七节与板块 1 第 10 篇。

## 四、常见陷阱

<a id="section-18"></a>

### 4.1 哈希算法选择

<a id="section-19"></a>

#### 只用 MD5 作为完整性依据

**现象**：报告里只有一列 MD5 值，作为"证据完整性已验证"的依据。

**原因**：MD5 已被证明可构造碰撞——两个不同文件产生相同 MD5 是可计算的现实，不是理论威胁。

更关键的是，即便不发生碰撞，MD5 也不适合作为法律证据。对方只需质疑"这个弱算法是否足以保证完整性"，整条链的可信度都会受影响。

**影响**：证据链在质证环节被攻击。对方律师不需要真的构造碰撞，只需要指出"你用了 2004 年已被攻破的算法"。

**核查**：MD5 只能作为辅助检索值（查 VirusTotal、查已知样本库），不能作为完整性声明的唯一依据。正式报告至少给 SHA-256，需要更高强度时给 SHA-512。

```bash
# 一次生成多算法哈希，MD5 仅作检索用
md5sum    DigiForensics.dd
sha256sum DigiForensics.dd
```

<a id="section-20"></a>

#### 把 SHA-1 当 SHA-256 用（位数不核对）

**现象**：报告里写"SHA-256: `a3f5...`"，但值只有 40 个十六进制字符。

**原因**：SHA-1 输出 40 位十六进制（160 bit），SHA-256 输出 64 位（256 bit）。两者都是十六进制串，肉眼扫过去极易混淆。

工具默认算法可能不是你以为的那个——`shasum` 默认 SHA-1，`sha256sum` 才明确是 SHA-256。

**影响**：报告里的算法标注与实际值不符，是可被当场指出的硬错误。这类错误会让整份报告的其他数据都受到怀疑。

**核查**：核对位数。40 位 = SHA-1，64 位 = SHA-256，128 位 = SHA-512。报告中同时写算法名和完整值，让读者能自行验证位数。

```bash
# 明确指定算法，不依赖工具默认值
sha1sum   DigiForensics.dd | awk '{print "SHA-1  :", $1, "len=" length($1)}'
sha256sum DigiForensics.dd | awk '{print "SHA-256:", $1, "len=" length($1)}'
```

<a id="section-21"></a>

#### 拿已知文件库「未命中」当可疑判据

**现象**：把镜像里全部文件的哈希导入 NSRL 比对，命中的一律标为「已知系统文件」排除，未命中的 200 多个文件打包成「可疑清单」交给人工审阅，报告写「比对已知文件库后筛出可疑文件」。

**原因**：NSRL 是已知文件库，未命中的含义是「这一份库里没有」，不是「它不属于系统」。 覆盖面本身有两个边界：索引主键是 **MD5**，只收进了 NSRL 采集团队认为有收录价值的文件，大量应用自带的库文件、字体、驱动、语言包都不在其中；而任何一个被合法更新过的系统文件（打过补丁的组件、不同构建号的 `dll`）其哈希必然与库里那份不同，落进未命中集。**NSRL 的设计用途是排除噪声，不是定性。**

**影响**：把一份噪声集写成了「可疑清单」，而这份清单会一路流转到人工审阅、二次分析、可能的处置建议里。若报告里再配上「未命中即非系统文件」的表述，整节的可信度会在专业读者面前一起崩塌——因为任何一个做过内网基线的同行都知道这条经验规则不成立。

**核查**：命中写「与 NSRL 已知文件一致」，未命中写「NSRL 未收录，不构成可疑判据」，两句话的措辞不能对称。未命中文件要靠别的判据收敛：路径是否在系统目录、是否有对应的签名、是否被当前运行的进程加载、创建时间是否与该卷首次安装时间吻合。NSRL 的输出在报告里的正确位置是「已排除项」，不是「发现项」。

<a id="section-22"></a>

#### 报告里截断哈希值却不加标注

**现象**：报告的哈希表格里写 `SHA-256: 9f86d081884c7d65`，值只有 16 个十六进制字符（64 bit），表格没写「前 16 位」或任何省略说明。

**原因**：**截断值不是哈希值，是一个前缀。** 它无法与任何完整哈希比对——要判断两个文件是否相同，得先确认它们都等于同一个完整值，而前缀相同什么也不能证明。更麻烦的是它在视觉上与完整哈希几乎无异：同一个字符长度的 SHA-1 恰好就是 40 位，读者扫过去不会意识到少了 48 位。第五章案例的对照表里用「前 16 位」是为了让表格排得开，那是**内部工作表**的写法；把这种简写带进交付报告，就把排版需求变成了技术缺陷。

**影响**：**复核环节必然对不上**。对方拿到交付件后独立复算，得到 64 位完整值，与报告里的 16 位一对就得出「哈希不一致」，继而质疑整条证据链。而实际数据完全一致——这是纯粹的、自证的错误，却要靠额外的沟通才能解释掉。

**核查**：**交付报告里写完整哈希值**。需要表格美观时，把完整值放在表格下方的代码块或附录里，并在表头写明「SHA-256（完整值见附录 A）」。若因格式限制必须截断，表头必须显式标注 `SHA-256（前 16 位，完整值见附录 A）`。核对用：`awk '{print length($1)}'` 应为 64。

<a id="section-23"></a>

### 4.2 哈希计算时机（★ 表示导致证据失效）

<a id="section-24"></a>

#### 采集完成后再回头单独算哈希 ★★★

**现象**：先把整个镜像采集到本地，然后再跑一次 `sha256sum`，作为"采集时已计算哈希"的凭据。

**原因**：读取和计算是两件事。采集读一遍、事后算哈希再读一遍，中间存在一个时间窗口，源设备（或其背后的使用者）可能正在修改数据。

两个不同时间点的读，天然不构成同一份证据的完整性证明。

**影响**：这是取证流程上的实质性缺陷，不是形式瑕疵。对方可以主张"你在采集和计算之间给了数据被改动的机会"，从而质疑整个镜像的证据价值。庭审中这类质疑往往无法完全排除。

**核查**：边读边算，单次读取。所有主流采集工具都支持流式哈希——`ewfexport`、`dc3dd`、`acquire` 都在写入输出的同时计算哈希，物理上不存在第二次读取。

```bash
# dc3dd：读取与哈希同一次流
dc3dd if=/dev/sdb of=DigiForensics.dd \
  hash=sha256 log=DigiForensics.dd.log

# FTK Imager / Guymager 同理，采集与哈希是单次读取的两个输出
ewfexport -u /dev/sdb -t DigiForensics -f /dev/stdout | \
  ewfverify -t -
```

<a id="section-25"></a>

#### 只算一次哈希

**现象**：报告里只有镜像文件（`DigiForensics.dd`）的哈希，没有后续副本的哈希。

**原因**："一次哈希"只能证明那一个文件在那一刻是这个内容。完整链条包含四个节点：源介质 → 采集镜像 → 分析副本 → 分析后状态。每一环都可能引入变化（分析工具挂载产生写入、副本传输、存储介质老化）。

**影响**：链条任一节点无哈希，该节点之后的完整性都无法证明。质证时对方只需问"分析副本的哈希是多少"，整条链就断了。

**核查**：四个节点全部记录，并在报告中以表格形式呈现，形成可追溯的链。

| 节点 | 对象 | 哈希 | 计算时机 |
|---|---|---|---|
| H0 | 源介质（原始设备） | `sha256:…` | 采集时流式计算 |
| H1 | 采集镜像 | `sha256:…` | 采集完成后立即 |
| H2 | 分析副本 | `sha256:…` | 复制到分析机后 |
| H3 | 分析后镜像 | `sha256:…` | 每次分析会话结束 |

<a id="section-26"></a>

#### 只记镜像哈希，不记源哈希

**现象**：报告给出 `DigiForensics.dd` 的 SHA-256，但没有源设备（`/dev/sda`）的哈希。

**原因**：只有 H1 而没有 H0，就无法证明"这个镜像忠实地反映了那块盘"。镜像自己没变，不等于镜像等于源。

取证人员通常把镜像哈希当作"整个过程已完成"的标志，而源侧哈希才是与原始证据直接绑定的那个。

**影响**：缺失证明力最强的一环。没有 H0，"这个镜像是怎么来的"只能靠取证人员的口述，无法自证。

**核查**：H0 和 H1 必须成对出现。采集日志（如 `dc3dd` 的 log 文件）里通常同时包含源设备标识和流式哈希，直接保存原始日志，不要手工誊抄。

```bash
# dc3dd 的采集日志本身就是 H0/H1 的原始凭据
cat DigiForensics.dd.log
```

<a id="section-27"></a>

#### ★ 事后补记的哈希被当成采集时的凭据

**现象**：委托方或所内既有案件卷宗里只有一份哈希值，写在受理登记表的备注栏，无采集时间、无计算工具、无对应的原始日志。分析时直接沿用这份值当 H1，报告写「采集时已计算 SHA-256」。

**原因**：**哈希值本身不携带「什么时候算的」这个属性。** 同一份检材在采集完成后、在复制到分析机后、在分析开始前、在分析结束后，都可以算出完全相同的值——四个时间点的值一模一样，单看结果无法区分。而事后补算的那一次，与原始检材之间隔着一整个未受控的时间窗口，期间源设备是否被改动、是否还通电、有没有人在那台机器上执行过什么，全部不在记录里。它证明的是「从补算那一刻起数据没变过」，不是「采集过程无损」。

**影响**：这是**保管链上的形式缺陷，且无法事后补救**。对方在质证时只需问一句「这个值是第几行写的、用什么工具算的」，你就得承认它是事后补的——而承认之后，H0/H1 这条最核心的证明也随之失效，因为无法证明补算与采集是同一次读取。第五章 5.3 那个反例的损失之所以不可挽回，正是这个原因：镜像已被改写，补多少个哈希都回不到锚点上。

**核查**：哈希必须在采集时与读盘同一次流计算，并落成原始日志。 事后补算的哈希在报告里只能这样写：「该哈希由 `<工具> <版本>` 于 `<时间>` 对 `<文件名>` 计算，用于固定分析副本当前状态（对应 H2/H3 节点），**不作为采集无损的证明**」。同时把补算这件事本身写进证据处理记录。实在无法补救时，把「H0 缺失、仅能证明分析期未变」列入报告的证据局限章节。

<a id="section-28"></a>

#### 用 `md5sum` 比对文件而忘了 `-c` 与换行

**现象**：写 `md5sum file > md5.txt`，之后校验时用 `md5sum -c md5.txt`，看到 `OK` 就认为校验通过；或者 `md5sum -c md5.txt` 报 `FAILED open or read`，直接判断为文件损坏。

**原因**：`-c` 读的是**清单文件里记录的那一行**，其中包含的是**路径**。清单是在 `/evidence` 下生成的、里面写的是 `DigiForensics.dd`；换到另一个目录下执行 `-c`，工具会去找**当前目录下**的 `DigiForensics.dd`，找不到就报 `FAILED open or read`。这个报错说的是「找不到文件」，不是「文件内容对不上」。 真实的内容不匹配报的是 `md5sum: WARNING: 1 computed checksum did NOT match`，两条消息长得像，含义完全相反。

**影响**：把路径问题当成完整性失败，会导向一次不必要的重新采集；反之，把 `OK` 建立在错误的文件上更糟——校验的对象根本不是要校验的那个。

**核查**：校验时显式给全路径，并在 `FAILED open or read` 时先确认目标文件存在。

```bash
# 在固定位置用绝对路径校验，并区分两类失败
cd /evidence && md5sum -c md5.txt
md5sum /evidence/DigiForensics.dd | grep -q "$(awk '{print $1}' /evidence/md5.txt)" \
  && echo "内容一致" || echo "内容不一致"
```

`FAILED open or read` → 路径不对；`did NOT match` → 内容真的变了。报告里若记录过校验结果，要写明是哪一类。

<a id="section-29"></a>

### 4.3 哈希用途误判

<a id="section-30"></a>

#### 误以为哈希能证明数据来源

**现象**：报告写"经 SHA-256 校验，该文件来自目标机器"，并以此论证文件归属。

**原因**：哈希只回答"内容是否被改变过"，完全不回答"内容从哪里来"。同一份文件放在任何地方，哈希都一样。

哈希是内容标识符，不是来源证明。取证人员容易把"完整性"和"归属"混为一谈。

**影响**：结论强度被严重高估。用哈希论证文件归属，等于把"文件没被改过"当成"文件确实是这台机器上的"——这两者之间隔着整个保管链和元数据。

**核查**：来源靠保管链和元数据，不靠哈希。文件归属需要文件路径、创建/修改时间、文件系统的卷序列号、应用侧数据库记录等旁证，哈希只负责保证这些旁证本身没被篡改。

<a id="section-31"></a>

#### 破解时用错哈希模式号

**现象**：用 `hashcat -m 0` 跑 NTLSM/NTDS 哈希，长时间无结果。

**原因**：hashcat 的模式号是纯数字，没有语义自解释。`-m 0` 是纯 MD5，`-m 1000` 才是 NTLM，`-m 1100` 是 NTDS（ntds.dit），`-m 2100` 是 DCC2，`-m 22000` 是 WPA/WPA2。

输错一位就会跑一个完全不同的算法。它不会报错，只会一直跑不出结果。

**影响**：看起来在正常工作，实际从第一秒起方向就错了。GPU 满载、进度条在动，极易让人误以为只是"哈希比较难"，从而换用更贵的字典继续错下去。

**核查**：先跑 `--example-hashes` 确认模式，把示例哈希的格式和你的样本对比，确认是同一个类型再启动正式任务。

```bash
# 先看模式对应的算法与示例
hashcat --example-hashes -m 1000 | head -20
# 与样本比对：长度、字符集、是否含 $DOLLAR$ 等分隔符
echo '$NT$hash' | cut -c1-20
```

<a id="section-32"></a>

### 4.4 容器格式的哈希对象

<a id="section-33"></a>

#### E01 内嵌哈希的对象搞错

**现象**：算出 E01 容器文件的 SHA-256，与源盘裸哈希一比对，发现完全不一致，误以为镜像损坏。

**原因**：E01 的内嵌哈希是针对解压后的原始数据流的，而你算的是 EWF 容器文件本身的字节。

两者是不同的对象：容器文件是分段压缩的封装，E01 记录的哈希覆盖的是压缩前的原始数据。你在拿"封装物的指纹"去对比"内容物的指纹"。

**影响**：误判为"采集失败"或"镜像损坏"，可能触发无意义的重新采集。而原始设备可能早已被改写，重新采集只会覆盖掉唯一的原始状态。

**核查**：用 EWF 自带工具读取内嵌哈希，或先把容器完整导出为裸镜像再对比。永远不要手工计算 EWF 容器文件的哈希去和裸盘哈希比。

```bash
# 读 E01 内嵌的原始数据哈希
ewfinfo -h DigiForensics.E01

# 或先导出裸镜像再比
ewfexport DigiForensics.E01 -t DigiForensics -f raw -u
sha256sum DigiForensics.raw
```

<a id="section-34"></a>

#### 把加密容器的哈希当内容哈希

**现象**：对 BitLocker 加密卷或 EFS 密文文件算哈希，把结果与其他样本的明文哈希比对。

**原因**：加密后的字节流与明文没有任何对应关系，连长度都可能因填充而不同。密文哈希只能证明"这串密文没变过"，无法关联到明文内容。

**影响**：拿密文哈希去查样本库（VirusTotal 等）必然无结果，会误判为"没有已知样本关联"。

**核查**：先解密再算哈希。密文哈希只在需要证明"某个密文文件未被改动"时使用，且要在报告中说明它是"密文对象"的哈希。

<a id="section-35"></a>

#### EWF 的分段文件（E01/E02…）只拷了 E01

**现象**：`DigiForensics.E01` 单个文件拷进证据目录，到分析机上 `ewfverify` 报 `unable to read segment`，误以为交付件损坏。

**原因**：**EWF 是一个分段容器。** 数据量超过单段上限时会被切成 `E01`、`E02`…，缺任何一段整个容器就读不出来，而 `E01` 本身完全看不出缺了什么——它只覆盖前面那一段。文件大小是最直接的判据：一个 500 GB 的镜像，`E01` 往往只有几百 MB 量级，后面还跟着十几段。

**影响**：现象是「校验失败」，最自然的反应是「镜像坏了」或「重新采集」。而真实情况是**拷贝不完整**——它会推动一次针对已封存检材的重复采集，在保管链上再添一个断点，重采还可能覆盖掉原始状态。

**核查**：**`E0*` 全部一起拷、一起哈希**。拷完先数一遍（`ls -l DigiForensics.E0* | wc -l`），再用 `ewfinfo` 看容器自己报告的段数与总大小是否与实物对得上。报告里记录段集时写明 `DigiForensics.E01`–`.E11` 共 11 段，别只写「E01 镜像」。

<a id="section-36"></a>

#### 把哈希当成「文件内容之外都没变」的证明

**现象**：源镜像与分析副本的 SHA-256 完全一致，报告写「文件及其属性未被改动」。

**原因**：**哈希只覆盖字节流。** 它不涵盖所有权与权限、扩展属性、时间戳、硬链接关系、符号链接目标——这些存在于文件系统元数据里，不在文件内容里。`chmod`、`chown`、`touch`、`setfattr` 以及直接改扩展属性的操作**都不改变任何一个字节**，所以哈希前后一模一样。一个被加上 SUID 位或 `security.capability` 扩展属性的文件，哈希与原来完全相同，而它的行为与风险已经变了。

**影响**：报告里「未改动」的覆盖面被默认放大到全部文件系统状态。委托方据此认为镜像里的一切都是原始状态，包括权限与属性——一旦后续发现 SUID 位或 setcap 属性是异常新增的，这份「未改动」的声明就成了需要解释的漏洞。

**核查**：**把哈希的结论范围显式写死**：「SHA-256 一致，覆盖 `<文件名>` 的全部字节内容；**不覆盖**文件系统元数据（所有权、权限、时间戳、扩展属性、硬链接关系）与卷上其他对象」。需要固定元数据时另走一条——把整个文件系统镜像一起哈希，而不是单个文件，或在报告中补记 `stat` 输出。

<a id="section-37"></a>

### 4.5 哈希与算法、索引的匹配

<a id="section-38"></a>

#### 拿 SHA-256 去比对 MD5 索引的数据库

**现象**：把文件用 SHA-256 算出值，导入 NSRL 比对，全部未命中，报告写「与已知样本库比对无关联」。

**原因**：哈希值只能在同算法之间比较，这是编码语义层面的不可比，不是概率问题。 一个 SHA-256 值是 64 个字符，库里根本没有对应条目，工具返回的是「无匹配」而不是「不匹配」。两种结果在终端和输出里长得几乎一样，含义却天差地别：「无匹配」不代表「比对过且不同」，它代表「根本没拿同一种标识去比」。

**影响**：一次完全没有发生过的比对被写成了「无关联」。恶意样本库比对是报告里分量很重的一环，而「无关联」往往是委托方最关心的答案之一——这个答案的取得方式是错的，且没有任何环节会报错提醒你。

**核查**：**先看数据库要什么算法，再选工具**。NSRL 的主索引是 MD5，比对前用 `md5sum`；VirusTotal 这类官方哈希库可用 SHA-256。核对只需一步：`awk '{print length($1)}'` 打出你算出的值位数，与索引位数对照。**报告里写明本次比对使用的算法**，阴性结论写成「以 MD5 为索引比对未命中」——算法名是阴性结论的组成部分，不是脚注。

<a id="section-39"></a>

#### 用 `shasum` 算出 SHA-1 却按 SHA-256 归档

**现象**：跑 `shasum DigiForensics.dd` 得到 40 位值，随手写进报告的「SHA-256」栏，后续所有比对都在错算法上进行。

**原因**：**工具的默认算法与它的名字不一致。** `shasum` 调用的接口默认输出 **SHA-1**，而 `sha1sum` 才是同算法的 GNU 工具名。两个名字都短、都不含算法全称、都不报错，只是安静地给出 160 bit 的结果。它与真正的 SHA-256 在位数上差得很明显（40 vs 64），但归档前只要没人核对长度，这个错误会一路留在报告里。

**影响**：整条链上最关键的那个数字用错了算法。对方复算时用 SHA-256，得到 64 位值，与报告里的 40 位对不上——而报告标的算法名正是 SHA-256，**你没法用「算法不匹配」解释**，只能承认记录有误。更麻烦的是在被发现之前，所有基于它的比较都已经做过了。

**核查**：**不用 `shasum`**，直接用名字自带算法的 `sha256sum`，并把算法名写进输出文件名，让错配无从发生：

```bash
sha256sum DigiForensics.dd > DigiForensics.dd.sha256
sha1sum   DigiForensics.dd > DigiForensics.dd.sha1
```

入库前统一自检：`awk 'length($1)!=64' *.sha256` 应当无输出。

## 五、案例示例

<a id="section-41"></a>

### 5.1 已通电 3 天的 SSD：四个哈希节点与结论边界

**场景**

查获一块 512 GB SSD，委托方要求证明"镜像与原始检材一致"。问题在于检材在扣押时已通电运行 3 天，存在被远程操作的可能——这意味着委托方想要的其实是一个不可能给出的结论。

选择这一路径的依据是主动把结论边界写清楚，比反复强调"我们的哈希是对的"更能回应质疑。

**处置过程**

1. 采集时同步计算双哈希，hashlog 与镜像同批落盘：

```bash
sudo dcfldd if=/dev/sdX of=DigiForensics.dd \
     hash=md5,sha256 hashlog=DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on
```

```text
MD5:    098f6bcd4621d373cade4e832627b4f6
SHA-256: 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
```

2. 独立复算，用另一条命令路径验证同一个值：

```bash
sha256sum DigiForensics.dd
```

3. E01 容器双路径验证：`ewfverify` 独立确认内嵌哈希匹配。

4. 分析前后各算一次，四次记录全部相同：采集时 dcfldd、采集后独立复算、容器内嵌验证、分析结束后再算：

| 节点 | 动作 | 命令/来源 | SHA-256（前 16 位） |
|---|---|---|---|
| H0 | 采集时同步计算 | `dcfldd hashlog=DigiForensics.hashlog` | `9f86d081884c7d65` |
| H1 | 采集后独立复算 | `sha256sum DigiForensics.dd` | `9f86d081884c7d65` |
| H2 | 容器内嵌验证 | `ewfverify -f sha256 DigiForensics.E01` | `9f86d081884c7d65` |
| H3 | 分析结束复算 | `sha256sum -c DigiForensics.sha256` | `9f86d081884c7d65` |

H0 之所以单列，是因为它和 H1 来自两条不同的读取路径：H0 是 `dcfldd` 在写盘时顺带算的，H1 是事后从已经落盘的镜像重新读的。两条路径撞在同一个值上，才排除了"写盘时错了一块、而错的那块又被一起算进去了"这种自证。

5. 补一条阳性对照，证明哈希比对本身不是空转：把源介质重新只读挂一个扇区出来单独算，值与整盘哈希对不上属正常，值与该扇区两次读取一致才说明读取稳定：

```bash
sudo blockdev --setro /dev/sdX
findmnt --source /dev/sdX -o TARGET,OPTIONS
dd if=/dev/sdX bs=512 count=1 skip=1048576 status=none | sha256sum
```

6. 针对"通电 3 天"的质疑作正面回应，报告中明确写出结论范围：

```text
检材扣押时处于运行状态，此为既有事实。
本鉴定无法回溯扣押前的状态，故：
- 结论范围仅限于镜像固定之后的数据完整性
- 未就扣押前是否被修改作出任何判断
- 未就哈希所覆盖的未分配空间是否残留旧数据作出判断
```

第三条限定是后来补上的。第一次写报告时只划了前两条，质证时对方追问"那未被覆盖到的空间里有没有上一次分区的残留"，这一条只能事后追补——而补写比一开始写清楚难看得多。

**结论**

能证明：`DigiForensics.dd` 在采集完成后至分析结束这段时间内未被改动，四个节点（采集 dcfldd、采集后复算、容器内嵌、分析后）SHA-256 完全一致。结论强度不依赖任何主观陈述。

不能证明：检材在被扣押前那 3 天内是否被修改过。

哈希是从某个时点起的锚点，不是对过去的追溯手段——扣押时算出的那个值本身就已经包含了此前所有变化。

限定范围要写到这个粒度才有用："未就扣押前是否被修改作出判断"是一句正确的废话，因为没人知道扣押前发生了什么。真正能挡住追问的是把范围划到具体的证据对象上——整盘镜像（含未分配空间）还是仅逻辑卷、是否覆盖 E01 解压后的原始字节流、是否覆盖采集时挂载产生的元数据。这三项只要有一项含糊，对方就能顺着模糊处往下问。

**误判对照**

最容易的误判是把哈希一致表述成「镜像与原始检材一致，检材数据未被篡改」。

判据要划到锚点的位置上：`sha256sum` 算的是扣押那一刻 `DigiForensics.dd` 的值。

扣押前的三次远程操作如果改过文件系统，这部分差异已经固化在哈希所覆盖的内容里，之后再算多少次都不可能与"扣押前的状态"对比。

还有两种更隐蔽的越界写法：

- 把 H0 与 H1 相等说成"采集无损"——严格说它是"采集结果与源介质在采集这一刻的可读内容一致"。源介质上若有坏道被 `conv=noerror` 跳过，H0 和 H1 会一起等于那份被跳过的内容，两边都不体现"缺了"这件事。
- 把 H2（`ewfverify` 通过）当作独立证据。H2 验的是 E01 内嵌的 Hash section，而这个 Hash section 是采集时写进容器的；若容器本身被重制过、内嵌哈希被同步替换，H2 照样通过。H2 的独立性是相对的，独立性来自 H1 与 H0 的独立读取，不是来自它自己。

正确判据是：哈希的起点是采集时刻，不是事实起点；每一级验证的独立性来源要单独写出来，不能笼统写成"多处验证一致"。

按错误判据走的代价是结论越界：对方律师只需问一句"你凭什么排除扣押前的操作"，整条证明链就断了——而技术部分其实完全没问题，输在结论写得太满。

<a id="section-42"></a>

### 5.2 MD5 与 SHA-256 不一致：先查算法串写错还是真被改

**场景**

同一批检材的 E01 交付件，对方用 `ewfverify`（默认 MD5）报校验失败，而本机构用 `-f sha256` 验证通过。委托方要求立即说明数据是否损坏。

这条路径值得单列，因为这是一个必然会发生、且看起来极其严重的误报。处置方式错了会把交付流程整体卡死。

**处置过程**

1. 先确认两个值来自同一份数据，而不是两个不同文件：

```bash
ewfverify -f md5     /case/DigiForensics.E01   # 失败
ewfverify -f sha256  /case/DigiForensics.E01   # 通过
ls -l /case/DigiForensics.E0*
```

2. 比对采集时的 hashlog，确认两个算法各自的记录值：

```bash
cat DigiForensics.hashlog
```

```text
md5    098f6bcd4621d373cade4e832627b4f6
sha256 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08
```

3. 结论：失败的是算法不匹配，不是数据损坏——MD5 那次校验的对象其实没被正确指定。

4. 但没有就此收工。分窗哈希跑一遍，把"只有 MD5 失败"这个现象再压一次：

```bash
# 采集时留的分窗日志，按 512 MB 一窗
awk '{print $1}' DigiForensics.window.log | head -20
# 从交付件重新分窗，逐窗与采集时对齐
sudo dcfldd if=/delivery/DigiForensics.dd \
     hash=sha256 hashwindow=512M hashlog=/tmp/run1.window.log \
     bs=4M conv=noerror,sync status=on
diff <(awk '{print $1}' DigiForensics.window.log) \
     <(awk '{print $1}' /tmp/run1.window.log)
```

分窗结果与整卷 SHA-256 通过两项合起来，才能说"MD5 失败是算法侧问题"而不是"MD5 那一项正好被抵消"。虽然就本案而言这层担心在两个独立算法同时覆盖同一份数据时本来就不成立，但把它写进处置记录，能省掉第二轮质证。

**结论**

能证明：`DigiForensics.E01` 数据内容完好，SHA-256 内嵌哈希匹配。对方只需用 `ewfverify -f sha256` 重新验证即可通过。

不能证明：对方第一次失败的 MD5 校验里究竟发生了什么。如果对方指定的段集不全，那个失败还可能掩盖真实的段缺失。

限定范围仅限 `DigiForensics.E01` 单卷及其 `.E02`–`.E11` 段集，未覆盖同批交付的其他 E01，也未覆盖交付目录外是否存在同名早期版本。**未覆盖范围**里最该写的是这一条：交付环节是哈希最容易出岔子的地方，因为"哪个文件才是正式交付件"这件事本身需要另一套记录来固定，见[证据格式与转换](../../imaging/imaging-acquire/imaging-acquire-evidence-image-formats.md)里的残件案例。

**误判对照**

默认反应是"数据可能损坏，重新采集"。

判据在命令层面：`ewfverify` 不带 `-f` 时用容器内嵌的 MD5 作为默认目标算法，而本机构采集时同时写入了 MD5 与 SHA-256。SHA-256 通过、MD5 失败，说明两者的目标值不是同一个。

三条可核验的判据，按强度排序：

①**失败是全卷失败还是分区失败**。`ewfverify` 报的是 `MD5 hash is not the same` 整体不匹配，而不是某个段或某个区间不匹配。真损坏通常伴随 `ewfverify` 额外报出段读取错误（`unable to read segment`）；本案日志里只有一条摘要不匹配，没有任何段级错误。

②**同一份 hashlog 里两条算法都在**。`cat DigiForensics.hashlog` 同时输出 md5 与 sha256 两行，说明采集时确实写入了两套目标值。目标值存在却没被命中，是"找错了值"，不是"数据变了"。

③**换算法重算整卷字节流**。`ewfexport` 导出到 RAW 后 `md5sum` 与 `sha256sum` 同一次读取中同时得到两个值，其中 sha256 与内嵌一致。这个"一次读取两个算法"的对照，堵死了"某一段被改而恰好只影响 MD5"的假设——尽管该假设在密码学上不成立，写清楚比让对方替你提出来好。

若数据真的被改，SHA-256 同样会失败——它不会只挑一个算法放过。正确判据是先确认验证算法与采集时记录的算法对应。

按错误判据走的代价是重新采集一块已经封存的检材，既无必要又会引出新的保管链断点，把一个小误报变成真正的事故。本案的实际代价是停工 3 天、委托方两次催促，第二次已经问到"你们是不是出了技术事故"。

### 5.3 反例：先在镜像上挂载可写，再回来算哈希

**场景**

某次分析中，分析员为图方便把 `DigiForensics.dd` 直接 `mount -o loop` 挂载（未加 `ro`），在其中打开 SQLite 数据库查询。几天后才按流程补算哈希，与采集时记录不一致，于是向委托方申请重新镜像。

这条列为反例，是因为它展示的是一个顺序错误导致的连锁代价——问题不在挂载本身，而在没有验证挂载是只读的。

**处置过程**

对照点在于只读标志与验证动作：

```bash
# 错误做法：未加 ro，挂载点是否可写未经验证
mount -o loop /case/DigiForensics.dd /mnt/case
# 在挂载点内执行了 sqlite3 ... "SELECT ..."，WAL 被回放写入

# 正确做法：显式只读 + 块级读保护，并事后验证
mount -o loop,ro,norecovery /case/DigiForensics.dd /mnt/case
# 或使用只读块设备 / 写保护器
```

**结论**

阴性发现：本案该镜像的采集时哈希与分析后哈希不一致，镜像字节流已发生改变，不可再作为原始证据使用。

未覆盖范围是改动内容本身——哪些字节被改、是否影响结论，需要逐项评估，而不是假定"只是 WAL 回放"。

补一项损失界定：这次不一致让镜像在结论里的地位从"原始证据"降为"工作副本"，原始证据必须回到封存的那份 E01 并重走 H2/H3 两步。也就是说代价不是"重采一次"，而是本案全部已完成的分析要在新副本上重跑一遍。停工 5 天，报告全部重写。

**误判对照**

事后的默认解释是"SQLite 查询不会改数据，只是读"。

判据要具体到 SQLite 的行为：以读写方式打开数据库时，SQLite 会按 journal 模式创建 `-journal` / `-wal` / `-shm` 文件并可能回放 WAL。这些动作产生的是真实的写入。

而 `mount -o loop` 在多数系统上给的是可写挂载点。"看起来只是一次读取"这件事，直到比对哈希才会暴露。

三条判据，按可操作性排序：

①**挂载点当时是否可写**，看的是 `findmnt -o OPTIONS` 里有没有 `rw`，不是看命令里写没写 `-o ro`。本案当时的记录里 `rw` 是在的。

②**挂载点内是否新增了 SQLite 附属文件**。`-wal`、`-shm`、`-journal` 三个后缀，摘出来看 mtime 全部落在 5 月 6 日 14:20–14:35 之间，也就是查询那一段窗口。这是可直接指认的写入痕迹，不依赖任何推测。

③**改动范围与 SQLite 无关的部位也在变**。把 `DigiForensics.dd` 与采集时的 E01 逐窗比对，变化出现在 3 个不相邻的窗口上，其中 2 个不含任何 SQLite 数据库。若改动只由 WAL 回放造成，它应该集中在同一个文件的簇链附近，跨文件的散点分布指向的是挂载期间系统的其他写活动。

第③条是本案最关键的一步。只查 SQLite 附属文件会得出"WAL 回放导致"的结论，而那结论会把范围写窄——真正的改动面比一条 WAL 大得多，报告里的影响评估也跟着错。

正确做法是在挂载层就挡住写入（`ro` + 写保护器），而不是依赖工具的自我约束。

按错误判据走的代价是整个检材作废重采。对于已封存或已交付的检材，这个损失不可挽回。

<a id="section-44"></a>

### 5.4 判据对撞：末窗对不上，该信整盘哈希还是分窗哈希

**场景**

一块 2 TB 采集盘，`dcfldd` 采集时同步写了 hashlog。两天后按流程复算，`sha256sum` 与 hashlog 里的 SHA-256 完全一致；但用 `md5deep` 做分窗哈希时，镜像最后一个窗口的值对不上采集日志里的分窗记录。

两条判据给了相反的结论。委托方要求当场定性：数据到底动没动。

**处置过程**

差异不在算法，在分窗边界。处置动作不是二选一，而是把两边还原到同一个字节区间上比：

```bash
# 判据 A：整盘 SHA-256，一个值覆盖全部 2 TB
sha256sum /case/DigiForensics.dd
# 9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08  ← 与 hashlog 一致

# 判据 B：分窗哈希，末窗单列
md5deep -l 32M /case/DigiForensics.dd > /tmp/DigiForensics.win.md5
tail -2 /tmp/DigiForensics.win.md5

# 关键一步：把末窗单独截出来重算
dd if=/case/DigiForensics.dd bs=32M skip=65535 status=none | md5sum
```

对照点在于窗参数。`DigiForensics.hashlog` 里的分窗记录是按 `bs=16M` 落的盘，而 `md5deep -l 32M` 按 32 MB 开窗。两套窗的边界不对齐，同一段字节在两边根本不是同一个窗，比较的不是同一批数据：

```text
bs=16M 划分:  [... | 16777216 | 16777216 | ...]
md5deep 32M:  [... | 33554432 | 33554432 | ...]
末窗 16 MB 在两套划分里分别跨了两个不同的窗
```

还有一层：hashlog 里同时记了 MD5 与 SHA-256，但**分窗值只有 MD5**。所以"A 一致、B 不一致"这个组合看上去很反常，实际只是两个不同算法在不同粒度上的独立结论——SHA-256 那条根本没参与这次比较。

**结论**

能证明：`DigiForensics.dd` 自采集起未被改动。判据 A 成立，它是覆盖完整 2 TB 的单一值；判据 B 的"不一致"来自分窗边界不匹配，不是数据差异。

不能证明：这次比对回答不了"源介质采集时刻是否存在未读出的坏道"。`conv=noerror` 跳过的扇区不进入镜像，H0 与 H1 会一起等于那份被跳过的内容，两个值相等并不说明缺了什么。

**误判对照**

默认反应是"分窗对不上，尾部被写坏了"，接着申请重采。

判据要落在**窗参数**上：`md5deep -l 32M` 与 `dcfldd bs=16M` 的分窗边界不同，同一段字节在两套划分里不属于同一个窗。判别动作很直接——把末窗单独 `dd` 出来重算，若这个值与 `md5deep` 的末窗一致、而与 hashlog 的末窗不一致，那差异来自窗划分，不是字节。

反向的误判是把判据 A 当成"覆盖了每个字节的证明"。SHA-256 相等只说明两个文件逐字节相同，它对读取过程跳过了哪些扇区毫无感知。`conv=noerror` 的跳过信息写在 `status=on` 的进度输出里，不在 hashlog 里。

按错误判据走的代价是为一次参数不匹配重采一块已封存的 2 TB 检材，重采还在保管链上再添一个断点，而真正的坏扇区问题原封不动——最坏的结果是问题原地不动，代价翻倍。

## 六、扩展阅读方向

哈希是全库被引用最多的工具，但它也是最容易被"当成一个函数"来理解的。

下面几组指向它的不同侧面。

<a id="section-46"></a>

### 前置基础：先弄清哈希证明不了什么

- [证据保管链与委托证明](../fundamentals-chain/fundamentals-chain-chain-of-custody-and-authorization.md) —— **本篇最重要的一条链接**。2.5 那四个哈希节点里，H0 == H1 证明"内容没变"，但证明不了"内容是从那台设备上来的"。这个缺口只能由保管链补，第五章案例里 13 天空档的场景就是它
- [取证流程与原则](../fundamentals-process/fundamentals-process-five-stage-forensics-process.md) —— 哈希链的四个节点对应流程里的哪几个环节。不先知道流程，"分析前后各算一次"的"分析"就没有边界
- [取证概念与分类](fundamentals-concepts-digital-forensics-concepts.md) —— 物理取证与逻辑取证的差别，可重复性为什么是证据能力的底线。**哈希是可重复性最直接的体现**

<a id="section-47"></a>

### 同层深入：同一问题的其他解法

- [近似匹配与模糊哈希](fundamentals-concepts-fuzzy-hashing.md) —— **本篇与它是最容易混的一对**。哈希回答"是否逐比特相同"，模糊哈希回答"是否高度相似"；ssdeep 与 TLSH 的输出格式、阈值含义、误报来源全都不一样。第四章陷阱 11 讲的正是把相似度当同一性的后果
- [时间戳换算](fundamentals-concepts-timestamps-and-timezones.md) —— 哈希与时间戳是取证里最基础的两个"客观锚点"。时间戳的问题是纪元和精度（FILETIME 100ns、DOS 2 秒、ext4 纳秒），**两者的误判都会直接变成错误的结论**
- [反取证手法与时间戳篡改检测](fundamentals-concepts-anti-forensics-and-timestamp-tampering.md) —— 那篇的核心结论是"要坐实篡改必须引入 MFT 之外的独立时钟"。**哈希正好是那类独立时钟的一种**，两篇合起来看才完整

<a id="section-48"></a>

### 相邻议题：哈希在证据处理链上的落点

- [证据文件格式](../fundamentals-chain/fundamentals-chain-dd-e01-aff4-evidence-formats.md) —— **第四章陷阱 8 的完整依据**。E01 内嵌哈希、VMDK 块 CRC、DD 无自校验，三者的"哈希对象"完全不同，这是本篇最容易被误用的地方
- [镜像制作](../../imaging/imaging-acquire/imaging-acquire-disk-imaging-and-evidence-preservation.md) —— `dcfldd hash=md5,sha256 hashlog=...` 的参数选择与坏扇区策略。哈希必须在采集时同步算，这是第三章步骤 1 的核心
- [只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md) —— H2/H3 这一对存在的唯一理由。如果分析过程根本没可能改写数据，这两次哈希就是形式；但挂载后的裸流确实可能被写入，所以它们必要
- [数据库与配置文件加密](../../crypto/crypto-app/crypto-app-database-configuration-decryption.md) —— 加密内容的哈希没有"内容意义"，只能证明密文未变。**这是"哈希对象的语义依赖对象类型"最明显的一处**
- [通用密码恢复](../../crypto/crypto-app/crypto-app-passware-and-password-recovery.md) —— 本篇步骤 6 的下游。**强调授权 + 最小化 + 脱敏**，路径 B 的每一步都要走这个前提

<a id="section-49"></a>

### 工具与规范：把判据落到可执行的命令上

- **命令行速查** —— 本篇第七章按用途分七组列了 `sha256sum` / `md5sum` / `dcfldd` / `ewfverify` / `hashdeep` 的具体调用形式，包括**分窗哈希的 16 MB 窗与 4 MB 跳距**这类参数怎么定。参数取值不是本章重点，用的时候回本文档末章查
- NSRL 与已知文件库 —— 本篇 2.6 讲了实战价值，但**导入构建、基线库自建、误报率控制**属于另一类工作。本库暂无专篇，涉及这部分时以 NSRL 官方文档为准

<a id="section-50"></a>

### 判据与反例：哈希用错的几种典型形态

- [浏览器密码库与 Token 解密](../../crypto/crypto-app/crypto-app-browser-passwords-and-tokens.md) —— DPAPI 主密钥与密码哈希是完全不同的两类对象，混淆会得出"数据库被改了"的错误指控
- [容器逃逸与运行时痕迹](../../server/server-k8s/server-k8s-container-escape-and-runtime-artifacts.md) —— 镜像摘要（image digest）也是哈希的一种形态，但它的语义是**内容寻址**而非完整性断言，两者的判读规则相反
- [SQLite-WAL 取证](../../mobile/mobile-database/mobile-database-sqlite-wal.md) —— 数据库文件的哈希会随正常写入而变化。**在活体系统上重算哈希等于制造假异常**，这是"哈希用错时机"的典型
- [术语查表](https://www.digiforensics.cn/wiki/digiforensics-glossary)—— `MD5` / `SHA-256` / `NSRL` / `Known Hash` 的定义。"Known Hash" 与 "Known File" 的区别值得单独看一眼：前者是哈希值集合，后者是文件集合，NSRL 同时提供两者且两者不是一一对应。

## 七、命令速查

```bash
# 环境：Ubuntu/Debian，apt install dcfldd ewf-tools coreutils

# 1) 基本计算
md5sum    file
sha1sum   file
sha256sum file
sha512sum file

# 2) 标准测试向量（可自行验证算法行为）
printf 'abc' | md5sum        # 900150983cd24fb0d6963f7d28e17f72
printf 'abc' | sha256sum     # ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad
printf ''   | md5sum        # d41d8cd98f00b204e9800998ecf8427e

# 3) 采集时同步计算（最佳实践）
sudo dcfldd if=/dev/sdX of=DigiForensics.dd \
     hash=md5,sha256 hashlog=DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on

# 4) 独立复算
sha256sum DigiForensics.dd

# 5) E01 容器验证
ewfverify DigiForensics.E01

# 6) 分窗哈希（故障盘）
sudo dcfldd if=/dev/sdX of=DigiForensics.dd \
     hash=sha256 hashwindow=512M hashlog=DigiForensics.window.log \
     bs=4M conv=noerror,sync status=on

# 7) 批量哈希 + 已知库比对
find /mnt/case -type f -exec sha256sum {} \; > allfiles.sha256
hfind allfiles.sha256

# 8) 密码哈希识别与破解（仅限合法授权）
hashcat -m 1000 --example-hashes
hashcat -m 1000 -a 0 hashes.txt rockyou.txt
hashcat -m 1000 -a 3 hashes.txt '?l?l?l?l?l?l?l?l'
hashcat --session=dg001 --restore

# 确认模式号与算法的对应关系（不同版本输出格式略有差异）
hashcat --example-hashes | grep -A1 'Hash mode #1000' | grep Name
hashcat -m 1000 --example-hashes
```
