# 反取证手法与时间戳篡改检测

> **定位**：本篇讨论的不是「如何隐藏痕迹」，而是**痕迹被隐藏后如何被识别出来**。核心结论只有一句：MFT 内部的一致性检查最多只能把文件判为「存疑」，要坐实篡改必须引入 MFT 之外的独立时钟。
>
> **与本板块其他文章的关系**：[时间戳换算](fundamentals-concepts-timestamps-and-timezones.md) 讲的是「怎么正确读时间戳」，本文讲的是「读出来之后怎么发现它在骗你」。前者是格式与换算，后者是对抗与验证——两者都必须掌握，缺一不可。
>
> **读者前提**：理解 MFT 记录结构与 `$STANDARD_INFORMATION` / `$FILE_NAME` 两个属性（见 [NTFS 结构与 MFT 解析](../../filesystem/filesystem-ntfs/filesystem-ntfs-ntfs-master-file-table.md)），并已掌握 [USN 日志与文件操作时间线](../../computer/computer-execution/computer-execution-usn-journal-timeline.md)。

**关键词**：timestomp · 时间戳篡改 · $STANDARD_INFORMATION · $FILE_NAME · MFT Modified · 反取证 · USN 交叉验证 · 亚秒精度 · 阴性发现


<a id="section-1"></a>

## 一、概述

时间戳在取证报告里承担的角色很重——「该文件于某时创建」「该用户在某时访问过目标文档」。但它的可修改性在所有工件里排第一：改一个文件的时间戳不需要管理员权限、不触发安全审计、不留下新的文件内容，只改动 MFT 里的几个数字。

这份脆弱性有个不对称。破坏真实性很容易，任意用户态程序调 `SetFileTime` 即可，通常不需要特权；恢复真实性很难，被改掉的数值没有备份，原值不保留在介质上。于是能高置信度地证明「这个时间戳是假的」，但几乎不可能高置信度地证明「这个时间戳是真的」——除非引入一个篡改者没碰过的独立时钟。

检测能力的来源是 NTFS 的双属性结构。每个 MFT 记录里有八个 FILETIME 值，分属 `$STANDARD_INFORMATION`（$SI，0x10）与 `$FILE_NAME`（$FN，0x30）两个属性，语义一一对应：Created 偏移 +0x00 / +0x08，Modified 偏移 +0x08 / +0x10，MFT Modified 偏移 +0x10 / +0x18，Accessed 偏移 +0x18 / +0x20。

都是 64 位 FILETIME，纪元 1601-01-01 UTC，单位 100 纳秒。

$SI 的第四个值最容易被搞错。媒体上常把它叫「MFT Modified」「MFT Changed」或「Change Time」，准确语义是「这条 MFT 记录本身最后一次被更新」——改名、改权限、改时间戳、写入新数据流都会推进它，它不是文件的第四个业务时间。单纯读取通常不会使 NTFS MFT 记录修改时间必然推进，所以 $SI 的 MFT Modified 晚于 $SI 其他三个值是正常状态而不是异常。判据只能是差值是否异常大（示例阈值用 30 天），而不是「是否存在差距」。

两套属性的更新时机不对称。$SI 由用户态 API 直接控制，`CreateFile`/`WriteFile`/`ReadFile`/`SetFileTime`/重命名/属性修改都会更新它。$FN 只在名字变化时更新，触发条件只有首次命名、重命名、跨目录移动三个。$SI 一直在动、$FN 长期不动，这构成了整个检测体系的基石。

`SetFileTime` 的文档化能力是三个字段：`$SI` 的 creation、last access、last write。`$SI` 的 MFT Modified 不在其列，由内核在记录写入时自动设为当前时刻，这就是它常被称为「漏出来的真实时间」的原因。$FN 四值对普通用户态程序没有直接写接口，改它需要绕过内核。

典型 timestomp 之后 $SI 三值是伪造的 2019-05-20 02:02:02.0000000，$SI 的 MFT Modified 是真实的 2024-03-16 09:13:58.6042217，而 $FN 四值保留着 2024-03-15 18:58:13.4471902 这个原样。

$SI 与 $FN 的 Created 差了将近五年，这已经在 MFT 内部构成强信号，但仍然是信号而不是确证。

$SI/$FN 差异就是篡改的「宽度」，纯 MFT 内部可得，不需要任何外部证据。它的上限也很明确：懂行的操作者会做「双重改名」——先 rename a.txt → a.tmp 强制 $FN 跟着走，再 `SetFileTime` 回拨，再 rename a.tmp → a.txt 让 $FN 携带伪造值。

完成后两套时间完全一致，$FN 这条旁证失效。但这一步挡不住别的东西：两次重命名都会写 USN 日志且时间是内核打的，两次重命名都要过 `$LogFile` 留下重命名事务，有卷影副本的话旧快照里存着改之前的 $FN 值。所以 $SI/$FN 一致恰恰是「有人处理过」的信号，交叉验证才是兜底。

亚秒精度提供一条高价值痕迹。FILETIME 的分辨率是 100 纳秒，内核时钟不会产生整齐的亚秒零，真实活动时间戳长这样：`2024-03-15 18:58:13.4471902`。而大量 timestomp 工具在写值前把时间截断到整秒，结果是 `2019-05-20 02:02:02.0000000`。

判据是：同一批次文件里若一批文件的 $SI 四个时间亚秒部分全为 0，而同卷其他文件不是这样，这是高价值信号——真实活动的亚秒部分是噪声，整秒截断会把噪声完全抹平，而一个文件系统上不会有大批文件恰好共享同一个亚秒模式。

这条判据的边界同样明确。填了随机亚秒的工具直接绕过它，所以漏检不等于不存在；老旧安装程序与部分复制工具会产出整齐的时间，会有假阳性；对 FAT/exFAT 完全不适用，因为 DOS 时间格式结构上就没有亚秒部分，判据必然全量假阳性。$SI 四值中三个相同这条判据也必须以统计形式使用——单文件三个时间相同在正常场景下相当常见，价值在于一个目录下 80% 的文件集中出现、亚秒全为 0、时间戳集中在某一分钟。

检测脚本实现 7 条判据，按证据强度分两级，硬矛盾（H1 SI 创建晚于 SI 修改、H2 SI 四值全为 0、H3 FAT 目录项时间早于 1980-01-01）是正常文件系统活动不可能产生的，弱信号（W1 SI/FN 创建时间分歧超 365 天、W2 亚秒全为 0、W3 SI 四值中三个相同、W4 MFT 变更时间滞后超 30 天）需要旁证。

输出分 `TAMPERED`/`SUSPECT`/`CONSISTENT` 三级。阈值必须从数据里来而不是从经验来：先在已知干净样本上统计分布，取「正常数据里的极值 + 余量」，或用分位数。`GAP_D = 365.0` 与 `AGE_D = 30.0` 是示例值不是推荐值。

上述 7 条判据仅适用于 NTFS。ext4 的普通目录项（如 `ext4_dir_entry_2`）不保存冗余 `i_ctime`；时间信息主要位于 inode，需结合 journal、目录增删痕迹和其他工件交叉核查，可用 `debugfs`、`istat` 读，不能用 `stat`；把 NTFS 判据原样搬过去会全部落空，而「什么都没检出」与「该卷干净」在结论里长得一模一样。

APFS 与 HFS+ 同样不适用。FAT 的时间字段限制是 DOS 时间只有 16 位字段、起点 1980-01-01、粒度 2 秒，结构上无法表达 1980 年之前的日期，字段会回绕看起来像正常时间。

检测的关键一步是引入独立时钟。USN 日志是最容易取到的一个，时间戳由内核在写入时打上，篡改者改不了。判读它靠三个 Reason 值：`FILE_CREATE` 是 `0x00000100`；成对的 `RENAME_OLD_NAME`（`0x00001000`）+ `RENAME_NEW_NAME`（`0x00002000`）连续出现两次且最终名字与初始相同，是双重改名的直接指纹；

`BASIC_INFO_CHANGE` 是 `0x00008000`，数值要记准，`0x00004000` 是 `INDEXABLE_CHANGE`，这两个经常被工具文档写反。`BASIC_INFO_CHANGE` 记录的是元数据被写这个动作而非内容被改，两类事件在时间线上要画成两个不同的事件点。

`CLOSE`（`0x80000000`）是伴随标志，统计实质操作时必须排除。

USN 日志可能被清空或被滚转覆盖（`$Max` 默认约 64 MB），这时要找第二个独立时钟。Sysmon Event ID 2 价值最高，它含 `CreationUtcTime`（新值）与 `PreviousCreationUtcTime`（原值），在篡改发生的那一刻就记下了改前值，缺点是默认不启用不能假设它存在。

Prefetch 是内核写入的执行时间，文件路径哈希可与 MFT 交叉。Amcache / ShimCache 记录程序路径与最后运行时间。事件日志的 Security 104/1102 记录日志被清。`$LogFile` 含元数据事务流水。卷影副本的旧快照里存的是篡改前的 $FN 原值，对同一 MFT 记录号分别解析主卷与快照，两套 $FN 值 diff 出来的差异即被改写的时间。

分层定级把线索转成结论，依据是证据组合而不是判据数量。命中 5 条弱信号但没有外部时钟，定级仍是 L2，因为存在「所有弱信号都源于同一次合法批量操作」的可能。L1 无异常对应「未发现时间戳异常特征」；L2 仅命中弱信号，对应「时间戳存在异常特征，与已知篡改手法的形态相符，需进一步核实」；

L3 弱信号加外部时钟矛盾（USN / Prefetch / 快照任一），对应「时间戳与独立记录的时间存在冲突，判定时间戳已被改写」；L4 抓到改写动作的直接记录（Sysmon EID 2 / USN `BASIC_INFO_CHANGE` 时刻吻合 / 快照 diff 出原值），对应「已确认该文件时间戳被改写，改写动作发生于 T，原始时间戳为 V」。

L3 与 L4 的区别在于 L4 拿到了动作或原值，L3 只有矛盾。「独立时钟」这四个字要出现在报告里，它是 L2 和 L3 的分界线。

$SI 的 MFT Modified 是上界不是点估计。它记的是「这条 MFT 记录最后一次被更新」，修改权限、添加数据流、被同步软件 touch 都会推进它，所以只能推出「该文件的 MFT 记录在 T 时刻被更新过」或「不早于这个时刻仍然存在或刚被操作过」，推不出「文件创建于 T」。要拿创建时刻得用 $FN Created、USN `FILE_CREATE` 记录或 Prefetch 首次执行时间。

反取证不是单一技术，是一个按「动的是什么」分层的谱系。元数据层动的是 MFT / inode 时间字段，包括时间戳回拨与时间戳清零，本篇深度覆盖；同层的「改文件名 / 扩展名」动的是目录项，只部分覆盖。数据层动的是数据簇，覆写文件内容或空闲空间，本篇只说明检测思路；同层的加壳、隐写动的是文件内部结构。

痕迹层动的是日志文件本身，清除事件日志、Prefetch、USN 属于交叉验证范围；同层的禁用时间戳更新动的是系统配置。密钥层动的是全部内容，加密卷、EFS、BitLocker 归入加密板块。排查清单按这五层逐层走，共十项，从事件日志、审计策略、USN 日志、Prefetch、卷影副本，到文件时间戳、空闲空间、回收站、系统配置、MFT 记录复用。

「清日志」类操作最好检，因为它们自己会留下新日志——Security 1102 记录审计日志被清、Security 104 记录某个日志文件被清。

时间戳一致性检测查不了删除型反取证。一个文件被删除后，$MFT 记录还在、$FN 属性还在、目录项也还在（只是被标记为已删除），时间戳字段一个都不会少，而被删文件的四个时间之间的关系本来就是自洽的。删除线要单独看：`$MFT` 记录的状态位、`$FILE_NAME` 中的 `FILE_NAME_FLAG_DELETED`（父目录索引里的删除标记）、`$I30` 目录索引的 slack、未分配簇的内容残留、回收站 `$RECYCLE.BIN`。

阴性表述也分开写：「时间戳字段未发现改写特征」与「已删除文件共 N 个，其时间戳字段未见异常」覆盖的是完全不同的范围。

阴性结论不能用绝对表述。「本机未发现反取证痕迹」这句话在技术上不可能成立，因为检材只是某个时间点的快照，痕迹可能在镜像制作之前就已被抹掉，而抹除动作本身留下的痕迹也随之一并消失。合格的写法是范围 + 检查 + 未发现三段式，四个要素是检查了什么（7 条判据）、检查了多少（记录号区间）、结论的强度（未发现命中硬矛盾）、没查什么（未覆盖范围）。

「USN 日志为空」的正确表述是「未获取到 USN 日志数据」，不是「USN 日志中无篡改记录」——日志为空的五种原因里只有「确实没有相关记录」是正常解释。

分析过程本身会改变时间戳，因此有三条纪律。所有挂载一律 `-o ro` 加 `noatime`；篡改检测必须在任何提取操作之前跑，用原始 MFT 一次成型，不要反复重跑；检测脚本的输出与 MFT 导出文件一起归档，作为「检测时的原始输入」便于第三方复核。

## 二、核心原理

<a id="section-3"></a>

### 2.1 NTFS 的八个时间戳

每个 MFT 记录里有**八个** FILETIME 值，分属两个属性、语义完全对应：

| 语义 | `$STANDARD_INFORMATION`（$SI，0x10） | `$FILE_NAME`（$FN，0x30） |
|---|---|---|
| Created 创建 | 偏移 +0x00 | 偏移 +0x08 |
| Modified 内容修改 | 偏移 +0x08 | 偏移 +0x10 |
| **MFT Modified 记录变更** | **偏移 +0x10** | 偏移 +0x18 |
| Accessed 访问 | 偏移 +0x18 | 偏移 +0x20 |

都是 64 位 FILETIME，纪元 1601-01-01 UTC，单位 100 纳秒。

> ⚠️ **第四个值的名字最容易被搞错。** 媒体上常把它叫「MFT Modified」「MFT Changed」或「Change Time」。它的准确语义是「这条 MFT 记录本身最后一次被更新是什么时候」——任何属性变化（改名、改权限、改时间戳、写入新数据流）都会推进它，它不是文件的第四个业务时间。
>
> 业内流传的「NTFS 记录创建 / 修改 / 访问 / 变更四个时间」这个说法里的「变更」，指的就是它。这一点在 2.3 会直接决定检测的成败。

<a id="section-4"></a>

### 2.2 Windows 自身如何更新这八个值

要设计判据，先必须知道正常情况下这些值怎么变。关键事实：

`$STANDARD_INFORMATION` 由用户态 API 直接控制。

`CreateFile` / `WriteFile` / `ReadFile` / `SetFileTime` / 重命名 / 属性修改，都会更新 $SI。资源管理器显示的属性对话框、绝大多数取证工具显示的时间，都是这一组。

`$FILE_NAME` 只在「名字变了」时更新。

具体触发条件只有三个：首次命名、重命名、跨目录移动（本质也是重命名）。文件改名之后，如果名字不再变，$FN 就长期静止。

这条「$SI 一直在动、$FN 长期不动」的不对称，是整个检测体系的基石。

MFT Modified 通常由内核维护，普通 API 改不到。

`SetFileTime` 的文档化能力是三个字段：creation、last access、last write。$SI 的第四个值（MFT Modified）不在其列，Windows 会在记录被写入时自动把它设为当前时刻。这就是为什么它常被称为「漏出来的真实时间」。

Windows Vista 及以后默认关闭 last access 更新。

注册表项 `HKLM\SYSTEM\CurrentControlSet\Control\FileSystem\NtfsDisableLastAccessUpdate` 默认为 `1`，意味着读取文件不再更新访问时间。

这带来两个后果：现代系统上 $SI 的 Accessed 值往往比 Modified 还旧，看起来「反常」但完全正常；而一些工具会通过修改该注册表项来「抹掉」访问痕迹——这个动作本身在 `Sysmon Event ID 13` 和该注册表的 LastWriteTime 上留痕。

<a id="section-5"></a>

### 2.3 SetFileTime 能改什么、不能改什么

这是整个检测逻辑的因果起点。

```
可以改（$SI 三个值）：
    $SI Created   ← SetFileTime(hFile, &creation, ...)
    $SI Modified  ← SetFileTime(hFile, NULL, &lastwrite, ...)
    $SI Accessed  ← SetFileTime(hFile, NULL, &lastaccess, ...)

改不了：
    $SI MFT Modified  ← 不在 SetFileTime 的参数里，由内核在记录写入时自动维护
    $FN 四值          ← 用户态没有接口直接写；改它需要绕过内核（改盘 / 双重改名）
```

于是典型 timestomp 之后，一条 MFT 记录会长这样：

```
$STANDARD_INFORMATION
    Created:   2019-05-20 02:02:02.0000000   ← 伪造
    Modified:  2019-05-20 02:02:02.0000000   ← 伪造
    MFT Mod:   2024-03-16 09:13:58.6042217   ← 真实：伪造动作发生的时刻
    Accessed:  2019-05-20 02:02:02.0000000   ← 伪造

$FILE_NAME
    Created:   2024-03-15 18:58:13.4471902   ← 真实
    Modified:  2024-03-15 18:58:13.4471902   ← 真实
    MFT Mod:   2024-03-15 18:58:13.4471902   ← 真实
    Accessed:  2024-03-15 18:58:13.4471902   ← 真实
```

读这张表的正确方式是：$SI 的 MFT Modified 晚于 $SI 的其他三个值，是「正常状态」而不是「异常」。 每一个文件在被读取时都会推进 MFT Modified。判据应该是「这个差距是否异常大」，而不是「是否存在差距」。

而 $SI 与 $FN 的 Created 差了将近五年，这在单纯的 MFT 内部就已经是一个强信号。

但它仍然是信号，不是确证。原因见 4.1。

<a id="section-6"></a>

### 2.4 SI/FN 不对称：检测能力的来源

$FN 的不可写（对普通用户态程序而言）成就了两件事。

**第一，$FN 成为 $SI 的旁证。** 篡改者改了 $SI，$FN 保持原样，两者的差值就是篡改的「宽度」。这是纯 MFT 内部可得的、不需要任何外部证据的信号。

第二，懂行的操作者会做「双重改名」来消除这个信号：

```
1. rename a.txt → a.tmp        （强制 $FN 跟着 SI 走）
2. SetFileTime                 （此时 $SI 与 $FN 都被回拨）
3. rename a.tmp → a.txt        （$FN 再次更新，携带伪造值）
```

完成后两套时间完全一致，$FN 这条旁证失效。

但这一步挡不住别的东西：

- 两次重命名都会写 USN 日志，日志里的时间是内核打的，伪造不了；
- 两次重命名都要过 `$LogFile`，会在事务日志里留下重命名事务；
- 如果有卷影副本，旧快照里存着改之前的 $FN 值，diff 一下就出来。

所以「$SI/$FN 不一致」的检测能力是有上限的，交叉验证才是兜底。

<a id="section-7"></a>

### 2.5 亚秒精度：一条不起眼的高价值痕迹

FILETIME 的分辨率是 100 纳秒，**内核时钟不会产生整齐的亚秒零**。真实活动时间戳长这样：

```
2024-03-15 18:58:13.4471902
2024-03-16 09:13:58.6042217
```

而大量 timestomp 工具在写值之前会把时间**截断到整秒**，结果是：

```
2019-05-20 02:02:02.0000000
2019-05-20 02:02:02.0000000
```

判据：同一批次文件里，若一批文件的 $SI 四个时间亚秒部分全为 0，而同卷其他文件不是这样，这是一个高价值信号。

为什么说它高价值：真实活动的亚秒部分是「噪声」，而这种噪声在整秒截断下会被完全抹平。一个文件系统上不会有大批文件恰好共享同一个亚秒模式。

**它的边界必须说清楚：**

- 优质工具会填随机亚秒，直接绕过这条判据 → **漏检不等于不存在**；
- 某些批量处理（老旧安装程序、部分复制工具）会产出整齐的时间 → 会有假阳性；
- **对 FAT/exFAT 完全不适用**——DOS 时间格式结构上就没有亚秒部分，判据必然全量假阳性。

<a id="section-8"></a>

### 2.6 其他文件系统的对应关系

timestomp 不是 NTFS 独有的。各文件系统的「可改/不可改」边界不同，判据必须逐一对应：

| 文件系统 | 存放位置 | 篡改面 | 本篇判据是否适用 |
|---|---|---|---|
| **NTFS** | $SI / $FN 双属性 | $SI 三值 | ✅ 全部适用 |
| **ext4** | inode + 目录项 | inode 的 `i_ctime` / `i_mtime` / `i_atime` + 目录项时间 | 部分（见下） |
| **APFS** | inode + 目录项 | 多数时间戳可改 | ❌ 不适用本篇判据 |
| **FAT/exFAT** | 目录项 16 位字段 | 3 个 DOS 时间 | ❌ 精度与表达力都不够 |
| **HFS+** | 目录 + 文件 Fork | 多数可改 | ❌ 不适用 |

**ext4 的特殊性**：ext4 在目录项里冗余存了一份 `i_ctime`，用来判断「文件是否在目录项缓存有效期内被改过」。如果 inode 的时间被回拨而目录项没改，或反之，`ls` 与 `stat` 可能给出不同的结果。

文件系统级别的「inode 与目录项时间不一致」是 ext4 版的 SI/FN 对照，但要通过底层工具（`debugfs`、`istat`）而不是 `stat` 才能看到。

**FAT 的时间字段限制**：DOS 时间是 16 位字段，起点 1980-01-01、粒度 2 秒，结构上无法表达 1980 年之前的日期。把一个文件的 FAT 时间设成 1970 年或更早，字段会回绕，看起来像 1980 年之后的一个正常时间。

在 FAT 上做时间戳篡改的痕迹检测，可用的判据空间很小——可表达的时间范围太窄，异常反而不容易显现。

## 三、操作步骤

<a id="section-10"></a>

### 3.1 导出并规范化 MFT 时间字段

第一步是把 MFT 里的八个时间抽成一张可排序、可计算的表。用 `MFTECmd` 导出：

```bash
# 从镜像导出 MFT 记录为 CSV（Windows 侧）
MFTECmd.exe -f DigiForensics.dd -m "Windows NTFS" --csv .\out --bodyfile .\body

# 生成的 CSV 中文件名通常是 record100-body-0.csv 之类
# 关键列：RecordNumber / FileName / Created / Modified / MFTModified / Accessed
#          + Created File Name / Modified File Name / MFT Modified File Name
```

Linux 侧用 Sleuth Kit：

```bash
# 只取 MFT（-1 表示 1 号 MFT 记录）
fls -r -p -o 2048 DigiForensics.dd > mft-body.txt

# 批量导出全部记录的原始十六进制（供自写解析器使用）
icat -o 2048 DigiForensics.dd 24-90 | xxd -r -p > mft-records.bin
```

**规范化成 TSV，字段顺序与本篇脚本一致：**

```
si_created  si_modified  si_accessed  si_mftmod  fn_created  fn_modified  fn_mftmod  fn_accessed  record  fs  full_path
```

两个要求：

- 时间一律转成 **FILETIME 整数**（十进制），不要保留原始日期字符串——字符串比较无法做算术，跨格式阈值判断会失效；
- **文件名里可能含 TAB**，用 `\\	` 转义或改用 CSV，否则字段会错位。

<a id="section-11"></a>

### 3.2 跑一致性检测并按等级分流

本篇配套的检测脚本实现 7 条判据，按**证据强度**分两级。**这个分级是全篇的核心，不要把弱信号当硬信号用。**

```python
# -*- coding: utf-8 -*-
"""NTFS 时间戳篡改一致性检测（概念验证）。

输入 TSV，字段用 TAB 分隔（共 11 列）：
  si_c  si_m  si_a  si_mftmod        $STANDARD_INFORMATION 四值
  fn_c  fn_m  fn_mftmod  fn_a        $FILE_NAME 四值
  record  fs  full_path
时间均为 FILETIME 整数（1601-01-01 起的 100ns），fs 取 ntfs / fat。

设计要点：MFT 内部一致性最多只能给出「存疑」，不能给出「确认篡改」。
真实的 timestomp 走 SetFileTime，改的是 $SI 四个值中的三个，
产生的矛盾全部是「弱信号」级别 —— 定罪必须靠 MFT 之外的独立时钟
（USN 日志 / $LogFile / Prefetch / 事件日志）。
"""
import sys

DAY    = 86400 * 10 ** 7      # FILETIME 一天（100ns 单位）
TICK   = 10 ** 7             # 一秒 = 10^7 个 100ns tick
DOS_EPOCH = 369 * 365 * DAY + 446 * DAY   # 1980-01-01 的 FILETIME
GAP_D    = 365.0             # SI/FN 创建时间分歧告警阈值（天）
AGE_D    = 30.0              # MFT 变更时间滞后于业务时间的合理上限（天）

RULES = []


def rule(code, level, title, why, cost):
    """注册一条判据。level: HARD=逻辑矛盾 / WEAK=需旁证。"""
    def deco(fn):
        RULES.append({'code': code, 'level': level, 'title': title,
                      'why': why, 'cost': cost, 'fn': fn})
        return fn
    return deco


# ============ 硬矛盾：正常文件系统活动不可能产生 ============

@rule('H1', 'HARD', 'SI 创建晚于 SI 修改',
      '文件必须先被创建才谈得上被修改；SI 内出现反序只可能来自显式赋值',
      '这类矛盾应在报告里单列一节，混进「时间线不一致」的泛化描述会丢掉唯一能定性的一击')
def h1(r):
    return r['si_c'] > r['si_m']


@rule('H2', 'HARD', 'SI 四值全为 0',
      'Windows 自身的写入路径不会产出全零时间戳',
      '全零记录常被当成「格式解析失败」整批丢弃，实际是删除型反取证的直接标志')
def h2(r):
    return r['si_c'] == 0 and r['si_m'] == 0 and r['si_a'] == 0 and r['si_mftmod'] == 0


@rule('H3', 'HARD', 'FAT 目录项时间早于 1980-01-01',
      'FAT 目录项的 DOS 时间字段结构上无法表达 1980 年之前的日期',
      '判据仅对 FAT 族有效；套到 NTFS 上无意义，因为 NTFS 起点是 1601 年')
def h3(r):
    if r['fs'] != 'fat':
        return False
    return any(r[k] < DOS_EPOCH for k in ('si_c', 'si_m', 'si_a'))


# ============ 弱信号：需 MFT 之外的旁证才能定性 ============

@rule('W1', 'WEAK', 'SI 与 FN 创建时间分歧超过 %g 天' % GAP_D,
      '改名会同时推进两套时间，只推进一边说明有工具只改了一边',
      '正常的大跨度改名/迁移也会命中；误当成结论会写出无法辩护的「已篡改」')
def w1(r):
    return abs(r['si_c'] - r['fn_c']) > GAP_D * DAY


@rule('W2', 'WEAK', 'SI 四值的亚秒部分全为 0',
      '内核时钟不产生整齐的亚秒零，只有按整秒写入的工具会',
      '高价值启发式；但填了随机亚秒的工具会绕过，漏检不等于不存在')
def w2(r):
    # FAT 的时间根本没有亚秒精度，对 FAT 判定此项必然假阳性
    if r['fs'] != 'ntfs':
        return False
    return all(r[k] % TICK == 0 for k in ('si_c', 'si_m', 'si_a', 'si_mftmod'))


@rule('W3', 'WEAK', 'SI 四值中三个相同',
      '创建 / 修改 / 访问三种语义在同一刻发生，自然活动几乎不产生',
      '批量解包与迁移拷贝也会命中，须与同批次文件一起看分布')
def w3(r):
    return len({r['si_c'], r['si_m'], r['si_a']}) == 1


@rule('W4', 'WEAK', 'MFT 变更时间滞后业务时间超过 %g 天' % AGE_D,
      '元数据最后变更时刻明显晚于内容修改时刻',
      '跨年复制的旧文件会命中；配合 W1 同时出现才有意义')
def w4(r):
    return r['si_mftmod'] - max(r['si_c'], r['si_m']) > AGE_D * DAY


HDR = ['si_c', 'si_m', 'si_a', 'si_mftmod',
       'fn_c', 'fn_m', 'fn_mftmod', 'fn_a', 'record', 'fs', 'path']

def verdict(r):
    hit = [x for x in RULES if x['fn'](r)]
    hard = [x for x in hit if x['level'] == 'HARD']
    weak = [x for x in hit if x['level'] == 'WEAK']
    if hard:
        return 'TAMPERED', hard, weak
    if weak:
        return 'SUSPECT', [], weak
    return 'CONSISTENT', [], []

def main():
    tally = {'TAMPERED': 0, 'SUSPECT': 0, 'CONSISTENT': 0}
    for i, line in enumerate(sys.stdin, 1):
        p = line.rstrip('\
').split('\	')
        if len(p) != len(HDR):
            print('第 %d 行字段数 %d，应为 %d' % (i, len(p), len(HDR)),
                  file=sys.stderr)
            continue
        r = dict(zip(HDR, p))
        for k in HDR[:8]:
            r[k] = int(r[k])
        v, hard, weak = verdict(r)
        tally[v] += 1
        print('[%s] %s' % (v, r['path']))
        for x in hard + weak:
            print('    %-3s %s' % (x['code'], x['title']))
            print('         机理: %s' % x['why'])
            print('         误判代价: %s' % x['cost'])
    print('\
合计: 硬矛盾 %d / 存疑 %d / 一致 %d' %
          (tally['TAMPERED'], tally['SUSPECT'], tally['CONSISTENT']))

if __name__ == '__main__':
    main()
```

运行：

```bash
python3 tsdetect.py < mft-times.tsv
```

**输出分三级，含义完全不同：**

| 标记 | 含义 | 可以写进报告的措辞 |
|---|---|---|
| `TAMPERED` | 命中硬矛盾，正常文件系统活动不可能产生 | 「存在明确的元数据异常，判定为人为改写」 |
| `SUSPECT` | 命中弱信号，需旁证 | 「时间戳存在异常特征，建议结合其他工件核实」 |
| `CONSISTENT` | 未命中本篇判据 | 「未发现时间戳异常特征」——注意不等于「时间戳真实」 |

<a id="section-12"></a>

### 3.3 引入 USN 日志做交叉验证

这是把 `SUSPECT` 推向定论的关键一步。USN 日志的时间戳由内核在写入时打上，篡改者改不了。

```bash
# Linux 侧（The Sleuth Kit，解析 $UsnJrnl:$J）
usnjrnl -o 2048 DigiForensics.dd > usn.csv

# Windows 侧
MFTECmd.exe -f "DigiForensics.dd" -m "Windows NTFS" -b 0 \
            -F -d "C:\$Extend\$UsnJrnl" --csv .\usn-out
```

在 `usn.csv` 中按文件名查找该文件的历史记录，重点看三行：

| USN Reason | 十六进制 | 含义 |
|---|---|---|
| `FILE_CREATE` | `0x00000100` | 文件创建，内核时间戳可信 |
| `RENAME_OLD_NAME` + `RENAME_NEW_NAME` | `0x00001000` + `0x00002000` | 重命名，**双重改名会留下成对记录** |
| `BASIC_INFO_CHANGE` | `0x00008000` | **时间戳或属性被改 —— 这就是篡改动作本身** |

> ⚠️ **数值要记准**：`BASIC_INFO_CHANGE` 是 `0x00008000`，`0x00004000` 是 `INDEXABLE_CHANGE`（内容索引属性变更）。这两个经常被工具文档写反。

**判定逻辑：**

```
若 usn.csv 中存在  BASIC_INFO_CHANGE @ T_real
且 $SI.Created      == 某个远早于 T_real 的值
且 $FN.Created      ≈ T_real

→  T_real 时刻该文件的时间戳被改成了更早的值
   篡改动作发生在 T_real，这是一条独立于 MFT 的时钟证据
```

成对的 `RENAME_OLD_NAME` / `RENAME_NEW_NAME` 连续出现两次、且最终名字与初始名字相同，是「双重改名」的直接指纹——它说明操作者在刻意消除 $SI/$FN 差异。USN 里的重命名时间戳是真实的，**这部分伪造不掉**。

细节见 [USN 日志与文件操作时间线](../../computer/computer-execution/computer-execution-usn-journal-timeline.md)。

<a id="section-13"></a>

### 3.4 引入执行痕迹做独立时钟

USN 日志可能被清空或被滚转覆盖（`$Max` 限制体积，默认约 64 MB）。**这时要找第二个独立时钟。**

| 来源 | 提取方式 | 特点 |
|---|---|---|
| **Prefetch** | `SCAuthenticode` / 专用解析器读 `C:\Windows\Prefetch` | 内核写入，含执行时间；**文件路径哈希可与 MFT 交叉** |
| **Amcache / ShimCache** | `ShimCache` 解析、`AMCache.hve` 挂载 | 记录程序路径与最后运行时间 |
| **事件日志** | `evtx` 解析 | Security 104/1102 记录日志被清 |
| **$LogFile** | `LogFile` 解析工具 | 元数据事务流水，含操作时间 |
| **卷影副本** | 逐个挂载旧快照 | **旧快照里的 $FN 是篡改前的原值** |
| **Sysmon** | `evtx` 解析 | Event ID 2 直接记录创建时间被改，含改前改后两值 |

其中 **Sysmon Event ID 2** 价值最高，它直接给出「进程改了某文件的创建时间」这个动作本身，含 `CreationUtcTime`（新值）与 `PreviousCreationUtcTime`（原值）：

```xml
<!-- Sysmon Event ID 2 关键字段 -->
<ProcessGuid>{...}</ProcessGuid>
<TargetFilename>C:\Temp\svc.exe</TargetFilename>
<CreationUtcTime>2019-05-20 02:02:02.0000000</CreationUtcTime>   <!-- 伪造值 -->
<PreviousCreationUtcTime>2024-03-15 18:58:13.4471902</PreviousCreationUtcTime>  <!-- 真值 -->
```

这种日志**在篡改发生的那一刻就被记下了改前值**，是最干净的证据。缺点是 Sysmon 默认不启用，不能假设它存在。

**卷影副本的 diff 值得单独做**，因为它能拿回原值而非旁证：

```bash
# 列出所有卷影副本
vssadmin list shadows

# 把旧快照只读挂载出来，单独解析它的 MFT
mount -o ro,loop,offset=$((SHADOW_OFFSET_SECTORS*512)) snapshot.vhd /mnt/vss
fls -r -p -o 2048 /mnt/vss | grep -i svc.exe
```

对同一 MFT 记录号分别解析主卷与快照，两套 $FN 值 diff，差异即为被改写的时间。

<a id="section-14"></a>

### 3.5 分层定级：把线索转成结论

把 3.2 到 3.4 的结果合并，按下表定级。这张表是本篇的产出核心。

| 级别 | 证据组合 | 报告表述 |
|---|---|---|
| **L1 无异常** | 无硬矛盾、无弱信号，且无外部矛盾 | 「未发现时间戳异常特征」 |
| **L2 存疑** | 仅命中弱信号 | 「时间戳存在异常特征，与已知篡改手法的形态相符，需进一步核实」 |
| **L3 高度可疑** | 弱信号 + 外部时钟矛盾（USN / Prefetch / 快照任一） | 「时间戳与独立记录的时间存在冲突，判定时间戳已被改写」 |
| **L4 确认** | 抓到改写动作的直接记录（Sysmon EID 2 / USN BASIC_INFO_CHANGE 时刻吻合 / 快照 diff 出原值） | 「已确认该文件时间戳被改写，改写动作发生于 T，原始时间戳为 V」 |

**定级必须来自证据组合，不能来自判据数量。** 命中 5 条弱信号但没有外部时钟，定级仍然是 L2——因为存在「所有弱信号都源于同一次合法批量操作」的可能。

L3 和 L4 的区别在于：L4 拿到了动作或原值，L3 只有矛盾。

<a id="section-15"></a>

### 3.6 反取证手法的整体排查清单

时间戳篡改只是反取证的一层。完整排查按「动了什么」逐层走：

| 层 | 排查动作 | 命令 / 位置 | 关注点 |
|---|---|---|---|
| 事件日志 | Security 104/1102、System 104 | `evtx` | 记录了「谁在何时清了哪个日志」 |
| 审计策略 | 4688 / 4698 / 4719 | `evtx` | 审计被关闭的**那一刻**本身就是证据 |
| USN 日志 | `BASIC_INFO_CHANGE` 批量统计 | `usnjrnl` | 成批出现 = 批处理式篡改 |
| Prefetch | 最近修改的 Prefetch 列表 | `C:\Windows\Prefetch` | 清 Prefetch 本身留痕于目录时间 |
| 卷影副本 | `vssadmin list shadows` + 数量对比 | 系统 | 数量为 0 或偏少要解释 |
| 文件时间戳 | 跑 3.2 的一致性检测 | MFT | 见本篇 |
| 空闲空间 | 大块覆写痕迹 | 未分配簇 | 覆写只改内容不改元数据，$FN 常残留 |
| 回收站 | `$RECYCLE.BIN` 内容 | MFT | 删除只是改目录项，数据仍在 |
| 系统配置 | `NtfsDisableLastAccessUpdate` 的 LastWriteTime | 注册表 | 关掉它是为了消除访问时间 |
| MFT 记录复用 | 记录号与 `MFT Entry Reuse` 标志 | MFT | 复用后残留旧文件的痕迹 |

**「清日志」类操作最好检，因为它们自己会留下新日志**——Security 1102 记录审计日志被清、Security 104 记录某个日志文件被清。

## 四、常见陷阱

<a id="section-17"></a>

### 4.1 判据方向与文件语义

<a id="section-18"></a>

#### 陷阱 1：把「MFT Modified 晚于 Modified」当成篡改特征

**现象**：跑完一致性检测，发现几乎所有文件的 $SI MFT Modified 都晚于 $SI Modified，于是判断「全盘被篡改」。

**原因**：**这是正常状态，不是异常。** $SI 的第四个值语义是「这条 MFT 记录最后一次被更新」，任何属性变化都会推进它——读一次文件、改一次权限、改一次时间戳都会。它在设计上就**总是**不早于该文件的其他时间。Windows 自身产生的 MFT 记录里，这个值通常就是文件最后一次被访问或被操作的时刻。

**影响**：把系统正常行为报告成篡改，会让整份报告的可信度崩塌。当报告里出现「全盘 12 万个文件均存在时间戳篡改」这种结论时，对方第一反应是分析员不懂 NTFS，接下来所有真实发现都会被一起怀疑。

**核查**：判据只能写成「$SI MFT Modified 与 $SI Created/Modified 之间的差值异常大」，设一个业务上说得通的阈值（本篇示例用 30 天），而不是「存在差值」。具体对应脚本里的 W4 规则。补充旁证：若该文件的 $SI MFT Modified 恰好紧跟在某个可疑操作时间之后（而不是散落在几个月里），那个时间点才有意义。

<a id="section-19"></a>

#### 陷阱 2：把「$SI Created 晚于 $FN Created」当成不可能

**现象**：在样本里发现某文件 $SI Created 是 2024-03-15、$FN Created 是 2024-03-20，于是判定「$SI 被回拨过 5 天」。

**原因**：$FN 的 Created 天然可以晚于 $SI 的 Created。 回顾 2.2——$FN 只在名字变化时更新，而 $SI 一直在动。一个 3 月 10 日创建、3 月 20 日改名的文件，$SI Created 必然早于 $FN Created。「$SI Created < $FN Created」是改名的正常结果，不是篡改的证据。

**影响**：这条判据一旦被写进检测规则，命中率会极高（几乎所有被改过名的文件都命中），假阳性会把真信号淹掉。更麻烦的是，一旦被对方发现规则里有这条错误，**整份规则的其余部分也会被当作同样不可靠**。

**核查**：只在**方向相反**时用 $FN 做旁证——$SI Created 明显早于 $FN Created 才是信号（脚本 W1），且必须设跨度阈值（本篇 365 天）并理解其局限。更严格的做法是只在「文件当前名字 == $FN 里记录的名字」时才做这个比较：如果名字对得上，$FN 就是这次命名的记录，两者应该同源；如果对不上，$FN 记录的是更早的某个名字，比较没有意义。

<a id="section-20"></a>

#### 陷阱 3：把「SI/FN 不一致」直接写成「已篡改」

**现象**：检测到 $SI 与 $FN 创建时间相差 5 年，报告直接写「该文件时间戳已被篡改」。

**原因**：$SI/$FN 差异是**信号，不是确证**，原因有三条：安装程序、复制工具、归档解包器都可能只更新其中一套；「双重改名」（2.4）会主动消除这个差异；有些同步工具、备份还原也会让两套时间脱节。换句话说，检测不到差异不代表没篡改，检测到差异也不必然是人为反取证——它可能只是「某个工具行为不标准」。

**影响**：在司法或合规场景下，「已篡改」是一个需要承担举证责任的结论。报告里一旦出现无法辩护的定性，对方律师或审计方只需找一个正常的安装程序就能推翻它，而你建立的其他所有发现也会被牵连。

**核查**：MFT 内部的信号一律定级为 **L2 存疑**，措辞用「时间戳存在异常特征，与已知篡改手法形态相符」。**要升到 L3，必须引入 MFT 之外的独立时钟**（USN 日志的 `BASIC_INFO_CHANGE`、Prefetch 执行时间、卷影副本原值），并明确写出是哪个工件提供了这个独立时钟。「独立时钟」这四个字要出现在报告里，它是 L2 和 L3 的分界线。

<a id="section-21"></a>

#### 陷阱 4：把双重改名当成已经绕过检测

**现象**：$SI 与 $FN 完全一致，报告写「未发现该文件的 $SI/$FN 异常，时间戳可信」。

**原因**：$SI/$FN 一致恰恰是**「有人处理过」的信号**，而不是「干净」的信号。正常文件在未改名时两者本应一致，一旦有人做了「改名 → 改时间 → 改回原名」三步，$FN 也会被写成伪造值，**表面上完全自洽**。这套手法专门设计来骗过 $SI/$FN 对照。

**影响**：把「伪装得很好」读成「没有问题」，等于主动放弃了唯一能定性的证据。这比误报更危险，因为误报会被对方质疑，而漏报是**无声的**——报告读起来完全正常，时间线照常重建，而真正的时间篡改点就藏在「一切自洽」里。

**核查**：$SI/$FN 完全一致时，**转去查 USN 日志有没有成对的重命名记录**。两次连续的重命名（`RENAME_OLD_NAME` + `RENAME_NEW_NAME`）且最终名字回到原样，是这套手法的直接指纹。改用 USN 的时间戳作为真实时间基准——它是内核打的，伪造不掉。

<a id="section-22"></a>

### 4.2 阈值与精度

<a id="section-23"></a>

#### 陷阱 5：亚秒精度判据在 FAT 上全量假阳性

**现象**：把「$SI 四个时间亚秒部分全为 0」这条判据直接用在 FAT/exFAT 或手机镜像的 exFAT 分区上，结果**几乎每个文件都命中**。

**原因**：DOS 时间格式是 16 位字段，结构上就没有亚秒部分。**所有 FAT 时间戳的亚秒部分必然是 0**，这条判据在 FAT 上不是「误报」，而是恒真——它对每一个文件都会说「可疑」。同理，如果把 MFT 里的 $SI 与 $FN 时间都换算成统一格式再判亚秒，两个不同来源的值在同一秒内亚秒不一致也是正常的，不代表有人改过。

**影响**：这条判据在 FAT 上一条判据就足以让整份检测报告失效——「100% 文件命中异常」在专业读者眼里等同于「这个工具坏了」。更隐蔽的情况是脚本里没有做格式分支，在 FAT 镜像上跑出了假阳性，但报告只挑了 NTFS 分区的结果说，**留下了一个未说明的适用性缺口**。

**核查**：判据必须**先判文件系统类型再决定是否适用**。脚本里对应 `if r['fs'] != 'ntfs': return False`。另外要注意方向：**只有在比较「同一来源的原生值」时判亚秒才有意义**——$SI 内部四个值之间可以比，$FN 内部可以比，**跨来源换算后比较会引入转换误差**。已在 2.5 标注该判据不适用于 FAT 族。

<a id="section-24"></a>

#### 陷阱 6：阈值拍脑袋，写死一个「安全间隔」

**现象**：检测规则里写「若 $SI MFT Modified 与 $SI Created 相差超过 7 天则判为异常」，然后在企业环境里跑出成片告警。

**原因**：**7 天这个数字没有任何文件系统依据。** 差距大到什么程度算异常，取决于数据在系统里怎么流转：批量从移动硬盘拷进来的照片、跨年归档的项目文件、从备份还原的数据库文件，MFT 变更时间与业务时间天然可能差几个月。**阈值脱离业务场景，就是把一种误报换成另一种误报。**

**影响**：阈值过紧会产生大量假阳性，分析员要么被淹没要么开始忽略告警；阈值过松会漏掉真正的篡改，而**漏掉的那一类往往正是案件核心文件**。更糟的是阈值写死在脚本里、报告里却不说明，**对方无法判断你的检测覆盖了哪些范围、漏了哪些**，这会直接影响证据的可信度评估。

**核查**：阈值**从数据里来，不从经验来**。做法是：先在**已知干净**的样本上跑一遍，统计各判据的分布，取「正常数据里的极值 + 余量」作为阈值；或者用分位数（例如正常样本 99.9 分位）。本篇脚本里的 `GAP_D = 365.0` 与 `AGE_D = 30.0` 是**示例值不是推荐值**，实际使用必须按目标环境重新标定。报告里要写明「本阈值基于 X 个已确认未篡改文件标定，超出该范围的样本不覆盖」——这既是方法说明，也是阴性结论的边界。

<a id="section-25"></a>

#### 陷阱 7：把「三个时间相同」当成必然篡改

**现象**：看到某文件 $SI 的 Created / Modified / Accessed 三值完全相同，直接判为 timestomp。

**原因**：三者相同在正常场景下**相当常见**。创建后从未被打开过的文件（下载了没看、安装包下载了没装）三个时间就是同一个值；批量解包工具（尤其是老旧的、在 FAT 上工作的）会给整批文件打上统一的时间；虚拟机模板、容器镜像层展开会产生大量时间戳相同的文件。「相同」只说明这个文件在创建之后没有再被读写过，这在很多场景下是正常状态。

**影响**：这条判据单看几乎无价值，写进报告会被直接质疑。

真正的价值在于**分布**。单文件三个时间相同是弱信号；一个目录下一大片文件三个时间都相同、亚秒全为 0、时间戳集中在某一分钟，这才是强信号。只看单文件会丢掉这条判据的全部价值——它的判据对象是分布，不是单个文件。

**核查**：这条判据**必须以统计形式使用，不能逐文件使用**。正确的做法是按目录、按时间窗口聚合计数，看「三个时间相同的文件」在局部范围内是否异常集中。本篇脚本把它放在 W3（弱信号级）就是这个原因。发现集中后，下一步是找出同批次文件里最早的那个时间点——那通常是批处理动作的执行时刻。

<a id="section-26"></a>

### 4.3 判据适用范围

<a id="section-27"></a>

#### 陷阱 8：把 NTFS 判据套到 ext4 或 APFS

**现象**：在 ext4 镜像上跑同一套 $SI/$FN 对照，全部落空——因为 ext4 根本没有 $STANDARD_INFORMATION 和 $FILE_NAME 这两个属性。

**原因**：MFT 的双属性结构是 **NTFS 特有设计**。ext4 的对应结构是「inode 里的 i_ctime/i_mtime/i_atime」加「目录项里冗余存的一份时间」，两者的语义与更新时机都不同；APFS 又是另一套（inode + 目录项，但目录项是 B-tree 节点）。把 NTFS 判据原样搬到别的文件系统，等于用错误的假设做检测。

**影响**：两种结果都不好。

**一是「什么都没检出」**。分析员可能因此认为该卷干净，而真实情况是**判据不适用**。这两件事在结论里长得一模一样，含义却天差地别。

**二是部分字段恰好能对上但语义不同**，产生出看似有道理实则错误的告警。**后者更危险，因为报告里的技术细节看起来很专业。**

**核查**：每种文件系统单独建立判据集，并且在报告里明确写出本卷适用的判据来自哪套文件系统语义。ext4 的做法见 2.6：用 `debugfs` / `istat` 读 inode 时间与目录项时间做对照（`debugfs -R "stat /path/to/file" image.ext4`），**不要用 `stat`**——`stat` 走的是当前挂载的缓存路径，不一定暴露底层不一致。本篇的 7 条判据**仅适用于 NTFS**。

<a id="section-28"></a>

#### 陷阱 9：USN 日志为空时当成「无篡改」

**现象**：USN 解析结果是空的，或者查询某文件名的记录数为 0，于是写下「该文件无时间戳篡改记录」。

**原因**：USN 日志为空的原因至少有五种，而其中四种与「没发生篡改」无关：

| 原因 | 说明 |
|---|---|
| 日志被清空 | 可被 `fsutil usn deletejournal` 或直接删 `$J` 数据流 |
| 日志被滚转覆盖 | `$Max` 默认约 64 MB，写满就从头覆盖，**旧记录自然消失** |
| 卷创建时未启用 | 域控的部分配置模板、某些格式化流程会关掉 |
| 数据流未导出 | 挂载时没导出 `$Extend\$UsnJrnl:$J` |
| **确实没有相关记录** | ← 这是唯一「正常」的解释 |

**影响**：这是典型的**把工具缺失误读成事实阴性**。

「查不到」和「不存在」在报告里长得很像，但它们的举证责任完全相反。

基于空结果写出的「无篡改」结论，一旦对方证明日志被清过（而 Security 104 恰好记录了这件事），整条时间线的可信度都会崩。这种错误在法庭上会直接被推翻。

**核查**：阴性结论必须写成三段式（详见 5.3）：「在 [明确的范围] 内的 [明确的检查] 中未发现 [明确的结论]」，并把未覆盖范围列出来。

「USN 日志为空」的正确表述是「未获取到 USN 日志数据（日志文件大小为 0 字节 / 数据流不存在）」，不能写成「USN 日志中无篡改记录」。前者是事实，后者是推断。

<a id="section-29"></a>

### 4.4 从线索到结论的跨越

<a id="section-30"></a>

#### 陷阱 10：把「MFT Modified 泄漏了真实时间」当成能直接用

**现象**：发现某文件 $SI MFT Modified 是 2024-03-16 09:13:58，而 $SI Created 声称是 2019 年，于是报告写「该文件实际创建于 2024-03-16」。

**原因**：$SI MFT Modified 记的是「这条 MFT 记录最后一次被更新」，不等于「文件被创建」。

任何操作都会推进它，包括：修改权限、添加数据流、被打包进安装程序、被同步软件 touch、甚至被取证工具自己只读挂载时的某些元数据读取。

它是一个**上界**——「这个文件在 T 时刻至少还存在或刚被操作过」，不是「这个文件在 T 时刻被创建」。

**影响**：把上界当成点估计，会在报告里产生一个精确但错误的结论。

这类错误比含糊的结论危险，因为它看起来是经过分析的。对方一旦指出「这个时间其实是文件被移动到新分区时的 MFT 记录重写时刻」，你对该文件全部时间线的解释都会失去可信度。

**核查**：把它当**下界/上界用，不当点估计用**。

正确表述是「该文件的 MFT 记录在 2024-03-16 09:13:58 被更新过，此时间戳由内核写入，不受 `SetFileTime` 影响」。

要拿到「文件实际创建时间」，必须用 $FN Created、USN `FILE_CREATE` 记录、或 Prefetch 首次执行时间——这三者才是「创建」语义对应的工件。

<a id="section-31"></a>

#### 陷阱 11：把「篡改动作时刻」当成「文件真实活动时刻」

**现象**：USN 日志显示某文件在 2024-03-16 09:13:58 有 `BASIC_INFO_CHANGE`，报告写「该文件在此刻被修改」。

**原因**：`BASIC_INFO_CHANGE` 的准确语义是「属性或时间戳被改」，它记录的是元数据被写这个动作，而不是文件内容被改。

一个纯 timestomp 操作只改时间戳、不动一个字节数据，却会产生 `BASIC_INFO_CHANGE`。反过来，内容被改（`DATA_OVERWRITE` / `DATA_EXTEND`）是完全独立的一类记录。

**影响**：报告里把「时间戳被改的时刻」当成「文件被改的时刻」，等于凭空把篡改行为和业务行为叠在了同一个时间点上。

这会直接污染时间线。一个用 timestomp 掩盖的恶意文件，其「真实行为时间」和「篡改时间」是两个独立事件，合并成一个会导致整个行为重建错位。

**核查**：USN 的 Reason 标志决定动作类型，必须分别统计。 内容变化看 `DATA_OVERWRITE`（0x1）/`DATA_EXTEND`（0x2）/`DATA_TRUNCATION`（0x4），时间戳变化看 `BASIC_INFO_CHANGE`（0x8000），改名看成对的 `RENAME_*`。

这两类在时间线上要画成两个不同的事件点，前者是业务活动，后者是反取证动作。`CLOSE`（0x80000000）是伴随标志，统计实质操作时必须排除，否则每个文件关闭都会产生一条噪声。

<a id="section-32"></a>

#### 陷阱 12：只查 MFT，不查删除型反取证

**现象**：跑完时间戳一致性检测，全卷「未发现异常」，报告写「时间戳未发现篡改」。

**原因**：**删除是比改时间戳更彻底的反取证。** 一个文件被删除后，$MFT 记录还在、$FN 属性还在、目录项也还在（只是被标记为已删除），时间戳字段一个都不会少。

一致性检测跑下来完全正常——因为被删文件的四个时间之间的关系本来就是自洽的。一致性检测检测不了删除，只能检测「被改坏的时间戳」。

**影响**：这是覆盖面错觉。

分析员跑完一套工具、看到满屏正常，就以为「篡改这条线查过了」。实际上一份用 shred 清理过的系统，「没有异常时间戳」恰恰就是预期结果。报告里那句「未发现异常」会被对方理解成「没有发生过反取证」。

**核查**：把「时间戳一致性」和「删除痕迹」分成两条独立的检查线。

删除线要看：$MFT 记录的状态位、`$FILE_NAME` 中的 `FILE_NAME_FLAG_DELETED`（父目录索引里的删除标记）、`$I30` 目录索引的 slack、未分配簇的内容残留、回收站 `$RECYCLE.BIN`。

阴性表述要分开写：「时间戳字段未发现改写特征」+「已删除文件共 N 个（列出 MFT 记录号），其时间戳字段未见异常」。两句话覆盖的是完全不同的范围。

<a id="section-33"></a>

### 4.5 报告表述

<a id="section-34"></a>

#### 陷阱 13：阴性结论用绝对表述

**现象**：报告里写「本机未发现反取证痕迹」或「时间戳未被篡改」。

**原因**：**这句话在技术上不可能成立。**

检材只是某个时间点的快照，而反取证可以发生在任何环节——篡改者可以在你制作镜像之前就抹掉了痕迹（痕迹被抹掉后，抹除动作本身留下的痕迹也已消失），可以在你做镜像时动手（若没上写保护器），也可以在事后针对你的分析结论做二次准备。

「未发现」永远是「在某个范围内的检查没有命中」，而不是「这件事没有发生」。

**影响**：绝对表述在证据法语境下风险极高。

一旦对方能举出任何一条未覆盖的反取证手段（另一块硬盘、另一个账户、云端版本、卷影副本的更早版本），这句结论就被推翻。

而推翻它会连带削弱报告中所有其他结论，因为读者会认为分析员对证据边界缺乏认识。

**核查**：**范围 + 检查 + 未发现**三段式，缺一不可（完整示例见 5.3）：

> 「在 `DigiForensics.dd` 中 NTFS 分区的 MFT 记录（已检查第 0–131071 号记录）内，对 $SI/$FN 时间关系、亚秒精度形态、零值记录三类共 7 条判据进行检查，**未发现命中硬矛盾的时间戳记录**。**未覆盖范围**：$LogFile 事务日志、卷影副本旧版本、USN 日志（数据流大小为 0 字节，无法解析）、其他分区与未分配空间。」

四个要素：检查了什么（7 条判据）、检查了多少（记录号区间）、结论的强度（未发现命中**硬矛盾**）、没查什么（未覆盖范围）。

注意结论是「未发现命中硬矛盾」而不是「未篡改」——前者是这句话能证明的东西。

<a id="section-35"></a>

#### 陷阱 14：把工具执行痕迹当成案件无关的噪声

**现象**：$MFT 里有一批 Prefetch 文件、SCAuthenticode 数据库条目、MFTECmd 自己的痕迹，报告里归为「系统组件」略过。

**原因**：**这些恰恰是交叉验证的核心来源。**

Prefetch 记着程序的执行时间，Amcache 记着路径，Sysmon 记着时间戳改动动作。在一份「文件声称来自 2019 年」的检材上，唯一能说真话的就是这些独立工件。

把它们当噪声丢掉，等于扔掉了唯一能升到 L3/L4 的证据。

**影响**：这条错误的代价是**把 L2 永远锁死在 L2**。

MFT 内部信号无论怎么组合都到不了定论，这一限制来自元数据的记录方式。丢掉独立时钟，等于主动接受只能出「存疑」级别的结论，而「存疑」在多数案件里不足以支撑处置决定。

**核查**：**先建立一份「可信时钟清单」**，把检材里所有由内核或系统服务写入的时间源列出来，逐个确认是否可用：MFT（半可信、可被部分改写）、USN 日志（可信，除非被清）、`$LogFile`（可信）、Prefetch（可信）、事件日志（可信，但可被清）、Sysmon（**最可信，因为它记下了改前值**）、卷影副本（**最可信，因为里面有原值**）、远程认证日志（域环境下可信度最高）。

分级之后，每条 MFT 内部的信号都去和这张清单里的可信时钟对一遍。

<a id="section-36"></a>

#### 陷阱 15：把「分析员自己的动作」算进篡改统计

**现象**：把检材挂载分析、跑 carving、导出文件之后，再跑一次时间戳检测，发现一批文件命中弱信号，于是把它们也统计进去。

**原因**：**分析过程本身会改变时间戳。**

把文件从镜像提取到工作目录会产生新的创建时间（虽然不会写回镜像，前提是挂载正确）；如果误用了读写挂载、或挂载了活系统，原始时间戳就被覆盖了。

更重要的是：用分析过程中产生的数据去反推分析之前的状态，逻辑上不成立。

**影响**：两类后果。

一是污染统计。自己制造的数据被当成篡改证据，误报率上升，还会让复核者怀疑整条工具链。

二是掩盖真实信号。真正重要的那批命中被淹没在自己的噪声里。

而且这个错误往往是不可逆的：一旦在读写挂载下做过操作，原始时间戳就永久丢失了，后续无论怎么分析都拿不回原值。

**核查**：三条纪律。

一、所有挂载一律 `-o ro` 加 `noatime`，从制度上排除写入可能（见 [只读挂载与安全接入](../../imaging/imaging-mount-simulate/imaging-mount-simulate-read-only-mounting.md)）。

**二、篡改检测必须在任何提取操作之前跑**，用原始 MFT 一次成型，不要反复重跑——每次重跑用的都是可能被自己污染过的数据。

**三、检测脚本的输出与 MFT 导出文件一起归档**，作为「检测时的原始输入」，便于第三方复核时验证分析员自己的操作没有影响结论。

## 五、案例示例

> 本节示例检材均为虚构构造，用于说明判定逻辑，不代表真实案件数据。

<a id="section-38"></a>

### 5.1 案例 A：一份自称 2019 年的系统文件

**背景**：某终端被怀疑安装了远控软件。检材 `DigiForensics.dd`（E01 转出，NTFS 分区，起始偏移 2048）。初查发现 `C:\Temp\svc.exe`，文件属性面板显示「修改时间 2019-05-20」，文件大小 412 KB。

**第一步：MFT 内部一致性检查**

```bash
# 用 MFTECmd 导出，把八个时间整理成 TSV
MFTECmd.exe -f DigiForensics.dd -m "Windows NTFS" --csv .\out
# 整理后该记录的关键值（FILETIME 十进制）
#   si_created = si_modified = si_accessed = 132027913220000000
#   si_mftmod  = 133436396786042217
#   fn_created = fn_modified = fn_mftmod = fn_accessed = 133429148344719020
```

```bash
$ python3 tsdetect.py < svc-only.tsv
[SUSPECT] C:\Temp\svc.exe
    W1  SI 与 FN 创建时间分歧超过 365 天
         机理: 改名会同时推进两套时间，只推进一边说明有工具只改了一边
         误判代价: 正常的大跨度改名/迁移也会命中；误当成结论会写出无法辩护的「已篡改」
    W3  SI 四值中三个相同
         机理: 创建 / 修改 / 访问三种语义在同一刻发生，自然活动几乎不产生
         误判代价: 批量解包与迁移拷贝也会命中，须与同批次文件一起看分布
    W4  MFT 变更时间滞后业务时间超过 30 天
         机理: 元数据最后变更时刻明显晚于内容修改时刻
         误判代价: 跨年复制的旧文件会命中；配合 W1 同时出现才有意义
```

**注意 W2 没有命中**。因为 $SI 的 MFT Modified 亚秒部分是 `6042217`，不是 0。这说明操作者用的工具会填随机亚秒，绕过了整秒截断这个特征。

这个「没命中」本身是有效信息：它排除了最低级的工具。

**第二步：换算与解读**

| 值 | 换算结果 |
|---|---|
| `si_created` = 132027913220000000 | 2019-05-20 02:02:02 UTC |
| `fn_created` = 133429148344719020 | 2024-03-15 18:58:13 UTC |
| `si_mftmod` = 133436396786042217 | 2024-03-16 09:13:58 UTC |

**解读**（注意每句话的强度）：

1. $SI 声称文件创建于 2019-05-20，$FN 记录 2024-03-15。**这是一个强信号，但不是结论。**
2. $SI MFT Modified 为 2024-03-16 09:13:58。这个时间由内核写入，`SetFileTime` 改不到 —— 「该文件的 MFT 记录在 2024-03-16 09:13:58 被更新过」。
3. **不能由此推出「文件创建于 2024-03-16」**（陷阱 10），只能推出「不早于这个时刻仍然存在或刚被操作过」。

**第三步：引入独立时钟 —— USN 日志**

```bash
$ usnjrnl -o 2048 DigiForensics.dd > usn.csv
$ grep -i 'svc.exe' usn.csv
```

```
Date and Time              File Name         Reason
2024-03-15 18:58:13        SVC.EXE           0x00000100        <- FILE_CREATE
2024-03-15 18:58:13        SVC.EXE           0x00000002        <- DATA_EXTEND
2024-03-16 09:13:58        SVC.EXE           0x00008000        <- BASIC_INFO_CHANGE
2024-03-16 09:13:58        SVC.EXE           0x80000002        <- CLOSE | DATA_EXTEND
```

**关键在最后两行。** `0x00008000`（`BASIC_INFO_CHANGE`）的时间是 **2024-03-16 09:13:58**，与 $SI MFT Modified **完全一致**。这个时间戳由 NTFS 内核在写元数据时记录，**篡改时间戳的常规工具改不到它**——这正是它能充当独立时钟的原因。

**第四步：定级**

| 步骤 | 证据 | 定级 |
|---|---|---|
| 3.2 MFT 内部 | W1 + W3 + W4，无硬矛盾 | **L2 存疑** |
| + USN 独立时钟 | `FILE_CREATE` @ 2024-03-15 证明文件不可能来自 2019 | **L3 高度可疑** |
| + USN `BASIC_INFO_CHANGE` @ 2024-03-16 09:13:58 与 $SI MFT Modified 吻合 | **改写动作本身被记录，时间与内核时钟精确对齐** | **L4 确认** |

**第五步：报告表述（可直接采用）**

> 该文件 `C:\Temp\svc.exe`（MFT 记录号待补）的时间戳已被改写。
>
> **改写前**：MFT 记录中 `$FILE_NAME` 属性记录的文件创建时间为 2024-03-15 18:58:13.4471902 UTC；$UsnJrnl 中 `FILE_CREATE` 记录（Reason `0x00000100`）时间为 2024-03-15 18:58:13 UTC，两者独立吻合。
>
> **改写后**：MFT 记录中 `$STANDARD_INFORMATION` 属性的 Created、Modified、Accessed 三值均为 2019-05-20 02:02:02.0000000 UTC。
>
> **改写动作发生时间**：2024-03-16 09:13:58 UTC。依据为两项独立证据：(1) $UsnJrnl 中 `BASIC_INFO_CHANGE` 记录（Reason `0x00008000`），该时间戳由 NTFS 内核在写入元数据时生成；(2) MFT 中 `$STANDARD_INFORMATION` 的 MFT Modified 字段值为 2024-03-16 09:13:58.6042217 UTC，该字段无法经 `SetFileTime` 接口修改。两者精确到秒一致。
>
> **未覆盖范围**：未获取卷影副本，无法确认是否存在更早的卷影快照含改写前的 `$FILE_NAME` 原值；`$LogFile` 未解析。

**为什么这段表述站得住**：每个时间都标了来源，且都是可独立复核的。

L4 结论靠的是「改写动作被内核记录」而不是「数值看起来不对」。**未覆盖范围明写**，避免被解读为「已彻底排除其他反取证」。

<a id="section-39"></a>

### 5.2 案例 B：全零时间戳的批处理痕迹

**背景**：某 U 盘（exFAT 格式，镜像 `DigiForensics-usb.e01`）被怀疑用于数据外传。初步查看文件名时发现一批文件的创建时间显示为 1970 年或空白。

**第一步：识别文件系统类型与判据适用性**

**这是本案例的第一个关键点**：exFAT 属于 FAT 族。回顾 2.6 与陷阱 5——本篇的 7 条 NTFS 判据里没有一条适用于 exFAT。

```bash
$ fsstat DigiForensics-usb.e01
File System Type: exFAT
Volume Serial Number: 0x1234ABCD
File System Features: Read Only Volume
```

因此第一步的结论是「本篇判据不适用于本卷」，不是「未发现异常」。 这个区别必须写进报告（陷阱 8）。

**第二步：FAT 族能查什么**

exFAT 上能做的是：

```bash
# FAT 目录项里的三个 DOS 时间：创建、修改、访问
# 用 Sleuth Kit 导出，会把 DOS 时间换算成标准格式
fls -r -p -o 0 DigiForensics-usb.e01 | head -40
```

```
r/r 12:20:00:00 2024-03-20 11:04:22   2024-03-20 11:04:22   2024-03-20 11:04:22  $FILE_NAME  REC   32
r/r 24:00:00:00 2024-03-20 11:31:07   2024-03-20 11:31:07   2024-03-20 11:31:07  $FILE_NAME  REC   40
```

`fls` 输出的前两列是 FAT 时间与标准时间的对照。DOS 时间只有 2 秒粒度，且只能表达 1980-01-01 之后的时间。

**第三步：批量文件名的时间分布异常**

本案例真正的发现不在时间戳本身，而在文件名的批量特征。

```bash
# 列出所有文件的创建时间，排序看聚集情况
# $3=日期 $4=时间（fls 把日期和时间拆成两列），要拼起来才是一个完整时间
fls -r -p -o 0 DigiForensics-usb.e01 \
  | awk '$3!="" {print $3, $4}' \
  | sort | uniq -c | sort -rn | head -20
```

```
   47 2024-03-20 11:04:22
   12 2024-03-20 11:31:07
    3 2024-03-20 14:22:41
    1 2024-03-18 09:15:00
    1 2024-03-15 18:58:13
```

47 个文件共享同一个创建时间到秒。回顾陷阱 7：单个文件三个时间相同是弱信号，一个批次里 47 个文件共享同一秒级时间戳，这就值得追了。

**第四步：内容侧的印证**

```bash
# 这 47 个文件是什么？
# fls 输出的列序：$1 类型 / $2 FAT时间 / $3 日期 / $4 时间 / $5 日期 / $6 时间 / …
# 注意日期和时间是两个独立字段，不要写成 $4=="2024-03-20" && $4=="11:04:22"（互斥，永远 0 行）
fls -r -p -o 0 DigiForensics-usb.e01 | awk '$3=="2024-03-20" && $4=="11:04:22" {print $1}' > batch47.txt
while read -r rec; do icat -o 0 DigiForensics-usb.e01 "$rec"; done < batch47.txt > batch47-raw.bin
binwalk batch47-raw.bin
```

```
DECIMAL   HEXADECIMAL     DESCRIPTION
0         0x0             Microsoft Office Document, Word 2007+
1152      0x480           Zip archive data, at least v2.0 to extract
```

47 个 Word 文档，全部共享同一个秒级时间戳。 结合扩展名与内部结构，这是典型的**批量生成或批量拷贝特征**——正常办公活动不会在同一秒创建 47 个 Word 文档。

**第五步：找这个时间点的外部印证**

```bash
# 同一批文件在宿主机上有没有对应的访问记录？
# 若同期拿到宿主机检材，Windows 的跳转列表 / 索引 / 浏览器下载记录都可能留下 2024-03-20 11:04 前后的事件
```

若有宿主机检材，2024-03-20 11:04:22 这个时间点应当能在宿主机上找到对应的操作记录（例如一次解压、或一次批量拷贝）。找到了，就是一次完整的印证；没找到，也不影响本节结论——U 盘自身只能证明「47 个文件共享一个时间戳」，不能证明这个时间戳是真是假。

**第六步：报告表述**

> `DigiForensics-usb.e01`（exFAT）中检出 47 个 Microsoft Word 文档（`.docx`）共享完全相同的目录项创建时间 **2024-03-20 11:04:22**（FAT 目录项时间，2 秒粒度）。
>
> **该现象的技术解释**：exFAT 目录项仅存三个 DOS 时间（创建 / 修改 / 访问），结构上无亚秒精度，且**无法表达 1980-01-01 之前的日期**。本卷不具备 NTFS `$STANDARD_INFORMATION` / `$FILE_NAME` 双属性对照结构，**因此时间戳篡改检测的 NTFS 判据在本卷不适用**。
>
> **结论**：目录项时间的批量一致性表明这 47 个文件在同一时刻被写入或被统一改写，**符合批量拷贝、批量解压或批量生成的行为特征**。本卷内**无独立时钟可用于交叉验证**（无 USN 日志、无 $LogFile、无卷影副本），故**该时间的真实性无法在本卷内判定**。
>
> **未覆盖范围**：未获取该 U 盘接入宿主机的镜像，无法与宿主机侧的操作记录做时间点比对；未分析未分配空间与已删除目录项。

**这段表述的价值在于它诚实地划了线**：发现了一个真实异常，明确说了**在本卷内无法判定真伪**，并把「需要什么才能判定」写清楚了。这比给出一个站不住的「已篡改」结论有用得多。

### 5.3 阴性发现的表述方式

反取证检测**大量产出的是阴性结果**。阴性结果的写法决定这份报告能不能用。

**不可接受的三种写法：**

| 写法 | 问题 |
|---|---|
| 「未发现反取证痕迹」 | 绝对表述，未说明检查了什么、检查了多少（陷阱 13） |
| 「时间戳未被篡改」 | 结论强度远超证据能支撑的范围；MFT 内部信号最多到 L2 |
| 「USN 日志中无相关记录」 | 混淆了「无数据」与「无记录」（陷阱 9） |

**可接受的分层写法：**

**第一层：检查范围（做什么、做多少）**

> 检查对象：`DigiForensics.dd` 中 NTFS 分区（起始偏移 2048）的 MFT，已解析第 0–131071 号记录，共 131,072 条，其中有效（非空闲）记录 87,431 条。
> 检查项：3.2 节的 7 条判据（H1–H3 硬矛盾、W1–W4 弱信号）。

**第二层：命中情况（实际结果）**

> 命中硬矛盾记录 **2 条**，均为 $SI 四值全零（MFT 记录号 58,214、93,007，对应路径 `C:\Temp\w.exe`、`C:\Temp\u.exe`）。
> 命中弱信号记录 **1,204 条**（占有效记录的 1.38%），其中 1,187 条集中在 `C:\Program Files\` 下（软件安装产生），17 条位于 `C:\Users\` 下的用户目录。

**第三层：结论及其强度**

> 在上述范围内，**检出 2 条明确的时间戳元数据异常**（$SI 四值全零），判定为人为改写，该两条记录的文件名与路径见附件 2。
> 除上述 2 条外，在 87,431 条有效 MFT 记录中未发现命中硬矛盾的时间戳异常。

**第四层：未覆盖范围（最重要，最常被省略）**

> **未覆盖范围**：
> - $LogFile 事务日志未解析，**无法判断是否存在元数据事务层面的痕迹**；
> - USN 日志数据流（`$Extend\$UsnJrnl:$J`）在镜像中不存在，**无法用内核时间戳交叉验证**；
> - 卷影副本未获取，**无法比对篡改前的原值**；
> - 未分析 MFT 之外的删除痕迹（$I30 目录索引 slack、未分配簇内容、回收站），**因此本结论仅覆盖时间戳字段，不覆盖删除型反取证**；
> - 未分析其他分区与镜像中的未分配空间；
> - 本结论基于 7 条 NTFS 判据，**不适用于 exFAT / FAT 分区**（本卷若含此类分区需另行处理）。

**第五层：方法可复核性**

> 检测脚本与输入数据随本报告归档：脚本 `tsdetect.py`，输入 `mft-times.tsv`（TSV，11 列，87,431 行）。判据阈值 `GAP_D=365.0` 天、`AGE_D=30.0` 天为**示例值**，本次未按目标环境标定（原因：本卷无已知干净基线样本），故弱信号结果（W1–W4）**仅作参考，不作为定性依据**。

**把这五段拼起来读，检查三件事：**

1. 结论强度是否与证据匹配？（7 条弱信号 ≠ 篡改）
2. 未覆盖范围是否具体到可核查？（不是笼统的「其他方面」，而是「$LogFile 未解析」）
3. 有没有把「无数据」写成「无发现」？（USN 那种陷阱要特别查）

**只写前三段的报告在形式上完整，在实质上仍有风险**——因为未覆盖范围正是对方质询时最常攻击的地方。**主动写出来，是把防守变成披露。**

## 六、扩展阅读方向

**前置与基础。** 本篇所有判据都建立在时间戳被正确换算之上——**先把纪元、
单位、精度这三件事弄准，再谈篡改**。时区差一秒被当成篡改，是这条线上最低级也最常见的错误。
然后是 NTFS 字段的字节级布局：`$STANDARD_INFORMATION` 与 `$FILE_NAME` 各字段在哪一偏移，
决定了「两个时间为什么不一样」这个问题有没有答案。见
[《时间戳换算与时区陷阱》](fundamentals-concepts-timestamps-and-timezones.md)、
[《NTFS 结构与 MFT 解析》](../../filesystem/filesystem-ntfs/filesystem-ntfs-ntfs-master-file-table.md)。

**同层深入。** 篡改只会改能改的地方，所以要找改不到的地方。`$LogFile` 事务日志、
Prefetch、ShimCache、Amcache 都由内核或系统服务写入，**篡改者通常接触不到、
也不知道该改**，这几类因此成为最有力的独立时钟。USN 日志是其中判读难度最高的一份——
`BASIC_INFO_CHANGE` 的准确定义与 `Reason` 标志位如何组合，都是读懂它的前提。
见[《USN 日志与文件操作时间线》](../../computer/computer-execution/computer-execution-usn-journal-timeline.md)。

**相邻议题。** 被删的数据不只藏在 ADS 和备用数据流里，slack 空间也可能留住残片。
macOS 侧的对应机制是 APFS 快照，Windows 侧是 VSS，卷影副本与 APFS 快照的 diff 属于同类技术。
「时间线重建」则是本篇定级结果的落点：单个文件的时间戳异常说明不了什么，
**必须并入多来源时间线才能看出矛盾**。见
[《NTFS 数据流与隐藏数据》](../../filesystem/filesystem-ntfs/filesystem-ntfs-ntfs-alternate-data-streams.md)、
[《时间线重建》](../../computer/computer-log/computer-log-linux-timeline-reconstruction.md)。

**工具与判据。** 2.1 的偏移表与 3.1 的导出方法都建立在 NTFS 解析之上；
3.4 的「独立时钟」判定依赖 Prefetch 与 ShimCache/Amcache 的读法；
3.6 排查清单里的 `$LogFile` 需要专门的解析工具。**每个来源的能力边界都不同**，
混用会把「该来源本来就看不到」误读成「没发生」。工具侧的取舍见
[《Prefetch 深度解析》](../../computer/computer-execution/computer-execution-prefetch.md)、
[《Steady-State 与 LogFile 还原》](../../filesystem/filesystem-ntfs/filesystem-ntfs-steady-state-logfile.md)。

**判据与反例。** 「两个时间不一致」本身不构成篡改证据——改名会让
`$SI Created` 早于 `$FN Created`，这是正常结果。可用的判据是
在「当前文件名 == `$FN` 中记录的名字」这个前提成立时才比较两个创建时间。
反向的例子同样重要：Security 日志里的 104 与 1102 事件是**越抹越明显**的自证记录，
清日志这个动作本身会留下痕迹，其价值往往高于原始日志。见
[《事件日志深度分析》](../../computer/computer-registry-log/computer-registry-log-windows-event-log-analysis.md)。
最后，所有时间戳判据都建立在只读接入之上，写入防护失效时本篇的结论全部不成立，
纪律来源见[《取证流程与原则》](../fundamentals-process/fundamentals-process-five-stage-forensics-process.md)。

## 七、命令速查

**MFT 时间字段导出**

```bash
# Sleuth Kit：列出全部记录（含删除）
fls -r -p -o 2048 DigiForensics.dd > mft-body.txt

# Sleuth Kit：取单条记录查看全部属性
istat -o 2048 DigiForensics.dd <record#>

# Sleuth Kit：提取原始 MFT 记录字节（供自写解析器）
icat -o 2048 DigiForensics.dd <record#> | xxd

# MFTECmd：导出全部 MFT 记录为 CSV
MFTECmd.exe -f DigiForensics.dd -m "Windows NTFS" --csv .\out --bodyfile .\body
```

**USN 日志**

```bash
# Linux：解析 $UsnJrnl:$J
usnjrnl -o 2048 DigiForensics.dd > usn.csv

# 按文件名查某文件的全部历史记录
grep -i 'svc.exe' usn.csv

# 提取全部 BASIC_INFO_CHANGE（时间戳/属性被改）
awk -F, '$NF ~ /0x0*8000/ || $NF ~ /0x[0-9a-f]*8000/' usn.csv

# 提取成对的重命名记录（双重改名指纹）
grep -E '0x0*1000|0x0*2000' usn.csv | sort -k2
```

**Reason 标志数值（务必记准）**

```
0x00000001  DATA_OVERWRITE       内容被覆写
0x00000002  DATA_EXTEND          内容被追加
0x00000004  DATA_TRUNCATION      内容被截断
0x00000100  FILE_CREATE          文件创建
0x00000200  FILE_DELETE          文件删除
0x00001000  RENAME_OLD_NAME      重命名（旧名）
0x00002000  RENAME_NEW_NAME      重命名（新名）
0x00004000  INDEXABLE_CHANGE     内容索引属性变更   ← 不是 BASIC_INFO_CHANGE
0x00008000  BASIC_INFO_CHANGE    属性或时间戳被改   ← 篡改动作本身
0x00010000  HARD_LINK_CHANGE     硬链接数变更
0x00040000  ENCRYPTION_CHANGE    EFS 加密状态变更
0x80000000  CLOSE                句柄关闭（伴随标志，统计时排除）
```

**时间戳一致性检测**

```bash
# 运行配套脚本（输入为规范化后的 TSV，11 列）
python3 tsdetect.py < mft-times.tsv

# 只看被判为 TAMPERED 的行
python3 tsdetect.py < mft-times.tsv | grep -A3 '^\[TAMPERED\]'
```

**卷影副本（Windows）**

```powershell
# 列出全部卷影副本
vssadmin list shadows

# 统计副本数量（为 0 或异常偏少需在报告中解释）
vssadmin list shadows | Select-String "Shadow Copy" | Measure-Object
```

**只读挂载纪律（陷阱 15 的预防手段）**

```bash
# Linux：只读 + 不更新访问时间
mount -o ro,noatime,loop,offset=$((2048*512)) DigiForensics.dd /mnt/ntfs

# 检查挂载参数是否真的生效（关键：确认 ro 与 noatime 都在）
findmnt -no OPTIONS /mnt/ntfs
```
