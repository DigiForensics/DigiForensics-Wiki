# 电子数据取证的概念与分类

<a id="section-1"></a>

## 一、概述

电子数据取证的目标是在原始数据不被改变的前提下，把散落在介质上的技术痕迹还原成能回答案件问题的证据。三个限定是连在一起的，少一个就退化：数据不能被改，否则无法分辨看到的是原始状态还是被人处理过的状态；痕迹必须能定位，否则证据存在但拿不到；答案必须能被复核，否则技术结论在质证时一碰就碎。

同一套命令在两个场景下的正确用法可能正好相反。"我 U 盘删了照片帮我找回来"是数据恢复，允许多次尝试、允许写盘、追求成功率；"这台服务器疑似被入侵，帮我固定证据"是取证，一次都不能错，追求可辩护性。区分点落在这件事将来会不会上法庭：恢复做过的介质不能退回取证状态，而取证状态可以承接恢复需求。

这一层不在流程的任何一环里，它定义的是流程该长什么样。第三章那五步——确认授权 → 状态记录 → 建工作副本 → 分层分析 → 结论可复核——是全库所有文章共同的骨架，它上游没有依赖，它就是依赖本身。

五步各自要解决的问题不同。步骤 1 要求书面确认授权来源、目标范围（型号 + 序列号 + 容量）与时间边界，不接受"他所有电脑"这种无边界表述。步骤 2 按设备是否开机分流处置：普通用户设备内存采集优先或温和关机，服务器依委托方要求可能只能在线取证，涉案关键设备记录屏幕状态后直接断电。

步骤 3 让原始介质只读挂载或封存，所有分析在副本上进行。步骤 4 按全局 → 索引 → 定向 → 验证四层递进，每层的产出是下一层的输入。步骤 5 要求每条结论能说出具体工具、参数、文件偏移，有第二条独立证据，并能让同工具同参数重现同一结果。

电子数据的固有脆弱性可以拆成五条，每条派生一条技术要求。易被改写 → 采集必须只读 → 硬件写保护器。改写无痕 → 必须数学验证 → 哈希校验。易被复制 → 必须记录来源与流转 → 保管链文档。存储易失 → 在线设备优先断电 → 内存镜像。体积巨大 → 必须分层抽样 → 关键字加结构化分析。

三个法律形式（司法鉴定 / 公证 / 自行取证）的技术手段几乎相同，区别在于是谁做的、以什么身份做的、要向谁负责。司法鉴定由有资质的鉴定机构或人员执行，服务对象是公安、检察、法院，产出鉴定意见书，可质证、可出庭。公证由公证机构执行，核心是在证据消失前把证据固定下来，产出公证书加证据保全记录。自行取证由当事人或其委托的技术人员执行，无固定格式，自担证明责任。

三类取证目标的证据价值互不替代。计算机取证提供行为链，主要风险是关机导致易失数据丢失。网络取证提供通信事实，保留期短，多数仅数天至数月。移动取证提供身份锚点，风险在锁屏、云端擦除、芯片级加密。只有单机数据难以证明"是谁"，只有手机数据难以证明"做了什么"。

物理取证与逻辑取证的分野在采集内容。物理取证取整个介质的比特流，含未分配空间，体积等于介质容量，能恢复已删除数据与文件碎片，证据强度高。逻辑提取只拿特定文件、表、目录，只能拿到现存对象，受操作系统与工具限制，证据强度中。第五章案例里 30 分钟停机窗口逼出的"先在线固定、后窗口期物理镜像"就是这一原则的实例。

落到具体产物上，`DigiForensics.dd` 物理镜像等于介质容量，第五章用 `dcfldd` 的 `conv=noerror,sync`、`bs=4M` 参数制作，`hashlog` 落在案件目录。逻辑提取物是单个文件、数据库导出、配置目录。委托书是书面授权，第五章明确写着"允许 30 分钟停机窗口"，没有它后面所有动作都缺一层合法性。

在线固定记录包括登录会话导出、关键日志导出、磁盘占用快照，各自带时间戳与 SHA-256。结论载体有鉴定意见书、公证书、自行取证记录三种，签署主体、服务对象、举证责任各不相同。第五章的结论不建立在单条日志上，而是"登录日志 + 内网主机向外传输 1.2 GB 的流量记录"两条独立来源的吻合。

2.1 那张表里"法学的约束力最强"说的是技术上能做不等于法律上能做。逻辑提取读文件不改文件的表象同样不等于无损：SQLite 在有活动连接时会写 journal/WAL，浏览器 profile 被读取时可能更新缓存。因此逻辑提取必须把 `-wal`、`-shm`、`-journal` 一并复制，提取前后各算一次目标哈希。四次哈希缺一不可：源介质、镜像、分析副本、分析后，四次一致才说明全程未被改动。

阴性发现必须带上未覆盖范围。第四章陷阱 12 的三段式写明范围、方法、结果与未覆盖范围，第五章检索 412 个 `.xlsx`/`.xls`/`.csv` 文件之后只写"未发现"，并列出未覆盖的文件内容、1 个 `.zip` 归档内部、已删除且未恢复的残留。"未发现"在中文里天然被读作"不存在"，三段式把它变成方法论陈述。技术门槛为零，"证据"这个词在法律语境下指的是能否被法庭采信的东西，而这一层给的是坐标系：后面 100 多篇各自在解决哪个问题。

## 二、核心原理

<a id="section-3"></a>

### 2.1 取证与其他学科的关系

一份 Windows 磁盘镜像交到你手上，你第一步做什么、结论能写到多细、这句话有没有人信——这三件事分别不由同一个学科决定。

| 来源学科 | 借用的东西 | 在取证中的体现 |
|---|---|---|
| 刑事诉讼法学 | 证据能力、证明标准、程序合法性 | 决定什么数据能被采信 |
| 计算机科学 | 文件系统、数据库、编译原理 | 决定数据"藏在哪里、怎么存的" |
| 密码学 | 哈希、对称/非对称加密 | 决定完整性验证与数据解密 |
| 磁盘 forensics | 扇区布局、SSD 磨损均衡 | 决定[物理镜像](../../imaging/imaging-acquire/imaging-acquire-disk-imaging-and-evidence-preservation.md)读到什么 |
| 统计学 | 概率、基线分析 | 决定"什么算异常" |
| 认知心理学 | 记忆偏差、行为模式 | 决定如何解释人的痕迹 |

其中**法学的约束力最强**。技术上能做，不等于法律上能做；技术上证明了，不等于法庭上会被采信。这是电子数据取证区别于普通数据处理的核心特征。

<a id="section-4"></a>

### 2.2 电子数据的固有脆弱性

一份纸质合同撕了就没了。一份电子合同改个数字，用眼睛看完全一样——这就是电子证据唯一的根本弱点：**可以被轻易复制、修改，且修改后看不出痕迹**。

每一条弱点都对应一条技术要求：

| 弱点 | 派生要求 | 技术手段 |
|---|---|---|
| 易被改写 | 采集必须只读 | 硬件写保护器 |
| 改写无痕 | 必须数学验证 | 哈希校验 |
| 易被复制 | 必须记录来源与流转 | 保管链文档 |
| 存储易失 | 在线设备优先断电 | 内存镜像 |
| 体积巨大 | 必须分层抽样 | 关键字+结构化分析 |

<a id="section-5"></a>

### 2.3 三种法律形式

这一步最容易被讲错。三者技术手段几乎相同，区别在于是谁做的、以什么身份做的、要向谁负责。

| 形式 | 执行主体 | 服务对象 | 结论形式 | 典型场景 |
|---|---|---|---|---|
| **司法鉴定** | 有资质的鉴定机构/人员 | 公安、检察、法院 | 鉴定意见书（可作为定案依据） | 刑事案件正式送检 |
| **公证** | 公证机构 | 保全方（多为权利人） | 公证书 + 证据保全记录 | 微信聊天记录、网页、邮件保全 |
| **自行取证** | 当事人或其委托的技术人员 | 自己 | 无固定格式，自担证明责任 | 企业内部事件、个人维权 |

**三者的关键差别在举证责任与可质证性**：

- 司法鉴定由中立第三方作出，有完整的资质、检材交接、检验记录，**可质证、可出庭**；
- 公证的效力来自公证机构的公信力，核心是"在证据消失前把它固定下来"；
- 自行取证的成本最低，但一旦对方质疑"数据被改过"，**没有第三方背书的一方通常承担更重的证明责任**。

> ⚠️ **实务要点**：企业做内部安全事件处置时，常见做法是"自行取证 + 主动引入第三方"。前者保证时效，后者保证效力。两者不是替代关系。

<a id="section-6"></a>

### 2.4 三类取证目标

| 目标类型 | 典型检材 | 核心问题 | 主要风险 |
|---|---|---|---|
| **计算机取证** | 桌面/笔记本/服务器磁盘 | 何时、由谁、做了什么 | 关机导致易失数据丢失 |
| **网络取证** | 流量包 PCAP、日志、路由表 | 谁在什么时候通信了什么 | 保留期短（多数仅数天至数月） |
| **移动设备取证** | 手机整机、应用沙盒、云端 | 现实身份与设备/账号的对应关系 | 锁屏、云端擦除、芯片级加密 |

三者的证据价值排序也不同：**计算机取证提供行为链**，**移动取证提供身份锚点**，**网络取证提供通信事实**。

只有单机数据，难以证明"是谁"；只有手机数据，难以证明"做了什么"。

<a id="section-7"></a>

### 2.5 物理取证 vs 逻辑取证

| 维度 | 物理取证（Physical） | 逻辑取证（Logical） |
|---|---|---|
| 采集内容 | 整个介质的比特流，含未分配空间 | 特定文件/表/目录 |
| 恢复能力 | 可恢复已删除数据、文件碎片 | 只能拿到现存对象 |
| 体积 | 等于介质容量 | 通常小得多 |
| 通用性 | 高，任何工具可读 | 受操作系统与工具限制 |
| 证据强度 | 高（完整固定现场） | 中（依赖提取工具的可信度） |

> **核心原则**：**能用物理镜像就不用逻辑提取**。逻辑提取是物理不可行时的妥协（如设备未拆机、服务器不允许停机、加密无法物理读取），而不是效率优先的选择。

## 三、操作步骤

<a id="section-9"></a>

### 步骤 1：确认任务性质与授权来源

动手前必须书面确认三件事，缺一不可：

```text
1. 授权来源：委托人是谁，授权书/委托书/搜查证编号是什么
2. 目标范围：明确的设备清单（型号 + 序列号 + 容量），不接受"他所有电脑"
3. 时间边界：是否在关机状态，是否允许拆机
```

范围模糊是最大的风险来源。

"查这台机器"必须落到"查这块序列号为 XXX 的 NVMe"。

<a id="section-10"></a>

### 步骤 2：现场状态记录与封装

```bash
# 记录外包装状态（拍照是必须的，文字是补充）
# 1. 封装前：拍照 —— 封条、接口、开机状态、外观
# 2. 核对封条编号与委托书一致
# 3. 拆封时：双人在场，记录拆封时间
```

若设备处于**开机或休眠状态**，不要直接拔电。先评估：

- 是普通用户设备（内存数据价值高，但无休眠数据）→ 优先考虑内存采集或温和关机
- 是服务器（有服务连续性要求）→ 依委托方要求，可能只能做在线/远程取证
- 是涉案关键设备（无休眠文件风险）→ 记录屏幕状态后直接断电

<a id="section-11"></a>

### 步骤 3：建立工作副本

```bash
# 原则：原始介质只读挂载或封存，所有分析在副本上进行
# 1. 计算原始介质哈希（若条件允许，在挂载前完成）
sudo sha256sum /dev/sdX

# 2. 制作物理镜像（详见板块 2）
sudo dcfldd if=/dev/sdX of=/case/DigiForensics.dd \
     hash=md5,sha256 hashlog=/case/DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on

# 3. 校验：镜像哈希必须与原始一致
sha256sum /case/DigiForensics.dd
```

<a id="section-12"></a>

### 步骤 4：分层分析

按"大而全到小而精"的顺序推进：

```text
第 1 层 全局：分区表、卷列表、文件数量、时间范围
第 2 层 索引：文件系统时间线、关键字搜索、已删除文件列表
第 3 层 定向：按案件假设（人/时间/行为）收敛到具体对象
第 4 层 验证：对每条结论做独立验证（实际打开、实际解密、实际连通）
```

<a id="section-13"></a>

### 步骤 5：结论必须可复核

每一条结论都要能回答三个问题：

| 问题 | 合格答案的标准 |
|---|---|
| 怎么得到的？ | 能说出具体工具、参数、文件偏移 |
| 怎么确认不是误判？ | 有第二条独立证据或实际验证 |
| 别人能重现吗？ | 同工具同参数能得到同一结果 |

## 四、常见陷阱

本章按「任务性质与授权 → 采集方式与状态 → 分析与验证 → 结论表述」归组，每条给出：现象、为什么会误判、误判代价、正确做法。
★ 标记表示该操作会导致原始检材永久灭失或不可逆改变，执行前必须停下来确认。

<a id="section-15"></a>

### 4.1 任务性质与授权

<a id="section-16"></a>

#### 陷阱 1：把数据恢复的处置方式用到取证上

**现象**：委托方说"这个 U 盘里的照片被误删了，帮忙找回来"，分析员按恢复思路处理——挂载、多轮扫描、反复尝试修复文件系统。

**原因**：一概述把两者的目标函数说得很清楚——数据恢复追求成功率，允许多次写盘尝试；取证追求可辩护性，一次都不能错。

而"找回来"这个委托描述在日常语言里与取证完全一样，接收者无法从需求描述判断这是哪一类任务。真正的区分点是：**这件事将来会不会上法庭**。

**影响**：在恢复目标下失败的介质，送到取证目标下已不具备完整证据价值——因为恢复过程已经改变了它。

这条路是单向的。恢复做过的介质不能退回取证状态；取证状态可以承接恢复需求。

而分析员往往是在介质已经被改写之后才意识到这一点。

**核查**：动手前书面确认任务性质：

```text
1. 授权来源：委托人是谁，委托书/授权书编号是什么
2. 目标范围：设备清单（型号 + 序列号 + 容量），不接受"他所有电脑"
3. 用途定性：仅供内部使用 / 拟用于诉讼 / 拟提交监管
4. 时间边界：是否在关机状态，是否允许拆机
```

**第 3 项是分水岭**。若答案涉及诉讼或监管，全程按取证标准执行；若纯内部恢复，可以协商空间。不确定时按高标准做——成本增加有限，事后无法补救。

已经在恢复路径上走了怎么办：立即停止并记录当前状态，明确写"该介质在本次操作前已有 `<N>` 次尝试写入记录"。这个事实必须进入报告，而不是省略——省略它意味着报告在这一点上不诚实。

<a id="section-17"></a>

#### 陷阱 2：授权范围写成"他的电子设备"

**现象**：委托书写"查清该人员的电子设备内是否存在涉案数据"，分析员据此把家里和办公室的设备都纳入。

**原因**："电子设备"在授权文本里是一个没有边界的词——它可以指一台，也可以指全部。

而授权书的作用恰恰是划定边界。一个无边界的授权在实务中极易被挑战，而挑战的后果是整个取证工作的合法性受质疑。这条被单独列出，是因为它最容易在委托阶段被默认掉，又最难在事后补救。

**影响**：越界取证的全部产出都不能用。不是"部分可用"，而是在超范围设备上发现的一切都要排除，连带上它与范围内设备之间的关联证据也难以主张。

这类问题的成本与工作量成正比。越晚发现，代价越大。

**核查**：范围必须落到可唯一识别的物理标识：

```text
目标设备清单
- 设备 1：LENOVO ThinkPad，SN PF2XXXXX，1 TB NVMe
- 设备 2：SanDisk Ultra，SN 4C5300XXXXXX，128 GB
- 设备 3：Samsung SSD 860，SN S3ZXXXXX，500 GB
```

**三个要素缺一不可**：型号（易混淆）、序列号（唯一）、容量（验证用）。回到步骤 1 那句原话："查这台机器"必须落到"查这块序列号为 XXX 的 NVMe"。

**范围变更必须书面追加**，不能靠口头补充：

```text
范围变更记录
- 变更内容：新增设备 4（外接移动硬盘，SN WD-XXXX）
- 变更原因：设备 1 的浏览器记录中出现该硬盘的卷序列号
- 追加授权人 / 时间 / 方式（书面/邮件）
```

"为什么扩到这台设备"必须可追溯。案例中扩展目标的正当性来自证据线索，而"因为方便一起做了"不是理由。

<a id="section-18"></a>

#### 陷阱 3：把自行取证的结论当成可直接用于诉讼的证据

**现象**：企业 IT 部门做了内部排查，导出一批日志和邮件形成报告，准备提交给监管或用于诉讼。

**原因**：三种法律形式的技术手段几乎相同，区别在于是谁做的、以什么身份做的、要向谁负责（2.3 的开篇）。

企业自己的技术人员做出来的东西，在技术层面可能完全正确——而这恰恰是问题所在：它的外观与司法鉴定意见书没有区别，但它没有中立第三方的资质、检材交接记录与检验记录。技术正确性不解决可质证性。

**影响**：一旦进入争议程序，没有第三方背书的一方通常承担更重的证明责任（2.3 的原话）。对方只需质疑"数据被改过"且你自己无法证明没有，整份结论的证明力就下降了。

下降幅度往往超出预期，因为它是推定不可信，而非"存在疑问"。

**核查**：2.3 的实务要点就是正解——自行取证 + 主动引入第三方：

```text
阶段一：企业内部快速固定（时效优先）
  - 立即导出易失数据与关键日志，计算 SHA-256，记录导出时间与操作人
  - 目的：防止数据消失，不是形成结论

阶段二：引入第三方（效力优先）
  - 将已固定的检材移交鉴定机构，附阶段一的完整记录
  - 由第三方独立检验并出具鉴定意见

阶段三：衔接
  - 阶段一的操作记录作为阶段二的背景材料
  - 结论一律以阶段二的鉴定意见书为准
```

**关键点：阶段一的记录必须完整且不带结论。**

记录"我们导出了什么、什么时候、哈希是多少"，而不是"我们认为是谁干的"。前者是事实，后者是未经中立检验的判断——它会污染第三方独立检验的起点。

<a id="section-19"></a>

### 4.2 采集方式与状态

<a id="section-20"></a>

#### 陷阱 4：用逻辑提取代替物理镜像

**现象**：设备不允许停机，用工具远程导出 C 盘的主要目录与几个关键数据库，形成分析结论。

**原因**：逻辑提取看起来是"只读"——它读文件，不改文件。但提取过程本身可能修改目标：SQLite 在有活动连接时会写 journal/WAL，浏览器 profile 被读取时可能更新缓存，提取工具为了保持一致性有时会尝试获取锁或执行恢复。

2.5 的核心原则是"能用物理镜像就不用逻辑提取"。逻辑提取是物理不可行时的妥协，而不是效率优先的选择。

**影响**：两类损失同时发生。① 覆盖性损失：拿不到未分配空间、已删除数据、文件碎片——而这些恰恰是删除痕迹与反取证行为的载体。② 完整性损失：提取过程可能已经改变了被提取的对象，而你没有记录这件事。

第二条更麻烦。它连"我们知道发生了什么"这个补救机会都剥夺了。

**核查**：逻辑提取有明确的适用条件，且必须配套处理：

```bash
# SQLite：必须把 journal / WAL / SHM 一并复制，否则拿到的是不一致状态
cp target.db target.db-wal target.db-shm target.db-journal /evidence/
# 复制后逐个算哈希

# 提取前后各算一次目标哈希，差异即为目标被修改的证据
sha256sum /evidence/target.db
# ... 提取动作 ...
sha256sum /evidence/target.db
```

**报告里逻辑提取的表述必须自带限定**：

> "本次因设备不允许停机、无法制作物理镜像，采用逻辑提取方式获得 `<文件列表>`。**逻辑提取无法覆盖未分配空间、已删除数据与文件碎片**，本报告结论仅基于现存文件内容。SQLite 数据库已连同 `-wal` / `-shm` 文件一并复制并计算哈希，**提取前后目标文件哈希一致**。"

这段限定不是免责，是让委托方知道结论的边界在哪。边界清楚的有限结论，比无边界的完整结论更有用。

<a id="section-21"></a>

#### 陷阱 5：设备已开机且已被操作过，仍按"原始状态"取证

**现象**：查获笔记本时它开着机，屏幕停在桌面，分析员关机后正常做镜像，报告未提及开机状态。

**原因**：开机即改变系统状态——时间戳更新、swap 写入、登录记录生成、Prefetch 追加、事件日志新增。

步骤 2 对三种状态给了不同的处置，而"普通用户设备（内存数据价值高）"这一档的正确处置是"优先考虑内存采集或温和关机"，不是直接拔电。直接拔电会丢失内存数据；先关机又意味着内存数据永久消失。这是一个必须做的取舍，而取舍过程本身要记录。

**影响**：既成事实污染，且报告未记录。

这比"没做内存采集"严重得多。没做是可以说明的局限；隐瞒开机状态是事实陈述的不完整。案例结论要点里"停机超窗已如实记录，不隐瞒"体现的正是这个原则。

**核查**：开机状态一律先记录，再处置。记录不可补：

```bash
# ① 记录开机状态（拆封时双人在场，拍照 + 文字）
#    拍摄：屏幕内容、开机指示灯、连接的外设、运行中的窗口
# ② 记录时间（不是"我记的时间"，是设备显示的时间与现场时间都要记）
# ③ 按设备类型选择处置
```

| 设备类型 | 处置 | 记录要求 |
|---|---|---|
| 普通用户设备 | **内存采集优先**，或温和关机 | 是否采集内存、为何不采集 |
| 服务器（连续性要求） | 依委托方要求，可能只能在线取证 | 委托方的书面指令 |
| 涉案关键设备（无休眠文件风险） | 记录屏幕状态后直接断电 | 断电前的完整状态记录 |

"已经被人动过"这件事要单独查：事件日志的最后登录时间、`$UsnJrnl` 的时间范围、文件时间戳分布。如果这些时间早于扣押时间，说明扣押前有人操作过——这本身是重要发现。

**报告写法**：

> "**检材接收状态**：设备处于开机状态，屏幕显示桌面，运行 `<应用>`。已拍摄开箱照片 `<N>` 张，含屏幕内容与外设连接情况。
> **处置**：因内存数据价值高但设备无休眠文件风险风险不可控，经评估后先执行内存采集 `<或：委托方要求直接断电，已获书面同意>`，耗时 `<N>` 分钟。
> **既有污染**：事件日志最后一次正常关机为 `<时间>`，最后一次登录为 `<时间>`，均**早于扣押时间 `<时间>`**，表明设备在扣押前已被使用。该期间产生的痕迹已混入检材，本报告对其不做因果归属。"

最后一句是关键：既有污染不需要查清是谁造成的，只需要如实声明其存在与时间范围。

<a id="section-22"></a>

#### 陷阱 6：整个流程只算一次哈希

**现象**：制作镜像时算了一次 SHA-256，之后所有分析都基于这个镜像，再没有算过第二次。

**原因**："算了一次"给了充分的安全感——哈希在采集日志里，看起来流程是完整的。

但从采集到出具报告之间还有若干个环节会碰这个文件：工作副本的复制、解密后的导出、格式转换、carve 产物的写入目录（如果误设在同一分区）、甚至某些工具的临时文件。

四步 5 的三条问题里，第一条"怎么得到的"能答，第二条"怎么确认不是误判"就答不上来了——因为你没有分析后的哈希可比对。

**影响**：无法证明分析对象与采集对象是同一个东西。这在争议程序里是一个结构性缺陷：委托方可以合理质疑"你分析的是不是原始镜像"，而你没有材料回应。

**核查**：四次哈希，缺一不可。

```bash
# ① 源介质（挂载前完成）
sudo sha256sum /dev/sdX

# ② 镜像（制作时由 dcfldd 记录到 hashlog）
sudo dcfldd if=/dev/sdX of=/case/DigiForensics.dd \
     hash=md5,sha256 hashlog=/case/DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on

# ③ 分析副本（从镜像复制出的工作副本）
sha256sum /case/DigiForensics.dd
cp --reflink=auto /case/DigiForensics.dd /work/DigiForensics-work.dd
sha256sum /work/DigiForensics-work.dd

# ④ 分析后（重新校验，确认分析全程未改动）
sha256sum /case/DigiForensics.dd
sha256sum /work/DigiForensics-work.dd
```

**四次一致才说明全程未被改动。** 记录成一张表：

| 环节 | 对象 | SHA-256 | 时间 | 操作人 |
|---|---|---|---|---|
| 采集 | `/dev/sdX` | `<值1>` | `<t1>` | `<人>` |
| 镜像产出 | `/case/DigiForensics.dd` | `<值1>` | `<t1>` | `<人>` |
| 副本建立 | `/work/DigiForensics-work.dd` | `<值1>` | `<t2>` | `<人>` |
| 分析后 | 两文件均 | `<值1>` | `<t3>` | `<人>` |

若 ④ 与 ① 不一致，立即停止分析并查明。这时的优先级是保护证据状态，不是完成分析。

<a id="section-23"></a>

### 4.3 分析与验证

<a id="section-24"></a>

#### 陷阱 7：结论只靠"格式匹配"支撑

**现象**：在磁盘中搜到 `password.txt` 并提取出来，报告写"已找到该文件密码"；或在内存里搜到某串 hex 判定为"账号密码"，报告写"已获取访问凭据"。

**原因**："找到了一个叫这个名字的文件"与"文件里有可用的密码"之间隔着内容。提取出来可能是空的、可能是模板、可能是示例、可能是另一个系统的。

而 4 步 4 的第 4 层专门要求"对每条结论做独立验证（实际打开、实际解密、实际连通）"。这条要求的存在就是为了防止"提取到"被当成"有效"。

更普遍的问题是：格式匹配的搜索结果会自动带上"这一定是关键证据"的暗示，尤其当文件名与委托描述高度吻合时。

**影响**：一个关于"已获取关键材料"的结论，若实际是空的或无效的，后续所有依赖它的推论全部落空。

而这类结论往往是报告的核心卖点。它会被委托方首先引用，也因此最经不起质疑。

**核查**：提取 → 验证 → 表述，三步不可跳：

```bash
# ① 提取
icat -o 2048 /work/DigiForensics.dd <inode> > /evidence/password.txt
# ② 验证内容（不是看文件名，是看内容）
file /evidence/password.txt
wc -c /evidence/password.txt            # 大小为零 = 空文件
strings /evidence/password.txt | head   # 看实际内容形态
# ③ 记录哈希
sha256sum /evidence/password.txt
```

**三种验证结果，三种表述**：

| 验证结果 | 报告写法 |
|---|---|
| 内容为可用的凭据 | "文件内含 `<N>` 组凭据，已用其中一组对 `<系统>` 做 `<实际验证动作>`，验证通过/失败" |
| 文件存在但内容为空 | "**存在该文件，大小 0 字节，无内容**" |
| 内容为模板/示例 | "文件内含 `<描述>`，**经检查为 `<发行版自带示例 / 模板文件>`**，非本案相关凭据" |

"实际验证"在很多场景下做不了（不能真的登录），那就要写成："内容形态为明文凭据格式，本次未做可用性验证。"

"未验证"是一个合法状态，"隐含已验证"不是。

<a id="section-25"></a>

#### 陷阱 8：把公用设备上的证据归给特定用户

**现象**：办公室共用电脑上有某个操作痕迹，报告认定"该用户在 `<时间>` 执行了 `<操作>`"。

**原因**：公用电脑有共享账户——多个员工用同一个 Windows 账户登录，文件系统元数据记录的是账户，不是人。

而排查方向一开始就指向某个具体人，这个预期会让"账户 = 人"这个跳跃自动完成。外观证据、事件日志、Prefetch 全部指向账户 ID，而账户 ID 背后可能是十个人。

**影响**：这是本篇最严重的结论错误类型。它把一个技术事实（某账户做了某操作）升级成一个人责事实（某人做了某操作）。

案例结论要点里写得很清楚："离职员工账号 ≠ 离职员工本人，需进一步做人机对应分析，报告中明确标注这一局限。"案例中那条"已离职员工账号成功登录 3 次"的发现，定性依据是"账号 + 时间线交叉"，不是"这个人"。

**核查**：账户与人之间必须有独立的绑定证据：

| 绑定维度 | 工件 | 绑定强度 |
|---|---|---|
| **用户特定活动痕迹** | UserAssist（用户特定 GUID 的执行记录）、SRUM | 强 |
| **应用层账号** | 浏览器登录账号、邮件客户端账户 | 中 |
| **人脸/生物特征** | 解锁记录、摄像头照片 | 中 |
| **物理在场** | 门禁、监控、座位 | 中 |
| **设备指纹** | 同一账号在其他设备登录 | 弱 |
| **时间线吻合** | 操作时间与作息/在岗时间一致 | 仅作辅助 |

```bash
# UserAssist 是用户特定最强的工件：每个用户有独立 GUID
python3 -m volatility3 -f DigiForensics-mem.raw windows.userassist

# SRUM（Vista+）：每用户的使用时长与前台应用记录
python3 -m volatility3 -f DigiForensics-mem.raw windows.srum
```

**报告表述必须分层**：

> "**技术事实**：Windows 账户 `<账户名>`（SID `<SID>`）于 `<时间>` 完成登录，并在随后 `<N>` 分钟内完成 `<操作>`。
> **交叉印证**：该账户登录后 2 分钟内，一台内网主机向公网 IP 传输 1.2 GB 数据，**两条独立时间线吻合**。
> **人机对应**：`<已通过 UserAssist 关联至用户 X / 未完成人机对应分析>`。
> **本报告不认定该操作由 `<具体人员>` 实施。**公用设备存在账户共用情形，账户与自然人的对应需 `<UserAssist / SRUM / 其他>` 证据支持。"

最后那句不是谨慎的措辞，是结论的准确性所必需的。

<a id="section-26"></a>

#### 陷阱 9：拿不到数据时以为"拿到了机器就等于拿到了数据"

**现象**：磁盘镜像做完了，`fls` 能列文件，但关键目录全部是密文或空目录，分析员判"该设备无相关数据"。

**原因**：2.2 列出了"易被改写"之外的多个派生要求，其中一条是"存储易失"——但真正拦住你的往往是访问控制层。

域环境、BitLocker、EFS、浏览器主密码都可能拦住你。

而"镜像做完了"这个里程碑会带来强烈的完成感，它容易被误当成"这一步结束了"。现象上，"文件是密文"与"没有文件"在目录列表里非常相似。

**影响**：一个彻底的假阴性，且它以"完成了全部工作"的形式交付。委托方据此结案，而实际上数据一直在盘上，只是被访问控制挡住了。

**核查**：访问控制层次要逐层确认，不能只看文件系统：

```bash
# ① BitLocker：分区类型 GUID + 卷尾标识，不看工具的类型翻译
fdisk -l /case/DigiForensics.dd
grep -aob -- '-FVE-FS-' /case/DigiForensics.dd

# ② EFS：文件名带随机扩展名，内容密文
fls -r -p -o 2048 /case/DigiForensics.dd | grep -E '\.[A-Za-z0-9]{14,16}$' | head

# ③ 全盘加密（Android 等）：检查设备加密状态
# ④ 浏览器主密码：Chrome 存在但 Key 3/4 不可读

# ⑤ 域凭据：是否存在可用凭据（授权范围内）
```

**阴性发现必须限定范围**：

> "在 `/case/DigiForensics.dd` 全盘范围（含未分配空间）内，以关键字 `<关键词>` 与文件签名扫描检索，**未发现与 `<案件描述>` 相关的内容**。
> **本次受以下限制**：① 目标卷为 BitLocker 全卷加密（卷尾存在 `-FVE-FS-` 标识，卷标识符因位于加密区未能读取），未获授权密钥，本次未解密，该卷内数据整体未纳入检索范围；② 存在 EFS 加密文件 `<N>` 个，内容为密文；③ 浏览器数据受主密码保护。
> **本结论不表明该设备不存在相关数据。**建议向委托方申请 BitLocker 恢复密钥后重新检索。"

这一段里最重要的不是"未发现"，而是"未覆盖范围"那三条。它把结论的适用边界画清楚了，委托方能据此决定下一步。

### 4.4 结论表述

<a id="section-28"></a>

#### 陷阱 10：分层分析跳层，直接做定向推断

**现象**：拿到镜像后直接对某个假设去找证据——委托方说怀疑是某账号登录的，就只查该账号的登录记录，找到就收工。

**原因**：步骤 4 的四层是递进的（全局 → 索引 → 定向 → 验证），每层的产出是下一层的输入。跳过前两层，定向层就失去了"全局认知"这个基础——你不知道这个系统的整体时间范围、文件总量、用户数、有没有第二个账号也在做类似的事。

而"按假设找证据"这个动作本身就带着只看得见符合假设的证据这个结构性偏差。

**影响**：一个由预设结论组织起来的报告。它不是造假，但它的问题是遗漏与选择性呈现——而这两者在质证时与造假的后果相当。

案例第 1 步"查该服务器 2024 年 3 月以来的异常登录"看起来是定向的，但案例的实际执行是先做全局、再做在线固定、再做物理镜像。定向假设是在全局认知之后才收敛的。

**核查**：四层递进，每层留输出：

```bash
# 第 1 层 全局：分区、卷、文件数量、时间范围
fdisk -l /case/DigiForensics.dd
fsstat -o 2048 /case/DigiForensics.dd | grep -iE 'created|modified'
fls -r -o 2048 /case/DigiForensics.dd | wc -l

# 第 2 层 索引：时间线、已删除、关键字
fls -r -p -o 2048 /case/DigiForensics.dd > /evidence/fls-all.txt
grep -iE 'deleted' /evidence/fls-all.txt | head -50

# 第 3 层 定向：按人/时间/行为收敛
# 第 4 层 验证：每条结论独立验证
```

第 1 层的产出直接决定第 3 层的合理性。如果你不知道这台机器有多少个用户，"只有该账号登录过"这个结论就没有对照。

没有基线就没有异常。这正是 2.1 表里"统计学 → 决定什么算异常"那行的含义。

<a id="section-29"></a>

#### 陷阱 11：把三种法律形式的结论混用

**现象**：企业内部排查形成的结论直接写进正式报告，格式与鉴定意见书一致，但没有鉴定机构资质与检验记录。

**原因**：格式相似会造成效力误认。用"检验所见"这样的措辞、用"鉴定意见"的标题，会让读者以为这是中立第三方的结论。

而 2.3 的表里三种形式的结论形式是不同的：鉴定意见书（可作为定案依据）、公证书 + 证据保全记录、无固定格式自担证明责任。

**影响**：在不知情的情况下承担了鉴定机构的责任，却不具备相应的资质与程序。

一旦进入争议程序，"我们公司出了鉴定意见"这个表述本身可能构成误导——它比"我们公司做了内部排查"严重得多。

**核查**：结论的署名与表述必须与执行主体一致：

| 执行主体 | 结论标题 | 必须包含 |
|---|---|---|
| 有资质鉴定机构 | 鉴定意见书 | 资质信息、检材交接记录、检验过程、逐项分析、结论 |
| 公证机构 | 公证书 + 证据保全记录 | 保全时间、方法、公证员信息、原始载体封存情况 |
| **企业自行** | **内部调查报告 / 技术分析说明** | 执行主体声明、适用范围、局限说明、不作法律结论的声明 |

**自行取证的报告必须有的三句话**：

> "1. **主体声明**：本报告由 `<公司>` 内部技术人员 `<姓名/岗位>` 执行，**本机构不具备司法鉴定资质**，本报告不构成鉴定意见。
> 2. **用途限定**：本报告用于 `<内部决策 / 配合第三方鉴定 / 初步线索>`，**未经法定鉴定程序，不作为诉讼中的定案依据**。
> 3. **局限声明**：本次工作基于 `<逻辑提取 / 物理镜像>` 方式获取的数据，**未覆盖 `<范围>`**；结论受第 X 节列明的限制约束。"

这三句话看起来是自我设限，实际作用是保护公司。它是"我尽了合理注意"的证明。

<a id="section-30"></a>

#### 陷阱 12：把阴性发现写成绝对否定

**现象**：报告写"未发现涉案数据"，全文没有说明检索了哪些范围、用什么方法、没覆盖什么。

**原因**："未发现"这个表述在中文里天然被读作"不存在"，尤其当它前面没有任何限定词时。

而 2.2 的五条派生要求里，"体积巨大 → 必须分层抽样"这一条本身就说明全覆盖是不现实的；步骤 4 的第 1–2 层是抽样性的检索，不是穷尽。把抽样结果写成穷尽结论，这是一个表述层面的越界。

**影响**：在争议程序里，无法支撑的否定性结论比不做结论更糟。"未发现"会被对方引用为"鉴定机构没有发现，也就是不存在"，而你的方法记录无法证明这个推论。

这属于表述引发的责任扩大。

**核查**：三段式否定表述（这个结构在 [NTFS 数据流与隐藏数据](../../filesystem/filesystem-ntfs/filesystem-ntfs-ntfs-alternate-data-streams.md) 与 [BitLocker](../../crypto/crypto-volume/crypto-volume-bitlocker.md) 中反复出现）：

> "**（1）范围**：在 `/case/DigiForensics.dd`（`<容量>`，NTFS，起始扇区 2048）的**全盘范围**内，包含已分配空间、未分配空间与卷影副本。
> **（2）方法**：① 关键字检索（UTF-8 / UTF-16LE 双编码）；② 文件签名扫描（PNG / JPEG / PDF / ZIP / OOXML 等 `<N>` 类）；③ 目录树全量枚举 + 已删除条目列举；④ 数据流检查（`fls` 全量输出 + `istat` 属性列表）。
> **（3）结果与未覆盖范围**：在上述范围内**未发现**与 `<案件描述>` 相关的内容。**未覆盖**：① BitLocker 加密卷（无密钥）；② EFS 加密文件 `<N>` 个；③ 设备上已物理损坏、镜像时以填充值替代的扇区 `<N>` 个；④ 云端数据（不在本次委托范围）；⑤ 委托范围外的其他设备。
> **本结论不表明该设备不存在相关数据。**"

第（3）项的"未覆盖"清单不是可选的。它把"未发现"从一个技术观察变成了一个方法论陈述，而后者才是可辩护的。

阴性发现的表达能力 ≠ 技术操作能力。不要用同一个标准衡量。

## 五、案例示例

<a id="section-32"></a>

### 5.1 运行中的服务器：30 分钟窗口与 96 分钟镜像

**场景**

某公司发现内部服务器疑似被未授权访问，委托第三方做取证。委托范围是"查该服务器 2024 年 3 月以来的异常登录"，并明确"服务器不得停机超过 30 分钟"。

委托方的问题有两个：登录是不是真的发生过，以及为什么停机时间超出了约定。

选择这一路径的依据是它同时踩中了三个取证分类维度：目标在运行状态（决定采集方式）、范围是逻辑而非全盘（决定委托书要写清）、服务连续性有硬约束（决定方案可行边界）。

三个维度里，"范围"这一个后来反复咬人。委托书写"异常登录"，报告里就不该出现与登录无关的分析；反过来，委托方中途追加的"查一下有没有工资表"（见 5.3）也必须走补充授权，否则即便查出来也不能用。范围不是工作量的问题，是这份报告能不能被引用的前提——超出授权取得的材料，在质证时对方第一句就会问它是怎么进来的。

**处置过程**

1. 确认授权，取得书面委托书：目标为机架式服务器、SN 已登记、允许 30 分钟停机窗口。委托范围只写"异常登录"，没写"全盘取证"——这个措辞差决定后面能不能碰非日志数据。

2. 状态判定：设备运行中。评估后决定先做在线数据固定，再申请窗口做物理镜像。

3. 在线固定当前状态：导出登录会话、关键日志、磁盘占用快照，全部记入时间戳并计算 SHA-256。

**这一步的顺序有讲究**：登录记录是最易失的证据之一，而物理镜像要 96 分钟。如果先关机、先插写保护器再取登录数据，这 96 分钟里新产生的登录记录就已经漏掉了。本案后来确实在 `Security.evtx` 的增量区段里发现了镜像制作期间的一条新登录——不是靠镜像，而是靠在线固定时导出的那份副本补上的。

4. 窗口期做物理镜像，挂载写保护器后拔出原盘：

```bash
sudo dcfldd if=/dev/sdX of=/case/DigiForensics.dd \
     hash=md5,sha256 hashlog=/case/DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on
```

实测耗时 96 分钟，超出 30 分钟窗口 66 分钟，已在报告中说明并取得委托方书面确认。

**停机时长该怎么量，是个容易做糊的地方**。96 分钟是 `dcfldd` 从读第一个块到写完最后一个块的墙钟时间，但它不包含写保护器接入前的确认时间（`lsblk` 三项核对、挂载点检查）与接入后的验证时间（`vf=` 复验、`sha256sum` 复算）。本案的实际服务中断是 104 分钟，比 96 多 8 分钟——这 8 分钟是分析员自己加进去的确认动作。

两种口径都对，但必须**明确声明用的是哪一种**。委托方事后核对监控时看到的是 104 分钟，报告里若只写 96，反差就成了新的疑点。

**还有一个分类问题在动手前就该定**。委托书写"异常登录"，那么"异常"这个词要不要在报告里重新定义？本案的做法是把"异常"落成可核验的三个条件，并写进报告首页：

```text
本报告所称"异常登录"，指同时满足以下任一条件的登录事件：
  (1) 账号在 HR 系统标记为离职/禁用状态后发生的成功登录
  (2) 源 IP 不属于该账号的常用终端登记清单
  (3) 登录后 5 分钟内该主机出现出站流量突增（阈值：100 MB）
```

这一段看起来像是多此一举，但它防住的是委托方最常见的反问："你说的异常是什么意思？"——定义写在报告里，双方的争议范围就从"这算不算异常"缩到了"事实是否如此"，而后者是可以被证据检验的。

定义落到数字上还有一个副作用值得留意：阈值一旦写进报告，日后任何人想改它都得走变更流程。本案后来委托方想把"出站突增"阈值从 100 MB 调到 50 MB 以便发现更小的外传，分析员没有直接改，而是另出一份补充分析并说明两次口径下的结论差异——阈值可以调，但不能让同一份报告出现两套标准。

**把口径固定在报告里，还有一个更重要的作用**。委托方内部往往有多个人同时在看进度，他们对"异常"的理解可能完全不同。定义写在报告首页，等于给所有人发了同一份说明书——取证报告的一个隐含功能，是把委托方内部的认知差异也一并对齐。

**结论**

能证明：镜像在写保护器接入状态下完成，`DigiForensics.dd` 与其 hashlog 同步产出，采集过程未对原盘产生写入。采集在源系统停机状态下进行，因此文件系统一致性成立。

超窗这一事实本身不影响镜像效力。它影响的是委托履行——报告如实记录并取得补充确认即可。

这里值得对照的是"在线镜像"与"停机镜像"在结论措辞上的差别：同一份 `DigiForensics.dd`，若在线采集，报告必须写明"文件系统非一致性快照，依赖全盘瞬时状态的结论不成立"；本案因为是停机状态，这句话可以完全省略。**多花 104 分钟买掉了这一整段限定**，这才是停机窗口这笔账真正的算法——委托方抱怨的从来不是超窗，是超窗换来的东西值不值。

顺序上也值得记一笔：正确的次序是"在线固定易失证据 → 停机 → 物理镜像"。本案最初的操作员想先关机再取日志，理由是"离线取更干净"——这在技术上没错，但在策略上错了，因为关机会让 96 分钟的采集窗口内产生的登录记录永久消失，而那批记录里恰好有后来成为关键证据的一条。

**代价与收益的对比最终是**：多花了几分钟做在线固定（几乎不增加停机时间），换回了镜像里本来没有的那条登录记录。若当时按"先关机"执行，这条记录永远拿不回来，且报告里不会有人知道它存在过——这类缺口比报错更危险。

**误判对照**

最容易得出的错误结论是「把这 96 分钟解释成'因业务高峰期延后'，或者干脆不写」。判据有三条：

①委托书上写的是 30 分钟、`dcfldd` 日志记录的墙钟是 96 分钟，差值 66 分钟是两份客观记录里的两个数字，**不需要任何解释性措辞**来成立；
②若报告只写 96 分钟而未声明口径，委托方核对门禁监控得到的 104 分钟（96 + 前后确认时间）会与报告直接矛盾，这个矛盾比"超窗"本身更难解释；
③委托范围写的是"异常登录"而非"全盘取证"，说明委托方对停机代价有明确预期却仍给了 30 分钟——超窗是**方案选择**问题（未先做 LVM snapshot 就直接对 1 TB 盘做全盘镜像），不是执行疏忽，混着写反而模糊了真正的改进点。

照实写「实测采集 96 分钟，含前后确认合计服务中断 104 分钟，超出约定窗口 74 分钟；原因：1 TB 数据量与 `bs=4M` 写入带宽，未采用 LVM snapshot 分层采集」，并附委托方补充确认。

按错误判据走的代价不是技术上的，而是执业上的：一旦对方复查门禁或监控日志发现真实停机时长与报告不符，整份报告的其余内容都会被连带怀疑。

<a id="section-33"></a>

### 5.2 离职员工账号的 3 次成功登录与 1.2 GB 外传

**场景**

镜像分析发现 Windows 事件日志中存在使用**已离职员工账号**的成功登录 3 次，该账号在 HR 系统中的离职日期为 2024-03-02，日志中的登录时间均在离职日之后。

委托方想知道是谁干的。

选择这一路径的依据是账号线索是最容易被过早定性的那一种——它是行为起点，不是行为主体。

**处置过程**

1. 提取登录事件并确认关键字段，而不是只记时间：

```bash
# 4624 成功登录：逐条看关键字段，不只看时间
# 关键字段：Account（域\\用户名）、LogonType、IpAddress、
#           WorkstationName、LogonTime
python3 -m Evtx.Evtx -f Security.evtx --ls | grep -c 4624
```

登录事件摘要（3 条，均在离职日之后）：

```text
2024-03-11 09:14  LogonType=3  CORP\\zhangwei  10.20.3.47
2024-03-14 22:07  LogonType=3  CORP\\zhangwei  10.20.3.47
2024-03-18 21:52  LogonType=3  CORP\\zhangwei  10.20.3.91
```

2. 把账号线索当线索而非结论，引入第二条独立时间线——出口流量记录：

```text
2024-03-11 09:16  10.20.3.47 -> 203.0.113.x   出站 1.2 GB
2024-03-14 22:09  10.20.3.47 -> 203.0.113.x   出站 870 MB
2024-03-18 21:54  10.20.3.91 -> 203.0.113.x   出站 640 MB
```

3. 三个会话里两次都在登录后 2 分钟内出现同一内网主机的大流量出站，构成模式一致而非单点巧合。

4. **主动去证伪"是本人"这个假设**，而不是等它自己站住。既然账号 ≠ 人是本案的核心，检验它就该是主动的：

```bash
# a) 该账号名下有没有交互式登录（LogonType=2/7/10）？有则"他人冒用"假设动摇
python3 -m Evtx.Evtx -f Security.evtx --ls | grep -E '4624' | grep 'zhangwei' | grep -v 'LogonType=3'

# b) 源主机 10.20.3.47 的物理位置与归属
python3 -m Evtx.Evtx -f Security.evtx --ls | grep -E '6013|4624.*10.20.3.47' | tail -20
# 命中：10.20.3.47 = 工位 FIN-0412，绑定设备 DLT-8841

# c) 离职交接单：设备是否已回收？
grep -A5 'zhangwei' /hr/离职交接表.csv
# 命中：笔记本 DLT-8841 于 2024-03-04 交回 IT，签收人：IT-资产管理员
```

第 c 项是决定性的一击：设备在 3 月 4 日已回收，而 3 月 11 日的登录来自绑定了这台设备的主机。登录主机上跑着一个属于别人的账号，且用的是一台已经交回的设备——这已经不是"冒用"的可能性，而是"内网内有人用交接后的机器登录他人账号"的确定路径。

补一句方法论上的提醒。账号归属这类线索的调查，最容易犯的错是**在账号方向上越挖越深**。本案在 `zhangwei` 的文件系统里花了 6 小时（邮件、浏览器历史、最近访问、回收站），总共只找到 1 条有价值的线索；而设备归属那一条查了 40 分钟，直接把结论从"账号被冒用"推到了"内部人员操作"。账号是行为起点，人和设备才是行为主体——**追主体比追凭据有效得多**。

**"账号 ≠ 人"这个检验还应该更早做**。本案在提取到 4624 记录之后、深入分析之前，本可以做一次快速的归属检查——查 HR 系统该账号状态、查设备登记单。成本是十分钟，能避免后面 6 小时的方向性投入。

**这个顺序的价值在于：它决定了后续所有工作的方向**。先确认账号与人的关系，再决定要不要往文件系统里挖；反过来，则容易在一个可能根本不相关的账号上投入全部时间。**取证分析的第一步往往不是分析，而是决定不做什么。**

而"账号 ≠ 人"这个检验比"主动证实"更省时间。顺着已有线索往下挖，速度快但方向单一；证伪只需要找到一个反例就能改变结论——本案设备回收记录只查了 40 分钟，就推翻了"账号被冒用"这个看起来已经成立的假设。更重要的是，**证伪的过程本身会产出新线索**：查"这台设备现在在谁手上"时，顺带发现它已回收到 IT 资产部门，这条信息是查之前不知道的。

5. 再补一条独立来源，把"外传"这件事坐实：

```text
2024-03-18 21:54  10.20.3.91 -> 203.0.113.x  出站 640 MB
2024-03-18 21:55  DLT-8841  USB 大容量存储设备插入事件（Event ID 2003）
2024-03-18 22:31  10.20.3.91 注销（LogonType=3）
```

出站、U 盘插入、注销三条记录在 3 分钟内首尾相接，三者来自不同日志源，互不依赖。

**这一步之后还要回头看那个"最像"的东西**。整理过程中，`zhangwei` 的 Outlook 数据目录里出现了大量 2024-03-11 之后的邮件——乍看像是"离职后仍在用邮箱"的有力证据。细查之后发现全是自动转发规则留下的痕迹：Exchange 侧显示该账号在 3 月 6 日被配置了向外部地址转发的规则，规则创建者是域管理员（运维变更单号 CHG-2024-0311），与 `zhangwei` 本人无关。

**一条最可疑的痕迹，最后被证明是系统正常行为**——这是本案最值得记下来的一处。它同时说明两件事：一是异常行为会在最显眼的地方留下最显眼的痕迹，而显眼往往意味着其他解释更容易被忽略；二是"看起来最像证据的东西"必须和行政记录（变更单、审批流）交叉验证，否则很容易把一次合规的运维配置写成离职人员的数据外传。

**结论**

能证明：该账号在离职后被用于三次成功登录，其中两次登录后 2 分钟内对应主机发生大流量出站传输。这是账号被冒用或被内部人员复用的强关联证据。

进一步地，设备 DLT-8841 已于 2024-03-04 回收至 IT 资产部门，而 3 月 11 日与 14 日的登录来自绑定该设备的主机 10.20.3.47——登录主机与设备归属之间的矛盾，是内网内部人员操作的有力指向。

不能证明：外传者就是账号名义持有人。三次登录全部为 `LogonType=3`（网络登录），而 3 月 18 日那次源 IP 已变为 `10.20.3.91`，说明至少存在一台不属于原持有人常用位置的终端。

**误判对照**

最容易得出的错误结论是「离职账号在离职后登录，因此是离职员工本人实施了外传」。判据有三条：

①三次登录的 `LogonType` 全为 3（网络登录），这类登录走的是域控的 NTLM 校验，**不需要交互式会话、不触发锁屏、不留键盘输入痕迹**——共享账号、缓存凭据、他人代登都完全正常；
②第 3 次的 `IpAddress` 由 `10.20.3.47` 变为 `10.20.3.91`，同一操作者若在原工位操作，源 IP 不会凭空变化，说明使用环境不固定；
③设备 DLT-8841 的归属记录显示它 2024-03-04 已回收，而绑定该设备的主机在 3 月 11 日仍有 `zhangwei` 的登录——**账号的登录主体与设备持有人已经分离**，这是"账号 ≠ 人"的直接证据，而非推测。

正确判据是登录类型、源 IP 与设备归属三者的组合。`LogonType=3` 连口令交互都不需要，账号泄露即可用；源 IP 变化说明使用环境不固定；设备归属错位说明有人在一台不该有该账号的机器上用了它。

报告结论应停在「账号被冒用或被复用，实施者为 IT 资产管理权限范围内的内部人员可能性较高，需进一步做人机对应」。

三条时间线并排看时，还有一个细节支持这个方向——三次登录的间隔：03-11、03-14、03-18，间隔分别为 3 天和 4 天。这个节奏不像一次持续的外传行动，更像**间歇性的、每次做一点就走**的试探性访问。真要大规模外传，2.7 GB 的量在有充足时间的情况下没有理由分三次、间隔三到四天。

这个推断不能作为证据写进报告——间隔模式不排除巧合——但它能决定下一步该查什么：查 10.20.3.47 与 10.20.3.91 的物理位置（工位归属、门禁记录），而不是继续深挖 `zhangwei` 的文件系统。一个方向已经足够清楚时，继续在原方向上加细节是浪费。

**这个决策的通用形式值得记住**：当某条线索已经足以指向下一步动作时，它就完成了自己的作用。继续在同一方向上收集更多同类证据，边际价值迅速递减；而**换一条独立来源的时间线**，价值往往更高。

三条登录记录再加十条，还是那三条；换成一条设备归属记录，一次就推翻了原假设。**证据的价值不取决于数量，取决于正交性。**

按错误判据走的代价：结论一旦指认到具体自然人，而对方举证那台终端当晚由他人使用，整条论证被推翻且难以挽回。对人的指认必须有比账号更强的独立证据——本案最终靠的是设备回收记录，不是登录记录。

### 5.3 委托范围外的文件类型：未发现即需限定

**场景**

同一案件中，委托方后追加问题："确认一下服务器上有没有员工私自存放的工资表"。该项需求不在原委托书范围内，涉及含个人信息的文件内容分析。

这条路径值得单列，因为它检验的是阴性发现的表述纪律——不是技术问题，是结论边界问题。

**处置过程**

1. 先确认授权范围是否已覆盖，未覆盖则补充授权，不擅自扩大：

```bash
# 范围核对：文件名与类型检索，列出但不打开内容
istat /mnt/case/DigiForensics.dd | grep -iE '\.(xlsx|xls|csv)$'
```

这一步的输出量本身就有意义。本案这类表格文件共 412 个，其中文件名含"薪酬/工资"字样的 3 个，全部是 HR 部门的正式发布件（有明确的发文目录与密级标识）。**把数量说出来，比只说"未发现"要有用得多**——它告诉委托方"我们查了 412 个，命名规范，3 个可解释"，这比一个孤零零的否定结论更能建立信任。

2. 检索要有对照，否则"未发现"没有说服力：

```bash
# 阳性对照：证明检索方法本身有效（能查到确实存在的关键字）
istat /mnt/case/DigiForensics.dd | grep -icE 'salary|payroll|工资|薪酬'
# 输出 3 —— 与人工核对的 HR 发布件数量一致，说明检索没跑偏

# 阴性对照：确认扩展名分布不是被 istat 的解析方式筛掉了
istat /mnt/case/DigiForensics.dd | grep -icE '\.(xlsx|xls|csv)$'   # 412
istat /mnt/case/DigiForensics.dd | grep -icE '\.(zip|rar|7z)$'     # 1
```

阳性对照这一条经常被省略，但它是阴性发现的方法论前提：先证明"如果东西在，我能找到"，再说"我没找到"。 没有阳性对照的阴性结论，本质上无法区分"确实没有"和"方法没覆盖到"。

本案有一个现成的机会差点被浪费掉。人工核对 HR 目录时发现有一个文件叫 `2024年薪酬调整汇总表.xlsx`——`istat` 检索命中了它，`grep -c` 输出 3，与预期一致。**这个"数量对上了"的巧合，比什么都值钱**：它证明检索确实在正常工作，而不是因为编码问题、路径问题或镜像解析问题导致的静默零命中。如果这里输出是 0，那就得回头查工具，而不是写进报告。

3. 把结果按"范围 + 检项 + 未发现"的句式写进报告，而不是一句"未发现工资表"。

具体到本案，这句话写出来是这样的：

```text
检项：文件名与扩展名匹配检索
范围：分区 2（-o 4624）内全部 MFT 记录，扩展名限 .xlsx/.xls/.csv
方法：istat 遍历 + grep -icE 关键词匹配；未打开任何文件内容
对照：阳性对照命中 3 个 HR 正式发布件，与人工核对数量一致
结果：412 个表格类文件中，未发现除上述 3 个 HR 发布件之外的工资表
未覆盖：（1）文件内容（2）1 个 .zip 归档内部（3）已删除且未恢复的残留
```

**这三行各有各的作用**。"方法"行决定了这份阴性结论能被引用的范围；"对照"行堵住了"工具根本没跑"这条质疑路径；"未覆盖"行把委托方需要注意的缺口提前摆在台面上，而不是等他们自己发现。第三行尤其重要——**主动写出缺口，比事后被人指出来更像专业**。

**这三行还有一层隐含作用：它们让这份结论可以被复用**。假设一年后另一个案件遇到类似问题，这份报告的检项描述可以直接被抄过去当起点。反过来，如果只写一句"未发现工资表"，任何人都无法判断它能不能用于自己的场景，也就只能从零重做一遍。**阴性发现的真正资产是它的方法描述，不是它的结论。**

对委托方而言，这三行同样决定他能否独立判断：如果只拿到一句"未发现工资表"，他能做的只是相信或不信；拿到"412 个文件全部核对、阳性对照 3 个命中、1 个压缩包未解"，他就能判断这份结论对他是否够用。委托方才是承担后果的一方。

本案后来正是靠这个判断权救回来的：委托方看了那行"1 个 .zip 未解"，决定自己找那台机器的持有者核实，最终在另一个人的移动硬盘里找到了目标文件。机构没能查出的东西，委托方顺着方法描述查到了——这份报告在那一刻才真正完成了它的作用。

**结论**

阴性发现：在上述文件名与扩展名检索范围内（412 个表格类文件全部核对），未发现文件名含 salary/payroll/工资/薪酬 字样且不属于 HR 正式发布件目录的表格文件。检项为文件名与扩展名匹配，未打开任何文件内容。

未覆盖范围包括：文件名不含相关关键词但内容为工资表的文件、加密压缩包内的表格（本案检出 1 个 `.zip`，未解压）、以及已被删除且残留数据未恢复的部分。这三个未覆盖项必须在报告里列出，否则"未发现"会被读成"服务器上没有工资表"。

还有两项本次也没进未覆盖清单、事后觉得应该写：一是取证范围的时间窗，本案只覆盖 `-o 4624` 事件之后到镜像采集之间的会话，更早的登录会话未回溯；二是这台机器是否存在第二个数据盘或网络共享，第五节的"服务器内"只指分区 2。前者是取证流程的既定边界，后者是委托范围本身的问题——两个都不该由分析员替委托方假定。

**误判对照**

最容易得出的错误结论是「经检查，服务器内不存在违规存储的工资表」。判据有三条：

①这个表述是**全称否定**，而实际检项只覆盖文件名与扩展名——从未打开任何 `.xlsx` 内容，也未做内容级关键词扫描，两者相差一个数量级的覆盖范围；
②检出的那个 `.zip` 归档从未解压，却未列入未覆盖范围，这等于默认它不含相关内容，而这正是 iii.1 里"先解包再检索"规则要防的漏检；
③412 这个数量本身说明服务器上确实存在大量表格文件，其中"文件名无害但内容是工资表"是现实存在的形态（改过名的导出文件最常见），这类文件本检项在原理上就看不到。

按错误判据走的代价是双向的：对委托方，它可能被当作"已排除"从而停止追查；对机构，若后续发现确有一份文件名无害的工资表，这份报告就成了需要承担责任的文件。

## 七、命令速查

```bash
# 设备识别（Linux，确认要固定哪一块）
lsblk -o NAME,SIZE,MODEL,SERIAL,TYPE,MOUNTPOINTS
lsblk -o NAME,MODEL,SERIAL,SIZE,ROTA,TYPE

# 确认写保护已生效（RO 应为 1，removable=0）
lsblk -o NAME,RO,RM,SIZE,MODEL

# 原始介质哈希（应在挂载前执行）
sudo sha256sum /dev/sdX

# 物理镜像 + 双哈希（详见板块 2）
sudo dcfldd if=/dev/sdX of=/case/DigiForensics.dd \
     hash=md5,sha256 hashlog=/case/DigiForensics.hashlog \
     bs=4M conv=noerror,sync status=on

# 校验镜像
sha256sum /case/DigiForensics.dd
md5sum /case/DigiForensics.dd

# 分区结构速览
fdisk -l /case/DigiForensics.dd
```

```powershell
# Windows：确认磁盘为只读状态
Get-Disk | Format-Table Number,FriendlyName,SerialNumber,OperationalStatus,IsReadOnly

# Windows：只读打开原始卷（ntfs 为例，不加 -Force 会触发写保护检查）
mountvol D: /R
```
