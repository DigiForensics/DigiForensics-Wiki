# 虚拟机仿真

> 原文链接：[DigiForensics Wiki · 在线阅读](https://www.digiforensics.cn/wiki/imaging-mount-simulate-virtual-machine-emulation)

<a id="section-1"></a>

## 一、概述

未经保护直接启动可疑硬盘，可能改写原始检材。

贵的不是挂载。挂载只是让你看见文件；启动系统是把执行权交给里面的东西，后果不可逆。

| 危害类型 | 具体表现 | 是否可逆 |
|---|---|---|
| **恶意程序激活** | 勒索软件加密全盘、木马启动、挖矿占满资源 | **不可逆** |
| **持久化被清除** | 恶意启动项被删、时间戳被改、反取证被卸载 | 不可逆（原始镜像仍在） |
| **网络扩散** | 木马向内网横向移动、勒索样本外泄 | 部分可逆，扩散已发生 |
| **时间线污染** | 系统时间跳变、`$UsnJrnl` 被新事件覆盖、事件日志轮转 | **不可逆**（最隐蔽的伤害） |
| **触发反取证** | 虚拟机被检测、样本自毁、加密密钥被抹除 | 通常不可逆 |

最后一行和倒数第二行值得停下来看一眼。

**时间线污染那一行是唯一一个"你什么都没做错"的项**。一次正常启动就会写几百条事件日志、推进 `$UsnJrnl`、更新预读与注册表——而这些恰恰是判断"这台机器什么时候被做了什么"的核心依据。

**虚拟机仿真是什么**：一个受控的观察环境，用来看程序运行态、内存行为和网络连接意图。

它能不能用，取决于三条要求：基础镜像永不改变、客户机写入全部进差分盘、网络完全隔离。技术要点就一句：让这台虚拟机无论怎么折腾，都动不到证据、碰不到你的网络。

它在流程里的位置，是**分析**环节的一条高风险分支，和[只读挂载与安全接入](imaging-mount-simulate-read-only-mounting.md)平级但性质完全不同。

**上游**是格式准备——虚拟化平台要 VMDK 或 VHDX，不吃 RAW 和 E01，转换见[证据格式与转换](../imaging-acquire/imaging-acquire-evidence-image-formats.md)。**它自己**的前置是一个判断：这个问题真的需要仿真吗？**能静态回答的，就不要启动系统。**

**下游**是运行态分析。内存里看到的凭据与注入代码进[内存取证总览](../../memory/memory-acquire/memory-acquire-memory-forensics-overview.md)，进程与注入的判读进[进程与注入检测](../../memory/memory-analyze/memory-analyze-process-and-injection-detection.md)，网络连接意图进[网络连接与流量痕迹](../../memory/memory-artifact/memory-artifact-memory-network-artifacts.md)。Windows 环境另有专门的坑——域控身份会在内网"复活"，见[Windows Server 环境仿真](imaging-mount-simulate-windows-server.md)。

三条要求展开成能执行的形式：

| 要求 | 实现手段 | 违反后的后果 |
|---|---|---|
| **基础镜像永不改变** | 基础盘挂为只读；**永远不勾 Consolidate** | 证据镜像被改写，且**无法察觉**（哈希会变，但你不知道为什么变） |
| **写入全进差分盘** | 快照 + 差分盘承接；实验做完丢弃差分盘重建 | 同上 |
| **网络完全隔离** | 网卡移除或 Not Connected；传文件用只读 ISO | 木马横向移动、样本外泄、**客户证据被送到第三方** |

事故多数出在第三条。快照人人记得拔，网线常常忘。

**"从虚拟机往外送东西"这个方向同样是攻击方向**。有的样本会自动上传到 C2 或样本库，那等于把客户证据送到第三方手里。

网络隔离的三种模式，安全性差了一个量级：

| 模式 | 访问宿主 | 访问互联网 | 评价 |
|---|---|---|---|
| **网卡断开**（移除设备 / Not Connected） | 否 | 否 | **默认选择，也是本篇的立场** |
| **Host-only** | 能（共享宿主网段） | 否 | **仅用于把工具喂进去**，不是安全选项 |
| **NAT / 桥接** | 能 | **能** | ❌ **绝对禁止** |

Host-only 也不是安全的。恶意程序会扫描宿主网段，尝试 SMB 漏洞横向移动到宿主机。**最安全的形态是"网卡根本不存在"**——要传文件就用 ISO 只读挂载，别给虚拟机开网卡。

为什么用差分盘而不是克隆，这是仿真的技术核心。克隆一份 500 GB 镜像意味着额外 500 GB 空间加几十分钟复制，每次重新分析都要重来。差分盘把范式换成"基础镜像只读不动，差分盘承接全部写入，做完删掉重建"：额外空间通常几百 MB，恢复初始状态是删一个文件，基础盘物理上不可能被改。

代价是它必须始终保持 parent/child 引用关系，单独拿出来是废数据。

**本篇能回答**：程序运行态的行为（解密后的代码、内存中的凭据、注入行为）、注册表之外的活的状态（服务、驱动、计划任务）、启动时自动执行了什么、程序**试图**建立的网络连接。

**本篇不能回答**，三条必须提前知道：

不能证明"没做过"——物理内存、真实驱动行为、加密通信的真实上下文都重现不了。

不能替代静态分析——没运行到的分支，你看不到。

**不产生新证据**——仿真不改变"镜像里有什么"，只产生观察记录。所以产出是"观察记录"而不是"证据"，**报告里必须与静态分析结论分开陈述**。这一条最容易破：把仿真的观察写成静态发现，等于把一次实验结果冒充成检材内容。

还有一条要单独说：**环境本身会影响观察结果**。恶意程序发现自己在虚拟机里会改行为——不执行、不解密、不外联。你在仿真里看到"程序很安静"，可能恰恰是它发现被观察了。

所以"仿真中未观察到 X"这句话有多强的证据，取决于"你确信它没检测到虚拟机"这个前提。这个前提通常不成立。

**读者前提**：虚拟化平台的基本操作（VMware / VirtualBox / KVM 任一）、差分盘与 backing file 链的机制，最关键的一条是清楚"这台机器已经不是原始检材了"这个状态转换。产物是差分盘和观察记录，归档与留痕要求见第四章 4.4 组。**目标主机是否真的关机还没确认，本篇就不该开始。**

## 二、核心原理

<a id="section-3"></a>

### 2.1 仿真的三层隔离模型

隔离靠三层手段叠加，缺一层就可能被绕过：

| 层 | 隔离对象 | 技术手段 | 被绕过后的后果 |
|---|---|---|---|
| **L1 磁盘隔离** | 原始镜像数据 | 基础镜像只读 + 差分盘承接写入 | **证据永久改变** |
| **L2 网络隔离** | 你的网络、互联网 | 网卡断开 / Not connected | 木马扩散、样本外泄 |
| **L3 环境隔离** | 宿主机 | 快照回滚、随时弃用、专用主机 | 宿主机被感染、横向渗透 |

事故多数发生在 L2。**快照人人记得拍，网线常常忘拔。**

<a id="section-4"></a>

### 2.2 为什么必须用差分盘而不是克隆

直觉做法是"复制一份镜像再启动"。500 GB 盘上意味着额外 500 GB 空间和几十分钟复制，**而且每次重新分析都要重来一遍**。差分盘换掉了这个范式：

```
基础镜像 DigiForensics-base.vmdk   ← 永远只读，永不修改
        ▲ 读取（未命中时穿透）
        │
差分盘   DigiForensics-delta.vmdk   ← 客户机所有写入落在这里
```

| 特性 | 完整克隆 | 差分盘 |
|---|---|---|
| 额外空间 / 准备时间 | = 镜像全量 / 分钟到小时 | 通常几百 MB / 秒级 |
| 恢复初始状态 | 再复制一次 | **删掉差分盘，重建** |
| 多次并行分析 | 需多份克隆 | **同一基础盘挂多个差分盘** |
| 基础盘是否安全 | 克隆期间也是副本 | **只读，物理上不可能被改** |

差分盘的读取规则：**先查差分盘，命中就返回；未命中就穿透到基础盘**。所以它必须始终保持 parent/child 引用关系，单独拿出来是废数据。

<a id="section-5"></a>

### 2.3 VMware 快照的文件级真相

快照不是备份。它是一组文件加一个指针：

| 文件 | 作用 | 误操作后果 |
|---|---|---|
| `*.vmsd` | 快照**元数据**：名字、描述、创建时间、`uid`，以及"当前状态指向哪个快照" | 删掉它，快照树信息丢失 |
| `*-Snapshot1.vmsn` | 快照点的**运行状态**：内存镜像、CPU/设备寄存器状态 | 删掉它，快照只能冷启动恢复 |
| `*-000001.vmdk` | 差分盘文件，后续写入全落这里 | **删掉 = 快照之后的所有操作记录全丢** |
| `*.vmx` | 虚拟机配置文件 | 改它只改硬件，不影响差分盘内容 |

**关键认知**：拍快照时 VMware 做三件事——**冻结**基础盘、创建新差分盘承接写入、把内存状态存进 `.vmsn`。恢复时反过来：丢弃当前差分盘，以快照点为基线重建。

快照树是栈结构（LIFO）。有子快照时，父快照不能直接删。

<a id="section-6"></a>

### 2.4 快照的三种"退场方式"差异极大

| 操作 | 基础盘 | 当前状态 | 能否回到快照点 |
|---|---|---|---|
| **Revert / Rollback** | 不变 | **丢弃** | 能，立刻 |
| **Delete + Consolidate** | **被合并写入** | 合并进基础盘 | **不能，数据已回写** |
| **Delete（保留分支）** | 不变 | 保留为新分支 | 能（在该分支上） |

> 取证场景要求：永远不要对证据机做 Consolidate。 合并会把差分盘内容写回基础盘，**证据镜像就此被改写**。看到 `Delete snapshot and consolidate changes` 选项时，取证机上一律不勾。

<a id="section-7"></a>

### 2.5 快照点应该选在哪里

| 快照时机 | 用途 | 评价 |
|---|---|---|
| **开机前（vmx 就绪、首次启动前）** | 观察"系统启动时自动发生什么" | ⭐⭐⭐⭐⭐ 必做，见第 05 篇 |
| **首次登录后、运行可疑程序前** | 观察程序的直接行为 | ⭐⭐⭐⭐⭐ 必做 |
| **执行完一轮操作后** | 归档当前实验状态 | ⭐⭐ 只在需保留中间结论时做 |

**绝对不能作为快照点的时机**：刚导入镜像**尚未做隔离配置**时（快照的是"裸机状态"，回滚回去依然裸奔）；可疑程序**已经运行**之后（污染已发生）；Consolidate 产生的"干净快照"（基线本身已被污染）。

**标准流程是"两次快照"**：导入镜像 → 完成所有配置（网络、硬件、共享目录）→ **快照 A（baseline）** → 首次启动 → 执行分析 → 需要时**快照 B** → 继续深挖。

这样每次回滚的语义都明确：回 A 是"重新开始但配置还在"，回 B 是"回到上一个发现点"。

快照树是栈结构（LIFO）。有子快照时，父快照不能直接删。

<a id="section-8"></a>

### 2.6 网络隔离的三种模式

| 模式 | 访问宿主 | 访问互联网 | 评价 |
|---|---|---|---|
| **网卡断开**（移除网卡 / Not Connected） | 否 | 否 | **默认选择** |
| **Host-only** | 能（共享宿主网段） | 否 | 仅用于把工具喂进去 |
| **NAT / 桥接（Bridged）** | 能 | **能** | ❌ **绝对禁止** |

> **即使是 Host-only 也要警惕**：恶意程序会扫描宿主网段，尝试 SMB 漏洞横向移动到宿主机。Host-only 的真实价值是"让分析人员能把工具喂进去"，不是安全。**最安全的是网卡完全不存在**——需要传文件时用 ISO 只读挂载。

**"从虚拟机往外送东西"的方向同样是攻击方向**。有的样本会自动上传到 C2 或样本库，等于把客户证据送到第三方手里，可能构成数据泄露。

所以本篇的默认立场是：**仿真机永远不联网**。

<a id="section-9"></a>

### 2.7 仿真能带来什么、不能带来什么

**能**：程序运行态（解密后的代码、内存中的凭据、注入行为）、注册表之外的服务/驱动/计划任务等活的状态、网络连接意图。

**不能**，三条：

❌ 不能证明"没做过"——物理内存、真实驱动行为、加密通信都重现不了。

❌ 不能替代静态分析——没运行到的分支看不到。

❌ **不改变"镜像里有什么"**。仿真不产生新证据，只产生观察记录。产出是"观察记录"而不是"证据"，报告中必须与静态分析结论分开陈述。

## 三、操作步骤

<a id="section-11"></a>

### 3.1 第 1 步：格式转换与导入前的无损验证

```bash
# 1) 转换前基线哈希
sha256sum /evidence/master/DigiForensics.dd | tee /lab/vmdx-baseline.sha256
# 2) RAW → VMDK（streamOptimized 单文件，兼容性与空间效率都最好）
qemu-img convert -f raw -O vmdk -o subformat=streamOptimized \
  /evidence/master/DigiForensics.dd /lab/vm/DigiForensics/DigiForensics-base.vmdk
# 3) 往返验证：VMDK 导回 RAW 再比哈希，必须逐字符一致
qemu-img convert -f vmdk -O raw /lab/vm/DigiForensics/DigiForensics-base.vmdk /tmp/rt.dd
sha256sum /tmp/rt.dd; rm -f /tmp/rt.dd
```

**为什么导入前要做这三步**：转换是唯一可能静默损坏数据的环节。VMware 也能直接读 RAW，但 `streamOptimized` 更省空间，而且能通过往返验证确认无损。

**基础镜像的哈希必须在导入前后各确认一次。**

<a id="section-12"></a>

### 3.2 第 2 步：创建虚拟机并做硬隔离

1. `File` → `New Virtual Machine` → `I will install the operating system later` → 选**与检材相同的版本**（版本不同会导致磁盘控制器与驱动行为不同），再选 `I will not install an operating system disk image file`
2. 内存给 1/2 物理内存（**不要超过宿主可用量**，否则宿主交换反而更慢）
3. `Remove` 掉默认的 CD/DVD、打印机、串口等**所有非必要设备**
4. `Customize Hardware` → `Network Adapter` → 选 `Not connected`（不选 NAT，不选 Bridged）
5. `Options` → `Guest Isolation` → `Copy paste from host` 与 `Drag and drop` **关闭**

> **为什么要删光驱和打印机**：恶意软件检测虚拟机时经常检查这些设备是否存在，检测到就可能改变行为（休眠、退出、甚至自毁）。删设备是一种**反检测加固**。

<a id="section-13"></a>

### 3.3 第 3 步：挂载差分盘（VMware）

VMware 默认就是快照式差分，也可以显式创建：

```bash
cd /lab/vm/DigiForensics
# 显式创建基于基础盘的差分盘（parent 关系写进 .vmdk 描述符）
vmware-vdiskmanager -r DigiForensics-base.vmdk -t 0 DigiForensics-delta.vmdk
# 查看差分盘当前指向的 parent（只读查询，不修改任何数据）
grep -i parentFileNameHint DigiForensics-delta.vmdk
```

> `vmware-vdiskmanager -R` 不要碰：该选项是**修复（repair）**，会直接改写磁盘，不用于查看父子链。查父子关系只用 `grep parentFileNameHint` 或 `qemu-img info --backing-chain`。

GUI 里的标准取证配置是**把 base VMDK 设为只读**（磁盘设置里勾 `Read Only`），拍快照时 VMware 自动把写入重定向到新差分盘。这个"基盘只读 + 快照自动分叉"就是隔离的落点。

<a id="section-14"></a>

### 3.4 第 4 步：VirtualBox 差分盘与快照

VirtualBox 有两套差分机制，用途完全不同：
```bash
# ① immutable 模式：每次开机自动丢弃写入（一次性分析）
VBoxManage modifyhd /lab/DigiForensics-base.vmdk --type immutable --autoreset on
# ② 标准快照：parent/child 差分链，可多次回滚（--pause 拍完保持暂停）
VBoxManage snapshot DigiForensics-VM take "baseline" --pause
VBoxManage snapshot DigiForensics-VM list
VBoxManage snapshot DigiForensics-VM restore "baseline"    # 回滚，丢弃当前状态
VBoxManage snapshot DigiForensics-VM delete "baseline"     # 非合并删除
# ③ 网络与外设一并收紧
VBoxManage modifyvm DigiForensics-VM --nic1 none --share-folder none --uart1 0
```

`restore` 等价 VMware 的 Revert。快照树同为 LIFO，删父快照前必须先删子快照。

<a id="section-15"></a>

### 3.5 第 5 步：PVE / KVM 快照法（团队协作场景）

实验室常用 Proxmox VE 集中管理，成员通过浏览器操作。这种情况下隔离更依赖平台策略：

```bash
# ① 建 VM：--net0 none 直接无网卡；-import-from 会把 VMDK 复制成私有 qcow2
qm create 101 --name DigiForensics-VM --memory 4096 --cores 2 \
  --net0 none --ostype win10 --scsihw virtio-scsi-pci \
  --scsi0 local-lvm:512,import-from=/lab/vm/DigiForensics/DigiForensics-base.vmdk

# ② 拍快照（--vmstate 1 连内存一起保存）→ ③ 回滚（保持关机态）→ ④ 删除 → ⑤ 确认
qm snapshot 101 pre-analysis --vmstate 1 --description "baseline before any execution"
qm rollback 101 pre-analysis --start 0
qm delsnapshot 101 pre-analysis
qemu-img info --backing-chain /var/lib/vz/images/101/vm-101-disk-0.qcow2
```

**两个注意点**。`--vmstate 1` 会把内存写入宿主，宿主内存要留够；不带 vmstate 的快照，恢复后是关机态。

`qm rollback` 与 `qm delsnapshot` 都是真操作。但由于导入用了 `-import-from`（PVE 把 VMDK 复制为私有 qcow2），**原始 VMDK 从此只读**。这一点必须在案例记录里写明。

<a id="section-16"></a>

### 3.6 第 6 步：录屏留痕、收工与归档

录屏是仿真中"观察结论"唯一的可复核载体。界面状态、弹窗内容、命令行回显，都无法从镜像里重建。所以报告里每句"仿真中程序弹出了 XX 提示"，都要能对应到一个录屏时间点。

```bash
# 屏幕录制（宿主机侧，VLC）+ 关键操作时间点留痕
vlc --intf dummy --sout '#transcode{vcodec=h264,vb=2000,scale=1280}:std{access=file,mux=mp4,dst=/lab/session.mp4}' screen:// --screen-fps 15
date -u +"%Y-%m-%dT%H:%M:%SZ" | tee -a /lab/session-log.txt
# 停机用 Power Off（不是 Suspend——挂起会让恶意进程在内存中存活）
sha256sum /lab/vm/DigiForensics/DigiForensics-base.vmdk    # 与 3.1 步比对
grep -E 'snapshot|FileName' /lab/vm/DigiForensics/*.vmx > /lab/snapshot-state.txt
tar -cf /lab/case-CASE-2026-0142-vm.tar -C /lab/vm DigiForensics/DigiForensics-base.vmdk \
  -C /lab session.mp4 session-log.txt snapshot-state.txt
```

差分盘记录的是"实验中产生的变化"，不是原始证据。**基础镜像必须归档，它是原始证据的仿真副本。**

## 四、常见陷阱

这一章的陷阱和前几章不一样。前面的陷阱通常在几分钟内造成可检测的破坏，仿真的陷阱往往当场看不出任何异常。

虚拟机正常启动，程序正常运行，界面显示一切正常。而系统时间已经跳变，`$UsnJrnl` 已被新事件覆盖，样本已悄悄外联到 C2。概述那张表把"时间线污染"标成"不可逆（最隐蔽的伤害）"，这一章讲的就是这些"看起来没事"的时刻。

三条要求在概述里给过：基础镜像永不改变、客户机写入全部进差分盘、网络完全隔离。2.1 把它拆成 L1/L2/L3 三层，判断很直白——**事故多数发生在 L2**。


★ 标记表示该操作会不可逆地改写原始检材或使实验状态无法回退，执行前必须停下来确认。

<a id="section-18"></a>

### 4.1 L2 网络隔离：最常出事的一层

<a id="section-19"></a>

#### 陷阱 1：只做了快照就开机，忘了断网

**现象**：导入镜像、配好硬件、拍好快照，**然后直接开机观察**。快照确实做了，硬盘确实没被改，但仿真机的网卡还挂在 NAT 或默认配置上。

**原因**：2.1 那句"事故多数发生在 L2"就是这一条的全部依据。

磁盘隔离有快照做视觉保障——文件都还在，哈希能验证。网络隔离**没有任何可见的证据**：一个恶意程序外联成功，在屏幕上不会表现为任何异常，**它只是在后台把数据送走了**。

L1/L3 有文件和快照作物证。**L2 的"没做"是不留痕迹的。**

**影响**：概述那张表里**两行直接命中**——"网络扩散：木马向内网横向移动、勒索样本外泄"，以及"样本外泄"。前者可能波及实验室所在网段的其它设备，后者则把客户证据送到了第三方。2.6 把这个方向单独点明：**"从虚拟机往外送东西"的方向同样是攻击方向**。

**核查**：3.2 第 4 步的 `Not connected` 是导入后必须完成的动作，不是可选项：

```text
VMware: Customize Hardware → Network Adapter → Not connected
VirtualBox: VBoxManage modifyvm DigiForensics-VM --nic1 none
PVE: qm create ... --net0 none
```

**检查动作要可验证**，不能凭印象：

```text
VMware 开机后：控制台 → 设备 → 网络适配器 → 状态应为"已断开"；
               或客户机内执行 ping 8.8.8.8 应当失败
客户机内：Get-NetTCPConnection -State Established
```

**传文件用 ISO 只读挂载，不要为此放开网络**（2.6：**最安全的是网卡完全不存在**）：

```bash
# 宿主机侧准备只读 ISO，挂到虚拟机光驱
qemu-img convert -f raw -O raw /lab/tools/toolset.img /lab/tools/toolset.iso
# VMware: VM → Removable Devices → CD/DVD → Connect
# 报告中记录所用 ISO 的 SHA-256
sha256sum /lab/tools/toolset.iso
```

<a id="section-20"></a>

#### 陷阱 2：选 Host-only 就认为"绝对安全"

**现象**：需要往仿真机里喂分析工具（RegRipper、7-ZFT、脚本），把网卡设成 Host-only，觉得"反正连不上互联网"，于是放心启动。

**原因**：2.6 的表格给了它 ★★ 而不是 ★★★★★，引用块里写得更直接：即使 Host-only 也要警惕——恶意程序会扫描宿主网段，尝试 SMB 漏洞横向移动到宿主机。

Host-only 的真实价值是"让分析人员能把工具喂进去"，不是安全。2.6 的引用块还把它和"最安全的做法"并列了：**最安全的是网卡完全不存在**。

**影响**：**被横向渗透的不是仿真机，是实验室宿主机**——而宿主机上放着全部案件证据。

更麻烦的是这条路径不留可见痕迹。宿主机被入侵后，仿真机里的实验记录（录屏、日志、差分盘）是否可信，就成了新的问题。

**核查**：**按阶段切换网卡状态，分析样本时网卡不存在**：

```bash
# 阶段 1 · 投喂工具：Host-only 短暂使用，只往里送工具包
# 阶段 2 · 观察样本：网卡完全移除或 Not connected
# 阶段 3 · 需要联网取证的场景另见第 05 篇的独立受控方案，不在本篇默认流程内
```

**送工具的方式优先级**（2.6 的立场）：

| 方式 | 适用 | 说明 |
|---|---|---|
| **只读 ISO** | 首选 | 网卡完全不存在即可完成 |
| **VirtualBox 共享文件夹** | 需频繁交换时 | 必须 `--share-folder none` 之外显式收紧，且仅在投喂阶段 |
| **Host-only** | 仅投喂阶段 | **不得在样本运行阶段保持** |

**共享文件夹本身也是一条独立风险**，不能因为"只是投喂工具"就长期开着——3.4 把它和网卡一起收紧到同一条命令里：

```bash
VBoxManage modifyvm DigiForensics-VM --nic1 none --share-folder none --uart1 0
```

<a id="section-21"></a>

#### 陷阱 3：为了"验证程序行为"临时恢复联网

**现象**：样本运行后没有外联迹象，怀疑是"因为没网所以没连"，于是打开 NAT 再观察一次，想确认它到底连不连 C2。

**原因**：2.7 已经把仿真的能力边界写死了，"不能"里第一条就是**不能证明"没做过"**。

这一条同样适用于网络。没观察到外联，不是"因为它不会外联"，而是因为环境里没有网络。恢复联网验证不了这个假设，它只是把一个受控实验换成了一个真实的攻击行为。

**影响**：用一个不可逆的实验去回答一个不需要实验就能回答的问题。

命令速查里的客户机注释把这个陷阱写在了代码旁边：无网环境下本命令必然为空，报告中必须写明"未观察网络行为"。空结果本身就是一个需要解释的观察结果，不是需要补做的实验。

**核查**：**网络意图走静态分析，不走动态联网**：

```bash
# 在无网仿真机上提取待分析样本（只读导出，不安装工具）
# 静态侧：域名/IP 提取、C2 规则、协议特征
strings -n 8 /lab/extracted/svhost1.exe | grep -iE '\.(com|net|org|io)|[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}\.[0-9]{1,3}'

# 报告写法：在无网条件下未观察网络行为，网络意图以静态样本分析结论为准
```

> "**网络行为**：本次仿真全程网卡 `Not connected`，`Get-NetTCPConnection -State Established` 返回空。该结果仅表明在无网环境下未观察到网络连接，不表明程序不具备外联能力。 样本 `svhost1.exe` 的外联意图以静态样本分析识别出的 C2 域名为依据，两类结论在本报告中分节陈述。"

**确实需要动态观察网络时**，走独立受控方案并单独授权，**不在本篇的无网默认流程内混做**。

<a id="section-22"></a>

### 4.2 L1 磁盘隔离与快照生命周期

<a id="section-23"></a>

#### 陷阱 4：★ 不用差分盘，直接把基础镜像挂为可写并启动

**现象**：把 `qemu-img convert` 出来的 `DigiForensics-base.vmdk` 直接作为虚拟机的可写磁盘挂上，开机观察；或者干脆"先复制一份 dd 出来启动看看"。

**原因**：2.2 的对照表把"基础盘是否安全"这一行说死了：克隆是"克隆期间也是副本"，差分盘是"只读，物理上不可能被改"。

概述里"持久化被清除：恶意启动项被删、时间戳被改、反取证被卸载"这一栏标了"不可逆（原始镜像仍在）"。**括号里那个前提条件，在没有原始镜像时就不成立。**

克隆在"临时看一眼"的语境下非常自然，但它把隔离的全部押在"我留着那份 dd"这个假设上。

**影响**：**证据被不可逆地改写。**

概述里还有一行特别标注："时间线污染：系统时间跳变、`$UsnJrnl` 被新事件覆盖、事件日志轮转"——不可逆（最隐蔽的伤害）。这一行的隐蔽之处在于**它不表现为任何异常**，只表现为分析结果里冒出一批来自"本次开机"的时间戳。

**核查**：**基础镜像只读，写入全部进差分盘**（2.1 的 L1 与 2.2 的结构）：

```bash
# 基础镜像建好后立即锁只读（宿主侧双保险）
chmod 444 /lab/vm/DigiForensics/DigiForensics-base.vmdk
chattr +i /lab/vm/DigiForensics/DigiForensics-base.vmdk

# VMware：磁盘设置里勾 Read Only，拍快照时 VMware 自动把写入重定向到新差分盘
# 或显式建差分盘
cd /lab/vm/DigiForensics
vmware-vdiskmanager -r DigiForensics-base.vmdk -t 0 DigiForensics-delta.vmdk
```

**"基础镜像只读 + 快照自动分叉"就是隔离的落点**（3.3）。**每次重新分析不需要重来一遍**——2.2 对照表里"恢复初始状态"一栏，差分盘的做法是"删掉差分盘，重建"，几秒钟的事。

`chattr +i` 是宿主侧的最后一道保险，但它有个副作用值得知道：设成 immutable 之后，**任何需要写这个文件的操作都会失败**，而虚拟化软件写 VMDK 正是靠常规文件写入。如果平台在建差分盘时报权限或 I/O 错误，先 `lsattr` 看一眼是不是自己加的锁——去掉锁（`chattr -i`）通常就能解决，不要把这个错误当成镜像损坏去重新采集。

`chmod 444` 在多数环境下更省事：不阻止读取，也不阻止有足够权限的进程写，但能挡住绝大多数误操作。两道的取舍在于——`chattr +i` 能挡住所有写入（包括 root），代价是可能挡掉平台自己；`chmod 444` 只挡普通用户，但不会跟平台冲突。

**把差分盘内容当作实验记录保留，而不是证据**（3.6 结尾）：差分盘记录的是"实验中产生的变化"，不是原始证据。基础镜像必须归档，它是原始证据的仿真副本。

<a id="section-24"></a>

#### 陷阱 5：★ 清理磁盘空间时用 Delete + Consolidate

**现象**：仿真做完，磁盘空间告急，在快照管理器里删除最老的那个快照，弹出的选项里有 `Delete snapshot and consolidate changes`，顺手勾了。

**原因**：2.4 的对照表把三种"退场方式"并列着，差别一眼可见。`Revert / Rollback` 是"基础盘不变、当前状态丢弃"；`Delete + Consolidate` 是"基础盘被合并写入"，"能否回到快照点"那一栏明确写着"不能，数据已回写"。

弹出框里的措辞把这件事说得很轻——"合并"听起来像一种整理动作。2.4 的引用块说明了操作要求：**永远不要对证据机做 Consolidate**。

**影响**：**差分盘内容被写回基础盘，证据镜像就此被改写**（2.4 原话）。**这一步不可回退**——没有备份能恢复，因为备份的对象本身就是被改的那个文件。

**核查**：**快照删除一律用 Revert 或非合并删除**：

```bash
# VMware：Revert（丢弃当前状态，不动基础盘）
# VirtualBox：delete 不带 --delete-snapshots-machine / consolidate
VBoxManage snapshot DigiForensics-VM delete "baseline"    # 非合并删除

# PVE：delsnapshot 同样是丢弃，不合并回基础盘
qm delsnapshot 101 pre-analysis
qemu-img info --backing-chain /var/lib/vz/images/101/vm-101-disk-0.qcow2   # 确认链状态
```

**看到 Consolidate 选项就停**。判断标准很简单：Consolidate 会写入基础盘，其余两种不会——**凡是会影响基础镜像哈希的操作，一律不做**。

快照树是栈结构（LIFO），有子快照时父快照不能直接删（2.3 与 2.5 都强调过）。**删父之前先处理子**，否则会出现"删不掉的快照"这种既占空间、又让人误以为隔离失效的状态。

<a id="section-25"></a>

#### 陷阱 6：把快照点在"刚导入、还没配隔离"的时候

**现象**：导入镜像后立刻拍一个快照当"干净基线"，然后才开始配置网卡、删设备、关共享。某次回滚到这个"基线"，发现网络又是通的。

**原因**：2.5 的"绝对不能作为快照点的时机"第一条就是它：刚导入镜像尚未做隔离配置时（快照的是"裸机状态"，回滚回去依然裸奔）。

这个快照的手感非常好——它确实能回到"刚导入"的状态，**但刚导入的状态恰恰是没有隔离的状态**。

2.5 给的标准流程顺序是明确的：导入镜像 → 完成所有配置（网络、硬件、共享目录）→ 快照 A（baseline）→ 首次启动。

**影响**：**一个名字听起来最安全的快照，实际是最危险的。**

案例第 2 步特意写明"**配置完成后**才拍快照 `A-configured-offline`"，就是这个顺序。回滚的语义必须是"重新开始但配置还在"（2.5），不是"回到一切都没设置的状态"。

**核查**：**两次快照，顺序不能颠倒**（2.5）：

```text
① 导入镜像 DigiForensics-base.vmdk
② 完成所有配置：网卡 Not connected、删光驱/打印机/串口、Guest Isolation 全关
③ 快照 A（baseline）—— 语义：重新开始但隔离配置仍在
④ 首次启动 → 执行分析
⑤ 需要保留中间结论时快照 B —— 语义：回到上一个发现点
```

**另两个绝对不能作为快照点的时机**（2.5）：

- **可疑程序已经运行之后**——**污染已发生**，快照只是把被污染的状态固定下来。
- **Consolidate 产生的"干净快照"**——**基线本身已被污染**，2.5 称之为"干净快照"，名字与内容正好相反。

判断一个已有快照是否可用，看它的配置状态而不是它的名字：

```text
挂载该快照点启动 → 检查网卡状态、设备列表、共享设置
三项都正确 = 可用的基线
任一项不对 = 这是隔离前的裸机状态，重拍
```

<a id="section-26"></a>

#### 陷阱 7：用"挂起"代替"关机"结束一轮观察

**现象**：观察告一段落，选择 Suspend / 挂起（有的工具叫 Pause）暂停虚拟机，认为"这样内存状态还在，明天可以接着看"。

**原因**：3.6 的注释把理由写死了：停机用 Power Off（不是 Suspend——挂起会让恶意进程在内存中存活）。

挂起时进程在内存中保持运行态。恶意进程在下次恢复时仍可继续执行它挂起前已经排好的动作——销毁自身、清密钥、继续外联。

**影响**：你以为保存了状态，实际上保存了一个随时会继续动作的进程。

挂起文件还会让下一轮分析的起点变得含糊："这个状态是哪个时刻的"。它既不是原始状态，也不是某个已归档的快照点。

**核查**：只用 `Power Off`；需要保留中间状态就拍快照：

```text
VMware: VM → Power → Power Off        （不要选 Suspend）
VirtualBox: Machine → ACPI Power Off
PVE: qm shutdown 101  →  qm rollback 101 pre-analysis --start 0
```

**快照才是"保存状态"的正确机制**——**它的语义明确、可复现、可记录**。案例第 4 步的处理顺序就是"Revert 到快照 A，随后 `Power Off`"。

<a id="section-27"></a>

### 4.3 平台与工具操作差异

<a id="section-28"></a>

#### 陷阱 8：把 `vmware-vdiskmanager -R` 当成"检查父子链"的命令

**现象**：想确认差分盘的 parent 指向，执行 `vmware-vdiskmanager -R DigiForensics-delta.vmdk`，或者从网上抄到带 `-R` 的命令直接跑。

**原因**：3.3 的引用块单独把这个选项圈了出来：`vmware-vdiskmanager -R` 是**修复（repair）**，**会直接改写磁盘，不用于查看父子链**。

而这个名字看起来像"递归显示/读取信息"。`-R` 紧跟文件名，输出一堆盘信息，很容易被当成只读查询。

3.3 同时给了正确答案：查父子关系只用 `grep parentFileNameHint` 或 `qemu-img info --backing-chain`。

**影响**：为了看一眼 parent 指向，把差分盘（以及可能的基础盘）改写了。

这一条要在做隔离配置时特别小心——它不属于概述那张"运行后才发现"的表，它发生在运行之前。

**核查**：**父子关系只用只读手段查**：

```bash
cd /lab/vm/DigiForensics
# 差分盘描述符里写的就是 parent 引用
grep -i parentFileNameHint DigiForensics-delta.vmdk

# 通用只读查询
qemu-img info --backing-chain /lab/vm/DigiForensics/DigiForensics-base.vmdk
qemu-img info --backing-chain /var/lib/vz/images/101/vm-101-disk-0.qcow2
```

**取证机上的禁用清单**（命令速查里已经写明）：删除快照一律不做 Consolidate；`-R` 是修复选项会改数据，禁用。

2.2 那句"差分盘必须始终保持 parent/child 引用关系，单独拿出来是废数据"，是这一组工具操作的共同前提——任何"把这个文件拷出来看看"的动作都要先确认引用关系还在。

<a id="section-29"></a>

#### 陷阱 9：VirtualBox 里同时用 immutable 和标准快照，语义搞混

**现象**：给同一个 VirtualBox 虚拟机既设了 `--type immutable --autoreset on`，又拍了标准快照。回滚时选了 `restore "baseline"`，却发现"immutable 的自动丢弃"没有按预期发生。

**原因**：3.4 把 VirtualBox 的两套差分机制并排列出，并直接标注了"用途完全不同"：

- `immutable` 模式：**每次开机自动丢弃写入**，一次性分析；
- 标准快照：**parent/child 差分链，可多次回滚**。

`restore` 等价 VMware 的 Revert（3.4 明确），**它丢弃的是当前状态**——**它不负责重置 immutable 模式的介质状态**。

两套机制作用在不同层面（介质 vs 快照树）。混用时"回滚"到底影响了哪些内容，不看文档无从确定。

**影响**：**一轮实验的起点和终点没有被清晰定义。**

2.5 强调"每次回滚语义明确"是标准流程的核心价值。**回滚语义不明，录屏里的观察就失去了时间坐标**。

**核查**：**按场景二选一，不叠加**：

```bash
# 场景 A · 一次性分析：immutable，开机即恢复
VBoxManage modifyhd /lab/DigiForensics-base.vmdk --type immutable --autoreset on

# 场景 B · 需要多次回滚：标准快照
VBoxManage snapshot DigiForensics-VM take "baseline" --pause
VBoxManage snapshot DigiForensics-VM list
VBoxManage snapshot DigiForensics-VM restore "baseline"    # 回滚，丢弃当前状态
VBoxManage snapshot DigiForensics-VM delete "baseline"     # 非合并删除
```

**快照树同为 LIFO，删父快照前必须先删子快照**（3.4）。**选 immutable 时不再依赖快照回滚**——它的可回退性来自"每次开机都是新状态"，而不是"可以回到某个中间点"。

<a id="section-30"></a>

#### 陷阱 10：在 PVE 上直接挂共享 VMDK 目录，多台 VM 并发写同一基础盘

**现象**：实验室用 Proxmox VE 集中管理，团队成员建 VM 时把 NFS/共享存储上的 `DigiForensics-base.vmdk` 直接作为磁盘指过去，多人同时分析；或者忘记 `-import-from`。

**原因**：3.5 特别说明了为什么导入要用 `-import-from`：PVE 会把 VMDK 复制成私有 qcow2，原始 VMDK 从此只读——**这一点必须在案例记录中写明**。

共享目录的写法在"文件都能看到"这一点上完全正常，**但它把基础盘放回了多 VM 并发写的环境**。2.1 的 L1 要求是"基础镜像只读"，**共享目录给的是共享，不是只读**。

**影响**：**多 VM 并发写同一基础盘，基础盘被改。**

这一条的严重性在于**它由并发引起**：单个操作者自己的所有步骤都正确，**破坏发生在两个操作者之间**，事后从各自的命令历史里都看不出问题。

**核查**：导入用 `-import-from`，让它变成私有副本：

```bash
qm create 101 --name DigiForensics-VM --memory 4096 --cores 2 \
  --net0 none --ostype win10 --scsihw virtio-scsi-pci \
  --scsi0 local-lvm:512,import-from=/lab/vm/DigiForensics/DigiForensics-base.vmdk

# 导入后确认：原始 VMDK 与 VM 实际使用的 qcow2 是两个文件
qemu-img info --backing-chain /var/lib/vz/images/101/vm-101-disk-0.qcow2
```

**"原始 VMDK 从此只读"这句话要写进案例记录**（3.5 明确要求）——**它是"未修改原始数据"这一结论的证据基础**。

**两个 PVE 注意点**（3.5）：`--vmstate 1` **会把内存写入宿主**，宿主内存要留够；不带 vmstate 的快照恢复后是关机态。`qm rollback` 与 `qm delsnapshot` 都是真操作，但因为导入用了 `-import-from`，**原始 VMDK 不受影响**。

**多人协作时基础盘只有一个**：`DigiForensics-base.vmdk` 由保管人维护只读，每人每次分析各自建 VM、各自 `-import-from`，产出各自的差分盘与录屏。

这也是 2.2 对照表里"多次并行分析：同一基础盘挂多个差分盘"那一行的实际含义。

### 4.4 记录、结论与归档

<a id="section-32"></a>

#### 陷阱 11：仿真观察直接写成"事实"，与静态结论混在同一节

**现象**：报告里写"仿真中程序加密了全盘文件"，与其他发现并列陈述。读者无法分辨哪句是镜像里读到的、哪句是仿真时看到的。

**原因**：2.7 的核心论断是"仿真不产生新证据，只产生观察记录"，加粗那句是：仿真的产出是"观察记录"而不是"证据"，报告中必须与静态分析结论分开陈述。

概述的表已经说明仿真会改变环境（"时间线污染"）。**观察本身是在被污染的环境里得到的。**

把两者混写，**等于让观察记录继承了证据的地位**。

**影响**：**报告失据**。这不只是文体问题——**委托方往往直接摘取报告中的肯定句作为认定依据**。

案例结论要点里那句"三条仿真观察已单独成节，与静态分析结论区分陈述"，是刻意安排的。

**核查**：**观察记录单独成节，每条对应录屏时间点**（3.6 与案例第 3 步的表格形式）：

| 时间(UTC) | 观察 | 录屏时间点 | 归类 |
|---|---|---|---|
| 09:14:22 | 桌面出现三个陌生快捷方式，指向 `C:\Users\Public\` | 00:02:11 | 仿真观察 |
| 09:16:05 | 程序自动确认"来自其他计算机"的恢复对话框 | 00:03:54 | 仿真观察 |
| 09:17:40 | 任务管理器出现 `svhost1.exe` | 00:05:29 | 仿真观察 |

**每一行都必须能落到录屏时间点**。3.6 说明了原因：录屏是仿真中"观察结论"唯一的可复核载体——界面状态、弹窗内容、命令行回显都无法从镜像中重建。

**没有录屏的观察等于没有观察。**

**留痕动作跟着做**：

```bash
# 宿主机侧录屏（VLC 抓 screen://）
vlc --intf dummy --sout '#transcode{vcodec=h264,vb=2000,scale=1280}:std{access=file,mux=mp4,dst=/lab/session.mp4}' screen:// --screen-fps 15
# 关键动作打时间点
date -u +"%Y-%m-%dT%H:%M:%SZ" | tee -a /lab/session-log.txt
```

**仿真的局限也要写进报告**，参照 2.7 的"不能"清单：

> "**仿真局限声明**：（1）本次仿真不改变"镜像里有什么"，其产出为观察记录而非新证据；（2）**无网环境下未观察网络行为**，样本外联能力未被排除；（3）未运行的代码分支不体现，仿真不能替代静态分析；（4）仿真不能证明"某行为未发生过"——物理内存、真实驱动行为与加密通信均不可重现。"

<a id="section-33"></a>

#### 陷阱 12：收工时不算基础镜像哈希，差分盘与录屏一起归档

**现象**：Power Off 之后直接打包归档。归档目录里既有基础镜像、又有差分盘、又有 `.vmsd`/`.vmsn`；哈希"印象里"是一致的，但没实际算。

**原因**：3.6 归档清单里那行 `sha256sum /lab/vm/DigiForensics/DigiForensics-base.vmdk    # 与 3.1 步比对` 是必做项，而 3.1 步要求"**基础镜像的哈希必须在导入前后各确认一次**"。

这个校验的价值在于：**它是"未修改任何原始数据"这句话的唯一支撑**。

案例结论要点里"基础 VMDK 哈希在导入后、仿真结束后两次比对完全一致"这句结论，正是从这里来的。**不计算，这句话就写不出来。**

**影响**：**最关键的那条结论失去数据支撑。**

归档里混进差分盘还有一个副作用：**归档件体积暴涨**，且接收方无法分辨哪些是原始证据的副本、哪些是实验产物。

**核查**：**哈希确认 → 只归档该归档的**（3.6 清单与案例第 4 步）：

```bash
# ① Power Off 之后，基础镜像哈希与 3.1 步比对
sha256sum /lab/vm/DigiForensics/DigiForensics-base.vmdk
# 必须与 3.1 步的基线值逐字符一致

# ② 记录当前快照与磁盘状态
grep -E 'snapshot|FileName' /lab/vm/DigiForensics/*.vmx > /lab/snapshot-state.txt

# ③ 归档：基础镜像（原始证据的仿真副本）+ 录屏 + 日志 + 快照元数据
tar -cf /lab/case-CASE-2026-0142-vm.tar -C /lab/vm DigiForensics/DigiForensics-base.vmdk \
  -C /lab session.mp4 session-log.txt snapshot-state.txt

# ④ 差分盘不归档 —— 实验产物，非证据
```

**归档清单与"归档范围"要分开写**（3.6 的理由）：**差分盘记录的是"实验中产生的变化"，不是原始证据**。`.vmsd`/`.vmsn` 是快照元数据与运行状态，**它们解释快照树，但本身不含原始数据**。

该留的是"能复核结论的东西"。

**哈希不一致时的处置照旧**（不隐瞒、从主副本重来、如实记录），理由与只读挂载篇一致：基础镜像一旦被改写，它就不再是原始检材的仿真副本了。

## 五、案例示例

<a id="section-35"></a>

### 5.1 勒索样本的无网仿真：只有运行时才看得见的自我修复

**场景**

查获一台 Windows 10 笔记本，磁盘含高度怀疑的勒索软件样本目录。检材为 `DigiForensics.E01`（478 GB）。需在不联网、不修改证据的前提下观察样本行为。委托方的问题是：这个样本启动后做什么。

选择这一路径的依据是**样本的"自我修复"能力在静态分析里是看不见的**。静态分析能看到代码里有一处写入注册表的操作，但看不出它会在运行时弹窗确认后写入。

委托方的问题是"这个样本启动后做什么"，而这个问题在纯静态分析下永远只能答一部分——代码里有的不等于运行时发生的，代码里没有的也可能发生。仿真的价值就在这个差集里。

**处置过程**

**第 1 步 · 转换与基线哈希**：

```bash
ewfexport -u -f raw -t /lab/src/DigiForensics \
  -l /lab/src/export.log /evidence/DigiForensics.E01
# 后续 qemu-img 转换与往返验证同 3.1 节
```

往返哈希与 `DigiForensics.dd` 一致（`b8f2a1c9…`），转换无损。

**这个哈希要在进虚拟机之前算，而不是之后**。它必须能回答"仿真的输入是什么"——如果放在仿真结束时算，万一中途做过什么又 revert 回去，得到的值同样正确，但中间发生过什么就没人知道了。

同时把仿真的输入清单固定下来，报告里直接引用：

```text
仿真输入：/lab/vm/DigiForensics/DigiForensics-base.vmdk
          SHA-256 = b8f2a1c94d7e3...
          由 /evidence/DigiForensics.E01 经 ewfexport + qemu-img convert 生成
隔离状态：网卡 Not connected / 共享文件夹关闭 / Guest Isolation 全关
快照：A-configured-offline（含内存）、B-process-dumped（不含内存）
```

**第 2 步 · 配置隔离并拍快照**——按 3.2 节删光驱/打印机/串口、网卡 `Not connected`、Guest Isolation 全关。

顺序是关键：**配置完成后**才拍快照 `A-configured-offline`（勾选 Include memory）。此时生成 `.vmsn`、`.vmsd` 与 `-000001.vmdk` 差分盘。

**第 3 步 · 首次启动与行为观察**，启动后全程录屏，三段关键行为记入 `session-log.txt`：

| 时间(UTC) | 观察 | 录屏时间点 |
|---|---|---|
| 09:14:22 | 桌面出现三个陌生快捷方式，指向 `C:\Users\Public\` | 00:02:11 |
| 09:16:05 | 弹出"此文件来自其他计算机"警告，程序在 4 秒后自动确认 | 00:03:54 |
| 09:17:40 | 任务管理器出现 `svhost1.exe`（正常系统无此名） | 00:05:29 |

**09:16:05 值得注意**。程序主动确认了"来自其他计算机"的文件恢复对话框，说明它在**尝试修复被反取证工具破坏的注册表项**。

这个行为只有运行时可见。静态分析只能看到代码，不会知道它会"尝试恢复"。

**这三行里还漏掉了一类行为**：`svhost1.exe` 出现之后，它对 `C:\Users\Public\data\` 发起了 11 次文件访问（从差分盘比对与客户机内观察得出），呈连续状而非离散事件。勒索软件的这类"准备阶段"通常不产生醒目的界面变化，只在差分盘上留下痕迹。

它没写进上面那张表，是因为**那张表的时间列只适合离散事件**。11 次访问写进"时间"列毫无意义，正确做法是单独记次数与目标路径：

```text
连续行为（非离散事件）：
  svhost1.exe -> C:\Users\Public\data\   访问 11 次，累计 4.2 MB 读取
  判定：疑似构建待加密文件列表（准备阶段）
```

**两类行为分两张表记，是仿真记录的基本要求**。混在一张表里的后果不是难看，而是时间列失去意义——因为连续行为的时间戳密度太高，会把真正重要的离散事件淹没。

**这背后是一个通病**：观察记录默认一切都是离散事件。实际上取证与仿真的观察对象里，连续行为占大多数——网络连接、文件访问、注册表读写、系统调用，全是连续或半连续的。只有把它们压缩成"次数 + 目标 + 累计量"这类聚合形式，时间维度才重新变得可用。

**这也解释了为什么工具日志常常帮不上忙**。默认的进程创建/文件访问日志记的是事件流，样本跑 6 分钟能产生上万条，人工根本读不完。**先聚合再看**，是处理这类数据的唯一现实方式——而聚合规则本身也需要写进记录，因为它决定了"看到什么"。

```bash
# 聚合而不是逐条读
grep -c 'FILE_CREATE'  activity.log          # 总次数
grep 'FILE_CREATE' activity.log | awk '{print $2}' | sort | uniq -c | sort -rn | head
# 输出：按目标路径聚合，出现频次最高的 10 个
```

这条命令给出的"哪些路径被反复碰"，比一万条原始日志有用得多。

**录屏的时间戳与虚拟机内部时钟可能不一致**。本案虚拟机每次启动都会重新取时（Guest Isolation 全关意味着客户机可以自己联网取时，而它没有网），所以虚拟机时钟可能停在某个旧时间。`session-log.txt` 里的 09:14:22 是**虚拟机内部时钟**，与录屏文件的 00:02:11 是两个不同的时间轴。

报告里要标明用的是哪一个，否则复核方把录屏时间轴和日志时间轴一对，全部对不上。本案的处理方式是：所有时间引用统一用虚拟机内部时钟，并在表头注明"时间为客户机本地时间"，而录屏时间点只作为定位索引使用。

```text
注意：下表"观察"列为客户机本地时间，"录屏时间点"为视频内偏移，两者不同轴
```

**第 4 步 · 只读采集与二次快照**，在客户机内导出进程树（只读取，不安装任何工具）：

```cmd
powershell -NoProfile -Command "Get-CimInstance Win32_Process |
  Select-Object ProcessId,ParentProcessId,Name,CommandLine |
  Sort-Object ParentProcessId | Format-Table -AutoSize" > C:\Users\Public\proc.txt
```

拿到结论后立刻拍快照 `B-process-dumped`。重复观察启动行为时 Revert 到快照 A，随后 `Power Off`，用 `sha256sum /lab/vm/DigiForensics/DigiForensics-base.vmdk` 确认与第 1 步完全一致。

再归档基础镜像 + `.vmsd` + `.vmsn` + 录屏 + `session-log.txt`。**差分盘未归档**（实验产物，非证据）。

**归档前逐项确认哈希**。快照文件也要算哈希并写进归档清单，因为它们是复现实验的关键——只有基础 VMDK 的哈希，而没有 `.vmsn` 的哈希，那"回滚到快照 A 能复现某行为"这句话就无法被第三方验证。

```text
DigiForensics-base.vmdk   SHA-256 = b8f2a1c9...
DigiForensics-A.vmsn      SHA-256 = 4e7c02aa...
DigiForensics-B.vmsd      SHA-256 = 91b3d5f0...
recording-01.mp4          SHA-256 = 0a1f8e3d...
session-log.txt           SHA-256 = 77c2b915...
```

**录屏文件必须单独哈希，且录屏本身要能自证时间**。视频文件本身不携带可信时间戳，一旦发生争议，"这段录屏是 09:16 拍的"只能靠文件名和日志来主张。所以配套做法是在录制开始时，让画面内可见一个实时显示时钟的窗口（客户机任务栏即可），或者在录制后立刻把 `session-log.txt` 与视频时长对齐并记录起始偏移。

这两条措施都不复杂，但它们把"录屏"从一段无法定位的媒体文件，变成一份能与日志互相印证的材料。没有它们，录屏在质证中基本只能起"示意"作用而非"证明"作用。

**结论**

能证明：基础 VMDK 哈希在导入后、仿真结束后两次比对完全一致，证明**未修改任何原始数据**。三条仿真观察已单独成节，与静态分析结论区分陈述。仿真机**全程无网络**，无外联发生。

"未修改任何原始数据"这句的措辞是有意收窄的：哈希比对的是基础 VMDK 这一个文件，它证明的是**该文件字节未变**，而不是"整个仿真过程中检材以任何形式都没被动过"——快照文件、差分盘、`.vmx` 配置都不在它的覆盖范围内。这条限定在第四章 4.5 已经讲过，此处是它的实际应用。

同理，"全程无网络"也只覆盖**客户机侧**：宿主机的网络配置、宿主上的共享文件夹、以及差分盘里可能混进的宿主文件，都不在这句话的保证范围内。所以案例开头那句"需在不联网、不修改证据的前提下观察"，在报告里必须拆成两个独立的限定分别陈述。

**不能证明**：**`svhost1.exe` 的网络意图未被观察**。

无网环境下它无法建立连接，因此其 C2 行为需结合静态样本分析中的 C2 域名结论。这一点必须在报告中声明，否则容易被读成"该进程没有网络行为"。

还有一条限定同样重要：**本案的观察窗口只有约 6 分钟**。样本若存在延时触发的行为（常见的是"安装后 N 小时或 N 天再激活"），这个窗口里根本不会显现。报告里写"未观察到 X"时，观察时长必须一并写出来——**否则读者会默认那 6 分钟代表了全部可能**。

**误判对照**

最容易得出的错误结论是「仿真全程无网络、无外联记录，所以该样本无网络通信行为」。判据有三条：

①网卡设为 `Not connected` 意味着样本的连接尝试**在协议层就被拒之门外**——它可能照常解析 DNS、照常尝试连接、照常失败退出，这些行为在仿真中全部不可见；
②观察窗口仅 6 分钟且全程无网，**延时触发的 C2 行为在这个窗口内不可能显现**，"未观察到"与"不存在"之间没有任何逻辑关系；
③无网环境下 DNS 解析会立即返回失败，很多恶意样本的 C2 逻辑在解析失败时就提前退出了，连"尝试"这个行为本身都没发生——观测到的"安静"是环境造成的，不是样本造成的。

正确判据是**无网仿真只能观察本地行为**。网络意图必须由静态分析（样本内的域名/IP 字符串、导入表）与有网环境下的动态分析分别补齐。

按错误判据走的代价：报告给出「该勒索样本不外联、不上传数据」的结论，委托方据此判定影响范围有限。而样本实际具备 C2 上传能力——**一个被反向使用的错误结论，比没有结论危险得多**。

### 5.2 Include memory 快照的取舍：内存态可复现与磁盘成本的平衡

**场景**

同一案件中，需要重复观察样本的启动行为。第一次观察它创建快捷方式，第二次想确认它是否每次都创建、是否有时序依赖。

将此情形单列的原因是"要不要勾 Include memory"是一个有实际成本的选择，而多数人只在遇到"回滚后行为不一致"时才发现它的意义。

**处置过程**

1. 第一次快照 `A-configured-offline` 勾选 Include memory，观察行为后 Revert 回去，再次启动。

2. 记录两次启动的行为差异，作为是否需要第二次快照的依据：

| 观察项 | 第一次启动 | Revert 后第二次 | 差异 |
|---|---|---|---|
| 快捷方式创建 | 3 个 | 3 个 | 一致 |
| 注册表修复弹窗 | 出现并确认 | **未出现** | **不一致** |
| `svhost1.exe` 启动 | 09:17:40 | 09:16:12 | 均启动 |

`svhost1.exe` 两行相差 92 秒，看着像"第二次更快"，但**这个差异不能当结论用**——两次启动的起点不同（第二次是 Revert 后的启动，经过了不同的初始化序列），秒级先后在这里没有可比性。

表格里保留这个差异是为了显示"这一项是一致的"，而不是为了比较快慢。观察表最容易出的错，就是把"两次都有"和"两次一样"混为一谈——前者是可复现性，后者是稳定性，它们的含义完全不同。

3. 结论落在快照类型上：勾了 Include memory 的快照保存了回滚前的 RAM 状态，第二次启动时系统会认为内存内容未变，因此**某些"自修复"逻辑判断为无需执行**。

弹窗没出现不是样本行为不确定，而是**观测手段改变了自己的观测对象**。

4. **把 5.2 那个"可补做的对照"真的补做了**。这一步不是可选的，它是把猜测变成结论的唯一办法：

```text
实验组：Revert 到 A（含内存快照）→ 启动 → 弹窗出现
对照组：Revert 到 A 时改选"不恢复内存"→ 启动 → 弹窗是否出现？
```

对照组的意义在于：如果不恢复内存后弹窗同样出现，那差异就不是内存造成的，而是前一次运行已经把注册表项修复完毕了——**这两种解释在原观察下完全无法区分**。本案对照组的弹窗未出现，从而确认了内存态才是差异来源。

5. 处理方式：把 09:16:05 的弹窗片段从录屏中单独剪出作为证据，与第二次启动的录屏分开归档，避免混淆。

**结论**

能证明：注册表修复弹窗的出现依赖内存中某项状态，且该状态被 Include memory 快照保留了下来。两条录屏分别对应两种内存初始状态，均可复现。对照组（Revert 不恢复内存）进一步排除了"前次运行已修复注册表"这一竞争解释。

**不能证明**：不能断言"样本必定在每次运行时都尝试修复"。

对照组排除了"注册表项已被前次运行修复"这一解释，但**没有排除第三种可能**——样本的"自修复"判断可能依赖的是别的运行时状态（如某个计时器或会话句柄），而 Include memory 恰好把它一并带回去了。要区分这一点，需要在不恢复内存的前提下人为重建那个状态，本案没有做。

因此报告里能写的是「该行为的可复现性受初始内存状态影响」，而不是「该行为由内存态决定」。前者是观察，后者是归因。

**这个区别值得多说一句**。"受 X 影响"是对观察到的关联的描述，它可以被后续实验支持或推翻；"由 X 决定"是一个因果断言，它需要排除所有其他变量才成立。

本案只做了两组观察（恢复内存 / 不恢复内存），每组一次——**样本量不足以支撑因果表述**。写报告时如果顺手写成"由内存态决定"，将来对方只要补一组对照就能推翻，而推翻一条已被引用的因果结论，代价比推翻一条观察性描述大得多。

**还有一层本案没有触及的**：Include memory 恢复的是**回滚那一刻的内存**，而不是"一台刚装好的机器的内存"。这两者差别不小——它包含上次运行残留的堆内容、已解密的文件缓存、甚至可能还有样本自身的驻留状态。

所以严格地说，回滚到含内存的快照 A 之后启动的客户机，**并不等于一台"运行过样本但状态干净"的机器**。这个区别在做对照组设计时很关键：想验证"内存态是不是唯一变量"，对照组必须只差这一个变量，而不是连"跑没跑过"都不同。

**这个细节在实务中很容易被忽略**，因为"Revert 到快照 A"这个动作给人的感觉是"回到那个干净的时刻"，而 Include memory 让它变成了"回到那个跑过一遍的时刻"。回滚的语义被扩展了，而扩展的那一部分恰恰是变量本身。

**误判对照**

最容易得出的错误结论是「第二次启动没弹窗，说明该样本的注册表修复行为不可复现、属偶发」。判据有三条：

①Include memory 勾选后，快照除磁盘差分外**还包含一份内存差分**，回滚到该快照时内存内容一并恢复——这正是两次启动初始条件不同的原因，而"条件不同却归因于样本本身"是逻辑跳跃；
②第二次启动时注册表项**可能已被前一次运行修复完毕**，两种解释在原始观察下完全不可区分，除非补做"Revert 不恢复内存"的对照组；
③录屏与 `session-log.txt` 用的是**两条不同时间轴**（视频偏移 vs 客户机本地时间），若不注明时间基准，两次启动的时序对照本身就会算错。

正确做法是**把"行为差异"和"观测条件差异"分开记录**。判据的落点是：行为不可复现有两种可能——样本不确定，或者你两次给的初始条件不同——**先排除第二种，再去谈第一种**。

按错误判据走的代价，是把一个可复现的实验设计问题写成样本行为特征，进而向委托方传递"该行为不稳定、结论不可靠"的错误印象。

**这个案子的方法论价值超出它本身**。Include memory 这个选项几乎所有人都会勾（谁想每次启动都重跑一遍配置），但很少有人知道**它勾上之后，实验的初始条件就不再是你以为的那个了**。这不只是取证问题——任何依赖"从干净状态开始"的可复现实验，都有同一个陷阱。

**还有一个便宜的替代方案**。如果只是想重复观察磁盘侧的行为，Include memory 完全可以不勾——代价只是每次启动多花十几分钟（Windows 会跑开机脚本、更新任务）。本案其实可以先不勾跑一轮：若不勾时两次行为一致，那说明这个选项根本不需要，实验设计还简化了。

**先做最简的实验，再考虑加复杂度**，这条在取证仿真里和在其他工程里是同一条原则。默认勾 Include memory 属于"为了省事而牺牲对照性"的典型——省下的十几分钟，换来的是"这两次到底是不是同一个初始条件"这个永远答不了的问题。

### 5.3 反例：仿真中途给虚拟机加网卡做网络行为观察

**场景**

某次仿真中，分析员为观察样本是否外联，在仿真进行到一半时给虚拟机接上了 NAT 网卡。样本随即连出域名解析请求，观察到了外联行为。事后该批仿真记录被质疑证据效力。

这条列为反例，是因为**它做了一件看起来很有价值的事**——真的看到了外联。

**处置过程**

对照点在于网络配置与快照归属：

```bash
# 错误：仿真中途接网卡，虚拟机的出站流量进入真实网络
# 正确：有网环境的动态分析必须在另一套隔离网络中做（该环境的产物
#       不与本案证据链关联，且需单独说明）
```

关键在于**基础镜像哈希验不出这件事**：网卡的接入改的是虚拟机配置（`.vmx`），不是基础 VMDK 的字节内容，`sha256sum` 依然通过。

**这就是本案最值得警惕的地方**——所有常规检查都通过，而被破坏的是最核心的实验条件。哈希验的是"检材有没有被改"，而这里出问题的是"观察者有没有改环境"。

`qemu-img info` 与 `binwalk` 这类工具能发现 VMDK 被拆成多文件、能读出 delta 盘链，但**它们都不校验 `.vmx` 的一致性**——因为 `.vmx` 在设计上就是可改的配置文件，它本来就不属于"证据"。

**所以"证据的边界"在这里要画两遍**。第一遍是文件级的：VMDK 是证据，`.vmx` 不是。第二遍是目录级的——仿真工作目录里哪些文件属于证据、哪些属于实验产物。本案明确归档了前者，未归档差分盘（后者被 revert 操作改写得最多，最不可能保持原始状态）。

这两遍都画清楚之后，"这份材料能不能用"才有确定答案。只画第一遍的人，会在复核时被问"那配置文件算不算证据"；只画第二遍的人，会漏掉配置文件本身也是过程记录这一点——它的 mtime 恰好能证明接网卡这个动作发生在快照之后，**它是不利证据的反面教材，却也是最有力的证据**。

**一个反直觉的结论**：本案里唯一能证明"配置被改过"的东西，恰恰是那个被改过的文件本身。`.vmx` 的 mtime 晚于快照 A 的创建时间，这条时间关系比任何操作日志都可靠——**因为它不是人写的，是系统记的**。这也是为什么"证据边界"要画两遍：同一类文件，既可能是不在证据链内的配置垃圾，也可能是无法伪造的过程记录，区别在于你有没有把它收进来。

**结论**

阴性发现：该批仿真中**无法证明**样本的外联行为是在原始检材状态下的表现，因为虚拟机配置在观察过程中被修改。基础 VMDK 的哈希一致只能证明磁盘未被改写，**不能覆盖虚拟机配置层的变更**。

未覆盖范围：接入网卡后样本的全部网络侧行为（连接目标、传输内容、持续时长）均不可用于本案结论；有网仿真产生的所有产物未纳入证据链，也不能与静态分析结论混同陈述。

**事后能做的补救极其有限**。正确做法本来是"先拍快照再改配置"——那样至少能证明改动发生在快照之后、且改动本身有记录。本案没有中间快照，所以那条外联观察**只能整条作废，不能降级使用**。它不是"证据强度弱一点"，是"不成立"。

**误判对照**

最容易得出的错误结论是「拿基础镜像哈希一致来为这次观察背书」。判据有三条：

①哈希只覆盖 `DigiForensics-base.vmdk` 这一个文件的内容，而网卡接入改的是虚拟机配置文件 `.vmx`——两者是不同的对象，校验前者对后者零覆盖；
②快照 `A-configured-offline` 拍摄于无网状态，而接网卡的动作发生在其后，配置变更时间晚于快照时间这一条本身就足以否定"原始状态下的观察"；
③样本一旦成功连出，其行为已经发生在真实网络上，**这段流量既不受仿真环境控制，也无法撤回**——这不是实验室内部的失误，是可能已经产生的实际外泄。

正确判据是**仿真环境的任何变更都必须在变更前拍快照并记录**。而"为了看某个行为临时改配置"这件事本身，就在改变被观测的初始条件。

按错误判据走的代价：这条外联观察是**在被人为改造过的环境里取得的**。一旦对方注意到配置变更的时间点晚于快照时间，整个仿真的证据链都要重做——而样本本身在真实网络里做什么，恰恰是最需要可信的那一部分结论。

**正确的替代路径**是：需要看网络行为时，另建一套隔离网络环境（沙箱 DNS 指向自建服务器、出站流量全部记录并阻断），**从检材的独立副本启动**，并明确声明该环境产物与本案证据链无关联、仅作行为参考。

这条路径拿不到"真实网络下的行为"，但它拿到的东西**是可复现、可解释、且不污染证据链的**——而这三点在证据价值上，比一次真实的但无法自证的连接更高。

## 六、扩展阅读方向

下面四组方向，按你在仿真这条路上会撞到什么排。


**先给一个判断标准**：本板块两条路线的分界是"**问题能不能静态回答**"。能用 [只读挂载与安全接入](imaging-mount-simulate-read-only-mounting.md) 与解析器回答的，不要启动系统。

只有"必须让程序实际运行才能观察到"的问题才值得上仿真——比如密钥什么时候被解密、注入代码在内存里长什么样、启动时哪些自启项被触发。下面第一组就是为了帮你把这个判断做扎实。

**第一组：前置基础——三块必须先有的能力**

- [只读挂载与安全接入](imaging-mount-simulate-read-only-mounting.md) —— **本篇最重要的前置判断**。那篇是"能不启动就不启动"的安全路线，本篇是"必须启动时怎么做"。先读那篇的 2.1 三条路径分级，你会发现很多问题根本不需要仿真——用启动系统去回答一个能静态回答的问题，是用最高的风险换最低的收益。
- [证据格式与转换](../imaging-acquire/imaging-acquire-evidence-image-formats.md) —— **虚拟化平台不读 RAW，也不直接读 E01**。VMDK / VHDX 的转换在这里，而"转换不改变内容、且必须用哈希证明"那条原则同样适用于本篇的第 1 步。稀疏 VMDK 的 backing file 链特性也在那篇。
- [取证装备与写保护器](../../fundamentals/fundamentals-practice/fundamentals-practice-forensics-equipment-and-write-blockers.md) —— 仿真工作站本身的硬件选型与耗材。仿真环境的磁盘会被反复读写，SSD 寿命与散热都是实际问题。

**第二组：同层深入——三个平台的差异与 Windows 特例**

- [Windows Server 环境仿真](imaging-mount-simulate-windows-server.md) —— **最需要提前知道的一篇**。域控与 IIS 检材在仿真时如果接了内网，缓存的域凭据会让这台机器在企业内网里"复活"并重新获得权限——不是被黑，是它本来就是域成员。身份类仿真的隔离要求比 Linux 侧高一个量级。
- [Docker 镜像层与 overlay2 解析](../../server/server-docker/server-docker-overlay2.md) —— **"分层"这个抽象的另一种语义**。虚拟机的差分盘与容器的 overlay2 都是"上层覆盖下层"，但虚拟机的差分盘是取证工具（用完就丢），容器的层是业务数据（本身就是证据）。这个对照能帮你理解差分盘为什么可以随便扔，也解释了为什么快照树是栈结构（LIFO）——**有子快照时父快照不能直接删**。
- [Volume 与绑定挂载取证](../../server/server-docker/server-docker-docker-volumes-and-bind-mounts.md) —— **"宿主侧状态 vs 内部状态"的两边对照思路**，与仿真里"观察客户机行为 + 检查宿主机状态"是同一种方法论。


**第三组：工具与规范——运行态的采集与分析**

- [内存取证总览](../../memory/memory-acquire/memory-acquire-memory-forensics-overview.md) 与 [内存采集方法](../../memory/memory-acquire/memory-acquire-memory-acquisition-methods.md) —— 仿真中挂载内存采集器（WinPmem / DumpIt）是仿真最有价值的产出。已解密的凭据、解密后的恶意代码、注入的内存区域，都只能在这里看到。注意：仿真出来的内存是"程序在仿真环境中的内存"，与真实受害主机的内存不是一回事，这个区别要在报告里写清楚。
- [进程与注入检测](../../memory/memory-analyze/memory-analyze-process-and-injection-detection.md) —— 仿真里观察到的进程树、父子关系、异常模块，正是这一篇的分析对象。
- [网络流量与 PCAP 取证](../../memory/memory-network/memory-network-pcap.md) —— 仿真机的抓包与真实抓包的分析方法相同，但**结论强度分级表在这里特别重要**：仿真里"程序试图连接 C2"是观察记录，"主机向 C2 传输了数据"是需要别的证据支撑的结论。**两者的措辞差别很大。**
- [取证流程与原则](../../fundamentals/fundamentals-process/fundamentals-process-five-stage-forensics-process.md) —— 仿真实验的留痕要求：录屏、命令日志、快照点命名规范、以及"什么算证据什么算观察记录"的界线。**本篇第四章 4.4 组给的是这套要求的落地模板。**

**第四组：判据与反例——环境会不会骗你**

仿真最大的风险不是证据被毁，而是**你观察到的现象是环境造成的，不是检材本身**。

- [反取证手法与时间戳篡改检测](../../fundamentals/fundamentals-concepts/fundamentals-concepts-anti-forensics-and-timestamp-tampering.md) —— **虚拟机检测**是这一类里最实用的部分。恶意程序发现自己在虚拟机里会改变行为：不执行、不解密、不外联。你在仿真里观察到的"程序很安静"可能是检测的结果，而不是程序无害。 读它是为了知道这个盲点在哪。
- [取证概念与分类](../../fundamentals/fundamentals-concepts/fundamentals-concepts-digital-forensics-concepts.md) —— **"观察记录"与"证据"的分类差别**。仿真的产出属于前者：它依赖于你的环境配置，所以它证明的是"在该环境下该程序如此表现"，而不是"该程序在被控主机上如此表现"。
- [合规授权与法律边界](../../fundamentals/fundamentals-practice/fundamentals-practice-legal-authorization-and-boundaries.md) —— **"让可疑程序在你的机器上执行"这件事本身需要授权**，尤其是当仿真机可能短暂联网、或者委托方要求验证程序的外部行为时。授权书里覆盖的是"分析"还是"执行"，字眼差别很关键。

**说明**：**仿真的产出是观察记录，不是证据。**

这个区分不是措辞上的洁癖。它决定了报告里哪部分能作为结论主张、哪部分只能作为辅助说明。

第三章 3.6 步的录屏与归档、第四章 4.4 组的记录要求，全部是为了让这份观察记录可复核。

而"永远不勾 Consolidate"这一条，是本篇唯一一条"做错了就不可挽回"的纪律。
